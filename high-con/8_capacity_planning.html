容量评估与规划

2026/9/30大约 14 分钟

容量评估与规划

前置阅读：并发参数调优

容量规划回答三个问题：要扛多少流量、单机能扛多少、需要多少机器，没有容量评估的系统要么资源浪费严重，要么在大促当天被打挂。本篇讲从业务指标推出峰值 QPS、单机压测与机器数计算、全链路压测与影子库，以及用水位监控持续守住容量。

一、流量估算方法

先从业务指标推出峰值 QPS，再用历史数据修正。 峰值而不是均值，决定了系统要准备多少容量。

容量规划各环节与本篇位置：

环节回答的问题本篇位置
流量估算峰值 QPS 是多少第一节
单机压测一台机器能扛多少第二节
机器数计算需要多少台、怎么放第三节
存储估算数据要多大空间、要不要分表第四节
全链路压测整条链路是否真的扛得住第五节
大促预案活动前后做什么第六节
水位与监控上线后如何持续守住容量第七节

1、从业务指标推导峰值 QPS

步骤公式说明
1. 日活DAU来自产品 / 运营数据
2. 日请求量DAU × 人均操作次数 × 每次操作的接口调用数一次"打开首页"可能触发 5 ~ 10 个接口
3. 平均 QPS日请求量 / 86400或按有效时长（如 12 小时 = 43200s）计算更准确
4. 峰值 QPS平均 QPS × 峰值系数日常峰值系数 2 ~ 5；大促 / 秒杀可达 10 ~ 100

二八原则也常用于估算峰值：80% 的请求集中在 20% 的时间内，峰值 QPS ≈ 日请求量 × 80% / (86400 × 20%)，约为平均值的 4 倍。

2、完整示例：电商商品详情服务

项目数值计算
DAU500 万—
人均浏览商品详情20 次—
每次详情页调用本服务1 次聚合接口
日请求量1 亿500 万 × 20 × 1
平均 QPS≈ 11571 亿 / 86400
日常峰值 QPS≈ 4600二八原则 ≈ 平均 × 4
大促峰值 QPS≈ 4.6 万日常峰值 × 10（历史大促数据）

读写拆分估算：若下单转化率 2%，则下单峰值 ≈ 4.6 万 × 2% ≈ 920 TPS，这是订单库需要承载的写入量（再乘以每单写入的 SQL 条数）。

3、依据历史数据修正

公式估算只是起点，更可靠的是历史数据：

  • 取过去同类活动的峰值与同期日常峰值之比，作为本次峰值系数
  • 按业务增长率（如同比 +50%）放大
  • 关注瞬时峰值：秒杀开始的前 1 秒流量可能是分钟均值的数十倍，按分钟监控数据估算会严重低估

二、单机能力评估

单机能扛多少 QPS 只能压测得出，不能靠理论推算；容量点取"满足 SLA 且留有余量"的值，而不是压到崩溃的极限。

步骤要点
环境与生产同规格机器、同版本、相近的数据量；下游依赖真实或按生产 RT 模拟
场景按真实流量比例混合接口，而不是只压单接口
阶梯加压逐步提升并发，记录 QPS、P99、错误率、CPU
确定容量点取 P99 满足 SLA 且 CPU ≤ 70% 时的 QPS
瓶颈确认容量点出现时的瓶颈资源（CPU / 线程 / 连接池 / 下游）

示例结果：8C16G 实例，混合场景下 P99 < 100ms、CPU 70% 时 QPS = 1500，记为单机容量 1500。

压测工具（JMeter、wrk、Gatling）见 性能测试；压测过程中各层参数的调整见 并发参数调优。单机压测证明不了整条链路，链路级验证见第五节。

三、机器数计算

机器数 = ⌈峰值 QPS / 单机 QPS × 估算误差系数 × 故障冗余系数⌉，最后再按可用区取整并核算下游。

冗余来源说明典型取值
容量点余量单机容量已按 CPU 70% 水位取值已包含在单机 QPS 中
估算误差流量预估不准、突发热点1.2 ~ 1.5
故障冗余部署在 N 个可用区、容忍 1 个可用区故障时，剩余 N−1 个要扛住全部流量N / (N − 1)：2 个可用区为 2，3 个为 1.5，4 个约 1.33

单可用区部署时，故障冗余通常按 N+1（多准备 1 台或若干台）考虑。

接上例：大促峰值 4.6 万 QPS，单机 1500 QPS，部署在 3 个可用区，要求任一可用区故障仍能扛住峰值。

步骤计算结果
基础机器数46000 / 1500 ≈ 30.7至少 31 台
故障冗余（3 个可用区，系数 1.5）剩余 2 个可用区要扛 30.7 台的量，每个可用区 ≥ ⌈30.7 / 2⌉ = 16 台3 × 16 = 48 台
验证任一可用区故障，剩余 32 台 × 1500 = 48000 QPS ≥ 46000满足
再叠加估算误差 1.2（可选）每个可用区 ≥ ⌈30.7 × 1.2 / 2⌉ = 19 台3 × 19 = 57 台

别忘了下游：应用扩到 48 台后，DB 连接总数 = 48 × 单实例连接池大小，需核算是否超过 max_connections × 80%（见 并发参数调优）；Redis、MQ 同理。容量规划必须全链路评估，瓶颈往往在最薄弱的那一环。

四、存储容量估算

总容量 = 日增量 × 保留天数 × 副本数 × (1 + 预留比例)，同时检查单表行数是否超过分表经验值。

项目公式
单行大小各字段长度之和 + 索引开销（InnoDB 二级索引通常额外 30% ~ 100%）
日增数据量日写入行数 × 单行大小
总容量日增量 × 保留天数 × 副本数 × (1 + 预留比例)

示例：订单表

项目数值
日订单量100 万
单行 + 索引约 1 KB
日增量≈ 1 GB
在线保留 1 年（冷数据归档）≈ 365 GB
1 主 2 从 + 30% 预留≈ 365 × 3 × 1.3 ≈ 1.4 TB
单表行数3.65 亿，远超单表 2000 万行经验值 → 需分表（如 32 张表，单表约 1100 万行）

Redis 容量同理：key 数量 × (key 长度 + value 长度 + 约 50 ~ 100 字节元数据开销)，并预留 30% 以上内存给 fork 持久化与碎片。分表规划见 数据层扩展，冷数据归档见 数据冷热分离。

五、全链路压测与影子库

单机压测只能证明一台机器的容量，真正的瓶颈常在网关、中间件、数据库、第三方这些共享环节。全链路压测在生产环境用真实链路跑压测流量，同时保证压测数据不污染生产数据。

关键问题解决手段
如何区分压测流量流量染色，并在全链路透传
压测数据写到哪里影子库 / 影子表 / 影子 key / 影子 topic
不能压的下游怎么办Mock / 挡板
压完的数据怎么办数据隔离与清理
压出问题怎么办分级加压、实时监控、熔断开关

1、流量染色与透传

在入口给压测请求打上标记，之后每一跳都要把标记带下去，任何一处丢失都会让压测数据写进生产库。

环节透传方式
入口（网关）压测平台发出的请求带 X-Stress-Test: 1 等请求头；网关校验来源（签名或白名单），外部请求带该头一律剥离
进程内写入上下文（ThreadLocal）；线程池切换时用 TransmittableThreadLocal 等方式传递
RPC / HTTP 调用放入请求头或 RPC attachment，或借助链路追踪的 Baggage 传播
MQ写入消息属性（header），消费端取出后恢复上下文
定时任务 / 异步回调无法从请求继承，需要在任务数据上记录压测标记
/** 入口过滤器：识别压测标记并放入上下文，后续数据源、缓存、MQ 路由据此判断 */
public class StressTagFilter extends OncePerRequestFilter {

    public static final String HEADER = "X-Stress-Test";

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        StressContext.set("1".equals(request.getHeader(HEADER)));   // 基于 TransmittableThreadLocal
        try {
            chain.doFilter(request, response);
        } finally {
            StressContext.clear();                                    // 防止线程复用时标记残留
        }
    }
}

2、影子库与影子表

压测流量的读写全部路由到与生产隔离的影子存储，结构与生产一致，数据是脱敏或构造的。

存储隔离方式说明
数据库影子库（同实例或独立实例的另一个库）或影子表（如 shadow_t_order）影子库隔离更彻底；影子表改造小，但与生产共享实例资源
缓存影子 key 前缀，如 shadow:item:1001注意影子 key 同样占用生产 Redis 内存，需设置 TTL
MQ影子 topic，或同 topic 带压测属性由消费端分流影子 topic 需配套影子消费组
日志 / 监控打压测标签压测指标单独统计，不触发生产告警、不进入业务报表
/** 按压测标记路由数据源：压测流量走影子库 */
public class StressRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return StressContext.isStress() ? "shadow" : "primary";
    }
}

ShardingSphere 也提供影子库功能，可按列值或 Hint 把压测 SQL 路由到影子库，见 分库分表与中间件。影子库要提前按生产数据量级准备数据，否则压出来的是"小表性能"。

3、下游 Mock 与挡板

支付、短信、物流等第三方和不参与本次压测的外部系统不能真实调用，用挡板返回模拟结果。

  • 挡板按压测标记生效：压测流量返回模拟响应，正常流量照常调用
  • 模拟响应要注入与生产相近的 RT（如 P99 200ms），否则上游线程占用时间被低估，压测结果偏乐观
  • 挡板本身要能扛住压测量级，避免挡板成为瓶颈

4、压测数据隔离与清理

  • 专用数据：压测账户、商品、店铺使用独立 ID 段或标记字段，与真实用户可区分
  • 业务隔离：压测订单不参与结算、对账、推荐、BI 报表；风控与营销系统识别并跳过压测数据
  • 清理：压测结束后清空影子表 / 影子 key / 影子 topic，或按标记批量删除；清理脚本与压测脚本一起维护
  • 兜底检查：在生产库定期扫描压测 ID 段，发现压测数据写入生产表立即告警并排查透传丢失点

5、生产压测风险控制与熔断开关

生产压测的首要目标是不影响真实用户，必须能随时一键停止。

措施做法
时间窗口选业务低峰期，提前通知相关团队与值班人员
分级加压按目标量的 10% → 30% → 50% → 100% 逐级加压，每级观察稳定后再加
实时监控同时盯压测流量与真实流量的 RT、错误率，以及核心资源水位
自动熔断真实流量 P99 或错误率超阈值、核心资源水位超过设定值（如 80%）时，压测平台自动停止发压
手动熔断开关配置中心全局开关，打开后网关直接拦截所有带压测标记的请求
预案事先准备扩容、限流、降级预案，压测中发现瓶颈可当场验证

六、大促预案

大促准备的主线是"估算 → 扩容 → 压测验证 → 预热 → 值守 → 复盘"，时间节点提前排好。

阶段事项
T-30 天流量预估；全链路压测找瓶颈；确定扩容清单（应用、DB、Redis、MQ 分区）
T-7 天完成扩容并再次压测验证；梳理降级开关与限流阈值；封网（冻结非必要变更）
T-1 天缓存预热（活动商品、库存、配置）；检查降级开关可用；值班与应急联系人就位
大促中实时监控水位；按预案逐级降级；热点探测与动态限流
大促后分批缩容；复盘峰值、瓶颈与预案执行情况，沉淀下次的峰值系数

降级开关梳理（按业务优先级）：

优先级功能降级方式
P0 核心下单、支付、库存不降级，限流保护
P1 重要商品详情、购物车降级为静态兜底数据 / 延长缓存
P2 次要评论、推荐、足迹直接关闭，返回空
P3 非必要积分、成长值、消息通知异步化延后处理

降级策略与开关实现见 降级，限流配置见 限流与过载保护，缓存预热见 缓存架构设计，热点探测见 热点问题。

七、容量水位与监控

容量规划不是一次性工作：上线后持续监控实际使用与容量上限的比值（水位），没有监控，扩容、调优、容量规划都无从下手。

1、监控关键指标

类别指标关注点
吞吐QPS / TPS与容量上限对比，计算水位
延迟P99 / P999 响应时间均值会掩盖长尾，看分位数
错误5xx / 超时比例突增通常是容量或依赖瓶颈
JVMGC 频率与停顿、堆使用率Full GC 会导致瞬时吞吐下跌
线程池活跃线程数、队列积压、拒绝次数队列持续积压 = 处理能力不足
依赖连接池活跃数 / 等待数、Redis / DB RT瓶颈常在下游而不是本服务

2、规划水位

水位 = 当前峰值 / 容量上限，容量上限来自压测：单机容量点 × 实例数（弹性伸缩时按 HPA maxReplicas 计算），下游组件按各自压测上限计算。

水位状态动作
< 50%健康可评估缩容
50% ~ 70%正常关注增长趋势
70% ~ 85%预警启动扩容评估：调高 maxReplicas、下游扩容、申请资源
> 85%危险立即扩容，准备限流降级

规划水位与扩容触发线不是一个口径

  • 扩容触发线：HPA 按单个 Pod 的 CPU 利用率自动扩缩，目标值取 60%（见 水平扩展与无状态化），低于单机容量点的 70%，是为了给扩容过程（调度、拉镜像、启动、预热通常需要分钟级）留出余量。它是分钟级、自动的。
  • 规划水位：按 QPS 与集群容量上限计算，用于天 / 周级的容量预算、maxReplicas 设定、下游扩容与资源采购。它是人工决策的。

HPA 能把单 Pod CPU 稳在 60%，但扛不住"副本数已到 maxReplicas"或"数据库先到顶"——这正是规划水位要提前发现的。

3、各资源的水位指标

资源水位指标告警参考
应用QPS / 单机容量、CPU、线程池活跃率CPU > 70% 持续 5 分钟
数据库QPS / TPS、连接数使用率、磁盘使用率连接数 > 80%；磁盘 > 75%
Redis内存使用率、单分片 QPS、带宽内存 > 75%；单分片 QPS 显著高于其他分片（热点）
MQ消费延迟、磁盘使用率Lag 持续增长

告警要区分趋势预警（按周增长率预测何时触顶，给扩容留出采购周期）与实时告警（突发流量）。指标采集、链路追踪与告警体系见 可观测性、指标监控、告警。

小结

  • 流量估算看峰值不看均值：DAU → 日请求量 → 平均 QPS → 峰值系数，再用历史数据修正，警惕秒级瞬时峰值
  • 单机容量只能压测得出，取"P99 满足 SLA 且 CPU ≤ 70%"的点；机器数按可用区冗余 N / (N − 1) 放大并取整，同时核算下游连接数
  • 单机压测证明不了链路，全链路压测靠流量染色透传 + 影子库表 + 下游挡板 + 数据清理 + 熔断开关保证不污染生产
  • 大促按 T-30 / T-7 / T-1 排好扩容、压测、预热与降级开关
  • 上线后用水位持续守住容量：HPA 60% 负责分钟级弹性，规划水位负责天 / 周级预算，两者口径不同
