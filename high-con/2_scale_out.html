水平扩展与无状态化

前置阅读：接入层架构

水平扩展是高并发的第一原则：流量翻倍时，靠加机器而不是重写系统来扛。本篇讲容量线性提升的前提——服务无状态、流量均匀分发、有状态组件可分片，以及自动扩缩容。

一、垂直扩展 vs 水平扩展

先垂直、后水平，但应用层从第一天就保持无状态。

对比项垂直扩展（Scale Up）水平扩展（Scale Out）
方式换更强的机器（CPU、内存、SSD）加更多同构机器
改造成本几乎为零，代码不用改需无状态化、负载均衡、数据分片
上限受单机硬件天花板限制接近线性，受共享资源（DB、锁）限制
成本曲线高配机器价格非线性上涨普通机器，成本近似线性
可用性单点，机器挂即服务挂多副本天然冗余
适用早期业务、数据库主库、短期应急应用层、缓存层、分片后的存储层

业务早期一台 16C32G 往往比 8 台 2C4G 更省心；单机接近上限或需要高可用时，再投入水平扩展改造。应用无状态几乎没有额外成本，却决定了后续能否平滑扩容。

二、无状态化

无状态服务：任意请求路由到任意实例，结果一致；实例可随时增删，不需要数据迁移。

1、常见的"状态"及外置方案

状态问题外置方案
HTTP Session用户请求换了机器即丢失登录态Redis 集中存储（Spring Session）或 JWT 无状态令牌
本地文件（上传、导出）其他实例读不到对象存储（OSS / S3 / MinIO）
本地内存计数、限流多实例各算各的，总量失控Redis 计数 / 分布式限流
本地定时任务多实例重复执行分布式调度（XXL-JOB）或分布式锁
本地缓存实例间数据不一致允许短暂不一致 + 广播失效（见两级缓存（L1 + L2））
WebSocket 长连接消息需要推到持有连接的实例连接注册表 + MQ 广播 / 路由（见接入层架构）

Session 外置的完整方案对比（粘性会话、Session 复制、集中存储、Token）见 分布式会话。

2、Spring Session 外置到 Redis

会话外置的依赖（Boot 4 为 spring-boot-starter-session-data-redis）、配置（spring.session.data.redis.*）与 Redis 键结构见 分布式会话 · Spring Session + Redis。

3、无状态化检查点

  • 代码中是否有 static 可变集合保存业务数据
  • 是否依赖 HttpSession 存储大对象（外置后每次请求都要序列化传输）
  • 是否写本地磁盘并假设下次还能读到
  • 定时任务、MQ 消费是否能容忍多实例并行
  • 实例启动是否依赖人工配置（应从配置中心拉取）

三、服务拆分

拆分让流量特征不同的模块独立扩容，避免"一个模块的流量拖垮整个应用"。

拆分原则说明
按业务域拆分用户、订单、库存、支付各自独立
读写分离部署商品详情读服务与商品管理写服务分开
按状态区分无状态服务水平扩展，有状态服务垂直扩展或分片
按流量特征隔离峰值差异大的模块单独部署，如秒杀服务独立集群

单体只能整体扩容：10 倍流量只落在"商品详情"时，也要把整个应用扩 10 倍；拆分后只需扩容商品读服务。拆分粒度与边界划分见 服务拆分。

四、流量分发

水平扩展的前提是流量能均匀分发到各实例。入口分层（DNS / CDN / 四层 / 七层）见 接入层架构，负载均衡算法与健康检查见 负载均衡。

扩展视角下的三个注意点：

  • 七层网关本身要能水平扩展，前面挂四层负载均衡
  • 慎用一致性哈希 / IP Hash 做"伪粘性"，会让热点用户集中到单实例
  • 新实例上线要预热（逐步放量），避免 JIT 未编译、连接池未建立时被打满

五、自动扩缩容（HPA）

手动扩容响应慢，流量突增时来不及。 Kubernetes HPA 按指标自动调整副本数，期望副本数 = ceil(当前副本数 × 当前指标值 / 目标值)；计算机制、behavior 字段与完整清单见 Kubernetes · HPA，这里只讲容量策略。

1、基础配置

策略上要定四个量：

  • minReplicas：按平日峰值算出的保底实例数，扩容生效前靠它扛住突增
  • maxReplicas：按下游（DB 连接、MQ 分区）能承受的上限设，不是越大越好
  • 目标利用率：低于单机容量点，留出扩容生效前的缓冲（见下方提示）
  • 扩缩节奏：扩容快（如每 60s 最多翻倍）、缩容慢（稳定窗口 5 分钟），宁可多付几分钟资源也不要来回抖动

60% 与容量规划的 70% 不矛盾

  • 扩容触发阈值（HPA 目标 60%）：平均 CPU 超过它就开始加副本。它必须低于单机容量点，因为新 Pod 从调度到就绪需要 30 秒到数分钟，这段时间老实例要靠余量扛住增长。
  • 规划水位（单机容量点 70%）：压测时 P99 满足 SLA 且 CPU ≤ 70% 的 QPS，用来算机器数，见 容量评估与规划。

两者的差值就是"扩容生效前的缓冲"。流量增长越陡、启动越慢，HPA 目标要设得越低。

2、指标选择

指标适用性说明
CPU 使用率计算密集型服务首选需要正确设置 resources.requests，否则使用率无意义
内存使用率不适合 JVM 服务堆扩张后通常不归还操作系统，容易只扩不缩
QPS / 在途请求数IO 密集型服务CPU 很低但线程池已满时，CPU 指标感知不到；通过 Prometheus Adapter 或 KEDA 接入
MQ 积压量异步消费服务按 Lag 扩容消费者（Kafka 消费者数受分区数上限约束）

3、局限与应对

问题说明应对
扩容有延迟拉镜像 + JVM 启动 + 预热，通常 30 秒到数分钟大促前提前手动扩容；保持合理的 minReplicas
就绪过早Pod 刚启动就接流量，JIT 未编译时 RT 偏高readinessProbe 在预热完成后才返回成功
下游扛不住应用扩了 10 倍，DB 连接数也翻 10 倍扩容前核算连接总量 = 实例数 × 单实例池大小，见 并发参数调优
缩容抖动流量波动导致副本反复增减设置缩容稳定窗口；配合优雅停机，见 优雅上下线与变更

六、有状态服务的扩展

数据库、缓存、MQ 等有状态组件无法简单"加机器"，核心手段是分片：把数据按某个键切分到多个节点，每个节点只负责一部分。

组件分片方式扩容方式
Redis Cluster16384 个哈希槽分配到各主节点新增节点后迁移槽位
KafkaTopic 分为多个 Partition增加 Partition（已有数据不迁移，会打乱 key 与分区的映射）
MySQL分库分表，按分片键路由数据迁移 + 双写，成本最高
Elasticsearch索引分为多个 Primary Shard主分片数创建后不可改，需 reindex 或 split
路由策略做法特点
取模hash(key) % N简单均匀，但 N 变化时几乎所有数据要迁移
范围按 ID 或时间区间扩容只需新增区间，但易产生写热点
一致性哈希 / 虚拟槽哈希环或固定槽位映射扩容只迁移部分数据，见 一致性哈希

数据库分片的具体方案见 数据层扩展。

七、水平扩展检查清单

  • [ ] 应用实例无本地状态，任意实例可随时下线
  • [ ] Session / Token 集中存储或使用无状态令牌
  • [ ] 文件存储使用对象存储
  • [ ] 定时任务使用分布式调度，MQ 消费支持多实例并行且幂等
  • [ ] 入口层（网关、Nginx）可水平扩展，前置四层负载均衡
  • [ ] 新实例上线有预热，下线有优雅停机（摘流量 → 等待在途请求 → 退出）
  • [ ] HPA 指标与服务瓶颈匹配，目标值低于单机容量点，min / max 副本数合理
  • [ ] 核算扩容后下游资源（DB 连接数、Redis 连接数、MQ 分区数）是否足够
  • [ ] 有状态组件已规划分片方案与扩容路径

小结

  • 容量线性扩展的前提是应用无状态：Session、文件、计数、定时任务全部外置
  • 服务拆分让流量特征不同的模块独立扩容，入口分发见接入层
  • HPA 目标值（如 CPU 60%）要低于规划水位（70%），给扩容生效留出缓冲；JVM 服务不要用内存指标扩容
  • 扩容应用前先核算下游连接数，否则压力只是转移到数据库
  • 有状态组件靠分片扩展，路由策略决定扩容时的迁移成本
