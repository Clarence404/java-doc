数据层扩展

参考链接：ShardingSphere 官方文档 · MySQL Replication

应用层无状态后可以随意加机器，最终瓶颈几乎总是落在数据库：单机 MySQL 通常能承载数千 TPS、上万 QPS，单表数据量超过千万行后索引与维护成本明显上升。数据层扩展按改造成本从低到高依次是：缓存 → 读写分离 → 冷热分离 → 垂直分库 → 水平分表 → 引入专用存储。

一、读写分离

主库负责写入，从库负责查询，利用主从复制将读压力分散到多个从节点。

适用前提：读多写少，且读流量是瓶颈。读写分离不能提升写能力，写瓶颈需要分库分表。

1、实现方式

方式代表优点缺点
应用层（客户端）ShardingSphere-JDBC、AbstractRoutingDataSource无额外组件，性能好与语言绑定，每个应用都要配置
代理层ShardingSphere-Proxy、MySQL Router、ProxySQL对应用透明，多语言多一跳网络，代理需高可用
云数据库RDS 读写分离地址开箱即用依赖云厂商

ShardingSphere 读写分离配置见 数据库中间件 - 读写分离配置。

2、主从延迟处理策略

MySQL 复制默认异步，从库通常落后毫秒级，大事务、从库负载高时可达秒级甚至更久。写后立即读可能读到旧数据。

策略做法适用场景
强制走主库对一致性要求高的查询显式指定主库（Hint）支付后查余额、下单后查订单
写后窗口内读主用户写操作后 N 秒内（如 Redis 标记 3s）的读请求路由到主库用户修改资料后立即查看
缓存兜底写 DB 同时写缓存，读优先读缓存读多、可缓存的数据
业务容忍前端提示"处理中"或延迟跳转发帖、评论等弱一致场景
等待 GTID读从库前 WAIT_FOR_EXECUTED_GTID_SET 等待复制到位强一致但仍想分流读
半同步复制至少一个从库收到 binlog 才返回降低数据丢失风险，并不消除读延迟
// ShardingSphere：本次线程内的查询强制路由到主库
try (HintManager hint = HintManager.getInstance()) {
    hint.setWriteRouteOnly();
    return accountMapper.selectBalance(userId);
}

延迟原因与并行复制优化见 MySQL 主从复制 - 主从延迟与并行复制。

二、分库分表

当单库写入压力过大、单表数据量过大时，通过分库分表将数据拆分。

1、垂直分库与水平分表

分库（垂直分库）：按业务域拆分，用户库、订单库、商品库各自独立，与服务拆分一一对应。

分表（水平分表）：同一业务的大表按规则（如 userId % 16）拆成多张表，分散到多个库。

拆分方式解决问题代价
垂直分库不同业务互相争抢连接、IO跨库 JOIN 变为服务调用，跨库事务
垂直分表大字段拖慢行扫描（如商品描述）查询需要两次或 JOIN
水平分表（单库）单表行数过大，索引树过深不解决单库资源瓶颈
水平分库分表单库写入、连接、存储瓶颈分片键约束、跨分片查询、分布式事务、扩容迁移

何时考虑水平拆分（经验值，需结合压测）：单表超过 2000 万行或 50GB；单库写 TPS 接近压测上限；单库存储接近磁盘或云实例上限。能用归档、冷热分离解决的，优先不拆。

2、分片键选择

分片键决定了数据分布与查询路由，选错几乎无法低成本修正。

原则说明
覆盖核心查询80% 以上的查询条件带分片键，否则会广播到所有分片
分布均匀避免大商家、大 V 用户集中到一个分片（数据倾斜）
不可变分片键修改意味着数据迁移
关联表同键订单表与订单明细表用同一分片键，保证同分片 JOIN（绑定表）

多维度查询的常见做法（以订单为例，按 user_id 分片，商家需按 seller_id 查）：

  • 基因法：把 user_id 的低几位嵌入 order_id，按 order_id 查询也能定位分片
  • 异构索引表：按 seller_id 再冗余一份（通过 Binlog / MQ 同步），牺牲存储换查询
  • 同步到 ES：复杂条件、运营后台查询统一走 ES

3、分布式 ID

分表后不能再依赖数据库自增主键，需要全局唯一且趋势递增的 ID（有利于 B+ 树顺序写入）：

方案特点
雪花算法（Snowflake）64 位，本地生成，趋势递增；依赖时钟
号段模式（Leaf-Segment）DB 批量取号段，性能高，需双 Buffer 防抖动
UUID无序，作为 InnoDB 主键会导致页分裂，不推荐

详见 分布式 ID。

4、跨分片查询

查询类型问题处理方式
不带分片键的查询广播到全部分片，N 倍开销异构索引表 / ES；限制仅后台使用
跨分片分页 LIMIT 10000, 10每个分片都要取前 10010 行再归并禁止深分页，改为游标分页（WHERE id > ? LIMIT 10）
跨分片聚合 / 排序中间件内存归并预计算汇总表；交给 OLAP（ClickHouse / Doris）
跨分片 JOIN不支持或性能极差绑定表同键分片；小表广播；应用层组装
跨分片事务本地事务失效尽量同分片；否则最终一致（见异步与削峰）

5、扩容迁移

分片数从 N 扩到 2N 是分库分表中最复杂的操作，常见的平滑迁移流程：

  1. 双写：新旧两套分片同时写（以旧库为准），可通过应用双写或 Binlog 同步（Canal / DTS）
  2. 历史数据迁移：全量拷贝历史数据到新分片，增量由双写 / Binlog 追平
  3. 校验：对比新旧数据行数与抽样内容，修复差异
  4. 灰度切读：按比例把读流量切到新分片，观察一段时间
  5. 切写：以新库为准，停止写旧库，保留回滚窗口后下线

降低扩容频率的技巧：一开始就规划足够的逻辑分片（如 1024 张表分布在 8 个库），扩容时只迁移整张表到新库，而不是重新哈希每一行。

ShardingSphere 分片配置、分片算法与内置迁移工具见 数据库中间件，Binlog 同步工具见 CDC 工具。

三、冷热分离

大量数据是"写入后很少再访问"的冷数据（如 1 年前的订单），它们占用存储、拖慢热数据的索引与备份。冷热分离把冷数据迁移到低成本存储，热库保持小而快。

对比项冷热分离分库分表
拆分维度时间 / 访问频率分片键哈希 / 范围
改造成本低，业务查询基本不变高，全链路改造
解决问题数据量增长、存储成本写入能力、连接数

很多系统在做分库分表之前，先做归档与冷热分离就足以撑过很长时间。判断标准、迁移策略与存储选型见 数据冷热分离。

四、引入 NoSQL / ES 分担查询

关系库擅长事务与点查，不擅长全文检索、复杂多条件筛选、海量时序写入。让专用存储承担专用查询，MySQL 只保留核心事务数据：

场景痛点引入存储同步方式
商品搜索、多条件筛选LIKE、多字段组合索引失效ElasticsearchBinlog → Canal → MQ → ES
运营报表、实时统计大表聚合拖垮主库ClickHouse / DorisCDC 实时同步
用户画像、宽表列多且稀疏HBase / 列存离线 + 实时
监控、IoT 指标海量时序写入InfluxDB / TDengine直接写入
计数、排行、会话高频读写小数据Redis应用双写 / 异步回写

注意：异构存储是最终一致的，同步延迟通常在秒级，业务要能容忍"刚下的单搜不到"。各类存储的特点见 搜索数据库、列式数据库。

五、方案选型

瓶颈现象优先方案次选方案
读 QPS 高，数据可缓存缓存（见缓存架构设计）读写分离
读 QPS 高，数据实时性要求高读写分离 + 主从延迟策略缓存 + 主动失效
单表数据量大，但大多是历史数据冷热分离 / 归档分区表
不同业务争抢同一个库垂直分库—
写 TPS 接近单库上限水平分库分表NewSQL（TiDB 等分布式数据库）
复杂搜索、多维筛选Elasticsearch异构索引表
大数据量聚合分析ClickHouse / Doris预计算汇总表

分布式数据库（TiDB、OceanBase）可以免去应用层分片的复杂度，代价是运维体系与成本，见 分布式数据库。
