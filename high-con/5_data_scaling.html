数据层扩展

数据层扩展

本篇目标：按改造成本从低到高掌握数据层的扩展路径，知道每一步解决什么瓶颈、代价是什么、何时该走下一步。

前置阅读：异步与削峰

参考链接：ShardingSphere 官方文档 · MySQL Replication

应用层无状态后可以随意加机器，瓶颈最终几乎都落在数据库：单机 MySQL 通常能承载数千 TPS、上万 QPS，单表超过千万行后索引与维护成本明显上升。数据层扩展按改造成本从低到高依次是：

步骤解决的瓶颈改造成本
1. 缓存读 QPS 高，数据可缓存低
2. 读写分离读 QPS 高，数据实时性要求较高低 ~ 中
3. 冷热分离数据量大，但大部分是历史数据中
4. 垂直分库不同业务争抢同一个库中
5. 水平分表 / 分库分表单表行数、单库写入与存储到顶高
6. 引入专用存储搜索、分析、时序等关系库不擅长的查询中 ~ 高

原则：能用前一步解决的，不急于走下一步。

一、缓存先行

读流量是瓶颈时，先加缓存，而不是先动数据库。 命中率 90% 的缓存等于把数据库读压力降到原来的 1/10，改造成本远低于读写分离和分片。

多级缓存分层、一致性取舍、预热与缓存三大问题见 缓存架构设计。缓存解决不了的场景是：数据实时性要求高、千人千面难以缓存、写入本身是瓶颈——这时进入下一步。

二、读写分离

主库负责写入，从库负责查询，利用主从复制把读压力分散到多个从节点。

适用前提是读多写少、读流量是瓶颈。读写分离不能提升写能力，写瓶颈需要分库分表。

1、实现方式

方式代表优点缺点
应用层（客户端）ShardingSphere-JDBC、AbstractRoutingDataSource无额外组件，性能好与语言绑定，每个应用都要配置
代理层ShardingSphere-Proxy、MySQL Router、ProxySQL对应用透明，多语言多一跳网络，代理需高可用
云数据库RDS 读写分离地址开箱即用依赖云厂商

ShardingSphere 读写分离配置见 分库分表与中间件。

2、主从延迟处理策略

MySQL 复制默认异步，从库通常落后毫秒级，大事务或从库负载高时可达秒级甚至更久，"写后立即读"可能读到旧数据。

策略做法适用场景
强制走主库对一致性要求高的查询显式指定主库（Hint）支付后查余额、下单后查订单
写后窗口内读主用户写操作后 N 秒内（如 Redis 标记 3s）的读请求路由到主库用户修改资料后立即查看
缓存兜底写 DB 同时写缓存，读优先读缓存读多、可缓存的数据
业务容忍前端提示"处理中"或延迟跳转发帖、评论等弱一致场景
等待 GTID读从库前 WAIT_FOR_EXECUTED_GTID_SET 等待复制到位强一致但仍想分流读
半同步复制至少一个从库收到 binlog 才返回降低数据丢失风险，并不消除读延迟
// ShardingSphere：本次线程内的查询强制路由到主库
try (HintManager hint = HintManager.getInstance()) {
    hint.setWriteRouteOnly();
    return accountMapper.selectBalance(userId);
}

延迟原因与并行复制优化见 MySQL 主从复制。

三、冷热分离

大量数据写入后很少再访问（如 1 年前的订单），它们占用存储、拖慢热数据的索引与备份。冷热分离把冷数据迁到低成本存储，热库保持小而快。

对比项冷热分离分库分表
拆分维度时间 / 访问频率分片键哈希 / 范围
改造成本低，业务查询基本不变高，全链路改造
解决问题数据量增长、存储成本写入能力、连接数

很多系统在分库分表之前，先做归档与冷热分离就足以撑很长时间。判断标准、迁移策略与存储选型见 数据冷热分离。

四、分库分表

单库写入压力过大、单表数据量过大，且归档解决不了时，才通过分库分表拆分数据。 先按业务垂直分库，再对仍然过大的表做水平拆分。

1、拆分方式

垂直分库：按业务域拆分，用户库、订单库、商品库各自独立，与服务拆分一一对应。

水平分表：同一业务的大表按规则（如 user_id % 16）拆成多张表，再分散到多个库。

拆分方式解决问题代价
垂直分库不同业务互相争抢连接、IO跨库 JOIN 变为服务调用，跨库事务
垂直分表大字段拖慢行扫描（如商品描述）查询需要两次或 JOIN
水平分表（单库）单表行数过大，索引树过深不解决单库资源瓶颈
水平分库分表单库写入、连接、存储瓶颈分片键约束、跨分片查询、分布式事务、扩容迁移

何时考虑水平拆分（经验值，需结合压测）：单表超过 2000 万行或 50GB；单库写 TPS 接近压测上限；单库存储接近磁盘或云实例上限。

2、分片键选择

分片键决定数据分布与查询路由，选错几乎无法低成本修正。

原则说明
覆盖核心查询绝大多数查询条件带分片键，否则会广播到所有分片
分布均匀避免大商家、大 V 集中到一个分片（数据倾斜）；不要用时间戳做哈希分片键
不可变分片键修改意味着数据迁移
关联表同键订单表与订单明细表用同一分片键，保证同分片 JOIN（绑定表）
业务语义优先选 user_id、tenant_id 等业务核心维度

多维度查询的常见做法（以订单为例，按 user_id 分片，商家需按 seller_id 查）：

  • 基因法：把 user_id 的低几位嵌入 order_id，按 order_id 查询也能定位分片
  • 异构索引表：按 seller_id 再冗余一份（通过 Binlog / MQ 同步），用存储换查询
  • 同步到 ES：复杂条件、运营后台查询统一走 ES

3、分片算法

算法做法优点缺点
哈希取模hash(key) % N分布均匀扩容需重新分布数据
范围按 ID 区间或时间（按月建表）扩容简单，范围查询友好新数据集中在最新分片，易成写热点
一致性哈希哈希环 + 虚拟节点扩容只迁移部分数据实现复杂，分布需虚拟节点调匀
映射表路由表记录 key → 分片最灵活，可单独迁移大租户多一次查询，路由表本身要高可用

一致性哈希原理见 一致性哈希，ShardingSphere 内置算法类型与配置见 分库分表与中间件。

4、分布式 ID

分表后不能再依赖数据库自增主键，需要全局唯一且趋势递增的 ID（有利于 B+ 树顺序写入）：

方案特点
雪花算法（Snowflake）64 位，本地生成，趋势递增；依赖时钟
号段模式（Leaf-Segment）DB 批量取号段，性能高，需双 Buffer 防抖动
UUID无序，作为 InnoDB 主键会导致页分裂，不推荐

详见 分布式 ID 生成。

5、跨分片查询与事务

查询类型问题处理方式
不带分片键的查询广播到全部分片，N 倍开销异构索引表 / ES；限制仅后台使用
跨分片分页 LIMIT 10000, 10每个分片都要取前 10010 行再归并禁止深分页，改为游标分页（WHERE id > ? ORDER BY id LIMIT 10）
跨分片聚合 / 排序中间件内存归并预计算汇总表；交给 OLAP（ClickHouse / Doris）
跨分片 JOIN不支持或性能极差绑定表同键分片；小表广播；应用层组装
跨分片事务本地事务失效尽量同分片；否则最终一致（本地消息表、Seata 等，见分布式事务）

6、扩容迁移

分片数从 N 扩到 2N 是分库分表中最复杂的操作，策略上要做到两点：迁移按「双写 → 历史数据迁移 → 校验对账 → 灰度切读 → 停旧写」平滑推进，每一步都有开关可回退；第一次拆分时就规划足够的逻辑分片（如 1024 张表），让扩容只搬整张表而不是重新哈希每一行。各步做法、ShardingSphere 迁移作业、预分配逻辑分片与倍数扩容的细节见 分库分表与中间件 · 平滑迁移与扩容。

Binlog 同步工具见 CDC 工具。分布式数据库（TiDB、OceanBase）可以免去应用层分片，代价是运维体系与成本，见 分布式数据库。

五、引入专用存储

关系库擅长事务与点查，不擅长全文检索、复杂多条件筛选、海量时序写入。让专用存储承担专用查询，MySQL 只保留核心事务数据。

场景痛点引入存储同步方式
商品搜索、多条件筛选LIKE、多字段组合索引失效ElasticsearchBinlog → Canal → MQ → ES
运营报表、实时统计大表聚合拖垮主库ClickHouse / DorisCDC 实时同步
用户画像、宽表列多且稀疏HBase / 列存离线 + 实时
监控、IoT 指标海量时序写入InfluxDB / TDengine直接写入
计数、排行、会话高频读写小数据Redis应用双写 / 异步回写

异构存储是最终一致的，同步延迟通常在秒级，业务要能容忍"刚下的单搜不到"。各类存储的特点见 搜索数据库、列式与 OLAP 数据库。

六、方案选型

瓶颈现象优先方案次选方案
读 QPS 高，数据可缓存缓存读写分离
读 QPS 高，数据实时性要求高读写分离 + 主从延迟策略缓存 + 主动失效
单表数据量大，但大多是历史数据冷热分离 / 归档分区表
不同业务争抢同一个库垂直分库—
写 TPS 接近单库上限水平分库分表NewSQL（TiDB 等分布式数据库）
复杂搜索、多维筛选Elasticsearch异构索引表
大数据量聚合分析ClickHouse / Doris预计算汇总表

小结

  • 扩展路径按成本排序：缓存 → 读写分离 → 冷热分离 → 垂直分库 → 水平分表 → 专用存储，能用前一步解决就不走下一步
  • 读写分离只扩读不扩写，必须配套主从延迟策略（强制读主、写后窗口读主、等待 GTID 等）
  • 分片键决定一切：覆盖核心查询、分布均匀、不可变；非分片键查询靠基因法、异构索引表或 ES
  • 一开始就规划足够的逻辑分片，扩容按"双写 → 迁移 → 校验 → 切读 → 切写"平滑进行
  • 异构存储都是最终一致，业务要能容忍秒级延迟
