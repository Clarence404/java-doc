可观测性总览

可观测性回答的是：系统出问题时，能否只凭它对外输出的信号判断发生了什么、在哪里、为什么。本模块讲平台侧——信号怎么采集、存储、查询与告警。

版本基线（2026 年 10 月）：Spring Boot 4.0 / 4.1、Micrometer 1.16 / 1.17、Micrometer Tracing 1.6 / 1.7、OpenTelemetry Java agent 2.32、Prometheus 3.15、Grafana 13.x、Loki 3.7、Tempo 3.x、Jaeger v2

一、三大信号与 Profiles

应用侧怎么打日志、怎么注册指标，分别在 日志 与 Actuator 监控 中讲，这里只链接不重复。版本要点：Boot 4 新增 spring-boot-starter-opentelemetry；OTel Java agent 2.0 起默认以 http/protobuf 协议向 4318 端口导出 OTLP；Prometheus 3 带来新版 UI、UTF-8 指标名与 OTLP 接收（另有 3.13 LTS 线）；Loki 原生接收 OTLP 日志并默认开启结构化元数据；Tempo 3.0 用新的写入架构取代了 ingester；Jaeger v2 基于 OpenTelemetry Collector 构建，v1 已于 2025-12-31 停止维护；OpenTelemetry Profiles 信号于 2026 年 3 月进入公开 Alpha。

信号回答的问题数据形态成本特征典型工具本模块
指标（Metrics）系统健康吗？趋势如何？数值时间序列：指标名 + 标签 + 时间戳 + 值存储与请求量无关，只与时间序列数（基数）有关Micrometer、Prometheus、Grafana指标监控
日志（Logs）具体发生了什么？带时间戳的离散事件，最好是结构化 JSON与请求量线性增长，是最贵的信号Fluent Bit、Loki、Elasticsearch日志体系
链路（Traces）一次请求经过了哪里，慢在哪一段？由 Span 组成的调用树，靠 traceId 串联通常需要采样Micrometer Tracing、OTel、Tempo、Jaeger链路追踪
Profiles哪段代码消耗了 CPU / 内存？带调用栈的采样数据，以火焰图呈现持续低频采样，开销可控JFR、async-profiler、Pyroscope、eBPF持续剖析与 eBPF；火焰图读法见 性能分析工具

几条使用原则：

  • 指标发现问题，链路定位位置，日志解释原因：告警来自指标（P99 升高、错误率上升），通过链路找到慢的那一跳，再看那一跳的日志和异常栈。Profiles 用于回答"代码层面为什么慢"
  • 信号之间要能互相跳转：日志带 traceId、指标带 exemplar、Span 能反查日志，没有关联字段三个后端就是三座孤岛；关联方式与字段统一见 链路追踪
  • 监控与可观测性的区别：监控针对已知问题预设看板和阈值；可观测性要求在未预料的问题出现时，仍能通过高维度的数据（标签、属性、traceId）临时下钻分析
  • 告警不是第四种信号，而是基于信号的判断规则；SLO 与燃烧速率告警的建模见 可用性度量，告警规则与路由见 告警体系

二、整体架构

一套典型的开源可观测性平台分为四层：

层职责常见选择
埋点与产生应用产生指标、Span 和日志Micrometer + Micrometer Tracing（Spring 原生方式），或 OpenTelemetry Java agent（零代码）；日志由 Logback 输出到 stdout
采集与处理接收、批处理、补充资源属性（服务名、Pod、集群）、脱敏、采样、按信号路由OpenTelemetry Collector；日志也常用 Fluent Bit / Vector 节点 Agent
存储与查询按信号特点各自存储指标：Prometheus（长期存储接 VictoriaMetrics / Thanos / Mimir）；日志：Loki / Elasticsearch；链路：Tempo / Jaeger v2；Profiles：Pyroscope
展示与告警看板、探索、跨信号跳转、告警Grafana；Prometheus 规则 + Alertmanager，或 Grafana Alerting

Spring Boot 应用有两条主路线和一个过渡选项，只选一条，不要混用导致重复埋点：

  • Micrometer 路线：spring-boot-starter-actuator 暴露 /actuator/prometheus 供 Prometheus 抓取，Micrometer Tracing 通过 OTel bridge 以 OTLP 导出 Span；Boot 4 的 spring-boot-starter-opentelemetry 把这套依赖打包好。优点是与 Spring 的 Observation API、配置属性完全对齐
  • OpenTelemetry agent 路线：-javaagent:opentelemetry-javaagent.jar 自动埋点 HTTP、JDBC、Kafka 等常见库，指标、链路、日志都走 OTLP 发往 Collector。优点是零代码、多语言统一；代价是启动变慢、与 Spring 自己的 Observation 埋点可能重叠
  • 过渡选项：OTel 社区 opentelemetry-spring-boot-starter，只用于 Boot 3 项目无法使用 agent（如原生镜像）的场景

本站立场是 Boot 4 新项目默认走 Micrometer 路线，多语言统一或要零代码覆盖时用 agent，取舍细节见 OpenTelemetry。

Collector 作为中间层的价值在于：应用只认 OTLP 一个协议，后端怎么换（Jaeger 换 Tempo、自建换云厂商）只改 Collector 配置；采样、脱敏、限流这类治理逻辑也集中在这一层做。

本地试验

Grafana 官方提供 grafana/otel-lgtm 镜像，一个容器内集成了 OTel Collector、Prometheus、Loki、Tempo、Pyroscope 与 Grafana，适合在本机跑通 order-service 的三大信号，不适合用于生产。

四、推荐阅读路径

  1. 先打好应用侧基础：读 日志（结构化日志、MDC 与 traceId）与 Actuator 监控（Micrometer 指标、Observation API），确认应用能正确产出信号。
  2. 按信号逐个建设：读 日志体系（采集链路、Loki / Elasticsearch 选型、LogQL），再读 指标监控（指标类型、PromQL、基数控制）和 链路追踪（上下文传播、采样、后端选型）。
  3. 把信号变成行动：读 告警体系，结合 可用性度量 中的 SLO 与燃烧速率，设计少而准的告警。
  4. 统一标准：读 OpenTelemetry，理解 OTLP、Collector 和语义约定，把各信号的采集收敛到一套标准上。
  5. 补上代码层视角：读 持续剖析与 eBPF，让火焰图常驻在线并与链路关联，再用 eBPF 覆盖内核与非 Java 进程。

复习时用 高频面试题 自测，答案在 可观测性面试题解答。
