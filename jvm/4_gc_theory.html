GC 原理

前置阅读：字节码执行

所有垃圾收集器都建立在同一套理论之上：用可达性分析找出垃圾，用标记-清除 / 复制 / 标记-整理回收，按分代假说组织堆，用三色标记 + 读写屏障让标记与业务线程并发。 本篇讲这套原理以及各类 GC 的触发时机，具体收集器放到下一篇。

一、如何判断对象可以被回收

JVM 采用可达性分析，而不是引用计数。

1、引用计数法（JVM 未采用）

每个对象维护一个引用计数器，计数为 0 时回收。

  • 缺陷：无法处理循环引用。A 引用 B、B 引用 A，两者都不可达，计数却都不为 0
  • Python（配合循环检测）、Swift ARC 等采用此方案，HotSpot 从未采用

2、可达性分析（JVM 采用）

从一组 GC Roots 出发沿引用链遍历，遍历不到的对象即为垃圾。GC Roots 本身不需要证明"存活"，因为它们就是程序正在使用的入口。

GC Root 类型说明
虚拟机栈中的引用各线程栈帧里的局部变量、参数
本地方法栈中的引用JNI 局部 / 全局引用的对象
类静态字段引用的对象已加载类的 static 字段（JDK 7 起静态变量随 Class 对象存于堆）
常量引用的对象如字符串常量池（StringTable）中的字符串
被 synchronized 持有的对象作为锁的监视器对象
JVM 内部引用基本类型对应的 Class 对象、常驻异常对象、系统类加载器等

局部回收时的额外"根"

只回收部分区域（如 Young GC、G1 的 Mixed GC）时，其他区域指向本区域的引用也要当作根，这就是下文"跨代引用"要解决的问题。

二、引用类型

Java 用四种引用强度，让程序参与决定对象的回收时机。

引用类型类GC 行为典型用途
强引用普通 = 赋值只要可达就不回收所有正常对象
软引用SoftReference内存不足时才回收内存敏感的缓存
弱引用WeakReference下一次 GC 发现即回收WeakHashMap、ThreadLocalMap 的 Entry key
虚引用PhantomReference不影响回收，get() 恒返回 null对象回收后收到通知，做资源清理
  • 虚引用必须配合 ReferenceQueue 使用：对象被回收后，引用对象进入队列，程序从队列中取出后执行清理
  • JDK 9 起推荐用 java.lang.ref.Cleaner（基于虚引用）替代 finalize()；DirectByteBuffer 释放堆外内存就依赖这套机制
  • 软 / 弱 / 虚引用都需要 GC 做额外的引用处理（Reference Processing），数量巨大时会拉长停顿

三、GC 算法

三种基础算法各有取舍：标记-清除有碎片，复制浪费空间，标记-整理移动成本高。 现代收集器按区域组合使用。

1、标记-清除（Mark-Sweep）

  1. 标记：从 GC Roots 出发，标记所有可达对象
  2. 清除：回收未被标记的对象，空闲空间记入空闲列表
  • 优点：实现简单，不移动对象
  • 缺点：产生内存碎片，大对象可能因找不到连续空间而提前触发 GC；传统实现中标记和清除都需要 STW（CMS 通过并发标记、并发清除缓解）
  • 应用：CMS 老年代

2、复制（Copying）

  1. 把内存分成两块，每次只使用其中一块
  2. GC 时把存活对象复制到另一块，然后整体清空当前块
  • 优点：无碎片，可用指针碰撞快速分配；存活对象少时效率极高
  • 缺点：朴素实现内存利用率只有 50%
  • 应用：年轻代。HotSpot 用 Eden + 两个 Survivor（默认 8:1:1），利用率提升到 90%

3、标记-整理（Mark-Compact）

  1. 标记：同标记-清除
  2. 整理：把存活对象向一端移动，然后清理边界外的内存
  • 优点：无碎片
  • 缺点：移动对象并更新所有引用，开销大；传统实现必须 STW
  • 应用：Serial Old、Parallel Old 老年代，以及各收集器的 Full GC

4、对比

算法碎片空间利用率是否移动对象适合区域
标记-清除有高否存活率高、不想移动对象的老年代
复制无50%（分代下 90%）是存活率低的年轻代
标记-整理无高是老年代

四、分代收集

分代的依据是两条经验假说：弱分代假说（绝大多数对象朝生夕死）和强分代假说（熬过越多次 GC 的对象越难消亡）。 于是年轻代频繁、快速地回收，老年代少回收。

1、堆的分代结构

区域默认占比存放内容回收方式
Eden年轻代的 8/10新创建的对象Young GC，复制算法，频繁、停顿短
Survivor 0 / 1年轻代各 1/10熬过 Young GC 的对象，两块轮流使用随 Young GC 一起回收
老年代默认为年轻代的 2 倍（NewRatio=2）长期存活对象、大对象标记-清除 / 标记-整理，频率低、停顿长

G1、分代 ZGC 仍然分代，但年轻代 / 老年代是逻辑上的 Region 集合，不再是固定的连续空间，详见 GC 收集器。

2、对象晋升

  1. 新对象优先在 Eden 分配（多数落在线程私有的 TLAB 中）
  2. Young GC 后存活对象复制到 Survivor，年龄 +1
  3. 年龄达到 MaxTenuringThreshold（默认 15），或触发动态年龄判断，晋升老年代
  4. Survivor 放不下的存活对象直接晋升；大对象可能直接进入老年代

晋升阈值、动态年龄判断、空间分配担保的细节见 内存结构。

3、跨代引用：记忆集与卡表

只回收年轻代时，老年代里指向年轻代的引用也是根，但不能为此扫描整个老年代。

  • 记忆集（Remembered Set）：记录"哪些外部区域有指针指向本区域"的抽象结构
  • 卡表（Card Table）：记忆集的常见实现，把老年代按 512 字节划分为卡页，某卡页中有对象引用了年轻代就把它标为"脏卡"
  • 写屏障：引用赋值时由 JIT 插入的一小段代码，负责维护卡表
  • Young GC 时只需扫描脏卡，而不是整个老年代；G1 为每个 Region 维护一个 RSet，原理相同

五、GC 的分类与触发时机

先分清三个名词：Young GC 只回收年轻代，Major GC 只回收老年代，Full GC 回收整个堆和元空间。 口语中常把 Major GC 和 Full GC 混用，排查时要以 GC 日志里的实际类型为准。

类型回收范围典型收集器
Young GC（Minor GC）年轻代所有分代收集器
Major GC（Old GC）仅老年代目前只有 CMS 的并发收集是单独回收老年代
Mixed GC年轻代 + 部分老年代 RegionG1 特有
Full GC整个堆 + 元空间（方法区）所有收集器的兜底，停顿最长

1、Young GC 的触发

  • Eden 空间不足，无法为新对象分配时触发
  • TLAB 分配失败不是直接触发条件：线程先尝试申请新的 TLAB 或在 Eden 共享区分配，只有 Eden 也放不下时才触发 Young GC

2、Full GC 的触发

  • 老年代空间不足：对象晋升或大对象直接分配时放不下
  • 元空间使用量达到高水位（初始为 MetaspaceSize），需要卸载类：Serial / Parallel 下是 Full GC，G1 通常先发起一次并发周期，回收不足再 Full GC
  • 空间分配担保失败（Serial / Parallel）：Young GC 前判断老年代可能装不下晋升对象
  • 并发收集跟不上分配：CMS 的 Concurrent Mode Failure、G1 的 Evacuation Failure 后回收仍不够
  • 显式调用 System.gc()（只是建议，JVM 可以忽略）

3、System.gc() 与 DisableExplicitGC

不要随手加 -XX:+DisableExplicitGC，它可能导致 OutOfMemoryError: Direct buffer memory。

  • DirectByteBuffer 的堆外内存要等它的 Java 对象被回收、Cleaner 执行后才释放
  • 分配直接内存时若超出 MaxDirectMemorySize，JDK 会先调用 System.gc() 触发引用处理、等待释放，再重试分配
  • 禁用显式 GC 后，这一步变成空操作；如果堆内一直没有 GC，堆外内存就回收不了，最终 OOM
  • 想避免 System.gc() 带来长时间的 Full GC 停顿，推荐 -XX:+ExplicitGCInvokesConcurrent：在 G1（以及已移除的 CMS）下把显式 GC 改为一次并发周期

提示

Netty 默认使用自己管理的池化直接内存，不依赖这条回收路径；但 NIO、部分中间件仍会用到 DirectByteBuffer，禁用前要确认。

六、STW 与安全点

STW（Stop The World）指 GC 期间暂停所有应用线程。 至少"根节点枚举"这一步必须 STW，否则扫描过程中栈上的引用还在变化，得不到一致的根集合。

  • OopMap：JIT 在特定位置记录"栈和寄存器里哪些位置是引用"，GC 据此快速枚举根，无需逐字扫描栈
  • 安全点（Safepoint）：只有在方法调用、循环回边、异常跳转等位置才记录 OopMap，线程必须跑到安全点才能停下
  • 安全区域（Safe Region）：处于 Sleep、Blocked 等状态的线程不执行代码，进入一段引用不会变化的区域后即视为已到达安全点
  • 所以 STW 的实际耗时 = 等所有线程到达安全点（TTSP）+ GC 本身的工作；长时间不含安全点的计数循环会拖慢 TTSP

七、三色标记与并发标记

标记阶段如果与业务线程并发执行，引用关系会一边被扫描一边被修改，可能把存活对象漏标而误回收。 三色标记是描述并发标记的通用模型，增量更新和 SATB 是两种防漏标方案。

1、三种颜色

颜色含义
白色尚未被 GC 访问。标记结束时仍为白色的对象就是垃圾
灰色已被访问，但它引用的对象还没全部扫描完
黑色自身和它引用的对象都已扫描完，GC 不会再回头扫描它

标记从 GC Roots 直接引用的对象开始（置灰），不断取出灰色对象、把它引用的白色对象置灰、自身置黑，直到没有灰色对象。

2、漏标的两个必要条件

只有两个条件同时成立，白色对象才会被漏标。

  1. 业务线程新增了一条从黑色对象到该白色对象的引用
  2. 业务线程删除了所有从灰色对象到该白色对象的（直接或间接）引用

黑色对象 A 不会再被扫描，灰色对象 B 原本能带到 C 的路径又被删掉，C 就一直是白色，最终被当作垃圾回收，而 A 还在引用它。

3、两种解决方案

破坏任意一个条件即可避免漏标。

方案破坏哪个条件做法代价使用者
增量更新（Incremental Update）条件一写屏障记录"黑色对象新增了指向白色对象的引用"，把该黑色对象重新置灰，重新标记阶段再扫描一遍重新标记阶段要扫描的对象可能较多CMS
原始快照（SATB，Snapshot At The Beginning）条件二写屏障在引用被删除前记录旧值，按并发标记开始时的对象图快照标记，被删的引用目标本轮一律视为存活产生更多浮动垃圾，留到下一轮回收G1、Shenandoah

ZGC 不使用 SATB，它的并发标记与并发重定位依靠染色指针和读屏障实现。

4、缩短 STW 的主要技术

技术说明使用者
并发标记标记与业务线程并发，只有初始标记、最终标记短暂 STWCMS、G1、ZGC、Shenandoah
写屏障 + 增量更新 / SATB记录并发期间的引用变化，保证不漏标CMS / G1、Shenandoah
并发整理（转移）移动对象也与业务线程并发，停顿不随堆大小增长ZGC、Shenandoah
染色指针把标记、重定位状态编码在指针的元数据位中ZGC
读屏障加载引用时检查并修正指针，使业务线程能访问正在被移动的对象ZGC（Load Barrier）、Shenandoah（LRB）

小结

  • JVM 用可达性分析判断垃圾，GC Roots 包括栈上引用、静态字段、常量、JNI、锁对象等
  • 三种算法各有取舍：年轻代用复制，老年代用标记-清除 / 标记-整理；跨代引用靠卡表 + 写屏障避免扫描整个老年代
  • 分清 Young / Major / Mixed / Full GC；Eden 不足才触发 Young GC，Full GC 回收整堆和元空间
  • DisableExplicitGC 可能导致 Direct buffer memory OOM，要避免显式 Full GC 应改用 ExplicitGCInvokesConcurrent
  • 并发标记的漏标需要两个条件同时成立：增量更新（CMS）破坏条件一，SATB（G1、Shenandoah）破坏条件二
