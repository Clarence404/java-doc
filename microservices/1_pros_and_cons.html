微服务优势与挑战

本篇目标：说清微服务是什么、与 SOA 有何不同，能从团队、业务和基础设施三方面判断「该不该拆、什么时候拆」，并掌握不做大爆炸重写的渐进迁移策略。

前置阅读：微服务总览

微服务首先是一种组织与交付方式，其次才是技术架构：它用分布式系统的复杂度，换取团队独立交付、按需扩展和故障隔离的能力。这笔交易是否划算，取决于团队规模、业务边界和基础设施成熟度。

一、什么是微服务

1、定义

微服务架构把单一应用拆成一组小的、可独立部署的服务，每个服务：

  • 围绕业务能力构建，职责单一
  • 运行在自己的进程中，拥有自己的数据存储
  • 通过轻量级机制（HTTP / gRPC / 消息队列）与其他服务通信
  • 可由一个小团队独立开发、测试、部署和扩展

2、核心原则

原则说明
单一职责每个服务对应一个业务能力，边界清晰
自治独立开发、独立部署、独立扩展，团队对服务全生命周期负责
数据去中心化每个服务管理自己的数据，不共享数据库表
为失败而设计默认远程调用会超时和失败，靠超时、重试、熔断、降级兜底（见 熔断）
基础设施自动化服务数量多，构建、部署、监控必须自动化

3、微服务 vs SOA

对比SOA微服务
通信重量级 ESB（企业服务总线）+ WS-* 协议轻量级 HTTP / gRPC / 消息队列，「智能端点、哑管道」
服务粒度粗粒度，面向企业系统集成细粒度，面向单个业务能力
数据管理常见共享数据库每个服务独立数据存储
治理集中式治理、统一技术栈去中心化治理，允许技术异构
目标跨部门、跨系统复用快速迭代、独立交付、独立扩展

可以把微服务理解为去掉 ESB 与重量级协议、把「服务」粒度降到单个业务能力的 SOA。

二、单体应用的瓶颈

单体在早期是最优解：开发、调试、部署都简单。问题出在业务和团队持续膨胀之后。

问题具体表现
复杂度失控模块间随意调用，没人能完整理解系统，改动影响面难以评估
部署风险高改一行代码也要全量打包部署，一次发布捆绑多个团队的改动
扩展受限只能整体扩容，无法只给热点模块加机器（见 水平扩展与无状态化）
故障不隔离一个模块内存泄漏或线程池打满，拖垮整个进程
技术栈锁定框架或 JDK 升级影响全局，难以局部引入新技术
协作瓶颈多团队共享一个仓库与发布窗口，合并冲突和发布排队频繁

三、微服务的优势

优势说明
独立部署每个服务单独发布，发布周期短，单次发布风险小，回滚范围小
独立扩展只对热点服务扩容，并可按服务选择不同的硬件规格
技术异构不同服务可选不同语言、框架和存储，各取所长
故障隔离非核心服务宕机不影响核心链路（前提是配好超时、熔断与降级）
团队自治团队边界与服务边界一致，减少跨团队协调
易于理解单个服务代码量小，新人只需理解自己负责的服务

四、微服务的挑战

挑战说明应对方案
分布式复杂性网络调用会超时、失败、乱序，远比本地调用复杂超时、重试、熔断、隔离（见 超时、重试与隔离）
数据一致性跨服务操作无法用本地事务保证Saga、本地消息表、Outbox 等最终一致性方案（见 分布式事务）
调用链排障一个请求经过多个服务，定位慢点和错误点困难基于 OpenTelemetry / SkyWalking 的链路追踪（见 链路追踪）
运维复杂度几十上百个服务的部署、配置、扩缩容、监控容器化与 Kubernetes、CI/CD、配置中心
测试困难端到端测试需要拉起多个服务，接口变更容易破坏调用方消费者驱动契约测试（Spring Cloud Contract、Pact），见 契约测试
接口演进服务间接口变更必须兼容存量调用方向后兼容的字段演进、接口版本号、灰度发布

结论：微服务不是银弹。没有完善的 CI/CD、容器化基础设施和可观测体系，微服务带来的麻烦远大于收益——最坏的结果是「分布式单体」：服务拆开了，但仍然必须一起发布、一起扩容、一起故障。

五、何时拆分

拆分没有一个「多少人、多少行代码」的硬阈值。Martin Fowler 的 MonolithFirst 观点是：先用单体把业务跑通、把边界看清，再按需拆分。判断时看的是信号，而不是规模数字。

信号说明建议
发布互相阻塞多个团队共用发布窗口，一个团队的改动经常拖住其他团队可以开始规划拆分
迭代节奏差异大有的模块一天多次发布，有的模块半年不动把高频变化的模块优先拆出
扩展需求不同少数模块承担大部分流量或需要特殊硬件把热点模块独立部署、独立扩容
业务边界模糊领域模型没理清，模块间调用错综复杂先在单体内做模块化与领域建模（见 DDD 领域驱动设计），再拆
基础设施不足没有容器化、自动化部署、集中日志与监控先补基础设施和可观测性，否则不要拆
团队小、业务简单单体的开发和部署效率仍然很高保持单体，做好模块化即可

六、单体到微服务的迁移策略

Chris Richardson 在「Refactoring a monolith into microservices」中总结了三种互补的策略：停止让单体继续变大、拆分前后端、抽取服务。核心原则是渐进式迁移，不做大爆炸式重写——他在文中引用 Martin Fowler 的说法：大爆炸式重写唯一能保证的，就是一场「大爆炸」。

1、停止挖掘：新功能不再进单体

单体已经是个坑，第一步是别再往下挖：新功能直接做成独立服务，单体与新服务之间通过网关路由和防腐层（Anti-Corruption Layer）协作，避免新服务被单体的领域模型污染。

2、前后端分离

把表现层与业务逻辑、数据访问层拆开，形成可独立部署的前端应用和后端 API。这一步往往能先把单体的发布耦合降下来，也为后续用网关切流打基础。

3、抽取服务：绞杀者模式（Strangler Fig）

绞杀者模式得名于绞杀榕：新服务像藤蔓一样沿着旧系统生长，逐步接管其功能，直到旧系统可以下线。

  1. 在单体前加 API 网关，所有流量先经过网关，此时网关只做透传
  2. 选一个模块抽取为独立服务，迁移它的数据，网关把对应路由切到新服务
  3. 新服务稳定后删除单体中的旧代码；出问题时把路由切回单体即可回滚
  4. 重复第 2、3 步，单体逐步缩小，最终下线

优先抽取的模块：

  • 频繁变化的模块：拆出后独立发布的收益最大
  • 资源消耗大或有特殊资源需求的模块：拆出后可独立扩容
  • 边界清晰、与其他模块耦合少的模块：拆分成本最低，适合作为第一个试点

数据迁移是最难的一步：服务拆出后必须拥有自己的数据。常见做法是先让新服务通过 API 读写单体数据，再用双写或 CDC 同步（见 CDC 工具）把数据迁到新库，最后切断对旧表的访问。

小结

  • 微服务是围绕业务能力、可独立部署、数据自治的小服务集合，本质是用分布式复杂度换取独立交付与独立扩展
  • 与 SOA 的区别在于去掉 ESB 与重量级协议、服务粒度更细、数据去中心化
  • 优势是独立部署、独立扩展、故障隔离、团队自治；代价是分布式复杂性、数据一致性、排障、运维与测试成本
  • 拆分看信号而不是人数：发布互相阻塞、节奏差异大、扩展需求不同时考虑拆；边界模糊、基础设施不足时先别拆
  • 迁移坚持渐进式：停止往单体加功能、前后端分离、用绞杀者模式逐个抽取服务，数据迁移单独规划
