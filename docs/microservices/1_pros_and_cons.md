# 微服务优势与挑战

> 前置阅读：[微服务架构总览](./0_overview)

微服务首先是一种**组织与交付方式**，其次才是技术架构：它用分布式系统的复杂度，换取团队独立交付、按需扩展和故障隔离的能力。本篇讲微服务的定义与原则、与 SOA 的区别，以及单体的瓶颈和微服务的收益与代价。

---

## 一、什么是微服务

### 1、定义

微服务架构把单一应用拆成一组**小的、可独立部署的服务**，每个服务：

- 围绕业务能力构建，职责单一
- 运行在自己的进程中，拥有自己的数据存储
- 通过轻量级机制（HTTP / gRPC / 消息队列）与其他服务通信
- 可由一个小团队独立开发、测试、部署和扩展

![单体应用 vs 微服务架构](../assets/microservices/monolith-vs-microservices.svg)

### 2、核心原则

| 原则 | 说明 |
|------|------|
| **单一职责** | 每个服务对应一个业务能力，边界清晰 |
| **自治** | 独立开发、独立部署、独立扩展，团队对服务全生命周期负责 |
| **数据去中心化** | 每个服务管理自己的数据，不共享数据库表 |
| **为失败而设计** | 默认远程调用会超时和失败，靠超时、重试、熔断、降级兜底（见 [熔断](/high-avail/5_circuit_breaking)） |
| **基础设施自动化** | 服务数量多，构建、部署、监控必须自动化 |

### 3、微服务 vs SOA

两者的核心区别在**集成方式与数据归属**，不在服务大小：

| 对比 | SOA | 微服务 |
|------|-----|--------|
| 集成方式 | 以 ESB（企业服务总线）为中心，路由、协议转换、流程编排放在总线上（智能管道），WS-* 等重协议 | 去掉中心总线，REST / gRPC / 消息队列直连，逻辑留在服务内部（智能端点、哑管道） |
| 数据归属 | 常见共享数据库 | 每个服务独占自己的数据，不共享表 |
| 治理 | 集中式治理、统一技术栈 | 去中心化治理，允许技术异构 |
| 目标 | 跨部门、跨系统复用 | 快速迭代、独立交付、独立扩展 |

粒度只是次要差异：微服务按单个业务能力 / 限界上下文划分，通常比 SOA 的企业级服务更细，但「拆得细」不是微服务的定义，拆得过细反而会变成纳米服务。可以把微服务理解为去掉 ESB、把数据交还给各服务的 SOA。

## 二、单体应用的瓶颈

单体在早期是最优解：开发、调试、部署都简单。问题出在业务和团队持续膨胀之后。

![单体应用从早期到大泥球的演变](../assets/microservices/monolith-growth.svg)

| 问题 | 具体表现 |
|------|---------|
| **复杂度失控** | 模块间随意调用，没人能完整理解系统，改动影响面难以评估 |
| **部署风险高** | 改一行代码也要全量打包部署，一次发布捆绑多个团队的改动 |
| **扩展受限** | 只能整体扩容，无法只给热点模块加机器（见 [水平扩展与无状态化](/high-con/2_scale_out)） |
| **故障不隔离** | 一个模块内存泄漏或线程池打满，拖垮整个进程 |
| **技术栈锁定** | 框架或 JDK 升级影响全局，难以局部引入新技术 |
| **协作瓶颈** | 多团队共享一个仓库与发布窗口，合并冲突和发布排队频繁 |

---

## 三、微服务的优势

| 优势 | 说明 |
|------|------|
| **独立部署** | 每个服务单独发布，发布周期短，单次发布风险小，回滚范围小 |
| **独立扩展** | 只对热点服务扩容，并可按服务选择不同的硬件规格 |
| **技术异构** | 不同服务可选不同语言、框架和存储，各取所长 |
| **故障隔离** | 非核心服务宕机不影响核心链路（前提是配好超时、熔断与降级） |
| **团队自治** | 团队边界与服务边界一致，减少跨团队协调 |
| **易于理解** | 单个服务代码量小，新人只需理解自己负责的服务 |

## 四、微服务的挑战

| 挑战 | 说明 | 应对方案 |
|------|------|---------|
| **分布式复杂性** | 网络调用会超时、失败、乱序，远比本地调用复杂 | 超时、重试、熔断、隔离（见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)） |
| **数据一致性** | 跨服务操作无法用本地事务保证 | Saga、本地消息表、Outbox 等最终一致性方案（见 [分布式事务](/distributed/4_transaction)） |
| **调用链排障** | 一个请求经过多个服务，定位慢点和错误点困难 | 基于 OpenTelemetry / SkyWalking 的链路追踪（见 [链路追踪](/observability/3_tracing)） |
| **运维复杂度** | 几十上百个服务的部署、配置、扩缩容、监控 | 容器化与 Kubernetes、CI/CD、配置中心 |
| **测试困难** | 端到端测试需要拉起多个服务，接口变更容易破坏调用方 | 消费者驱动契约测试（Spring Cloud Contract、Pact），见 [契约测试](/testing/6_contract_test) |
| **接口演进** | 服务间接口变更必须兼容存量调用方 | 向后兼容的字段演进、接口版本号、灰度发布 |

**结论**：微服务不是银弹。没有完善的 CI/CD、容器化基础设施和可观测体系，微服务带来的麻烦远大于收益——最坏的结果是「分布式单体」：服务拆开了，但仍然必须一起发布、一起扩容、一起故障。

## 五、何时拆、怎么迁

收益与代价摆清楚之后，是否拆看信号而不是规模数字：没有明确信号时先做模块化单体，存量单体用绞杀者模式一次抽一个服务、每一步都能回退。判断信号、前提条件、拆分依据与迁移步骤统一见 [服务拆分](./2_service_split)。

---

## 小结

- 微服务是围绕业务能力、可独立部署、数据自治的小服务集合，本质是用分布式复杂度换取独立交付与独立扩展
- 与 SOA 的核心区别是集成方式（ESB 智能管道 vs 智能端点、哑管道）与数据归属（共享库 vs 服务独占），粒度更细只是次要差异
- 优势是独立部署、独立扩展、故障隔离、团队自治；代价是分布式复杂性、数据一致性、排障、运维与测试成本
- 拆不拆看信号而不是人数，存量迁移坚持渐进式，二者都在 [服务拆分](./2_service_split) 展开
