# 服务拆分

> 前置阅读：[微服务优势与挑战](./1_pros_and_cons)、[DDD 领域驱动设计](/architecture/2_ddd)

边界划得好坏，决定了拆出来的是能独立交付的微服务还是「分布式单体」。本篇讲拆分依据、粒度判断、数据拆分、迁移步骤与拆后治理，基线为 Spring Boot 4、Spring Cloud 2025.1。

---

## 一、什么时候该拆、什么时候不该拆

### 1、单体优先

拆分要解决的是**组织与交付问题**：多个团队抢同一个发布窗口、少数模块需要单独扩容、模块迭代节奏差别很大。没有这些问题时拆分只带来成本——网络调用、分布式事务、链路排障、几十条流水线。

拆分没有一个「多少人、多少行代码」的硬阈值。Martin Fowler 的 MonolithFirst 观点是：先用单体把业务跑通、把边界看清，再按需拆分。判断时看的是**信号**，而不是规模数字：

| 信号 | 说明 | 建议 |
|------|------|------|
| 发布互相阻塞 | 多个团队共用发布窗口，一个团队的改动经常拖住其他团队 | 可以开始规划拆分 |
| 迭代节奏差异大 | 有的模块一天多次发布，有的模块半年不动 | 把高频变化的模块优先拆出 |
| 扩展需求不同 | 少数模块承担大部分流量或需要特殊硬件 | 把热点模块独立部署、独立扩容 |
| 团队小、业务简单 | 单体的开发和部署效率仍然很高 | 保持单体，做好模块化即可 |

即使出现了上面的信号，下面三条前提不满足时也先别拆：

| 前提 | 不满足时的后果 |
|------|---------------|
| 业务边界已经看清 | 边界在业务摸索期频繁变化，拆早了每次调整都是跨服务重构；应先在单体内做模块化与领域建模（见 [DDD 领域驱动设计](/architecture/2_ddd)） |
| 有容器化、自动化部署、集中日志、链路追踪 | 服务一多就无法发布、无法排障；先补基础设施和可观测性 |
| 团队能为服务全生命周期负责 | 服务没人认领，出了故障互相推诿 |

### 2、模块化单体

信号不够强时，先把单体做成**模块化单体**：一个部署单元，代码按业务模块划清边界，模块之间只走公开接口、不访问对方的表。概念与取舍见 [分布式架构](/distributed/1_distributed#三、模块化单体与何时拆分)，落地时要让边界**可校验**，否则半年后就会被随手的跨模块调用打穿。Spring Modulith 把顶层包当作模块，用一个测试守住依赖规则：

```java
class ModularityTests {

    @Test
    void verifyModuleBoundaries() {
        // 模块间只能访问对方的公开 API 包，出现循环依赖或访问 internal 包时测试失败
        ApplicationModules.of(ShopApplication.class).verify();
    }
}
```

模块之间的协作也按「将来是两个服务」来写：同步交互只调对方的公开接口，异步交互用 `ApplicationEventPublisher` 发领域事件。这样做的好处是拆分时改的是**部署方式**而不是**代码结构**：公开接口换成 HTTP 客户端，进程内事件换成消息队列。

::: tip 模块化单体不是过渡态
很多系统一直停在模块化单体就足够了。拆分是为了解决具体的组织或扩容问题，不是架构演进的必经终点。
:::

## 二、拆分依据

几种依据经常同时成立，优先级大致是：**限界上下文定边界，业务能力做初稿，团队结构与非功能差异做校正**。

### 1、业务能力

按「企业做什么」列出业务能力（下单、支付、库存、营销、履约），每项能力对应一个候选服务。业务能力比组织结构和技术分层都稳定，适合作为拆分初稿；电商的能力划分表见 [微服务设计模式](./2_patterns#一、服务拆分模式)。

它的局限是粒度偏粗、不处理「同一个词在不同能力里含义不同」的问题，所以需要限界上下文细化。

### 2、限界上下文

限界上下文是**模型的边界**：同一个「商品」在商品中心是标题、图片、属性，在订单中心是下单时的价格快照，在库存中心是 SKU 与可售数量。一个上下文内部术语一致、不变量自洽，天然适合作为一个服务的边界。识别方法和上下文映射见 [DDD 领域驱动设计](/architecture/2_ddd#_2、限界上下文-bounded-context)，拆分时用到的结论有三条：

- **聚合不跨服务**：必须在一个事务内保持一致的数据（订单与订单行）放在同一个服务里，否则就要引入分布式事务
- **上下文映射就是服务间关系**：客户-供应商关系对应同步 API，开放主机服务对应稳定的公开协议，遗留系统前面放防腐层
- **上下文与服务不是一一对应**：一个上下文可以因扩容需要拆成读写两个服务，一个服务在初期也可以承载两个紧密相关的上下文

### 3、团队结构与康威定律

康威定律（Melvin Conway，1968）：系统的结构会复制设计它的组织的沟通结构。对拆分的直接影响是：

- **一个服务只归一个团队**：两个团队共同维护一个服务，就会退化成单体式的协作；一个团队维护十几个服务，则大部分精力花在运维上
- **逆康威操作**（Inverse Conway Maneuver）：先按目标架构调整团队，再让系统结构跟着演化。服务边界画好但团队没调，边界会被跨团队的需求慢慢侵蚀
- **团队认知负荷是粒度上限**：服务数量要与团队能长期维护的数量匹配，常见做法是一个 5–9 人的团队负责 2–5 个服务

### 4、变更频率与非功能需求差异

同一个限界上下文内部，如果有一部分的**变更节奏**或**运行要求**明显不同，也是拆出来的理由：

| 差异 | 例子 | 拆出后的收益 |
|------|------|-------------|
| 变更频率 | 营销规则一天改几次，账务核心半年不动 | 高频部分独立发布，不拖累核心 |
| 流量与扩容 | 商品详情读流量是写流量的上千倍 | 读服务单独水平扩容（见 [水平扩展与无状态化](/high-con/2_scale_out#三、服务拆分)） |
| 可用性要求 | 下单链路要 99.99%，报表可以 99.9% | 核心链路与非核心链路隔离部署 |
| 安全与合规 | 支付涉及卡数据，需要 PCI DSS 审计 | 把审计范围收敛到一个小服务 |
| 资源特征 | 图片处理吃 CPU，推荐模型要 GPU | 按资源类型选机型 |

::: warning 不要按技术层拆
「Controller 服务」「DAO 服务」「公共工具服务」这类按技术分层的拆法，让每个需求都要同时改多个服务，是分布式单体最常见的来源。
:::

## 三、拆分粒度

粒度没有标准答案，但「拆错了」的信号很明确。判断的核心标准是：**一个常规需求通常只改一个服务、只发一个服务**。

### 1、过细的信号

| 信号 | 表现 | 根因 |
|------|------|------|
| 分布式单体 | 服务必须按顺序一起发布，一个服务的接口改动要同步改五六个调用方 | 边界切在了高内聚的逻辑中间 |
| 链式调用 | A → B → C → D 的同步调用链，每一跳只做少量转发和组装 | 一个业务能力被切成了多个纳米服务 |
| 同步调用过深 | 一个外部请求经过 5 层以上同步调用，延迟累加、可用性相乘（每层 99.9%，5 层约 99.5%） | 用同步调用代替了本该放在一起的逻辑 |
| 频繁分布式事务 | 大部分写操作都要 Saga 或 TCC 才能保持一致 | 聚合被拆到了不同服务 |
| 数据来回搬 | 服务间大量接口只是在「查一下对方的字段」 | 数据归属划错，或缺少冗余快照 |
| 服务比人多 | 每个开发者维护三四个服务，流水线、告警、依赖升级应接不暇 | 粒度超过团队承载力 |

### 2、过粗的信号

| 信号 | 表现 |
|------|------|
| 发布排队 | 多个团队的改动挤在同一个服务里，互相等待发布窗口 |
| 扩容浪费 | 只有一个接口是热点，却要整体扩容一个很大的服务 |
| 故障面过大 | 一个非核心功能的内存泄漏或慢查询拖垮核心接口 |
| 模型冲突 | 同一个实体类上堆了多个上下文的字段，改一处牵动多处 |

### 3、粒度自检

拆分方案评审时逐条过一遍：

- 这个服务能用一句不含「和」的话说清职责吗
- 它的核心写操作能在一个本地事务里完成吗
- 过去半年的需求中，有多少需要同时改它和另一个服务；比例高说明两者应该合并
- 它的同步下游有几个，调用深度是否超过 3 层
- 哪个团队负责它，这个团队还负责哪些服务

## 四、数据拆分

### 1、每服务独享库

服务拆开但共用一个库，等于没拆：任何一张表的 DDL 都会波及多个服务，任何一个服务的慢查询都会拖垮别人。每个服务**独占**自己的数据，其他服务只能通过它的 API 或事件访问。「独占」指逻辑所有权，同一个 MySQL 实例上的不同 schema 加上按服务授权的账号也能满足，详见 [微服务设计模式](./2_patterns#三、数据管理模式)。

### 2、共享表的拆法

单体里最难拆的是被多个模块共同读写的表。先给每张表**确定唯一的写方（owner）**，再按访问方式处理：

| 现状 | 拆法 |
|------|------|
| 一张表被多个模块读写 | 写方成为 owner，其他模块的写改为调用 owner 的 API，读改为调 API 或订阅事件 |
| 宽表里混着多个上下文的字段（`t_product` 里有 `stock`） | 按列拆：库存列迁到库存服务，商品表只保留商品自己的字段 |
| 跨模块 JOIN 与外键 | 外键改为 ID 引用；需要展示的字段在下单时冗余一份快照（订单里存商品名和成交单价） |
| 公共字典表（地区、币种、类目树） | 由一个服务拥有并发布变更事件，其他服务本地缓存只读副本 |
| 多个模块共用的流水号、计数器 | 改用各服务自己的 ID 生成，或抽出独立的发号服务 |

快照与引用的取舍看语义：订单要的是**下单那一刻**的价格，所以存快照；收货地址如果允许用户事后修改并影响未发货订单，就存引用并在发货时读取最新值。

### 3、跨服务查询

数据分开后，「订单列表带商品名和用户昵称」这类查询有两种做法：

- **API 组合**：BFF 或查询服务并行调用各服务后在内存拼接，适合数据量小、要求实时的查询
- **CQRS 读模型**：各服务发布领域事件，由专门的查询服务物化一张宽表（常放在 Elasticsearch），适合分页、排序、复杂过滤，代价是秒级延迟

两者的适用边界见 [微服务设计模式](./2_patterns#三、数据管理模式)，读模型的投影实现见 [架构模式与风格](/architecture/1_arch_patterns#四、cqrs-命令查询职责分离)。

### 4、跨服务一致性

原来一个本地事务完成的操作，拆开后只能做到最终一致。第一选择是**调整边界让它重新落在一个服务内**；确实跨服务时，用 Outbox 保证「写库 + 发事件」原子，用 Saga 编排多步业务并定义补偿，方案对比与选型见 [分布式事务](/distributed/4_transaction#九、方案选型)。

## 五、拆分步骤

存量单体的拆分坚持渐进式：用绞杀者模式一次抽一个服务，每一步都可以回退。总体策略（停止往单体加功能、前后端分离、绞杀者）见 [微服务优势与挑战](./1_pros_and_cons#六、单体到微服务的迁移策略)，下面展开单个服务的抽取过程：

![服务拆分迁移四阶段：网关接管、抽出新服务、迁移数据、切写并下线](../assets/microservices/split-migration-stages.svg)

### 1、选第一个服务：先拆边缘

第一个服务的目标是**把流程跑通**：网关、CI/CD、监控告警、链路追踪、数据迁移工具，而不是拿下最难的核心。优先选：

- 边界清楚、依赖少的边缘能力，如通知、文件、搜索
- 只读或读多写少的能力，数据迁移简单
- 变更频繁、拆出后收益明显的能力

核心域（订单、账务）放在流程成熟之后再拆。拆核心域时优先「先拆数据访问、再拆部署」：先在单体内把订单模块的表访问收敛到一个仓储接口，确认没有其他模块直接读写订单表，再动部署。

### 2、防腐层隔离单体模型

新服务难免要调用单体的接口、读单体的数据。如果直接复用单体的 DTO 和枚举，新服务的模型会被旧模型「传染」，单体下线时还得重构一遍。做法是在新服务里放一层**防腐层**（ACL），把单体的数据翻译成本服务的领域对象：

```java
// 新库存服务读取单体中的商品数据，翻译为本上下文的 Sku 值对象
@Component
class LegacyProductAdapter implements SkuCatalog {

    private final LegacyShopClient legacy;   // @HttpExchange 声明的单体接口客户端

    LegacyProductAdapter(LegacyShopClient legacy) {
        this.legacy = legacy;
    }

    @Override
    public Sku findSku(SkuId id) {
        LegacyGoodsDTO dto = legacy.getGoods(id.value());
        // 单体用 status=3 表示下架，本上下文只关心是否可售
        return new Sku(id, dto.getGoodsName(), dto.getStatus() != 3);
    }
}
```

单体下线、数据迁到新的商品服务后，只需替换这个适配器的实现，领域代码不动。上下文映射里防腐层的定位见 [DDD 领域驱动设计](/architecture/2_ddd#_3、上下文映射)。

### 3、双写与数据迁移

数据所有权的转移按「旧库为准 → 新库为准」分阶段进行，每一阶段都明确以哪边为准：

1. **新服务通过单体 API 读写旧表**：先切流量、不动数据，验证新服务的逻辑
2. **建服务独享库并同步**：用 CDC 订阅单体库 binlog，把存量与增量同步到新库，优先 CDC 而不是在业务代码里双写（见 [CDC 工具](/database/5_practice/0_cdc_tools)）
3. **校验对账与灰度切读**：行数与分段 checksum 比对，按用户维度逐步把读切到新库
4. **切写**：短暂停写、等增量追平、切到新库为主写，同时开启新库到旧库的反向同步，让还没迁走的单体报表、对账逻辑继续可用
5. **断开旧表**：确认单体没有残留访问后，回收旧表的账号权限，最后归档或删除

第 2–4 步的位点记录、限速、checksum 写法与停写窗口控制和分库分表迁移完全相同，见 [分库分表与中间件](/database/5_practice/3_sharding#_1、不停机迁移五步)。

::: warning 第 5 步最容易被跳过
旧表只要还能被访问，就一定有人在用：定时任务、报表 SQL、运维脚本、别的团队的直连。下线前先回收写权限、观察一个周期，再回收读权限。
:::

### 4、灰度切流与回滚

切流在网关做，按比例或按用户维度逐步放量。Spring Cloud Gateway 用 `Weight` 断言把同一路径按权重分给新旧两组路由（Spring Cloud 2025 起服务端配置前缀为 `spring.cloud.gateway.server.webflux`）：

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: inventory-new
              uri: lb://inventory-service
              predicates:
                - Path=/api/inventory/**
                - Weight=inventory, 10      # 10% 流量进新服务
            - id: inventory-legacy
              uri: lb://shop-monolith
              predicates:
                - Path=/api/inventory/**
                - Weight=inventory, 90
```

放量过程中对比新旧两边的错误率、延迟和关键业务指标；写操作在数据切换前仍落旧库，所以出问题时把权重调回 0 即可回滚。需要「同一个用户始终走同一边」时，改用按用户 ID 哈希的自定义断言或在请求头里打灰度标。

## 六、拆分后的治理

拆完只是开始，边界在后续迭代中会被不断侵蚀。治理的目标是让「越界」在 CI 和评审阶段就被发现。

### 1、接口契约

服务间接口就是服务的边界，需要像对外 API 一样管理：

- **契约先行**：用 OpenAPI 或 `.proto` 描述接口，评审通过后再实现，规范见 [API 设计规范](/engineering/4_api_design_rule)
- **消费者驱动契约测试**：调用方声明依赖的字段与行为，提供方在 CI 中验证，破坏调用方就构建失败，见 [契约测试](/testing/6_contract_test)
- **只暴露业务语义**：接口返回领域对象，不返回数据库实体；不提供「按任意条件查表」的通用接口，否则调用方会把它当成远程 SQL 用

### 2、版本演进

- **默认向后兼容**：只加可选字段、不删字段、不改语义；调用方忽略不认识的字段（宽容读者）
- **破坏性变更走新版本**：新旧版本并存一段时间，按调用量逐个迁移调用方后下线旧版本，见 [API 设计规范](/engineering/4_api_design_rule#八、版本管理)
- **事件同样要版本化**：消息体加 schema 版本号，消费者兼容新旧两种格式后，生产者才切换

### 3、调用链深度

- **限制同步深度**：外部请求的同步调用链一般不超过 3 层，超过时考虑合并服务、改为事件驱动或在调用方冗余数据
- **禁止循环依赖**：A 调 B、B 又调 A 说明边界有问题，用链路追踪的服务依赖图定期检查（见 [链路追踪](/observability/3_tracing)）
- **非核心链路异步化**：下单后的积分、通知、统计全部走事件，不放在同步链路上
- **每个远程调用设超时**：超时、重试、熔断的配置见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

### 4、团队边界

- **服务目录**：每个服务登记负责团队、值班人、上下游依赖、SLA，没有 owner 的服务不允许上线
- **代码所有权**：仓库用 CODEOWNERS 指定评审人，跨团队修改必须经 owner 评审
- **定期复盘边界**：统计「需要同时改多个服务的需求」比例，持续偏高时合并服务或调整团队

## 七、电商示例

### 1、服务划分

以一个中等规模的电商为例，第一轮拆出五个核心服务：

| 服务 | 拥有的数据 | 对外提供 | 依赖 |
|------|-----------|---------|------|
| 用户服务 | 账号、收货地址、会员等级 | 用户信息查询、地址管理 | 无 |
| 商品服务 | 商品、SKU、类目、价格 | 商品详情、价格查询 | 无 |
| 订单服务 | 订单、订单行（含商品快照）、订单状态 | 下单、取消、订单查询 | 库存（同步）、支付（同步）、商品（下单时读价格） |
| 库存服务 | 可售库存、预占记录 | 预占、确认扣减、释放 | 订阅订单事件 |
| 支付服务 | 支付单、渠道流水、退款单 | 创建支付单、渠道回调、退款 | 发布支付事件 |

几个关键的边界决定：

- **订单行冗余商品快照**：订单展示不依赖商品服务，商品改名、改价不影响历史订单
- **库存不并入商品服务**：库存写入频率和并发远高于商品信息，还有秒杀等热点场景，需要单独扩容
- **用户 ID 来自令牌**：订单服务从网关解析的身份信息拿用户 ID，下单时不调用户服务；收货地址由 BFF 查询后随下单请求传入并存为快照

### 2、依赖关系

![电商服务拆分与依赖：网关聚合查询，订单同步调用库存与支付，其余协作走领域事件](../assets/microservices/ecommerce-service-split.svg)

依赖方向只有「订单 → 库存」「订单 → 支付」两条同步边，且都是必须马上知道结果的操作；其余协作全部走事件，同步调用深度最多 2 层。

### 3、下单链路

1. 订单服务读取商品价格，同步调用库存服务**预占**库存（预占记录带过期时间）
2. 本地事务内写订单（待支付）并通过 Outbox 发布 `OrderCreated`，再同步调用支付服务创建支付单
3. 支付成功后支付服务发布 `PaymentSucceeded`，订单服务消费后把订单改为已支付，库存服务把预占转为扣减
4. 超时未支付时订单服务取消订单并发布 `OrderCancelled`，库存服务释放预占

这是一个协同式 Saga：每一步都是本地事务，失败靠补偿（释放预占、关闭支付单）回到一致状态，所有消费者按订单号幂等。秒杀等热点场景下的库存设计见 [秒杀](/scenario/4_seckill)。

## 八、常见反模式

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| 分布式单体 | 服务必须一起发布、一起扩容、一起故障 | 合并强耦合的服务，按限界上下文重划边界 |
| 共享数据库 | 多个服务直接读写同一张表 | 确定表的 owner，其他服务改走 API 或事件 |
| 按技术层拆分 | Controller 服务、DAO 服务、Common 服务 | 按业务能力纵向切分 |
| 纳米服务 | 一个服务只有一两个接口，或「订单创建」「订单查询」各成一个服务 | 合并共享同一份数据与不变量的服务 |
| 一次性大爆炸重写 | 冻结单体、并行开发新系统、某天整体切换 | 绞杀者模式逐个抽取，每步可回退 |
| 先拆服务、后想数据 | 代码拆开了但仍连着单体库 | 拆分方案里必须包含数据归属与迁移计划 |
| 公共 jar 承载业务 | 所有服务依赖同一个包含领域模型与业务逻辑的 common 包，改一处全体升级 | common 只放技术工具类，领域模型各服务自有 |
| 同步调用链过长 | 一个请求串行经过五六个服务 | 冗余数据、合并服务、非核心链路改事件 |
| 服务无主 | 服务数量超过团队承载力，部分服务没人维护 | 服务目录登记 owner，合并低价值服务 |

## 小结

- 拆分解决的是组织与交付问题：没有明确信号时先做模块化单体，并用 Spring Modulith 之类的工具让模块边界可校验
- 拆分依据以限界上下文定边界、业务能力做初稿，再用团队结构（康威定律）、变更频率与非功能需求差异校正；不要按技术层拆
- 粒度的检验标准是「一个常规需求只改一个服务」；分布式单体、链式调用、同步调用过深、频繁分布式事务都是拆得过细的信号
- 数据先于代码：每服务独享库，共享表先定 owner 再按列拆、改 ID 引用加快照；跨服务查询用 API 组合或 CQRS，一致性优先调边界，其次 Outbox + Saga
- 存量拆分用绞杀者模式一次抽一个服务：先拆边缘跑通流程，防腐层隔离旧模型，数据按「旧库为准 → 新库为准」分阶段迁移，网关按权重灰度切流
- 拆完靠契约测试、兼容的版本演进、调用深度约束和服务 owner 守住边界
