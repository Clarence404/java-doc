# 服务间通信与契约

> 前置阅读：[服务拆分](./2_service_split)、[微服务设计模式](./3_patterns)、[消息队列基础](/messaging/1_basics)

服务拆开之后，服务之间怎么交互决定了耦合程度和故障半径，接口怎么演进决定了各服务能不能真正独立发布。本篇从架构层面讲同步与异步的选择、事件驱动的用法与边界、接口契约、版本兼容与跨服务查询，HTTP Service Clients、gRPC、Dubbo 等客户端的写法见微服务治理模块。

---

## 一、同步还是异步

### 1、两种交互方式

- **同步请求响应**：调用方发出请求后等待结果，HTTP、gRPC、Dubbo 都属于这一类；调用方知道下游是谁，并且需要它此刻在线
- **异步消息 / 事件**：发送方把消息交给消息队列就返回，接收方稍后处理；发送方不等结果，发布事件时甚至不知道有哪些订阅方

![同步请求响应与事件驱动的依赖方向对比](../assets/microservices/sync-vs-event.svg)

两者的根本差别不在快慢，而在**依赖方向**：同步调用里上游依赖下游（下游挂了上游跟着失败）；事件驱动里下游依赖上游发布的事件（上游不感知下游）。

### 2、判断依据

| 维度 | 同步请求响应 | 异步消息 / 事件 |
|------|-------------|----------------|
| 是否需要立即结果 | 调用方下一步依赖返回值 | 调用方不关心结果，或可以稍后再查 |
| 耦合 | 时间耦合：双方必须同时在线；调用方知道下游地址与接口 | 只耦合消息格式；发送方与接收方可以分别上下线 |
| 可用性 | 链路可用性约等于各服务可用性的乘积，一个下游故障会向上传染 | 下游故障时消息堆积，恢复后继续处理，上游不受影响 |
| 延迟 | 调用方等待的时间是各跳耗时之和，链路越深越慢 | 主流程响应快，但业务整体完成时间变长且不确定 |
| 一致性 | 返回时就知道成功与否，失败可立即处理 | 最终一致，要处理重复、乱序与失败后的补偿 |
| 排障 | 调用链清晰，链路追踪直接可见 | 需要消息轨迹与跨消息的 traceId 透传 |
| 典型场景 | 查询、下单时校验与扣减库存、发起支付 | 支付成功后的积分、通知、统计、搜索索引同步 |

按下面的顺序问，基本就能定下来：

1. 调用方的下一步是否依赖这次结果？依赖就用同步，不依赖进入下一问
2. 下游失败时，调用方是否也必须失败？不必失败的操作（发通知、加积分）适合异步
3. 一个写操作是否要扇出给多个下游？扇出越多越适合发布事件，避免上游逐个调用
4. 同步链路是否已经很深？外部请求的同步深度一般控制在 3 层以内，超出部分改为事件或在调用方冗余数据，见 [服务拆分 · 调用链深度](./2_service_split#_3、调用链深度)

### 3、混合用法

实际系统几乎都是两者混用，常见组合：

- **核心链路同步、旁路异步**：下单时同步扣减库存、创建支付单，支付成功后发布 `OrderPaid` 事件，积分、通知、统计各自订阅
- **同步受理、异步处理**：耗时操作（导出、批量处理）先同步返回 `202 Accepted` 和任务号，后台异步执行，调用方轮询状态或等待回调
- **少用基于消息的请求 - 回复**：用 MQ 模拟同步调用（发请求消息、等回复消息）同时拿到了两边的缺点，只在确实需要缓冲且调用方能等待时使用

同步客户端的选型与写法见 [服务通信](/service-governance/3_communication)，削峰场景的系统设计见 [异步与削峰](/high-con/4_async_peak_shaving)，一个订单服务把哪些环节异步化、哪些保持同步的完整决策见 [项目演进 · 异步化](/project/5_async)。

## 二、事件驱动的用法与边界

### 1、三种用法

同样叫「事件驱动」，事件里放什么、消费方怎么用，差别很大：

| 用法 | 事件里有什么 | 消费方怎么做 | 适合 | 代价 |
|------|-------------|-------------|------|------|
| **事件通知**（Event Notification） | 事件类型与业务 ID，如 `OrderPaid{orderId}` | 需要详情时回调生产方接口查询 | 下游少、需要最新数据、事件体要小 | 回查流量与对生产方的运行时依赖又回来了，订阅方一多容易形成回查风暴 |
| **事件携带状态转移**（Event-Carried State Transfer） | 变更后的完整快照或下游需要的字段 | 在本地维护一份只读副本，不再回查 | 读多写少、希望下游在生产方故障时仍能工作 | 数据冗余、副本最终一致；事件体变大，字段增减要按第四节做兼容 |
| **事件溯源**（Event Sourcing） | 状态的每一次变化，事件序列就是事实来源 | 重放事件得到当前状态，或投影为读模型 | 需要完整审计与历史回溯（账户、订单） | 建模、事件版本演进与快照复杂，团队门槛高 |

前两种是服务间集成方式，大多数系统从事件通知起步，读压力或可用性要求上来后改为携带状态；事件溯源是服务内部的持久化方式，原理与实现见 [架构模式与风格 · Event Sourcing（事件溯源）](/architecture/1_arch_patterns#五、event-sourcing-事件溯源)。

### 2、什么时候用、边界在哪

- **事件表达已发生的事实，不是命令**：用过去式命名（`OrderPaid`、`StockReserved`），发布方不关心谁处理、怎么处理；「请扣减库存」这类必须有人执行且要知道结果的诉求，用同步调用或由 Saga 编排的命令消息
- **事件是公开契约**：发布之后订阅方不可控，字段只能按兼容规则演进，删改字段的成本比同步接口更高
- **协同链不宜过长**：A 发事件触发 B、B 再发事件触发 C……链条一长就没人能看清完整流程，失败补偿也难以定义；步骤多、需要补偿时改用编排式 Saga，见 [分布式事务 · Saga](/distributed/4_transaction#四、saga)
- **消费方按至少一次设计**：消息会重复、会乱序，消费者必须幂等（见 [消息队列基础 · 幂等消费](/messaging/1_basics#四、幂等消费)），对状态有顺序要求时用版本号兜底（见 [接口调用顺序性](./4_call_ordering)）
- **不是所有解耦都需要事件**：只有一个下游、且调用方需要结果时，同步调用更简单、更好排障

### 3、可靠投递

「写数据库」和「发事件」是两个系统，不能靠在事务里发 MQ 保证原子性；可靠做法是本地消息表（Outbox）或 RocketMQ 事务消息，见 [消息队列基础 · 分布式事务中的消息](/messaging/1_basics#八、分布式事务中的消息) 与 [分布式事务 · 本地消息表（Transactional Outbox）](/distributed/4_transaction#五、本地消息表-transactional-outbox)。

## 三、接口契约

### 1、契约包含什么

服务之间的接口就是服务的边界，契约要写清的不只是字段：

| 部分 | 内容 |
|------|------|
| 结构 | 路径或方法名、请求与响应字段、类型、是否必填 |
| 语义 | 字段含义、单位（分还是元）、取值范围、枚举含义 |
| 错误 | 状态码或错误码、哪些错误可以重试 |
| 行为约定 | 是否幂等、超时建议、调用配额、事件的投递语义（至少一次、分区键） |

后两部分最容易漏写，却最常引发线上事故：调用方把不幂等的接口拿去重试，或把「分」当成「元」。

### 2、契约优先还是代码优先

| 做法 | 流程 | 优点 | 缺点 | 适合 |
|------|------|------|------|------|
| **契约优先** | 先写 OpenAPI / `.proto`，评审后生成服务端接口与客户端 | 接口先于实现被讨论，双方可并行开发；多语言天然统一 | 规范要单独维护，生成代码有时不合口味 | 跨团队、多语言、对外开放的接口 |
| **代码优先** | 先写 Controller 或接口，从注解生成规范 | 上手快，规范与代码不会脱节 | 接口设计容易被实现细节牵着走，评审往往在实现之后 | 单团队内部、迭代快的接口 |

两者可以折中：代码优先，但把生成的规范提交入库，在 CI 中比对规范差异、拦截破坏性变更。生成规范与从规范生成代码的具体做法见 [API 文档 · 契约优先：从规范生成代码](/engineering/5_api_doc#五、契约优先-从规范生成代码)。

### 3、用什么描述

- **HTTP 接口**：OpenAPI 3.1，命名、状态码、错误响应等约定见 [API 设计规范](/engineering/4_api_design_rule)
- **RPC 接口**：gRPC 与 Dubbo Triple 用 protobuf 的 `.proto` 文件，编码与兼容规则见 [RPC 协议 · Protobuf](/protocols/5_rpc_protocols#二、protobuf)；Dubbo 用 Java 接口 jar 作契约时，jar 里只放接口与 DTO，不放实现和重依赖，否则一次升级会牵动所有调用方
- **事件**：用 JSON Schema、Avro 或 protobuf 描述消息体，AsyncAPI 可以像 OpenAPI 一样描述主题、消息与订阅关系；Kafka 生态常配合 Schema Registry 在生产时校验兼容性

### 4、契约测试

OpenAPI 加破坏性变更检查能发现「提供方删了什么」，却不知道「调用方用了什么」；消费者驱动契约测试由调用方声明真实依赖、提供方在 CI 中验证，两者叠加才守得住内部接口，见 [契约测试](/testing/6_contract_test)。

## 四、版本与兼容

服务独立发布，滚动发布期间新旧实例同时在线，调用方也不会同一时刻升级，所以**新旧版本并存是常态**。接口演进的目标是：提供方升级时不要求调用方同步发布。

### 1、向后兼容规则

| 规则 | HTTP / JSON | protobuf | 事件 |
|------|-------------|----------|------|
| 只加不删 | 新增响应字段；删除前确认已无人使用 | 新增字段用新编号；删除字段用 `reserved` 保留编号和名字 | 新增字段；旧字段在所有消费者迁移前保留 |
| 新字段可选 | 新增请求参数必须可选，不传时行为与原来一致 | 需要区分「未设置」时用 `optional` 或 wrapper 类型 | 消费者不能假设新字段一定存在 |
| 默认值等于旧行为 | 缺省值的效果与改动前相同 | proto3 标量缺省为 0 / 空串，业务上要能接受 | 处理旧格式事件时按默认值补齐 |
| 不改语义 | 字段含义、单位、枚举含义不变，要改就加新字段 | 不改编号、不改类型 | 同左；语义变了就发新的事件类型 |
| 宽容读者 | 忽略未知字段，未知枚举值走兜底分支 | 未知字段自动跳过 | 消费者忽略不认识的字段与事件类型 |

HTTP 接口逐项的兼容 / 破坏对照见 [API 设计规范 · 版本管理](/engineering/4_api_design_rule#八、版本管理)，protobuf 的细则见 [RPC 协议 · 兼容性规则](/protocols/5_rpc_protocols#_3、兼容性规则)。

### 2、破坏性变更：扩展 - 迁移 - 收缩

必须破坏兼容时，不要原地修改，而是分三步走（Parallel Change）：

1. **扩展**：新增字段、新接口或新版本，与旧的并存，提供方同时支持两种
2. **迁移**：调用方逐个切换；按调用方、按版本统计旧接口的调用量，逐个跟进
3. **收缩**：旧版本调用量归零（或到达约定的下线日期）后，再删除旧字段、旧接口

废弃要有明确流程：文档标注废弃并给出迁移指南 → 响应带 `Deprecation`、`Sunset` 头 → 迁移窗口 → 下线，响应头格式与下线步骤见 [API 设计规范 · 废弃与下线](/engineering/4_api_design_rule#九、废弃与下线)。同时在线的主版本最好不超过两个，否则每个版本都要测试、监控与修复。

### 3、发布顺序与多版本并存

- **请求响应接口**：提供方先发布（新版本能同时处理新旧请求），调用方后发布并开始使用新字段
- **事件**：消费者先升级到能处理新旧两种格式，生产者再开始发送新格式；顺序反过来，老消费者会处理失败或悄悄丢字段
- **多版本并存的两种方式**：同一个服务进程内按版本映射到不同实现（Framework 7 内置 API 版本控制，见 [MVC · API 版本控制](/spring/3_mvc#七、api-版本控制)），或者新旧版本部署为不同实例、按请求携带的版本分流（见 [流量治理 · 服务版本与兼容性](/service-governance/5_traffic_governance#六、服务版本与兼容性)）
- **灰度放量**：新版本先接小比例或带标记的流量，观察错误率与延迟再逐步放大，发布策略见 [发布策略](/devops/7_release_strategy)

## 五、跨服务查询

每个服务独占数据之后，「订单列表带商品名和用户昵称」这类查询不能再 JOIN。三种做法：

| 做法 | 怎么做 | 适合 | 代价 |
|------|--------|------|------|
| **API 组合** | BFF 或查询服务并行调用各服务，在内存中拼接 | 数据量小、要求实时的详情类查询 | 可用性取决于所有被调服务，延迟取最慢的一个；无法跨服务分页、排序、复杂过滤 |
| **CQRS 读模型** | 各服务发布领域事件，查询服务订阅后物化一张宽表（常放 Elasticsearch） | 列表、搜索、报表等复杂查询 | 多维护一套存储与投影程序，读写之间有秒级延迟，投影出错要能重建 |
| **数据冗余 + 事件同步** | 消费方在本地存下需要的少量字段（快照或只读副本），靠事件更新 | 高频读、只需要少量稳定字段（订单里的商品名、成交单价） | 冗余数据最终一致；必须明确字段的 owner 和更新事件，否则副本越改越乱 |

选择顺序：先看是不是边界划错了，一个查询总要跨很多服务往往说明应该合并；边界没问题时，小而实时的查询用 API 组合，复杂查询建读模型，热点少字段直接冗余。冗余存快照还是存引用取决于业务语义，见 [服务拆分 · 共享表的拆法](./2_service_split#_2、共享表的拆法)；读模型的投影实现见 [架构模式与风格 · CQRS（命令查询职责分离）](/architecture/1_arch_patterns#四、cqrs-命令查询职责分离)。

两种做法要避免：直接读别的服务的库（哪怕是只读账号，也会让对方无法自由改表），以及提供「按任意条件查表」的通用查询接口（调用方会把它当成远程 SQL 用）。

## 六、常见坑

| 坑 | 后果 | 做法 |
|----|------|------|
| 所有交互都用同步调用 | 调用链越来越深，一个下游抖动拖垮整条链路，成了「分布式单体」 | 按第一节的判断顺序把旁路改为事件 |
| 用事件发命令 | 发布方实际在等结果，只是把同步调用藏进了 MQ，失败无人处理 | 需要结果用同步调用，多步业务用编排式 Saga |
| 事件只带 ID 且订阅方很多 | 每个订阅方都回查生产方，事件一来就是一波回查流量 | 改为携带状态，或只给需要详情的少数订阅方回查 |
| 在数据库事务里发 MQ | 回滚后消息已发出，或提交后消息丢失 | 本地消息表或事务消息 |
| 共享领域模型 jar | 改一个公共类所有服务都要升级，独立发布名存实亡 | 每个服务定义自己的 DTO，契约靠 OpenAPI / `.proto` |
| 改字段语义或复用 protobuf 编号 | 老调用方不报错但读到错误数据，问题最难发现 | 语义变了就加新字段，删除字段用 `reserved` |
| 异步之后丢了链路 | 出问题时不知道消息从哪来、卡在哪 | traceId 随消息头透传，见 [链路追踪](/observability/3_tracing) |

## 小结

- 同步还是异步看依赖方向：调用方下一步依赖结果、下游失败上游也必须失败时用同步，其余旁路、扇出的操作发布事件
- 事件表达已发生的事实；事件通知简单但会回查，携带状态更解耦但要维护副本，事件溯源是服务内部的持久化方式，按需选择
- 契约包括结构、语义、错误与行为约定；跨团队用契约优先，CI 中用规范比对与契约测试守住破坏性变更
- 兼容规则：只加不删、新字段可选、默认值等于旧行为、不改语义、宽容读者；破坏性变更走扩展 - 迁移 - 收缩，事件让消费者先升级
- 跨服务查询在 API 组合、CQRS 读模型与数据冗余之间按数据量、实时性与查询复杂度取舍，不直接读别人的库
