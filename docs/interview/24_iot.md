# IoT 面试题解答

> 题目清单见 [IoT 面试题](/iot/99_interview)；细节见 [IoT 总览](/iot/0_overview)。
>
> 版本基线：MQTT 5.0（兼顾 3.1.1）、EMQX 5.9+ / 6.x（5.x 配置语法）、TDengine 3.x、Flink 2.2、JDK 21 / Spring Boot 4。

## 一、MQTT 协议

### Q1：MQTT 是什么？为什么适合 IoT？

**一句话**：MQTT 是跑在 TCP 上的轻量级发布 / 订阅协议，设备和服务都只连 Broker，按 Topic 收发消息，互相不用知道对方在哪，所以特别适合海量、弱网、资源紧张的设备。

- 发布 / 订阅：消息经 Broker 按 Topic 转发，新增一个消费者不用改设备
- 报文小：固定头只有 2 字节，适合流量贵、带宽小的蜂窝网络
- 长连接 + 心跳：服务端可以随时下发指令，Keep Alive 发现断线
- 可靠性分级：QoS 0 / 1 / 2 按消息重要程度选
- 通配符：`+` 匹配一层、`#` 匹配剩余所有层，只能用于订阅

→ 详见 [通信协议](/iot/1_protocol#二、mqtt)

### Q2：MQTT 的三个 QoS 等级是什么？QoS 2 能保证端到端恰好一次吗？

**一句话**：QoS 0 最多一次、1 至少一次、2 恰好一次，但它们只管「一跳」（发布方到 Broker、Broker 到订阅方各算一跳），QoS 2 也不是端到端的恰好一次。

| QoS | 语义 | 交互 | 用在哪 |
|-----|------|------|--------|
| 0 | 可能丢 | PUBLISH | 高频遥测 |
| 1 | 可能重复 | PUBLISH → PUBACK | 告警、指令（配合幂等） |
| 2 | 一跳内恰好一次 | 四次握手 | 重复代价极大的场景 |

- 订阅方实际拿到的 QoS 取发布 QoS 和订阅 QoS 的较小值
- Broker 宕机、订阅方处理失败、桥接到 Kafka 再消费，都可能重复或丢
- 实践里大多用 **QoS 1 + 业务幂等**（带请求 ID 去重），比 QoS 2 吞吐高

→ 详见 [通信协议](/iot/1_protocol#_2、qos-三个等级)

### Q3：持久会话、保留消息、遗嘱消息分别解决什么问题？

**一句话**：持久会话解决「断线期间的消息别丢」，保留消息解决「一订阅就拿到当前值」，遗嘱消息解决「设备异常掉线要通知别人」。

- 持久会话：Broker 按 Client ID 保存订阅和离线期间的 QoS 1 / 2 消息，重连后继续投递；前提是 Client ID 固定
- 保留消息：每个 Topic 只留最新一条，新订阅者马上收到；发一条空 payload 的保留消息就清除
- 遗嘱消息：CONNECT 时登记，非正常断开（断网、心跳超时）由 Broker 代发，正常 DISCONNECT 不发
- 常见组合：遗嘱 Topic `devices/{clientId}/status`、payload `offline`、带 retain，上线后再发一条 `online` 覆盖

**常见坑**：所有设备共用一个遗嘱 Topic，状态互相覆盖；每次启动随机生成 Client ID，等于每次都开新会话。

→ 详见 [通信协议](/iot/1_protocol#_3、会话、保留消息与遗嘱)

### Q4：Broker 怎么判断设备离线了？

**一句话**：靠 Keep Alive：Broker 在 1.5 倍 Keep Alive 时间内收不到客户端的**任何报文**就断开连接，并发布遗嘱；但「连着却不上报数据」只能靠业务侧的数据超时检测。

- 客户端在 Keep Alive 间隔内没有别的报文要发时才发 PINGREQ，有业务报文就不用发
- 断开后触发遗嘱消息，EMQX 还会产生 `$events/client/disconnected` 事件
- 采集模块死机但 TCP 连接还在：用 Flink 按设备注册「最后一条数据 + N 秒」的处理时间定时器判断
- 负载均衡的空闲超时必须大于 1.5 倍 Keep Alive，否则空闲设备会被周期性断开

→ 详见 [通信协议](/iot/1_protocol#_1、核心概念)、[数据处理](/iot/4_data#_3、离线检测-keyedprocessfunction-定时器)

### Q5：MQTT 5.0 相比 3.1.1 新增了哪些常用能力？

**一句话**：协议主体没变，加的都是工程上用得着的东西：原因码、共享订阅、消息过期、用户属性、请求 / 响应，以及把 `cleanSession` 拆成两个字段。

- 原因码：CONNACK、PUBACK、SUBACK 等都带原因码，如 `0x87` 未授权、`0x97` 超出配额，排查不用猜
- 共享订阅：`$share/{group}/{topic}`，组内每条消息只给一个成员，类似 Kafka 消费者组
- 消息过期：给控制指令设有效期，设备离线很久上线不会收到一串过期命令
- 请求 / 响应：Response Topic + Correlation Data，下发指令等回执有了标准写法
- 会话控制：Clean Start 管「连接时要不要新会话」，Session Expiry Interval 管「断开后会话留多久」

→ 详见 [通信协议](/iot/1_protocol#_4、mqtt-5-0-新特性)

### Q6：共享订阅是什么？平台服务横向扩容时怎么消费设备消息？

**一句话**：共享订阅让同一组的多个订阅者分摊消息，每条只投给其中一个；后端多实例都订阅 `$share/worker/devices/+/data`，就是天然的负载均衡。

- 不用共享订阅时，每个实例都订阅全量 Topic，消息被重复处理
- 组内分配策略（随机、轮询、按 Client ID 哈希）由 Broker 决定，协议不规定
- 共享订阅打散后，跨实例的顺序要靠 Kafka 分区（按设备 ID 做 Key）或业务版本号保证
- 每个实例的 Client ID 要唯一（拼主机名或 Pod 名），否则互相踢下线

→ 详见 [MQTT 客户端](/iot/6_mqtt_client#_3、订阅与发布)

### Q7：Java 的 MQTT 客户端怎么选？Client ID 和会话有哪些坑？

**一句话**：独立进程用持续维护的 HiveMQ MQTT Client；Spring Boot 服务用 Spring Integration 的 v5 适配器（底层是 Paho）。Paho 的最后一个正式版停在 2020 年的 1.2.5，新代码不要再直接用 mqttv3。

- 持久会话：`cleanStart=false` + 足够长的 `sessionExpiryInterval`，短暂断线不丢 QoS 1 消息
- Client ID：同一实例重启保持不变，多实例之间全局唯一
- 回调线程：回调里只做轻量转发（如写 Kafka），重活放到下游
- Spring Integration：`DirectChannel` 挂多个处理器会轮询分发，每个只收到一半，要按 Topic 路由，一条通道一个处理器

→ 详见 [MQTT 客户端](/iot/6_mqtt_client#一、客户端选型)

## 二、其他协议

### Q8：CoAP / LwM2M、LoRaWAN、NB-IoT、Modbus、OPC UA 分别用在什么场景？

**一句话**：按层次分：MQTT、CoAP 是设备上云的应用层协议；LoRaWAN、NB-IoT 是最后一跳的无线接入；Modbus、OPC UA 是工厂里的工业总线。

| 场景 | 选什么 |
|------|--------|
| 设备 / 网关与云双向通信 | MQTT |
| 电池供电、长时间休眠 | CoAP / LwM2M（UDP，无需长连接） |
| 园区、农场自建低功耗广域网 | LoRaWAN（非授权频段，自建网关） |
| 大范围公共设施 | NB-IoT（运营商基站，按流量付费） |
| 存量 PLC、仪表 | Modbus |
| 新建产线、需要语义互操作 | OPC UA（自带信息模型和安全） |

- NB-IoT 设备进入省电模式后不可达，下发指令要缓存到下次唤醒，这正是设备影子的用途

→ 详见 [通信协议](/iot/1_protocol#九、协议选型速查)

### Q9：Modbus TCP 和 RTU 有什么区别？采集时有哪些常见坑？

**一句话**：TCP 走以太网、靠 MBAP 头分帧；RTU 走 RS-485 串口、靠 CRC 和静默间隔分帧，而且一条总线同一时刻只能有一个请求。最常见的坑是地址偏移、有符号数和字序。

- RTU 严格串行：多个从站排队轮询，一个从站掉线每次都等满超时，所以超时要短、失败的从站要降频
- 地址：手册里的 `40001` 对应协议地址 0，差一位读到的是相邻寄存器，而且不报错
- 负数变几千：可能为负的量要按 `short`（有符号）读
- 浮点数是天文数字：32 位值占两个寄存器，ABCD / CDAB 字序因厂商而异，写进点表
- 连接：每个从站一个长连接，不要每次轮询都新建，很多 PLC 只允许几个并发连接

→ 详见 [Modbus 采集](/iot/7_modbus#六、常见坑)

## 三、平台与接入网关

### Q10：EMQX 5.9 之后许可有什么变化？怎么选 MQTT Broker？

**一句话**：EMQX 从 5.9 起开源版和企业版合并，统一用 BSL 1.1：单节点生产免费，多节点集群要商业 License；需要免费集群可以停在 5.8 开源版，或换别的 Broker。

- 每个版本发布 4 年后自动转为 Apache 2.0；5.8.x 及以前的开源版仍是 Apache 2.0
- 不能把 EMQX 作为托管服务对外提供，也不能嵌进卖给第三方的产品
- 替代品：Mosquitto（轻量单机）、NanoMQ（边缘网关）、VerneMQ（从源码构建可免费集群）、HiveMQ CE（社区版无集群）
- 选型前确认三件事：许可是否允许你的部署方式、时序数据存哪、接入层能否水平扩展

→ 详见 [平台选型](/iot/2_platform#_1、许可变化)

### Q11：MQTT 集群放在四层负载均衡后面要注意什么？

**一句话**：三件事：空闲超时要大于 1.5 倍 Keep Alive、用 PROXY protocol 保留设备真实 IP、重连到别的节点能否恢复订阅取决于持久会话。

- 空闲超时：Keep Alive 60 秒时 Broker 允许 90 秒无报文，LB 超时设 300 秒留余量；设成 30 秒会让空闲设备周期性断线重连
- 真实 IP：不开 PROXY protocol，Broker 看到的全是 LB 的地址，限流和审计都失效
- 会话接管：只有 Clean Start 为 false 且 Session Expiry 大于 0 时，订阅和离线消息才随会话迁移
- TLS：要做双向证书认证时一般透传到 Broker，由 Broker 校验客户端证书
- 连接风暴：客户端重连用指数退避加随机抖动

→ 详见 [平台选型](/iot/2_platform#_3、何时需要集群)

### Q12：只会发私有 TCP 二进制帧的设备怎么接入？坏帧怎么处理？

**一句话**：用 Netty 自研接入网关，把私有协议翻译成统一消息写 Kafka；坏帧的处理方式取决于链路：可靠链路直接断开，DTU 串口透传则跳过一个字节重新找帧头。

- 可靠的直连 TCP：`LengthFieldBasedFrameDecoder` 拆帧，魔数、长度或 CRC 不对就关连接
- 有噪声的 DTU 链路：单个 `ByteToMessageDecoder` 自己找 Magic、校验 CRC，失败丢 1 字节重新同步
- 两种策略不要叠加：长度字段已经切出一帧，再「跳字节找帧头」毫无意义
- 长度按无符号读并设上限；CRC 失败计数进监控，而不是抛异常把设备踢下线
- 有出站消息就必须有编码器，否则 `writeAndFlush` 写不出去

→ 详见 [Netty 接入网关](/iot/9_netty_gateway#二、带-crc-的私有协议帧)

### Q13：海量设备连在多个网关节点上，平台下发指令怎么找到设备？

**一句话**：网关保持无状态，每个节点维护「设备 ID → Channel」的本地注册表，同时把「设备 ID → 节点」的路由写进 Redis 并带过期时间；下发时先查路由，再投递到该节点专属的通道。

- 重复登录：新连接注册时用 `remove(key, value)` 只删自己那条，避免误删新连接
- 第一帧必须鉴权并设超时，鉴权只查本地缓存，不在 IO 线程上访问数据库
- 写出前检查 `isWritable()`，超过高水位说明对端慢，指令拒绝或延后
- 状态放设备影子、规则放规则引擎，节点故障时设备重连到别的节点即可

→ 详见 [Netty 接入网关](/iot/9_netty_gateway#四、连接管理与下行路由)

## 四、数据链路与存储

### Q14：IoT 数据链路怎么设计？为什么要在 EMQX 和 Flink 之间加 Kafka？

**一句话**：典型链路是设备 → EMQX 规则引擎 → Kafka → Flink → 时序库 → Grafana；Kafka 负责缓冲、削峰和重放，让设备批量重连或下游变慢时既不压垮 Broker，也不丢数据。

- EMQX 只做无状态的过滤和格式转换，有状态的窗口、离线检测交给 Flink
- Kafka 消息 Key 用设备 ID：同一设备进同一分区，保证单设备有序
- 下游以 ACL 绑定过的 `clientid` 作为可信设备标识，不信消息体里自报的设备 ID
- 几千台设备、没有复杂计算时，可以省掉 Kafka 和 Flink，用 EMQX 直写 TDengine

→ 详见 [数据处理](/iot/4_data#一、iot-数据链路)

### Q15：TDengine 的超表、子表、TAG 怎么设计？时序数据怎么控制存储成本？

**一句话**：一台设备一张子表，同类设备共用一张超表作模板，TAG 放设备的静态属性；成本靠「原始数据短期保留、降采样结果长期保留」。

- TAG 只放「设备是什么」（型号、位置），不放「测到什么」
- 同一子表同一时间戳再写一次会覆盖，所以 Kafka 重放、至少一次投递不会产生重复行
- 设备 ID 会变成表名，写入前做白名单校验并用参数绑定，不拼 SQL
- 分层保留：原始 7–30 天、5 分钟聚合 1 年、1 小时聚合 3–5 年；聚合层一定要存 `count`
- 降采样在 TDengine 流计算或 Flink 里二选一，两边同时算会口径不一致

→ 详见 [数据处理](/iot/4_data#三、tdengine-超表建模)、[时序数据库](/database/4_nosql/1_time_series_db)

### Q16：设备离线检测为什么用 KeyedProcessFunction 而不用 CEP？告警放在哪一层？

**一句话**：「N 秒内没有数据」是「没发生某事」，用定时器表达最直接：每来一条数据就把处理时间定时器往后推，到点没被推走就是离线。

- 为什么用处理时间：设备不发数据就不会推动事件时间，全部断网时水位线停住，事件时间定时器永远不触发
- 为什么不用 CEP：只有一个节点的模式收到第一条心跳就匹配完成，不会超时
- 「连续 3 次超温」这类有顺序的模式才用 CEP，写成 `times(3).consecutive()`

| 告警类型 | 放在 |
|----------|------|
| 离线、连续超温、多条件组合 | Flink |
| 单指标阈值、趋势 | Grafana |
| 连接断开 | EMQX 规则引擎 |

→ 详见 [数据处理](/iot/4_data#四、flink-2-x-实时处理)

## 五、设备管理与边缘

### Q17：设备影子是什么？desired、reported、delta 分别是什么？并发冲突怎么处理？

**一句话**：影子是云端为每台设备存的一份 JSON 状态，应用写 `desired`（期望），设备写 `reported`（实际），影子服务算出两者的差 `delta` 推给设备；设备离线时应用照样能读能改。

- `delta` 只看 `desired` 里有、且与 `reported` 不同的字段；`delta` 为空表示配置已生效
- `version` 每次更新加 1：应用改 `desired` 带版本做乐观锁，冲突返回 409；设备丢弃版本不大于本地记录的消息
- 设备上线：先订阅 `delta`，再主动拉一次全量影子，影子才是权威来源，持久会话只是补充
- 影子只放「当前状态」，温度曲线写时序库，重启这类一次性命令走带过期时间的指令

→ 详见 [设备影子](/iot/8_device_shadow#四、版本号与冲突处理)

### Q18：OTA 怎么防篡改、防降级、防变砖？

**一句话**：防篡改靠 SHA-256 摘要 + 私钥签名（Ed25519 / ECDSA），防降级靠只增不减的安全版本计数器，防变砖靠 A/B 分区 + 试运行确认 + 自动回退。

- MD5 只能发现传输损坏，挡不住篡改；HTTPS 只保护传输，挡不住对象存储被入侵
- 签名私钥放 KMS / HSM，设备出厂内置公钥，Bootloader 也要验签（安全启动）
- 安全版本计数器写在 eFuse 或安全芯片里，新固件确认正常后才提升
- 新固件写备用分区并标记「待测试」，自检通过才确认，崩溃或超时未确认就回到旧分区

→ 详见 [OTA 升级](/iot/10_ota#二、固件签名)

### Q19：OTA 的灰度发布和任务状态怎么设计？

**一句话**：按批次灰度（1% → 10% → 50% → 全量），失败率超阈值自动暂停；任务状态用条件更新推进，MQTT 发送不放进数据库事务。

- 下发限速 + CDN 分发，避免全量同时下载打满带宽；下载用短时效预签名 URL 和 HTTP Range 断点续传
- 前置条件：设备在线、电量够、没在业务使用中
- 条件更新：任务 ID、设备 ID 匹配且当前状态在允许的来源状态里才更新，一步完成检查和修改，防并发、防乱序、防伪造
- 先发消息再更新状态，崩溃时下一轮重发，设备按 `taskId` 去重
- 定时扫描卡在中间状态的任务，标记超时并计入失败率

→ 详见 [OTA 升级](/iot/10_ota#五、任务编排与灰度)

### Q20：规则引擎怎么避免告警风暴和动作重复执行？为什么不能在数据库事务里发消息？

**一句话**：边沿触发 + 静默期解决告警风暴，执行前用 Redis `SET NX` 占位解决重复执行；事务里发消息的问题是回滚了消息却撤不回，所以事务提交后再发。

- 电平触发：温度在 85℃ 停一小时，每 10 秒一条就是 360 条告警；边沿触发只在「不满足 → 满足」时执行一次
- 幂等键：告警用「规则 + 设备」并设静默期，指令和 Webhook 加上消息时间戳
- 提交后再发：`@TransactionalEventListener(AFTER_COMMIT)`；要求严格不丢时用本地消息表
- 外部调用还会长时间占住数据库连接和行锁，Webhook 要配超时并做 SSRF 校验

→ 详见 [规则引擎](/iot/11_rule_engine#四、动作执行)

### Q21：边缘和云端怎么分工？KubeEdge 的断网自治是怎么做到的？

**一句话**：要毫秒级响应、断网也必须工作的逻辑（本地告警、联动控制、协议转换）放边缘；要全局数据和算力的（模型训练、跨站分析、设备管理）放云端，规则和模型由云端下发。

- KubeEdge：云端 CloudCore、边缘 EdgeCore，通过 WebSocket（可选 QUIC）同步资源
- 断网自治：EdgeCore 把元数据持久化到本地，断网时继续管理 Pod，重启后也能从本地恢复
- 设备管理：DeviceModel / Device CRD 加 Mapper，可写属性的期望值思路与设备影子相同
- 边缘 AI 模型更新要原子发布、先建后换、可回退，签名与灰度复用 OTA 那一套

→ 详见 [边缘计算](/iot/3_edge#二、云边端三层架构)

## 六、设备安全

### Q22：一机一密和一型一密有什么区别？各有什么风险？

**一句话**：一机一密是每台设备出厂烧录唯一密钥或证书，泄露只影响一台；一型一密是同型号共用一个产品密钥，首次上线再换本机密钥，产品密钥一旦泄露，攻击者就能伪造该型号的新设备。

- 一型一密只是产线没法逐台烧录时的折中，换到本机密钥后立刻弃用产品密钥
- 动态注册接口必须校验序列号白名单，每台只能注册一次
- 密码类方案用 HMAC 签名：设备用密钥对 `clientId + 时间戳` 签名当密码，密钥本身不上网
- HMAC 需要原始密钥，台账里用 KMS 加密存储，不能像用户密码那样只存哈希

→ 详见 [设备安全](/iot/5_security#_2、一机一密与一型一密)

### Q23：设备证书认证怎么做？EMQX 的 verify_peer 和 fail_if_no_peer_cert 有什么区别？

**一句话**：私钥在设备的安全芯片里生成、永不离开设备，只把 CSR 交给 CA 签名；EMQX 要同时开 `verify_peer` 和 `fail_if_no_peer_cert = true` 才算强制双向认证。

- `verify_peer` 只表示「请求并校验客户端证书」，客户端不出示证书照样能连
- `peer_cert_as_clientid = cn` 把证书 CN 绑定为 clientid，必须配合强制 mTLS，否则可以自签证书随便填 CN
- 证书选 ECDSA P-256，比 RSA 短、MCU 上握手快；用途写 `clientAuth`
- 轮换：设备本地生成新密钥、提交新 CSR（可用 EST）；吊销走 CRL，在 TLS 握手阶段就拒绝

→ 详见 [设备安全](/iot/5_security#三、传输加密)、[HTTPS 与 TLS](/protocols/3_https_tls)

### Q24：EMQX 的认证和授权怎么分工？怎么限制设备只能访问自己的 Topic？

**一句话**：认证回答「你是谁、能不能连」，授权回答「能发布 / 订阅哪些 Topic」；ACL 用 `${clientid}` 占位符只放行 `devices/${clientid}/...`，最后用 `no_match = deny` 加 `{deny, all}` 兜底。

- 配置了认证器后，未通过认证的客户端直接被拒，不再需要单独的「禁止匿名」规则
- 认证服务必须校验 clientid 与设备身份一致：否则设备拿 `+` 当 clientid，`devices/${clientid}/cmd` 就成了通配订阅
- 按 username 授权的前提是 username 也经过认证（证书场景用 `peer_cert_as_username = cn`）
- 5.x 用 `${clientid}` / `${username}`，4.x 的 `%c` / `%u` 不再生效；REST API 用 API Key 认证

→ 详见 [设备安全](/iot/5_security#四、topic-授权-emqx-acl)

### Q25：怎么发现设备暴力破解和越权尝试？

**一句话**：EMQX 的审计日志只记管理操作，设备侧的安全事件要用规则引擎订阅 `$events/...` 事件，转到 Kafka 或 SIEM 再配告警。

- `$events/client/connack`、`$events/auth/check_authn_complete`：认证失败，看来源 IP
- `$events/auth/check_authz_complete` 里 `result = deny`：越权尝试
- 典型规则：同一 IP 短时间大量认证失败、单台设备反复越权、设备从没出现过的地区上线
- 处置：按来源 IP 限速、吊销证书或凭证，并结合网段微隔离限制横向扩散

→ 详见 [设备安全](/iot/5_security#六、审计与零信任落地)
