# IoT 面试题解答

> 题目清单见 [IoT 面试题](/iot/99_interview)；细节见 [IoT 总览](/iot/0_overview)。
>
> 版本基线：MQTT 5.0（兼顾 3.1.1）、EMQX 6.x（配置沿用 5.x 起的 HOCON 语法）、TDengine 3.x、Flink 2.2、JDK 21 / Spring Boot 4。

## 一、MQTT 协议

### Q1：MQTT 是什么？为什么适合 IoT？

**一句话**：MQTT 是跑在 TCP 上的轻量级发布 / 订阅协议，设备和服务都只连 Broker，按 Topic 收发消息，互相不用知道对方在哪，所以特别适合海量、弱网、资源紧张的设备。

- 发布 / 订阅：消息经 Broker 按 Topic 转发，新增一个消费者不用改设备
- 报文小：固定头只有 2 字节，适合流量贵、带宽小的蜂窝网络
- 长连接 + 心跳：服务端可以随时下发指令，Keep Alive 发现断线
- 可靠性分级：QoS 0 / 1 / 2 按消息重要程度选
- 通配符：`+` 匹配一层、`#` 匹配剩余所有层，只能用于订阅

→ 详见 [通信协议](/iot/1_basics/1_protocol#二、mqtt)

### Q2：MQTT 的三个 QoS 等级是什么？QoS 2 能保证端到端恰好一次吗？

**一句话**：QoS 0 最多一次、1 至少一次、2 恰好一次，但它们只管「一跳」（发布方到 Broker、Broker 到订阅方各算一跳），QoS 2 也不是端到端的恰好一次。

| QoS | 语义 | 交互 | 用在哪 |
|-----|------|------|--------|
| 0 | 可能丢 | PUBLISH | 高频且可丢的测点 |
| 1 | 可能重复 | PUBLISH → PUBACK | 遥测的默认选择、告警、指令（配合幂等） |
| 2 | 一跳内恰好一次 | 四次握手 | 重复代价极大的场景 |

- 订阅方实际拿到的 QoS 取发布 QoS 和订阅 QoS 的较小值
- Broker 宕机、订阅方处理失败、桥接到 Kafka 再消费，都可能重复或丢
- 实践里大多用 **QoS 1 + 业务幂等**（带请求 ID 去重），比 QoS 2 吞吐高

→ 详见 [通信协议](/iot/1_basics/1_protocol#_2、qos-三个等级)

### Q3：持久会话、保留消息、遗嘱消息分别解决什么问题？

**一句话**：持久会话解决「断线期间的消息别丢」，保留消息解决「一订阅就拿到当前值」，遗嘱消息解决「设备异常掉线要通知别人」。

- 持久会话：Broker 按 Client ID 保存订阅和离线期间的 QoS 1 / 2 消息，重连后继续投递；前提是 Client ID 固定
- 保留消息：每个 Topic 只留最新一条，新订阅者马上收到；发一条空 payload 的保留消息就清除
- 遗嘱消息：CONNECT 时登记，非正常断开（断网、心跳超时）由 Broker 代发，正常 DISCONNECT 不发
- 常见组合：遗嘱 Topic `devices/{clientId}/status`、payload `offline`、带 retain，上线后再发一条 `online` 覆盖

**常见坑**：所有设备共用一个遗嘱 Topic，状态互相覆盖；每次启动随机生成 Client ID，等于每次都开新会话。

→ 详见 [通信协议](/iot/1_basics/1_protocol#_3、会话、保留消息与遗嘱)

### Q4：Broker 怎么判断设备离线了？

**一句话**：靠 Keep Alive：Broker 在 1.5 倍 Keep Alive 时间内收不到客户端的**任何报文**就断开连接，并发布遗嘱；但「连着却不上报数据」只能靠业务侧的数据超时检测。

- 客户端在 Keep Alive 间隔内没有别的报文要发时才发 PINGREQ，有业务报文就不用发
- 断开后触发遗嘱消息，EMQX 还会产生 `$events/client/disconnected` 事件
- 采集模块死机但 TCP 连接还在：用 Flink 按设备注册「最后一条数据 + N 秒」的处理时间定时器判断
- 负载均衡的空闲超时必须大于 1.5 倍 Keep Alive，否则空闲设备会被周期性断开

→ 详见 [通信协议](/iot/1_basics/1_protocol#_1、核心概念)、[遥测数据链路](/iot/3_platform/2_data#_3、离线检测-keyedprocessfunction-定时器)

### Q5：MQTT 5.0 相比 3.1.1 新增了哪些常用能力？

**一句话**：协议主体没变，加的都是工程上用得着的东西：原因码、共享订阅、消息过期、用户属性、请求 / 响应，以及把 `cleanSession` 拆成两个字段。

- 原因码：CONNACK、PUBACK、SUBACK 等都带原因码，如 `0x87` 未授权、`0x97` 超出配额，排查不用猜
- 共享订阅：`$share/{group}/{topic}`，组内每条消息只给一个成员，类似 Kafka 消费者组
- 消息过期：给控制指令设有效期，设备离线很久上线不会收到一串过期命令
- 请求 / 响应：Response Topic + Correlation Data，下发指令等回执有了标准写法
- 会话控制：Clean Start 管「连接时要不要新会话」，Session Expiry Interval 管「断开后会话留多久」

→ 详见 [通信协议](/iot/1_basics/1_protocol#_4、mqtt-5-0-新特性)

### Q6：共享订阅是什么？平台服务横向扩容时怎么消费设备消息？

**一句话**：共享订阅让同一组的多个订阅者分摊消息，每条只投给其中一个；后端多实例都订阅 `$share/worker/devices/+/telemetry`，就是天然的负载均衡。

- 不用共享订阅时，每个实例都订阅全量 Topic，消息被重复处理
- 组内分配策略（随机、轮询、按 Client ID 哈希）由 Broker 决定，协议不规定
- 共享订阅打散后，跨实例的顺序要靠 Kafka 分区（按设备 ID 做 Key）或业务版本号保证
- 每个实例的 Client ID 要唯一且重启后不变（拼稳定的实例编号），否则互相踢下线，或留下没人认领的旧会话

→ 详见 [MQTT 客户端](/iot/2_access/3_mqtt_client#_3、发布与关闭)

### Q7：Java 的 MQTT 客户端怎么选？Client ID 和会话有哪些坑？

**一句话**：独立进程用持续维护的 HiveMQ MQTT Client；Spring Boot 服务用 Spring Integration 的 v5 适配器（底层是 Paho）。Paho 的最后一个正式版停在 2020 年的 1.2.5，新代码不要再直接用 mqttv3。

- 持久会话：`cleanStart=false` + 足够长的 `sessionExpiryInterval`，短暂断线不丢 QoS 1 消息
- Client ID：同一实例重启保持不变，多实例之间全局唯一
- 回调线程：回调里只做轻量转发（如写 Kafka），重活放到下游
- Spring Integration：`DirectChannel` 挂多个处理器会轮询分发，每个只收到一半，要按 Topic 路由，一条通道一个处理器

→ 详见 [MQTT 客户端](/iot/2_access/3_mqtt_client#一、客户端选型)

## 二、其他协议

### Q8：CoAP / LwM2M、LoRaWAN、NB-IoT、Modbus、OPC UA 分别用在什么场景？

**一句话**：按层次分：MQTT、CoAP 是设备上云的应用层协议；LoRaWAN、NB-IoT 是最后一跳的无线接入；Modbus、OPC UA 是工厂里的工业总线。

| 场景 | 选什么 |
|------|--------|
| 设备 / 网关与云双向通信 | MQTT |
| 电池供电、长时间休眠 | CoAP / LwM2M（UDP，无需长连接） |
| 园区、农场自建低功耗广域网 | LoRaWAN（非授权频段，自建网关） |
| 大范围公共设施 | NB-IoT（运营商基站，按流量付费） |
| 存量 PLC、仪表 | Modbus |
| 新建产线、需要语义互操作 | OPC UA（自带信息模型和安全） |

- NB-IoT 设备进入省电模式后不可达，下发指令要缓存到下次唤醒，这正是设备影子的用途

→ 详见 [通信协议](/iot/1_basics/1_protocol#九、协议选型速查)

### Q9：Modbus TCP 和 RTU 有什么区别？采集时有哪些常见坑？

**一句话**：TCP 走以太网、靠 MBAP 头分帧；RTU 走 RS-485 串口、靠 CRC 和静默间隔分帧，而且一条总线同一时刻只能有一个请求。最常见的坑是地址偏移、有符号数和字序。

- RTU 严格串行：多个从站排队轮询，一个从站掉线每次都等满超时，所以超时要短、失败的从站要降频
- 地址：手册里的 `40001` 对应协议地址 0，差一位读到的是相邻寄存器，而且不报错
- 负数变几千：可能为负的量要按 `short`（有符号）读
- 浮点数是天文数字：32 位值占两个寄存器，字节序有 ABCD、CDAB、BADC、DCBA 四种，因厂商而异，写进点表
- 连接：每个从站一个长连接，不要每次轮询都新建，很多 PLC 只允许几个并发连接

→ 详见 [Modbus 采集](/iot/2_access/4_modbus#六、常见坑)

## 三、平台与接入网关

### Q10：EMQX 5.9 之后许可有什么变化？怎么选 MQTT Broker？

**一句话**：EMQX 从 5.9 起开源版和企业版合并，统一用 BSL 1.1：单节点生产免费，多节点集群要商业 License；需要免费集群可以换别的 Broker；停在 5.8 开源版也行，但它已于 2026-02-28 停止维护，只适合内网或过渡期。

- 每个版本发布 4 年后自动转为 Apache 2.0；5.8.x 及以前的开源版仍是 Apache 2.0，但不再有缺陷修复和安全补丁
- 不能把 EMQX 作为托管服务对外提供，也不能嵌进卖给第三方的产品
- 替代品：Mosquitto（轻量单机）、NanoMQ（边缘网关）、VerneMQ（从源码构建可免费集群）、HiveMQ CE（社区版无集群）
- 选型前确认三件事：许可是否允许你的部署方式、时序数据存哪、接入层能否水平扩展

→ 详见 [EMQX 许可与部署](/iot/1_basics/3_emqx_deploy#二、许可变化)

### Q11：MQTT 集群放在四层负载均衡后面要注意什么？

**一句话**：三件事：空闲超时要大于 1.5 倍 Keep Alive、用 PROXY protocol 保留设备真实 IP、重连到别的节点能否恢复订阅取决于持久会话。

- 空闲超时：Keep Alive 60 秒时 Broker 允许 90 秒无报文，LB 超时设 300 秒留余量；设成 30 秒会让空闲设备周期性断线重连
- 真实 IP：不开 PROXY protocol，Broker 看到的全是 LB 的地址，限流和审计都失效
- 会话接管：只有 Clean Start 为 false 且 Session Expiry 大于 0 时，订阅和离线消息才随会话迁移
- TLS：要做双向证书认证时一般透传到 Broker，由 Broker 校验客户端证书
- 连接风暴：客户端重连用指数退避加随机抖动

→ 详见 [EMQX 许可与部署](/iot/1_basics/3_emqx_deploy#五、三节点集群-需-license)

### Q12：只会发私有 TCP 二进制帧的设备怎么接入？坏帧怎么处理？

**一句话**：用 Netty 自研接入网关，把私有协议翻译成统一消息写 Kafka；坏帧的处理方式取决于链路：可靠链路直接断开，DTU 串口透传则跳过一个字节重新找帧头。

- 可靠的直连 TCP：`LengthFieldBasedFrameDecoder` 拆帧，魔数、长度或 CRC 不对就关连接
- 有噪声的 DTU 链路：单个 `ByteToMessageDecoder` 自己找 Magic、校验 CRC，失败丢 1 字节重新同步
- 两种策略不要叠加：长度字段已经切出一帧，再「跳字节找帧头」毫无意义
- 长度按无符号读并设上限；CRC 失败计数进监控，而不是抛异常把设备踢下线
- 有出站消息就必须有编码器，否则 `writeAndFlush` 写不出去

→ 详见 [Netty 接入网关](/iot/2_access/6_netty_gateway#二、带-crc-的私有协议帧)

### Q13：海量设备连在多个网关节点上，平台下发指令怎么找到设备？

**一句话**：网关保持无状态，每个节点维护「设备 ID → Channel」的本地注册表，同时把「设备 ID → 节点」的路由写进 Redis 并带过期时间；下发时先查路由，再投递到该节点专属的通道。

- 重复登录：新连接注册时用 `remove(key, value)` 只删自己那条，避免误删新连接
- 第一帧必须鉴权并设超时，鉴权只查本地缓存，不在 IO 线程上访问数据库
- 写出前检查 `isWritable()`，超过高水位说明对端慢，指令拒绝或延后
- 状态放设备影子、规则放规则引擎，节点故障时设备重连到别的节点即可

→ 详见 [Netty 接入网关](/iot/2_access/6_netty_gateway#四、连接管理与下行路由)

### Q14：网关代子设备接入时，平台凭什么相信「这条数据是 meter-01 的」？ACL 之外为什么还要核对归属？

**一句话**：主流平台有两种信任模型：子设备自带凭据（网关只转发，伪造不了子设备），或者只认证网关、子设备 ID 由网关在载荷里声明；后者 ACL 只能管住 Topic，载荷里写的是谁还得平台查拓扑表。

| | 子设备自带凭据 | 信任网关 |
|---|---|---|
| 代表 | 阿里云、Greengrass、Azure 透明网关 | ThingsBoard、Azure 身份转换 |
| 网关被攻破 | 伪造不了子设备 | 能伪造它名下的子设备，碰不到别的网关的 |
| 适合 | 有 MCU、能存密钥的终端 | Modbus 仪表这类没有身份的存量设备 |

- ACL 用 `gateways/${clientid}/…` 只保证网关写自己的前缀，Broker 不看载荷里的子设备 ID
- 拆包时逐台核对「子设备确实绑定在这个网关名下且未禁用」，不合格的丢弃并记安全事件
- 绑定只走平台接口，网关的 `connect` 只报在线；网关能自建绑定，被攻破的网关就能把任意设备拉到自己名下
- 下行指令由平台改投网关的 `cmd` Topic，免得按子设备逐条写 ACL

→ 详见 [网关与子设备](/iot/2_access/5_gateway_subdevice#_2、两种信任模型)

### Q15：连接风暴为什么会越来越重？设备和 Broker 各该怎么防？

**一句话**：危险在放大：认证变慢 → 设备等不到 CONNACK 超时 → 立刻重试 → 认证请求更多 → 更慢；要在设备侧把重连摊开，在 Broker 侧按最慢的一环限速。

- 设备：指数退避加全抖动，等待时间在 `[0, min(上限, 基数 × 2^n)]` 里随机取；只有指数没有抖动，同一刻掉线的设备会同一刻重试
- 冷启动先随机等一会儿再首连；CONNACK 是限流类原因码时退避更长，凭据错误就别再狂试
- Broker：`max_conn_rate` 按认证服务每秒能处理的次数定，不按 Broker 能扛多少定；抖动检测把反复重连的客户端挡在认证之前
- 认证服务：身份走缓存、不用慢哈希，过载时快速失败而不是挂到超时

**常见坑**：负载均衡没开 PROXY protocol，按 IP 的限速和封禁全落在负载均衡自己的地址上。

→ 详见 [海量连接与连接风暴](/iot/2_access/7_connection_storm#一、风暴是怎么形成的)

## 四、物模型与指令

### Q16：物模型的属性、事件、服务怎么区分？各走哪条通道？

**一句话**：属性是「设备有什么数据和配置」，事件是「设备主动告诉平台发生了什么」，服务是「平台能让设备做什么」；物模型挂在产品上，同型号设备共用一份。

| 要素 | 例子 | 通道 |
|------|------|------|
| 只读属性 | 温度、湿度 | 遥测 `devices/{id}/telemetry` |
| 读写属性 | 上报周期 | 设备影子的 `desired` / `reported` |
| 事件 | 高温告警 | `devices/{id}/event`，载荷带事件标识 |
| 服务 | 重启 | 指令 `devices/{id}/cmd` 与 `…/response` |

- 「设置属性」不占指令通道：改的是影子里的期望值，设备离线也不丢
- 事件级别（信息、告警、故障）写在模型里，不放进载荷
- 名字和划分对齐阿里云 TSL；Azure DTDL 把时序数据和状态分成 Telemetry、Property 两类

→ 详见 [物模型](/iot/3_platform/1_thing_model#三、三要素与数据通道)

### Q17：一条上报里有一个测点不合格，整条拒收吗？

**一句话**：不拒收：逐点校验，合格的照常入库，不合格的剔除并留痕；主流平台（阿里云弱校验、Azure IoT Central）也都不会因为个别测点拒收整条。

- 校验项：标识是否定义、类型是否相符、是否在取值范围内、枚举值是否存在
- 超范围的值多半是传感器故障码（−127、65535），放进去就是曲线上的一根尖刺
- 被剔除的测点进死信、日志或指标，不用 0 或上一个值顶替；全部不合格才把整条当坏消息
- `INT` 接受 `220.0`：不少固件的 JSON 库把数字一律按浮点输出

**常见坑**：一个探头坏了，整台设备的数据全没了，就是因为一个测点不合格就拒收整条。

→ 详见 [物模型](/iot/3_platform/1_thing_model#_2、上报校验)

### Q18：物模型发布以后要改怎么办？

**一句话**：只增不改：新增属性、事件、服务和放宽范围是兼容的；改标识、改类型、改单位、收窄范围都不兼容，不原地改，新增一个标识、旧的标记为废弃。

- 已发布的模型有三方依赖：出厂的固件、历史数据、下游应用
- 类型不能改的根源在存储：时序库的一列写入过某种类型后不能再写别的类型
- 主流平台都把「已发布」当成一道闸：阿里云发布后不能编辑，DTDL 已发布的模型不可变、新版本用新 ID
- 真要做不兼容的改动就新建一个产品，不让同一个产品里同时存在两种互不兼容的设备

→ 详见 [物模型](/iot/3_platform/1_thing_model#_3、版本与发布)

### Q19：什么时候改设备影子的 desired，什么时候下发指令？

**一句话**：要设备「进入某个状态」用影子 `desired`（上报周期、阈值、开关），要设备「现在做一件事并知道结果」用指令（重启、拍照、开门）；Azure 的官方选型指南也是这样划分的。

| | 影子 desired | 指令 |
|---|---|---|
| 关心 | 最终状态，中间改过几次无所谓 | 每一次都要执行且只执行一次 |
| 设备离线 | 保留期望值，上线后对齐 | 立即失败，或缓存到上线并带过期时间 |
| 结果 | `delta` 清空即生效 | 每次调用一个状态与结果 |

- 把「设置上报周期」做成指令，设备离线时这次设置就丢了
- 把「重启」写进影子，设备每次上线对齐状态都可能再重启一次

→ 详见 [指令下发与服务调用](/iot/3_platform/4_command#_1、两类下行)

### Q20：指令被重复投递了，怎么保证设备只执行一次？

**一句话**：两端各管一半：平台生成命令 ID、重发时沿用同一个；设备记住最近处理过的命令 ID 和结果，重复到达时不再执行，直接把上次的结果再应答一遍。

- 重复的来源：QoS 1 重投、平台补发、调用方重试、上线事件重复触发补发
- 调用方传了业务幂等键（如工单号）时，同一个键只建一条命令
- 离线时不把命令发进 Broker 排队，命令带过期时间，上线后按创建顺序补发未过期的
- 平台判定的超时不算终态：设备迟到的成功应答照样记账，否则运维看到「超时」去重发，设备就重启两次

→ 详见 [指令下发与服务调用](/iot/3_platform/4_command#_1、幂等-重发不等于重复执行)

### Q21：同步调用设备的指令怎么实现？平台多实例时应答怎么回到发起的实例？

**一句话**：同步是「异步加一个等待」：命令先落库、发出去，调用方拿一个带超时的 `CompletableFuture` 等结果；多实例下收到应答的实例更新命令表后广播结果，持有等待者的实例完成它。

- 不在业务线程里阻塞或轮询数据库，控制器直接返回 `CompletableFuture`，超时返回 504
- 先登记等待者再发送，应答再快也不会漏；先发消息再标 `SENT`，崩溃时宁可重发
- 共享订阅把一条应答只分给一个实例，等待它的可能在另一个实例上，所以要用 Redis 发布订阅广播
- 另一种做法是 MQTT 5 的 Response Topic 填实例专属 Topic，但设备的 ACL 要放宽，3.1.1 设备用不上

**常见坑**：广播丢了的那次同步调用按超时处理，命令表里的状态仍然正确，调用方要能查状态而不是直接重发。

→ 详见 [指令下发与服务调用](/iot/3_platform/4_command#_4、多实例-应答回到发起的实例)

## 五、数据链路与存储

### Q22：IoT 数据链路怎么设计？为什么要在 EMQX 和 Flink 之间加 Kafka？

**一句话**：典型链路是设备 → EMQX 规则引擎 → Kafka → Flink → 时序库 → Grafana；Kafka 负责缓冲、削峰和重放，让设备批量重连或下游变慢时既不压垮 Broker，也不丢数据。

- EMQX 只做无状态的过滤和格式转换，有状态的窗口、离线检测交给 Flink
- Kafka 消息 Key 用设备 ID：同一设备进同一分区，保证单设备有序
- 下游以 ACL 绑定过的 `clientid` 作为可信设备标识，不信消息体里自报的设备 ID
- 几千台设备、没有复杂计算时，可以省掉 Kafka 和 Flink，用 EMQX 直写 TDengine

→ 详见 [遥测数据链路](/iot/3_platform/2_data#一、iot-数据链路)

### Q23：TDengine 的超表、子表、TAG 怎么设计？时序数据怎么控制存储成本？

**一句话**：一台设备一张子表，同类设备共用一张超表作模板，TAG 放设备的静态属性；成本靠「原始数据短期保留、降采样结果长期保留」。

- TAG 只放「设备是什么」（型号、位置），不放「测到什么」
- 同一子表同一时间戳再写一次会覆盖，所以 Kafka 重放、至少一次投递不会产生重复行
- 设备 ID 会变成表名，写入前做白名单校验并用参数绑定，不拼 SQL
- 分层保留：原始 7–30 天、5 分钟聚合 1 年、1 小时聚合 3–5 年；聚合层一定要存 `count`
- 降采样在 TDengine 流计算或 Flink 里二选一，两边同时算会口径不一致

→ 详见 [遥测数据链路](/iot/3_platform/2_data#三、tdengine-超表建模)、[时序数据库概览](/nosql/8_tsdb)

### Q24：设备离线检测为什么用 KeyedProcessFunction 而不用 CEP？告警放在哪一层？

**一句话**：「N 秒内没有数据」是「没发生某事」，用定时器表达最直接：每来一条数据就把处理时间定时器往后推，到点没被推走就是离线。

- 为什么用处理时间：设备不发数据就不会推动事件时间，全部断网时水位线停住，事件时间定时器永远不触发
- 为什么不用 CEP：只有一个节点的模式收到第一条心跳就匹配完成，不会超时
- 「连续 3 次超温」这类有顺序的模式才用 CEP，写成 `times(3).consecutive()`

| 告警类型 | 放在 |
|----------|------|
| 离线、连续超温、多条件组合 | Flink |
| 单指标阈值、趋势 | Grafana |
| 连接断开 | EMQX 规则引擎 |
| 设备联动、要关联业务数据 | 触发-条件-动作规则引擎 |

→ 详见 [遥测数据链路](/iot/3_platform/2_data#四、flink-2-x-实时处理)

## 六、设备管理与边缘

### Q25：设备影子是什么？desired、reported、delta 分别是什么？并发冲突怎么处理？

**一句话**：影子是云端为每台设备存的一份 JSON 状态，应用写 `desired`（期望），设备写 `reported`（实际），影子服务算出两者的差 `delta` 推给设备；设备离线时应用照样能读能改。

- `delta` 只看 `desired` 里有、且与 `reported` 不同的字段；`delta` 为空表示配置已生效
- `version` 每次更新加 1：应用改 `desired` 带版本做乐观锁，冲突返回 409；设备丢弃版本不大于本地记录的消息
- 设备上线：先订阅 `delta`，再主动拉一次全量影子，影子才是权威来源，持久会话只是补充
- 影子只放「当前状态」，温度曲线写时序库，重启这类一次性命令走带过期时间的指令

→ 详见 [设备影子](/iot/3_platform/3_device_shadow#四、版本号与冲突处理)

### Q26：OTA 怎么防篡改、防降级、防变砖？

**一句话**：防篡改靠 SHA-256 摘要 + 私钥签名（默认 ECDSA P-256，启动链与工具都支持时用 Ed25519），防降级靠只增不减的安全版本计数器，防变砖靠 A/B 分区 + 试运行确认 + 自动回退。

- MD5 只能发现传输损坏，挡不住篡改；HTTPS 只保护传输，挡不住对象存储被入侵
- 签名私钥放 KMS / HSM，设备出厂内置公钥，Bootloader 也要验签（安全启动）
- 安全版本计数器写在 eFuse 或安全芯片里，新固件确认正常后才提升
- 新固件写备用分区并标记「待测试」，自检通过才确认，崩溃或超时未确认就回到旧分区

→ 详见 [OTA 升级](/iot/3_platform/5_ota#二、固件签名)

### Q27：OTA 的灰度发布和任务状态怎么设计？

**一句话**：按批次灰度（1% → 10% → 50% → 全量），失败率超阈值自动暂停；任务状态用条件更新推进，MQTT 发送不放进数据库事务。

- 下发限速 + CDN 分发，避免全量同时下载打满带宽；下载用短时效预签名 URL 和 HTTP Range 断点续传
- 前置条件：设备在线、电量够、没在业务使用中
- 条件更新：任务 ID、设备 ID 匹配且当前状态在允许的来源状态里才更新，一步完成检查和修改，防并发、防伪造，乱序到达的倒退上报直接拒绝
- 先发消息再更新状态，崩溃时下一轮重发，设备按 `taskId` 去重
- 定时扫描卡在中间状态的任务，标记超时并计入失败率

→ 详见 [OTA 升级](/iot/3_platform/5_ota#五、任务编排与灰度)

### Q28：主流平台的规则引擎有哪几类？各适合干什么？

**一句话**：三类：SQL 式数据流转（AWS IoT Rules、EMQX 规则引擎）把消息过滤后转发出去；流程与脚本式（ThingsBoard 规则链）做多步加工与分支；触发-条件-动作式（阿里云场景联动、华为云设备联动、ThingsBoard 告警规则）给业务人员配联动和告警。

- 共性都是数据源、条件、动作三件事；数据源可以是设备消息、上下线事件或定时
- SQL 式一条消息一次判断、无状态，「持续 5 分钟」「连续 3 次」这类要状态的条件做不了
- 三类可以叠用：Broker 侧的 SQL 规则把数据搬进 Kafka，平台内的规则面向业务配联动与告警
- 自己实现的通常是第三类：触发器之间为或、条件之间为与，「不满足 → 满足」时执行动作

→ 详见 [规则引擎与告警](/iot/3_platform/6_rule_engine#_1、三类模型)

### Q29：规则引擎怎么避免告警风暴和动作重复执行？为什么不能在数据库事务里发消息？

**一句话**：边沿触发加告警去重解决告警风暴，执行前用 Redis `SET NX` 占位解决重复执行；事务里发消息的问题是回滚了消息却撤不回，所以事务提交后再发。

- 电平触发：温度在 85℃ 停一小时，每 10 秒一条就是 360 条告警；边沿触发只在「不满足 → 满足」时执行一次
- 去重：告警靠「同一设备同一类型只有一条活动告警」，指令和 Webhook 用「规则 + 设备 + 动作 + 消息时间戳」算出请求 ID 占位
- 提交后再发：`@TransactionalEventListener(AFTER_COMMIT)`；要求严格不丢时用本地消息表
- 外部调用还会长时间占住数据库连接和行锁，Webhook 要配超时并做 SSRF 校验

→ 详见 [规则引擎与告警](/iot/3_platform/6_rule_engine#四、动作执行)

### Q30：设备告警为什么要做成有状态的对象？四种状态是什么？

**一句话**：告警不是一条条通知，而是有生命周期的对象：同一设备同一类型任意时刻只有一条活动告警，靠「是否已确认」「是否已清除」两个独立维度组合出四种状态，参照的是 ThingsBoard 的告警模型。

| | 未确认 | 已确认 |
|---|---|---|
| 活动 | 问题还在，没人处理 | 问题还在，已有人处理 |
| 已清除 | 自己恢复了，没人看过 | 闭环，归档 |

- 去重：再次触发只更新已有那条的最近时间与读数，清除之后再坏才新建一条，比按时间窗口静默更准
- 确认只表示「有人看到了」，不清除告警；清除由规则的「满足 → 不满足」边沿或人工触发，记录保留
- 严重级别只升不降；活动未确认超时通知下一级，属于通知路由

→ 详见 [规则引擎与告警](/iot/3_platform/6_rule_engine#五、设备告警模型)

### Q31：边缘和云端怎么分工？KubeEdge 的断网自治是怎么做到的？

**一句话**：要毫秒级响应、断网也必须工作的逻辑（本地告警、联动控制、协议转换）放边缘；要全局数据和算力的（模型训练、跨站分析、设备管理）放云端，规则和模型由云端下发。

- KubeEdge：云端 CloudCore、边缘 EdgeCore，通过 WebSocket（可选 QUIC）同步资源
- 断网自治：EdgeCore 把元数据持久化到本地，断网时继续管理 Pod，重启后也能从本地恢复
- 设备管理：DeviceModel / Device CRD 加 Mapper，可写属性的期望值思路与设备影子相同
- 边缘 AI 模型更新要原子发布、先建后换、可回退，签名与灰度复用 OTA 那一套

→ 详见 [边缘计算](/iot/1_basics/4_edge#二、云边端三层架构)

## 七、设备安全

### Q32：一机一密和一型一密有什么区别？各有什么风险？

**一句话**：一机一密是每台设备出厂烧录唯一密钥或证书，泄露只影响一台；一型一密是同型号共用一个产品密钥，首次上线再换本机密钥，产品密钥一旦泄露，攻击者就能伪造该型号的新设备。

- 一型一密只是产线没法逐台烧录时的折中，换到本机密钥后立刻弃用产品密钥
- 动态注册接口必须校验序列号白名单，每台只能注册一次
- 密码类方案用 HMAC 签名：设备用密钥对 `clientId + 时间戳` 签名当密码，密钥本身不上网
- HMAC 需要原始密钥，台账里用 KMS 加密存储，不能像用户密码那样只存哈希

→ 详见 [设备安全](/iot/2_access/1_security#_2、一机一密与一型一密)、[设备注册与生命周期](/iot/2_access/2_provisioning)

### Q33：一型一密怎么做到「最终一机一密」？预注册和免预注册差在哪？

**一句话**：设备出厂只带一份产品级引导凭据，首次上线用它签名调注册接口，平台核对白名单后发放这台设备唯一的密钥，此后只用唯一密钥连接；预注册多一张序列号白名单，把产品级泄露的影响压回「抢注还没激活的序列号」。

| | 预注册 | 免预注册 |
|---|---|---|
| 平台侧 | 先导入序列号白名单 | 引导凭据对就放行 |
| 引导凭据泄露后 | 只能抢注未激活的序列号，真设备注册失败本身就是告警 | 能无限造新设备，只能靠配额或二次校验兜住 |

- 「只能换一次」靠带 `status = 'INACTIVE'` 条件的 UPDATE，不靠先查后改
- 注册接口走 TLS、带时间戳防重放、按产品与来源 IP 限流；明文密钥只返回一次、不落日志
- 引导凭据的权限只够调注册接口；AWS Fleet Provisioning、Azure DPS、ThingsBoard 都是同一个模型

→ 详见 [设备注册与生命周期](/iot/2_access/2_provisioning#_2、两个维度与各自的风险)

### Q34：要禁用一台正在线的设备，该怎么做？顺序为什么不能反？

**一句话**：认证只发生在建连那一刻，只改台账状态的话，已连着的设备照样收发；要先改状态让认证拒绝，再踢掉现有连接，授权缓存随连接断开一起清掉。

- 第一步：台账改为 DISABLED，清掉认证服务的身份缓存，认证回调对它返回 `deny`
- 第二步：事务提交后调 EMQX 的踢线接口 `DELETE /api/v5/clients/{clientid}`
- 反过来先踢线，设备立刻重连，认证服务还没看到 DISABLED，又放它进来了
- 被禁用的设备会不停重连：用黑名单或抖动检测把它挡在认证之前

**常见坑**：证书设备疑似泄露时只去吊销证书。EMQX 的 CRL 有刷新周期、只在握手时检查，第一步仍是禁用并踢线。

→ 详见 [设备注册与生命周期](/iot/2_access/2_provisioning#_2、禁用要做三件事)

### Q35：设备证书认证怎么做？EMQX 的 verify_peer 和 fail_if_no_peer_cert 有什么区别？

**一句话**：私钥在设备的安全芯片里生成、永不离开设备，只把 CSR 交给 CA 签名；EMQX 要同时开 `verify_peer` 和 `fail_if_no_peer_cert = true` 才算强制双向认证。

- `verify_peer` 只表示「请求并校验客户端证书」，客户端不出示证书照样能连
- `peer_cert_as_clientid = cn` 把证书 CN 绑定为 clientid，必须配合强制 mTLS，否则可以自签证书随便填 CN
- 证书选 ECDSA P-256，比 RSA 短、MCU 上握手快；用途写 `clientAuth`
- 轮换：设备本地生成新密钥、提交新 CSR（可用 EST）；吊销走 CRL，在 TLS 握手阶段就拒绝

→ 详见 [设备安全](/iot/2_access/1_security#三、传输加密)、[HTTPS 与 TLS](/protocols/3_https_tls)

### Q36：EMQX 的认证和授权怎么分工？怎么限制设备只能访问自己的 Topic？

**一句话**：认证回答「你是谁、能不能连」，授权回答「能发布 / 订阅哪些 Topic」；ACL 用 `${clientid}` 占位符只放行 `devices/${clientid}/...`（影子是其下的 `shadow/...`），网关走 `gateways/${clientid}/...`，用 `no_match = deny` 兜底。

- 配置了认证器后，未通过认证的客户端直接被拒，不再需要单独的「禁止匿名」规则
- 认证服务必须校验 clientid 与设备身份一致：否则设备可以自报别人的 ID；6.3 之前还能拿 `+` 当 clientid，让 `devices/${clientid}/cmd` 变成通配订阅（6.3 起默认拦截）
- 按 username 授权的前提是 username 也经过认证（证书场景用 `peer_cert_as_username = cn`）
- 5.x 用 `${clientid}` / `${username}`，4.x 的 `%c` / `%u` 不再生效；REST API 用 API Key 认证

→ 详见 [设备安全](/iot/2_access/1_security#四、topic-授权-emqx-acl)

### Q37：怎么发现设备暴力破解和越权尝试？

**一句话**：EMQX 的审计日志只记管理操作，设备侧的安全事件要用规则引擎订阅 `$events/...` 事件，转到 Kafka 或 SIEM 再配告警。

- `$events/client/connack`、`$events/auth/check_authn_complete`：认证失败，看来源 IP
- `$events/auth/check_authz_complete` 里 `result = deny`：越权尝试
- 典型规则：同一 IP 短时间大量认证失败、单台设备反复越权、设备从没出现过的地区上线
- 处置：按来源 IP 限速、吊销证书或凭证，并结合网段微隔离限制横向扩散

→ 详见 [设备安全](/iot/2_access/1_security#六、审计与零信任落地)

## 八、平台实战

### Q38：设备上报的数据怎么保证不丢？收到 PUBACK 为什么还不够？

**一句话**：PUBACK 只说明 Broker 收到了，不代表消息已经交到平台手里；要端到端不丢，得让设备留着本地副本，等平台写入成功后发回的业务回执，收不到就原样重发。

- 逐跳确认：每一跳都是下游收妥后才确认上游，接入服务把消息写进总线成功才回 PUBACK，业务服务写完时序库才确认消费
- 第一跳守不住：Broker 发出 PUBACK 时消息还没落盘，实测强杀 EMQX 能丢掉已确认的尾部消息
- 业务回执：报文带消息 `id` 与 `ts`，平台写入总线后向设备的下行 Topic 发一条 QoS 0 回执，设备超时没收到就重发同一条
- 重复靠幂等吸收：时序库按「同设备、同时间戳」覆盖，最新值按时间戳比较，重发不会多出数据

**常见坑**：回执表示「平台已持久接收」，不等于已入库；设备的待确认队列要先落盘再发送，否则设备自己断电照样丢。

→ 详见 [可靠上报与接入层主备](/iot/4_practice/3_reliable_uplink)

### Q39：订阅 Broker 的接入服务怎么做主备？为什么不让两个实例同时连？

**一句话**：两个实例各自订阅会让每条消息收两份，所以用一把 Redis 锁选主，只有主实例连接 Broker；主实例挂了，备实例用同一组 Client ID 连上去，接管会话里排队的消息。

- 锁是一个带过期时间的键，值是实例 ID；抢锁、续期、释放都用 Lua 先比对值再操作，旧主删不掉别人的锁
- 参数：锁 15 秒过期、5 秒续期一次、备实例每 2 秒抢一次；主实例崩溃后约 17～25 秒接管，正常停止则立即交接
- 续期失败立即断开：宁可暂时没有主，也不能有两个主；Redis 不可用时全体待命，消息排在 Broker 的会话队列里
- 持久会话兜住切换窗口：`cleanStart=false`，切换期间的消息由 Broker 按 Client ID 攒着，新主连上后补发

**常见坑**：不要开 MQTT 客户端的自动重连，下台的旧主会自己连回来把新主踢掉；断线后先确认仍持有锁再重连。

→ 详见 [可靠上报与接入层主备](/iot/4_practice/3_reliable_uplink)

### Q40：为什么把设备接入和业务处理拆成两个进程？

**一句话**：接入进程只把设备报文原样搬进消息总线，业务进程从总线拉取后再解码、校验、入库，这样业务慢了或重启了，都不会堵住设备接入。

- 业务重启不丢数据：消息在总线里排队，恢复后接着处理，设备侧的确认照常返回
- 加协议不动业务：新增一种接入协议只是多一个适配器，输出同样的消息格式
- 同步依赖压到最少：只有连接鉴权同步回调业务进程，它挂了只影响新连接，已连接的设备照常上报
- 各自做高可用：接入层单活多备，业务层靠消费组多实例分摊

**常见坑**：多了一跳也多了一个关键依赖，总线不可用时消息只能排在 Broker 的会话队列里，队列满了会丢；总线有长度上限，业务长时间不消费时旧消息会被裁掉。

→ 详见 [平台实战概览](/iot/4_practice/0_intro)、[数据流水线](/iot/4_practice/4_pipeline)

### Q41：缺测和零值怎么区分？为什么不能把没上报的测点补成 0？

**一句话**：没上报是「不知道」，报了 0 是「知道是零」；把缺测画成 0，运维会以为设备在正常上报一个零值，平均值也会算错。

| 情况 | 含义 | 展示 |
|------|------|------|
| 测点这次没报 | 缺测 | 无数据，曲线断开 |
| 数值 0、布尔 false、枚举 0 | 有效值 | 正常显示，参与计算 |
| 校验失败、NaN | 无效数据 | 拒绝并留记录，不改成 0 |

- 设备要表达「这次没有值」就不报这个键，不要报 null
- 聚合只算有效样本，没有样本的时间桶返回 null 而不是 0
- 曲线在缺口处断开，不补零、不延续前值、不插值

**常见坑**：`value || 0`、`value ?? 0`、SQL 里的 `COALESCE(value, 0)` 都会把缺测变成零；用真值判断查缺测会把 0 和 false 一起丢掉。

→ 详见 [物模型与解码](/iot/4_practice/2_thing_model)、[时序存储与历史查询](/iot/4_practice/5_telemetry)

### Q42：平台只用一条连接订阅全部设备上行，瓶颈会出在哪？怎么发现和解决？

**一句话**：EMQX 里每条连接是一个 Erlang 进程，只能用一个核；全平台的上行都挤过平台订阅的那一条连接时，它先顶到单核上限，下游怎么优化都没用。

- 现象：发压 9,000 条/秒时入库约 7,400 条/秒到顶，整机 CPU 没满，优化流水线和批大小都看不到效果
- 定位：用 EMQX 自带的 `recon` 看各进程的工作量，平台那条连接约为单个设备连接的 350 倍
- 先验证方向：换成 4 个只回确认的探测订阅者做共享订阅，确认 Broker 侧能分摊、成员离线不丢，再写代码
- 解决：主实例开 4 条连接，用共享订阅加 `hash_clientid` 策略分摊，同一设备固定走同一条连接，单设备内保序
- 结果：同一台 8 核虚拟机上可靠无损约 11,500 条/秒，瓶颈移到硬件

**常见坑**：分发策略的配置键写错层级会被静默忽略，命令照样成功；改完配置要回读运行中的值。

→ 详见 [压测与瓶颈排查](/iot/4_practice/10_capacity)

### Q43：多租户平台的数据怎么隔离？只靠每条 SQL 带 tenant_id 够吗？

**一句话**：不够，靠自觉总会漏；要让「漏了就失败」，并在数据库层再兜一道：拦截器自动补租户条件，没有租户上下文直接报错，外键写成带租户的组合外键。

- 强制过滤：ORM 的租户拦截器给每条 SQL 补 `tenant_id`，租户取自线程上下文，没绑定时抛异常而不是查全部
- 组合外键：外键写成 `(tenant_id, 父表 id)`，数据库拒绝把 A 租户的设备挂到 B 租户的产品上
- 跨租户查询只留一条路：必须跨租户的查询（如按全局设备标识鉴权）集中在一个包里并显式标注，用架构测试守住
- 缓存与时序库没有拦截器：先用受租户过滤的数据库查询拿到设备，再用查出来的设备标识去读，不直接用请求参数
- 用越权测试证明：以另一个租户的身份逐个接口去试，资源越权返回 404

**常见坑**：这套隔离只在应用层，持有数据库凭据直连的访问拦不住；访问隔离不等于资源隔离，没有配额时一个租户的流量仍会挤占其他租户。

→ 详见 [多租户与授权](/iot/4_practice/6_tenant)

### Q44：压测怎么判定「合格」？为什么不能只看客户端的成功率？

**一句话**：看计数守恒而不是速率：客户端收到的确认数要等于数据库里实际多出来的行数，同时丢弃、死信、失效日志都为 0；只看客户端会把失败判成通过。

- 确认不等于入库：过载时 Broker 先向设备确认、之后才在订阅端队列满时丢弃，客户端全绿而数据在丢
- 对外只报入库 TPS：接入 QPS 里可能含着随后被丢掉的消息
- 再加稳定性判据：设备不掉线、确认时延 p99 不超过 1 秒、积压不持续增长、Broker 没有过载告警
- 先确认喂进去的量：接入量恰好是目标的固定比例时，先查发压端是不是没打够
- 单次结果不算数：容量上限附近同一配置多次运行有过有败，结论按区间给

**常见坑**：发压机和被测机在同一台物理机上时，测到的可能是宿主机或虚拟网卡的上限，不是平台的上限。

→ 详见 [压测与瓶颈排查](/iot/4_practice/10_capacity)
