# 消息队列面试题解答

> 题目清单见 [消息队列面试题](/messaging/99_interview)；细节见 [消息队列总览](/messaging/0_overview)。
>
> 版本基线：Kafka 4.x、RocketMQ 5.x（兼顾 4.x）、RabbitMQ 4.x。

## 一、MQ 基础

### Q1：消息队列有哪些使用场景？（异步解耦、削峰填谷、广播通知）

**一句话**：MQ 主要干三件事：解耦、削峰、异步。好处是上下游互不拖累，代价是要处理重复、乱序、积压和数据一致性这些新问题。

- 解耦：订单完成后发一条消息，库存、积分、物流各自去收，新增下游不用改订单服务
- 削峰：秒杀请求先进队列，后端按自己的处理能力慢慢消费
- 异步：注册后发邮件、推送这类非核心操作不阻塞主流程
- 广播：同一条事件，每个消费者组各收一份；也常用来汇集日志、埋点数据
- 代价：多了一个要保证高可用的中间件，上下游变成「最终一致」，排查问题要靠消息轨迹

→ 详见 [消息队列基础](/messaging/1_basics)

### Q2：消息队列的核心工作流程是什么？（Producer → Broker → Consumer）

**一句话**：生产者发消息给 Broker（消息服务器）并等确认，Broker 存盘并复制到副本，消费者拿到消息处理成功后再确认。可靠性就建立在这几次确认上。

- 发送：生产者收到 Broker 的确认才算发送成功，失败就重试
- 存储：Broker 写入磁盘并复制到其他节点，复制够了才回确认
- 消费：同一个消费者组内的实例分摊消息；不同组之间各自完整收一份
- 确认：Kafka / RocketMQ 记录「消费到哪了」（位点 offset），RabbitMQ 按单条 ACK
- 失败：退避重试，超过次数进死信队列；重试会带来重复，所以消费端必须幂等

**常见坑**：以为消费完消息就没了。Kafka、RocketMQ 消费后数据还在，可以按位点回放；RabbitMQ 普通队列确认后就删除。

→ 详见 [消息队列基础](/messaging/1_basics)

### Q3：Kafka、RocketMQ、RabbitMQ 的对比？各自适合什么场景？

**一句话**：Kafka 适合大数据量的日志和数据管道；RocketMQ 适合订单、支付这类业务消息，事务、定时、重试都现成；RabbitMQ 路由灵活，适合中小规模的业务解耦。

| 对比 | Kafka | RocketMQ | RabbitMQ |
|------|-------|----------|----------|
| 吞吐 | 最高 | 高 | 中 |
| 事务消息 | 无（有自己的事务写，不是一回事） | 原生支持 | 无 |
| 延迟消息 | 不支持 | 支持任意时间 | TTL + 死信或插件 |
| 消息回放 | 支持 | 支持 | 仅 Stream 支持 |
| 典型场景 | 日志、埋点、数据管道 | 订单、支付等核心链路 | 业务解耦、复杂路由 |

- 选型顺序：先看有没有硬需求（事务、延迟、顺序），再看量级，最后看团队熟悉程度
- 网上「百万 / 十万 / 万」的吞吐数字只能看相对大小，实际取决于消息大小和配置
- 上了公有云优先考虑托管版；一个公司最好只用一到两种 MQ

→ 详见 [MQ 选型](/messaging/6_selection)

### Q4：RocketMQ 5.x 相比 4.x 有哪些主要变化？

**一句话**：5.x 是架构升级：加了一层无状态的 Proxy 和轻量多语言客户端，补上了任意时间的定时消息、按消息分配的 POP 消费和自动切主。老客户端还能继续连。

- 接入：4.x 客户端直连 Broker；5.x 可以通过 Proxy 用 gRPC 接入，客户端变轻
- 定时消息：4.x 只有 18 个固定延迟级别（最长 2 小时）；5.x 可以指定任意投递时间
- 顺序消息：5.x 把 Topic 声明成 FIFO 类型，按 MessageGroup（比如订单号）保证组内有序
- POP 消费：Broker 按消息分配给消费者，消费者数量可以超过队列数
- 高可用：新增 Controller 模式，主节点挂了自动从同步副本里选新主

→ 详见 [RocketMQ](/messaging/3_rocketmq)

### Q5：RabbitMQ 延迟消息有哪几种实现方式？各有什么坑？

**一句话**：两种：TTL + 死信交换机（不用插件，但同一队列里延迟时间不同会互相堵）；延迟插件（每条可任意延迟，但消息只存在一个节点上）。

| 对比 | TTL + 死信交换机 | 延迟插件 |
|------|----------------|---------|
| 原理 | 消息在没人消费的队列里过期，变成死信转到真正的队列 | 消息先存在插件里，到期才投递 |
| 精度 | 只在消息到队头时检查是否过期 | 每条单独计时，较准 |
| 可靠性 | 可用多副本队列 | 只存一个节点，节点丢数据就丢 |
| 做法 | 一种延迟时长建一个队列 | 不适合海量或超长延迟 |

- 量大、时间任意、要求可靠的场景，更适合 RocketMQ 定时消息或「数据库 + 定时扫描」

**常见坑**：延迟消息到了直接关单。应该先确认订单还是「待支付」再取消，否则会误关已支付的订单。

→ 详见 [RabbitMQ](/messaging/4_rabbitmq)

## 二、消息可靠性

### Q6：如何保证消息不丢失？（生产确认 + 持久化 + 消费 ACK）

**一句话**：发送、存储、消费三个环节都要防：发送要等确认、Broker 要多副本、消费成功后再确认。做到这些得到的是「至少一次」，所以消费端还必须幂等。

| 环节 | Kafka | RocketMQ | RabbitMQ |
|------|-------|----------|----------|
| 发送 | `acks=all` | 同步发送并检查 `SEND_OK` | 开启发布确认 |
| 存储 | 3 副本，至少 2 个同步才算写成功 | 同步复制 | 持久化 + Quorum 队列 |
| 消费 | 关自动提交，处理完再提交 | 处理完才返回成功 | 处理完再 ack |

- 三种语义：先确认再处理是「最多一次」；处理完再确认是「至少一次」（业务默认）；「恰好一次」= 至少一次 + 幂等
- Kafka 不丢数据靠多副本，不靠每条都刷盘

**常见坑**：靠发送回调来补救失败。进程可能在回调前就崩了，要和数据库保持一致得用本地消息表（见 Q18）。

→ 详见 [消息队列基础](/messaging/1_basics)、[Kafka](/messaging/2_kafka)

### Q7：RocketMQ 的同步刷盘和异步刷盘有什么区别？

**一句话**：同步刷盘等消息真正写到磁盘才返回，可靠但慢；异步刷盘（默认）写到操作系统缓存就返回，快但断电可能丢最近一点数据。生产上常用「异步刷盘 + 同步复制」，单机丢的由副本兜底。

| 方式 | 何时返回 | 特点 |
|------|---------|------|
| 异步刷盘（默认） | 写入内存页缓存 | 快；断电可能丢未刷盘数据 |
| 同步刷盘 | 写入磁盘 | 最可靠；吞吐明显下降 |

- 刷盘管的是「单机不丢」，复制管的是「机器挂了还有备份」，两者是两回事
- 同步复制要等从节点确认才返回；异步复制更快，但主节点宕机可能丢少量消息
- 发送返回 `FLUSH_DISK_TIMEOUT` 这类状态时，消息到了 Broker 但没达到刷盘或复制要求，关键消息要告警

→ 详见 [RocketMQ](/messaging/3_rocketmq)

### Q8：Kafka 的 ISR 机制是什么？如何保证数据不丢失？

**一句话**：ISR 是「跟得上 Leader 的副本名单」。`acks=all` 时 Leader 要等名单里所有副本都写好才回确认，Leader 挂了也只从名单里选新 Leader，所以确认过的消息不会丢。

- 副本落后太久就被移出 ISR，追上了再加回来
- 消费者只能读到 ISR 里所有副本都有的消息，避免读到可能丢的数据
- 常用组合：3 副本 + `min.insync.replicas=2`（少于 2 个同步副本时直接拒绝写入），允许坏 1 台
- 不允许落后的副本当 Leader（`unclean.leader.election.enable=false`，默认就是）
- 生产者 `acks=all` 和幂等发送在 3.0 之后默认开启；消费端关自动提交，处理完再提交

**常见坑**：把 `retries` 调小。这只会让网络闪断、Leader 切换这种能自动恢复的情况变成发送失败。

→ 详见 [Kafka](/messaging/2_kafka)

### Q9：消息幂等性（重复消费）如何保证？（业务键去重：去重记录与业务写入同一本地事务 / Redis 状态机）

**一句话**：任何 MQ 都可能重复投递，消费端必须幂等。首选做法：用业务键（如订单号）写一条去重记录，和业务操作放在同一个数据库事务里，业务失败去重记录一起回滚。

- 去重键用业务键（订单号 + 动作），不要用 MQ 的消息 ID：生产者重发时消息 ID 会变
- 去重记录用唯一键 + `INSERT IGNORE`，插不进去说明处理过，直接返回成功
- 业务数据不在同一个库时用 Redis 状态机：先占位「处理中」，成功改「已完成」，失败删掉占位再抛异常
- 抢占时发现别人「处理中」，要抛异常稍后重试，不能直接确认跳过
- 最简单的兜底：更新语句带状态条件，如 `WHERE status = 'UNPAID'`，天然幂等

**常见坑**：先用 `SETNX` 写「已消费」标记再处理业务。业务失败后重投的消息会因为标记已存在被跳过，消息就丢了。

→ 详见 [消息队列基础](/messaging/1_basics)

### Q10：Kafka 消费失败时为什么可能"跳过"消息？如何正确重试？

**一句话**：Kafka 每个分区只记一个「消费到哪了」的位置，提交第 6 条就等于说前面都处理完了。所以第 5 条失败、第 6 条成功提交，第 5 条就被一起跳过了。正确做法是抛异常，让框架原地重试，重试用完转到死信 Topic。

- 跳过的常见原因：开了自动提交；监听方法里 catch 住异常只打日志；失败的不提交、后面的提交了
- Spring Kafka 配 `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`：退避重试几次，失败发到 `<topic>.DLT`
- 原地重试：分区内顺序不乱，但重试期间这个分区停住不动
- 转重试 Topic（`@RetryableTopic`）：主分区不卡，但同一个 key 可能乱序
- 参数错误、反序列化失败这类重试也没用的异常，直接进死信

**常见坑**：只配了 `DefaultErrorHandler` 没配死信。默认重试 9 次后只打一行日志就跳过了。

→ 详见 [Kafka](/messaging/2_kafka)

## 三、消息顺序

### Q11：如何保证消息的顺序消费？

**一句话**：MQ 只保证一个分区（队列）内有序。实际要的通常是「同一个订单的消息有序」：发送时按订单号路由到同一个分区，消费时一个分区只用一个线程处理。

- 发送端：Kafka 设消息 key；RocketMQ 按 hashKey 选队列或设 MessageGroup；RabbitMQ 同 key 路由到同一队列
- 发送端要同步串行发，异步并发发会打乱顺序
- 全局有序只能用一个分区，吞吐上不去，一般不这么做
- 热点 key（比如大商户）会让一个分区成为瓶颈，可以把 key 拆细

**常见坑**：消费者把消息丢进线程池异步处理，顺序就乱了。确实要并行时，按 key 哈希到固定的单线程里。

→ 详见 [消息队列基础](/messaging/1_basics)

### Q12：RocketMQ 如何实现顺序消息？（MessageGroup + FIFO 队列）

**一句话**：4.x 是「同一个 hashKey 发到同一个队列，消费时锁住队列单线程处理」；5.x 把 Topic 声明成 FIFO 类型，发送时设 MessageGroup，同组有序、不同组并行。

- 4.x：发送用 `syncSendOrderly(topic, payload, hashKey)`，消费用 `ConsumeMode.ORDERLY`
- 5.x：FIFO Topic + MessageGroup（如订单号），消费者组开启顺序投递
- 生产端必须同步发送
- 顺序消费失败不会发回 Broker，而是在本地反复重试同一条，整个队列停住等它

**常见坑**：不设最大重试次数（`maxReconsumeTimes`）。一条坏消息会永远卡住整个队列。

→ 详见 [RocketMQ](/messaging/3_rocketmq)

### Q13：Kafka 如何保证分区内有序？跨分区能保证顺序吗？

**一句话**：分区是一个只追加的日志，写入有序、按顺序读，而且一个分区同时只给一个消费线程，所以分区内天然有序。跨分区不保证顺序，要有序的消息用同一个 key 发到同一个分区。

```java
kafkaTemplate.send("order-events", orderId.toString(), payload);   // key = orderId
```

- 消费端不需要把并发度设成 1：每个分区本来就只由一个线程处理，并发是在分区之间
- 生产者开启幂等（3.0 起默认）时，重试也不会打乱分区内的顺序
- 增加分区数会改变 key 落到哪个分区，扩容瞬间可能乱序

→ 详见 [Kafka](/messaging/2_kafka)

## 四、高性能

### Q14：消息队列如何实现高效读写？（零拷贝 MMap/SendFile、顺序写入、PageCache）

**一句话**：三招：顺序追加写（磁盘顺序写很快）、读写先走操作系统的页缓存（相当于内存）、零拷贝（少在内核和程序之间来回复制数据）。

- 顺序写：消息只往文件末尾追加；RocketMQ 所有 Topic 共用一个 CommitLog 文件，Topic 再多也是顺序写
- 页缓存：不占 JVM 堆内存，刚写入的数据通常直接从缓存读到
- mmap（RocketMQ 用）：把文件映射到内存直接读写，拷贝从 4 次减到 3 次
- sendfile（Kafka 用）：数据从页缓存直接送到网卡，完全不经过程序，拷贝只剩 2 次

![mmap + write 数据路径](../assets/messaging/zero-copy-mmap.svg)

![sendfile 数据路径](../assets/messaging/zero-copy-sendfile.svg)

**常见坑**：开了 TLS 还以为能零拷贝。加密必须在程序里做，sendfile 用不了，CPU 开销明显上升。

→ 详见 [Kafka](/messaging/2_kafka)、[RocketMQ](/messaging/3_rocketmq)

### Q15：Kafka 为什么吞吐量这么高？

**一句话**：Kafka 本质是一个分区化的顺序日志：顺序写、读走页缓存和零拷贝、所有操作都按批处理，再用多分区把压力分到多台机器上。

- 顺序追加写，读写都走操作系统页缓存，不给 JVM 增加 GC 压力
- 消费时用 sendfile 零拷贝，数据直接从缓存送到网卡
- 批量 + 压缩：生产者攒一批再发，整批压缩，Broker 原样存，消费者解压
- 分区并行：分区分布在多台 Broker 上，生产和消费都能水平扩展
- 消费只是移动位点，多个消费者组读同一份数据不用额外写

**常见坑**：`linger.ms` 调大能提高吞吐，但单条消息的延迟也会变大，要权衡。

→ 详见 [Kafka](/messaging/2_kafka)

### Q16：消息积压了怎么处理？

**一句话**：积压就是生产比消费快。先止血（找出卡住的原因），再扩容（加消费者，必要时加分区），最后复盘消费能力和告警。

- 先排查：是所有分区都涨（整体能力不够），还是个别分区涨（热点 key、某个实例卡住）；下游有没有慢 SQL、超时
- 隔离坏消息：反复失败的消息转死信，不然扩容也没用
- 扩消费者：Kafka 实例数超过分区数就闲着了，要同时加分区；RabbitMQ 可以直接加
- 提升单实例能力：批量拉取、批量写库，减少同步远程调用
- 应急：暂停非核心消费组；或者把消息先转到分区更多的临时 Topic 再用大量实例消费

**常见坑**：直接重置位点跳过积压。这是最后手段，只在业务允许丢弃时用，事后要补数据。

→ 详见 [消息队列基础](/messaging/1_basics)、[Kafka](/messaging/2_kafka)

## 五、分布式事务

### Q17：如何用消息队列实现分布式事务最终一致性？

**一句话**：MQ 只能做到最终一致：保证「本地事务成功，消息一定发出去」，下游失败就重试 + 幂等，最后用对账兜底。常用做法是本地消息表或 RocketMQ 事务消息。

| 方案 | 可靠性 | 适用 |
|------|-------|------|
| 本地消息表 | 可靠 | 通用首选，不绑定 MQ |
| RocketMQ 事务消息 | 可靠 | 已在用 RocketMQ 的核心链路 |
| 最大努力通知 | 有限次重试 + 对账 | 跨公司回调，如支付结果通知 |
| 提交后直接发 | 可能丢 | 不重要的通知 |

- 下游消费失败不会回滚上游，只能重试，重试用完进死信后人工处理或反向补偿
- Kafka 事务管不到数据库，不能替代本地消息表
- 需要回滚的强流程用 TCC / Saga

→ 详见 [消息队列基础](/messaging/1_basics)

### Q18：为什么不能在数据库事务里直接发 MQ 消息？本地消息表（Outbox）怎么做？

**一句话**：数据库和 MQ 是两个系统，放不进一个事务。事务里发消息，可能「消息发了但事务回滚」，也可能「事务提交了但消息没发」。正确做法是把要发的消息和业务数据写进同一个本地事务，再由后台任务发出去。

- 第 1 步：同一个事务里写业务表和消息表（状态 `NEW`），要么都成功，要么都失败
- 第 2 步：后台任务扫描 `NEW` 消息发到 MQ，收到确认后标记 `SENT`，失败下次再发
- 第 3 步：可能重复发，消费端必须幂等
- 多实例扫表用 `SELECT ... FOR UPDATE SKIP LOCKED` 避免重复扫到同一条；也可以用 CDC（读 binlog）推送

**常见坑**：用 `@TransactionalEventListener(AFTER_COMMIT)` 发消息就以为可靠了。提交后、发送前进程崩溃照样丢，只适合不重要的通知。

→ 详见 [消息队列基础](/messaging/1_basics)

### Q19：RocketMQ 事务消息的原理是什么？（半消息 + 本地事务 + 回查）

**一句话**：先发一条消费者看不到的「半消息」，再执行本地事务，成功就提交让消息可见，失败就删掉；结果没传到时，Broker 会定时来问生产者「这个事务到底成没成」（回查）。

- 本地事务里同时记一条事务 ID，作为回查的依据
- 本地事务成功返回 `COMMIT`，确定失败返回 `ROLLBACK`，不确定返回 `UNKNOWN`
- 回查超过上限（默认 15 次）后，半消息默认被丢弃
- 回查可能落到别的生产者实例上，所以依据必须存数据库，不能存内存
- 只保证生产端「本地事务和消息一致」，下游仍要重试 + 幂等

**常见坑**：回查时查不到记录就返回 `ROLLBACK`。本地事务可能还没提交，应该返回 `UNKNOWN`，等超过合理时间仍查不到再回滚。

→ 详见 [RocketMQ](/messaging/3_rocketmq)

### Q20：本地消息表和 RocketMQ 事务消息的区别？

**一句话**：效果一样（本地事务成功，消息一定送达），区别在谁负责送：本地消息表靠自己的表和后台任务，跟用哪种 MQ 无关；事务消息交给 Broker 的半消息和回查，省了消息表，但只能用 RocketMQ。

| 对比 | 本地消息表 | RocketMQ 事务消息 |
|------|-----------|------------------|
| 一致性靠什么 | 业务表和消息表同一事务 | 半消息 + 回查 |
| 绑定 MQ | 不绑定 | 只能 RocketMQ |
| 延迟 | 取决于扫表间隔 | 提交后马上投递 |
| 排查 | 消息表里直接能查 | 状态在 Broker 内部 |

- 共同点：都是「至少一次」，下游都要幂等，都不会回滚上游
- 已经在用 RocketMQ 的核心链路用事务消息；跨 MQ 或要统一管理时用本地消息表

→ 详见 [RocketMQ](/messaging/3_rocketmq)、[消息队列基础](/messaging/1_basics)

## 六、高可用

### Q21：RocketMQ 如何保证高可用？（主从复制 + DLedger / 5.x Controller）

**一句话**：NameServer（路由中心）无状态，部署多个、活一个就行；Broker 经历了三代：主从复制（主挂了不自动切）→ DLedger（用 Raft 投票自动选主）→ 5.x Controller（从同步副本里自动选主）。新集群优先用 Controller 模式。

- 主从复制：主节点挂了这组就不能写，只能从从节点读，靠多组 Broker 分担写入
- DLedger：至少 3 副本，多数写成功才算提交，能自动选主，但改了存储格式
- Controller 模式：只从数据同步的副本里选主，不丢数据；2 副本就能工作，存储格式不变
- 常见的可靠性组合：同步复制（或 Controller）+ 异步刷盘

→ 详见 [RocketMQ](/messaging/3_rocketmq)

### Q22：Kafka 的副本机制是什么？Leader 宕机如何选举？

**一句话**：每个分区有多个副本，读写都走 Leader，其他副本从 Leader 拉数据同步。Leader 挂了，由 Controller 从 ISR（跟得上的副本）里选一个新 Leader，客户端刷新元数据后切过去。Kafka 4.0 起不再依赖 ZooKeeper。

- 同一分区的副本分散在不同机器上，可以按机架分布
- Controller 发现 Broker 下线后，从 ISR 里选新 Leader
- ISR 为空时宁可分区暂时不可用，也不让落后的副本上位丢数据
- 旧 Leader 恢复后变成跟随者，先删掉自己多出来的未提交数据再追上
- Controller 通常 3 或 5 个节点组成投票组（KRaft），生产环境建议和 Broker 分开部署

**常见坑**：老集群直接升 4.x。必须先在 3.x 完成从 ZooKeeper 到 KRaft 的迁移。

→ 详见 [Kafka](/messaging/2_kafka)

### Q23：RabbitMQ 的镜像队列（4.0 已移除）和 Quorum Queue 有什么区别？为什么要迁移？

**一句话**：镜像队列是老的主从复制方案，RabbitMQ 4.0 已经删掉了；现在要复制的业务队列只能用 Quorum 队列（基于 Raft，多数节点写成功才确认），升级前必须先迁移。

| 对比 | 镜像队列 | Quorum 队列 |
|------|---------|------------|
| 复制方式 | 一主多镜像 | Raft：多数节点写成功才确认 |
| 数据安全 | 切换到未同步的镜像可能丢消息 | 主挂了自动选主，不丢已确认消息 |
| 坏消息保护 | 无 | 超过投递次数（默认 20）进死信 |
| 现状 | 4.0 已移除 | 业务队列的默认选择 |

- 副本数用奇数（3 或 5），3 副本能容忍坏 1 个节点
- 要回放、大量消费者或海量堆积时用 Stream 队列
- 普通 Classic 队列即使持久化也只存一个节点，只适合可丢的临时数据

→ 详见 [RabbitMQ](/messaging/4_rabbitmq)

### Q24：如何设计一个消息队列？

**一句话**：按一条消息的一生来讲：怎么收（网络）→ 怎么存（存储）→ 怎么投（消费）→ 怎么不丢不重（可靠性）→ 怎么扩容和容错（分区与副本），再补上事务、延迟、死信等能力，每处都说清取舍。

- 网络：长连接 + 自定义二进制协议，批量收发和压缩
- 存储：顺序追加的分段日志 + 索引，走页缓存和零拷贝，按时间或大小清理
- 消费：消费者组（组内分摊、组间各收一份），拉模式 + 长轮询，位点存在 Broker
- 可靠与高可用：发送确认 + 多副本写成功才确认 + 消费成功再提交；Leader 挂了自动选主
- 扩展：Topic 拆成多个分区，分布到多台机器；加分区和节点扩容

**常见坑**：只讲功能不讲取舍。要主动说：同步刷盘换可靠牺牲吞吐、分区多了 Rebalance 开销大、全局有序和高吞吐不可兼得；幂等消费最终还是交给业务。

→ 详见 [MQ 选型](/messaging/6_selection)、[Kafka](/messaging/2_kafka)
