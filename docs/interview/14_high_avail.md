## 一、可用性度量

### Q1：SLA 99.99% 意味着每年多少故障时间？每月呢？

**核心结论**：99.99%（4 个 9）每年约 **52.6 分钟**，每月（按 30 天）约 **4.32 分钟**，每周约 1 分钟。

| 可用率 | 年停机 | 月停机 |
|-------|-------|-------|
| 99% | ≈ 3.65 天 | ≈ 7.2 小时 |
| 99.9% | ≈ 8.76 小时 | ≈ 43.2 分钟 |
| 99.95% | ≈ 4.38 小时 | ≈ 21.6 分钟 |
| 99.99% | ≈ 52.6 分钟 | ≈ 4.32 分钟 |
| 99.999% | ≈ 5.26 分钟 | ≈ 25.9 秒 |

- 每多一个 9，成本通常数量级上升：4 个 9 要求单次故障分钟级自动恢复，人工介入基本来不及，必须依赖自动故障转移
- 互联网核心业务一般以 99.95%～99.99% 为目标，目标不是越高越好

→ 详见 [可用性度量](/high-avail/1_sla_slo)

### Q2：SLA、SLO、SLI 分别是什么？三者什么关系？

**核心结论**：**SLI 是度量，SLO 是目标，SLA 是合同**。SLO 必须比 SLA 更严格，给团队留出反应余量，例如 SLA 99.9%、SLO 99.95%。

| 概念 | 含义 | 示例 |
|------|------|------|
| SLI | 可量化的服务质量指标 | 非 5xx 请求占比、延迟 < 300ms 的请求占比 |
| SLO | 对 SLI 设定的内部目标 | 30 天滚动窗口内成功率 ≥ 99.9% |
| SLA | 对外承诺，违约有赔偿 | 月可用率 < 99.9% 返还 10% 服务费 |

- 延迟 SLI 用"**达标请求占比**"而不是平均值，可直接参与错误预算计算
- 从用户视角（网关 / 负载均衡入口）统计；按关键链路分别定义；用 28 或 30 天滚动窗口；先按历史数据定，再逐步收紧

→ 详见 [可用性度量](/high-avail/1_sla_slo)

### Q3：什么是错误预算？如何用它约束发布节奏？

**核心结论**：**错误预算 = 1 − SLO**，是一个周期内允许"不可用"的额度。SLO 99.9% 时，30 天预算为 43.2 分钟，或月 1 亿请求中 10 万次失败。按剩余预算决定发布节奏：

| 预算状态 | 策略 |
|---------|------|
| 剩余 > 50% | 正常迭代，可以做有风险的发布与实验 |
| 剩余 10% ~ 50% | 放慢节奏，发布必须灰度，加强变更评审 |
| 剩余 < 10% | 冻结功能发布，只允许稳定性修复与紧急安全补丁 |
| 已耗尽 | 全面冻结，投入可靠性改进直到窗口内预算恢复 |

- 错误预算把"开发要快、运维要稳"变成共同规则，需要研发、测试、运维、产品**事先共同认可**才能执行

→ 详见 [可用性度量](/high-avail/1_sla_slo)

### Q4：为什么基于燃烧速率告警比直接按错误率告警更好？

**核心结论**：`燃烧速率 = 实际错误率 / (1 − SLO)`，直接对应"**按当前速度多久会耗尽预算**"。固定错误率阈值不区分持续时间：短暂尖刺会误报，长时间的小幅泄漏会漏报；燃烧速率告警只在真正威胁 SLO 时触发。

| 告警级别 | 长窗口 | 短窗口 | 燃烧速率 | 消耗 30 天预算 |
|---------|-------|-------|---------|--------------|
| 立即呼叫（Page） | 1 小时 | 5 分钟 | 14.4 | 2% |
| 立即呼叫（Page） | 6 小时 | 30 分钟 | 6 | 5% |
| 工单（Ticket） | 3 天 | 6 小时 | 1 | 10% |

- 长短双窗口同时满足才触发：长窗口保证显著性，短窗口保证恢复后告警及时解除
- 例：SLO 99.9% 时，Page 规则为 1h 与 5m 错误率都 > `14.4 × 0.001`

→ 详见 [可用性度量](/high-avail/1_sla_slo)

### Q5：MTBF、MTTR 是什么？提升可用性应优先降低哪一个？

**核心结论**：MTBF 是平均无故障时间，MTTR 是平均恢复时间（含发现、定位、止血），`可用率 = MTBF / (MTBF + MTTR)`。工程上**优先降低 MTTR** 更划算：故障无法杜绝，但"先止血后定位"能把分钟级恢复变为常态。

| 指标 | 改进手段 |
|------|---------|
| MTBF | 代码质量、容量规划、变更管控、混沌演练 |
| MTTD（平均发现时间） | 基于 SLO 的告警、拨测、链路追踪 |
| MTTR | 自动故障转移、一键回滚、降级开关、预案 |

- 例：平均 720 小时出一次故障、每次恢复 1 小时，可用率 = 720 / 721 ≈ 99.86%；恢复缩到 6 分钟即接近 99.99%

→ 详见 [可用性度量](/high-avail/1_sla_slo)、[故障应急与复盘](/high-avail/11_incident_response)

### Q6：四个 99.9% 的服务串联，整体可用率是多少？两个 99% 的实例并联呢？

**核心结论**：串联 `A = A₁ × A₂ × … × Aₙ`，四个 99.9% 串联为 `0.999⁴ ≈ 99.6%`（年停机约 35 小时）；并联 `A = 1 − (1 − A₁)ⁿ`，两个 99% 并联为 `1 − 0.01² = 99.99%`。

- **串联的依赖越多，整体可用率越低**，且低于其中最差的组件，所以要减少同步强依赖，非核心依赖异步化或可降级
- **混合系统找短板**：LB 99.99% → 两个 99.9% 应用并联（99.9999%）→ 单主库 99.95%，整体约 99.94%，再加应用实例几乎无收益，瓶颈是数据库单点
- 并联公式假设**故障相互独立**；同机架断电、同一版本 Bug、共享配置中心故障会让副本同时失效，冗余要跨故障域部署、发布要灰度

→ 详见 [可用性度量](/high-avail/1_sla_slo)

## 二、冗余与故障转移

### Q7：冷备、温备、热备有什么区别？

**核心结论**：区别在备用节点平时的状态和数据同步方式，决定了切换时间（RTO）和成本。

| 类型 | 备用节点状态 | 数据同步 | RTO | 成本 |
|------|------------|---------|-----|------|
| 冷备 | 未运行，只有备份文件 | 定期全量备份 | 小时级 ~ 天级 | 低 |
| 温备 | 已部署但不承接流量 | 异步复制，可能落后 | 分钟级 | 中 |
| 热备 | 运行中，随时接管 | 实时 / 半同步复制 | 秒级 ~ 分钟级 | 高 |
| 多活 | 同时承接流量 | 双向同步或分片隔离 | 秒级（切流即可） | 最高 |

- 冷备不等于没用：**备份是防误删、防勒索的最后防线**，复制会把 `DELETE` 同步到所有副本；备份必须定期做恢复演练

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q8：主备、主主、集群三种模式各有什么优缺点？

**核心结论**：主备简单无写冲突但备节点闲置、切换有中断；主主资源利用率高但有写冲突；集群靠多数派自动选主、可扩展但实现复杂。

| 模式 | 优点 | 缺点 | 示例 |
|------|------|------|------|
| 主备 | 简单，无写冲突 | 备节点资源闲置；切换有中断 | MySQL 主从、Keepalived 双机 |
| 主主 | 资源利用率高 | 写冲突、自增 ID 冲突，需冲突解决 | MySQL 双主（通常仅单边写） |
| 集群 | 自动选主、可水平扩展 | 实现复杂，需奇数节点 | Redis Cluster、MGR、etcd、Kafka |

- 生产中 MySQL 双主通常是**双主单写**：互为主从但同一时刻只有一边写，本质仍是主备，只是切换后无需重建复制关系

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q9：K8s 的 liveness 和 readiness 探针有什么区别？为什么探针不建议检查数据库等共享依赖？

**核心结论**：liveness 问"**还活着吗，要不要重启**"，失败即重启容器；readiness 问"**现在能接流量吗**"，失败只从 Service Endpoints 摘除、不重启。两者都**不应包含 DB、Redis、下游服务等共享依赖**。

| 探针 | 失败后果 | 应检查 | 不应检查 |
|------|---------|-------|---------|
| `startupProbe` | 超阈值重启；成功前不执行另外两个探针 | 是否启动完成 | — |
| `livenessProbe` | 重启容器 | 进程自身是否已无法恢复（死锁、事件循环卡死） | 任何外部依赖 |
| `readinessProbe` | 摘除流量，不重启 | 本实例能否接流量（预热完成、未在停机中） | 多实例共享的依赖 |

为什么不查共享依赖：

- **共享依赖一抖动，所有实例同时判定失败**：liveness 会让所有实例一起重启；readiness 会让 Service 后面没有任何 Endpoint，局部依赖故障被放大成 100% 不可用
- **摘流量解决不了共享依赖的问题**：换到哪个实例，连的都是同一个 DB
- 依赖故障应由调用路径的超时、熔断、降级处理，让能服务的请求继续服务

- Spring Boot 2.3+ 提供 `/actuator/health/liveness` 与 `/readiness`，readiness 组默认只含 `readinessState`；开启 `add-additional-paths` 在主端口探测 `/livez`、`/readyz`，避免独立管理端口掩盖业务端口卡死

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q10：Keepalived 如何实现 VIP 漂移？

**核心结论**：Keepalived 基于 VRRP 协议，多台节点中优先级最高的成为 Master 并持有虚拟 IP（VIP），定期发送通告；Backup 在超时时间内收不到通告，或 Master 的健康检查脚本失败导致优先级下降时，Backup 接管 VIP，秒级完成切换。

- `track_script` 定时检查 Nginx 等进程，失败时 `weight -20` 降低优先级触发切换
- 两台都配 `state BACKUP` + `nopreempt`，避免原主恢复后抢回 VIP 造成二次抖动
- 风险是**脑裂**：心跳线中断时两台都持有 VIP，需第三方仲裁（如检测网关连通性），见 Q11

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q11：什么是脑裂？有哪些防护手段？fencing token 是什么？

**核心结论**：脑裂是网络分区导致两侧都认为对方故障，**同时存在两个"主"并各自接受写入**，恢复后数据冲突甚至无法合并。核心防护是多数派仲裁，并让存储层能拒绝"旧主"的写入。

| 防护手段 | 原理 | 示例 |
|---------|------|------|
| 多数派仲裁 | 只有拿到多数票的一方能成为主 | Raft、Sentinel quorum、MGR |
| Fencing Token | 每次选主递增任期号，存储层拒绝旧任期写入 | Raft term、ZooKeeper zxid、分布式锁的递增 token |
| STONITH | 切换前强制隔离旧主（断电、摘网卡、撤权限） | Pacemaker、云 API 关停实例 |
| 旧主自我降级 | 联系不上足够副本时拒绝写入 | Redis `min-replicas-to-write` |
| 第三方仲裁 | 仲裁节点 / 仲裁机房判断谁存活 | 两地三中心仲裁点 |

- **fencing token**：旧主可能只是暂停（Full GC、网络抖动）而未真正下线，恢复后仍以为自己是主；每次写入携带单调递增的 token，存储层记录见过的最大 token，拒绝更小的，旧主的写入就会失败
- 集群取奇数节点：3 节点容忍 1 个故障，5 节点容忍 2 个

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q12：MySQL 主库宕机如何自动切换？MHA、Orchestrator、MGR 有什么区别？

**核心结论**：自动切换 = 监控判定主库故障 → 选出数据最新的从库提升为主 → 其余从库改指向新主 → 应用连接切到新主。MHA 与 Orchestrator 基于传统主从复制做外部切换，MGR 是基于 Paxos 的组复制、内置选主。

| 方案 | 原理 | 切换 | 一致性 |
|------|------|------|-------|
| MHA | 监控主库，故障时从最新从库补齐差异 binlog 并提升 | 自动，30s 左右 | 尽力补齐；项目已多年未维护 |
| Orchestrator | 识别复制拓扑，自动提升并重建拓扑，自身基于 Raft 高可用 | 自动，秒级 | 依赖复制模式 |
| MGR / InnoDB Cluster | 组复制，单主模式自动选主 | 自动，秒级；需多数派存活 | 多数派确认，强一致 |

应用侧配合：

- 连接串不写死主库 IP：用 VIP、DNS、ProxySQL / MySQL Router 等代理
- 连接池设合理的 `maxLifetime` 和连接校验，避免长时间持有指向旧主的连接
- 半同步复制降低切换丢数据风险，但退化为异步时仍可能丢

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q13：如何梳理强弱依赖？弱依赖故障时怎样保证主链路不受影响？

**核心结论**：强依赖是失败即核心功能无法完成且无替代结果的依赖（库存扣减、订单写库、支付）；弱依赖失败时核心功能仍可完成（推荐、积分、评价）。梳理后要让弱依赖**真正"弱"**：超时短、可熔断、可降级或改为异步，并用故障注入验证。

梳理方法：

1. 从**链路追踪拓扑**出发列出每个核心接口的全部下游，而不是凭印象
2. 由业务方逐个确认"这个依赖挂了，功能还能不能用"
3. 对标注为弱依赖的下游注入延迟与异常，核心接口成功率不应下降

保证主链路：

- **最常见的问题是弱依赖被写成了强依赖**：同步调用、没有超时或超时过长、异常直接抛出、结果被当成必填字段，要逐一检查代码路径
- 每个依赖写好预案：超时与重试、熔断阈值、降级方式、开关位置与负责人、恢复条件
- 不需要在请求内拿到结果的调用（发积分、发通知）改为事件异步处理，下游故障只造成消息积压

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

## 三、负载均衡

### Q14：常见负载均衡算法有哪些？一致性哈希解决什么问题？

**核心结论**：实例同构、请求耗时相近用轮询；耗时差异大看连接数或响应时间（最少连接、P2C）；需要"同一个 key 落到同一实例"用哈希。一致性哈希解决的是**扩缩容时只迁移少量 key**，而普通取模在节点数变化时几乎所有 key 都要重新映射。

| 算法 | 适用场景 | 注意事项 |
|------|---------|---------|
| 轮询 / 加权轮询 | 实例配置相同或按权重分配、预热期逐步放量 | Nginx 用平滑加权轮询，避免连续打到同一实例 |
| 随机 / 加权随机 | 客户端负载均衡 | 小流量下分布不均 |
| 最少连接 | 长短请求混合、长连接 | 新实例会被瞬间灌满，需配合预热 |
| P2C | 实例性能波动大的 RPC | 随机挑两个取较优，Envoy `LEAST_REQUEST` 默认即 P2C |
| 一致性哈希 | 本地缓存亲和、有状态服务、分布式存储 | 热点 key 导致单实例过载；用虚拟节点改善均匀度 |

→ 详见 [负载均衡](/high-avail/3_load_balancing)、[一致性哈希](/distributed/9_consistent_hashing)

### Q15：四层负载均衡和七层负载均衡的区别？

**核心结论**：四层按 IP + 端口转发连接、不解析内容，性能极高，负责"扛连接"；七层解析 HTTP，可按 URL / Header 路由、做 TLS 卸载、鉴权与限流，负责"懂业务"。生产上四层做入口 VIP，后面挂多台七层网关。详细对比见 [高并发 Q6](./13_high_con)。

- 高可用视角的差异：四层健康检查通常只到 TCP 端口级，七层可以探测 HTTP 健康接口并按状态码做失败转移

→ 详见 [接入层架构](/high-con/1_access_layer)、[负载均衡](/high-avail/3_load_balancing)

### Q16：服务端负载均衡与客户端负载均衡（Spring Cloud LoadBalancer）有什么区别？

**核心结论**：服务端负载均衡是独立的代理层（Nginx / LVS / SLB），对调用方透明；客户端负载均衡是调用方从注册中心拉取实例列表、**在本地进程内选择实例**，少一跳、无代理单点，是微服务间调用的主流方式。

| 对比 | 服务端（Nginx / LVS / SLB） | 客户端（SCL / Dubbo） |
|------|--------------------------|---------------------|
| 位置 | 独立代理层 | 调用方进程内 |
| 实例列表 | 静态配置或服务发现集成 | 注册中心推送 / 拉取，本地缓存 |
| 优点 | 透明、语言无关 | 少一跳、无代理单点、可按调用上下文路由 |
| 缺点 | 多一跳、代理需要高可用 | 每种语言要 SDK；实例列表有感知延迟 |

- Spring Cloud LoadBalancer（替代已停止维护的 Ribbon）：默认轮询，可换随机或按元数据 `weight` 加权；支持**区域优先**（同可用区优先，无可用实例再跨区）与 **Hint 路由**；实现 `ReactorServiceInstanceLoadBalancer` 可按版本、标签做灰度
- 灰度路由要求灰度标记全链路透传（Feign 拦截器、MQ 消息头）

→ 详见 [负载均衡](/high-avail/3_load_balancing)、[Spring Cloud 服务治理](/spring-cloud/5_service_governance)

### Q17：负载均衡如何配合健康检查摘除故障实例？会话保持有哪些做法？

**核心结论**：主动检查（定时探测健康接口）与被动检查（按真实请求失败 / 超时摘除）结合使用；失败转移**只对幂等请求开启并限制次数**。会话保持是给有状态服务打的补丁，优先做无状态化。

- Nginx 开源版只支持被动检查：`max_fails=3 fail_timeout=10s`，配合 `proxy_next_upstream error timeout` 与 `proxy_next_upstream_tries 2`；主动检查需 Nginx Plus 或 Tengine 的 upstream check 模块
- 非幂等请求（POST）默认不会转发到下一个实例，不要随意加 `non_idempotent`
- 注册中心摘除有感知延迟（Nacos 2.x 秒级，Eureka 可达 2～3 分钟），调用方要配合超时、重试其他实例与熔断

| 会话保持方式 | 问题 |
|------|------|
| IP 哈希 | NAT / 代理后大量用户共用一个 IP，负载严重倾斜 |
| Cookie 粘滞 | 实例故障时会话仍然丢失 |
| 一致性哈希（按 userId） | 扩缩容时部分用户迁移 |
| 无状态化（推荐） | Session 外置到 Redis 或改用 Token |

→ 详见 [负载均衡](/high-avail/3_load_balancing)、[冗余与故障转移](/high-avail/2_redundancy_failover)

## 四、超时、重试与隔离

### Q18：超时设置的原则是什么？上下游超时应该如何配合？

**核心结论**：**每一次跨进程调用都必须显式设置超时**，按下游 P99～P999 加 20%～50% 余量、按接口分别配置。上下游配合的规则是"**越靠近用户越长，越靠近数据越短**"，上游超时必须覆盖下游的全部尝试。

| 超时类型 | 建议 |
|------|------|
| 连接超时 | 同机房 100ms ～ 1s，连不上通常意味着实例不可用 |
| 读取超时 | 按下游 P99～P999 加余量 |
| 获取连接超时 | 几百毫秒，池耗尽时快速失败 |
| 整体超时 / deadline | 由上游剩余时间决定 |

- 很多客户端默认超时过长或不超时：OpenFeign 默认连接 10s、读取 60s，JDBC 驱动 `socketTimeout` 默认 0（不限）
- 上游超时推导：`T_上游 ≥ T × (N + 1) + B + S`（T 下游单次超时、N 重试次数、B 退避总时长、S 自身耗时）；算不过来时缩短下游超时、减少重试或去掉某一层重试，而不是加大上游超时
- 开启 Spring Cloud CircuitBreaker + Resilience4j 时 TimeLimiter 默认只有 1s，可能先于 Feign 读超时触发，要显式配置并保持一致

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

### Q19：重试适用于哪些场景？非幂等接口能直接加重试吗？

**核心结论**：重试只用来消化**短暂故障**（网络抖动、实例切换），且只对**幂等操作**开启。非幂等接口不能直接加重试：读取超时时下游可能已经执行成功，重试会造成重复扣款、重复下单，必须先做幂等（幂等键、唯一约束、状态机）。

| 错误类型 | 是否重试 |
|---------|---------|
| 连接失败、连接被拒绝 | 可以，请求未到达下游，换实例最安全 |
| 读取超时 | 仅幂等操作 |
| 503 / 429 过载信号 | 谨慎，遵守 `Retry-After` |
| 4xx 参数错误、业务异常 | 不重试 |
| 熔断打开（`CallNotPermittedException`） | 不重试 |

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)、[幂等设计](/architecture/5_idempotence)

### Q20：指数退避是什么？为什么要加 Jitter？

**核心结论**：指数退避让每次重试的等待时间按指数增长（100ms、200ms、400ms…），给下游恢复时间；Jitter（随机抖动）把大量客户端的重试时刻打散，避免它们**在同一时刻集中重试**、形成周期性尖峰。

```java
RetryConfig config = RetryConfig.custom()
    .maxAttempts(3)                                   // 总调用次数（含首次）
    .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(
        Duration.ofMillis(100), 2.0, 0.5, Duration.ofSeconds(2)))  // 初始、倍数、±50% 抖动、上限
    .ignoreExceptions(BusinessException.class, CallNotPermittedException.class)
    .build();
```

- 在线请求的重试等待控制在百毫秒级，整体仍要落在上游超时之内；秒级、分钟级退避只适合异步任务和消息重投

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

### Q21：什么是重试放大？如何用"只在一层重试"、重试预算、deadline 传播来控制？

**核心结论**：每层都"重试 3 次"时放大是乘法：3 层调用、每层最多 3 次尝试，最底层会收到 **3 × 3 × 3 = 27 倍**请求，下游本来只是过载，被重试流量直接打垮。

| 规则 | 做法 |
|------|------|
| 只在一层重试 | 放在直接调用不稳定依赖的那一层，其他层失败直接向上返回 |
| 单请求限次 | 最多尝试 2～3 次，换实例重试（`proxy_next_upstream_tries`、SCL 重试）也计入 |
| 重试预算 | 按客户端统计，重试量不超过正常请求的一定比例（如 10%），超出直接失败；可用令牌桶实现：成功返还 ratio 个额度，每次重试消耗 1 个 |
| deadline 传播 | 上游把剩余时间传给下游，下游用 `min(自身超时, 剩余时间)`，剩余不足时不再调用或重试 |

- gRPC 原生支持 deadline 传播；HTTP 自行约定请求头（如 `X-Timeout-Ms`），传**相对时长**而不是绝对时间戳，避开机器间时钟偏差
- Resilience4j 默认装饰顺序中 Retry 在最外层，每次尝试都经过熔断统计，`CallNotPermittedException` 必须排除在重试之外

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

### Q22：线程池隔离和信号量隔离的区别？各自适用什么场景？

**核心结论**：线程池隔离给每个依赖独立线程池，慢调用只占隔离池线程，调用方可按超时放弃等待，隔离最强但有线程切换开销；信号量隔离只限制并发数，调用仍在当前线程执行，几乎无开销但慢调用仍占调用方线程。

| 对比 | 线程池隔离 | 信号量隔离 |
|------|-----------|-----------|
| 隔离程度 | 强 | 中 |
| 开销 | 线程切换、上下文传递（ThreadLocal、链路追踪需额外处理） | 几乎没有 |
| 超时控制 | 调用方可放弃等待（Future 超时） | 依赖下游客户端自身超时 |
| 适用 | 外部 HTTP 调用、慢且不稳定的依赖 | 内部快速依赖、调用量大的场景 |

- **配额按 Little 定律估算**：并发 ≈ 该依赖 QPS × P99 延迟，如 200 QPS、P99 50ms 稳态约 10，配额取 15～20
- 实现：Resilience4j `ThreadPoolBulkhead` / `Bulkhead`、Sentinel 并发线程数限流

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

## 五、熔断

### Q23：熔断器的三种状态是什么？如何切换？半开状态放行多少请求？

**核心结论**：Closed 正常放行并统计失败率 / 慢调用率 → 超过阈值进入 Open，直接拒绝走降级 → 熔断时长到期进入 Half-Open，放行少量探测请求 → 探测成功回到 Closed，失败回到 Open 并重新计时。

| 状态 | 行为 | 进入条件 |
|------|------|---------|
| Closed | 正常放行，持续统计 | 初始状态；或半开探测成功 |
| Open | 直接拒绝，不调用下游 | 统计窗口内指标超过阈值 |
| Half-Open | 放行少量探测请求 | Open 持续熔断时长后自动进入 |

- 半开放行数：**Sentinel 只放行 1 个**探测请求；**Resilience4j 放行 `permittedNumberOfCallsInHalfOpenState` 个**（默认 10，建议显式配置），按这批请求的失败率判断

→ 详见 [熔断](/high-avail/5_circuit_breaking)

### Q24：熔断有哪几种策略？慢调用阈值、最小请求数、熔断时长怎么定？

**核心结论**：三类策略——**慢调用比例、异常比例、异常数**。慢调用比例最常用，因为"变慢"往往比"报错"更早出现，也更伤资源。

| 参数 | 建议 |
|------|------|
| 慢调用 RT 阈值 | 下游正常 P99 的 1.5 ~ 2 倍，且小于调用方超时 |
| 比例阈值 | 50% ~ 60%，太低容易误熔断 |
| 最小请求数 | 按低峰期流量设定，避免"2 个请求失败 1 个就熔断" |
| 统计窗口 | 5 ~ 10s（时间窗口）或最近 50 ~ 100 次（计数窗口） |
| 熔断时长 | 5 ~ 30s，与下游典型恢复时间匹配 |

- 异常数策略适合调用量小、比例波动大的接口
- Resilience4j 默认值偏宽松：`minimumNumberOfCalls` 与 `slidingWindowSize` 均为 100，`waitDurationInOpenState` 60s，`slowCallDurationThreshold` 60s，**每个实例都应显式设置**
- 熔断粒度推荐按接口，而不是按整个依赖服务

→ 详见 [熔断](/high-avail/5_circuit_breaking)

### Q25：哪些异常应该计入熔断统计，哪些不应该？

**核心结论**：只计入**反映下游健康度**的失败；与下游健康无关的业务异常不计入，否则会误熔断。

- **计入**：超时、连接失败、5xx、下游返回的"系统繁忙"类错误
- **不计入**：参数校验失败、业务规则拒绝（如余额不足）等 4xx 类业务异常，Resilience4j 用 `ignore-exceptions` 配置
- 被熔断拒绝本身（`CallNotPermittedException`、`DegradeException`）不能再被重试，否则熔断形同虚设

→ 详见 [熔断](/high-avail/5_circuit_breaking)

### Q26：Sentinel、Hystrix、Resilience4j 的区别？新项目怎么选？

**核心结论**：新项目在 Sentinel 和 Resilience4j 之间选：用 Spring Cloud Alibaba 体系、需要控制台动态调规则选 **Sentinel**；追求轻量、与 Spring Cloud CircuitBreaker 标准集成选 **Resilience4j**。Hystrix 2018 年起进入维护模式，不再用于新项目。

| 维度 | Sentinel | Resilience4j | Hystrix |
|------|---------|-------------|---------|
| 熔断策略 | 慢调用比例、异常比例、异常数 | 失败率、慢调用率 | 失败率 |
| 统计窗口 | 滑动时间窗口 | 计数或时间窗口 | 滑动时间窗口 |
| 隔离 | 并发线程数限制（信号量式） | `Bulkhead` 与 `ThreadPoolBulkhead` | 线程池、信号量 |
| 其他能力 | 限流、热点参数、系统自适应保护 | 限流、重试、TimeLimiter | 请求合并、缓存 |
| 规则配置 | 控制台、配置中心动态推送 | 配置文件、代码 | 配置文件、Archaius |
| Spring 集成 | Spring Cloud Alibaba | Spring Cloud CircuitBreaker | 已从 Spring Cloud 2020 移除 |

→ 详见 [熔断](/high-avail/5_circuit_breaking)

### Q27：`@SentinelResource` 的 `blockHandler` 和 `fallback` 有什么区别？

**核心结论**：`blockHandler` 只处理 Sentinel 规则触发抛出的 `BlockException`（流控、熔断、系统保护）；`fallback` 处理业务代码抛出的异常。两者都配置时，被限流熔断走 `blockHandler`。

- `blockHandler` 方法签名 = 原方法参数 + 最后一个 `BlockException` 参数，必须 `public`；放在其他类时用 `blockHandlerClass` 指定，且方法为 `static`
- `fallback` 方法参数与原方法一致，可额外加一个 `Throwable` 参数
- 非幂等写操作的兜底不要静默返回成功，应抛出明确异常

→ 详见 [Spring Cloud Alibaba - Sentinel](/spring-cloud/6_alibaba)、[熔断](/high-avail/5_circuit_breaking)

## 六、降级

### Q28：降级和熔断有什么区别和联系？

**核心结论**：熔断回答"**要不要继续调用下游**"，是被动触发的保护机制；降级回答"**停止之后返回什么、放弃什么**"，是预先定义的应对策略。熔断打开后通常执行降级逻辑，但降级不一定由熔断触发。

| 对比 | 熔断 | 降级 |
|------|------|------|
| 性质 | 被动触发的保护机制 | 预先定义的应对策略 |
| 触发 | 下游失败率 / 慢调用率超阈值 | 熔断、限流、超时、异常，或人工打开开关 |
| 关注点 | 是否调用下游 | 返回什么、放弃什么 |

→ 详见 [降级](/high-avail/6_degradation)

### Q29：服务降级有哪些级别和手段？如何给功能分级？

**核心结论**：按业务重要性给功能分为核心、重要、一般、边缘四级，故障时**从最不重要的开始放弃**；核心链路不降级，只能靠扩容和限流保护。

| 级别 | 示例 | 降级策略 |
|------|------|---------|
| 核心 | 下单、支付、登录 | 不降级，扩容、限流保护 |
| 重要 | 库存展示、优惠计算 | 返回缓存或近似值 |
| 一般 | 推荐、评论、足迹 | 返回兜底数据或隐藏 |
| 边缘 | 埋点、日志上报、报表 | 直接关闭或改为异步 |

| 手段 | 示例 |
|------|------|
| 返回兜底数据 | 个性化推荐改为热销榜 |
| 关闭功能 | 大促期间关闭商品评价 |
| 读降级 | 读缓存或静态快照 |
| 写降级 | 同步写改为 MQ 异步，稍后补偿 |
| 精度降级 | 实时销量改为分钟级更新 |
| 页面降级 | 活动页切换为 CDN 静态快照 |
| 提示降级 | "系统繁忙，请稍后重试" |

→ 详见 [降级](/high-avail/6_degradation)

### Q30：静态降级和动态降级（开关）分别怎么实现？

**核心结论**：静态降级写死在代码里，由异常自动触发（fallback 兜底）；动态降级由**配置中心开关**控制，无需重启即可生效。两者配合：静态降级兜住意外故障，动态开关用于预案和人工干预。

- **静态降级**：`@SentinelResource(fallback = ...)`、Resilience4j `fallbackMethod`，兜底返回本地缓存的热销榜等，并上报降级指标
- **动态降级**：开关放在 Nacos 等配置中心，用 `@ConfigurationProperties` 绑定（配置变更后自动刷新，无需 `@RefreshScope`），代码中判断开关关闭时直接走兜底、不再调用下游
- 每个手动开关写清打开条件、影响范围、负责人和恢复条件，纳入故障预案

→ 详见 [降级](/high-avail/6_degradation)

### Q31：Sentinel 规则持久化到 Nacos 后，控制台修改的规则为什么重启会丢失？

**核心结论**：因为数据流是单向的。`sentinel-datasource-nacos` **只负责从 Nacos 拉取并监听规则**；Sentinel 控制台默认把规则直接推到应用内存，**不会写回 Nacos**。应用重启后重新从 Nacos 加载，控制台上改的规则就丢了。

- 解决一：改造 Dashboard 的规则发布逻辑，让控制台修改写入 Nacos（推模式），应用再从 Nacos 监听生效
- 解决二：约定只在 Nacos 中修改规则，控制台仅用于查看

→ 详见 [降级](/high-avail/6_degradation)、[Spring Cloud Alibaba - Sentinel](/spring-cloud/6_alibaba)

### Q32：降级逻辑设计时要注意什么？为什么非幂等写操作不能静默降级？

**核心结论**：降级逻辑平时不执行，最容易在真正需要时失效，所以要**有业务价值、不依赖故障源、可观测、定期演练**。非幂等写操作若静默返回"成功"，用户以为下单 / 扣款成功而实际没有执行，造成数据不一致和客诉，用户重试还可能重复执行，必须明确报错或改为"受理 + 异步处理"。

- 兜底数据要有业务价值：避免返回 `null` 或空列表导致前端报错
- 降级逻辑不依赖故障源：推荐服务故障时兜底不能再调推荐服务，也不要调另一个同样可能过载的远程服务
- 可观测：每次降级打日志、上报指标，降级量突增要告警
- 避免级联降级：A 的兜底依赖 B 的数据，B 也在降级，最终返回无意义数据
- 定期演练：真实打开开关、注入故障验证降级路径

→ 详见 [降级](/high-avail/6_degradation)

## 七、限流与过载保护

### Q33：常见限流算法有哪些？令牌桶和漏桶的区别？

**核心结论**：四种——固定窗口、滑动窗口、令牌桶、漏桶。**令牌桶允许突发**（空闲时攒下的令牌可被瞬间消耗），适合入口限流；**漏桶强制匀速输出、不允许突发**，适合保护处理能力固定的下游。

| 算法 | 突发流量 | 典型场景 |
|------|---------|---------|
| 固定窗口 | 边界处可达 2 倍阈值 | 粗粒度配额（如每天调用次数） |
| 滑动窗口 | 平滑，精度取决于子窗口数 | 服务端 QPS 统计（Sentinel） |
| 令牌桶 | 允许，上限为桶容量 | 网关、用户级 / API 级限流（Guava `RateLimiter`、Gateway `RedisRateLimiter`） |
| 漏桶 | 不允许 | 第三方 API 配额、匀速写入（Sentinel "匀速排队"） |

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q34：固定窗口限流有什么问题？滑动窗口如何解决？

**核心结论**：固定窗口有**临界突发**：窗口 1 的最后 100ms 和窗口 2 的最前 100ms 各放行 100 次，200ms 内实际通过 200 次，是阈值的 2 倍。滑动窗口把大窗口拆成多个子窗口随时间滑动，只统计最近 N 个子窗口的总和，子窗口越多越平滑、内存越大。

- Sentinel 秒级统计就是滑动窗口（`LeapArray`），默认 1s 拆成 2 个 500ms 子窗口
- 分布式场景可用 Redis ZSET 记录每次请求时间戳实现精确滑动窗口（见 Q35）

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q35：如何用 Redis + Lua 实现滑动窗口限流？member 和时间戳要注意什么？

**核心结论**：用 ZSET 以时间戳为 score 记录每次请求，Lua 脚本原子完成"**清理窗口外记录 → 计数 → 写入**"。两个关键细节：**member 必须唯一**，**时间取 Redis 服务端时间**。

```lua
-- KEYS[1] 限流 key；ARGV[1] 窗口毫秒；ARGV[2] 上限；ARGV[3] 本次请求唯一 ID
local key, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2])
local t = redis.call('TIME')                                  -- Redis 服务端时间，避免多实例时钟漂移
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)          -- 清理窗口外记录
if redis.call('ZCARD', key) < limit then
    redis.call('ZADD', key, now, now .. '-' .. ARGV[3])        -- member 唯一，同毫秒请求不互相覆盖
    redis.call('PEXPIRE', key, window)
    return 1
end
return 0
```

- member 若直接用时间戳，同一毫秒的多个请求会互相覆盖、少计数
- Lua 中先调用 `TIME` 再写入要求 Redis 5+（默认按效果复制），更老版本需 `redis.replicate_commands()`
- ZSET 每个请求占一个元素，内存与阈值成正比，只适合阈值较小的场景；阈值大时用令牌桶或子窗口计数
- Redis 不可用时要有降级策略：放行（fail-open）并依赖单机限流兜底，强管控场景改为拒绝

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q36：限流应该放在哪一层？网关限流能替代服务内限流吗？

**核心结论**：多层叠加，**越靠外越粗粒度、越省资源，越靠内越精确、越贴近真实容量**。网关限流**不能替代**服务内限流：网关管的是集群总量，挡不住负载不均或部分实例变慢时的单机过载，自我保护的限流必须在服务内做。

| 层次 | 典型实现 | 维度 | 主要作用 |
|------|---------|------|---------|
| 接入层 | CDN / WAF、Nginx `limit_req` | IP、URL | 挡恶意刷量和 CC 攻击 |
| 网关 | Spring Cloud Gateway、APISIX + Redis 令牌桶 | 用户、租户、API | 集群级配额，按调用方公平分配 |
| 服务 | Sentinel、Resilience4j、Guava | 实例级 QPS / 并发 | 按单机容量自保，不依赖外部组件 |
| 方法 / 资源 | Sentinel 热点参数、下游客户端限流 | 参数值、下游资源 | 热点 key 单独限速，保护下游配额 |

- 按用户 / IP 限流时注意 key 基数与过期；经过 CDN / SLB 后要从可信 `X-Forwarded-For` 取真实 IP

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q37：限流阈值如何确定？被限流时应该返回什么？

**核心结论**：阈值来自压测：**单机阈值 ≈ 压测拐点 × 0.7～0.8**，集群阈值 ≈ 单机阈值 × 实例数并按负载不均打折，先宽松上线再按命中数据收紧。被限流是正常业务结果：超配额返回 **429**，服务过载返回 **503**，都带 `Retry-After`。

| 场景 | 状态码 | 说明 |
|------|-------|------|
| 超过调用方配额（按用户 / AppKey） | `429 Too Many Requests` + `Retry-After` | 调用方自己降速 |
| 服务整体过载（过载保护、按优先级卸载） | `503 Service Unavailable` + `Retry-After` | 客户端应退避 |
| gRPC | `RESOURCE_EXHAUSTED` / `UNAVAILABLE` | 语义同上 |

- 集群阈值平均拆到单机时，扩缩容会让总阈值被动变化；需严格控制总量用网关集中限流或 Sentinel 集群流控
- 客户端收到 429 / 503 不能立即重试，按 `Retry-After` 或指数退避，并计入重试预算
- Spring Cloud Gateway 的 `RequestRateLimiter` 触发时**直接写 429 并结束响应、不抛异常**，`ErrorWebExceptionHandler` 捕获不到；默认响应体为空、不带 `Retry-After`，需要时自行扩展
- Gateway 的 `KeyResolver` 不要把空 key 兜底成固定值，否则所有匿名请求共用一个桶；用 `deny-empty-key` 拒绝

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q38：为什么并发数限流比 QPS 限流更能应对下游变慢？和 Little 定律有什么关系？

**核心结论**：由 Little 定律 `并发数 = 吞吐量 × 平均 RT`，QPS 阈值不变时 RT 上涨会让**在途请求成倍堆积**；并发上限不变时，**吞吐会随 RT 自动收缩**，线程池始终安全。

| 状态 | 吞吐量 | 平均 RT | 所需并发 |
|------|-------|--------|---------|
| 正常 | 1000 QPS | 50ms | 50 |
| 下游变慢，只限 QPS | 1000 QPS | 500ms | 500，线程池被打满 |
| 下游变慢，限并发 50 | 自动降到 100 QPS | 500ms | 50，线程池安全 |

- 实现：Sentinel `FLOW_GRADE_THREAD`、Resilience4j `Bulkhead`，或一个 `Semaphore`

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q39：什么是过载保护？Sentinel 系统自适应保护和 BBR 思想是什么？

**核心结论**：固定阈值只在"容量不变"时成立，依赖变慢、Full GC、宿主机争抢都会让真实容量临时下降。过载保护根据**系统实时状态**决定是否放行。BBR 思想源自 TCP 拥塞控制：系统最佳在途量 ≈ **最大吞吐 × 最小延迟**，在途请求超过这个估算值时拒绝新请求。

- **Sentinel SystemRule**：从整机维度保护入口流量（只对 `EntryType.IN` 生效），可设 load、CPU 使用率、入口平均 RT、入口并发线程数、入口总 QPS 阈值
- load 超阈值时不直接拒绝，而是再做 **BBR 式判断**：当前并发 > `最大成功 QPS × 最小 RT` 才拒绝，避免误杀
- load 指标只在 Linux / Unix 生效；容器中 load 反映宿主机，**容器内优先用 CPU、RT、并发数指标**
- 同类实现：Kratos 的 BBR 限流器、Netflix concurrency-limits（Vegas / Gradient 动态调整并发上限）

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q40：负载卸除时如何按优先级丢弃请求？客户端自适应节流是怎么工作的？

**核心结论**：必须丢请求时**先丢不重要的**：给请求分级，在途请求越多，允许进入的优先级越高。客户端自适应节流让调用方根据后端的接受率在本地按比例提前拒绝，减轻后端"拒绝本身"的成本。

- **按优先级卸载**：以压测拐点并发为上限，如 CRITICAL（下单、支付）到上限才拒绝、NORMAL 在 80% 开始卸载、LOW（推荐、埋点、报表）在 60% 开始卸载，被卸载请求返回 503 + `Retry-After`
- 优先级由网关按路由或调用方写入，不信任客户端自带的值；已超过调用方 deadline 的请求直接丢弃；越早卸载越省资源
- **客户端节流**（Google SRE）：统计最近一段时间（如 2 分钟）的请求数 `requests` 与被接受数 `accepts`，本地拒绝概率 `p = max(0, (requests − K × accepts) / (requests + 1))`，K 通常取 2；后端正常时 p 为 0
- 与熔断的区别：熔断是开 / 关二值切换，自适应节流按比例连续调节，更平滑

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

## 八、优雅上下线与变更

### Q41：什么是优雅停机？如何在 Spring Boot 中实现？

**核心结论**：优雅停机是**先摘流量、再处理完在途请求和异步任务、最后释放资源退出**，让停机过程不产生失败请求。最常见的错误是顺序颠倒：先停 Web 容器再注销，调用方感知下线之前仍把请求发过来。

| 顺序 | 动作 |
|------|------|
| 1 | 从注册中心注销 / 从 K8s Endpoints 摘除 |
| 2 | 等待调用方刷新实例列表（数秒） |
| 3 | Web 容器停止接收新请求，处理完在途请求 |
| 4 | 停止 MQ 消费、定时任务，等待线程池任务完成 |
| 5 | 关闭连接池、释放资源，进程退出 |

```yaml
server:
  shutdown: graceful                     # 2.3+ 支持；3.4 起嵌入式容器默认开启
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s      # 每个生命周期阶段最长等待
```

- 自定义线程池设 `setWaitForTasksToCompleteOnShutdown(true)` 与 `setAwaitTerminationSeconds`；`@Scheduled` 需开启 `spring.task.scheduling.shutdown.await-termination`
- MQ 消费者先停止拉取、处理完已拉取消息并提交位点，未提交的会重投，消费必须幂等；Dubbo 内置优雅停机
- 禁止 `kill -9`，它不会触发 JVM Shutdown Hook

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)

### Q42：K8s 中如何配合实现优雅停机？`preStop` 的作用是什么？为什么需要 sleep？

**核心结论**：Pod 删除时，**从 Endpoints 摘除与发送 SIGTERM 是并行发生的**，kube-proxy、Ingress、注册中心客户端感知摘除都需要时间。`preStop` 在 SIGTERM 之前执行，sleep 一段时间让流量先摘干净，再让应用开始停机。

```yaml
spec:
  terminationGracePeriodSeconds: 60      # 总宽限期，包含 preStop 耗时，超时后 SIGKILL
  containers:
    - name: order-service
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "curl -s -X POST localhost:8080/internal/offline; sleep 15"]
```

| 参数 | 建议 |
|------|------|
| `preStop` 等待 | 覆盖 Endpoints 传播 + 注册中心推送 + 客户端缓存刷新，一般 10 ~ 20s |
| `timeout-per-shutdown-phase` | 大于 P99.9 请求耗时，一般 20 ~ 30s |
| `terminationGracePeriodSeconds` | ≥ preStop 等待 + 应用停机超时 + 余量 |

- 微服务场景在 `preStop` 中先主动从注册中心注销（调用方有本地实例缓存）
- **SIGTERM 要能到达 JVM**：Dockerfile 用 exec 形式 `ENTRYPOINT ["java", "-jar", "app.jar"]` 或 `tini` 作 PID 1；shell 形式时 JVM 收不到信号，最终被 SIGKILL

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)

### Q43：PodDisruptionBudget 的作用是什么？它能约束滚动更新吗？

**核心结论**：PDB 限制**通过 Eviction API 发起的自愿中断**同时驱逐的 Pod 数，如 `kubectl drain`、集群自动缩容回收节点、托管集群节点升级。它**不能约束滚动更新**：滚动期间的可用实例数由 Deployment 的 `maxUnavailable` / `maxSurge` 控制。

| 机制 | 约束 | 不约束 |
|------|------|-------|
| `maxUnavailable` / `maxSurge` | Deployment 自身的滚动更新 | 节点维护、驱逐 |
| PDB | 走 Eviction API 的自愿中断 | 滚动更新、直接 `kubectl delete pod`、节点宕机等非自愿中断 |

- 滚动更新不减可用实例：`maxUnavailable: 0` + `maxSurge: 1`，配合 `minReadySeconds` 给预热留余量
- PDB 不要把驱逐堵死：`minAvailable` 等于副本数（或单副本配 `minAvailable: 1`）会让 `kubectl drain` 一直卡住；副本数会被 HPA 调整时优先用 `maxUnavailable: 1` 或百分比

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)

### Q44：为什么新实例启动后需要预热？有哪些预热手段？

**核心结论**：新实例 JIT 未编译、本地缓存为空、连接池未建立、懒加载 Bean 未初始化，RT 明显偏高，直接接满流量可能被打垮，甚至触发熔断和级联故障。手段是"**预热完成再就绪 + 权重逐步放量**"。

| 冷启动原因 | 预热手段 |
|-----------|---------|
| JIT 未编译 | 启动后执行预热请求；小流量逐步放大 |
| 本地缓存为空 | 启动时加载热点数据 |
| 连接池未建立 | 启动阶段主动获取连接，配置 `minimumIdle` |
| 类加载、懒加载 | 预热调用核心接口 |

- Spring Boot 在所有 `ApplicationRunner` 执行完才置为 `ACCEPTING_TRAFFIC`，预热放在 Runner 中，readiness 自然等到预热结束
- **注册中心的注册时机早于就绪**：Spring Cloud 自动注册在 Web 容器启动时触发，Nacos 等调用方可能在预热前就发现实例；可关闭自动注册、预热后代码注册，或先注册低权重
- 权重预热：Dubbo 内置 warmup（默认 10 分钟线性增长）；Nacos 由发布平台分步调权重；SCL 需自定义负载均衡器按启动时间计算权重

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)、[JVM 层性能策略](/high-perf/5_jvm_tuning)

### Q45：变更三板斧是什么？配置变更如何灰度？

**核心结论**：变更三板斧是**可灰度、可监控、可回滚**，任何一项做不到的变更都不应在高峰期上线。配置变更通常秒级推送到全部实例、没有滚动过程，比代码发布更危险，要先推少量实例观察。

| 原则 | 常见做法 |
|------|---------|
| 可灰度 | 单机 → 单机房 → 1% → 10% → 全量，每批之间留观察时间 |
| 可监控 | 发布大盘对比新旧版本成功率 / RT；燃烧速率告警 |
| 可回滚 | 镜像版本化、`kubectl rollout undo`、功能开关、配置历史版本 |

- **配置灰度**：Nacos Beta 发布到指定 IP，观察后再全量；发布前 Schema 校验，代码对非法值兜底为默认值；保留历史版本一键回滚；审批与操作审计
- 配套规则：发布期间异常先回滚再排查；变更可追溯；大促前封网；错误预算不足时冻结非紧急变更
- 表结构变更遵循**先扩展后收缩（Expand-Contract）**，保证任一时刻回滚代码不需要回滚表结构

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)

## 九、多活与容灾

### Q46：RPO 和 RTO 分别是什么？

**核心结论**：RPO（Recovery Point Objective）是故障后**最多丢失多长时间的数据**，由数据复制方式决定；RTO（Recovery Time Objective）是故障后**多长时间恢复服务**，由备用环境状态与切换自动化程度决定。

| 容灾级别 | 架构 | RPO | RTO |
|---------|------|-----|-----|
| 数据级 | 异地定期备份 | 小时 ~ 天 | 天级 |
| 应用级（冷 / 温备） | 异地部署应用，数据异步复制 | 秒 ~ 分钟 | 小时级 |
| 业务级（热备） | 备用机房实时同步，可快速切换 | 秒级 | 分钟级 |
| 多活 | 多机房同时服务 | 接近 0（单元内） | 秒 ~ 分钟（切流） |

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q47：同城双活和异地多活的区别？各自解决什么问题？

**核心结论**：同城双活利用同城机房间 1～2ms 的 RTT，可以跨机房同步调用和同步复制，大多是"**应用双活、数据主备**"，防单机房故障；异地多活面对 25～30ms 的跨地域 RTT，只能异步复制，必须**单元化**让一次请求在本地域闭环，防城市 / 地域级故障。

| 对比 | 同城双活 | 异地多活 |
|------|---------|---------|
| 距离与 RTT | 同城几十公里，1 ~ 2ms | 跨城市，如北京—上海 25 ~ 30ms |
| 数据 | 通常单主，另一机房为半同步从库 | 按路由键分片，各单元写自己的数据，异步同步 |
| 改造成本 | 中 | 高（业务、数据、中间件全面改造） |
| 防御范围 | 单机房故障 | 地域级故障 |

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q48：两地三中心是什么架构？异地灾备中心为什么"不敢切"？

**核心结论**：两地三中心 = **同城双中心 + 异地灾备中心**：同城两中心做双活或主备（同步 / 半同步复制），异地中心通过异步复制接收数据（RPO 秒～分钟），平时通常不承接流量。"不敢切"是因为异地中心长期不承接流量，**配置漂移、容量不足、依赖缺失**都要到切换那一刻才暴露，切换本身风险极高。

- 这正是异地多活要解决的问题：让每个中心常态承接流量，能力持续被验证
- 没有常态化演练的灾备只是昂贵的冷备

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q49：什么是单元化？如何选择路由键？全局数据如何处理？

**核心结论**：单元是一个能完成全部业务闭环的自包含部署集合（接入、应用、缓存、消息和本单元的数据分片）。选一个**贯穿业务的路由键**，所有请求和数据按它划分到单元，单元型数据的读写和调用都不出单元；无法按路由键拆分的全局数据**中心单元集中写，各单元读副本**。

| 业务 | 常用路由键 |
|------|-----------|
| 电商交易 | 买家 userId（订单、购物车、支付单都归属买家） |
| 外卖 / 出行 | 城市 / 区域 |
| SaaS | 租户 ID（大租户可独占单元） |

| 数据类型 | 示例 | 写入 | 读取 |
|---------|------|------|------|
| 单元型 | 订单、购物车、用户资产 | 归属单元 | 归属单元 |
| 全局型 | 库存、商家、商品主数据 | 中心单元 | 各单元只读副本（容忍秒级延迟） |
| 共享只读 | 类目、地区码、配置 | 后台统一维护 | 各单元本地 |

- 路由两级映射：`userId → 分片号（如 userId % 100）→ 单元`，映射放配置中心，切流只改分片到单元的映射；网关对误入请求转发到正确单元
- 强一致场景（如扣库存）走中心单元，或给各单元预分配库存额度；全局 ID 带单元信息或全局唯一

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q50：双向数据同步如何避免复制回环和写冲突？

**核心结论**：**复制回环**靠给同步写入打来源标记、同步组件过滤；**写冲突**靠单元化从源头避免（同一数据只在一个单元写），兜底按版本号或 `update_time` "后写胜"并告警。

| 问题 | 处理方式 |
|------|---------|
| 复制回环 | 同步写入时打来源标记（事务标记表 / GTID 来源），同步组件过滤 |
| 写冲突 | 单元化避免；兜底"后写胜"并告警 |
| 主键冲突 | 分布式 ID；或自增步长错开（`auto_increment_increment` / `offset`） |
| 复制延迟 | 监控延迟，切流前必须追平 |
| DDL 同步 | 统一变更平台，先兼容再切换 |

- 工具：Canal（订阅 binlog 的底座）、Otter（双向同步与回环控制，社区已不活跃）、云上 DTS 双向同步、X-Pipe（Redis 跨机房）、MirrorMaker 2（Kafka）

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q51：计划内切流为什么要先禁写？

**核心结论**：跨单元是异步复制，源单元总有尚未同步到目标单元的数据。先禁写防止切换过程中**两边同时写**，再等同步延迟归零，才能做到 **RPO = 0**；禁写窗口通常为秒级到分钟级。

| 步骤 | 操作 |
|------|------|
| 1 | 确认目标单元容量余量 |
| 2 | 源单元对待切分片**禁写** |
| 3 | 等待源 → 目标数据同步延迟归零 |
| 4 | 修改路由表，推送到所有网关 |
| 5 | 目标单元对这些分片开放写 |
| 6 | 验证核心指标，观察跨单元转发量 |

- 真实故障时源单元已不可用、无法追平，只能接受异步复制带来的少量差异，事后对账修复
- 演练要常态化、从小比例分片开始、全程盯 SLO、异常立即回切

→ 详见 [多活与容灾](/high-avail/9_multi_active)

## 十、混沌工程

### Q52：混沌工程是什么？和传统测试有什么区别？有哪些工具？

**核心结论**：混沌工程在可控范围内**主动注入真实世界会发生的故障**，验证系统在异常条件下能否保持稳态，提前发现弱点并证明冗余、熔断、降级、切流预案真的有效。传统测试验证功能是否符合预期，混沌工程发现未知弱点，以稳态指标是否偏离假设来判定。

| 对比 | 传统测试 | 混沌工程 |
|------|---------|---------|
| 目标 | 验证功能是否符合预期 | 发现异常条件下的未知弱点 |
| 输入 | 构造的正常 / 异常输入 | 宕机、延迟、丢包、资源耗尽等真实故障 |
| 环境 | 测试环境 | 从预发逐步推进到生产 |
| 判定 | 用例通过 / 失败 | 稳态指标是否偏离假设 |

| 工具 | 特点 |
|------|------|
| ChaosBlade（阿里） | 主机、容器、K8s、JVM 方法级故障注入 |
| Chaos Mesh（CNCF） | K8s 原生，CRD 声明实验，`Schedule` 做周期实验、`Workflow` 编排 |
| Chaos Monkey（Netflix） | 随机终止实例，混沌工程鼻祖 |
| Litmus | K8s 原生，实验市场丰富 |

→ 详见 [混沌工程](/high-avail/10_chaos_engineering)

### Q53：混沌实验的流程是什么？如何控制爆炸半径？

**核心结论**：流程是 **建立稳态假设 → 设计实验 → 注入故障 → 观察指标 → 修复加固**并重跑验证，形成闭环。控制爆炸半径的核心是"**从小开始、有终止条件、能自动恢复**"。

| 阶段 | 输出物 |
|------|--------|
| 建立假设 | 稳态指标与基线，如"下游延迟 +300ms 时下单成功率仍 > 99.9%、P99 < 500ms" |
| 设计实验 | 故障类型、注入目标、爆炸半径、终止条件、回滚方案 |
| 注入故障 | ChaosBlade / Chaos Mesh 执行，设置自动恢复时间 |
| 观察指标 | 对比监控与告警，验证假设 |
| 修复加固 | 补超时、熔断、副本、告警阈值，然后重新实验 |

- 爆炸半径：从单实例、小比例流量开始逐步扩大；先测试环境、再预发、再生产低峰期
- 实验命令加 `--timeout` / `duration` 自动恢复，准备一键回滚；稳态指标越过终止条件（如成功率 < 99.5%）立即停止
- 实验前通知相关团队与值班，避免被误判为真实故障

→ 详见 [混沌工程](/high-avail/10_chaos_engineering)

### Q54：如何用故障注入验证熔断、降级是否生效？

**核心结论**：针对依赖注入"变慢"和"不可用"两类故障，在正常压力下观察熔断是否按阈值打开、降级是否返回有意义的兜底、核心成功率是否保持，恢复后确认熔断经半开探测自动关闭。

```bash
# 假设：库存服务 checkStock 变慢到 800ms（超过 Sentinel 慢调用阈值 500ms）时，下单接口 10s 内熔断并走降级
./blade prepare jvm --pid <inventory-pid>                       # JVM 实验前必须先挂载 Agent
./blade create jvm delay --time 800 \
  --classname com.example.InventoryService --methodname checkStock \
  --pid <inventory-pid> --timeout 600                           # 10 分钟后自动恢复
# 对下单接口施加正常水平的压力，观察 Sentinel Dashboard：熔断是否打开、降级量与成功率
./blade destroy <experimentUid>                                 # 销毁实验，确认熔断自动恢复
```

- 验证降级：对依赖注入 100% 丢包或方法抛异常，确认兜底数据有业务价值、不依赖故障源
- 同一思路验证其他预案：Pod Kill 验证故障摘除、DB 方法延迟验证获取连接超时与舱壁隔离、滚动发布中杀 Pod 验证优雅停机

→ 详见 [混沌工程](/high-avail/10_chaos_engineering)

## 十一、故障应急与复盘

### Q55：故障如何分级？P0 和 P1 的判定标准与响应要求有什么不同？

**核心结论**：分级决定响应规格（谁被叫起来、多快响应、要不要对外通告），标准要**事先量化**、最好与 SLO 挂钩，不能在现场讨论"这算不算大故障"。P0 是核心业务全面不可用或数据、资损问题；P1 是核心业务部分不可用或重要功能完全不可用。

| 级别 | 判定标准（满足任一） | 响应要求 | 通报范围 |
|------|------------------|---------|---------|
| P0 | 核心业务（下单、支付、登录）全面不可用；数据丢失或泄露；资损持续扩大 | 5 分钟内响应，立即拉应急群，负责人与技术负责人到场 | 管理层、客服，必要时对外公告 |
| P1 | 核心业务部分不可用或成功率明显下降（如 > 5% 用户受影响）；重要功能完全不可用 | 15 分钟内响应，值班 + 相关服务负责人 | 技术负责人、业务方、客服 |
| P2 | 非核心功能不可用；核心性能明显下降但可用 | 30 分钟内响应 | 相关团队 |
| P3 | 影响很小或有绕过方案 | 1 个工作日内 | 提单跟踪 |

- **定级宁高勿低**，影响扩大随时升级；燃烧速率超阈值可自动定为 P1

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)

### Q56：线上出现故障时的处理流程是什么？为什么要先止血后定位？

**核心结论**：流程是 **发现 → 响应 → 止血 → 恢复 → 复盘**。先止血是因为可用性由 MTTR 决定，而根因定位耗时不可控；大部分线上故障由发布、配置、数据变更或流量变化引起，回滚、切流、降级往往几分钟就能恢复业务。

| 阶段 | 关键动作 | 常见误区 |
|------|---------|---------|
| 发现 | 告警、巡检、客服反馈；确认影响范围 | 只盯告警，忽略客服和舆情 |
| 响应 | 确认告警、定级、拉应急群、指定应急指挥（IC） | 多人同时处理却没人统筹 |
| 止血 | 按预案回滚、切流、降级、限流 | 在线上边猜边改代码 |
| 恢复 | 验证核心指标回到正常，逐步撤销临时措施 | 指标刚好转就宣布恢复 |
| 复盘 | 1 ~ 3 个工作日内完成 | 只写经过不写改进 |

- 止血的第一个问题永远是"**最近有没有变更**"，有疑似变更先回滚
- 止血前花一分钟保留现场（`jstack`、`jmap -histo`、GC 日志、异常实例先摘流量不销毁），但**不能阻塞止血**
- P0 / P1 明确分工：IC 统筹决策、技术处理人排查执行、沟通负责人定时同步、记录人记时间线

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)

### Q57：常见的止血手段有哪些？分别适用于什么场景？

**核心结论**：按"影响小、见效快"的顺序选择，手段要**平时准备好、演练过**，故障时只做选择和执行。

| 手段 | 适用场景 | 注意事项 |
|------|---------|---------|
| 回滚 | 故障与最近的发布、配置变更时间吻合 | 最常用最有效；要求数据库变更向后兼容 |
| 切流 | 单实例、单机房或单地域故障 | 先确认目标有足够容量 |
| 摘除 / 重启 | 个别实例假死、内存泄漏、连接泄漏 | 先摘流量保留现场再重启，重启只是临时手段 |
| 降级开关 | 非核心依赖故障或资源紧张 | 按预案顺序打开 |
| 限流 | 流量突增超过容量，或保护故障中的下游 | 优先限低优先级流量 |
| 扩容 | 流量增长导致资源不足 | 瓶颈在数据库等共享资源时，扩应用反而加剧故障 |
| 隔离攻击流量 | 恶意刷量、CC 攻击 | 按 IP、设备、账号封禁 |
| 数据修复 | 错误数据写入导致的故障 | 先止住错误写入再修数据，修复脚本需复核 |

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)

### Q58：如何降低 MTTD 和 MTTR？

**核心结论**：缩短 MTTD 靠**告警质量**（对准用户可感知的症状、少而准）；缩短 MTTR 靠**变更关联、预案 Runbook、统一观测入口和演练**。

| 手段 | 作用 | 做法 |
|------|------|------|
| 基于 SLO 的告警 | 缩短 MTTD、减少误报 | 告警对准成功率、延迟，用燃烧速率告警 |
| 告警降噪 | 防止重要告警被淹没 | 聚合、抑制、静默；每条告警都应可操作，否则删除 |
| 变更关联 | 快速定位诱因 | 发布、配置、数据变更统一记录，告警时自动展示前后变更 |
| 预案与 Runbook | 缩短决策和执行时间 | 触发条件、影响判断、止血步骤、验证方法、升级联系人，告警直接链接 Runbook |
| 统一观测入口 | 缩短定位时间 | 指标、日志、链路通过 TraceId 关联 |
| 故障演练 | 验证预案可用、熟悉操作 | 定期混沌实验与切流演练 |

- 配套 On-call：主备值班、明确升级路径（如 5 分钟未确认升级备值班，15 分钟未定位升级负责人）

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)

### Q59：什么是无责复盘？复盘报告应包含哪些内容？

**核心结论**：无责复盘的目的是**改进系统而不是追究个人**：一次误操作能造成故障，说明系统缺少防护；追责只会让大家隐瞒信息，下次更难找到真实原因。报告要能从时间线得出 MTTD / MTTR，用 5 Whys 找到系统层面的根因，并产出有负责人和截止日期的改进项。

| 部分 | 内容 |
|------|------|
| 概要 | 级别、影响时长、影响范围（用户数、订单数、资损）、错误预算消耗 |
| 时间线 | 按分钟记录：故障开始、告警、响应、关键决策、止血、恢复 |
| 关键指标 | MTTD、MTTR 与各阶段耗时 |
| 根因分析 | 直接原因、根本原因，5 Whys 逐层追问 |
| 做得好的 | 哪些告警、预案、操作发挥了作用 |
| 改进项 | 每项有负责人、截止日期、验收标准，按预防 / 发现 / 恢复三类考虑 |

- 例：根因不是"某人把超时从 3s 改成了 300ms"，而是**超时配置缺乏集中管理、灰度缺乏与基线的自动对比**
- 同一根因的故障再次发生，先检查上次的改进项是否落实

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)
