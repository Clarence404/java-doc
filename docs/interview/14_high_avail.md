# 高可用面试题解答

> 题目清单见 [高可用面试题](/high-avail/99_interview)，细节见 [高可用模块](/high-avail/0_overview)；三高另外两页：[高性能](./12_high_perf) · [高并发](./13_high_con)。
>
> 版本基线：JDK 21 / 25 LTS、Spring Boot 4.x，与旧版本不同处单独说明。

## 一、可用性度量

### Q1：SLA 99.99% 意味着每年多少故障时间？每月呢？

**一句话**：99.99%（4 个 9）每年最多停约 52.6 分钟，每月（按 30 天）约 4.32 分钟，每周大约 1 分钟。

- 99.9%：每年约 8.76 小时，每月约 43.2 分钟
- 99.999%：每年约 5.26 分钟，每月不到半分钟
- 每多一个 9，成本往往涨一个数量级：4 个 9 意味着出故障只能靠自动切换，人工来不及
- 互联网核心业务一般定在 99.95%～99.99%，不是越高越好

→ 详见 [可用性度量](/high-avail/1_sla_slo)

### Q2：SLA、SLO、SLI 分别是什么？三者什么关系？

**一句话**：SLI 是「量出来的指标」，SLO 是「内部定的目标」，SLA 是「对外签的合同」。SLO 要比 SLA 更严，给团队留出反应时间，比如 SLA 99.9%、SLO 99.95%。

- SLI 例子：非 5xx 请求的占比、延迟低于 300ms 的请求占比
- SLO 例子：最近 30 天成功率 ≥ 99.9%
- SLA 例子：月可用率低于 99.9% 就退 10% 服务费
- 延迟用「达标请求占比」而不是平均值；从用户入口（网关）统计，先按历史数据定，再慢慢收紧

→ 详见 [可用性度量](/high-avail/1_sla_slo)

### Q3：什么是错误预算？如何用它约束发布节奏？

**一句话**：错误预算 = 1 − SLO，就是一个周期内「允许出错的额度」。SLO 99.9% 时，30 天里可以停 43.2 分钟；额度剩得多就大胆发布，快用完就停下来修稳定性。

- 剩余 > 50%：正常迭代，可以做有风险的发布
- 剩余 10%～50%：放慢节奏，必须灰度发布
- 剩余 < 10% 或已耗尽：冻结新功能，只允许稳定性修复和紧急补丁
- 它把「开发要快、运维要稳」变成一条共同规则，前提是研发、运维、产品事先都认可

→ 详见 [可用性度量](/high-avail/1_sla_slo)

### Q4：为什么基于燃烧速率告警比直接按错误率告警更好？

**一句话**：燃烧速率 = 实际错误率 /（1 − SLO），表示「照现在的速度，预算多快会烧完」。固定错误率阈值分不清短暂抖动和长期小问题，燃烧速率只在真正威胁 SLO 时才告警。

- 固定阈值的问题：几秒的尖刺会误报，长时间的小幅出错又会漏报
- 常用做法：1 小时内燃烧速率超过 14.4（烧掉 30 天预算的 2%）就立刻叫人
- 用长短两个窗口同时判断：长窗口确认问题真实存在，短窗口保证恢复后告警能及时消失

→ 详见 [可用性度量](/high-avail/1_sla_slo)

### Q5：MTBF、MTTR 是什么？提升可用性应优先降低哪一个？

**一句话**：MTBF 是平均多久出一次故障，MTTR 是平均多久能恢复，可用率 = MTBF /（MTBF + MTTR）。优先降低 MTTR，因为故障没法杜绝，但恢复可以做到很快。

- 例：平均 720 小时坏一次、每次恢复 1 小时，可用率约 99.86%；恢复缩到 6 分钟就接近 99.99%
- 提高 MTBF：代码质量、容量规划、变更管控、故障演练
- 降低 MTTR：自动故障切换、一键回滚、降级开关、提前写好预案
- 发现得快（MTTD，平均发现时间）也算在恢复时间里，靠好的告警

→ 详见 [可用性度量](/high-avail/1_sla_slo)、[故障应急与复盘](/high-avail/11_incident_response)

### Q6：四个 99.9% 的服务串联，整体可用率是多少？两个 99% 的实例并联呢？

**一句话**：串联是相乘，0.999⁴ ≈ 99.6%（一年约停 35 小时）；并联是「全部坏掉才算坏」，1 − 0.01² = 99.99%。

- 串联依赖越多，整体越差，而且比最差的那个还差，所以要减少同步强依赖
- 并联能大幅提高可用率，但前提是各副本「不会一起坏」
- 同机架断电、同一个版本 Bug 会让副本同时挂，所以冗余要跨机房 / 机架部署、发布要灰度
- 整体可用率看短板：应用加再多实例，数据库是单点，整体还是被数据库卡住

→ 详见 [可用性度量](/high-avail/1_sla_slo)

## 二、冗余与故障转移

### Q7：冷备、温备、热备有什么区别？

**一句话**：区别在于备用机器平时「醒着没有」：冷备完全没运行，温备开着但不接流量，热备随时可接管。越热切换越快，成本也越高。

| 类型 | 平时状态 | 切换时间 | 成本 |
|------|---------|---------|------|
| 冷备 | 只有备份文件 | 小时 ~ 天 | 低 |
| 温备 | 已部署，不接流量 | 分钟级 | 中 |
| 热备 | 运行中，实时同步 | 秒 ~ 分钟 | 高 |
| 多活 | 同时接流量 | 秒级 | 最高 |

- 冷备不是没用：复制会把误删也同步过去，备份是防误删、防勒索的最后一道防线，要定期演练恢复

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q8：主备、主主、集群三种模式各有什么优缺点？

**一句话**：主备最简单但备机闲着；主主两边都能用但会写冲突；集群靠投票自动选主、能扩展，但最复杂。

| 模式 | 优点 | 缺点 | 例子 |
|------|------|------|------|
| 主备 | 简单，无写冲突 | 备机闲置，切换有中断 | MySQL 主从、Keepalived |
| 主主 | 资源利用率高 | 写冲突、自增 ID 冲突 | MySQL 双主 |
| 集群 | 自动选主、可扩展 | 复杂，要奇数节点 | Redis Cluster、etcd |

- 生产里 MySQL 双主一般是「双主单写」：同一时间只写一边，本质还是主备，只是切换后不用重建复制

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q9：K8s 的 liveness 和 readiness 探针有什么区别？为什么探针不建议检查数据库等共享依赖？

**一句话**：liveness 问「还活着吗」，失败就重启容器；readiness 问「现在能接流量吗」，失败只是把流量摘掉、不重启。两者都不该去查数据库、Redis 这类大家共用的依赖。

| 探针 | 失败后果 | 应该检查 |
|------|---------|---------|
| liveness | 重启容器 | 进程自己是否卡死（死锁等） |
| readiness | 摘流量，不重启 | 本实例是否准备好（预热完、没在停机） |
| startup | 启动超时就重启 | 是否启动完成，期间不跑另外两个探针 |

- 查共享依赖的后果：数据库一抖，所有实例同时失败，要么一起重启，要么全被摘光，局部故障变成全站不可用
- 而且摘流量也没用：换哪个实例，连的都是同一个数据库
- 依赖出问题应该靠超时、熔断、降级处理

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q10：Keepalived 如何实现 VIP 漂移？

**一句话**：Keepalived 用 VRRP 协议在几台机器间选出优先级最高的当主，主持有虚拟 IP（VIP）并定期发心跳；备机收不到心跳或主机健康检查失败时，备机接管 VIP，秒级完成切换。

- 用 `track_script` 定时检查 Nginx 等进程，失败就降低本机优先级，触发切换
- 两台都配成 BACKUP + `nopreempt`（不抢占），避免原主恢复后又把 VIP 抢回来，多抖一次
- 风险是脑裂：两台之间心跳断了，会都以为自己是主，同时持有 VIP，需要第三方仲裁（见 Q11）

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q11：什么是脑裂？有哪些防护手段？fencing token 是什么？

**一句话**：脑裂是网络断开后两边都以为对方挂了，同时出现两个「主」各自写数据，恢复后数据冲突。防护靠「多数派投票选主」，再让存储拒绝旧主的写入。

- 多数派仲裁：拿到超过半数票的一方才能当主（Raft、Redis Sentinel）；所以集群用奇数节点，3 个容忍坏 1 个，5 个容忍坏 2 个
- fencing token：每次选主发一个递增的编号，写数据时带上，存储只接受最大编号，旧主（比如 Full GC 卡住后醒来）写入会被拒绝
- 强制隔离旧主：切换前先把旧主断电、断网或收回权限
- 旧主自我降级：联系不上足够的从库时主动拒绝写入

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q12：MySQL 主库宕机如何自动切换？MHA、Orchestrator、MGR 有什么区别？

**一句话**：自动切换就是：发现主库挂了 → 选数据最新的从库当新主 → 其他从库改连新主 → 应用连接切过去。MHA 和 Orchestrator 是外部工具帮你切，MGR 是 MySQL 自带的组复制，内部投票选主。

| 方案 | 怎么做 | 切换速度 | 备注 |
|------|-------|---------|------|
| MHA | 外部监控，补齐差异 binlog 再提升从库 | 约 30 秒 | 已多年不维护 |
| Orchestrator | 识别复制拓扑，自动提升并重建 | 秒级 | 自身也高可用 |
| MGR | 组复制，多数派确认后提交 | 秒级 | 强一致，需多数节点存活 |

- 应用侧：连接串不要写死主库 IP，用 VIP、DNS 或 ProxySQL / MySQL Router 这类代理
- 半同步复制能减少切换时丢数据，但它退化成异步时仍可能丢

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

### Q13：如何梳理强弱依赖？弱依赖故障时怎样保证主链路不受影响？

**一句话**：强依赖挂了核心功能就做不成（库存、下单、支付）；弱依赖挂了核心功能照样能用（推荐、积分、评价）。关键是让弱依赖「真的弱」：超时短、能熔断、能降级或改成异步。

- 梳理：从链路追踪里列出每个核心接口的所有下游，再让业务方逐个确认「它挂了还能不能用」
- 最常见的问题是弱依赖写成了强依赖：同步调用、没设超时、异常直接往上抛
- 不需要马上拿结果的调用（发积分、发通知）改成发消息异步处理
- 用故障注入验证：给弱依赖制造延迟和报错，核心接口成功率不应下降

→ 详见 [冗余与故障转移](/high-avail/2_redundancy_failover)

## 三、负载均衡

### Q14：常见负载均衡算法有哪些？一致性哈希解决什么问题？

**一句话**：机器差不多、请求耗时差不多就用轮询；耗时差异大就看谁连接少、谁响应快；需要「同一个 key 总落到同一台」就用哈希。一致性哈希解决的是扩缩容时只有少量 key 需要搬家。

- 轮询 / 加权轮询：最常用，按权重分配，适合新实例逐步加流量
- 最少连接：适合长短请求混合，但新实例会被瞬间灌满，要配合预热
- P2C：随机挑两台、选负载低的那台，简单又有效
- 普通取模（`hash % N`）在机器数变化时几乎所有 key 都要重新分配；一致性哈希只影响相邻一小段，用虚拟节点让分布更均匀

→ 详见 [负载均衡](/high-avail/3_load_balancing)、[一致性哈希](/distributed/9_consistent_hashing)

### Q15：四层负载均衡和七层负载均衡的区别？

**一句话**：四层只看 IP 和端口转发连接，不看内容，速度极快，负责「扛连接」；七层会解析 HTTP，能按 URL、Header 路由，还能做 HTTPS 卸载、鉴权、限流，负责「懂业务」。

| 对比 | 四层（LVS 等） | 七层（Nginx、网关） |
|------|--------------|------------------|
| 看什么 | IP + 端口 | URL、Header 等 HTTP 内容 |
| 性能 | 极高 | 较低 |
| 健康检查 | 一般只到端口通不通 | 可探测 HTTP 接口和状态码 |

- 生产常见组合：四层做入口 VIP，后面挂多台七层网关

→ 详见 [接入层架构](/high-con/1_access_layer)、[负载均衡](/high-avail/3_load_balancing)

### Q16：服务端负载均衡与客户端负载均衡（Spring Cloud LoadBalancer）有什么区别？

**一句话**：服务端负载均衡是中间多一层代理（Nginx、SLB），调用方不用管；客户端负载均衡是调用方自己从注册中心拿到实例列表，在本地挑一台直接调，少一跳也没有代理单点，是微服务之间调用的主流做法。

| 对比 | 服务端（Nginx / SLB） | 客户端（Spring Cloud LoadBalancer） |
|------|---------------------|----------------------------------|
| 位置 | 独立代理层 | 调用方进程内 |
| 优点 | 对调用方透明、跨语言 | 少一跳、无单点 |
| 缺点 | 多一跳，代理也要高可用 | 每种语言要 SDK，实例变化感知有延迟 |

- Spring Cloud LoadBalancer 替代了已停维的 Ribbon，默认轮询，可自定义按版本 / 标签做灰度路由

→ 详见 [负载均衡](/high-avail/3_load_balancing)、[Spring Cloud 服务治理](/spring-cloud/5_service_governance)

### Q17：负载均衡如何配合健康检查摘除故障实例？会话保持有哪些做法？

**一句话**：健康检查分两种：主动的定时去探测，被动的看真实请求失败了几次就摘掉，两者一起用。会话保持是给「有状态服务」打的补丁，最好的办法是让服务无状态。

- Nginx 开源版只有被动检查：`max_fails=3 fail_timeout=10s`，失败转到下一台只对幂等请求开、限制次数
- 注册中心摘除有延迟（Eureka 可能要 2～3 分钟），调用方还要配合超时、重试其他实例和熔断
- 会话保持做法：IP 哈希（很多用户共用出口 IP 时会严重倾斜）、Cookie 粘滞（实例挂了会话还是丢）
- 推荐：Session 放到 Redis 或改用 Token，任何实例都能处理

→ 详见 [负载均衡](/high-avail/3_load_balancing)、[冗余与故障转移](/high-avail/2_redundancy_failover)

## 四、超时、重试与隔离

### Q18：超时设置的原则是什么？上下游超时应该如何配合？

**一句话**：每一次跨进程调用都必须设超时，一般取下游 P99 耗时再加 20%～50% 余量。上下游的规则是「越靠近用户越长、越靠近数据越短」，上游超时要能装下下游所有重试。

- 连接超时短（同机房 100ms～1s），连不上通常说明对方已经不可用
- 很多客户端默认值很危险：OpenFeign 默认读超时 60 秒，JDBC 的 `socketTimeout` 默认不限
- 上游超时 ≥ 下游单次超时 ×（重试次数 + 1）+ 退避时间 + 自身耗时；算不过来就减少重试，而不是加大上游超时
- 同时用了 Resilience4j 时，它的 TimeLimiter 默认只有 1 秒，要和 Feign 超时一起显式配置

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

### Q19：重试适用于哪些场景？非幂等接口能直接加重试吗？

**一句话**：重试只用来对付短暂故障（网络抖一下、实例切换），而且只对幂等操作（执行多次结果一样）开启。非幂等接口不能直接重试：超时时对方可能已经执行成功了，再来一次就是重复扣款、重复下单。

- 连接失败：可以重试，请求还没到对方，换一台最安全
- 读超时：只有幂等操作才重试
- 429 / 503（对方说太忙）：谨慎重试，按 `Retry-After` 等一会儿
- 参数错误、业务异常、熔断已打开：不重试
- 非幂等接口要先做幂等（幂等键、唯一约束、状态机），再谈重试

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)、[幂等设计](/architecture/5_idempotence)

### Q20：指数退避是什么？为什么要加 Jitter？

**一句话**：指数退避是每次重试前等待的时间翻倍（100ms、200ms、400ms…），给下游喘息的时间；Jitter 是在等待时间上加随机抖动，让大量客户端别在同一时刻一起重试，形成一波波尖峰。

- 没有 Jitter 时：一次故障让上万个客户端同时失败，它们会在同一时刻同时重试，把刚恢复的服务再打挂
- 要设上限，比如最长等 2 秒
- 在线请求的重试等待控制在百毫秒级，总时间要在上游超时以内；秒级、分钟级退避只适合异步任务和消息重投
- Resilience4j 里一行配置：`IntervalFunction.ofExponentialRandomBackoff(...)`

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

### Q21：什么是重试放大？如何用"只在一层重试"、重试预算、deadline 传播来控制？

**一句话**：每层都重试 3 次时，放大是相乘的：3 层调用最底层会收到 3 × 3 × 3 = 27 倍请求，下游本来只是有点忙，直接被重试流量打垮。

- 只在一层重试：放在直接调用不稳定依赖的那一层，其他层失败就直接往上返回
- 单个请求最多尝试 2～3 次
- 重试预算：重试量不超过正常请求的一定比例（如 10%），超了就直接失败
- deadline 传播：上游把「还剩多少时间」传给下游，时间不够就不再调用或重试；传相对时长，避免机器时钟不一致

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

### Q22：线程池隔离和信号量隔离的区别？各自适用什么场景？

**一句话**：线程池隔离是给每个依赖单独一个线程池，慢调用只占自己池子的线程，调用方还能超时放弃；信号量隔离只是限制同时调用的数量，还在当前线程执行，几乎没开销但慢调用会占住调用方线程。

| 对比 | 线程池隔离 | 信号量隔离 |
|------|----------|----------|
| 隔离程度 | 强 | 中 |
| 开销 | 有线程切换，ThreadLocal 要额外传递 | 几乎没有 |
| 超时 | 调用方可直接放弃等待 | 靠下游客户端自己的超时 |
| 适合 | 慢且不稳定的外部调用 | 快速、调用量大的内部依赖 |

- 配额估算：并发 ≈ QPS × P99 延迟，如 200 QPS、50ms 约需 10，配额取 15～20

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)

## 五、熔断

### Q23：熔断器的三种状态是什么？如何切换？半开状态放行多少请求？

**一句话**：关闭（正常放行并统计）→ 失败太多就打开（直接拒绝、走降级）→ 过一段时间进入半开（放少量请求试探）→ 试探成功就关闭，失败就重新打开。

- Closed：正常放行，统计失败率和慢调用比例
- Open：不调用下游，直接返回降级结果，等熔断时长到期
- Half-Open：放少量请求去试探下游是否恢复
- 半开放行数：Sentinel 只放 1 个；Resilience4j 默认放 10 个，按这批的失败率决定

→ 详见 [熔断](/high-avail/5_circuit_breaking)

### Q24：熔断有哪几种策略？慢调用阈值、最小请求数、熔断时长怎么定？

**一句话**：三种：慢调用比例、异常比例、异常数。最常用的是慢调用比例，因为服务往往先变慢、后报错，而变慢更占资源。

- 慢调用阈值：下游正常 P99 的 1.5～2 倍，且小于调用方超时
- 比例阈值：50%～60%，太低容易误熔断
- 最小请求数：按低峰流量设，避免「2 个请求错 1 个就熔断」
- 熔断时长：5～30 秒，跟下游一般恢复时间差不多
- 异常数策略适合调用量很小的接口；熔断粒度最好按接口，而不是整个服务

**常见坑**：直接用 Resilience4j 默认值（慢调用阈值 60 秒、熔断 60 秒，太宽松），每个实例都应显式配置。

→ 详见 [熔断](/high-avail/5_circuit_breaking)

### Q25：哪些异常应该计入熔断统计，哪些不应该？

**一句话**：只统计能说明「下游不健康」的失败；业务异常和下游健康无关，算进去就会误熔断。

- 计入：超时、连接失败、5xx、下游返回的「系统繁忙」
- 不计入：参数校验失败、余额不足这类业务拒绝（Resilience4j 用 `ignore-exceptions` 排除）
- 被熔断拒绝本身（`CallNotPermittedException` 等）不能再去重试，否则熔断等于白开

→ 详见 [熔断](/high-avail/5_circuit_breaking)

### Q26：Sentinel、Hystrix、Resilience4j 的区别？新项目怎么选？

**一句话**：新项目在 Sentinel 和 Resilience4j 里选：用 Spring Cloud Alibaba、要控制台动态改规则选 Sentinel；想轻量、走 Spring Cloud 标准接口选 Resilience4j。Hystrix 2018 年起就不再开发，新项目不用。

| 对比 | Sentinel | Resilience4j | Hystrix |
|------|---------|-------------|---------|
| 熔断策略 | 慢调用、异常比例、异常数 | 失败率、慢调用率 | 失败率 |
| 额外能力 | 限流、热点参数、系统保护 | 限流、重试、超时 | 请求合并 |
| 改规则 | 控制台 / 配置中心动态推送 | 配置文件、代码 | 配置文件 |
| 状态 | 活跃 | 活跃 | 维护模式，已从 Spring Cloud 移除 |

→ 详见 [熔断](/high-avail/5_circuit_breaking)

### Q27：`@SentinelResource` 的 `blockHandler` 和 `fallback` 有什么区别？

**一句话**：`blockHandler` 只处理被 Sentinel 规则拦下的情况（限流、熔断、系统保护抛出的 `BlockException`）；`fallback` 处理业务代码自己抛的异常。两个都配时，被限流熔断走 `blockHandler`。

- `blockHandler` 方法参数 = 原方法参数 + 最后一个 `BlockException`，必须 `public`；写在别的类里要用 `blockHandlerClass` 并声明为 `static`
- `fallback` 方法参数和原方法一样，可以多加一个 `Throwable`
- 非幂等写操作的兜底不要假装成功，要明确报错

→ 详见 [Spring Cloud Alibaba - Sentinel](/spring-cloud/6_alibaba)、[熔断](/high-avail/5_circuit_breaking)

## 六、降级

### Q28：降级和熔断有什么区别和联系？

**一句话**：熔断决定「还要不要调下游」，是自动触发的保护；降级决定「不调之后返回什么、放弃什么」，是提前设计好的方案。熔断打开后通常会执行降级，但降级不一定是熔断引起的。

| 对比 | 熔断 | 降级 |
|------|------|------|
| 性质 | 自动触发的保护 | 预先设计的方案 |
| 触发 | 失败率 / 慢调用超阈值 | 熔断、限流、超时、异常，或人工开关 |
| 关心 | 要不要调下游 | 返回什么、放弃什么 |

→ 详见 [降级](/high-avail/6_degradation)

### Q29：服务降级有哪些级别和手段？如何给功能分级？

**一句话**：先按重要性把功能分成核心、重要、一般、边缘四级，出问题时从最不重要的开始放弃；核心链路（下单、支付、登录）不降级，只能靠扩容和限流保护。

- 重要功能（库存展示、优惠计算）：返回缓存或近似值
- 一般功能（推荐、评论）：返回兜底数据，比如个性化推荐换成热销榜，或直接隐藏
- 边缘功能（埋点、报表）：直接关掉或改成异步
- 其他手段：同步写改成发 MQ 稍后补偿、实时数据改成分钟级更新、活动页切成 CDN 静态页

→ 详见 [降级](/high-avail/6_degradation)

### Q30：静态降级和动态降级（开关）分别怎么实现？

**一句话**：静态降级写在代码里，出异常自动走兜底；动态降级用配置中心的开关控制，不用重启就能生效。前者兜意外故障，后者用于预案和人工干预。

- 静态：`@SentinelResource(fallback = ...)` 或 Resilience4j 的 `fallbackMethod`，返回本地缓存的兜底数据，并上报降级指标
- 动态：开关放在 Nacos 等配置中心，代码里判断开关关了就直接走兜底，不再调用下游
- 每个手动开关写清楚：什么时候开、影响什么、谁负责、什么时候关

→ 详见 [降级](/high-avail/6_degradation)

### Q31：Sentinel 规则持久化到 Nacos 后，控制台修改的规则为什么重启会丢失？

**一句话**：因为数据是单向流动的：应用只会从 Nacos 读规则，而控制台改的规则只推到应用内存，不会写回 Nacos。应用一重启，重新从 Nacos 加载，控制台改的就没了。

- 解决一：改造 Sentinel 控制台，让它修改规则时写入 Nacos，应用再从 Nacos 监听生效
- 解决二：约定只在 Nacos 里改规则，控制台只用来看

→ 详见 [降级](/high-avail/6_degradation)、[Spring Cloud Alibaba - Sentinel](/spring-cloud/6_alibaba)

### Q32：降级逻辑设计时要注意什么？为什么非幂等写操作不能静默降级？

**一句话**：降级代码平时不跑，最容易在真正需要时失效，所以要有业务价值、不依赖故障源、能监控、定期演练。非幂等写操作如果偷偷返回「成功」，用户以为下单扣款成功了其实没有，数据就不一致了。

- 兜底数据要有用：别返回 `null` 让前端报错
- 不依赖故障源：推荐服务挂了，兜底就不能再去调推荐服务
- 能监控：每次降级打日志、上报指标，降级量突增要告警
- 写操作降级要么明确报错，要么改成「已受理、稍后处理」

→ 详见 [降级](/high-avail/6_degradation)

## 七、限流与过载保护

### Q33：常见限流算法有哪些？令牌桶和漏桶的区别？

**一句话**：常见四种：固定窗口、滑动窗口、令牌桶、漏桶。令牌桶允许突发（空闲时攒下的令牌可以一下用掉），适合入口限流；漏桶不管进来多快都匀速放出，适合保护处理能力固定的下游。

| 算法 | 能否突发 | 典型场景 |
|------|---------|---------|
| 固定窗口 | 窗口交界处可达 2 倍 | 每天调用次数这种粗配额 |
| 滑动窗口 | 平滑 | 服务端 QPS 限流（Sentinel） |
| 令牌桶 | 可以，最多桶容量 | 网关、按用户 / API 限流 |
| 漏桶 | 不可以 | 第三方接口配额、匀速写入 |

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q34：固定窗口限流有什么问题？滑动窗口如何解决？

**一句话**：固定窗口在两个窗口交界处会放过 2 倍流量：上一秒最后 100ms 放 100 个、下一秒最前 100ms 再放 100 个，200ms 内过了 200 个。滑动窗口把一秒切成几个小格子，始终统计「最近一秒」的总数。

- 小格子越多越平滑，但占的内存也越多
- Sentinel 的秒级统计就是滑动窗口，默认 1 秒切成 2 个 500ms
- 分布式场景可以用 Redis ZSET 记录每次请求时间，做精确的滑动窗口（见 Q35）

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q35：如何用 Redis + Lua 实现滑动窗口限流？member 和时间戳要注意什么？

**一句话**：用 ZSET 存每次请求，score 是时间戳；Lua 脚本一次性原子完成「删掉窗口外的记录 → 数一下还剩几条 → 没超就写入」。两个细节：member 必须唯一，时间要取 Redis 服务器的时间。

- member 只用时间戳的话，同一毫秒的多个请求会互相覆盖，少算次数，要拼上请求 ID
- 时间用 Redis 的 `TIME` 命令取，避免各应用机器时钟不一致
- 每个请求占一个元素，阈值大时内存吃不消，那时改用令牌桶或分格计数
- Redis 挂了要有预案：一般放行并靠单机限流兜底，强管控场景就拒绝

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q36：限流应该放在哪一层？网关限流能替代服务内限流吗？

**一句话**：多层叠加：越外层越粗、越省资源，越内层越精确、越贴近真实容量。网关限流不能替代服务内限流，网关只管集群总量，挡不住负载不均或个别实例变慢时的单机过载。

- 接入层（CDN、WAF、Nginx）：按 IP 挡恶意刷量
- 网关：按用户、租户、API 分配配额，常用 Redis 令牌桶
- 服务内：按单机容量自我保护（Sentinel、Resilience4j），不依赖外部组件
- 方法级：热点参数单独限速，保护下游配额
- 按 IP 限流时，经过 CDN / SLB 后要从可信的 `X-Forwarded-For` 取真实 IP

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q37：限流阈值如何确定？被限流时应该返回什么？

**一句话**：阈值来自压测：单机阈值约等于压测拐点的 70%～80%，先宽松上线再按数据收紧。被限流时，超出调用方配额返回 429，服务整体过载返回 503，都带上 `Retry-After` 告诉对方多久后再来。

- 集群阈值 ≈ 单机阈值 × 实例数，再按负载不均打个折
- 客户端收到 429 / 503 不能马上重试，要等一等或指数退避
- gRPC 对应 `RESOURCE_EXHAUSTED` / `UNAVAILABLE`

**常见坑**：Gateway 的 `KeyResolver` 把取不到的 key 兜底成固定值，导致所有匿名请求共用一个桶（应开启 `deny-empty-key` 直接拒绝）。

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q38：为什么并发数限流比 QPS 限流更能应对下游变慢？和 Little 定律有什么关系？

**一句话**：Little 定律：并发数 = QPS × 平均耗时。只限 QPS 时，下游一变慢，在途请求就成倍堆积；限并发数时，下游变慢吞吐会自动降下来，线程池始终安全。

- 正常：1000 QPS × 50ms = 50 个并发
- 下游变慢到 500ms，只限 QPS：1000 × 0.5s = 500 个并发，线程池被打满
- 限并发 50：吞吐自动降到 100 QPS，线程池依然安全
- 实现：Sentinel 线程数限流、Resilience4j `Bulkhead`，或者一个 `Semaphore`

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q39：什么是过载保护？Sentinel 系统自适应保护和 BBR 思想是什么？

**一句话**：固定阈值只在容量不变时有效，但下游变慢、Full GC 都会让真实容量临时下降。过载保护根据系统实时状态决定放不放行。BBR 思想来自 TCP 拥塞控制：系统能承受的在途请求 ≈ 最大吞吐 × 最小耗时，超过就拒绝。

- Sentinel 系统规则：按整机的 CPU、load、入口平均耗时、入口并发、入口 QPS 保护入口流量
- load 超阈值时不直接拒绝，而是再用 BBR 判断：当前并发超过「最大成功 QPS × 最小耗时」才拒绝，避免误杀
- 容器里 load 反映的是宿主机，优先用 CPU、耗时、并发数指标

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

### Q40：负载卸除时如何按优先级丢弃请求？客户端自适应节流是怎么工作的？

**一句话**：非丢不可时先丢不重要的：给请求分级，越忙只放越重要的请求进来。客户端自适应节流是调用方根据后端最近的接受率，在本地按比例提前拒绝，后端连「拒绝」的开销都省了。

- 按优先级卸载：比如负载到 60% 开始丢低优先级（推荐、埋点），80% 丢普通请求，满了才拒绝核心请求（下单、支付）
- 优先级由网关按路由写入，不信任客户端自己带的值；已经超过调用方 deadline 的请求直接丢
- 客户端节流（Google SRE 做法）：统计最近的请求数和被接受数，被拒绝越多，本地主动拒绝的概率越高；后端正常时概率为 0
- 和熔断的区别：熔断是开 / 关两种状态，自适应节流按比例连续调节，更平滑

→ 详见 [限流与过载保护](/high-avail/7_rate_limiting)

## 八、优雅上下线与变更

### Q41：什么是优雅停机？如何在 Spring Boot 中实现？

**一句话**：优雅停机是先摘流量，再把手上的请求和任务处理完，最后释放资源退出，整个过程不产生失败请求。最常见的错误是顺序反了：先停 Web 容器再注销，调用方还在往这台发请求。

- 正确顺序：注册中心注销 → 等调用方刷新几秒 → 停止接新请求并处理完在途请求 → 停 MQ 消费和定时任务 → 关连接池退出
- Spring Boot 配 `server.shutdown=graceful`（3.4 起默认开启），`spring.lifecycle.timeout-per-shutdown-phase` 控制最长等待
- 自定义线程池要设置停机时等待任务完成；MQ 消费者处理完已拉取的消息并提交位点
- 禁止 `kill -9`，它不会触发 JVM 的关闭钩子

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)

### Q42：K8s 中如何配合实现优雅停机？`preStop` 的作用是什么？为什么需要 sleep？

**一句话**：删除 Pod 时，「从 Service 摘流量」和「给容器发停止信号 SIGTERM」是同时进行的，而各处感知摘流量需要时间。`preStop` 在 SIGTERM 之前执行，sleep 一会儿让流量先摘干净，应用再开始停机。

```yaml
preStop: { exec: { command: ["sh", "-c", "sleep 15"] } }
```

- `preStop` 等待一般 10～20 秒，覆盖 K8s、注册中心和客户端缓存的刷新时间；微服务里先在 `preStop` 主动从注册中心注销
- `terminationGracePeriodSeconds`（总宽限期，超时直接强杀）要 ≥ preStop 等待 + 应用停机时间 + 余量

**常见坑**：Dockerfile 用 shell 形式启动，JVM 收不到 SIGTERM（应该用 exec 形式 `ENTRYPOINT ["java", "-jar", "app.jar"]`）。

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)

### Q43：PodDisruptionBudget 的作用是什么？它能约束滚动更新吗？

**一句话**：PDB 限制「主动维护」时一次能赶走多少个 Pod，比如节点排空（`kubectl drain`）、集群缩容、节点升级。它管不了滚动更新，滚动时的可用数量由 Deployment 的 `maxUnavailable` / `maxSurge` 控制。

- PDB 只对走驱逐接口的操作生效；直接 `kubectl delete pod`、节点宕机它都拦不住
- 滚动更新不减少可用实例：`maxUnavailable: 0` + `maxSurge: 1`
- 不要把 PDB 设成和副本数一样（或单副本配 `minAvailable: 1`），否则 `drain` 会一直卡住；副本数会变时用 `maxUnavailable: 1`

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)

### Q44：为什么新实例启动后需要预热？有哪些预热手段？

**一句话**：新实例刚启动时代码还没被 JIT 编译成机器码、缓存是空的、连接池没建好，响应明显偏慢，直接接满流量可能被打垮，甚至触发熔断连锁故障。做法是「预热完再就绪 + 权重慢慢放大」。

- 启动时主动调一遍核心接口、加载热点数据、提前建好连接
- Spring Boot 等所有 `ApplicationRunner` 跑完才标记可接流量，预热逻辑放在 Runner 里，readiness 自然会等
- 注意注册中心往往在 Web 容器启动时就注册了，比预热完成更早，可以关掉自动注册、预热后再注册
- 权重预热：Dubbo 内置（默认 10 分钟线性增长），其他框架需发布平台或自定义负载均衡逐步调权重

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)、[JVM 层性能策略](/high-perf/5_jvm_tuning)

### Q45：变更三板斧是什么？配置变更如何灰度？

**一句话**：三板斧是可灰度、可监控、可回滚，做不到任何一条的变更都不该在高峰期上线。配置变更通常几秒内推到所有机器，没有滚动过程，比发代码更危险，要先推少量机器观察。

- 可灰度：单机 → 单机房 → 1% → 10% → 全量，每批之间留观察时间
- 可监控：对比新旧版本的成功率和耗时
- 可回滚：镜像有版本、`kubectl rollout undo`、功能开关、配置保留历史版本
- 配置灰度：Nacos Beta 发布到指定 IP；发布前校验格式，代码对非法值回落默认值
- 表结构变更「先加后删」：先兼容新旧两版，确认稳定再删旧字段，保证随时能回滚代码

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release)

## 九、多活与容灾

### Q46：RPO 和 RTO 分别是什么？

**一句话**：RPO 是故障后最多丢多长时间的数据，由数据怎么复制决定；RTO 是故障后多久能恢复服务，由备用环境准备程度和切换自动化程度决定。

- 只有异地定期备份：RPO 小时～天，RTO 天级
- 冷 / 温备，数据异步复制：RPO 秒～分钟，RTO 小时级
- 热备，实时同步：RPO 秒级，RTO 分钟级
- 多活：单元内 RPO 接近 0，切流秒～分钟级恢复

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q47：同城双活和异地多活的区别？各自解决什么问题？

**一句话**：同城双活机房之间延迟只有 1～2ms，可以跨机房同步调用和同步复制，通常是「应用双活、数据主备」，防单个机房故障；异地多活延迟 25～30ms，只能异步复制，必须做单元化让请求在本地闭环，防整个城市出问题。

| 对比 | 同城双活 | 异地多活 |
|------|---------|---------|
| 延迟 | 1～2ms | 25～30ms（如北京—上海） |
| 数据 | 通常单主，另一边做从库 | 按用户等分片，各写各的，异步同步 |
| 改造成本 | 中 | 高（业务、数据、中间件都要改） |
| 防什么 | 单机房故障 | 城市 / 地域级故障 |

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q48：两地三中心是什么架构？异地灾备中心为什么"不敢切"？

**一句话**：两地三中心 = 同城两个中心 + 异地一个灾备中心。同城两个做双活或主备，异地中心异步接收数据，平时一般不接流量。「不敢切」是因为它长期不干活，配置不一致、容量不够、依赖缺失这些问题都要到切换那一刻才暴露。

- 同城两中心之间同步或半同步复制，异地中心可能落后秒到分钟
- 异地多活就是为解决这个问题：让每个中心平时都接流量，能力一直被验证
- 没有常态化演练的灾备，只是一个昂贵的冷备

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q49：什么是单元化？如何选择路由键？全局数据如何处理？

**一句话**：单元是一套能独立完成全部业务的部署（接入、应用、缓存、消息和自己那份数据）。选一个贯穿业务的路由键（比如用户 ID），请求和数据都按它分到单元，读写不出单元；拆不开的全局数据在中心单元写、各单元读副本。

- 路由键：电商用买家 userId，外卖出行用城市，SaaS 用租户 ID
- 路由分两级：`userId → 分片号 → 单元`，切流只改「分片属于哪个单元」这张映射表
- 全局数据（库存、商品）中心单元写，各单元读只读副本，能容忍秒级延迟
- 强一致场景（如扣库存）走中心单元，或给各单元预分配额度

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q50：双向数据同步如何避免复制回环和写冲突？

**一句话**：复制回环（A 同步给 B、B 又同步回 A）靠给同步写入打来源标记，同步组件看到就过滤掉；写冲突靠单元化从源头避免（同一条数据只在一个单元写），兜底按版本号或更新时间「后写的赢」并告警。

- 主键冲突：用分布式 ID，或者让两边自增步长错开
- 复制延迟：持续监控，切流前必须追平
- 表结构变更：走统一平台，先兼容再切换
- 常用工具：Canal（订阅 binlog）、云厂商 DTS 双向同步、Kafka MirrorMaker 2

→ 详见 [多活与容灾](/high-avail/9_multi_active)

### Q51：计划内切流为什么要先禁写？

**一句话**：跨单元是异步复制，源单元总有一部分数据还没同步过去。先禁写，避免切换过程中两边同时写，等同步延迟归零再切，才能做到一条数据都不丢；禁写一般持续几秒到几分钟。

- 步骤：确认目标有容量 → 源单元禁写 → 等同步追平 → 改路由表推到网关 → 目标单元开写 → 验证指标
- 真实故障时源单元已经挂了，追不平，只能接受少量差异，事后对账修复
- 演练要常态化，从小比例分片开始，出异常立刻切回

→ 详见 [多活与容灾](/high-avail/9_multi_active)

## 十、混沌工程

### Q52：混沌工程是什么？和传统测试有什么区别？有哪些工具？

**一句话**：混沌工程是在可控范围内主动制造真实会发生的故障（宕机、延迟、丢包），看系统能不能扛住，提前发现弱点，证明冗余、熔断、降级这些预案真的有效。传统测试验证「功能对不对」，混沌工程寻找「没想到的弱点」。

| 对比 | 传统测试 | 混沌工程 |
|------|---------|---------|
| 目标 | 验证功能符合预期 | 发现未知弱点 |
| 输入 | 构造的输入数据 | 宕机、延迟、资源耗尽等故障 |
| 环境 | 测试环境 | 从预发逐步到生产 |
| 判定 | 用例过没过 | 核心指标有没有偏离 |

- 工具：ChaosBlade（阿里，可到 JVM 方法级）、Chaos Mesh（K8s 原生）、Chaos Monkey（Netflix，随机杀实例）

→ 详见 [混沌工程](/high-avail/10_chaos_engineering)

### Q53：混沌实验的流程是什么？如何控制爆炸半径？

**一句话**：流程是：先定好「正常是什么样」（稳态指标）→ 设计实验 → 注入故障 → 观察指标 → 修复后再跑一遍验证。控制影响范围（爆炸半径）的核心是：从小开始、有停止条件、能自动恢复。

- 稳态假设举例：下游延迟加 300ms 时，下单成功率仍 > 99.9%
- 从单实例、小比例流量开始；先测试环境、再预发、再生产低峰期
- 实验设置自动恢复时间，准备一键回滚；指标越过停止线（如成功率 < 99.5%）立刻停
- 实验前通知相关团队和值班，免得被当成真故障

→ 详见 [混沌工程](/high-avail/10_chaos_engineering)

### Q54：如何用故障注入验证熔断、降级是否生效？

**一句话**：给依赖制造「变慢」和「不可用」两种故障，在正常压力下看熔断有没有按阈值打开、降级有没有返回有用的兜底、核心成功率有没有保住，故障撤销后再看熔断能不能自己恢复。

- 例：用 ChaosBlade 让库存服务的 `checkStock` 方法延迟 800ms（超过 500ms 慢调用阈值），观察下单接口是否在 10 秒内熔断并走降级
- 验证降级：让依赖 100% 丢包或抛异常，确认兜底数据有用、不依赖故障源
- 同样思路验证其他预案：杀 Pod 验证故障摘除，滚动发布时杀 Pod 验证优雅停机

→ 详见 [混沌工程](/high-avail/10_chaos_engineering)

## 十一、故障应急与复盘

### Q55：故障如何分级？P0 和 P1 的判定标准与响应要求有什么不同？

**一句话**：分级决定叫谁起来、多快响应、要不要对外通告，标准必须提前量化，不能到现场再讨论。P0 是核心业务全面不可用或丢数据、资损；P1 是核心业务部分不可用或重要功能完全不可用。

| 级别 | 判定 | 响应 |
|------|------|------|
| P0 | 下单 / 支付 / 登录全挂；数据丢失泄露；资损扩大 | 5 分钟内，负责人到场，通报管理层 |
| P1 | 核心业务部分不可用（如 > 5% 用户受影响） | 15 分钟内，值班 + 服务负责人 |
| P2 | 非核心功能不可用 | 30 分钟内 |
| P3 | 影响很小或有绕过办法 | 1 个工作日内 |

- 定级宁高勿低，影响扩大随时升级

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)

### Q56：线上出现故障时的处理流程是什么？为什么要先止血后定位？

**一句话**：流程是发现 → 响应 → 止血 → 恢复 → 复盘。先止血是因为可用性取决于恢复速度，而找根因要多久说不准；大部分故障由发布、配置变更或流量变化引起，回滚、切流、降级几分钟就能恢复。

- 止血的第一个问题永远是「最近有没有变更」，有就先回滚
- 止血前花一分钟保留现场（`jstack`、GC 日志、异常实例先摘流量不销毁），但不能耽误止血
- 分工明确：一个人统筹指挥，有人排查执行，有人对外同步，有人记时间线
- 恢复要看核心指标真的回到正常，复盘在 1～3 个工作日内完成

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)

### Q57：常见的止血手段有哪些？分别适用于什么场景？

**一句话**：按「影响小、见效快」的顺序选，而且这些手段要平时准备好、演练过，故障时只做选择和执行。

- 回滚：故障时间和最近的发布 / 配置变更吻合，最常用也最有效
- 切流：单实例、单机房故障，先确认目标有足够容量
- 摘除 / 重启：个别实例假死、内存泄漏，先摘流量保留现场再重启
- 降级、限流：非核心依赖故障或流量突增，优先限低优先级流量
- 扩容：资源不足时用；但瓶颈在数据库时，扩应用反而加重故障

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)

### Q58：如何降低 MTTD 和 MTTR？

**一句话**：发现得快（MTTD）靠告警质量：盯用户能感受到的症状，少而准；恢复得快（MTTR）靠变更关联、预案手册、统一的排查入口和演练。

- 告警对准成功率和延迟，用燃烧速率告警；每条告警都要能采取行动，否则删掉
- 变更关联：发布、配置、数据变更统一记录，告警时自动列出前后的变更
- 预案手册（Runbook）：写清触发条件、止血步骤、验证方法、找谁升级，告警里直接带链接
- 指标、日志、链路通过 TraceId 串起来；定期做故障演练
- 值班要有升级路径：如 5 分钟没人确认就通知备岗

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)

### Q59：什么是无责复盘？复盘报告应包含哪些内容？

**一句话**：无责复盘的目的是改进系统而不是追究个人：一次误操作就能造成故障，说明系统缺防护；追责只会让人隐瞒信息，下次更难找到真因。

- 报告内容：概要（级别、时长、影响范围）、按分钟的时间线、MTTD / MTTR、根因分析、做得好的地方、改进项
- 根因用「5 个为什么」逐层追问，找到系统层面的原因
- 例：根因不是「某人把超时从 3s 改成 300ms」，而是「超时配置没有集中管理、灰度时没有自动对比」
- 改进项要有负责人、截止日期和验收标准；同类故障再发生，先查上次改进项落实没有

→ 详见 [故障应急与复盘](/high-avail/11_incident_response)
