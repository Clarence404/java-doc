# 应用安全面试题解答

> 题目清单见 [应用安全高频面试题](/security/99_interview)；细节见 [应用安全总览](/security/0_overview)。
>
> 版本基线：Spring Boot 4 / Spring Security 7、RFC 9700（OAuth 2.0 安全最佳实践）+ PKCE、RFC 8725（JWT 最佳实践）、OIDC Core 1.0、OWASP Top 10:2025 / API Security Top 10 2023、NIST SP 800-207。

## 一、认证与令牌

### Q1：JWT 由哪几部分组成？有什么优缺点？

**一句话**：JWT 是 `Header.Payload.Signature` 三段 Base64URL 拼起来的令牌，签名保证不被改，但内容谁都能解开看；好处是服务拿到就能本地验，坏处是发出去就收不回来。

- Header：写算法 `alg`、密钥编号 `kid`、类型 `typ`
- Payload：放声明（claims），常用 `iss` 签发方、`sub` 用户 ID、`aud` 给谁用、`exp` 过期时间、`jti` 令牌唯一 ID
- Signature：对前两段签名，防篡改，不加密
- 优点：自包含，资源服务不用查库，适合多服务、多实例
- 缺点：到 `exp` 之前天然有效，吊销要额外设计；每个请求都带着，不宜太大

**常见坑**：把手机号、身份证号塞进 Payload；Base64URL 只是编码，不是加密。

→ 详见 [JWT 令牌机制](/security/1_jwt#二、结构)

### Q2：JWT 签发出去了，怎么让它提前失效？

**一句话**：JWT 本身收不回来，只能「短有效期兜底 + 按需加查询」：Access Token 只给几分钟，真要立刻失效就加黑名单或版本号。

| 策略 | 做法 | 生效速度 |
|------|------|----------|
| 短有效期 | AT 只给 5～15 分钟 | 最迟一个 AT 周期 |
| 吊销 RT 家族 | 退出、改密时删掉该用户的 Refresh Token | 下次刷新时 |
| `jti` 黑名单 | 写进 Redis，TTL = 剩余有效期 | 立即，每个请求多查一次 |
| 令牌版本号 | 用户表存 `token_version`，改密时加 1 | 立即，比对版本 |

- 推荐组合：短 AT + RT 轮换打底，退出时吊销 RT 家族并拉黑当前 `jti`，改密 / 禁用时递增版本号

→ 详见 [JWT 令牌机制](/security/1_jwt#七、吊销策略)

### Q3：为什么要 Access Token + Refresh Token 双令牌？Refresh Token 轮换怎么做？

**一句话**：AT 短命、每个请求都带，泄露了损失有限；RT 长命、只发给令牌端点，用来换新 AT。RT 每用一次就换新的，旧的再出现就说明被偷了。

- AT：JWT，5～15 分钟，资源服务本地验签
- RT：不透明随机串，服务端只存哈希，数天到数周，有空闲超时和绝对超时
- 轮换：每次刷新都发新 RT、旧 RT 标为已用；同一次登录的 RT 属于一个「家族」
- 重用检测：已用过的 RT 又来了，分不清谁是真用户，直接吊销整个家族、要求重新登录并告警
- 并发刷新：多标签页可能同时交同一个 RT，可给刚轮换的 RT 留几秒宽限期

**常见坑**：家族不设绝对过期时间，靠无限轮换永久续命。

→ 详见 [JWT 令牌机制](/security/1_jwt#_1、轮换与重用检测)

### Q4：HS256 和 RS256 怎么选？kid 和 JWKS 是干什么的？

**一句话**：HS256 是对称签名，谁能验签谁就能伪造，只适合单体自签自验；多服务用 RS256 / ES256，私钥只在签发方，其他服务通过 JWKS 拿公钥，按 `kid` 选钥。

- HS256：共享一个 secret（至少 32 字节），最快，但第二个服务一要验签就该换掉
- RS256 / ES256：非对称，私钥签、公钥验；新系统优先 ES256，兼容老系统用 RS256
- JWKS：签发方公开的公钥集合（`/.well-known/jwks.json`），每把公钥带 `kid`
- 密钥轮换四步：发布新公钥 → 等资源服务缓存刷新后切换签发私钥 → 等旧令牌过期 → 下线旧公钥
- 验签方式由服务端决定：算法白名单、只信配置的 JWKS，`alg=none` 和算法混淆就打不进来

→ 详见 [JWT 令牌机制](/security/1_jwt#八、密钥轮换-kid-与-jwks)

### Q5：浏览器里的 Token 应该存在哪里？

**一句话**：不要放 `localStorage`，一个 XSS 就被读走；浏览器应用推荐 BFF：令牌留在服务端，浏览器只拿一个 HttpOnly 的会话 Cookie。

| 方案 | 问题 | 结论 |
|------|------|------|
| `localStorage` | 脚本能直接读 | 不推荐 |
| HttpOnly Cookie 装 JWT | 自动携带，重新引入 CSRF | 可用，必须防 CSRF |
| BFF + 会话 Cookie | 令牌不进浏览器 | 推荐 |
| Authorization 头 | 非浏览器场景 | App、服务间的标准做法 |

- BFF（Backend for Frontend，给前端配的后端）代替前端走授权码 + PKCE，转发请求时再附上 Bearer 令牌
- 会话 Cookie：`HttpOnly`、`Secure`、`__Host-` 前缀、`SameSite=Lax`，并且照样开 CSRF Token

→ 详见 [JWT 令牌机制](/security/1_jwt#九、token-存在哪里)

## 二、OAuth2 / OIDC / SSO

### Q6：OAuth2 和 OIDC 有什么区别？

**一句话**：OAuth2 管「授权」（这个应用能访问什么），OIDC 在它上面加了一层「认证」（你是谁），多出来的核心就是 ID Token。

- OAuth2 产物：access token，用来调 API；本身没有标准的「用户是谁」
- OIDC：授权请求的 scope 带 `openid`，令牌端点额外返回 ID Token（JWT）
- 用户唯一标识：ID Token 里的 `iss` + `sub`，不是邮箱
- 配套标准：UserInfo 端点、Discovery（自动发现端点和 JWKS）、登出规范
- 典型场景：OAuth2 是第三方应用访问用户资源；OIDC 是企业 SSO、「用 XX 账号登录」

→ 详见 [OIDC](/security/3_oidc#一、oidc-在-oauth-2-上加了什么)

### Q7：授权码模式为什么要加 PKCE？

**一句话**：授权码要经过浏览器回跳，可能被截获；PKCE 让客户端先交一个哈希、换令牌时再交原文，截到 code 的人没有原文就换不出令牌。

- 流程：前端通道只传一次性、短时效的 code；后端通道用 code 直连令牌端点换令牌
- `code_verifier`：每次授权前随机生成的高熵串
- `code_challenge`：`BASE64URL(SHA256(code_verifier))`，随授权请求发出
- 换令牌时带 `code_verifier`，服务端重算比对，不一致就拒绝；方法必须用 `S256`
- 机密客户端也要用：它还能防「授权码注入」（攻击者把自己的 code 塞进受害者回调），client_secret 挡不住

→ 详见 [OAuth2](/security/2_oauth2#五、授权码-pkce)

### Q8：为什么隐式模式和密码模式被淘汰了？

**一句话**：隐式模式把令牌直接放在 URL 里，容易泄露；密码模式让客户端直接拿用户密码，违背 OAuth 的初衷，所以 OAuth 2.1 把两者都删了。

- 隐式模式：令牌在 URL 片段里，会进浏览器历史、Referer，也没法绑定客户端
- 密码模式（ROPC）：客户端接触明文密码，没法做 MFA（多因素认证）
- 替代：SPA 和自家 App 都改用授权码 + PKCE，浏览器应用最好再配 BFF
- 保留的模式：授权码 + PKCE、客户端凭证（服务间）、设备码（电视 / CLI）、刷新令牌
- Spring Security 7 的 OAuth2 客户端已经移除了密码模式支持

→ 详见 [OAuth2](/security/2_oauth2#四、授权模式总览)

### Q9：ID Token 和 Access Token 有什么区别？能不能拿 ID Token 调 API？

**一句话**：ID Token 是给客户端看的「登录证明」，Access Token 是给 API 用的「通行证」，ID Token 绝不能拿去调 API。

| | ID Token | Access Token |
|---|---|---|
| `aud` | 客户端的 `client_id` | 资源服务器 |
| 用途 | 确认登录结果、建本地会话 | 调用 API |
| 格式 | 必须是 JWT | JWT 或不透明串 |

- 资源服务器接受 ID Token，等于接受「发给别人的凭证」，拿到任一 RP 的 ID Token 就能冒充用户
- 反过来，客户端也不该解析 Access Token 来判断用户身份
- 校验 ID Token 要核对签名、`iss`、`aud`、`exp` 和 `nonce`（防 ID Token 重放）

→ 详见 [OIDC](/security/3_oidc#二、id-token-与-access-token)

### Q10：Cookie 不能跨域，不同域名的系统怎么做单点登录？

**一句话**：SSO 不靠共享 Cookie：全局会话 Cookie 只写在认证中心自己的域名下，每个系统都跳去认证中心拿一次性票据，再各自建本地会话。

- 流程：访问 A → 跳认证中心 → 登录后种全局会话、发票据 → A 后端验票建本地会话
- 访问 B 时再跳认证中心，全局会话还在，直接发新票据，不用再输密码
- 票据三要素：短时有效、只能用一次、绑定具体系统
- 两层会话相互独立：IdP 全局会话管「要不要重新输密码」，本地会话管「本系统内是否已登录」
- 会话 Cookie 用 `SameSite=Lax`；用 `Strict` 时从 IdP 跳回来不带 Cookie，会表现为反复要求登录

**常见坑**：把同一主域下共享 Cookie + Redis 会话当成 SSO，那只是共享本地会话。

→ 详见 [单点登录](/security/4_sso#_1、跨域名为什么也能-sso)

### Q11：单点登出怎么做？为什么比单点登录难？

**一句话**：在 A 点退出只销毁了 A 的本地会话，IdP 和 B、C 的会话都还活着；完整的单点登出要通知 IdP，再由 IdP 逐个通知其他系统，推荐走后端通道。

- 前端通道：IdP 登出页用 iframe 逐个访问各系统的登出地址，依赖第三方 Cookie，越来越不可靠
- 后端通道：IdP 服务端直接 POST 各系统的回调，OIDC 里是签名的 `logout_token`，可重试、可记录
- 应用登录时要记下 IdP 会话标识（OIDC 的 `sid`）和本地会话的映射，多实例要放共享存储
- 无状态 JWT 的 Access Token 收不回来，只能靠几分钟的短有效期兜底
- 常见组合：后端通道 + 短会话兜底

→ 详见 [单点登录](/security/4_sso#八、单点登出-slo)

## 三、授权

### Q12：RBAC、ABAC、ReBAC 有什么区别？怎么选？

**一句话**：RBAC 看「你是什么角色」，ABAC 看「各方属性满不满足规则」，ReBAC 看「你和这个对象有没有关系」；大多数系统 RBAC 打底，再按需叠加另外两种。

| 模型 | 判断依据 | 典型场景 |
|------|---------|---------|
| RBAC | 用户 → 角色 → 权限 | 后台管理、企业内部系统 |
| ABAC | 主体 / 资源 / 环境属性 + 策略表达式 | 「同部门」「工作时间」这类条件 |
| ReBAC | 对象之间的关系图，可传递 | 文档分享、组织树、多租户 SaaS |

- RBAC 管能不能调这个接口，ABAC 规则管能不能动这条数据
- 角色爆炸（地区 × 业务线 × 操作拆出成百上千个角色）说明维度放错了，应改成属性
- ReBAC 代表实现是 OpenFGA、SpiceDB，代价是业务数据变化时要同步写关系

→ 详见 [权限模型：RBAC 与 ABAC](/security/5_rbac_abac#五、模型对比与选型)

### Q13：OPA 是什么？为什么要把授权规则交给它？

**一句话**：OPA 是一个通用策略引擎，用 Rego 语言写规则，业务服务只把「谁、要干什么、对什么」发给它，它返回允许或拒绝，规则从业务代码里抽了出来。

- PEP（策略执行点）：业务服务或网关，负责收集上下文、执行结果
- Rego：声明式策略语言，OPA 1.0 起默认 Rego v1 语法
- 部署：Sidecar 本地调用延迟最低；也可集中部署或编译成 Wasm 嵌入
- 策略用 Bundle 统一下发，决策日志记录每次输入和结果，方便审计「为什么被拒」
- 同一个引擎还用于 K8s 准入控制、Envoy / Istio 外部授权

→ 详见 [权限模型：RBAC 与 ABAC](/security/5_rbac_abac#六、opa-策略引擎)

### Q14：数据权限（行级权限）怎么做？

**一句话**：功能权限回答「能不能调接口」，数据权限回答「调通后能看到哪些行」，本质是一条「用户部门和数据所属部门比较」的规则，要在服务端统一追加过滤条件。

- 常见数据范围：仅本人、本部门、本部门及子部门、全部、自定义部门
- 数据范围挂在角色上（如「部门经理 → 本部门及子部门」），多角色取并集
- 超级管理员跳过过滤
- 通常用 MyBatis-Plus 拦截器在 SQL 上自动拼条件，业务代码不用每处手写

**常见坑**：靠前端传部门 ID 做过滤，改个参数就能看别的部门。

→ 详见 [权限模型：RBAC 与 ABAC](/security/5_rbac_abac#数据权限)

## 四、API 与数据安全

### Q15：开放接口为什么要「签名 + 时间戳 + nonce」？

**一句话**：签名证明「请求没被改过、是持有 Secret 的人发的」，时间戳 + nonce 防止合法请求被截下来原样重发，三者缺一不可。

- 签名：用 HMAC 对规范串计算，Secret 本身不在网络上传
- 规范串要包括 HTTP 方法、路径、排序后的查询串、时间戳、nonce、请求体摘要，防止参数被挪到别的接口
- 时间戳：超出允许窗口（如 5 分钟）直接拒绝
- nonce（一次性随机数）：在窗口期内存进 Redis，重复出现就是重放
- 有标准方案 RFC 9421（HTTP Message Signatures）可直接采用

→ 详见 [API 安全](/security/6_api_security#三、接口签名与防重放)

### Q16：什么是 BOLA / 越权访问？怎么防？

**一句话**：BOLA（对象级授权失效）就是「改一下 URL 里的 ID 就能看别人的订单」，排在 OWASP API Top 10 第一；防法是每次都按「当前用户 + 对象 ID」一起查。

- 根因：只校验了「登录了没有」，没校验「这条数据是不是你的」
- 写法：`findByIdAndUserId(id, 当前用户)`，不要 `findById(id)`
- 查不到返回 404 而不是 403，不暴露这个 ID 存在
- 对外 ID 用 UUID / 雪花 ID 只能降低枚举风险，不能代替授权检查
- 限流防刷属于另一类问题（API4 / API6），按调用方维度做，见限流专题

→ 详见 [API 安全](/security/6_api_security#五、bearer-token-与对象级授权)

### Q17：用户密码应该怎么存？

**一句话**：密码只能用专门的慢哈希单向处理，首选 Argon2id，老系统用 bcrypt；MD5、SHA-256 加盐也不行，问题在于太快。

| 算法 | 说明 |
|------|------|
| Argon2id | 首选，内存困难，抗 GPU |
| bcrypt | 老系统常用，cost ≥ 10，只处理前 72 字节 |
| PBKDF2 | 需要 FIPS 合规时用 |

- 慢哈希：故意算得慢、吃内存，把每次猜测的成本抬高几个数量级
- Spring Security 用 `DelegatingPasswordEncoder`，存成 `{argon2}...`，前缀记录算法，换算法老数据仍能校验
- 平滑升级：用户下次登录成功时自动用新算法重新哈希
- 参数按单次校验 200～500ms 压测确定，登录接口配限流和失败锁定

→ 详见 [数据安全](/security/7_data_security#密码哈希)

### Q18：敏感字段怎么加密？什么是信封加密？

**一句话**：对称加密首选 AES-GCM；密钥不能和数据放一起，用信封加密：KMS 里的主密钥只加密「数据密钥」，数据密钥在本地加密数据。

- AES-GCM：加密的同时防篡改，同一密钥下 IV（初始向量）绝不能重复；ECB 模式禁止使用
- AAD（附加认证数据）放「属于哪条记录哪个字段」，密文被挪到别人名下就解不开
- 主密钥（KEK）：在 KMS / HSM 里永不导出
- 数据密钥（DEK）：KMS 生成，明文用完就丢，只存加密后的 DEK 和数据密文
- 好处：轮换主密钥只需重新加密 DEK，不用重加密全部数据

**常见坑**：密钥写在配置文件或代码里，等于没加密。

→ 详见 [数据安全](/security/7_data_security#信封加密)

### Q19：数据脱敏怎么做？日志里要注意什么？

**一句话**：接口输出按类型遮挡（手机号留前 3 后 4），日志按「源头不打、兜底再遮」两层处理，密码、完整 Token、密钥一律不能记。

- 常见规则：手机号 `138****5678`，身份证留前 6 后 4，银行卡只留后 4 位，姓名只留姓
- 接口输出：给字段加注解，由 Jackson 序列化时自动脱敏，不在每个接口手写
- 源头不打：不直接打印整个请求对象，含敏感字段的 DTO 重写 `toString()`
- 兜底遮盖：Logback 按正则把手机号、证件号遮住
- 请求日志过滤掉 `Authorization`、`Cookie`、签名头

→ 详见 [数据安全](/security/7_data_security#六、数据脱敏)

## 五、漏洞与零信任

### Q20：SQL 注入怎么防？MyBatis 的 `#{}` 和 `${}` 有什么区别？

**一句话**：防 SQL 注入只有一招：参数化查询，让输入永远只当数据；MyBatis 里 `#{}` 是参数化，`${}` 是直接拼字符串。

| 写法 | 实现 | 安全性 |
|------|------|--------|
| `#{}` | `PreparedStatement` 的 `?` 占位符 | 安全 |
| `${}` | 直接字符串替换 | 不安全，只能配白名单 |

- 动态排序、表名只能用 `${}` 时，把前端值映射成代码里写死的列名（如枚举）
- LIKE 也用 `#{}`：`CONCAT('%', #{kw}, '%')`，不要写 `'%${kw}%'`
- MyBatis-Plus 的 `last()`、`apply()` 拼用户输入同样会注入
- 数据库账号按最小权限分配，注入发生时能控制损失

→ 详见 [常见漏洞与防护](/security/8_vulnerabilities#_2、参数化查询)

### Q21：XSS 和 CSRF 分别是什么？各怎么防？

**一句话**：XSS 是攻击者的脚本在你的页面里执行；CSRF 是恶意网站借浏览器自动带的 Cookie 冒充你发请求。前者靠输出编码 + CSP，后者靠 CSRF Token + SameSite。

- XSS 根本防护：输出时按上下文转义（HTML、属性、JS、URL 各不相同），不是入库时过滤
- CSP（内容安全策略）：告诉浏览器只执行哪些来源的脚本，避免 `'unsafe-inline'`
- CSRF 要不要防只看一件事：凭据是不是浏览器自动携带的（Cookie 要防，Authorization 头不用）
- SameSite 用 `Lax`：挡住跨站 POST，又不破坏 SSO 回跳
- SameSite 只是纵深防御，不能替代 CSRF Token；有副作用的操作不能用 GET

**常见坑**：以为 HttpOnly Cookie 能防 XSS，它只防脚本读 Cookie，挡不住脚本以用户身份发请求。

→ 详见 [常见漏洞与防护](/security/8_vulnerabilities#四、csrf-跨站请求伪造)

### Q22：什么是 SSRF？怎么防？

**一句话**：SSRF 是让服务器按用户给的 URL 去发请求，被拿来访问内网和云主机元数据；防法是出站白名单 + 网络层隔离。

- 高危功能：图片抓取、链接预览、Webhook 回调、导入远程文件
- 典型目标：`169.254.169.254` 元数据服务（能拿到云上临时密钥）、内网 Redis、Actuator
- 应用层：只允许 https、主机白名单、解析后拒绝内网 IP
- DNS 重绑定：校验时和连接时解析结果不同，所以还要网络层兜底
- 网络层：走专用出口代理、K8s NetworkPolicy 限制出站，AWS 上强制 IMDSv2

→ 详见 [常见漏洞与防护](/security/8_vulnerabilities#五、ssrf-服务端请求伪造)

### Q23：反序列化漏洞是怎么回事？

**一句话**：共同根因是「数据决定了要实例化哪个类」，攻击者构造数据触发危险类的方法链（gadget 链）执行任意代码；防法就是不让外部数据决定类型。

- Java 原生序列化：不对不可信数据做 `readObject`，遗留系统用 `ObjectInputFilter` 白名单
- Fastjson 1.x：AutoType 黑名单多次被绕过，2.x 默认关闭，不要手动开
- Jackson：多态用 `@JsonTypeInfo(use = Id.NAME)` 加子类型列表，不用 `Id.CLASS`
- 确需全局 Default Typing 时，必须配限定包前缀的类型校验器
- 对外接口一律用 JSON / Protobuf

→ 详见 [常见漏洞与防护](/security/8_vulnerabilities#六、不安全的反序列化)

### Q24：零信任是什么？服务间怎么落地？

**一句话**：零信任就是「不因为在内网就信任」：以身份代替网络位置做信任依据，每次访问都认证授权，最小权限，假设已经被攻破；服务间落地靠工作负载身份 + mTLS。

- 内网流量同样加密认证，每个服务都校验调用方，不只在网关做一次
- IP 不能当身份：Pod IP 随时变，需要可验证的工作负载身份（SPIFFE ID）
- mTLS（双向 TLS）：双方都出示证书，从证书里取出对端身份交给授权
- mTLS 只解决「对方是谁」，「能做什么」还要授权策略（如 Istio AuthorizationPolicy 默认拒绝）
- 证书要短时效、自动轮换，靠服务网格或 SPIRE 管理

→ 详见 [零信任架构](/security/9_zero_trust#四、服务间-工作负载身份与-mtls)
