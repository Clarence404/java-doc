# 项目难点与亮点面试题解答

> 题目清单见 [业务场景高频面试题](/scenario/99_interview)；细节见各题链接的正文。
>
> 版本基线：JDK 21 / 25、Spring Boot 4、MySQL 8.4、Redis 8。「可量化的效果」里的数字只示意量级和讲法，面试时一律换成自己项目的实测值。

## 一、并发与一致性

### Q1：怎么讲「用分布式锁防止并发重复操作」这个亮点？

**一句话**：锁只负责「同一业务键同一时刻只有一个请求在处理」，真正判断「做没做过」的是锁内的条件更新或唯一约束。

**背景问题**：用户连点、网关重试、多实例同时处理同一笔退款，出现重复退款或数据被覆盖。

**方案要点**：
- Redisson `tryLock`，key 细到资源 ID（如 `lock:refund:{refundNo}`），不传 leaseTime 让看门狗续期
- 锁内用 `PENDING → PROCESSING` 条件更新做最终判断，影响 0 行就返回当前状态
- 加锁放在事务边界外，避免「锁先释放、事务后提交」
- 拿不到锁返回「处理中，请稍后」，不当成失败也不当成成功

**可量化的效果**：上线后重复退款工单从每月若干起降到 0；锁等待耗时 P99 在个位数毫秒。

**面试官可能的追问**：
- 锁过期了业务还没执行完怎么办？（看门狗续期；极端情况靠条件更新或 Fencing Token 兜底）
- Redis 主从切换锁丢了怎么办？（锁只是减少并发，正确性由数据库条件更新保证）
- 为什么不用锁做秒杀防超卖？（串行化吞吐太低，库存应原子扣减）

→ 详见 [幂等设计](/architecture/3_idempotence#八、分布式锁-只做串行化)、[分布式锁](/distributed/3_lock#七、常见坑)

### Q2：怎么讲「Redis Lua 预扣库存防超卖」这个亮点？

**一句话**：限购校验和扣库存放进一个 Lua 脚本原子完成，Redis 挡住瞬时流量，数据库条件更新做最终兜底。

**背景问题**：秒杀开始瞬间几十倍流量，直接 `UPDATE` 库存行，所有请求排队抢同一行锁，数据库被打满。

**方案要点**：
- 活动前把库存预热到 Redis，一个脚本完成「是否已购 → 库存是否够 → 扣减 → 记录已购」
- 预扣成功才发 MQ 异步下单，消费端一个本地事务 + 唯一约束落库
- 本地售罄标记：售罄后各实例直接返回，不再访问 Redis
- MQ 发送失败回补库存，定时对账兜住「预扣了却没下单」的少卖

**可量化的效果**：峰值请求量是平时的几十倍时数据库 QPS 平稳；超卖 0 单，少卖由对账在分钟级补回。

**面试官可能的追问**：
- 为什么限购和扣减不能分两次调用？（中间状态会导致记了已购却没扣库存）
- 单个库存 key 成为热点怎么办？（库存拆分到多个 key 或分段）
- 进程在预扣后、发 MQ 前崩溃怎么办？（对账任务回补）

→ 详见 [秒杀](/scenario/4_seckill#_2、一个-lua-脚本完成限购与扣减)、[秒杀](/scenario/4_seckill#_2、对账-兜住少卖)

### Q3：怎么讲「状态机 + 条件更新做支付回调幂等」这个亮点？

**一句话**：渠道流水号加唯一约束挡住重复通知，状态流转只用 `UPDATE … WHERE status = 旧状态`，影响 0 行就说明已经处理过。

**背景问题**：支付渠道会重复回调，回调和主动查单也可能同时到达，导致重复记账、重复发货。

**方案要点**：
- 回调和查单走同一个入口，先验签、再校验金额与商户号
- 同一事务内：插入渠道流水（唯一约束）→ 交易单 `PAYING → SUCCESS` 条件更新 → 写出站事件
- 捕获 `DuplicateKeyException` 视为已处理，直接给渠道返回成功
- 状态枚举里显式定义允许的流转，非法流转直接拒绝

**可量化的效果**：重复回调占比在一定比例时，重复入账为 0；回调处理 P99 在几十毫秒内。

**面试官可能的追问**：
- 为什么不用 Redis 去重？（Redis 和数据库不在一个事务，判断与写入之间有窗口）
- 回调一直没来怎么办？（定时主动查单补偿）
- 需要加 version 字段吗？（状态本身就是版本，`WHERE status = ?` 已足够）

→ 详见 [支付](/scenario/14_payment#_3、回调幂等-渠道流水号唯一约束-条件更新)、[幂等设计](/architecture/3_idempotence#四、条件更新-状态机与版本号)

### Q4：怎么讲「解决支付成功与超时关单的并发冲突」这个亮点？

**一句话**：关单前先让支付中心关闭渠道交易，本地再用「待支付 → 已取消」的条件更新改状态，支付回调和关单谁先改成功谁生效，另一个影响 0 行。

**背景问题**：用户在最后一秒付款，关单消息同时到达，出现「已付款却被关单」或库存被重复回补。

**方案要点**：
- 订单状态机只允许 `PENDING_PAYMENT → PENDING_SHIPMENT / CANCELLED` 二选一
- 关单先查单、关闭渠道交易；渠道返回已支付就放弃关单，等支付成功事件推进
- 关单的条件更新和「释放库存」事件写在同一个本地事务
- 库存服务用预占记录 `RESERVED → RELEASED` 条件更新保证只回补一次

**可量化的效果**：「已付款被关单」类客诉从每月若干起降到 0；库存回补差错为 0。

**面试官可能的追问**：
- 关单之后用户又付款成功了怎么办？（渠道交易已关闭；仍到账的走自动退款）
- 为什么不用 version 乐观锁？（状态字段本身就是乐观锁条件）
- 超时关单用什么触发？（事务提交后发延迟消息，定时扫描兜底）

→ 详见 [订单](/scenario/5_order_system#_3、关单与释放库存原子化)、[订单](/scenario/5_order_system#_2、只用条件更新改状态)

### Q5：怎么讲「本地消息表保证最终一致性」这个亮点？

**一句话**：业务数据和待发消息写进同一个本地事务，再由投递程序把消息发到 MQ，失败重试，消费方幂等，做到「数据在，消息就一定会发出」。

**背景问题**：下单后要通知库存、积分等服务，直接在事务里发 MQ，会出现「回滚了消息已发」或「提交了消息没发」。

**方案要点**：
- `outbox_message` 表带业务唯一键、状态和下次重试时间，与业务表同事务写入
- 提交后立即投递（`AFTER_COMMIT`），定时扫表只兜漏发和失败
- 多实例扫表用 `FOR UPDATE SKIP LOCKED`，各实例锁不同的行
- 消费方按业务键去重，去重记录与业务写入同一本地事务

**可量化的效果**：跨服务数据不一致从靠人工修数变为自动收敛；消息端到端延迟 P99 在秒级以内，积压可监控告警。

**面试官可能的追问**：
- 和 RocketMQ 事务消息比怎么选？（本地消息表不依赖特定 MQ；已用 RocketMQ 可直接用事务消息）
- 消息表越来越大怎么办？（已发送记录定期归档）
- 能不能不轮询？（用 Debezium 读 binlog 投递）

→ 详见 [分布式事务](/distributed/4_transaction#五、本地消息表-transactional-outbox)、[订单](/scenario/5_order_system#八、分布式事务-按流程选一种)

## 二、性能与异步

### Q6：怎么讲「用 CompletableFuture 编排降低接口耗时」这个亮点？

**一句话**：把互不依赖的下游调用并行化，接口耗时从「各调用之和」降到「最慢的那个」，非核心数据超时就降级。

**背景问题**：详情接口串行调用商品、价格、库存、评价等多个下游，RT 随下游数量线性增长。

**方案要点**：
- 每个下游一个 `supplyAsync`，必须传专用、有界的 IO 线程池，不用 `commonPool`
- `allOf` 汇总，整体用 `orTimeout` 设超时预算
- 非核心数据用 `exceptionally` / `completeOnTimeout` 降级为空，不拖垮整页
- HTTP / RPC 客户端自身设读超时，因为 `orTimeout` 不会中断底层调用

**可量化的效果**：接口 P99 从几百毫秒降到接近最慢下游的耗时；非核心下游故障时接口可用率不受影响。

**面试官可能的追问**：
- 线程池大小怎么定？（按下游 RT 和并发用 Little 定律估算，再压测）
- 异步线程里 traceId 丢了怎么办？（执行器包装或 `TaskDecorator`）
- `join` 和 `get` 的异常有什么区别？（`join` 包成 `CompletionException`）

→ 详见 [异步与批量](/high-perf/8_async_batch#_2、并行调用-completablefuture)、[CompletableFuture](/java/29_topic_completable_future#六、超时与取消)

### Q7：怎么讲「用 Spring 事件 + 异步解耦主流程」这个亮点？

**一句话**：下单、注册这类主流程只做核心写库，发通知、加积分、刷缓存等后续动作通过事件在事务提交后异步执行，主流程变短，模块之间也不再互相调用。

**背景问题**：主流程里塞了越来越多的附属逻辑，一个短信接口慢就拖慢下单，改需求要动核心代码。

**方案要点**：
- 主流程只 `publishEvent`，各附属动作写成独立监听器
- 用 `@TransactionalEventListener`（默认 `AFTER_COMMIT`），回滚时不会误发
- 耗时监听器配 `@Async` + 自定义有界线程池
- 进程内事件是「至多一次」，不能丢的动作改走本地消息表或 Spring Modulith 事件发布注册表

**可量化的效果**：下单接口 RT 降低一截（附属逻辑移出关键路径）；新增一个后续动作只加一个监听器类。

**面试官可能的追问**：
- 进程挂了事件丢了怎么办？（可靠性要求高的改用 Outbox）
- 监听器里要写库怎么办？（`AFTER_COMMIT` 里写库要开 `REQUIRES_NEW` 新事务）
- `@Async` 不生效的常见原因？（同类内部调用绕过代理）

→ 详见 [事件机制](/spring/7_event#_3、可靠性边界-至多一次)、[异步与批量](/high-perf/8_async_batch#_3、非关键路径-进程内异步与-mq)

### Q8：怎么讲「用 TransmittableThreadLocal 在线程池中传递上下文」这个亮点？

**一句话**：TTL 在提交任务时捕获上下文、执行前回放、执行后恢复，解决线程池复用线程导致的 traceId 丢失和租户串用。

**背景问题**：异步任务里日志没有 traceId、取到的是上一个请求的租户 ID，排查问题断链，甚至出现数据串租户。

**方案要点**：
- 普通 `ThreadLocal` 不跨线程，`InheritableThreadLocal` 只在创建线程时复制，线程池复用后值是旧的
- 用 `TtlExecutors` 包装线程池，或 `TtlRunnable` 包装单个任务，或 Java Agent，三选一不叠加
- Spring 的 `ThreadPoolTaskExecutor` 也可用 `TaskDecorator` 传 MDC，恢复而不是清空
- JDK 25 的虚拟线程场景改用 `ScopedValue`

**可量化的效果**：异步链路日志 traceId 覆盖率接近 100%；串租户问题清零。

**面试官可能的追问**：
- 为什么执行完要恢复而不是 `clear`？（`CallerRunsPolicy` 下任务可能在提交线程执行）
- `ThreadLocal` 内存泄漏的原因？（线程池线程长期存活，值没 `remove`）
- 虚拟线程还用 TTL 吗？（副本多、内存放大，优先 `ScopedValue`）

→ 详见 [线程基础](/java/23_topic_thread_basics#_4、transmittablethreadlocal-ttl)、[CompletableFuture](/java/29_topic_completable_future#七、上下文传递)

### Q9：怎么讲「热点数据预热 + 多级缓存」这个亮点？

**一句话**：流量到来前把热点数据提前加载进本地缓存和 Redis，读请求按「本地缓存 → Redis → 数据库」逐层命中，数据库只承接极少量回源。

**背景问题**：大促零点或实例刚发布时缓存为空，瞬间流量击穿到数据库；单一 Redis 也扛不住热点商品的读。

**方案要点**：
- 启动预热放在 `ApplicationRunner` 里，预热完成后才就绪接流量
- 定时 / 活动预热：按离线热度把 Top N 写入 Redis，TTL 加随机抖动
- L1 用 Caffeine 短 TTL，数据变更在事务提交后广播失效
- 预热分批限速，别让预热本身压垮数据库

**可量化的效果**：整体缓存命中率提升到很高水平，数据库读 QPS 下降一个量级；大促开场 RT 无明显毛刺。

**面试官可能的追问**：
- 多级缓存的一致性怎么保证？（先更新库再删缓存，L1 靠广播失效 + 短 TTL 兜底）
- 预热覆盖不到的突发热点怎么办？（实时探测热 key 再晋升到本地缓存）
- 为什么 TTL 要加随机值？（避免同时过期造成雪崩）

→ 详见 [缓存架构设计](/high-con/3_cache_architecture#三、缓存预热)、[两级缓存（L1 + L2）](/cache/8_two_level_cache#三、多实例-l1-失效)

### Q10：怎么讲「热点 key 探测与打散」这个亮点？

**一句话**：先识别出热点 key，读热点优先放进本地缓存，不能用本地缓存时把一个 key 复制成多个副本分散到不同分片。

**背景问题**：某个爆款商品的 key 集中落在一个 Redis 分片上，该节点 CPU、带宽打满，其他分片却很空闲。

**方案要点**：
- 探测：客户端滑动窗口计数或集中式探测，超过阈值标记为热 key
- 热 key 走本地缓存（短 TTL，接受秒级不一致）
- 多副本：`key#0 … key#N-1` 读时随机选一个，写时更新全部副本；不能用 hash tag
- 写热点（热点行更新）另外处理：合并写、分段计数

**可量化的效果**：热点分片 CPU 从接近打满降到与其他分片相当；热 key 读 RT 稳定在毫秒内。

**面试官可能的追问**：
- 副本之间不一致怎么办？（更新瞬间短暂不一致，业务能容忍才用）
- 怎么确认副本落在不同节点？（`CLUSTER KEYSLOT` 校验）
- 热点探测放客户端还是集中式？（实例多时集中式更准）

→ 详见 [热点问题](/high-con/6_hotspot#二、读热点治理)

## 三、数据与任务

### Q11：怎么讲「EasyExcel 流式导入导出」这个亮点？

**一句话**：导出按主键游标分批查、分批写文件，导入用监听器分批读、逐批校验入库，内存占用与总行数无关，再放进异步任务避免接口超时。

**背景问题**：一次导出几十万到上百万行，全量查出再写 Excel 直接 OOM；同步接口超时，用户反复点导致重复导入。

**方案要点**：
- 导出：`WHERE id > lastId LIMIT n` 游标分批，EasyExcel 按批写入，超过单 sheet 上限换 sheet 或改 CSV
- 异步任务表记录状态，文件传到对象存储，用预签名 URL 下载
- 导入：先上传再异步解析，监听器每批几百行校验后批量插入，断点行号与数据同事务提交
- 重复导入：业务唯一键 + 唯一约束兜底，文件摘要只做提醒

**可量化的效果**：百万行导出的堆内存占用稳定在几十 MB 量级；导出从同步超时变为几分钟内异步完成。

**面试官可能的追问**：
- 为什么不用 `LIMIT offset, n`？（深分页越翻越慢）
- 导入部分失败怎么处理？（逐批提交 + 错误报告，或按批次号整批撤销）
- 多实例同时执行同一导入任务怎么办？（断点条件更新保证每批只生效一次）

→ 详见 [海量数据导入导出](/scenario/3_sheet_export#_2、easyexcel-按批写入)、[海量数据导入导出](/scenario/3_sheet_export#_5、重复导入的幂等)

### Q12：怎么讲「Redis ZSet 实时排行榜」这个亮点？

**一句话**：用 ZSet 维护实时榜单，Top N 和「我的排名」都是对数级查询；同分先到先得靠把时间编码进 score，并注意双精度的精度上限。

**背景问题**：用数据库 `ORDER BY` 实时算排名，数据量一大就慢；同分用户的排序还经常被用户投诉不公平。

**方案要点**：
- `ZINCRBY` 更新、`ZREVRANGE` 取 Top N、`ZREVRANK` 查我的排名
- 分时段榜单每期一个 key，设过期时间，结束后归档到数据库
- 同分先到：`score = 积分 × 10^7 + (10^7 - 1 - 距开始秒数)`，组合值小于 2^53，用 Lua 读改写
- 积分以数据库流水为准，榜单可由流水重建

**可量化的效果**：排名查询从数据库的秒级降到毫秒级；同分排序投诉清零。

**面试官可能的追问**：
- 为什么不能直接用毫秒时间戳拼 score？（超过 2^53 精度丢失，时间部分失效）
- 榜单数据丢了怎么办？（从积分流水重建）
- 千万级成员的大榜单怎么办？（分片后合并 Top N）

→ 详见 [排行榜和积分](/scenario/7_rank_system#五、同分时先到先得)、[Redis 典型应用场景](/cache/4_redis_scenario#一、排行榜-zset)

### Q13：怎么讲「XXL-JOB 分片广播扫描分表」这个亮点？

**一句话**：用 XXL-JOB 分片广播把定时任务拆给多个执行器，每个实例只负责一部分物理表，表内按主键游标分批处理，任务整体幂等。

**背景问题**：订单分成几十上百张表，单实例定时扫描（超时关单、对账、归档）跑几个小时，还经常和下一次调度重叠。

**方案要点**：
- 分片广播：执行器拿到 `shardIndex` / `shardTotal`，只处理 `表序号 % shardTotal == shardIndex` 的表
- 表内 `id > lastId` 游标分批，每批短事务提交，避免长事务和大锁
- 阻塞策略选「丢弃后续调度」，设置任务超时，实例数变化时分片自动重新分配
- 重试、故障转移会重复处理，靠状态机条件更新保证幂等

**可量化的效果**：全量扫描耗时随执行器数量近线性下降，从小时级降到分钟级；调度重叠告警消失。

**面试官可能的追问**：
- 某个分片执行失败怎么办？（失败重试 + 告警，幂等保证重跑安全）
- 调度中心多实例怎么避免重复触发？（数据库行锁抢占扫描权）
- 为什么不按 `id % shardTotal` 在一张大表里分？（分表场景按物理表划分更自然，没有跨表扫描）

→ 详见 [分布式调度](/distributed/6_job_scheduler#三、xxl-job)、[分布式调度](/distributed/6_job_scheduler#_3、分片)

### Q14：怎么讲「雪花算法 / 号段模式生成分布式 ID」这个亮点？

**一句话**：分库分表后不能再用数据库自增，按场景选雪花算法（本地生成、趋势递增）或号段模式（只依赖数据库、递增性更强），并处理好时钟回拨和 workerId 分配。

**背景问题**：分表后各表自增主键重复；直接用 UUID 做主键又导致 B+ 树页分裂、索引膨胀。

**方案要点**：
- 雪花：时间戳 + workerId + 序列号，workerId 从配置中心或 StatefulSet 序号显式分配
- 时钟回拨：小幅等待追上，大幅拒绝发号并告警
- 号段：一次从数据库取一段 ID 放内存，双 Buffer 提前加载下一段
- 接口里把 64 位 ID 序列化为字符串，避免前端精度丢失

**可量化的效果**：发号耗时在微秒级，不再成为写入瓶颈；上线以来 ID 冲突为 0。

**面试官可能的追问**：
- 容器里 workerId 为什么会冲突？（默认按 MAC 和进程号推导，容器里常常相同）
- 低 QPS 时按 ID 取模分片为什么会倾斜？（序列号几乎总是 0）
- 号段模式重启会怎样？（丢掉未用完的号段，只是不连续）

→ 详见 [分布式 ID 生成](/distributed/8_id_generator#_3、时钟回拨)、[分布式 ID 生成](/distributed/8_id_generator#八、方案对比与选型)

### Q15：怎么讲「用 Bitmap 记录预约时段」这个亮点？

**一句话**：把「某资源某天」做成一个 Bitmap，每个时段占一位，占用、查询空闲、统计已约数都是位运算，内存极小；数据库唯一约束仍是最终的防重保证。

**背景问题**：场馆、医生号源按 15 分钟一格预约，用行记录查空闲时段要扫大量数据，高峰期查询和抢占都慢。

**方案要点**：
- key 设计为 `resv:{资源ID}:{日期}`，偏移量 = 时段序号
- 单格占用用 `SETBIT` 的返回值判断：返回 1 说明已被占，原子且无需加锁
- 连续多格预约用 Lua 先检查全部位再一起置位，保证原子
- 预约单写数据库时以「资源 + 日期 + 时段」唯一约束兜底，Redis 丢数据可从数据库重建

**可量化的效果**：每个资源每天只占几十字节；空闲时段查询从扫表变为一次 `BITFIELD`，RT 降到毫秒级。

**面试官可能的追问**：
- Bitmap 和数据库不一致怎么办？（数据库为准，定时校对或按天重建）
- 取消预约怎么处理？（`SETBIT` 置 0，与预约单状态变更同步）
- 什么时候不适合 Bitmap？（偏移量稀疏且很大时浪费内存）

→ 详见 [Redis 典型应用场景](/cache/4_redis_scenario#三、签到统计-bitmap)、[Redis 基础](/cache/1_redis_base#_1、bitmap)

## 四、稳定性与安全

### Q16：怎么讲「API Key + 签名 + 滑动窗口限流保护开放接口」这个亮点？

**一句话**：调用方用 Secret 对规范串做 HMAC 签名，时间戳 + nonce 防重放，再按 access key 维度用 Redis 滑动窗口限流，防篡改、防重放、防刷三件事分别解决。

**背景问题**：开放接口被抓包重放、参数被篡改，个别调用方脚本刷接口拖垮服务。

**方案要点**：
- 规范串包含方法、路径、排序后的查询串、时间戳、nonce、请求体摘要，只签参数不够
- 服务端校验时间窗口，nonce 在窗口期内存 Redis 去重
- Secret 加密存储、支持新旧并存轮换和吊销
- 限流按调用方维度，Redis + Lua 滑动窗口，被限流返回 429 并带重试时间

**可量化的效果**：重放和篡改请求全部被拦截；单个调用方突发流量不再影响其他调用方，接口可用率保持稳定。

**面试官可能的追问**：
- 为什么用滑动窗口而不是固定窗口？（固定窗口在边界处可能放过两倍流量）
- 经过网关改写路径签名怎么校验？（按外部路径在网关校验）
- HTTPS 了还需要签名吗？（HTTPS 防传输被看，签名证明调用方身份和请求未被改）

→ 详见 [API 安全](/security/6_api_security#三、接口签名与防重放)、[限流与过载保护](/high-avail/7_rate_limiting#五、分布式限流-redis-lua-滑动窗口)

### Q17：怎么讲「优雅上下线与服务预热」这个亮点？

**一句话**：下线时先摘流量、再处理完存量请求、最后关闭；上线时先预热、再就绪、再逐步放量，让发布过程对调用方无感。

**背景问题**：每次发布都有一波 5xx 和 RT 毛刺：旧实例被直接杀掉，新实例冷启动就接满流量。

**方案要点**：
- Spring Boot 开启优雅停机，K8s `preStop` 等待注册中心和负载均衡摘除
- 预热逻辑放在 `ApplicationRunner`：建连接池、加载热点缓存、调用核心路径促进 JIT
- 用 Nacos 等注册中心时，预热完成后再注册或先给低权重
- 滚动参数 + PDB 保证可用实例数，消息消费者先停拉取再退出

**可量化的效果**：发布期间错误请求数从每次几百降到接近 0；新实例启动后的 RT 毛刺明显收窄。

**面试官可能的追问**：
- 为什么 Readiness 正常了还有调用方打过来？（注册中心注册早于预热完成）
- 停机等待时间怎么定？（大于最长请求耗时，小于 `terminationGracePeriodSeconds`）
- 长连接、MQ 消费怎么优雅退出？（先停止接新任务，处理完再关闭）

→ 详见 [优雅上下线与变更](/high-avail/8_graceful_release#一、优雅停机)、[优雅上下线与变更](/high-avail/8_graceful_release#二、服务预热)

### Q18：怎么讲「慢 SQL 治理」这个亮点？

**一句话**：把慢 SQL 治理做成「发现 → 按总耗时排序 → 看执行计划 → 优化 → 验证 → 上线前审核」的闭环，而不是出事后临时救火。

**背景问题**：数据库 CPU 经常飙高，高峰期接口超时，但每次只是临时 kill 掉几条查询。

**方案要点**：
- 开慢查询日志，用 `pt-query-digest` 按「次数 × 单次耗时」排出 Top N
- `EXPLAIN` / `EXPLAIN ANALYZE` 看访问类型、扫描行数、filesort
- 常见手段：联合索引与覆盖索引、消除隐式转换、深分页改游标、N+1 改批量查询
- 上线前 SQL 审核，CI 检查执行计划，慢 SQL 持续告警

**可量化的效果**：Top 10 慢 SQL 治理后数据库 CPU 峰值明显下降，相关接口 P99 从秒级降到百毫秒级。

**面试官可能的追问**：
- 为什么按总耗时而不是单次最慢排序？（高频的中等慢 SQL 对数据库压力更大）
- 加了索引还是不走索引，可能是什么原因？（隐式转换、函数、区分度低、统计信息不准）
- 优化后怎么确认没影响其他 SQL？（对比执行计划、灰度观察慢日志）

→ 详见 [数据访问性能](/high-perf/10_db_performance#一、慢-sql-治理闭环)、[EXPLAIN 与 SQL 优化](/database/1_mysql/7_topic_explain#四、慢-sql-定位)
