# 业务场景面试题解答

> 题目清单见 [业务场景面试题](/scenario/99_interview)；细节见 [业务场景总览](/scenario/0_overview)。
>
> 版本基线：JDK 21、Spring Boot 4、Redis 8.x、RocketMQ 5.x（兼顾 4.x）、MySQL 8.4 LTS、ShardingSphere 5.5、Elasticsearch 9.x、Flink 2.x。
>
> 系统设计题的答法：先用一句话说清核心思路，再讲 3~5 个关键设计决策，每个决策说明它解决哪个瓶颈，最后主动讲坑和兜底。单项技术（锁、事务、幂等、缓存一致性）只点到为止，展开见对应的答案页。

## 一、交易类

### Q1：如何设计一个秒杀系统？

**一句话**：逐层拦截，让流量像漏斗一样越往下越少：CDN 拦静态请求，网关拦超频和脚本，本地售罄标记拦售罄后的请求，Redis 拦超出库存的请求，数据库只承接预扣成功的那部分。

- 页面静态化 + CDN：开抢前页面请求不回源，解决静态资源压垮应用的问题
- 防刷与限流：一次性下单 token、验证码把瞬时峰值拉平到几秒，网关按用户和接口总量限流，解决脚本和超出容量的流量
- Redis 预扣：一个 Lua 脚本完成限购校验、扣库存、记已购，解决数据库单行锁扛不住瞬时并发的问题
- MQ 异步下单：预扣成功后同步发消息、返回「排队中」，订单服务按自己的能力消费，解决写库峰值
- 结果查询：用户按 orderId 轮询结果；超时未支付由定时消息关单并回补库存

**常见坑**：只讲 Redis 扣库存，不讲 Redis 与 MQ 之间的一致性（发送失败要回补、崩溃要对账），也不讲售罄标记在回补后要清除。

→ 详见 [秒杀](/scenario/4_seckill#二、整体架构)

### Q2：秒杀如何防超卖？Redis 预扣成功但 MQ 发送失败或进程崩溃，怎么避免少卖？

**一句话**：防超卖靠原子扣减：Redis 用 Lua 判断库存再扣，数据库用 `WHERE stock >= n` 条件更新兜底；分布式锁不是防超卖的主手段。少卖靠回补和对账。

- 限购和扣库存放进同一个 Lua 脚本：分两次调用会出现「记了已购、库存没扣到」的中间状态
- key 不存在时 Lua 里 `GET` 返回 false，要先判断；Cluster 下用 `{activityId}` hash tag 保证所有 key 同槽
- 同步发送 MQ，失败就执行回补脚本（以 `SREM` 成功为条件，可重复执行）并广播清除各实例的售罄标记
- 进程在预扣后、发送前崩溃：定时对账比较「已购集合」和订单表，核对「剩余 + 已售 = 初始库存」；要零丢失就改用 Outbox
- 消费端在一个本地事务里先插订单（唯一约束 `user_id + activity_id`），再条件扣数据库库存，重复消息撞唯一键即视为已处理

**常见坑**：单个库存 key 打满一个分片时，要拆成分桶库存，见 [热点问题](/high-con/6_hotspot#_3、分桶库存)。

→ 详见 [秒杀](/scenario/4_seckill#四、库存预扣-防超卖核心)

### Q3：下单如何做幂等和库存预占？订单流程里 Seata、事务消息、Outbox 怎么选？

**一句话**：下单以业务单号（`biz_no`）唯一约束兜底，库存和优惠券预占也按 `biz_no` 幂等；一个流程只选一种分布式事务方案，按「是否必须同步知道结果」来选。

- 下单（库存、优惠券）：必须同步知道成败，用幂等预占（TCC 思路：下单 Try 预占、支付后 Confirm、关单 Cancel），悬挂预占靠扫描释放
- 支付成功 → 发货、积分：最终一致，用 Outbox 或 RocketMQ 事务消息二选一
- Seata AT 只用于内部、低并发、要同步整体回滚的流程；它是最终一致而非强一致，注意全局锁的写阻塞和默认读未提交
- 订单状态只靠 `WHERE status = 旧状态` 的条件更新流转，状态机本身就防并发，不需要再加 version

**常见坑**：一个流程同时套 Seata 全局事务和事务消息，边界不清，出了问题不知道该谁回滚。

→ 详见 [订单](/scenario/5_order_system#八、分布式事务-按流程选一种)、[分布式面试题解答](/interview/10_distributed#三、分布式事务)

### Q4：订单超时关单有哪些方案？关单与释放库存如何原子化？

**一句话**：推荐「RocketMQ 5.x 定时消息 + 定时扫描兜底」：定时消息精确，扫描兜住发送失败和消息丢失；关单用状态条件更新，影响 1 行才释放库存。

| 方案 | 评价 |
|------|------|
| 定时扫描 | 简单可靠，有分钟级延迟，适合兜底 |
| RocketMQ 5.x 定时消息 | 精确可靠；4.x 只有 18 个固定级别，没有 15 分钟 |
| RabbitMQ 延迟插件 / TTL + 死信 | 可用；TTL 方案有队头阻塞 |
| Redis 过期通知 | 通知不持久化、订阅方断开即丢，不能用于关单 |
| 内存时间轮 | 重启丢失，只能配合持久化与扫描 |

- 定时消息在事务提交后发送（`@TransactionalEventListener(AFTER_COMMIT)`），否则会出现回滚后消息照发、或提交前就被消费查不到订单
- 关单先调支付平台的关单接口，再在一个事务里条件更新订单并写释放库存事件；库存侧按预占记录状态只释放一次

→ 详见 [订单](/scenario/5_order_system#六、超时关单)、[延迟任务](/scenario/23_delay_task#二、方案全景与选型)

### Q5：支付回调如何保证幂等与安全？

**一句话**：先验签并核对金额、商户号与本地一致，再用支付单 `WAITING → SUCCESS` 条件更新做幂等，后续动作通过 Outbox 事件异步触发，回调本身只做校验和落库、快速应答。

- 只验签不校验金额和商户号，可能被别的订单或低金额的合法通知冒充
- 支付宝成功状态是 `TRADE_SUCCESS` / `TRADE_FINISHED`，应答纯文本 `success`；微信支付 APIv3 返回 200 或 204
- 支付流水号建唯一约束；重复通知、通知与主动查单并发都只影响 0 行，不需要分布式锁
- 订单已关闭又收到支付成功：自动退款或转人工，不能忽略
- 通知可能丢失：定时查询「待支付且已发起支付」的订单，调用同一个处理入口

→ 详见 [订单](/scenario/5_order_system#五、支付回调)、[幂等设计](/architecture/3_idempotence#_2、支付回调)

### Q6：抢红包系统如何设计？怎么保证不超发、不少发、可靠入账？

**一句话**：发红包时扣款、流水、红包和全部份额在一个本地事务里落库，提交后装载到 Redis；抢红包用一个 Lua 脚本原子完成判关闭、判重、弹出份额、记领取；入账用事务消息保证必达，过期先关闭再对账后退款。

- 金额分配用二倍均值法：每次在 `[1, 剩余均值 × 2 - 1]` 分内随机，最后一人拿剩余；金额全程用「分」
- 份额可预先拆好存成 List，抢的时候只弹出，不在抢的瞬间计算
- 入账：RocketMQ 事务消息的本地事务就是执行 Lua，回查看领取记录，不确定时返回 `UNKNOWN`
- 消费端以 `(packet_id, user_id)` 唯一约束去重，领取记录、份额状态、余额、流水在同一本地事务
- 退款不能直接用「总额减已领」：先关闭红包 → 等待在途领取完成 → 对账补齐 → 条件更新状态后退未领份额

→ 详见 [抢红包](/scenario/11_red_packet)

### Q7：如何设计一个支付系统？超时关单和对账怎么做？

**一句话**：支付中心只认渠道给的证据（回调、主动查单、日终账单），本地状态只是对证据的记录；状态只用条件更新推进，每天用对账证明本地账和渠道账一致。

- 两层模型：支付单对应一次收款，交易单对应一次渠道尝试，只认第一张成功的交易单，见 [Q51](#q51-同一笔支付单-用户在两个渠道几乎同时付了款-怎么办)
- 回调和查单走同一个入口：验签并核对金额、商户号，渠道流水号去重记录与状态更新同一个事务，后续动作走 Outbox；回调会丢，所以要定时查「支付中」的交易单
- 关单顺序：先查单 → 再调渠道关单 → 最后改本地；只改本地不关渠道，用户手里的收银台还能付款，就成了「本地已关、钱已扣」
- 退款：退款单号申请时生成一次、重试复用；可退额度用条件更新占用，部分退款按累计金额推进状态
- 对账：次日下载渠道账单逐笔比对；长款（渠道有、本地没有）补单或退款，短款（本地有、渠道没有）挂到次日复核；差错用调账流水修正，不改历史数据

**常见坑**：把前端跳转回来的「支付成功」当成结果，它只能用来展示。

→ 详见 [支付](/scenario/14_payment#五、主动查单与超时关单)、[对账](/scenario/14_payment#七、对账)

### Q8：优惠券系统怎么设计？大促领券怎么不超发，用券时状态怎么流转？

**一句话**：券分模板和实例两层；领券用一个 Lua 脚本原子扣库存、判限领，成功后异步落库；用券靠带原状态的条件更新在「未使用 → 锁定 → 已使用」之间流转。

- 领券：一个脚本里判库存、判每人限领、扣库存、记已领数，并写一条待落库记录（相当于 Redis 里的发件箱），脚本成功就算领到
- 落库：MQ 发送失败不回补库存，由补发任务用同一个券 ID 重发；券 ID 主键和 `issue_key`（发放键，含用户和第几张）唯一约束去重
- 用券：下单锁券、支付核销、关单解锁、整单退款返还，`UPDATE` 条件里带原状态和 `lock_biz_no` / `order_id`，重复消息影响 0 行，也不会误解锁别的订单锁住的券
- 过期：锁券条件直接带 `valid_end > NOW()`，扫描任务只改展示状态；不要每张券发一条延迟消息
- 多券叠加：逐层计算、同层互斥，用最大余额法精确到分地分摊到每个商品行，退款按分摊后的实付退

**常见坑**：模板表每领一张就 `issued_count + 1`，这一行变成写热点；总量靠 Redis 原子扣减，再按「Redis 剩余 + 待落库 + 已落库 = 总量」对账。

→ 详见 [优惠券和营销](/scenario/15_coupon#四、发券)

### Q9：库存在下单时扣、支付时扣，还是先预占？怎么选？

**一句话**：默认选「预占 + 确认」：下单把可售挪到预占，支付后转已售，超时关单再还回可售，既保证付了钱一定有货，又让未付款的占用有时限。

| 方式 | 问题 |
|------|------|
| 下单扣 | 恶意下单不付款就能占光库存 |
| 支付扣 | 多人同时付款，后付的人钱付了却没货，只能退款 |
| 预占 + 确认 | 多一张预占表，要处理悬挂预占（下单失败却占着库存） |

- 预占带 TTL（支付超时 + 余量），恶意占库存的代价被限制在一个支付窗口内，再配合限购、风控
- 超时释放以关单事件为主；扫描兜底时先问订单服务，订单已支付就补做确认而不是释放

→ 详见 [库存与票务](/scenario/22_inventory#四、扣减时机-下单扣、支付扣还是预占)

### Q10：在线选座怎么设计？多人抢同一个座位、一次锁多个连座怎么办？

**一句话**：位图负责展示，Redis Lua 全成或全败地锁一组座位，MySQL 条件更新做最终裁决，影响行数等于座位数才算锁座成功。

- 座位图：每个「场次-区域」一个 Redis 位图，1 位 = 1 个座位是否已占，实例本地缓存约 1 秒，只用于展示
- 锁座：Lua 先检查所选座位全部空闲，再一起置位并记 lockNo；建单事务里 `UPDATE ... WHERE status = 'AVAILABLE'`，行数不对就回滚并撤销 Redis 置位
- 同一座位冲突：失败者立即提示重选并推荐相邻空座，不排队等待
- 连座：在内存里按行扫位图找连续空位段，按离舞台距离、是否留下孤座（单独剩下的一个空位）打分，冲突就换下一个候选

**常见坑**：锁座过期就当空闲抢过来，用户可能正在付款；释放只走关单流程，并带上 `lock_no` 防止误放别人刚锁的座位。

→ 详见 [库存与票务](/scenario/22_inventory#九、选座与锁座)

### Q11：多仓库、多渠道（主站、直播间、门店）的库存怎么建模？

**一句话**：库存按「SKU × 仓库」一行存，下单先选仓再预占；渠道专供量从可售里冻结出一块配额，用完再扣共享池。

- 四个数量桶：可售、预占、锁定（冻结）、已售，实物 = 四者之和，查问题时能说清少的货被谁占着
- 选仓：按「能整单发货 → 距离最近 → 成本最低」排序，一个仓凑不齐就拆单，预占失败换下一个候选仓
- 渠道库存：共享池先到先得；独占配额保证直播间承诺的量；常用「配额 + 共享兜底」
- 划配额本身就是一次带渠道标记的冻结，活动结束未用完再解冻回共享池

→ 详见 [库存与票务](/scenario/22_inventory#_3、多仓与渠道库存)

### Q12：库存数对不上了，怎么对账和修复？

**一句话**：每次库存变化都在同一事务里写一条只增不改的流水，对账就是用流水、预占明细、订单、Redis 四层互相核对，修复也写流水而不是直接改数。

- 流水 vs 快照：某 SKU 流水累加必须等于当前库存，发现绕过流水改库或事务不完整
- 预占明细 vs 快照：未确认预占之和 = 预占数，已确认之和 = 已售数
- 库存 vs 订单：已确认的预占集合 = 已支付未发货订单集合，发现支付事件丢失、悬挂预占
- Redis vs MySQL：预扣层余量与数据库对得上，兜住少卖

**常见坑**：发现差异直接 `UPDATE` 余额，事后查不到谁改、为什么改；应写一条 `ADJUST` 流水，原因不明的转人工。

→ 详见 [库存与票务](/scenario/22_inventory#_3、对账修复)

## 二、读写模型类

### Q13：如何设计一个短链接系统？跳转用 301 还是 302？

**一句话**：发号器生成自增 ID，做可逆混淆后 Base62 编码成短码；跳转走缓存，需要统计点击就用 302；点击量走 Redis 计数和 OLAP 明细，不放主表。

- 短码生成：发号器 + Base62 无冲突（6 位约 568 亿个），先混淆 ID 防止被顺序枚举；哈希方案必然冲突，要靠唯一约束 + 比较原 URL + 加盐重试
- 同一长链去重：按 `long_url_hash` 建索引查重
- 缓存：生成时预热，空值缓存防穿透；主从延迟下从库查不到要再查一次主库，再写空值
- 状态码：301 会被浏览器缓存，之后统计不到；需要统计用 302 加 `Cache-Control: no-store`；目标是 POST 接口用 307
- 安全：只允许 http / https，接入恶意网址检测

→ 详见 [短链接](/scenario/6_shorturl)

### Q14：排行榜如何设计？同分时怎么让先达到的人排前面？

**一句话**：实时榜用 ZSet（`ZINCRBY` 加分、`ZRANGE ... REV` 取 Top N、`ZREVRANK` 查名次），日周月榜每个时段一个 key；同分先到先得要把「分数 + 时间」编码进一个 score。

- 组合 score：分数 × 10^7 + (10^7 − 1 − 活动开始后的秒数)，必须小于 2^53，否则 double 丢精度；用 Lua 读改写更新
- 时段 key 用 `EXPIREAT` 设绝对过期时间，过期前由分布式调度归档到 MySQL
- 亿级用户的单 key 是大 key：分片后 Top N 归并、名次用 `ZCOUNT` 求和，或只维护头部榜
- 积分增减：条件更新余额 + 流水唯一键去重，同一本地事务；榜单在提交后更新，定时对账兜底

→ 详见 [排行榜和积分](/scenario/7_rank_system)

### Q15：Feed 流推模式、拉模式、推拉结合怎么选？分页为什么不能用 offset？

**一句话**：推模式（写扩散）读最快但大 V 发布要写几千万个收件箱；拉模式（读扩散）写简单但关注越多读越慢；粉丝分布极不均的平台用推拉结合：普通作者推，大 V 只写发件箱，浏览时归并去重。

| 维度 | 推模式 | 拉模式 | 推拉结合 |
|------|-------|-------|---------|
| 读性能 | 最快 | 关注越多越慢 | 快 |
| 写放大 | 粉丝数倍 | 无 | 只对普通作者 |

- 收件箱用 ZSet，只保留最新 N 条，更早的回源内容表
- 翻页用游标（上一页最后一条的 score，开区间）：新内容不断插入，offset 会导致重复和漏读
- 扇出走「本地消息表 + MQ + 批量管道写」，`ZADD` 天然幂等；不要用进程内线程池发后不管

→ 详见 [Feed 流和消息推送](/scenario/8_feed_stream)

### Q16：搜索系统如何设计？MySQL 数据怎么同步到 ES 并防止乱序？

**一句话**：面向用户的商品搜索用 Elasticsearch；数据走「binlog CDC → MQ → 同步消费者 → ES」，按商品 ID 分区、回查数据库、用外部版本号写入防乱序。

- MySQL ngram 全文索引能用但分词质量、相关性调优、分面和扩展性都不足
- 索引带版本号，业务只访问别名；关键词放 `must`，筛选条件放 `filter`
- 防乱序：消费者回查数据库拿最新行，用外部版本号写 ES，旧版本被拒（409 忽略）
- 零停机重建：先起新消费组写新索引，再全量导入（导入时 `refresh_interval -1`、副本 0），验证后原子切换别名

→ 详见 [搜索](/scenario/9_search_system#五、数据同步-mysql-→-es)

### Q17：「附近的人」怎么做？Geohash 有什么边界问题？

**一句话**：Redis GEO 按城市分 key 存位置，再配一个上报时间 ZSet；查询多取一些再按新鲜度、可见性过滤，定时清理过期成员。

- GEO 底层就是 ZSet + Geohash 编码，`GEOSEARCH ... BYRADIUS` 按半径查
- Geohash 边界问题：两个点很近却落在不同格子里，只查自己的格子会漏；要查周围九宫格，再按实际距离过滤
- 不可见是持久的用户设置，上报时检查、查询时再过滤
- 隐私：对外只给模糊距离还不够（可多点三边定位），要做网格吸附、限制查询中心、限流
- 打车派单：状态与位置在同一个 Lua 里判断并原子占用司机，再数据库条件更新落地，避免一个司机被派两单

→ 详见 [附近的人](/scenario/12_geo_nearby)

### Q18：商品详情页如何设计？

**一句话**：按「静动分离」拆成三部分：骨架、图片、描述走 CDN；标题、规格这类千人一面的 base 数据走三级缓存；价格、库存、促销走 dynamic 接口实时并发拉取。

- 三级缓存：Nginx 共享字典（几秒 TTL，挡住大部分流量）→ 应用本地 Caffeine → Redis 全量快照，逐层回源后到商品库只剩万分之几
- 变更重建：商品改完发消息，只带 skuId 和版本号；重建服务回查最新数据、按版本号写 Redis，消息重复或乱序都不会把旧数据写回
- dynamic 并发调各服务，每个依赖单独设超时和兜底值；价格拿不到就不显示并禁止购买，不展示可能过期的价格
- 热点：大促爆款提前逐层预热；回源时同一个 key 只放一个请求去加载（单飞），防止缓存击穿
- 降级：Redis 挂了用本地旧值顶住并对回源限流，最后一层兜底是 CDN 上的只读页

**常见坑**：会员价、可领的券这类个性化数据混进 Nginx / CDN 的共享缓存，用户会看到别人的价格。

→ 详见 [商品详情页](/scenario/13_product_detail#二、整体架构)、[缓存架构设计](/high-con/3_cache_architecture)

### Q19：IM 怎么保证消息不丢、不重、有序？群聊用读扩散还是写扩散？

**一句话**：不追求每次推送都成功，而是保证任何时候按位点拉取都能补齐：服务端落库后才回 ACK，推送尽力而为，丢了靠拉取兜底；顺序以会话内的服务端 seq 为准。

- 不重：每条消息带客户端生成的 `clientMsgId`，`(conv_id, sender_id, client_msg_id)` 唯一约束去重；接收端按 `(convId, seq)` 去重
- 不丢（三段确认）：发送方收到落库后的 ACK 才算发出，否则用同一个 ID 重发；网关推送后等接收方 ACK，超时重推几次；上线、重连、发现缺号时按位点拉取
- 有序：只保证会话内有序，seq 由 Redis 分配、数据库主键兜底；客户端按 seq 插入，发现缺口就拉这段区间
- 多端：同步位点按设备记录，互不干扰；已读也用位点表示，只升不降
- 群聊：单聊和小群写扩散（每人一个收件箱，经 Outbox 可靠扇出），大群读扩散并合并推送，和 Feed 对大 V 用拉模式是同一个思路

**常见坑**：网关断开连接时直接删路由，用户这时可能已经重连到新网关，新路由被旧网关删掉；要比较 value 再删。

→ 详见 [即时通讯](/scenario/16_im#四、消息顺序与可靠性)、[WebSocket](/netty/10_websocket)

### Q20：点赞数、阅读数这类计数系统怎么设计？

**一句话**：有关系记录的计数（点赞、评论、粉丝）以关系表为准，计数只是派生值，从 binlog 异步算出来；阅读数没有明细，直接在 Redis 累加、定时刷盘。

- 去重：点赞关系表 `(user_id, target_id)` 唯一约束，撞键就是已赞过；列表页批量查是否已赞（大 V 只查当前用户）
- 计数事件：CDC 订阅关系表 binlog，插入记 +1、删除记 -1，按对象 ID 分区；业务代码不在事务里发 MQ
- 不多加：消费者按对象合并增量，计数和消费位点在同一个本地事务提交，重放的消息直接跳过；提交后 Redis 只在 key 存在时加
- 热点：爆款的阅读数拆成多个桶 key，写时随机选一个、读时求和，再加 1 秒本地缓存
- 校准：定期按关系表重算，只修正最近没有变化的对象，用 `update_time` 做 CAS

**常见坑**：Redis key 过期后照样 `HINCRBY`，会建出一个从 0 开始的计数；Redis 故障时应该隐藏数字，而不是显示 0。

→ 详见 [计数服务](/scenario/17_counter#四、点赞写路径与异步落库)、[点赞关系查询](/scenario/17_counter#八、点赞关系查询与大-v-场景)、[热点问题](/high-con/6_hotspot)

### Q21：购物车存 Redis 还是数据库？未登录的购物车登录后怎么合并？

**一句话**：用户量不大就直接存库、Redis 做缓存；千万级用户写多时以 Redis Hash 为主存储、异步合并刷库。购物车只存用户的选择，价格和库存每次实时查，结算时再校验。

- 写入：一个 Lua 脚本完成上限校验、改数据、加版本号、记脏标记；刷盘按版本号 upsert 整车快照，脏标记比较版本后再删，不会写回旧数据
- Redis 为主时内存淘汰策略设为 `noeviction` 并对水位告警，不能让 Redis 淘汰还没刷盘的数据
- 临时车：服务端生成并签名的 guestId，临时车存 Redis、TTL 7 天；不签名就能伪造别人的 guestId
- 登录合并三步：读临时车 → 在登录车所在的槽用脚本合并并写合并标记 → 删临时车；重试时合并标记让第二步变成空操作，数量不会累加两次
- 结算：进入结算页和提交订单各校验一次价格、库存、优惠、限购，金额与客户端确认的不一致就拒绝下单；收到下单成功消息后才删已购商品

→ 详见 [购物车](/scenario/19_cart#四、存储选型与异步持久化)、[登录合并](/scenario/19_cart#五、未登录购物车与登录合并)

### Q22：评论系统怎么设计？楼中楼回复怎么存？

**一句话**：用两级结构：`root_id` 指向所属一级评论、`parent_id` 指向直接回复的那条，再深的回复也平铺在一级评论下显示「回复 @某人」；表按内容 ID（`obj_id`）分片。

- 查一级评论：`obj_id + root_id = 0` 按 ID 倒序；展开楼中楼：`obj_id + root_id = ?` 按 ID 正序，都走同一个联合索引，不用递归
- `reply_to_uid` 冗余被回复人，展示和发通知都不用再查一次
- 按 `obj_id` 分片：评论区的查询都是「某内容下的评论」，一次只访问一个分片；「我发过的评论」走按用户分片的异构表
- 点赞数、回复数交给计数服务，不放评论表，避免评论行被点赞写热
- 分页用 ID 游标，不用 offset；楼中楼预览缓存每楼前 3 条，别用窗口函数扫整楼

**常见坑**：做成无限嵌套的树，展开一层就要递归查一次；需要完整树形的论坛才用路径枚举。

→ 详见 [评论系统](/scenario/21_comment#三、数据模型)

### Q23：评论要审核，先审后发还是先发后审？

**一句话**：实际都是分级：同步机审明显违规的直接拒，可疑的、新账号的、敏感内容下的先审后发，其余先发后审、事后复审下线。

- 同步阶段只做本地敏感词（AC 自动机）、黑名单和风控评分，几毫秒内完成，不同步调外部模型服务
- 异步阶段跑文本 / 图片模型，拿不准的进人审，结果用「带旧状态的条件更新」回写，晚到的结果不会覆盖新状态
- 作者自己要能立刻看到自己的评论（待审的标「审核中」），否则会反复提交
- 刷子账号给「仅自己可见」：他看着正常，别人看不到，也就不会换号重试
- 评论和事件同一本地事务写入，计数、缓存、通知只在「变为已发布」时动作

→ 详见 [评论系统](/scenario/21_comment#四、发评论链路)

### Q24：热评怎么排序？只按点赞数排有什么问题？

**一句话**：只按点赞数，先发的评论永远占着榜首；要把时间算进去（时间衰减或「对数点赞 + 发布时间」），有赞有踩时用 Wilson 置信区间下界，结果放进每个内容一个的热度 ZSet。

| 公式 | 特点 |
|------|------|
| `(赞 + 1) / (小时数 + 2)^1.8` | 越旧越低，分数随时间变，要定时重算 |
| `log10(赞) + 发布时间 / 45000` | 晚发的基础分高，只在点赞时变，不用定时重算 |
| Wilson 下界 | 样本少时保守，10 赞 0 踩不会压过 900 赞 100 踩 |

- ZSet 只保留前 1000 条，点赞按评论聚合后隔几秒重算一次，不是每赞写一次
- 热度一直在变，翻页按快照或客户端按 ID 去重
- 刷出来的点赞（同 IP、同设备集中）在热度里降权

→ 详见 [评论系统](/scenario/21_comment#六、热评排序)、[排行榜和积分](/scenario/7_rank_system)

### Q25：爆款内容的评论区每秒几万次打开，怎么扛？

**一句话**：一次打开要读列表、几十条评论、用户信息和计数，读放大几十倍且全压在同一个内容上；列表缓存存 ID、内容按 ID 缓存，热点内容的首屏结果再放进程内缓存 1～2 秒。

- 列表（时间 / 热度 ZSet）只存评论 ID，内容 `cmt:c:<id>` 单独缓存、`MGET` 批量取，删一条评论只删一个 key
- 热点探测发现爆款后，各实例本地缓存首屏组装结果，单 key 每秒几万次读变成每实例每秒一次
- 「我是否已赞」「我的待审评论」因人而异，不进公共缓存，单独查再合并
- 缓存过期只让一个请求回源重建，其余等结果，防止击穿到分片库

**常见坑**：按内容拆多个分片来分摊读压力——写入其实很少，问题在读，该加的是缓存层。

→ 详见 [评论系统](/scenario/21_comment#八、缓存)、[热点问题](/high-con/6_hotspot)

## 三、海量数据与基础能力

### Q26：海量数据的经典题怎么答？（Top K、URL 去重、UV 统计、大文件交集）

**一句话**：核心是两招：内存放不下就哈希分治，允许误差就用概率结构；先问清「能不能有误差」再选方案。

| 问题 | 方案 |
|------|------|
| 10 亿个数求 Top K | 大小为 K 的小顶堆，O(N log K)；分布式时各机求本地 Top K 再汇总 |
| 10 亿 URL 去重 | 允许漏判用布隆过滤器（0.1% 误判约 1.7GB）；精确去重用 `hash % 1000` 分治 |
| 海量 UV | HyperLogLog 每 key 约 12KB，误差约 0.81%；要精确且 ID 连续用 Bitmap |
| 两个大文件求交集 | 同一哈希函数分桶后逐对求交；或外排序 + 双指针归并；整数有限范围用位图 AND |

- 布隆过滤器的误判方向是「没见过的说成见过」：新 URL 有一定概率被当成重复丢掉，只适合允许漏少量数据的场景
- Redis 8 可直接用 `BF.*`；用作防缓存穿透时它说「不存在」就一定不存在

→ 详见 [海量数据算法题](/scenario/3_massive_data)、[海量数据架构选型](/scenario/2_big_data#五、经典海量数据问题)

### Q27：海量数据 Top K 的通用套路是什么？多台机器时怎么求？

**一句话**：先分清求「最大的 K 个数」还是「出现最多的 K 个」：前者用小顶堆扫一遍；后者先计数再用堆，计数放不下就哈希分桶；多机求频率 Top K 必须先按 key 重新分区再汇总。

- 数值 Top K：维护大小为 K 的小顶堆（堆顶是当前 K 个里最小的），新数比堆顶大才替换，O(N log K)，内存只有 K 个元素
- 频率 Top K：HashMap 计数 + 小顶堆；不同元素太多放不下，就按 `hash(key) % n` 拆成 n 个小文件，每个文件各自计数求 Top K，再合并
- 多机数值 Top K：各机本地 Top K 合起来再选一次即可，每个数只在一台机器上
- 多机频率 Top K：不能直接合并本地结果，同一个 key 散在各机，每台都不是第一、加起来却是第一；要先按 key 重新分区（shuffle），让同一 key 集中到一台
- 实时热点（秒级）用 Count-Min Sketch（近似计数）+ 堆

→ 详见 [海量数据算法题](/scenario/3_massive_data#十、top-k-的通用套路)、[堆](/algorithms/1_data_structures/4_heap)

### Q28：40 亿个整数，怎么快速判断某个数在不在？2.5 亿个整数怎么找出不重复的？

**一句话**：值域是 int 这种固定范围时用位图：每个值占 1 bit，2³² bit = 512MB，与数据有多少条无关；要区分「出现一次」和「出现多次」就每个值给 2 bit。

- 判断存在：只查一次就直接扫一遍文件；要查很多次才建 512MB 的 Bitmap，之后每次 O(1)
- 不用布隆过滤器：它的内存按元素个数算，40 亿个元素在 1% 误判下要约 4.46GB，比位图还大，还有误判
- 找不重复：2-Bitmap，`00` 没出现、`01` 一次、`10` 多次，2³² × 2 bit = 1GB；扫一遍更新状态，再输出状态为 `01` 的值
- 内存不够：按高位拆成几轮，比如按符号位分两轮，每轮位图减半，代价是数据多读一遍

**常见坑**：int 有负数，不能直接当数组下标，要先转成无符号的 long（`x & 0xFFFFFFFFL`）。

→ 详见 [海量数据算法题](/scenario/3_massive_data#五、海量整数中找不重复的整数)

### Q29：5 亿个整数、内存很小，怎么求中位数？

**一句话**：中位数就是第 k 小的数，不用排序：先按值的高位分区间只计数，找到第 k 小落在哪个区间，再只在这个区间里按低位计数一次，读两遍文件就能定位。

- 第一遍：按高 16 位把值域分成 65536 个区间，每个区间只记个数（long 数组 65536 × 8B = 512KB）
- 累加计数，找到第 k 小所在的区间，同时算出它在区间里排第几
- 第二遍：只看这个区间里的数，按低 16 位再计数一次，直接得到那个值
- 5 亿是偶数，中位数是第 2.5 亿和第 2.5 亿 + 1 小的两个数的平均值；两者通常在同一区间，可以合并成一趟
- 两个计数数组共约 1MB，数据怎么倾斜都不会爆内存

**常见坑**：有符号 int 直接按高 16 位分区，负数会排在正数后面；要先翻转符号位（`x ^ Integer.MIN_VALUE`）再分区。

→ 详见 [海量数据算法题](/scenario/3_massive_data#九、5-亿个数找中位数)

### Q30：每天几千万笔交易要和渠道账单对账，怎么比对才不会内存溢出？单边账怎么处理？

**一句话**：两份数据按交易号分片后逐片比对，先比每片的摘要、只对不一致的片比明细；靠近日切点对不上的先记「在途」，第二天再对一次仍不平才算差错。

- 2000 万条一次装进 HashMap 约 2.5GB；按 `hash(交易号) % 64` 分片后每片约 40MB，还能按片并行、按片重跑
- 两边都按交易号排好序时用双指针归并，内存只占两条记录
- 先比每片的摘要（条数 + 金额合计 + 哈希之和），一致就跳过，只对不一致的片拉明细
- 差错分长款（我方没有、渠道有）、短款（我方有、渠道没有）、金额不一致、状态不一致，先登记差错表，再自动或人工处理
- 自动补单在一个本地事务里完成认领、改单、写 Outbox；退款用固定退款单号，重试只退一次

**常见坑**：拉数据用深分页或者直接查主库，会把源库拖垮；要按主键游标分批、读从库并限速。

→ 详见 [海量数据对账](/scenario/3_reconcile#三、比对方法)

### Q31：百万行数据导出 Excel、批量导入 Excel，怎么设计才不 OOM、不超时、不重复导入？

**一句话**：都改成异步任务：导出时流式读、分批写，文件放对象存储后给下载链接；导入时先上传文件再分批解析校验，用断点行号和唯一约束保证重复导入不出错。

- 导出：提交任务后立即返回，后台按主键游标分批读从库，用 SXSSF 或 EasyExcel 分批写，内存只取决于批大小
- 单个 sheet 最多 1,048,576 行，量更大时拆 sheet 或改 CSV 并压缩；生成后上传对象存储，用预签名 URL 下载
- 每人同时只允许一个导出任务（任务表生成列 + 唯一索引），完成通知在事务提交后发送
- 导入：监听器每 1000 行一批，先做内存校验、再批量查库，合法行批量插入，错误行汇总成错误报告文件
- 幂等三层：断点行号与数据同一事务提交、文件哈希提醒重复上传、业务唯一键加唯一约束兜底

**常见坑**：MySQL 流式结果集必须用 `fetchSize = Integer.MIN_VALUE` 或开启 `useCursorFetch`，否则驱动会把结果一次性读进内存。

→ 详见 [海量数据导入导出](/scenario/3_sheet_export#二、导出整体方案)

### Q32：大文件分片上传、断点续传和秒传怎么实现？

**一句话**：浏览器直传对象存储，后端只建上传会话、签发分片预签名 URL、校验和落库；续传以对象存储的 `ListParts` 为准；秒传必须由服务端复核，不能只信客户端的哈希。

- 分片遵循 S3 协议：每片 5 MiB~5 GiB（最后一片可更小），最多 10000 片
- 前端在 Worker 里算 SHA-256，用固定数量的并发工人上传，全部完成后才请求合并
- 合并时服务端 `ListParts` 校验片数和总大小，会话状态 CAS 防并发合并
- 秒传风险：只凭哈希就能「拥有」别人的文件；要求哈希 + 大小匹配、只用服务端已校验的对象、客户端提交随机区间的持有证明，成功后只新增用户引用
- 桶上配置清理未完成分片上传的生命周期规则

→ 详见 [大文件上传](/scenario/10_file_upload)

### Q33：对外开放的 API 如何保证安全？

**一句话**：HTTPS 传输 + AppKey/Secret 签名防篡改 + timestamp 与 nonce 防重放 + 按调用方限流授权，敏感数据再做加密和脱敏。

- 签名与防重放：规范串覆盖 HTTP 方法、路径、排序后的查询串、时间戳、nonce、请求体摘要，只签参数会被挪到别的接口；原理见 [安全面试题解答 Q17](/interview/23_security#q17-开放接口为什么要「签名-时间戳-nonce」)
- 按 AppKey 限流、按接口授权、按「当前用户 + 对象 ID」防越权；涉及资金的写接口加 `Idempotency-Key` 幂等

→ 详见 [API 安全](/security/6_api_security#三、接口签名与防重放)

### Q34：扫码登录怎么设计？PC 怎么知道手机已经确认？

**一句话**：PC 展示只含随机 qrId 的二维码，已登录的手机扫码确认，服务端给 PC 新签发一个独立会话；二维码状态存 Redis，每次状态迁移用 Lua 做「比较 + 写入」。

- 状态机：等待扫描 → 已扫描 → 已确认 / 已取消，一个 key 的 TTL（如 120 秒）管所有状态的过期，不用定时任务；两部手机同时扫，只有一部能迁移成功
- PC 取结果：首选长轮询（挂起约 25 秒，小于网关常见的 60 秒读超时），跨实例用 Redis Pub/Sub 唤醒；页面已有 WebSocket 通道时可以复用推送
- 领取会话：推送和轮询只返回状态，PC 再调接口领取，领取即删 key，并校验申请二维码时下发的绑定 Cookie
- 不把手机令牌给 PC：PC 拿独立的 Web 会话，可以单独下线、按 Web 策略过期，敏感操作仍要二次验证

**常见坑**：以为绑定 Cookie 能防钓鱼扫码。攻击者在自己的浏览器打开真实登录页、把二维码转贴出去，要靠确认页展示设备和位置、异地加强校验、登录后通知来防。

→ 详见 [扫码登录](/scenario/18_qr_login#三、二维码与状态机)、[分布式会话](/distributed/5_session)

### Q35：如何设计一个消息通知中心？验证码怎么不被营销消息拖慢？

**一句话**：业务方只传模板编码、接收人和变量，通知中心按「去重落任务 → 偏好与频控过滤 → 渲染选渠道 → 按优先级入队 → 执行发送 → 回执更新状态」走完；不同优先级从队列到服务商通道全部分开。

- 任务表第一步就落库，后面每一步只推进状态，哪一步失败都能扫表补偿
- 验证码、交易、互动、营销各用一个 Topic、一个消费组、一组线程池；Kafka 和 RocketMQ 没有单条消息优先级，混在一起营销会堵住验证码
- 短信服务商账号也分开：验证码和营销用不同通道与签名，营销被运营商限速不影响验证码
- 营销任务用令牌桶匀速放量（令牌桶：按固定速率发放许可，拿到才能发），过载时先暂停营销消费
- 适配器只做协议转换和错误码归类，重试、切换、限速放在统一的执行器里

**常见坑**：让通知中心做业务判断（该不该提醒、提醒谁），最后它变成了另一个业务系统。

→ 详见 [消息通知中心](/scenario/20_notification#二、整体架构)、[优先级与隔离](/scenario/20_notification#五、优先级与隔离)

### Q36：短信服务商不稳定，发送失败怎么重试和切换？怎么避免给用户重复发？

**一句话**：先把错误分成可重试、不可重试和配置错误，只对可重试的退避重试；接两家以上服务商，按回执成功率调权重和熔断，验证码失败立即换下一家。

- 可重试：超时、5xx、限流；不可重试：空号、token 失效、退订；配置错误：模板未审核、签名不对，直接失败并告警
- 健康度要看回执成功率，不能只看接口返回：接口成功但运营商侧大面积失败很常见
- 每家服务商的模板 ID 都要提前报备好，否则切过去才发现发不出去
- 去重三层：任务表唯一键挡上游重复，状态机 CAS（只有把状态改成「发送中」成功的线程才发）挡重复消费，超时后先查服务商状态再决定是否重发

**常见坑**：调用超时就直接重发，服务商其实已受理，用户收到两条；验证码宁可重新生成一个新码再发。

→ 详见 [失败重试与供应商切换](/scenario/20_notification#八、失败重试、降级与多供应商切换)、[去重与幂等](/scenario/20_notification#七、去重与幂等)

### Q37：站内信的全员公告用写扩散还是读扩散？未读数怎么算？

**一句话**：个人消息写扩散，每个接收人收件箱一行；全员公告读扩散，只存一份，每个用户记一个「读到哪条公告」的位点，未读就是位点之后的有效公告。

| 类型 | 方式 | 原因 |
|------|------|------|
| 个人消息 | 写扩散 | 可以逐条已读、删除，读取简单 |
| 全员公告 | 读扩散 | 2 亿用户写扩散一次就是 2 亿行、约 60 GB |

- 个人未读数存 Redis Hash，按类别计；标记已读时数据库影响行数为 1 才减 1，重复点击不会减成负数
- 公告未读不存计数，用本地缓存的有效公告列表现算，再和个人未读相加
- 计数不准时以数据库 COUNT 重建，界面显示「99+」不需要精确

→ 详见 [站内信存储模型](/scenario/20_notification#十、站内信存储模型)

### Q38：通知的频控和免打扰怎么做？

**一句话**：频控分用户 × 渠道、用户 × 类别、模板、服务商四层，前三层在编排时用 Redis 计数判断，服务商限额在执行器用令牌桶；免打扰按用户时区推迟非紧急消息。

- 用户级多个窗口（1 分钟、1 小时、1 天）用一个 Lua 脚本先全部检查、再一起加 1，避免一个窗口通过另一个超限时计数已被加上
- 验证码同时按手机号、设备、IP 计数，只按手机号拦不住换号刷接口
- 验证码和交易通知不受免打扰影响；营销、互动推迟到静默结束，并随机打散，避免 8 点整同时发出
- 有时效的消息设置过期时间，推迟后已过期的直接丢弃

→ 详见 [频控与免打扰](/scenario/20_notification#六、频控与免打扰)

### Q39：延迟任务有哪些实现方案？怎么选？

**一句话**：按精度、规模、可靠性三个指标选：量小、精度低就扫表；时长固定、不用取消就用 MQ 定时消息加扫表兜底；多业务共用、要取消改期才自研延迟任务服务。

| 方案 | 精度 | 可靠性 | 适合 |
|------|------|--------|------|
| 数据库扫表 | 分钟级 | 高 | 天级提醒、兜底 |
| `DelayQueue` / 时间轮 | 毫秒级 | 低，重启即丢 | 单机超时控制 |
| Redis ZSet | 秒级 | 中，看持久化 | 中等规模 |
| RocketMQ 5 定时消息 | 秒级 | 高 | 关单这类固定时长 |

- Kafka 没有原生延迟消息，只能按档位建多个 Topic，到期前暂停消费
- Redis 过期通知不能用：事件不持久化，订阅方断线就丢

**常见坑**：MQ 定时消息发出去就撤不回，取消只能靠消费时检查业务状态。

→ 详见 [延迟任务](/scenario/23_delay_task#二、方案全景与选型)

### Q40：如何设计一个通用的延迟任务服务？千万级任务、秒级精度怎么做？

**一句话**：近远分层：所有任务落库，按到期日分区；只把未来 5 分钟要到期的任务预加载进内存时间轮，到点通过 MQ 投给业务方执行。

- 任务表：按到期日分区（历史分区直接删），按逻辑分片分库，索引是「分片 + 状态 + 到期时间」
- 预加载：每 30 秒拉一次自己负责的分片；查询不设时间下限，过期没投出去的任务会自动补上
- 投递：先发 MQ 再把状态改成「已投递」，崩溃了最多重复，不会丢
- 多实例：协调中心把分片分给各节点，各扫各的，不用全局锁
- 执行在业务方，服务只负责准时、不丢地把任务交出去

→ 详见 [延迟任务](/scenario/23_delay_task#三、自研延迟任务服务)

### Q41：时间轮是什么？和 DelayQueue 比好在哪？多级时间轮怎么工作？

**一句话**：时间轮是一个环形数组，每个槽代表一个刻度，指针每走一格就执行这一槽的任务；插入是 O(1)，比基于堆、O(log n) 的 `DelayQueue` 更适合海量定时任务。

- 精度就是一个刻度：Netty `HashedWheelTimer` 默认 100 ms 一格、512 个槽
- 超过一圈怎么办：单层轮给任务记「还剩几圈」；多级轮像钟表的时、分、秒
- 多级下沉：远期任务先放小时轮，槽到期后按剩余时间放进分钟轮，再进秒轮执行
- 纯内存、重启即丢，生产中只能做「数据库持久化 + 扫描」之上的加速层
- Kafka 内部的延迟操作、RocketMQ 5 的定时消息都基于时间轮

→ 详见 [时间轮原理](/scenario/23_delay_task#_3、时间轮原理)

### Q42：延迟任务怎么保证不丢、不重？任务取消了或大量任务同一秒到期怎么办？

**一句话**：不丢靠「数据库是唯一真相 + 先投递后改状态」，不重靠业务方执行前校验状态加幂等；取消只改库里的状态，洪峰靠限流投递和提交时打散。

- 不丢：内存时间轮只是副本，节点挂了，库里仍是「待执行」，下一轮预加载重新捞出
- 不重：到期只是「检查一下」的信号，关单用「待支付 → 已关闭」条件更新，影响 0 行就跳过
- 取消：把状态改成「已取消」，投递前再查一次状态过滤掉；和投递撞上时靠业务状态兜底
- 洪峰：按业务类型限流投递，能容忍误差的任务提交时加随机抖动，必须准点的改成「按生效时间读取」

**常见坑**：先改状态再发 MQ，发送前崩溃任务就永远丢了。

→ 详见 [关键问题](/scenario/23_delay_task#四、关键问题)

### Q43：数据更新后通知下游，服务端推送还是客户端拉取？

**一句话**：要实时用推，要稳定可控用拉，常见的是两者结合：推送负责及时，拉取负责兜底补偿。

| 维度 | 推送（MQ、WebSocket、SSE） | 拉取（轮询、定时批量拉） |
|------|---------------------------|------------------------|
| 实时性 | 高 | 取决于拉取间隔 |
| 消费节奏 | 由发送方决定，下游可能被压垮 | 由消费方控制 |
| 实现 | 需要通道和连接管理 | 简单 |

- 推送的可靠性看通道：MQ 有持久化、确认和重试，可靠性高；WebSocket、SSE 只是在线通道，断线就丢，要配 ACK 和重推
- 消费方处理能力不稳定、允许分钟级延迟、多个消费方节奏不同时用拉取
- 推拉结合：变更时推一条通知，下游再按版本号拉最新数据，错过通知就靠定时拉取补齐

→ 详见 [Feed 流和消息推送](/scenario/8_feed_stream#七、在线推送)、[消息队列基础](/messaging/1_basics)

### Q44：面试时项目的亮点和难点怎么讲？

**一句话**：按「背景（规模与问题）→ 方案（为什么选它而不是别的）→ 实现细节（难点与坑）→ 量化结果（前后对比）」四步讲，数字用自己项目的真实数据。

- 好的亮点方向：缓存与一致性（先更新数据库再删缓存 + binlog 兜底，不要说成「先删缓存再延迟双删」）、热点治理（本地缓存 + 多副本 key，写时更新全部副本并容忍短暂不一致）、防超卖（Lua 原子扣减 + 数据库条件更新）、异步削峰、慢 SQL 治理、冷热归档
- 一致性方案要讲准：Seata AT 是全局锁 + 默认读未提交，不适合热点库存；MQ 消费去重用业务键而不是 msgId，去重记录与业务写入同一本地事务
- 分库分表迁移：双写只是一步，还要讲以哪边为准、增量追平（binlog 同步）、对账校验、灰度切读和回滚开关
- 被问「你具体做了什么」：讲清自己的职责边界，「我负责了 X 模块的设计与实现」比「我设计了整个系统」更可信
- 被问「重来会怎么改」：诚实指出当前方案的局限和更好的选择，体现反思

**常见坑**：只罗列技术名词不讲取舍；数字前后矛盾或明显夸大（如单机 Redis 扛百万 QPS）；把通用八股当项目难点。

→ 详见 [项目难点与亮点面试题解答](/interview/16_scenario_highlights)（18 个亮点的逐题讲法）、[分库分表与中间件](/database/5_practice/3_sharding#八、平滑迁移与扩容)

### Q45：拿到一道系统设计题，你会怎么推进？

**一句话**：先广后深，按「需求澄清 → 容量估算 → 接口设计 → 数据模型 → 高层架构 → 深入瓶颈 → 扩展与取舍」七步走，前 20 分钟对齐问题和数字，后面才挑重点深入。

- 需求澄清：问清核心 2–3 个功能和规模，明确哪些不做
- 容量估算：只估峰值读写 QPS 和存储的数量级，每个数字都落到一个决策
- 接口与数据模型：只列主链路接口，表结构由查询反推
- 高层架构：先画最简可跑通的方案，再按瓶颈逐个加组件
- 深入与取舍：挑 1–2 个瓶颈讲到命令和失败处理，最后讲规模扩大 10 倍和故障时怎么办

**常见坑**：题目一出就开始画架构图，后面的设计没有依据，被追问时只能推翻重来。

→ 详见 [系统设计方法论](/scenario/1_design_method#二、答题流程总览)

### Q46：需求澄清阶段要问哪些问题？

**一句话**：问三类：功能（做什么、不做什么）、非功能（规模、延迟、一致性、可用性）、约束（已有技术栈、工期、外部依赖），最后把结论复述一遍再往下走。

- 功能：核心用例是什么，读路径和写路径分别是什么，有没有搜索、统计这类派生需求
- 规模：DAU、读写比、峰值是均值的几倍，这决定要不要缓存和分库
- 一致性：写完能不能立刻读到，能不能接受几秒延迟，这决定缓存和同步异步
- 准确性与可用性：能否丢数据或重复（计数能否有误差），目标几个 9、哪些功能可以降级

**常见坑**：只问功能不问规模，结果给日活 1 万的系统设计了分库分表和多活。

→ 详见 [系统设计方法论](/scenario/1_design_method#三、需求澄清)

### Q47：系统设计中的容量估算怎么做？要记哪些数量级？

**一句话**：一天按 10⁵ 秒算，1 亿次 / 天约 1000 QPS，再乘峰值系数；目的是做决策（要不要分库、加几个分片），不是算准数字。

- 峰值 QPS = 日请求量 ÷ 86400 × 峰值系数（日常 2–5 倍，大促 10–100 倍）
- 存储 = 日增条数 × 单条大小 × 保留天数 × 副本数，再乘 1.3–2 留给索引和余量
- 带宽：1 Gbps 约 125 MB/s，大文件交给 CDN 和对象存储

| 对象 | 数量级 |
|------|--------|
| 业务接口单机 | 1000–5000 QPS |
| Redis 单分片 | 约 10 万 ops/s |
| MySQL 单主写入 / 单表 | 数千 TPS / 千万级行 |

→ 详见 [系统设计方法论](/scenario/1_design_method#四、容量估算)

### Q48：设计时什么时候该加缓存、MQ、分库分表、搜索引擎？

**一句话**：从「客户端 → 网关 → 无状态服务 → 数据库」的最简方案出发，估算哪里扛不住就加对应的组件，每个组件都要能说出它解决的是哪个数字。

- 缓存：读 QPS 远超数据库能力、读多写少时加，同时说清一致性策略
- MQ：写入有突发峰值，或一个动作要触发多个下游时加，用来削峰和解耦
- 分库分表：写 TPS 或单表行数超过单机能力时加，分片键要让最高频查询落在单分片
- 搜索引擎：需要模糊查询或按非分片键做多条件组合查询时加

**常见坑**：一开始就把 Kafka、ES、分库分表全堆上，却说不清日活 10 万的系统为什么需要它们。

→ 详见 [系统设计方法论](/scenario/1_design_method#六、高层架构与组件选型)

### Q49：系统设计面试中常见的失分点有哪些？怎么讲取舍？

**一句话**：最常见的是跳过澄清、只有名词没有细节、只讲正常路径；讲取舍要用「选 A 是因为 X，代价是 Y，用 Z 兜底」的句式。

- 估算不落到决策：算出数字后要接一句「所以单库够用 / 所以要分片」
- 只有名词：「用 Redis」要讲到 key 结构、命令和失败时怎么办
- 只讲正常路径：每一步都问自己重复请求、消息丢失、节点宕机时会怎样
- 过度设计：方案要和估算出的规模匹配

| 取舍 | 怎么选 |
|------|--------|
| 一致性 vs 可用性 | 资金、库存选一致；计数、Feed 选可用 |
| 推 vs 拉 | 普通用户推，大 V 拉 |

→ 详见 [系统设计方法论](/scenario/1_design_method#九、常见失分点)

## 五、场景速答

### Q50：订单 11:00 超时关单，支付恰好在 11:00 成功，听谁的？

**一句话**：听状态机的：关单和支付成功都用「`WHERE status = 待支付`」的条件更新改订单，谁先改成功谁说了算；输的一方走补偿，关单输了就当正常支付，支付输了就自动退款。

- 条件更新谁先谁赢：两条 `UPDATE` 只可能有一条影响 1 行，不需要加锁，也不会出现两边都成功
- 渠道过期时间早于本地关单时间：下单时传给渠道的过期时间比本地关单早 1～2 分钟，到 11:00 渠道已不再收款，绝大多数并发窗口直接消失
- 支付成功消息到达时订单已关闭：不改订单状态，按原路自动退款并通知用户
- 业务允许的话，也可以在库存还够时把已关闭订单「复活」，但要重新占库存，规则要提前定好

**常见坑**：关单只改本地不关渠道，关单顺序见 [Q7](#q7-如何设计一个支付系统-超时关单和对账怎么做)。

→ 详见 [支付](/scenario/14_payment#_2、超时关单)、[订单](/scenario/5_order_system#五、支付回调)

### Q51：同一笔支付单，用户在两个渠道几乎同时付了款，怎么办？

**一句话**：支付单只认第一笔成功的交易单，后到的那笔记为「重复支付」并原路退款；这种情况前端拦不住，要靠服务端兜底。

- 两层模型：支付单对应业务的一次收款，每换一次渠道新建一张交易单，一张支付单可以有多张交易单
- 认第一笔：支付单用 `UPDATE ... SET success_trade_no = ? WHERE status = 'WAITING'` 条件更新，影响 1 行的那笔胜出
- 后到的成功交易单进差错池，自动发起原路退款，并通知用户
- 尽量少发生：发起新渠道支付前，先关闭同一支付单下还未支付的旧交易单

→ 详见 [支付：两层模型](/scenario/14_payment#_1、两层模型)、[回调幂等](/scenario/14_payment#_3、回调幂等-渠道流水号唯一约束-条件更新)

### Q52：峰值 3000 QPS、RT 200ms，要几台机器？

**一句话**：先用 Little 定律算「同时在处理的请求数」，再用压测得到的单机容量算台数，最后乘故障冗余；公式只给量级，最终以压测为准。

- Little 定律：并发数 = QPS × RT = 3000 × 0.2s = 600，任一时刻约有 600 个请求在处理中
- 线程维度：单机 200 个工作线程且以等待 IO 为主，600 / 200 = 3 台只是理论下限
- CPU 维度：每个请求真正耗 CPU 20ms，4 核满载约 4 / 0.02 = 200 QPS，按 70% 水位取 140 QPS，需要 3000 / 140 ≈ 22 台
- 取两个维度里更大的结果，并核算数据库连接、Redis 等下游是否扛得住；冗余系数算法见 [高并发 Q40](/interview/13_high_con#q40-如何评估单机能力-需要多少台机器-多可用区部署时冗余系数怎么算)

**常见坑**：只用线程数算台数，忽略 CPU 和下游连接池；把 RT 平均值当成 P99 用。

→ 详见 [Little 定律](/high-perf/1_metrics#四、指标之间的关系-little-定律)、[机器数计算](/high-con/8_capacity_planning#三、机器数计算)

### Q53：一台 4C8G 的 Java 服务，CPU、Load、GC、RT 多少算正常？

**一句话**：没有放之四海皆准的数字，要和自己的基线比；经验上峰值 CPU 不超过 70%，Load 不超过核数，Young GC 停顿几十毫秒、Full GC 几乎不出现，P99 在 SLA 以内。

- CPU：平时 30%～50%，峰值 ≤ 70%，给扩容和突发留余量；容器里还要看是否被 CPU limit 限流
- Load：长期小于核数（4）为宜；Load 高但 CPU 低，多半是一批任务卡在不可中断的 IO 等待里（D 状态，如磁盘、NFS）
- 内存与 GC：堆一般占容器内存的 50%～75%（如 `-XX:MaxRAMPercentage=70`），Young GC 间隔秒级以上、单次几十毫秒，Full GC 按天计甚至没有
- RT：看 P99 而不是平均值，和压测基线比，突然上涨比绝对值更值得关注

→ 详见 [Linux 速查：负载与 CPU](/handbook/1_cheatsheet/0_linux#一、负载与-cpu)、[Load 高但 CPU 不高](/handbook/2_incidents/18_load_high_cpu_low)、[各资源的水位指标](/high-con/8_capacity_planning#_3、各资源的水位指标)

### Q54：已经「加锁 → 查询 → 更新」了，为什么还是出现了重复数据？

**一句话**：锁只保证「同一时刻只有一个人在里面」，但锁和事务、锁和数据可见性之间有缝隙，常见的是锁先于事务提交被释放、锁过期、读到了旧数据。

- 锁在事务里面：解锁时事务还没提交，下一个线程拿到锁去查，看不到上一个人刚插入的数据
- 锁过期：业务执行时间超过锁的租期，锁自动释放，另一个实例也进来了
- 读旧数据：可重复读下事务快照在加锁前就建好了，或者查询走了有延迟的从库
- 锁的 key 粒度不对：两个请求用了不同的 key，根本没互斥
- 根治：加锁包在事务外面，最终用唯一约束或条件更新兜底，锁只负责串行化，不负责正确性

→ 详见 [分布式锁只做串行化](/architecture/3_idempotence#八、分布式锁-只做串行化)、[分布式锁常见坑](/distributed/3_lock#七、常见坑)

### Q55：表用逻辑删除，唯一约束怎么建？

**一句话**：唯一约束要「只约束未删除的行」；MySQL 没有部分索引，常用两种做法：删除标记存一个不重复的值，或用生成列把已删除行变成 NULL。

- 删除标记存 ID：`deleted` 未删除时为 0、删除时写成主键 ID，唯一键建在 `(email, deleted)` 上，删多少次都不冲突
- 生成列：`active_email AS (IF(deleted = 0, email, NULL))` 上建唯一索引，NULL 不参与唯一性比较
- PostgreSQL 直接用部分唯一索引：`CREATE UNIQUE INDEX ... (email) WHERE deleted_at IS NULL`
- 恢复已删除数据时要先检查是否已有同值的新数据，否则恢复会撞唯一键

**常见坑**：`deleted` 只有 0 / 1 两个值时放进唯一键，同一个邮箱只能删除一次，第二次删除就冲突。

→ 详见 [生成列与函数索引](/database/1_mysql/1_feature#_2、生成列与「函数索引」)、[唯一约束](/architecture/3_idempotence#三、唯一约束-插入类操作)

### Q56：为什么不要在数据库事务里调用外部服务？

**一句话**：网络调用又慢又不可控，放在事务里会一直占着数据库连接和行锁；而且事务回滚撤不回已经发生的远程调用，反而制造不一致。

- 占资源：外部接口慢 3 秒，这期间连接和行锁都不释放，并发一高连接池耗尽、其他请求锁等待超时
- 回滚不了：调用成功后本地事务回滚，对方已经扣款、发货，两边对不上
- 超时最难办：调用超时不知道对方成没成，事务提交还是回滚都不对
- 正确拆法：事务一写「处理中」并提交 → 事务外调用外部服务 → 事务二按结果条件更新；要求可靠送达时用本地消息表，结果不明由查单任务补偿

→ 详见 [大事务故障](/handbook/2_incidents/7_big_transaction#_5、事务为什么迟迟不提交)、[本地消息表](/distributed/4_transaction#五、本地消息表-transactional-outbox)

### Q57：依赖的第三方接口不稳定，怎么保护自己？

**一句话**：把它当成随时会慢、会挂的依赖来设计：严格超时、有限重试、资源隔离、熔断降级，再加异步补偿和对账兜底。

- 超时：连接超时和读取超时都要设，读取超时参考对方的 P99，不要用默认的无限等待
- 重试：只重试幂等或带请求号的调用，指数退避加随机抖动，限制重试比例，防止放大流量
- 隔离：给它单独的线程池或信号量配额，它慢了只拖垮自己那一格，不影响其他接口
- 熔断与降级：错误率或慢调用比例超过阈值就熔断，返回缓存、默认值或「处理中」
- 结果不确定时异步查询补偿，日终按对方账单对账

→ 详见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)、[熔断策略与阈值](/high-avail/5_circuit_breaking#三、熔断策略与阈值)

### Q58：把接口开放给合作方调用，要考虑哪些问题？

**一句话**：对方是你控制不了的外部系统，要做到四件事：认得出是谁（签名）、重复调用不出错（幂等）、调用量可控（限流配额）、升级不坑人（版本管理）。

- 签名与防重放：每个合作方一对 AppKey 和密钥，做法见 [Q33](#q33-对外开放的-api-如何保证安全)
- 幂等：写接口要求带合作方请求号，`(app_key, request_no)` 唯一，重复请求返回第一次的结果
- 限流与配额：按 AppKey 分别限流，超限返回 429 和建议的重试时间，防止一个合作方拖垮所有人
- 版本：URL 或请求头带版本号，只做兼容变更；破坏性变更出新版本，并提前公告旧版本下线时间
- 其他：回调同样要签名和重试，加 IP 白名单、调用审计日志，提供沙箱环境

→ 详见 [接口签名与防重放](/security/6_api_security#三、接口签名与防重放)、[API 版本管理](/engineering/4_api_design_rule#八、版本管理)

### Q59：敏感词过滤怎么做？

**一句话**：把所有敏感词建成 Trie，再加失配指针变成 AC 自动机，文本只扫一遍就能找出全部命中的词；真正的难点在变形词和词库热更新。

- 为什么不逐个 `contains`：词库上万条时每段文本要扫上万遍；AC 自动机的耗时只和文本长度、命中次数有关
- 先归一化再匹配：全角转半角、统一大小写、繁简转换、跳过夹在中间的空格和符号，对付「敏 感 词」这类变形
- 热更新：后台改词库后在新对象上重建自动机，再用 `volatile` 引用整体替换，匹配过程不加锁
- 配白名单减少误伤；图片、语音和语义类违规交给专门的内容审核服务

→ 详见 [Trie 应用场景](/algorithms/1_data_structures/6_trie#三、应用场景)

### Q60：几百万会员要在到期前 3 天提醒，用什么方案？

**一句话**：精度要求是「天」，最简单可靠的是每天定时分片扫描到期日索引；延迟消息、Redis ZSet 更适合精确到秒、数量可控的延迟任务。

| 方案 | 适合 | 问题 |
|------|------|------|
| 定时扫描 | 天级精度、数据量大 | 要分片、走索引 |
| MQ 延迟消息 | 秒级精度 | 最大延迟受 Broker 配置限制；到期日变了要作废旧消息 |
| Redis ZSet | 秒级精度、量可控 | 全放内存，取出和删除要用 Lua 保证原子 |

- 扫描：按 `expire_date` 建索引，调度框架分片，每片按主键游标批量取，投到 MQ 由消费者限速发送
- 幂等：发送记录以 `(member_id, 到期周期)` 唯一，任务重跑不会重复提醒；续费后到期日变了自然不再命中

→ 详见 [延迟任务方案对比](/scenario/23_delay_task#二、方案全景与选型)、[调度分片](/distributed/6_job_scheduler#_3、分片)

### Q61：一个账户被多个订单同时扣款，怎么防止扣成负数？

**一句话**：不要「先查余额再扣」，而是用一条条件更新把校验和扣减合在一起：`UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?`，影响 0 行就是余额不足。

- 条件更新靠行锁串行执行，并发再高也不会扣成负数，不需要额外的分布式锁
- 防重复扣：扣款流水以 `(account_id, biz_order_no)` 唯一，和扣减放在同一事务里
- 先冻结后扣：下单时冻结金额（可用 = 余额 - 冻结），支付成功再扣，取消就解冻
- 热点账户（如平台收款账户）写入特别频繁时：拆成多个子账户分摊，或先记流水再定时汇总入账

→ 详见 [条件更新](/architecture/3_idempotence#四、条件更新-状态机与版本号)、[写热点](/high-con/6_hotspot#三、写热点-热点行更新)

### Q62：几百万个酒店房价要在早上 7:00 准时变更，怎么做？

**一句话**：别等到 7:00 才开始改几百万行，而是提前把新价格写好并带上生效时间；到点只是「切换版本」，读价时按当前时间选生效的那一版。

- 价格带生效时间：查询取 `effective_at <= now` 的最新一条，到点自然生效，不需要集中批量更新
- 提前预热：新版本价格提前写入缓存，缓存 key 带版本号，到点切换「当前版本」指针
- 下游（分销渠道、搜索索引）提前分片推送带生效时间的数据，避免 7:00 集中推送
- 兜底：7:00 后抽样核对各端价格，切换开关可以回滚到旧版本

→ 详见 [缓存预热](/high-con/3_cache_architecture#三、缓存预热)、[同一时刻大量到期](/scenario/23_delay_task#_5、大量任务同一时刻到期)

### Q63：怎么按手机号后 4 位查询？

**一句话**：`LIKE '%1234'` 是左模糊，用不上索引；把后 4 位单独存一列（或建生成列）再加索引，查询就变成等值匹配。

- 冗余列：写入时同时存 `phone_last4` 并建索引，查询 `WHERE phone_last4 = '1234'`
- 生成列：`phone_last4 CHAR(4) AS (RIGHT(phone, 4)) STORED` 加索引，应用层不用改写入逻辑
- 后 4 位区分度低：只有 1 万种取值，最好和其他条件（如姓名、日期）组成联合索引
- 手机号加密存储时：为后 4 位单独建一个盲索引（HMAC），只支持精确匹配

→ 详见 [生成列与函数索引](/database/1_mysql/1_feature#_2、生成列与「函数索引」)、[盲索引](/security/7_data_security#盲索引-加密后仍能精确查询)

### Q64：登录失败次数怎么限制？怎么把已登录的用户踢下线？

**一句话**：失败次数要同时按账号和按 IP 计数，逐步加验证码、延迟、临时锁定；踢下线就是让服务端的会话失效，JWT 则要配合版本号或黑名单。

- 计数：Redis 按 `login:fail:{account}` 和 `login:fail:{ip}` 计数并设过期时间，登录成功清零
- 渐进处理：失败 3 次加验证码，再多就临时锁定 15 分钟，不做永久锁定，避免攻击者故意把正常用户锁死
- 会话方案踢人：删除 Redis 里的会话；Spring Security 用 `maximumSessions(1)` 限制同时在线数
- JWT 踢人：用户表存 token 版本号，踢人时加 1、校验时比对；或把 `jti` 放进黑名单直到令牌过期

→ 详见 [限流、锁定与撞库](/security/1_authentication#_4、限流、锁定与撞库)、[分布式会话](/distributed/5_session)

### Q65：压测能扛 600 QPS，上线 300 QPS 就出问题了，为什么？

**一句话**：压测环境和生产不一样：数据量、流量结构、缓存状态、下游都不同，600 是在「理想条件」下测出来的。

- 数据量：测试库只有几万行，生产几千万行，同一条 SQL 的执行时间能差几个数量级
- 流量结构：只压了单个接口，生产是多个接口混合，还有慢接口、定时任务一起抢连接池
- 缓存与热点：压测数据少、命中率高；生产冷数据多，或者请求集中在少数热点 key
- 下游被 Mock：压测时依赖接口秒回，生产上下游一慢就占满线程
- 其他：压测前 JIT 已经预热，生产刚发布就接全量流量；日志量、网络带宽也不一样

→ 详见 [全链路压测与影子库](/high-con/8_capacity_planning#五、全链路压测与影子库)

### Q66：批量扫描处理数据，为什么总有一部分被跳过？

**一句话**：用 `LIMIT offset, n` 翻页，同时又在修改作为查询条件的字段，处理完的行从结果集里消失，后面的行整体前移，下一页的 offset 就跳过了一批。

- 例子：`WHERE status = 0 LIMIT 1000, 500`，处理完把 status 改成 1，剩下的行往前挪，从第二页起漏行
- 改用主键游标：`WHERE status = 0 AND id > #{lastId} ORDER BY id LIMIT 500`，每批记下最后一个 id
- 游标翻页还顺带解决了深分页越翻越慢的问题
- 处理逻辑要幂等，任务中断后从上次的 lastId 继续

→ 详见 [游标翻页](/database/1_mysql/4_topic_index#_3、方案三-游标翻页-适合「下一页」场景)、[深分页故障](/handbook/2_incidents/9_deep_paging)

### Q67：IP 地址在数据库里怎么存？

**一句话**：IPv4 存成 4 字节无符号整数，IPv6 存成 16 字节二进制；比字符串省空间、比较快，还能做网段范围查询。

- IPv4：`INT UNSIGNED`，用 `INET_ATON()` / `INET_NTOA()` 转换；字符串形式最长 15 个字符，整数只要 4 字节
- IPv6 或两者混存：`VARBINARY(16)`，用 `INET6_ATON()` / `INET6_NTOA()` 转换
- 范围查询：IP 归属地库按 `(start_ip, end_ip)` 整数区间存，查询时直接做数值比较
- 只用来记日志、不做范围查询时，存字符串也可以，可读性更好

→ 详见 [索引设计原则](/database/1_mysql/4_topic_index#十、索引设计原则)
