# 业务场景面试题解答

> 题目清单见 [业务场景面试题](/scenario/99_interview)；细节见 [业务场景总览](/scenario/0_overview)。
>
> 版本基线：JDK 21、Spring Boot 4、Redis 8.x、RocketMQ 5.x（兼顾 4.x）、MySQL 8.4 LTS、ShardingSphere 5.5、Elasticsearch 9.x、Flink 2.x。
>
> 系统设计题的答法：先用一句话说清核心思路，再讲 3~5 个关键设计决策，每个决策说明它解决哪个瓶颈，最后主动讲坑和兜底。单项技术（锁、事务、幂等、缓存一致性）只点到为止，展开见对应的答案页。

## 一、交易类

### Q1：如何设计一个秒杀系统？

**一句话**：逐层拦截，让流量像漏斗一样越往下越少：CDN 拦静态请求，网关拦超频和脚本，本地售罄标记拦售罄后的请求，Redis 拦超出库存的请求，数据库只承接预扣成功的那部分。

- 页面静态化 + CDN：开抢前页面请求不回源，解决静态资源压垮应用的问题
- 防刷与限流：一次性下单 token、验证码把瞬时峰值拉平到几秒，网关按用户和接口总量限流，解决脚本和超出容量的流量
- Redis 预扣：一个 Lua 脚本完成限购校验、扣库存、记已购，解决数据库单行锁扛不住瞬时并发的问题
- MQ 异步下单：预扣成功后同步发消息、返回「排队中」，订单服务按自己的能力消费，解决写库峰值
- 结果查询：用户按 orderId 轮询结果；超时未支付由定时消息关单并回补库存

**常见坑**：只讲 Redis 扣库存，不讲 Redis 与 MQ 之间的一致性（发送失败要回补、崩溃要对账），也不讲售罄标记在回补后要清除。

→ 详见 [秒杀系统设计](/scenario/4_seckill#二、整体链路)

### Q2：秒杀如何防超卖？Redis 预扣成功但 MQ 发送失败或进程崩溃，怎么避免少卖？

**一句话**：防超卖靠原子扣减：Redis 用 Lua 判断库存再扣，数据库用 `WHERE stock >= n` 条件更新兜底；分布式锁不是防超卖的主手段。少卖靠回补和对账。

- 限购和扣库存放进同一个 Lua 脚本：分两次调用会出现「记了已购、库存没扣到」的中间状态
- key 不存在时 Lua 里 `GET` 返回 false，要先判断；Cluster 下用 `{activityId}` hash tag 保证所有 key 同槽
- 同步发送 MQ，失败就执行回补脚本（以 `SREM` 成功为条件，可重复执行）并广播清除各实例的售罄标记
- 进程在预扣后、发送前崩溃：定时对账比较「已购集合」和订单表，核对「剩余 + 已售 = 初始库存」；要零丢失就改用 Outbox
- 消费端在一个本地事务里先插订单（唯一约束 `user_id + activity_id`），再条件扣数据库库存，重复消息撞唯一键即视为已处理

**常见坑**：单个库存 key 打满一个分片时，要拆成分桶库存，见 [热点问题](/high-con/6_hotspot#_3、分桶库存)。

→ 详见 [秒杀系统设计](/scenario/4_seckill#四、库存预扣-防超卖核心)

### Q3：下单如何做幂等和库存预占？订单流程里 Seata、事务消息、Outbox 怎么选？

**一句话**：下单以业务单号（`biz_no`）唯一约束兜底，库存和优惠券预占也按 `biz_no` 幂等；一个流程只选一种分布式事务方案，按「是否必须同步知道结果」来选。

- 下单（库存、优惠券）：必须同步知道成败，用幂等预占（TCC 思路：下单 Try 预占、支付后 Confirm、关单 Cancel），悬挂预占靠扫描释放
- 支付成功 → 发货、积分：最终一致，用 Outbox 或 RocketMQ 事务消息二选一
- Seata AT 只用于内部、低并发、要同步整体回滚的流程；它是最终一致而非强一致，注意全局锁的写阻塞和默认读未提交
- 订单状态只靠 `WHERE status = 旧状态` 的条件更新流转，状态机本身就防并发，不需要再加 version

**常见坑**：一个流程同时套 Seata 全局事务和事务消息，边界不清，出了问题不知道该谁回滚。

→ 详见 [订单系统设计](/scenario/5_order_system#五、分布式事务-按流程选一种)、[分布式面试题解答](/interview/10_distributed#三、分布式事务)

### Q4：订单超时关单有哪些方案？关单与释放库存如何原子化？

**一句话**：推荐「RocketMQ 5.x 定时消息 + 定时扫描兜底」：定时消息精确，扫描兜住发送失败和消息丢失；关单用状态条件更新，影响 1 行才释放库存。

| 方案 | 评价 |
|------|------|
| 定时扫描 | 简单可靠，有分钟级延迟，适合兜底 |
| RocketMQ 5.x 定时消息 | 精确可靠；4.x 只有 18 个固定级别，没有 15 分钟 |
| RabbitMQ 延迟插件 / TTL + 死信 | 可用；TTL 方案有队头阻塞 |
| Redis 过期通知 | 通知不持久化、订阅方断开即丢，不能用于关单 |
| 内存时间轮 | 重启丢失，只能配合持久化与扫描 |

- 定时消息在事务提交后发送（`@TransactionalEventListener(AFTER_COMMIT)`），否则会出现回滚后消息照发、或提交前就被消费查不到订单
- 关单先调支付平台的关单接口，再在一个事务里条件更新订单并写释放库存事件；库存侧按预占记录状态只释放一次

→ 详见 [订单系统设计](/scenario/5_order_system#四、超时关单)

### Q5：支付回调如何保证幂等与安全？

**一句话**：先验签并核对金额、商户号与本地一致，再用支付单 `WAITING → SUCCESS` 条件更新做幂等，后续动作通过 Outbox 事件异步触发，回调本身只做校验和落库、快速应答。

- 只验签不校验金额和商户号，可能被别的订单或低金额的合法通知冒充
- 支付宝成功状态是 `TRADE_SUCCESS` / `TRADE_FINISHED`，应答纯文本 `success`；微信支付 APIv3 返回 200 或 204
- 支付流水号建唯一约束；重复通知、通知与主动查单并发都只影响 0 行，不需要分布式锁
- 订单已关闭又收到支付成功：自动退款或转人工，不能忽略
- 通知可能丢失：定时查询「待支付且已发起支付」的订单，调用同一个处理入口

→ 详见 [订单系统设计](/scenario/5_order_system#三、支付回调)、[幂等设计](/architecture/5_idempotence#_2、支付回调)

### Q6：抢红包系统如何设计？怎么保证不超发、不少发、可靠入账？

**一句话**：发红包时扣款、流水、红包和全部份额在一个本地事务里落库，提交后装载到 Redis；抢红包用一个 Lua 脚本原子完成判关闭、判重、弹出份额、记领取；入账用事务消息保证必达，过期先关闭再对账后退款。

- 金额分配用二倍均值法：每次在 `[1, 剩余均值 × 2 - 1]` 分内随机，最后一人拿剩余；金额全程用「分」
- 份额可预先拆好存成 List，抢的时候只弹出，不在抢的瞬间计算
- 入账：RocketMQ 事务消息的本地事务就是执行 Lua，回查看领取记录，不确定时返回 `UNKNOWN`
- 消费端以 `(packet_id, user_id)` 唯一约束去重，领取记录、份额状态、余额、流水在同一本地事务
- 退款不能直接用「总额减已领」：先关闭红包 → 等待在途领取完成 → 对账补齐 → 条件更新状态后退未领份额

→ 详见 [抢红包系统设计](/scenario/11_red_packet)

## 二、读写模型类

### Q7：如何设计一个短链接系统？跳转用 301 还是 302？

**一句话**：发号器生成自增 ID，做可逆混淆后 Base62 编码成短码；跳转走缓存，需要统计点击就用 302；点击量走 Redis 计数和 OLAP 明细，不放主表。

- 短码生成：发号器 + Base62 无冲突（6 位约 568 亿个），先混淆 ID 防止被顺序枚举；哈希方案必然冲突，要靠唯一约束 + 比较原 URL + 加盐重试
- 同一长链去重：按 `long_url_hash` 建索引查重
- 缓存：生成时预热，空值缓存防穿透；主从延迟下从库查不到要再查一次主库，再写空值
- 状态码：301 会被浏览器缓存，之后统计不到；需要统计用 302 加 `Cache-Control: no-store`；目标是 POST 接口用 307
- 安全：只允许 http / https，接入恶意网址检测

→ 详见 [短链接系统设计](/scenario/6_shorturl)

### Q8：排行榜如何设计？同分时怎么让先达到的人排前面？

**一句话**：实时榜用 ZSet（`ZINCRBY` 加分、`ZRANGE ... REV` 取 Top N、`ZREVRANK` 查名次），日周月榜每个时段一个 key；同分先到先得要把「分数 + 时间」编码进一个 score。

- 组合 score：分数 × 10^7 + (10^7 − 1 − 活动开始后的秒数)，必须小于 2^53，否则 double 丢精度；用 Lua 读改写更新
- 时段 key 用 `EXPIREAT` 设绝对过期时间，过期前由分布式调度归档到 MySQL
- 亿级用户的单 key 是大 key：分片后 Top N 归并、名次用 `ZCOUNT` 求和，或只维护头部榜
- 积分增减：条件更新余额 + 流水唯一键去重，同一本地事务；榜单在提交后更新，定时对账兜底

→ 详见 [排行榜 & 积分系统设计](/scenario/7_rank_system)

### Q9：Feed 流推模式、拉模式、推拉结合怎么选？分页为什么不能用 offset？

**一句话**：推模式（写扩散）读最快但大 V 发布要写几千万个收件箱；拉模式（读扩散）写简单但关注越多读越慢；粉丝分布极不均的平台用推拉结合：普通作者推，大 V 只写发件箱，浏览时归并去重。

| 维度 | 推模式 | 拉模式 | 推拉结合 |
|------|-------|-------|---------|
| 读性能 | 最快 | 关注越多越慢 | 快 |
| 写放大 | 粉丝数倍 | 无 | 只对普通作者 |

- 收件箱用 ZSet，只保留最新 N 条，更早的回源内容表
- 翻页用游标（上一页最后一条的 score，开区间）：新内容不断插入，offset 会导致重复和漏读
- 扇出走「本地消息表 + MQ + 批量管道写」，`ZADD` 天然幂等；不要用进程内线程池发后不管

→ 详见 [Feed 流 & 消息推送系统设计](/scenario/8_feed_stream)

### Q10：搜索系统如何设计？MySQL 数据怎么同步到 ES 并防止乱序？

**一句话**：面向用户的商品搜索用 Elasticsearch；数据走「binlog CDC → MQ → 同步消费者 → ES」，按商品 ID 分区、回查数据库、用外部版本号写入防乱序。

- MySQL ngram 全文索引能用但分词质量、相关性调优、分面和扩展性都不足
- 索引带版本号，业务只访问别名；关键词放 `must`，筛选条件放 `filter`
- 防乱序：消费者回查数据库拿最新行，用外部版本号写 ES，旧版本被拒（409 忽略）
- 零停机重建：先起新消费组写新索引，再全量导入（导入时 `refresh_interval -1`、副本 0），验证后原子切换别名

→ 详见 [搜索系统设计](/scenario/9_search_system#四、数据同步-mysql-→-es)

### Q11：「附近的人」怎么做？Geohash 有什么边界问题？

**一句话**：Redis GEO 按城市分 key 存位置，再配一个上报时间 ZSet；查询多取一些再按新鲜度、可见性过滤，定时清理过期成员。

- GEO 底层就是 ZSet + Geohash 编码，`GEOSEARCH ... BYRADIUS` 按半径查
- Geohash 边界问题：两个点很近却落在不同格子里，只查自己的格子会漏；要查周围九宫格，再按实际距离过滤
- 不可见是持久的用户设置，上报时检查、查询时再过滤
- 隐私：对外只给模糊距离还不够（可多点三边定位），要做网格吸附、限制查询中心、限流
- 打车派单：状态与位置在同一个 Lua 里判断并原子占用司机，再数据库条件更新落地，避免一个司机被派两单

→ 详见 [附近的人 & LBS 地理位置设计](/scenario/12_geo_nearby)

## 三、海量数据与基础能力

### Q12：海量数据的经典题怎么答？（Top K、URL 去重、UV 统计、大文件交集）

**一句话**：核心是两招：内存放不下就哈希分治，允许误差就用概率结构；先问清「能不能有误差」再选方案。

| 问题 | 方案 |
|------|------|
| 10 亿个数求 Top K | 大小为 K 的小顶堆，O(N log K)；分布式时各机求本地 Top K 再汇总 |
| 10 亿 URL 去重 | 允许漏判用布隆过滤器（0.1% 误判约 1.7GB）；精确去重用 `hash % 1000` 分治 |
| 海量 UV | HyperLogLog 每 key 约 12KB，误差约 0.81%；要精确且 ID 连续用 Bitmap |
| 两个大文件求交集 | 同一哈希函数分桶后逐对求交；或外排序 + 双指针归并；整数有限范围用位图 AND |

- 布隆过滤器的误判方向是「没见过的说成见过」：新 URL 有一定概率被当成重复丢掉，只适合允许漏少量数据的场景
- Redis 8 可直接用 `BF.*`；用作防缓存穿透时它说「不存在」就一定不存在

→ 详见 [海量数据处理](/scenario/2_big_data#五、经典海量数据问题)

### Q13：大文件分片上传、断点续传和秒传怎么实现？

**一句话**：浏览器直传对象存储，后端只建上传会话、签发分片预签名 URL、校验和落库；续传以对象存储的 `ListParts` 为准；秒传必须由服务端复核，不能只信客户端的哈希。

- 分片遵循 S3 协议：每片 5 MiB~5 GiB（最后一片可更小），最多 10000 片
- 前端在 Worker 里算 SHA-256，用固定数量的并发工人上传，全部完成后才请求合并
- 合并时服务端 `ListParts` 校验片数和总大小，会话状态 CAS 防并发合并
- 秒传风险：只凭哈希就能「拥有」别人的文件；要求哈希 + 大小匹配、只用服务端已校验的对象、客户端提交随机区间的持有证明，成功后只新增用户引用
- 桶上配置清理未完成分片上传的生命周期规则

→ 详见 [大文件上传 & 对象存储](/scenario/10_file_upload)

### Q14：分布式系统的主键怎么选？节点本地生成还是用发号服务？

**一句话**：不想引入发号服务、能接受 128 位就用 UUIDv7；要 64 位有序主键用 Snowflake（显式分配 workerId、处理时钟回拨）或号段模式；对外暴露的单号再另行编码。

- 本地生成（UUIDv7、Snowflake）：无网络依赖、性能最高，但 Snowflake 依赖时钟和 workerId 分配
- 发号服务（号段模式、Leaf）：只依赖数据库，ID 节点内递增，服务本身要高可用
- UUIDv4 作主键会导致 B+ 树页分裂，不推荐；分库分表时 ID 要能均匀路由
- 前端接收 64 位 ID 要序列化成字符串，否则超过 2^53 丢精度

→ 详见 [分布式 ID 生成](/distributed/8_id_generator#八、方案对比与选型)、[分布式面试题解答](/interview/10_distributed#四、分布式-id)

### Q15：对外开放的 API 如何保证安全？

**一句话**：HTTPS 传输 + AppKey/Secret 签名防篡改 + timestamp 与 nonce 防重放 + 限流与权限控制，敏感数据再做加密和脱敏。

- 签名：参数按 key 字典序拼接，加上 timestamp、nonce，用 `HMAC-SHA256(appSecret, 拼接串)` 计算，服务端用同样规则重算比对
- 防重放：timestamp 超出时间窗口直接拒绝；nonce 在窗口内用 Redis 去重
- AppSecret 不在网络上传输，服务端加密存储，支持轮换与吊销
- 按 AppKey 限流、按接口授权；日志脱敏，错误响应不暴露内部信息
- 涉及资金的写接口还要做幂等（`Idempotency-Key`）

→ 详见 [API 安全](/security/6_api_security)

## 四、综合

### Q16：如何设计一个高并发系统？

**一句话**：先估清楚流量（DAU → 峰值 QPS），再按「能扩、少打、慢做、分散」逐层设计，最后用限流降级兜底、用压测和水位监控验证。

- 能扩：服务无状态化，水平扩展；数据层读写分离、分库分表
- 少打：CDN、多级缓存，让请求尽量不到数据库
- 慢做：MQ 削峰填谷，非核心流程异步化
- 分散：热点探测、key 打散、分桶库存，避免单点被打满
- 兜底：限流、熔断、降级、隔离，配合全链路压测与容量水位告警

→ 详见 [高并发面试题解答](/interview/13_high_con#一、总体设计)、[高并发总览](/high-con/0_overview)

### Q17：分布式场景下 `synchronized` 还能用吗？

**一句话**：`synchronized` 和 `ReentrantLock` 只在一个 JVM 内有效，多实例部署时各实例各锁各的，互斥失效；跨进程互斥要用分布式锁，正确性要求高的写操作最终还要靠数据库约束。

- 单实例内防并发仍可以用，比如本 JVM 内合并缓存回源
- 跨实例：Redisson、ZooKeeper、etcd 分布式锁，注意租约过期问题
- 扣库存、改余额这类场景优先用数据库条件更新或 Redis Lua 原子操作，比加锁吞吐高
- 锁要包住事务提交，在 `@Transactional` 方法内部解锁会让下一个线程读不到刚写的数据

→ 详见 [分布式锁](/distributed/3_lock#一、为什么需要分布式锁)

### Q18：数据更新后通知下游，服务端推送还是客户端拉取？

**一句话**：要实时用推，要稳定可控用拉，常见的是两者结合：推送负责及时，拉取负责兜底补偿。

| 维度 | 推送（MQ、WebSocket、SSE） | 拉取（轮询、定时批量拉） |
|------|---------------------------|------------------------|
| 实时性 | 高 | 取决于拉取间隔 |
| 消费节奏 | 由发送方决定，下游可能被压垮 | 由消费方控制 |
| 实现 | 需要通道和连接管理 | 简单 |

- 推送的可靠性看通道：MQ 有持久化、确认和重试，可靠性高；WebSocket、SSE 只是在线通道，断线就丢，要配 ACK 和重推
- 消费方处理能力不稳定、允许分钟级延迟、多个消费方节奏不同时用拉取
- 推拉结合：变更时推一条通知，下游再按版本号拉最新数据，错过通知就靠定时拉取补齐

→ 详见 [Feed 流 & 消息推送系统设计](/scenario/8_feed_stream#六、在线推送)、[消息队列基础](/messaging/1_basics)

### Q19：面试时项目的亮点和难点怎么讲？

**一句话**：按「背景（规模与问题）→ 方案（为什么选它而不是别的）→ 实现细节（难点与坑）→ 量化结果（前后对比）」四步讲，数字用自己项目的真实数据。

- 好的亮点方向：缓存与一致性（先更新数据库再删缓存 + binlog 兜底，不要说成「先删缓存再延迟双删」）、热点治理（本地缓存 + 多副本 key，写时更新全部副本并容忍短暂不一致）、防超卖（Lua 原子扣减 + 数据库条件更新）、异步削峰、慢 SQL 治理、冷热归档
- 一致性方案要讲准：Seata AT 是全局锁 + 默认读未提交，不适合热点库存；MQ 消费去重用业务键而不是 msgId，去重记录与业务写入同一本地事务
- 分库分表迁移：双写只是一步，还要讲以哪边为准、增量追平（binlog 同步）、对账校验、灰度切读和回滚开关
- 被问「你具体做了什么」：讲清自己的职责边界，「我负责了 X 模块的设计与实现」比「我设计了整个系统」更可信
- 被问「重来会怎么改」：诚实指出当前方案的局限和更好的选择，体现反思

**常见坑**：只罗列技术名词不讲取舍；数字前后矛盾或明显夸大（如单机 Redis 扛百万 QPS）；把通用八股当项目难点。

→ 详见 [业务场景总览](/scenario/0_overview)、[分库分表与中间件](/database/5_practice/2_sharding#_3、数据迁移)
