> 题目清单见 [微服务架构面试题](/microservices/99_interview)，模块入口见 [微服务架构总览](/microservices/0_overview)；Nacos、网关、Feign、Sentinel、Seata、Dubbo、服务网格等落地题见 [微服务治理面试题解答](/interview/18_service_governance)，熔断限流策略见 [高可用面试题解答](/interview/21_high_avail)。

## 一、拆分与演进

### Q1：微服务和单体架构各有什么优缺点？什么时候该拆分？

**一句话**：微服务用「分布式的麻烦」换来「各自发布、各自扩容、故障隔离」。没有「多少人就该拆」的硬标准，一般先用单体把业务跑通、边界看清，再按需拆。

| 对比 | 单体 | 微服务 |
|------|------|--------|
| 开发调试 | 简单，本地调用 | 网络调用会超时、失败 |
| 发布 | 改一行也要整体发布 | 按服务单独发布 |
| 扩容 | 只能整体扩 | 只扩热点服务 |
| 一致性 | 本地事务 | 要靠 Saga、Outbox 等最终一致方案 |

- 该拆的信号：多个团队抢同一个发布窗口、模块迭代节奏差别大、个别模块要单独扩容
- 先别拆的信号：业务边界还模糊、团队小、容器化和监控等基础设施没跟上（先在单体内做模块化）

→ 详见 [服务拆分](/microservices/2_service_split#一、什么时候该拆、什么时候不该拆)

### Q2：微服务和 SOA 的区别是什么？

**一句话**：区别不在服务大小，而在**怎么连、数据归谁**：SOA 靠中心总线（ESB）串起各系统，微服务去掉总线、各服务直连并独占自己的数据。

| 对比 | SOA | 微服务 |
|------|-----|--------|
| 集成方式 | ESB 总线做路由、协议转换、编排（智能管道），WS-* 重协议 | HTTP / gRPC / MQ 直连，逻辑放在服务里，管道只负责传输（智能端点、哑管道） |
| 数据 | 常共享数据库 | 每个服务独立存储 |
| 目标 | 跨系统复用 | 快速迭代、独立交付 |

**常见坑**：把「拆得更细」当成微服务的定义。粒度只是次要差异，拆过头就成了纳米服务。

→ 详见 [微服务优势与挑战](/microservices/1_pros_and_cons#_3、微服务-vs-soa)

### Q3：微服务拆分的原则是什么？如何避免过度拆分和「分布式单体」？

**一句话**：按业务边界拆（DDD 里的限界上下文，就是「一块业务说同一套话」的范围），每个服务职责单一、数据独占。最怕拆成「分布式单体」：服务分开了，却还得一起发布、一起出故障。

- 不要按技术分层拆（controller 服务、dao 服务）
- 一个服务一个库，禁止多个服务读写同一张表
- 好的拆分：一个需求通常只改一个服务；一个需求要改五个服务还得按顺序发布，就是拆错了
- 防过度拆分：服务数量和团队维护能力匹配；总是一起改的模块不要拆开

→ 详见 [服务拆分](/microservices/2_service_split#三、拆分粒度)、[DDD 领域驱动设计](/architecture/2_ddd)

### Q4：如何把单体迁移到微服务？绞杀者模式怎么做？

**一句话**：一点点迁，不推倒重写。新功能直接做成新服务；老功能用绞杀者模式逐个搬出去，像藤蔓一点点包住老树。

- 第 1 步：单体前面加一个网关，所有流量先走网关（先只做转发）
- 第 2 步：挑一个模块抽成新服务，网关把这部分路由切过去；出问题切回单体即可回滚
- 第 3 步：新服务稳定后删掉单体里的旧代码，重复直到单体下线
- 先抽：变化频繁、边界清楚、耦合少的模块
- 数据迁移最难：先让新服务通过接口读写老数据，再双写或用 CDC（监听数据库变更日志）同步到新库，最后断开旧表

→ 详见 [服务拆分 · 拆分步骤](/microservices/2_service_split#五、拆分步骤)

### Q5：什么是模块化单体？为什么常建议先做模块化单体再拆？

**一句话**：模块化单体是「一个部署包，但内部按业务模块划清边界」，模块之间只调公开接口、不碰对方的表。它保留单体的简单（本地事务、好调试），将来真要拆，模块边界直接就是服务边界。

- 拆分解决的是团队抢发布窗口、局部要单独扩容这类问题，没有这些问题时拆分只增加成本
- 边界要能自动检查：Spring Modulith 用一个测试校验模块依赖，越界就构建失败
- 模块间按「将来是两个服务」来写：同步走公开接口，异步发领域事件，拆的时候只改部署方式

**常见坑**：只按包名分了模块，却允许互相直接查表，拆的时候数据依然缠在一起。

→ 详见 [服务拆分](/microservices/2_service_split#_2、模块化单体)

### Q6：康威定律对服务拆分有什么影响？什么是逆康威操作？

**一句话**：康威定律说「系统结构会长成组织沟通结构的样子」。所以服务边界要和团队边界对齐，一个服务只归一个团队；逆康威操作就是先按想要的架构调整团队，再让系统跟着演化。

- 两个团队共管一个服务：协作方式退化成单体，互相等发布
- 一个团队管十几个服务：精力全耗在运维和升级上
- 团队能长期维护的服务数，就是拆分粒度的上限（常见是一个团队 2–5 个服务）

**常见坑**：只画了服务边界没调团队，跨团队需求会慢慢把边界侵蚀掉。

→ 详见 [服务拆分](/microservices/2_service_split#_3、团队结构与康威定律)

### Q7：单体里被多个模块共用的表，拆服务时怎么拆？

**一句话**：先给每张表定唯一的「写方」（owner），只有它能直接写；其他服务要写就调它的接口，要读就调接口或订阅它发的变更事件。

| 现状 | 拆法 |
|------|------|
| 宽表混着多个业务的字段 | 按列拆，比如商品表里的库存列迁到库存服务 |
| 跨模块 JOIN、外键 | 改成只存对方 ID，展示用的字段存一份快照 |
| 地区、币种等字典表 | 一个服务拥有，其他服务缓存只读副本 |

- 快照还是引用看语义：订单要的是下单那一刻的价格，所以存快照

→ 详见 [服务拆分](/microservices/2_service_split#_2、共享表的拆法)

### Q8：拆服务时，数据怎么从单体库平滑迁到新服务的库？

**一句话**：分阶段把「以哪边为准」从旧库换到新库，每一步都能退回：先切流量不动数据，再同步数据、切读，最后切写、断开旧表。

- 第 1 步：新服务先通过单体接口读写老表，只验证逻辑
- 第 2 步：建新库，用 CDC（监听数据库变更日志）同步存量和增量，比在代码里写两遍更可靠
- 第 3 步：对账校验后，按用户逐步把读切到新库
- 第 4 步：短暂停写、等同步追平后切写，同时把新库数据反向同步回旧库，方便回滚
- 第 5 步：回收旧表权限，确认没人再访问后归档

**常见坑**：跳过最后一步，旧表还被报表、定时任务偷偷读写，数据慢慢就对不上了。

→ 详见 [服务拆分](/microservices/2_service_split#_3、双写与数据迁移)

### Q9：服务之间同步调用链太深有什么问题？怎么治理？

**一句话**：同步链越深，延迟越叠加、可用性越相乘（每层 99.9%，5 层只剩约 99.5%），任何一层变慢都会拖住整条链。一般把一个外部请求的同步调用控制在 3 层以内。

- 链深往往说明拆得太细：一个业务能力被切成几个只做转发的小服务，考虑合并
- 调用方需要的字段可以冗余一份，不必每次都去查
- 积分、通知、统计等非核心步骤改成发事件，不放在同步链上
- 禁止循环依赖，用链路追踪的服务依赖图定期检查；每个远程调用都设超时

→ 详见 [服务拆分](/microservices/2_service_split#_3、调用链深度)

## 二、通信与 RPC

### Q10：客户端服务发现与服务端服务发现有什么区别？

**一句话**：客户端发现是调用方自己去注册中心拿实例列表、自己挑一个直连（Nacos + LoadBalancer、Dubbo）；服务端发现是调用方只访问一个固定地址，由平台转发（Kubernetes Service、服务网格）。

| 对比 | 客户端发现 | 服务端发现 |
|------|-----------|-----------|
| 谁做负载均衡 | 调用方进程内 | 平台或代理 |
| 多语言 | 每种语言要有 SDK | 与语言无关 |
| 网络跳数 | 直连，少一跳 | 多一次转发 |

- 注册中心不在调用路径上：它短暂故障时，调用方用本地缓存的列表照样能调

→ 详见 [微服务设计模式](/microservices/3_patterns#_3、服务发现-service-discovery)

### Q11：服务间同步调用与异步消息怎么选？

**一句话**：要马上拿到结果就同步调用；能晚点处理、要削峰、一个事件有多方关心，就用消息队列。常见组合是核心链路同步、非核心链路异步。

- 同步例子：下单时要立刻知道库存扣没扣成功
- 异步例子：下单后发积分、发通知、做统计
- 同步要注意：每次调用都设超时，调用链别太深
- 异步要注意：消息可靠投递、重复消费要幂等（同一消息处理多次结果一样）、最终一致

→ 详见 [服务间通信与契约 · 同步还是异步](/microservices/5_communication#一、同步还是异步)、[消息队列基础](/messaging/1_basics)

### Q12：gRPC、Dubbo 与 HTTP（REST）分别适合什么场景？

**一句话**：对外、给浏览器和第三方用 REST；内部调用量大、要流式或多语言用 gRPC；Java 为主、想要框架自带治理用 Dubbo。性能差距只在调用量大、消息体大时才明显，选型更看团队熟悉度和维护成本。

| 对比 | REST | gRPC | Dubbo 3 |
|------|------|------|---------|
| 接口定义 | URL + DTO | `.proto` 文件生成代码 | Java 接口 jar |
| 浏览器直接调 | 可以 | 需要转换 | Triple 协议可以 |
| 服务治理 | 靠 Spring Cloud 组件 | 靠网格或自建 | 框架自带 |

**常见坑**：gRPC 用长连接，四层负载均衡只在建连时分配一次，请求会全落在一台上，要按请求做均衡。

→ 详见 [服务通信](/service-governance/3_communication#六、选型)、[RPC 协议](/protocols/5_rpc_protocols)

### Q13：如何设计一个 RPC 框架？

**一句话**：目标是让调用远程服务像调用本地方法：动态代理拦截调用 → 序列化 → 网络传输 → 服务端找到实现并调用 → 原路返回结果，再加上注册发现、负载均衡、容错这些治理能力。

- 注册中心：提供方启动时注册地址，调用方订阅并在本地缓存列表，注册中心短暂故障时照样能调（Nacos、ZooKeeper）
- 动态代理：调用方只依赖接口，代理把接口名、方法名、参数打包成请求（JDK 动态代理或字节码生成）
- 序列化：二进制格式体积小、速度快（Protobuf、Hessian2），JSON 便于调试；不用 Java 原生序列化（慢，还有反序列化漏洞）
- 网络传输：基于 Netty 长连接 + 自定义帧（魔数、版本、请求 ID、长度）；请求 ID 把异步返回的响应对应到正在等待的 Future 上
- 负载均衡与容错：随机、轮询、最少活跃、一致性哈希；超时、失败换实例重试、快速失败、熔断；各环节用 SPI 做成可替换的插件

**常见坑**：失败自动重试对非幂等的写接口会造成重复下单、重复扣款，写操作要关掉重试或保证幂等。

→ 详见 [Dubbo](/service-governance/8_dubbo#二、架构与调用流程)、[自定义私有协议](/netty/8_custom_protocol#七、请求-响应匹配-rpc-的核心)、[RPC 协议](/protocols/5_rpc_protocols)

## 三、微服务模式

### Q14：BFF 是什么？和 API 网关有什么区别？

**一句话**：API 网关是所有客户端的统一大门，做鉴权、限流、路由这些通用的事；BFF（Backend for Frontend）是给某一类客户端专门做的接口层，比如 App 一个、Web 一个，负责合并请求、裁剪字段。

- BFF 由对应的前端团队负责，只做拼装和适配，不放核心业务逻辑
- 常见组合：网关在前做通用能力，后面按客户端类型分多个 BFF
- 目的：避免一个「万能网关」被各端的需求拉扯

→ 详见 [微服务设计模式](/microservices/3_patterns#_2、bff-backend-for-frontend)

### Q15：Database per Service 之后如何做跨服务查询？API Composition 还是 CQRS？

**一句话**：简单查询、数据量小用 API Composition——同时调几个服务、在内存里拼结果；要跨服务分页、排序、复杂筛选就用 CQRS——专门维护一份给查询用的数据（比如 ES 宽表），靠事件异步更新。

- API Composition：实时、简单，但数据多了内存拼接扛不住
- CQRS：查询灵活，代价是读到的数据会有短暂延迟
- 「独占数据」指的是归属权：同一个 MySQL 实例上分不同库、只授权给对应服务也可以；但禁止多个服务直接读写同一张表

→ 详见 [服务间通信与契约 · 跨服务查询](/microservices/5_communication#五、跨服务查询)、[微服务设计模式](/microservices/3_patterns#三、数据管理模式)、[架构模式与风格](/architecture/1_arch_patterns)

### Q16：Outbox 模式如何保证「写库 + 发消息」的原子性？

**一句话**：在同一个本地事务里同时写业务表和一张「待发消息表」（outbox），事务提交两者就一起生效；再由单独的进程把待发消息发到 MQ，发成功就标记完成，失败就重试。

→ 完整答案见 [消息队列面试题解答](/interview/15_mq) Q20；正文详见 [微服务设计模式](/microservices/3_patterns#_5、outbox-事务发件箱)、[分布式事务](/distributed/4_transaction)

### Q17：Saga 的编排式与协同式有什么区别？

**一句话**：编排式有一个「总指挥」统一调度，流程清楚好监控，适合步骤多、补偿复杂；协同式没有总指挥，各服务听事件自己往下走，适合步骤少。

→ 完整答案见 [分布式基础面试题解答](/interview/16_distributed) Q16；正文详见 [分布式事务](/distributed/4_transaction#四、saga)

### Q18：消费者驱动契约测试解决什么问题？

**一句话**：服务各自发布，提供方改了接口很容易把调用方搞坏；契约测试让调用方写下「我需要你返回什么」，提供方在 CI 里用它验证，一旦改坏就构建失败。

→ 完整答案见 [测试工程面试题解答](/interview/26_testing) Q11；正文详见 [微服务设计模式](/microservices/3_patterns#_4、消费者驱动契约测试-consumer-driven-contract)、[契约测试](/testing/6_contract_test)

## 四、分布式场景

### Q19：微服务之间的分布式事务如何处理？

**一句话**：能不用分布式事务就不用；优先用最终一致方案（Outbox、事务消息、Saga、对账补偿），只有必须同步拿到一致结果的链路才用 TCC、Seata 这类方案。

→ 完整答案见 [分布式基础面试题解答](/interview/16_distributed) Q13；正文详见 [分布式事务](/distributed/4_transaction#九、方案选型)

### Q20：微服务接口如何实现幂等？

**一句话**：超时重试、MQ 重复投递、Dubbo 自动重试都会让同一个请求来好几次，所以写接口必须幂等；核心是给每次操作一个唯一标识，服务端按它去重。

→ 完整答案见 [系统架构面试题解答](/interview/23_architecture) Q18；正文详见 [幂等设计](/architecture/3_idempotence)

### Q21：分布式接口请求的顺序性如何保证？

**一句话**：先想办法让业务不依赖顺序；真要顺序，也只要求同一业务键（如订单号）内有序：同一个键路由到同一处、实例内串行执行，最后在数据层用版本号兜底。

- 能消掉就消掉：调用方等上一步成功再发下一步、把两次调用合成一个接口、同步全量状态而不是「减 20」这种增量指令
- 路由：Dubbo 一致性哈希负载均衡、Nginx 按请求头哈希；异步场景改走 MQ，用业务键做分区键（顺序消息）
- 实例内：按业务键哈希到固定数量的单线程队列，同一个键排队执行
- 数据层兜底：请求带单调递增的序列号，`UPDATE ... WHERE last_seq < ?` 只接受更新的请求；状态流转再加前置状态条件

**常见坑**：用分布式锁保证顺序。锁只保证同一时刻一个请求在执行，不保证谁先拿到，后发的请求照样可能先执行。

→ 详见 [接口调用顺序性](/microservices/4_call_ordering)、[消息队列基础](/messaging/1_basics#五、顺序消息)

### Q22：服务间如何传递认证信息与上下文（用户身份、灰度标记、traceId）？

**一句话**：都靠请求头一跳一跳往下传，每一跳都要转给下一跳，否则到第二跳就丢了。

- 用户身份：网关验完令牌后，先删掉客户端自己带的同名请求头，再写入用户信息；或者原样转发 `Authorization` 让下游自己再验
- 灰度标记：HTTP 客户端用拦截器加请求头；MQ 写进消息头；Dubbo 用 `RpcContext` 附带
- traceId：Micrometer Tracing 自动加到请求头并写进日志 MDC

**常见坑**：请求上下文绑定在当前线程上，切到线程池或 `@Async` 后就拿不到了，要用 `TaskDecorator` 等方式手动带过去。

→ 详见 [API 网关](/service-governance/2_api_gateway#四、统一鉴权-网关作为-oauth2-资源服务器)、[流量治理](/service-governance/5_traffic_governance#_5、灰度标记透传)

## 五、事件与契约

### Q23：事件通知、事件携带状态转移、事件溯源有什么区别？

**一句话**：区别在事件里放了什么。事件通知只说「出事了」（带个 ID），要详情得回头去查；携带状态转移把变化后的数据一起带上，下游自己存一份；事件溯源是把每次变化都存下来，状态靠重放算出来。

| 用法 | 事件里有什么 | 代价 |
|------|-------------|------|
| 事件通知 | 类型 + 业务 ID | 订阅方多时回查流量大 |
| 携带状态转移 | 变更后的数据快照 | 下游存副本，最终一致 |
| 事件溯源 | 每一次状态变化 | 建模、版本演进复杂 |

- 前两种是服务之间怎么集成，事件溯源是服务内部怎么存数据
- 事件说的是已经发生的事（`OrderPaid`），不是命令；要对方必须做且要结果，就用同步调用或 Saga 编排

→ 详见 [服务间通信与契约 · 事件驱动的用法与边界](/microservices/5_communication#二、事件驱动的用法与边界)

### Q24：服务接口怎么演进才能不影响老调用方？

**一句话**：默认只做兼容的改动——只加不删、新字段可选、不改语义；非改不可时走「扩展 - 迁移 - 收缩」：先让新旧并存，调用方逐个迁走，旧版本没人用了再删。

- 宽容读者：调用方忽略不认识的字段和枚举值，提供方多返回一个字段不会出错
- 默认值等于旧行为：新参数不传时，效果必须和改之前一样
- protobuf 不复用字段编号，删字段用 `reserved` 占住编号
- 发布顺序：接口提供方先发；事件则是消费者先升级到能读新格式，生产者再开始发

**常见坑**：改了字段的含义或单位（分改成元）却没换字段名，老调用方不报错但算错数，最难发现。

→ 详见 [服务间通信与契约 · 版本与兼容](/microservices/5_communication#四、版本与兼容)、[API 设计规范 · 版本管理](/engineering/4_api_design_rule#八、版本管理)

### Q25：契约优先和代码优先有什么区别？怎么选？

**一句话**：契约优先是先写接口描述文件（OpenAPI、`.proto`）评审，再生成代码；代码优先是先写代码，再从注解生成文档。跨团队、多语言、对外的接口用契约优先，单团队内部迭代快的接口可以代码优先。

- 契约优先：接口先被讨论，双方可以并行开发；代价是规范要单独维护
- 代码优先：上手快，文档和代码不会对不上；代价是接口容易被实现细节牵着走
- 折中：代码优先，但把生成的规范提交入库，CI 里比对差异、拦截破坏性改动
- 契约不只是字段，还要写清单位、错误码、是否幂等这些约定

→ 详见 [服务间通信与契约 · 接口契约](/microservices/5_communication#三、接口契约)、[API 文档](/engineering/5_api_doc)
