# 性能分析方法论

> 前置阅读：[性能指标](./1_metrics)

性能分析最常见的错误是"凭经验猜"，方法论的价值在于给出**可重复的排查路径**，让每一步都有数据支撑。本篇讲 USE / RED 方法、自顶向下的瓶颈定位流程、用 Amdahl 定律决定优化顺序，以及可验证的优化闭环。

---

## 一、USE 方法：面向资源

**对每一种资源检查三个维度：使用率、饱和度、错误。** 由 Brendan Gregg 提出：

| 维度 | 含义 | 示例 |
|------|------|------|
| Utilization（使用率） | 资源忙碌的时间占比 | CPU 使用率 85%、磁盘 %util 95% |
| Saturation（饱和度） | 资源无法立即处理、需要排队的程度 | Load 高于核数、线程池队列堆积、磁盘 aqu-sz 升高 |
| Errors（错误） | 资源相关的错误事件 | 网卡丢包、TCP 重传、连接获取超时 |

常见资源的 USE 检查清单：

| 资源 | 使用率 | 饱和度 | 错误 |
|------|--------|--------|------|
| CPU | `top` us+sy | Load Average、`vmstat` r 列 | —— |
| 内存 | `free` used | Swap 使用、`vmstat` si/so | OOM Killer 日志 |
| 磁盘 | `iostat -x` %util | await、aqu-sz | `dmesg` IO 错误 |
| 网络 | `sar -n DEV` 带宽 | 丢包、socket backlog 溢出 | 重传、`netstat -s` 错误计数 |
| 线程池 | 活跃线程 / 最大线程 | 队列长度 | 拒绝次数 |
| 连接池 | 活跃连接 / 最大连接 | 等待获取连接的线程数 | 获取连接超时 |

::: tip iostat 列名
较新版本的 sysstat 中平均队列长度列名为 `aqu-sz`，旧版本为 `avgqu-sz`，含义相同。
:::

USE 的优点是**覆盖完整、不遗漏**，适合"系统整体变慢但不知道原因"时做第一轮排查。线程池、连接池、锁这类**软件资源**同样适用 USE。

## 二、RED 方法：面向服务

**对每个服务（或接口）采集请求速率、错误、耗时三个指标：**

| 指标 | 含义 | Prometheus 示例 |
|------|------|-----------------|
| Rate | 每秒请求数 | `rate(http_server_requests_seconds_count[1m])` |
| Errors | 每秒失败请求数或错误率 | 状态码 5xx 的 rate |
| Duration | 请求耗时分布（分位数） | `histogram_quantile(0.99, ...)` |

- RED 回答"**哪个服务、哪个接口**有问题"，USE 回答"**哪种资源**有问题"，两者互补：先用 RED 找到慢接口，再用 USE 查它所在机器与依赖的资源。
- Spring Boot + Micrometer 暴露的 `http.server.requests` 指标就是 RED 所需的数据；分位数直方图需开启 `management.metrics.distribution.percentiles-histogram.http.server.requests=true`。监控体系建设见 [可观测性](/observability/0_overview)。

## 三、瓶颈定位流程

### 1、自顶向下

**从现象出发逐层下钻，每一层用数据排除或确认，再进入下一层：**

![自顶向下的瓶颈定位](../assets/high-perf/bottleneck_topdown.svg)

| 步骤 | 要回答的问题 | 手段 | 下钻方向 |
|------|--------------|------|----------|
| ① 系统资源 | CPU、内存、IO、网络是否打满或饱和 | `top`、`vmstat`、`iostat`、`sar` | CPU 高 → 看是哪个进程/线程；IO 高 → 看哪个进程在读写 |
| ② JVM | GC 是否频繁、停顿是否过长、堆是否持续上涨 | GC 日志、`jstat -gcutil`、JFR | GC 问题 → [JVM 层性能策略](./5_jvm_tuning)；内存泄漏 → 堆 dump 分析 |
| ③ 应用线程/锁 | 哪些方法耗 CPU、线程卡在哪里、是否有锁竞争 | `jstack`、Arthas `thread` / `trace`、火焰图 | 热点方法 → 代码优化；BLOCKED 多 → 锁优化 |
| ④ 外部依赖 | 时间是否花在等待 DB、缓存、RPC、MQ | 链路追踪、慢查询日志、客户端耗时埋点 | 慢 SQL → [数据访问性能](./10_db_performance) |

### 2、快速判断：CPU 忙还是在等

**请求慢时，先看 CPU 是高还是低**，这是最实用的分叉点：

- **CPU 高、RT 高**：计算型瓶颈。用 CPU 火焰图找热点方法，或检查是否 GC 线程占满 CPU。
- **CPU 低、RT 高**：等待型瓶颈。线程在等锁、等 IO、等连接池、等下游。用 `jstack` 看线程状态分布，或用 async-profiler 的 wall-clock 模式（`-e wall`）采样。

具体故障排查步骤（CPU 飙高、内存泄漏、死锁）见 [JVM 故障排查](/jvm/9_troubleshooting) 与 [线上诊断](/engineering/4_diagnosis)。

## 四、Amdahl 定律：决定优化顺序

### 1、公式

**局部优化对整体的加速上限：`S = 1 / ((1 - p) + p / k)`**，其中 `p` 为被优化部分占总耗时的比例，`k` 为该部分自身的加速倍数。

推导：设原总耗时为 1，未优化部分耗时 `1 - p` 不变，被优化部分从 `p` 变为 `p / k`，新耗时为 `(1 - p) + p / k`，加速比即原耗时除以新耗时。

| 被优化部分占比 p | 自身加速 k | 整体加速比 |
|------------------|-----------|-----------|
| 5% | ∞ | 1.05 |
| 10% | 10 倍 | 1.10 |
| 50% | 10 倍 | 1.82 |
| 90% | 10 倍 | 5.26 |
| 90% | ∞ | 10 |

### 2、推论

- **先优化占比最大的部分**：占比 5% 的环节即使降到 0，整体也只快约 5%。
- **并行化同样受限**：任务中有 10% 必须串行，无论加多少核，加速比上限都是 10 倍。
- **微基准的收益不能直接外推**：某方法快 30%，要乘以它在接口总耗时中的占比才是真实收益。

::: tip Little 定律
容量与并发的关系用 Little 定律 `L = λW` 估算，推导与示例见 [性能指标](./1_metrics)。典型用法：下游 RT 从 20ms 涨到 200ms，调用方占用的线程数放大 10 倍，线程池被打满。
:::

## 五、常见瓶颈类型与信号

| 瓶颈类型 | 典型信号 | 确认手段 | 常见方向 |
|----------|----------|----------|----------|
| CPU 计算热点 | us 高、RT 随 QPS 线性上涨 | CPU 火焰图 | 算法、减少重复计算、缓存结果 |
| GC 压力 | GC 线程 CPU 高、STW 频繁、P99 周期性毛刺 | GC 日志、`jstat` | 减少分配、调整堆与收集器 |
| 锁竞争 | CPU 不高但吞吐上不去、大量 BLOCKED | `jstack`、lock 火焰图 | 缩小锁粒度、无锁结构、分段 |
| 线程池/连接池耗尽 | 获取超时、队列堆积、RT 突增 | 池监控指标、线程 dump | 调整池大小、降低下游 RT |
| 慢 SQL | 数据库 CPU/IO 高、慢日志增长 | 慢查询日志、`EXPLAIN` | 索引、改写、批量 |
| 下游慢 | 链路追踪中某依赖耗时占比大 | APM、客户端耗时埋点 | 缓存、并行调用、超时与降级 |
| 网络 | 重传多、带宽打满、跨机房 RTT 大 | `ss`、`sar`、抓包 | 压缩、减少往返、就近部署 |
| 磁盘 IO | await 高、iowait 高 | `iostat`、`iotop` | 顺序写、批量刷盘、异步日志 |
| 序列化 | 火焰图中大量 JSON/反射栈 | CPU 火焰图 | 更换序列化方式、减少字段 |
| 日志 | 同步日志阻塞、磁盘写满 | 线程栈卡在 Appender | 异步 Appender、降低日志级别 |

## 六、长尾治理

**P99 往往不是"慢代码"造成的，而是排队、GC、缓存未命中、邻居干扰等偶发因素；扇出越多，偶发因素越会变成常态。** 所以长尾要单独治理，而不是只盯平均耗时。

### 1、P99 放大

| 场景 | 现象 | 原因 |
|------|------|------|
| 并行扇出 | 调用 N 个下游，整体耗时取最慢的一个 | 至少一个下游命中 P99 的概率 `1 - 0.99^N`，N = 100 时约 63% |
| 串行链路 | 多跳调用逐级叠加 | 每一跳的长尾叠加，且上游超时通常大于下游 |
| 重试 | 失败后重试拉长总耗时 | 一次超时 + 一次重试，耗时可达单次的两倍以上 |

降低扇出本身（聚合接口、批量 API、合并下游）往往比优化单个下游更有效。

### 2、对冲请求（Hedged Request）

**先向一个副本发请求，等待超过该接口的 P95 等阈值仍未返回，再向另一个副本补发一份，取先返回的结果并取消另一个。**

- 只额外增加少量请求（阈值取 P95 时理论上约 5%），却能显著削掉长尾，来自 Google 的 The Tail at Scale。
- **只适用于幂等、无副作用的读请求**，写请求不能对冲。
- 下游整体过载时对冲会加剧拥塞，应设置对冲比例上限，并与熔断、限流配合。
- gRPC 的 hedging policy、部分数据库与缓存客户端提供对冲或"推测执行"能力，使用前确认所用版本是否支持。
- 基于 `CompletableFuture` 的实现示例见 [异步与批量 - 长尾治理](./8_async_batch)。

### 3、超时预算（Deadline Propagation）

**给整条请求一个总时限，每一跳用"剩余预算"作为自己的超时，而不是每跳各自配置固定超时。**

| 做法 | 说明 |
|------|------|
| 入口设总预算 | 如网关给下单请求 800ms |
| 向下传递截止时间 | 通过请求头或 RPC 元数据传递 deadline（gRPC 原生支持 deadline 传播） |
| 每跳扣减 | 本跳超时 = 剩余预算 − 本地处理余量；预算已耗尽时直接失败，不再调用下游 |
| 重试也占预算 | 剩余预算不足以完成一次调用时不再重试 |

超时与重试的具体取值策略见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)。

## 七、优化闭环

**性能优化应是一个可验证的循环，而不是一次性"拍脑袋"修改：**

| 阶段 | 做什么 | 产出 |
|------|--------|------|
| 1、建立基线 | 在固定环境、固定数据量、固定压测模型下测出当前指标 | QPS、P50/P99、错误率、资源使用率 |
| 2、提出假设 | 根据分析数据指出瓶颈并预测收益 | "该接口 70% 耗时在 N+1 查询，改为批量后 P99 预计降低 60%" |
| 3、实验 | **一次只改一个变量**，在相同条件下复测 | 对比数据 |
| 4、验证 | 与基线对比，确认收益符合预期且无副作用（正确性、资源、其他接口） | 结论与记录 |
| 5、固化 | 上线、加监控告警、把基线纳入回归（如 CI 中的 JMH 或定期压测） | 防止性能回退 |

注意事项：

- **环境一致**：压测环境与线上的硬件、JVM 参数、数据规模差异越大，结论越不可信。
- **预热**：JIT 编译、缓存、连接池都需要预热，冷启动数据不能作为基线。
- **看分布不看平均**：以 P99 等分位数和资源使用率共同判断。
- **记录每一次实验**：包括无效的尝试，避免重复踩坑。

微观代码对比使用 [JMH 基准测试](./4_benchmark)，系统级验证使用 [压测](/testing/7_performance_test)。

## 小结

- USE 面向资源（使用率、饱和度、错误），RED 面向服务（速率、错误、耗时），先 RED 找接口再 USE 查资源
- 自顶向下：系统资源 → JVM → 线程/锁 → 外部依赖；先判断"CPU 忙还是在等"
- Amdahl 定律决定优化顺序：先优化占比最大的部分，微基准收益要乘以占比
- 长尾要单独治理：减少扇出、对冲请求（仅幂等读）、超时预算逐跳传递
- 优化是闭环：基线 → 假设 → 单变量实验 → 验证 → 固化
