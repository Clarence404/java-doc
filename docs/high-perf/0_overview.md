# 高性能总览

本模块聚焦**系统级的性能优化策略与方法**：如何度量、如何定位瓶颈、各层有哪些通用手段。本篇给出高性能优化的全局视图，以及模块的阅读顺序。

---

## 一、什么是高性能

"三高"中的高性能，关注的是**单次请求更快、单位资源处理更多**：

| 维度 | 目标 | 核心指标 |
|------|------|----------|
| 延迟（Latency） | 单个请求处理得更快，长尾更短 | RT 的 P50 / P99 / P999 |
| 吞吐（Throughput） | 同样的机器每秒处理更多请求 | QPS / TPS、MB/s |
| 资源利用率（Efficiency） | 同样的流量消耗更少的 CPU、内存、IO、带宽 | CPU 使用率、GC 开销、每请求资源成本 |

三者并不总是同向：批量化提升吞吐但会增加单条延迟；缓存降低延迟但消耗内存。**优化之前先明确目标是哪一个**，并写成可度量的指标（如"下单接口 P99 从 800ms 降到 200ms，CPU 不增加"）。指标定义见 [性能指标](./1_metrics)。

## 二、优化分层

性能问题可以出现在请求链路的任何一层，每一层的手段、收益和代价差异很大：

![性能优化分层](../assets/high-perf/optimization_layers.svg)

| 层次 | 典型手段 | 典型收益 | 主要代价 | 详见 |
|------|----------|----------|----------|------|
| 代码 | 更优算法、集合预分配、减少对象创建和装箱、缩小锁粒度 | 局部数倍，热点路径上效果明显 | 低，但需要 Profiler 指明热点 | [代码级优化](./6_code_optimization) |
| JVM | 收集器选型、堆与容器内存、降低分配速率、JIT 预热 | 主要改善长尾与吞吐稳定性 | 参数改动需压测验证 | [JVM 层性能策略](./5_jvm_tuning) |
| 缓存 | 本地缓存、分布式缓存、多级缓存 | 读路径常见十倍级 | 一致性、内存成本 | [缓存架构设计](/high-con/3_cache_architecture)、[缓存模块](/cache/0_overview) |
| 资源复用 | 连接池、HTTP 连接池、对象池 | 消除建连与创建开销 | 池参数配置不当反成瓶颈 | [池化技术](./7_pooling) |
| 数据库 | 索引、SQL 改写、深分页治理、批量写、消除 N+1 | 慢 SQL 优化常见十到千倍 | 低～中，需关注索引写放大 | [数据访问性能](./10_db_performance) |
| 架构 | 同步转异步、预计算、请求合并、读写分离、拆分 | 量级提升 | 高：一致性、链路变长、团队协作 | [异步与批量](./8_async_batch)、[数据层扩展](/high-con/5_data_scaling) |
| 网络 | 连接复用、HTTP/2、压缩、高效序列化、CDN、减少往返 | 跨机房/公网场景收益显著 | 中：协议升级、兼容性 | [IO 与网络优化](./9_io_network) |

经验规律：

- **越靠近数据和 IO 的优化，收益往往越大**。一个接口 500ms，其中 480ms 在等 SQL，优化 Java 代码没有意义。
- **越靠近架构的优化，代价越高且越难回滚**，应在代码、SQL、缓存等低成本手段用尽后再考虑。

## 三、核心原则

### 1、先度量，再优化

- 没有基线数据就无法判断优化是否有效，也无法说明收益。
- 线上用 APM / 链路追踪 / 指标系统定位慢在哪里；微观代码用 [JMH 基准测试](./4_benchmark) 对比；整体容量用 [压测](/testing/7_performance_test) 验证。

### 2、优化瓶颈，而不是凭感觉猜热点

- 由 Amdahl 定律：只优化占总耗时 5% 的环节，即使降到 0，整体也只快约 5%。推导见 [性能分析方法论](./2_methodology)。
- 用 Profiler 和火焰图找到真正的热点，见 [性能分析工具](./3_profilers)。

### 3、常用优化思路

| 思路 | 本质 | 典型例子 |
|------|------|----------|
| 空间换时间 | 用内存/存储换计算与 IO | 缓存、索引、预计算、布隆过滤器 |
| 时间换空间 | 用计算换内存/带宽 | 压缩、位图、编码优化 |
| 异步化 | 把非关键路径移出主流程 | CompletableFuture 并行调用、MQ 解耦 |
| 批量化 | 摊薄每次操作的固定开销 | 批量 SQL、Redis Pipeline、MQ 批量发送 |
| 池化 | 复用创建代价高的资源 | 连接池、线程池 |
| 并行化 | 利用多核与多节点 | 并行调用下游、分片处理 |
| 减少往返 | 降低网络 RTT 次数 | 聚合接口、批量 API、Keep-Alive |
| 就近访问 | 缩短物理距离 | CDN、本地缓存、同机房部署 |
| 做减法 | 不做不必要的事 | 去掉冗余查询、按需加载字段、减少日志 |

### 4、避免过早优化

- 优化会增加复杂度，应只针对**有数据证明的瓶颈**，并权衡可读性和维护成本。
- "避免过早优化"不等于"不考虑性能"：数据结构选型、接口粒度、索引设计等决定性能上限的问题，应在设计阶段就考虑。

## 四、与高并发、高可用的关系

| 模块 | 关注点 | 典型手段 |
|------|--------|----------|
| 高性能（本模块） | 单次请求更快、资源更省 | 代码/SQL/缓存优化、池化、异步、批量 |
| [高并发](/high-con/0_overview) | 流量大时扛得住 | 水平扩展、削峰填谷、热点隔离、容量规划 |
| [高可用](/high-avail/0_overview) | 故障时不停服 | 冗余、超时重试、熔断降级、限流、容灾 |

- **高性能是高并发的基础**：由 Little 定律（推导见 [性能指标](./1_metrics)），线程数固定时 RT 减半，可承载 QPS 翻倍，性能优化是最便宜的"扩容"。
- **高性能也服务于高可用**：RT 稳定、长尾短，就不容易因下游变慢导致线程池耗尽和级联故障；反过来，重试、多副本同步等高可用手段会增加延迟，需要取舍。
