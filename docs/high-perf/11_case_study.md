# 端到端优化案例

> **本篇目标**：用一次完整的下单接口优化，把指标、方法论、工具和各类优化手段串成一条可复用的工作流。
>
> **前置阅读**：[数据访问性能](./10_db_performance)

前面各篇分别讲了"怎么度量、怎么定位、怎么优化"。这一篇把它们放进一个真实感较强的场景：**下单接口 P99 从 800ms 降到 200ms 以内**。

::: warning 关于文中数字
本文所有耗时、QPS、命中率等数字均为**示例数据**，用于说明分析过程和量级关系，不代表任何真实系统的测量结果。你的系统必须用自己的压测和监控数据说话。
:::

---

## 一、现象与目标

**先把"慢"翻译成可验收的 SLO，否则优化没有终点。**

背景：电商下单接口 `POST /api/orders`，4 个应用实例，大促前评估峰值为单实例 300 QPS。压测发现 P99 达到 800ms，且出现少量"获取数据库连接超时"错误。

| 项 | 目标（SLO） |
|----|------------|
| 负载 | 单实例 300 QPS 持续 10 分钟 |
| 延迟 | P99 ≤ 250ms |
| 错误率 | < 0.1% |
| 资源 | CPU < 60%，留出突发余量 |

指标的定义与百分位的意义见 [性能指标](./1_metrics)。

---

## 二、建立基线

**没有基线就无法证明优化有效。** 固定压测脚本、数据量和环境，预热后取稳态数据：

| 指标（示例数据） | 基线值 | 数据来源 |
|-----------------|-------|---------|
| P50 / P99 | 320ms / 800ms | 压测工具 + Micrometer `http_server_requests` |
| 错误率 | 0.3%（全部是获取连接超时） | 应用日志 |
| CPU | 45% | 主机监控 |
| Hikari active / pending | 20 / 峰值 15 | `hikaricp_connections_*` |
| 单请求 SQL 条数 | 26 | SQL 日志统计 |

压测方法（固定速率、避免协调遗漏）见 [性能测试](/testing/7_performance_test)，单机压测与容量换算见 [容量评估与规划](/high-con/8_capacity_planning)。

---

## 三、定位

按 [性能分析方法论](./2_methodology) 自顶向下：先看请求时间花在哪，再用工具确认根因。

### 1、链路追踪：拆解一次请求

**先用 Trace 看清时间分布，确定是"等待型"还是"计算型"问题。** 一次典型请求的 Span 拆解如下（P50 附近的样本）：

| 步骤 | 耗时（示例数据） | 观察 |
|------|----------------|------|
| 查用户（RPC） | 40ms | 与后两个 RPC 串行执行 |
| 查商品与价格 | 80ms | 10 件商品，逐个查 SKU 和价格，共 20 条 SQL |
| 查可用优惠券（RPC） | 60ms | 串行 |
| 查地址与运费（RPC） | 50ms | 串行 |
| 下单事务 | 110ms | 扣库存、写订单、**逐条写 10 条明细**、**事务内调用积分服务** |
| 打印日志 | 5ms | INFO 级别把整个订单序列化成 JSON |

链路追踪的接入见 [链路追踪](/observability/3_tracing)。

### 2、火焰图与 JFR：确认根因

| 工具 | 发现 | 结论 |
|------|------|------|
| wall-clock 火焰图 | 大量线程栈停在 JDBC / HTTP 的 Socket 读，以及 `HikariPool.getConnection` | 时间主要花在等待，不是计算 |
| CPU 火焰图 | Jackson 序列化约占 CPU 采样的 12%，调用来源是日志 | 日志是 CPU 热点 |
| JFR | `HikariPool` 上有大量线程 park 事件；GC 停顿 P99 约 15ms | 连接池排队明显，**GC 不是瓶颈** |

工具用法见 [性能分析工具](./3_profilers)。

### 3、慢 SQL 日志：总耗时而非单次最慢

在 `long_query_time=0.5` 下几乎看不到慢 SQL。把阈值临时调到 0 采样 1 分钟，用 `pt-query-digest` 按总耗时排序，排第一的是 `SELECT ... FROM t_sku WHERE id = ?`——单次只要 4ms，但调用次数最多，是典型的 N+1。

### 4、用 Little 定律解释连接池排队

**所需连接数 = QPS × 每次持有连接的时间 = 300 × 0.11s ≈ 33**，而池只有 20 个连接，排队必然发生，这正是 P99 长尾和连接超时的来源。结论：**要缩短持有时间，而不是把池调大**（原因见 [池化技术](./7_pooling)）。

## 四、逐项优化

**一次只改一项，每项改完单独压测**，这样才能把收益归因到具体改动。整体效果如下图：

![下单接口 P99 优化过程（示例数据）](../assets/high-perf/case_study_p99.svg)

### 1、N+1 批量化

- 商品和价格改为按 `IN` 批量查询、内存组装；10 条明细改为 JDBC 批量写入并开启 `rewriteBatchedStatements=true`。
- 单请求 SQL 条数 26 → 6。

| 指标（示例数据） | 优化前 | 优化后 |
|-----------------|-------|-------|
| 查商品与价格 | 80ms | 12ms |
| 下单事务（持有连接） | 110ms | 75ms |
| P99 | 800ms | 560ms |

此时 300 × 0.075 ≈ 22.5 个连接，仍超过池大小 20，排队还在，于是有了下一步。

做法见 [数据访问性能](./10_db_performance)。

### 2、事务内 RPC 移出，消除连接池等待

- 积分服务调用从事务内移到**事务提交后**，通过可靠消息异步发放（本地消息表 / 事务消息）。
- 事务持有连接时间约 75ms → 25ms；Little 定律校验：300 × 0.025 ≈ 7.5 个连接，远低于池大小 20。

| 指标（示例数据） | 优化前 | 优化后 |
|-----------------|-------|-------|
| Hikari pending 峰值 | 15 | 0 |
| 错误率 | 0.3% | 0.02% |
| P99 | 560ms | 400ms |

连接池原理见 [池化技术](./7_pooling)，可靠异步见 [异步与削峰](/high-con/4_async_peak_shaving)。

### 3、串行调用并行化

- 查用户、查优惠券、查地址运费三者互不依赖，改为 `CompletableFuture` 并行，使用独立有界线程池，并给三个 HTTP 客户端设置读超时（`orTimeout` 不会取消底层调用）。
- 三段 RPC 耗时 150ms → 约 65ms（最慢的一段 + 调度开销）。

| 指标（示例数据） | 优化前 | 优化后 |
|-----------------|-------|-------|
| RPC 阶段耗时 | 150ms | 65ms |
| P99 | 400ms | 290ms |

写法见 [异步与批量](./8_async_batch)。

### 4、热点数据本地缓存

- 商品基础信息、运费模板读多写少，加 Caffeine 本地缓存（TTL 60s + 变更消息主动失效）；**价格和库存不缓存**，保证下单时强一致。
- 缓存命中率约 92%。

| 指标（示例数据） | 优化前 | 优化后 |
|-----------------|-------|-------|
| 查商品阶段耗时 | 12ms | 3ms |
| 运费计算耗时 | 20ms | 4ms |
| P99 | 290ms | 230ms |

缓存架构与一致性见 [缓存架构设计](/high-con/3_cache_architecture)、[Caffeine](/cache/7_caffeine)。

### 5、日志瘦身与异步化

- 去掉 INFO 级别的整单 JSON，只用占位符记录订单号、金额等关键字段；完整报文降为 DEBUG 并加级别判断。
- 文件 Appender 改为异步（注意队列满时的丢弃 / 阻塞策略）。

| 指标（示例数据） | 优化前 | 优化后 |
|-----------------|-------|-------|
| CPU | 45% | 36% |
| P99 | 230ms | 195ms |

做法见 [代码级优化](./6_code_optimization)。

### 6、没做的事同样重要

- **没有调 GC 参数**：JFR 显示 GC 停顿对 P99 的贡献很小，改参数只会引入风险。JVM 层何时值得调见 [JVM 层性能策略](./5_jvm_tuning)。
- **没有加大连接池**：Little 定律已说明问题在持有时间，加大池子只会把压力转移给数据库。

## 五、验证与回归

### 1、微基准：验证纯 CPU 改动

**日志格式化、对象组装这类纯 CPU 改动，用 JMH 单独验证。** 例如对比"整单 JSON 序列化"与"占位符关键字段"两种日志写法的单次耗时，确认收益来自改动本身而非环境波动。JMH 的正确用法见 [基准测试（JMH）](./4_benchmark)。

### 2、压测对比：验证整体收益

| 要求 | 说明 |
|------|------|
| 同条件 | 同一脚本、同一数据量、同一环境，预热后取稳态 |
| 看分布 | 对比 P50 / P99 / P999，而不只是平均值 |
| 看拐点 | 逐步加压找吞吐拐点，确认余量 |
| 看副作用 | 数据库 CPU、下游 QPS、缓存命中率、错误率 |

最终结果（示例数据）：

| 指标 | 基线 | 优化后 |
|------|------|-------|
| P50 / P99 | 320ms / 800ms | 90ms / 195ms |
| 错误率 | 0.3% | 0.02% |
| CPU | 45% | 36% |
| Hikari pending 峰值 | 15 | 0 |
| 单请求 SQL 条数 | 26 | 6 |

### 3、上线与防回归

- **灰度验证**：先上 1 个实例，与其他实例的 P99、错误率对比，再全量。
- **性能基线入流程**：核心接口的压测结果作为发布前检查项，P99 劣化超过阈值时阻断。
- **持续监控**：P99 > 250ms、Hikari pending > 0 持续 1 分钟即告警。

## 六、复盘清单

| 阶段 | 检查项 |
|------|--------|
| 目标 | 是否把"慢"定义成了可验收的 SLO（负载、百分位、错误率） |
| 基线 | 压测条件是否固定可复现；指标是否覆盖延迟分布、错误、资源、池状态 |
| 定位 | 是否先用 Trace 看时间分布，再用火焰图 / JFR / 慢日志确认根因 |
| 数据库 | 单请求 SQL 条数是否异常；慢日志是否按总耗时排序 |
| 连接池 | 是否用 Little 定律校验；事务内是否有 RPC |
| 调用链 | 独立的下游调用是否并行；客户端超时是否设置 |
| 缓存 | 读多写少的数据是否缓存；强一致数据是否被误缓存 |
| 代码 | 日志、序列化等 CPU 热点是否处理 |
| 验证 | 每项改动是否单独压测；是否有灰度与防回归手段 |

---

## 小结

- 先定 SLO 和基线，再动手；每项改动单独压测，收益才能归因
- 定位顺序：Trace 看时间分布 → 火焰图 / JFR 确认等待还是计算 → 慢日志按总耗时找 N+1
- 连接池排队先用 Little 定律算，缩短持有时间比加大池子有效
- 本例收益最大的是 N+1 批量化和把 RPC 移出事务，都属于"减少等待"
- 不做没有数据支撑的优化，GC 调参就是反例；全模块内容回顾见 [模块总览](./0_overview)
