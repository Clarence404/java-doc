# 分布式架构

架构不是越新越好，每一次演进都是用更高的运维和一致性成本换取**独立扩容、独立发布和团队自治**。本篇分清单体、集群、垂直拆分、SOA、微服务各自的收益与代价，以及什么时候不该拆、拆了要补哪些能力。

---

## 一、演进路线

![架构演进：部署单元与通信方式](../assets/distributed/architecture-evolution.svg)

| 架构 | 部署单元 | 拆分依据 | 通信方式 | 解决的问题 | 引入的代价 |
|------|----------|----------|----------|------------|------------|
| 单体 | 一个应用 | 不拆 | 进程内调用 | 起步快、调试简单、事务简单 | 代码膨胀后耦合高，只能整体扩容和发布 |
| 集群 | 同一应用多副本 | 不拆，只复制 | 副本之间无业务调用，前置负载均衡 | 吞吐量与单点故障 | 状态要外置（会话、缓存、定时任务） |
| 垂直拆分（分布式） | 多个应用 | 按业务线 | RPC / HTTP | 各业务独立扩容与发布 | 跨进程调用、分布式事务、链路排障 |
| SOA | 多个服务 + ESB | 按企业级可复用服务 | 经 ESB 集成，协议转换与编排都在总线上（智能管道） | 异构系统集成与服务复用 | ESB 成为中心瓶颈与变更热点 |
| 微服务 | 多个小型自治服务 | 按业务能力 / 限界上下文 | REST、gRPC、MQ 等轻量协议，逻辑在服务端（智能端点、哑管道） | 团队自治、独立演进 | 服务治理、可观测性、数据一致性全部要自建 |

## 二、几个容易混淆的点

### 1、集群与分布式

- **集群**是同一份应用的多个副本，每个节点都能完整处理请求，节点之间不做业务调用。它提升吞吐和可用性，但前提是应用**无状态**：会话放到 Redis（见 [分布式会话](./5_session)），定时任务避免多实例重复执行（见 [分布式调度](./6_job_scheduler)）
- **分布式**是把一个系统拆成多个不同职责的部分，靠网络协作完成一次业务。它带来独立扩容与发布，代价是网络延迟、部分失败和跨服务一致性
- 两者通常叠加使用：拆分后的每个服务本身又以集群方式部署

### 2、SOA 与微服务

二者的区别不在于「服务粒度大小」，而在于**集成方式与数据归属**：

- SOA 以 ESB 为中心，路由、协议转换、流程编排都放在总线上，服务往往共享数据库，目标是企业内异构系统的复用
- 微服务去掉了中心总线，每个服务拥有自己的数据，通过轻量协议直接通信，逻辑留在服务内部，目标是团队独立交付

### 3、微服务按什么拆

微服务按**业务能力或限界上下文**拆，而不是按「一个功能一个服务」拆。把「订单创建」「订单查询」拆成两个服务是纳米服务反模式：它们共享同一份数据和不变量，拆开只会制造分布式事务。拆分方法见 [微服务优势与挑战](/microservices/1_pros_and_cons) 与 [DDD 领域驱动设计](/architecture/3_ddd)。

### 4、拆分后的故障隔离不是自动获得的

「一个服务挂了不影响其他服务」只在补齐保护措施后才成立。同步调用链上的下游变慢，会占满上游线程池并逐级传导，形成雪崩。需要的措施：

- 每个远程调用都设置超时，重试有上限且只用于幂等操作，见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)
- 熔断与降级，见 [熔断](/high-avail/5_circuit_breaking)
- 非核心链路改成异步消息，削掉同步依赖

## 三、模块化单体与何时拆分

**模块化单体**（Modular Monolith）是单体与微服务之间的务实选择：一个部署单元，但代码按业务模块划清边界，模块之间只通过公开接口交互、不直接访问对方的表。它保留了单体的简单事务与调试体验，将来真要拆时，模块边界就是服务边界。Spring Modulith 可以在测试中校验模块依赖。

出现下面这些信号时再考虑拆分：

| 信号 | 说明 |
|------|------|
| 团队规模 | 多个团队频繁在同一代码库冲突，发布需要排队协调 |
| 扩容需求差异大 | 某个模块的负载远高于其他模块，整体扩容浪费明显 |
| 发布节奏不同 | 某些模块需要每天发布，另一些一个月才动一次 |
| 技术约束 | 某个模块需要不同的运行时或存储（如搜索、AI 推理） |

没有这些信号时，先把单体做成模块化单体。没有成熟的 CI/CD、链路追踪和监控就上微服务，结果通常是「分布式单体」：服务拆开了，却必须一起发布、一起出故障。

---

## 小结

- 演进的驱动力是规模与组织，而不是性能；拆分会增加单请求延迟和运维成本
- 集群是复制，分布式是拆分；集群要求应用无状态
- SOA 与微服务的核心差别是 ESB 智能管道与「智能端点、哑管道」，以及数据是否归服务私有
- 微服务按业务能力 / 限界上下文拆，避免纳米服务
- 故障隔离要靠超时、熔断、隔离与异步化，不是拆分天然带来的
- 没有明确信号时优先模块化单体
