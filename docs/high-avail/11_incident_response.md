# 故障应急与复盘

> 前置阅读：[混沌工程](./10_chaos_engineering)

故障不可能完全避免，可用性由 `MTBF / (MTBF + MTTR)` 决定（见 [可用性度量](./1_sla_slo)），**缩短发现和恢复时间是提升可用性最直接的手段**。本篇讲故障发生之后的事：怎么定级、谁来响应、先做什么止血、事后怎么无责复盘。

---

## 一、故障分级

**分级决定响应规格：谁要被叫起来、多快响应、要不要对外通告。** 分级标准要事先写清并量化，不能在故障现场讨论"这算不算大故障"。

| 指标 | 含义 | 主要影响因素 |
|------|------|------------|
| MTTD（平均发现时间） | 故障发生到被发现 | 告警覆盖率与质量 |
| MTTR（平均恢复时间） | 故障发现到业务恢复 | 响应速度、止血手段、预案完备度 |
| 复发率 | 同类故障再次发生的比例 | 复盘质量与改进项落实 |

| 级别 | 判定标准（满足任一） | 响应要求 | 通报范围 |
|------|------------------|---------|---------|
| P0 | 核心业务（下单、支付、登录）全面不可用；数据丢失或泄露；资损持续扩大 | 5 分钟内响应，立即拉起应急群，负责人与技术负责人到场 | 管理层、客服、必要时对外公告 |
| P1 | 核心业务部分不可用或成功率明显下降（如 > 5% 用户受影响）；重要功能完全不可用 | 15 分钟内响应，值班 + 相关服务负责人参与 | 技术负责人、业务方、客服 |
| P2 | 非核心功能不可用；核心业务性能明显下降但可用 | 30 分钟内响应，工作时间内处理 | 相关团队 |
| P3 | 影响很小或有临时绕过方案；单个用户或内部工具问题 | 1 个工作日内处理 | 提单跟踪 |

- 具体比例和时长按业务调整，但**必须量化**，最好直接与 SLO 挂钩：错误预算燃烧速率超过阈值即自动定为 P1
- **定级宁高勿低**：不确定时先按高一级响应，事后可以降级；低估导致的响应延迟代价更大
- 故障期间影响扩大要随时升级，不必等首次定级结束

## 二、On-call 与升级机制

**On-call 保证任何时间都有明确的第一响应人，升级机制保证第一响应人处理不了时能迅速找到更多人。**

### 1、On-call 排班

| 要素 | 做法 |
|------|------|
| 主备值班 | 每个服务或业务域设主值班与备值班，主值班未响应时自动通知备值班 |
| 轮换周期 | 常见一周一轮，交接时同步进行中的问题与近期变更 |
| 值班职责 | 响应告警、初步定级、执行止血、拉人升级，不要求值班人独自修复根因 |
| 值班负担 | 统计每班告警量与夜间唤醒次数，负担过重说明告警或系统稳定性需要治理 |

### 2、升级路径

| 条件 | 升级到 |
|------|-------|
| 告警 5 分钟未确认 | 备值班 |
| 15 分钟未确认或无法定位 | 服务负责人 / 团队 Leader |
| 定级为 P0，或涉及多团队 | 应急指挥（Incident Commander）与技术负责人 |
| 涉及资损、数据安全、合规 | 同步业务负责人与安全 / 法务 |

### 3、应急角色

P0 / P1 故障要明确分工，避免所有人都在排查、没人对外同步：

| 角色 | 职责 |
|------|------|
| 应急指挥（IC） | 统筹决策：定级、选择止血方案、协调资源，自己不深入排查 |
| 技术处理人 | 排查问题、执行止血和恢复操作 |
| 沟通负责人 | 定时在群内和对外同步进展（如每 15 分钟一次），回应业务与客服 |
| 记录人 | 记录关键时间点、操作与决策，为复盘提供时间线 |

## 三、应急流程

**应急的核心原则是先恢复、后定位：止血优先于找根因。**

![故障应急五步流程](../assets/high-avail/incident-response-flow.svg)

| 阶段 | 关键动作 | 常见误区 |
|------|---------|---------|
| 发现 | 告警、巡检、客服反馈；第一时间确认影响范围 | 只盯告警，忽略客服和舆情渠道 |
| 响应 | 确认告警、定级、拉应急群、指定 IC | 多人同时处理却没人统筹 |
| 止血 | 按预案执行回滚、切流、降级、限流等，让业务先恢复 | 在线上边猜边改代码，试图直接修复根因 |
| 恢复 | 验证核心指标回到正常，逐步撤销临时措施 | 指标刚好转就宣布恢复，没有观察期 |
| 复盘 | 故障结束后 1 ~ 3 个工作日内完成复盘 | 只写经过不写改进，或改进项无人跟进 |

止血阶段的第一个问题永远是：**最近有没有变更？** 大部分线上故障由发布、配置变更、数据变更或流量变化引起，找到变更时先回滚再说。

::: warning 保留现场
止血前尽量花一分钟保留排查线索：`jstack` 线程栈、`jmap -histo` 对象统计、GC 日志、异常实例先摘流量不销毁。但**保留现场不能阻塞止血**，P0 故障以恢复为先。线上诊断方法见 [线上诊断](/engineering/4_diagnosis)。
:::

## 四、止血手段清单

**止血手段要在平时就准备好、演练过，故障时只做选择和执行。** 按"影响小、见效快"的顺序优先考虑：

| 手段 | 适用场景 | 前提条件 | 注意事项 |
|------|---------|---------|---------|
| 回滚 | 故障与最近的发布、配置变更时间吻合 | 发布可一键回滚，数据库变更向后兼容 | 最常用、最有效；有疑似变更就先回滚 |
| 切流 | 单实例、单机房或单地域故障 | 多副本、多机房，切流工具可用 | 切流前确认目标有足够容量，见 [多活与容灾](./9_multi_active) |
| 摘除 / 重启 | 个别实例异常（假死、内存泄漏、连接泄漏） | 多副本且剩余容量足够 | 先摘流量保留现场，再重启；重启只是临时手段 |
| 降级开关 | 非核心依赖故障或系统资源紧张 | 开关和兜底逻辑事先实现并演练 | 按预案顺序打开，见 [降级](./6_degradation) |
| 限流 | 流量突增超过容量，或需保护故障中的下游 | 限流规则可动态调整 | 优先限低优先级流量，见 [限流与过载保护](./7_rate_limiting) |
| 扩容 | 流量增长导致资源不足 | 服务无状态，扩容能快速完成 | 瓶颈在数据库等共享资源时，扩应用反而加剧故障 |
| 隔离攻击流量 | 恶意刷量、CC 攻击 | WAF、黑名单能力 | 按 IP、设备、账号维度封禁 |
| 数据修复 | 错误数据写入导致的故障 | 有备份、binlog 或变更前快照 | 先止住错误写入，再修数据，修复脚本需复核 |

## 五、降低 MTTD 与 MTTR

**缩短 MTTD 靠告警质量，缩短 MTTR 靠变更关联、预案和演练。**

| 手段 | 作用 | 做法 |
|------|------|------|
| 基于 SLO 的告警 | 缩短 MTTD，减少误报 | 告警对准用户可感知的症状（成功率、延迟），用燃烧速率告警，见 [可用性度量](./1_sla_slo) 与 [告警体系](/observability/4_alerting) |
| 告警降噪 | 防止重要告警被淹没 | 聚合、抑制、静默重复告警；每条告警都应可操作，否则删除 |
| 变更关联 | 快速定位诱因 | 发布、配置、数据变更统一记录，告警时自动展示故障前后的变更 |
| 预案与 Runbook | 缩短决策和执行时间 | 每类常见故障写好判断条件、操作步骤、验证方法，告警直接链接 Runbook |
| 统一观测入口 | 缩短定位时间 | 指标、日志、链路通过 TraceId 关联，一个入口看全链路 |
| 故障演练 | 验证预案可用、熟悉操作 | 定期混沌实验和切流演练，见 [混沌工程](./10_chaos_engineering) |

一份 Runbook 至少包含以下内容：

| 字段 | 内容 |
|------|------|
| 触发条件 | 对应哪条告警、什么现象 |
| 影响判断 | 如何确认影响范围与级别 |
| 止血步骤 | 可直接复制执行的命令或平台操作，按顺序列出 |
| 验证方法 | 看哪些指标确认已恢复 |
| 升级联系人 | 处理不了找谁 |

## 六、无责复盘

**复盘的目的是改进系统，不是追究个人。** 人为失误是结果而不是原因：一次误操作能造成故障，说明系统缺少防护。追责只会让大家隐瞒信息，下一次故障的真实原因就更难找到。

### 1、复盘模板

| 部分 | 内容 |
|------|------|
| 概要 | 故障级别、影响时长、影响范围（用户数、订单数、资损金额）、SLO 错误预算消耗 |
| 时间线 | 按分钟记录：故障开始、告警触发、响应、关键决策、止血、恢复 |
| 关键指标 | MTTD、MTTR，以及各阶段耗时 |
| 根因分析 | 直接原因、根本原因，用 5 Whys 逐层追问 |
| 做得好的 | 哪些告警、预案、操作发挥了作用 |
| 改进项 | 每项都有负责人、截止日期、验收标准 |

### 2、时间线示例

| 时间 | 事件 |
|------|------|
| 14:00 | 订单服务发布 v2.3.1 |
| 14:06 | 下单成功率从 99.9% 降至 92%，燃烧速率告警触发 |
| 14:09 | 值班确认告警，定级 P1，拉起应急群 |
| 14:15 | 关联到 14:00 的发布，IC 决定回滚 |
| 14:22 | 回滚完成，成功率恢复至 99.9% |
| 14:52 | 观察 30 分钟无异常，宣布恢复 |

从时间线直接得出：MTTD 6 分钟，发现到恢复 16 分钟，其中定位诱因用了 6 分钟，是可以优化的环节。

### 3、5 Whys 根因分析

| 追问 | 回答 |
|------|------|
| 为什么下单失败？ | 新版本调用优惠服务的超时从 3s 被改成了 300ms，大量调用超时 |
| 为什么超时配置会被改错？ | 配置项在代码里硬编码，重构时误改 |
| 为什么测试没发现？ | 测试环境优惠服务响应快，300ms 内都能返回 |
| 为什么发布后 6 分钟才告警？ | 灰度批次只有 5% 流量，告警按全量成功率计算 |
| 为什么灰度没被拦住？ | 灰度阶段没有与基线版本的指标对比 |

根因不是"某人改错了配置"，而是**超时配置缺乏集中管理、灰度缺乏自动对比**。

### 4、改进项

| 改进项 | 类型 | 负责人 | 截止日期 |
|-------|------|-------|---------|
| 超时配置迁移到配置中心，并加取值范围校验 | 预防 | 订单组 | +2 周 |
| 灰度批次增加与基线版本的成功率对比，异常自动暂停 | 发现 | 平台组 | +4 周 |
| 发布平台在告警详情中展示最近变更 | 恢复 | 平台组 | +3 周 |

改进项按"预防、发现、恢复"三类分别考虑，并纳入团队迭代计划跟踪到关闭；**同一根因的故障再次发生，要先检查上次的改进项是否落实**。

---

## 小结

- 缩短 MTTD 与 MTTR 是提升可用性最直接的手段，应急机制要在平时建好
- 故障分级要量化、与 SLO 挂钩，定级宁高勿低；On-call 主备值班加明确的升级路径
- 应急遵循"发现 → 响应 → 止血 → 恢复 → 复盘"，先恢复后定位，有疑似变更先回滚
- 止血手段（回滚、切流、摘除、降级、限流、扩容）要事先准备和演练，配套 Runbook
- 复盘无责，用时间线和 5 Whys 找到系统层面的根因，改进项必须有负责人和截止日期
