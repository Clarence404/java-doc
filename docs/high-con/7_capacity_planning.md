# 容量评估与规划

> 参考链接：[Google SRE - Capacity Planning](https://sre.google/sre-book/software-engineering-in-sre/) · [Google SRE - Handling Overload](https://sre.google/sre-book/handling-overload/)

容量规划回答三个问题：**要扛多少流量、单机能扛多少、需要多少机器**。没有容量评估的系统，要么资源浪费严重，要么在大促当天被打挂。

---

## 一、流量估算方法

### 1、从业务指标推导峰值 QPS

| 步骤 | 公式 | 说明 |
|------|------|------|
| 1. 日活 | DAU | 来自产品 / 运营数据 |
| 2. 日请求量 | DAU × 人均操作次数 × 每次操作的接口调用数 | 一次"打开首页"可能触发 5 ~ 10 个接口 |
| 3. 平均 QPS | 日请求量 / 86400 | 或按有效时长（如 12 小时 = 43200s）计算更准确 |
| 4. 峰值 QPS | 平均 QPS × 峰值系数 | 日常峰值系数 2 ~ 5；大促 / 秒杀可达 10 ~ 100 |

**二八原则**也常用于估算峰值：80% 的请求集中在 20% 的时间内，`峰值 QPS ≈ 日请求量 × 80% / (86400 × 20%)`，约为平均值的 4 倍。

### 2、完整示例：电商商品详情服务

| 项目 | 数值 | 计算 |
|------|------|------|
| DAU | 500 万 | — |
| 人均浏览商品详情 | 20 次 | — |
| 每次详情页调用本服务 | 1 次 | 聚合接口 |
| 日请求量 | 1 亿 | 500 万 × 20 × 1 |
| 平均 QPS | ≈ 1157 | 1 亿 / 86400 |
| 日常峰值 QPS | ≈ 4600 | 二八原则 ≈ 平均 × 4 |
| 大促峰值 QPS | ≈ 4.6 万 | 日常峰值 × 10（历史大促数据） |

读写拆分估算：若下单转化率 2%，则下单峰值 ≈ 4.6 万 × 2% ≈ **920 TPS**，这是订单库需要承载的写入量（再乘以每单写入的 SQL 条数）。

### 3、依据历史数据修正

公式估算只是起点，更可靠的是历史数据：

- 取过去同类活动的峰值与同期日常峰值之比，作为本次峰值系数
- 按业务增长率（如同比 +50%）放大
- 关注**瞬时峰值**：秒杀开始的前 1 秒流量可能是分钟均值的数十倍，按分钟监控数据估算会严重低估

## 二、单机能力评估

单机能扛多少 QPS **只能压测得出**，不能根据理论推算：

| 步骤 | 要点 |
|------|------|
| 环境 | 与生产同规格机器、同版本、相近的数据量；下游依赖真实或按生产 RT 模拟 |
| 场景 | 按真实流量比例混合接口，而不是只压单接口 |
| 阶梯加压 | 逐步提升并发，记录 QPS、P99、错误率、CPU |
| 确定容量点 | 取 **P99 满足 SLA 且 CPU ≤ 70% 时的 QPS**，而不是压到崩溃的极限值 |
| 瓶颈确认 | 容量点出现时的瓶颈资源（CPU / 线程 / 连接池 / 下游） |

**示例结果**：8C16G 实例，混合场景下 P99 < 100ms、CPU 70% 时 QPS = 1500，记为单机容量 1500。

压测工具（JMeter、wrk、Gatling）与全链路压测方案见 [性能测试](/testing/7_performance_test)；压测过程中各层参数的调整见 [并发参数调优](/high-con/6_concurrency_tuning)。

## 三、机器数计算

```
机器数 = 峰值 QPS / 单机 QPS × 冗余系数
```

| 冗余来源 | 说明 | 典型取值 |
|----------|------|----------|
| 容量点余量 | 单机容量已取 70% CPU 水位 | 已包含在单机 QPS 中 |
| 故障冗余 | 一个可用区 / 若干实例宕机后仍能承载 | N+1 或按可用区数 × 1.5 |
| 估算误差 | 流量预估不准、突发热点 | 1.2 ~ 1.5 |

**接上例**：大促峰值 4.6 万 QPS，单机 1500 QPS，冗余系数 1.5：

```
机器数 = 46000 / 1500 × 1.5 ≈ 46 台
```

若部署在 3 个可用区，每个可用区 16 台，任一可用区故障后剩余 32 台承载能力为 4.8 万 QPS，仍能扛住峰值。

**别忘了下游**：应用扩到 46 台后，DB 连接总数 = 46 × 单实例连接池大小，需核算是否超过数据库 `max_connections`；Redis、MQ 同理。容量规划必须**全链路**评估，瓶颈往往在最薄弱的那一环。

## 四、存储容量估算

| 项目 | 公式 |
|------|------|
| 单行大小 | 各字段长度之和 + 索引开销（InnoDB 二级索引通常额外 30% ~ 100%） |
| 日增数据量 | 日写入行数 × 单行大小 |
| 总容量 | 日增量 × 保留天数 × 副本数 × (1 + 预留比例) |

**示例：订单表**

| 项目 | 数值 |
|------|------|
| 日订单量 | 100 万 |
| 单行 + 索引 | 约 1 KB |
| 日增量 | ≈ 1 GB |
| 在线保留 1 年（冷数据归档） | ≈ 365 GB |
| 1 主 2 从 + 30% 预留 | ≈ 365 × 3 × 1.3 ≈ 1.4 TB |
| 单表行数 | 3.65 亿，远超单表 2000 万行经验值 → 需分表（如 32 张表，单表约 1100 万行） |

Redis 容量同理：`key 数量 × (key 长度 + value 长度 + 约 50 ~ 100 字节元数据开销)`，并预留 30% 以上内存给 fork 持久化与碎片。分表规划见 [数据层扩展](/high-con/4_data_scaling)，冷数据归档见 [数据冷热分离](/architecture/1_cold_hot_data)。

## 五、大促预案

| 阶段 | 事项 |
|------|------|
| **T-30 天** | 流量预估；全链路压测找瓶颈；确定扩容清单（应用、DB、Redis、MQ 分区） |
| **T-7 天** | 完成扩容并再次压测验证；梳理降级开关与限流阈值；封网（冻结非必要变更） |
| **T-1 天** | 缓存预热（活动商品、库存、配置）；检查降级开关可用；值班与应急联系人就位 |
| **大促中** | 实时监控水位；按预案逐级降级；热点探测与动态限流 |
| **大促后** | 分批缩容；复盘峰值、瓶颈与预案执行情况，沉淀下次的峰值系数 |

**降级开关梳理**（按业务优先级）：

| 优先级 | 功能 | 降级方式 |
|--------|------|----------|
| P0 核心 | 下单、支付、库存 | 不降级，限流保护 |
| P1 重要 | 商品详情、购物车 | 降级为静态兜底数据 / 延长缓存 |
| P2 次要 | 评论、推荐、足迹 | 直接关闭，返回空 |
| P3 非必要 | 积分、成长值、消息通知 | 异步化延后处理 |

降级策略与开关实现见 [降级](/high-avail/5_degradation)，限流配置见 [限流](/high-avail/3_rate_limiting)，缓存预热见 [缓存架构设计 - 缓存预热](/high-con/2_cache_architecture)。

## 六、容量水位与告警

容量规划不是一次性工作，需要持续监控实际使用与容量上限的比值（**水位**）：

```
水位 = 当前峰值 / 容量上限（压测得出）
```

| 水位 | 状态 | 动作 |
|------|------|------|
| < 50% | 健康 | 可评估缩容 |
| 50% ~ 70% | 正常 | 关注增长趋势 |
| 70% ~ 85% | 预警 | 触发扩容评估，HPA 自动扩容 |
| > 85% | 危险 | 立即扩容，准备限流降级 |

**关键水位指标**：

| 资源 | 水位指标 | 告警参考 |
|------|----------|----------|
| 应用 | QPS / 单机容量、CPU、线程池活跃率 | CPU > 70% 持续 5 分钟 |
| 数据库 | QPS / TPS、连接数使用率、磁盘使用率 | 连接数 > 80%；磁盘 > 75% |
| Redis | 内存使用率、单分片 QPS、带宽 | 内存 > 75%；单分片 QPS 显著高于其他分片（热点） |
| MQ | 消费延迟、磁盘使用率 | Lag 持续增长 |

告警要区分"趋势预警"（按周增长率预测何时触顶，给扩容留出采购周期）与"实时告警"（突发流量）。监控体系见 [高并发总览 - 服务监控](/high-con/0_overview) 与 [可观测性](/observability/0_overview)。
