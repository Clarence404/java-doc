# 数据层扩展

> **本篇目标**：按改造成本从低到高掌握数据层的扩展路径，知道每一步解决什么瓶颈、代价是什么、何时该走下一步。
>
> **前置阅读**：[异步与削峰](./4_async_peak_shaving)
>
> **参考链接**：[ShardingSphere 官方文档](https://shardingsphere.apache.org/document/current/cn/overview/) · [MySQL Replication](https://dev.mysql.com/doc/refman/8.0/en/replication.html)

应用层无状态后可以随意加机器，瓶颈最终几乎都落在数据库：单机 MySQL 通常能承载数千 TPS、上万 QPS，单表超过千万行后索引与维护成本明显上升。数据层扩展按改造成本从低到高依次是：

| 步骤 | 解决的瓶颈 | 改造成本 |
|------|-----------|---------|
| 1. 缓存 | 读 QPS 高，数据可缓存 | 低 |
| 2. 读写分离 | 读 QPS 高，数据实时性要求较高 | 低 ~ 中 |
| 3. 冷热分离 | 数据量大，但大部分是历史数据 | 中 |
| 4. 垂直分库 | 不同业务争抢同一个库 | 中 |
| 5. 水平分表 / 分库分表 | 单表行数、单库写入与存储到顶 | 高 |
| 6. 引入专用存储 | 搜索、分析、时序等关系库不擅长的查询 | 中 ~ 高 |

**原则：能用前一步解决的，不急于走下一步。**

---

## 一、缓存先行

**读流量是瓶颈时，先加缓存，而不是先动数据库。** 命中率 90% 的缓存等于把数据库读压力降到原来的 1/10，改造成本远低于读写分离和分片。

多级缓存分层、一致性取舍、预热与缓存三大问题见 [缓存架构设计](./3_cache_architecture)。缓存解决不了的场景是：数据实时性要求高、千人千面难以缓存、写入本身是瓶颈——这时进入下一步。

---

## 二、读写分离

**主库负责写入，从库负责查询，利用主从复制把读压力分散到多个从节点。**

![读写分离](../assets/concurrency/read_write_split.svg)

适用前提是读多写少、读流量是瓶颈。读写分离**不能提升写能力**，写瓶颈需要分库分表。

### 1、实现方式

| 方式 | 代表 | 优点 | 缺点 |
|------|------|------|------|
| 应用层（客户端） | ShardingSphere-JDBC、`AbstractRoutingDataSource` | 无额外组件，性能好 | 与语言绑定，每个应用都要配置 |
| 代理层 | ShardingSphere-Proxy、MySQL Router、ProxySQL | 对应用透明，多语言 | 多一跳网络，代理需高可用 |
| 云数据库 | RDS 读写分离地址 | 开箱即用 | 依赖云厂商 |

ShardingSphere 读写分离配置见 [分库分表与中间件](/database/5_practice/2_sharding)。

### 2、主从延迟处理策略

**MySQL 复制默认异步，从库通常落后毫秒级，大事务或从库负载高时可达秒级甚至更久，"写后立即读"可能读到旧数据。**

| 策略 | 做法 | 适用场景 |
|------|------|----------|
| **强制走主库** | 对一致性要求高的查询显式指定主库（Hint） | 支付后查余额、下单后查订单 |
| **写后窗口内读主** | 用户写操作后 N 秒内（如 Redis 标记 3s）的读请求路由到主库 | 用户修改资料后立即查看 |
| **缓存兜底** | 写 DB 同时写缓存，读优先读缓存 | 读多、可缓存的数据 |
| **业务容忍** | 前端提示"处理中"或延迟跳转 | 发帖、评论等弱一致场景 |
| **等待 GTID** | 读从库前 `WAIT_FOR_EXECUTED_GTID_SET` 等待复制到位 | 强一致但仍想分流读 |
| **半同步复制** | 至少一个从库收到 binlog 才返回 | 降低数据丢失风险，并不消除读延迟 |

```java
// ShardingSphere：本次线程内的查询强制路由到主库
try (HintManager hint = HintManager.getInstance()) {
    hint.setWriteRouteOnly();
    return accountMapper.selectBalance(userId);
}
```

延迟原因与并行复制优化见 [MySQL 主从复制](/database/1_mysql/9_topic_replication)。

## 三、冷热分离

**大量数据写入后很少再访问（如 1 年前的订单），它们占用存储、拖慢热数据的索引与备份。冷热分离把冷数据迁到低成本存储，热库保持小而快。**

| 对比项 | 冷热分离 | 分库分表 |
|--------|----------|----------|
| 拆分维度 | 时间 / 访问频率 | 分片键哈希 / 范围 |
| 改造成本 | 低，业务查询基本不变 | 高，全链路改造 |
| 解决问题 | 数据量增长、存储成本 | 写入能力、连接数 |

很多系统在分库分表之前，先做归档与冷热分离就足以撑很长时间。判断标准、迁移策略与存储选型见 [数据冷热分离](/architecture/1_cold_hot_data)。

## 四、分库分表

**单库写入压力过大、单表数据量过大，且归档解决不了时，才通过分库分表拆分数据。** 先按业务垂直分库，再对仍然过大的表做水平拆分。

### 1、拆分方式

**垂直分库**：按业务域拆分，用户库、订单库、商品库各自独立，与服务拆分一一对应。

![数据分离-分库](../assets/concurrency/db_split.svg)

**水平分表**：同一业务的大表按规则（如 `user_id % 16`）拆成多张表，再分散到多个库。

![数据分离-分表](../assets/concurrency/table_split.svg)

| 拆分方式 | 解决问题 | 代价 |
|----------|----------|------|
| 垂直分库 | 不同业务互相争抢连接、IO | 跨库 JOIN 变为服务调用，跨库事务 |
| 垂直分表 | 大字段拖慢行扫描（如商品描述） | 查询需要两次或 JOIN |
| 水平分表（单库） | 单表行数过大，索引树过深 | 不解决单库资源瓶颈 |
| 水平分库分表 | 单库写入、连接、存储瓶颈 | 分片键约束、跨分片查询、分布式事务、扩容迁移 |

**何时考虑水平拆分**（经验值，需结合压测）：单表超过 2000 万行或 50GB；单库写 TPS 接近压测上限；单库存储接近磁盘或云实例上限。

### 2、分片键选择

**分片键决定数据分布与查询路由，选错几乎无法低成本修正。**

| 原则 | 说明 |
|------|------|
| 覆盖核心查询 | 绝大多数查询条件带分片键，否则会广播到所有分片 |
| 分布均匀 | 避免大商家、大 V 集中到一个分片（数据倾斜）；不要用时间戳做哈希分片键 |
| 不可变 | 分片键修改意味着数据迁移 |
| 关联表同键 | 订单表与订单明细表用同一分片键，保证同分片 JOIN（绑定表） |
| 业务语义 | 优先选 `user_id`、`tenant_id` 等业务核心维度 |

**多维度查询的常见做法**（以订单为例，按 `user_id` 分片，商家需按 `seller_id` 查）：

- **基因法**：把 `user_id` 的低几位嵌入 `order_id`，按 `order_id` 查询也能定位分片
- **异构索引表**：按 `seller_id` 再冗余一份（通过 Binlog / MQ 同步），用存储换查询
- **同步到 ES**：复杂条件、运营后台查询统一走 ES

### 3、分片算法

| 算法 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 哈希取模 | `hash(key) % N` | 分布均匀 | 扩容需重新分布数据 |
| 范围 | 按 ID 区间或时间（按月建表） | 扩容简单，范围查询友好 | 新数据集中在最新分片，易成写热点 |
| 一致性哈希 | 哈希环 + 虚拟节点 | 扩容只迁移部分数据 | 实现复杂，分布需虚拟节点调匀 |
| 映射表 | 路由表记录 key → 分片 | 最灵活，可单独迁移大租户 | 多一次查询，路由表本身要高可用 |

一致性哈希原理见 [一致性哈希](/distributed/9_consistent_hashing)，ShardingSphere 内置算法类型与配置见 [分库分表与中间件](/database/5_practice/2_sharding)。

### 4、分布式 ID

分表后不能再依赖数据库自增主键，需要全局唯一且趋势递增的 ID（有利于 B+ 树顺序写入）：

| 方案 | 特点 |
|------|------|
| 雪花算法（Snowflake） | 64 位，本地生成，趋势递增；依赖时钟 |
| 号段模式（Leaf-Segment） | DB 批量取号段，性能高，需双 Buffer 防抖动 |
| UUID | 无序，作为 InnoDB 主键会导致页分裂，不推荐 |

详见 [分布式 ID 生成](/distributed/8_id_generator)。

### 5、跨分片查询与事务

| 查询类型 | 问题 | 处理方式 |
|----------|------|----------|
| 不带分片键的查询 | 广播到全部分片，N 倍开销 | 异构索引表 / ES；限制仅后台使用 |
| 跨分片分页 `LIMIT 10000, 10` | 每个分片都要取前 10010 行再归并 | 禁止深分页，改为游标分页（`WHERE id > ? ORDER BY id LIMIT 10`） |
| 跨分片聚合 / 排序 | 中间件内存归并 | 预计算汇总表；交给 OLAP（ClickHouse / Doris） |
| 跨分片 JOIN | 不支持或性能极差 | 绑定表同键分片；小表广播；应用层组装 |
| 跨分片事务 | 本地事务失效 | 尽量同分片；否则最终一致（本地消息表、Seata 等，见[分布式事务](/distributed/4_transaction)） |

### 6、扩容迁移

**分片数从 N 扩到 2N 是分库分表中最复杂的操作**，常见的平滑迁移流程：

1. **双写**：新旧两套分片同时写（以旧库为准），可通过应用双写或 Binlog 同步（Canal / DTS）
2. **历史数据迁移**：全量拷贝历史数据到新分片，增量由双写 / Binlog 追平
3. **校验**：对比新旧数据行数与抽样内容，修复差异
4. **灰度切读**：按比例把读流量切到新分片，观察一段时间
5. **切写**：以新库为准，停止写旧库，保留回滚窗口后下线

**降低扩容频率的技巧**：一开始就规划足够的逻辑分片（如 1024 张表分布在 8 个库），扩容时只把整张表迁到新库，而不是重新哈希每一行。

ShardingSphere 内置迁移工具见 [分库分表与中间件](/database/5_practice/2_sharding)，Binlog 同步工具见 [CDC 工具](/database/5_practice/0_cdc_tools)。分布式数据库（TiDB、OceanBase）可以免去应用层分片，代价是运维体系与成本，见 [分布式数据库](/database/3_relational/1_distributed_db)。

## 五、引入专用存储

**关系库擅长事务与点查，不擅长全文检索、复杂多条件筛选、海量时序写入。让专用存储承担专用查询，MySQL 只保留核心事务数据。**

| 场景 | 痛点 | 引入存储 | 同步方式 |
|------|------|----------|----------|
| 商品搜索、多条件筛选 | `LIKE`、多字段组合索引失效 | Elasticsearch | Binlog → Canal → MQ → ES |
| 运营报表、实时统计 | 大表聚合拖垮主库 | ClickHouse / Doris | CDC 实时同步 |
| 用户画像、宽表 | 列多且稀疏 | HBase / 列存 | 离线 + 实时 |
| 监控、IoT 指标 | 海量时序写入 | InfluxDB / TDengine | 直接写入 |
| 计数、排行、会话 | 高频读写小数据 | Redis | 应用双写 / 异步回写 |

异构存储是**最终一致**的，同步延迟通常在秒级，业务要能容忍"刚下的单搜不到"。各类存储的特点见 [搜索数据库](/database/4_nosql/3_search_db)、[列式与 OLAP 数据库](/database/4_nosql/0_column_db)。

## 六、方案选型

| 瓶颈现象 | 优先方案 | 次选方案 |
|----------|----------|----------|
| 读 QPS 高，数据可缓存 | 缓存 | 读写分离 |
| 读 QPS 高，数据实时性要求高 | 读写分离 + 主从延迟策略 | 缓存 + 主动失效 |
| 单表数据量大，但大多是历史数据 | 冷热分离 / 归档 | 分区表 |
| 不同业务争抢同一个库 | 垂直分库 | — |
| 写 TPS 接近单库上限 | 水平分库分表 | NewSQL（TiDB 等分布式数据库） |
| 复杂搜索、多维筛选 | Elasticsearch | 异构索引表 |
| 大数据量聚合分析 | ClickHouse / Doris | 预计算汇总表 |

## 小结

- 扩展路径按成本排序：**缓存 → 读写分离 → 冷热分离 → 垂直分库 → 水平分表 → 专用存储**，能用前一步解决就不走下一步
- 读写分离只扩读不扩写，必须配套主从延迟策略（强制读主、写后窗口读主、等待 GTID 等）
- 分片键决定一切：覆盖核心查询、分布均匀、不可变；非分片键查询靠基因法、异构索引表或 ES
- 一开始就规划足够的逻辑分片，扩容按"双写 → 迁移 → 校验 → 切读 → 切写"平滑进行
- 异构存储都是最终一致，业务要能容忍秒级延迟
