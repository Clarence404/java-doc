# 高并发总览

> 参考链接：[advanced-java 高并发架构](https://gitee.com/Doocs/advanced-java#%E9%AB%98%E5%B9%B6%E5%8F%91%E6%9E%B6%E6%9E%84)

高并发系统设计的核心目标是：**流量变大时系统依然扛得住**——在有限的资源下支撑尽可能多的并发请求，保持合理的响应时间，并且流量翻倍时可以通过加机器（而不是重写系统）线性提升容量。

![高并发系统设计全景](../assets/concurrency/hc_overview.svg)

---

## 一、核心要点

**高并发关注的是"规模"**：请求量从 1k QPS 涨到 10w QPS 时，瓶颈在哪里、如何扩展、如何削峰、如何应对热点。单次请求快不快是高性能的问题，故障时停不停服是高可用的问题。

![高并发系统核心](../assets/concurrency/hc_sys.svg)

一个典型的高并发架构，涵盖从接入层到存储层的各个环节：

![高并发设计方案](../assets/concurrency/hc_sys_demo.svg)

高并发设计的基本思路可归纳为四句话：

| 思路 | 含义 | 典型手段 |
|------|------|----------|
| **能扩** | 任何一层都能通过加机器提升容量 | 无状态化、负载均衡、分库分表 |
| **少打** | 让请求尽量不落到最慢、最贵的那一层 | CDN、页面静态化、多级缓存 |
| **慢做** | 非核心、可延迟的工作不在请求链路上同步完成 | MQ 异步、削峰填谷、排队 |
| **分散** | 避免流量集中到单点、单 key、单行 | 热点打散、分桶、请求合并 |

## 四、推荐阅读路径

按请求从外到内的路径阅读：**入口 → 扩展 → 缓存 → 异步 → 数据 → 热点 → 调优 → 容量**。

| 阶段 | 要解决的问题 | 文章 |
|------|-------------|------|
| **入口与扩展** | 请求怎么进来、应用层怎么靠加机器扛量？ | [接入层架构](./1_access_layer) → [水平扩展与无状态化](./2_scale_out) |
| **读写分流** | 读流量怎么挡在数据库之前、写洪峰怎么摊平？ | [缓存架构设计](./3_cache_architecture) → [异步与削峰](./4_async_peak_shaving) |
| **存储与热点** | 数据库怎么扩展、流量集中到单点怎么办？ | [数据层扩展](./5_data_scaling) → [热点问题](./6_hotspot) |
| **调优与容量** | 参数怎么配、要多少机器、怎么持续监控水位？ | [并发参数调优](./7_concurrency_tuning) → [容量评估与规划](./8_capacity_planning) |

::: tip 容量估算也是设计的起点
阅读顺序上容量规划放在最后，但做新系统设计时应**先估算流量**（日活 → 平均 QPS → 峰值 QPS → 存储量），再据此决定需要哪些手段。估算方法见 [容量评估与规划](./8_capacity_planning)。
:::

## 六、与高性能、高可用的关系

"三高"是同一系统的三个观察角度，手段有交叉，但关注点不同：

| 模块 | 核心问题 | 衡量指标 | 典型手段 |
|------|----------|----------|----------|
| [高性能](/high-perf/0_overview) | 单次请求如何更快、更省资源 | RT、P99、CPU / 内存占用 | 算法与数据结构、池化、异步与批量、JVM 调优、SQL 优化 |
| **高并发** | 流量大时系统如何扛得住 | 峰值 QPS、并发数、水位 | 接入分层、水平扩展、缓存、削峰、分片、热点治理 |
| [高可用](/high-avail/0_overview) | 出故障时如何不停服 | 可用性 SLA、MTTR | 冗余、限流、熔断、降级、隔离、故障转移 |

- **高性能是高并发的基础**：单机 RT 从 100ms 降到 20ms，同样的线程数可承载 5 倍 QPS（Little 定律 `并发数 = QPS × RT`，推导见 [性能指标](/high-perf/1_metrics)）
- **高可用是高并发的底线**：流量超过容量时，靠限流、降级保住核心链路，而不是整体雪崩；限流在入口与网关的分层设计见 [限流与过载保护](/high-avail/7_rate_limiting)
- 同一手段往往兼顾多个目标：缓存既降低 RT（高性能）又分担 DB 流量（高并发），多副本既扩展读能力（高并发）又提供故障转移（高可用）
- 写流量的放大问题（一条动态推给百万粉丝的读写扩散取舍）见 [Feed 流系统设计](/scenario/8_feed_stream)
