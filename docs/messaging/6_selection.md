# MQ 选型

> **本篇目标**：能按业务特征在 Kafka / RocketMQ / RabbitMQ（以及 Pulsar 等其他 MQ）之间做出有理由的选择，避开选型时的常见误判。
>
> **前置阅读**：[Kafka](./2_kafka)、[RocketMQ](./3_rocketmq)、[RabbitMQ](./4_rabbitmq)、[其他 MQ](./5_other_mq)

前面几篇分别讲了三大 MQ 与 Pulsar 等其他 MQ 的原理与用法。选型时真正起作用的往往不是"谁性能最高"，而是**消息语义**（事务、延迟、回放、路由）和**团队能否运维得住**。本篇把差异收拢到一张表里，再给出场景化的建议。

---

## 一、三大 MQ 对比

**一句话定位：Kafka 是事件流平台（日志即存储），RocketMQ 是面向业务消息的中间件，RabbitMQ 是灵活路由的消息代理。**

| 维度 | Kafka（4.x） | RocketMQ（5.x） | RabbitMQ（4.x） |
|------|-------------|-----------------|-----------------|
| **定位** | 分布式事件流平台 | 业务消息中间件 | 通用消息代理 |
| **协议** | 自有二进制协议 | 自有协议（Remoting）/ 5.x Proxy 提供 gRPC | AMQP 0-9-1 / AMQP 1.0，插件支持 MQTT / STOMP |
| **吞吐量（相对）** | 最高 | 高 | 中 |
| **延迟** | 毫秒级，批量参数影响大 | 毫秒级 | 毫秒级，低负载下通常最低 |
| **顺序消息** | 分区内有序 | 队列内有序（5.x 按 MessageGroup） | 单队列 + 单消费者有序 |
| **事务** | 事务 = 跨分区原子写 + 精确一次（EOS），**不是**半消息回查 | **原生事务消息**（半消息 + 本地事务 + 回查） | 无事务消息；只有 AMQP `tx`（性能差）与 Publisher Confirms |
| **延迟消息** | 不原生支持 | 5.x 任意时间定时消息（4.x 为 18 个固定级别） | TTL + 死信交换机，或延迟消息插件 |
| **消息存储** | 按时间 / 大小长期保留 | 按时间保留（默认数天） | 经典 / 仲裁队列消费确认后删除；Stream 长期保留 |
| **消息回放** | 支持（重置 Offset） | 支持（重置消费位点） | Stream 支持；经典 / 仲裁队列不支持 |
| **死信** | 无内置，常用 `DeadLetterPublishingRecoverer` 写 DLT | 内置重试队列 + 死信队列 | 内置死信交换机（DLX） |
| **高可用** | 副本 ISR + Leader 选举，元数据 KRaft | 主从 / DLedger（4.x），5.x Controller 模式自动切主 | 仲裁队列（Raft）；4.0 已移除经典镜像队列 |
| **运维依赖** | 4.0 起不再依赖 ZooKeeper，只用 KRaft | NameServer + Broker（5.x 可加 Proxy） | 单一 Erlang 集群，部署最简单 |
| **生态** | Connect / Streams / Flink / CDC 最完善 | 国内电商、金融场景广泛，云厂商托管成熟 | Spring AMQP 成熟，多语言客户端齐全 |
| **典型场景** | 日志、埋点、数据管道、事件溯源 | 订单、支付等业务链路，最终一致事务 | 业务解耦、复杂路由、中低并发通知 |

几点说明：

- **吞吐量只看量级关系**：具体数字取决于消息大小、批量、刷盘和副本策略，压测前不要拿网上的"百万 / 十万 / 万"直接下结论
- **Kafka 的"事务"和 RocketMQ 的"事务消息"是两回事**：前者解决"消费—处理—生产"链路的原子性（读一个 Topic、写另一个 Topic 且只生效一次），后者解决"本地数据库事务与发消息"的一致性
- **RabbitMQ 新项目直接用仲裁队列**，需要回放或大积压时用 Stream；镜像队列在 4.0 已删除，老集群升级前要先迁移

## 二、场景决策表

| 场景 | 推荐 | 原因 |
|------|------|------|
| 日志收集 / 埋点上报 | **Kafka** | 顺序写、高吞吐、长期保留，Flink / Spark 直接消费 |
| 大数据 Pipeline / 事件溯源 / CDC | **Kafka** | 多个消费者组独立消费同一份数据，可按 Offset 回放；CDC 工具见 [数据库 · CDC 工具](/database/5_practice/0_cdc_tools) |
| 流式计算（读—处理—写） | **Kafka** | 事务 + EOS，Kafka Streams / Connect 生态完善 |
| 电商核心链路（订单 / 支付 / 库存） | **RocketMQ** | 事务消息、定时消息（超时关单）、重试与死信开箱即用 |
| 本地事务 + 发消息的最终一致 | **RocketMQ** 事务消息，或任意 MQ + 本地消息表 | 半消息回查保证"本地事务成功则消息必达"；方案对比见 [分布式 · 分布式事务](/distributed/4_transaction) |
| 中低并发业务解耦 / 微服务通知 | **RabbitMQ** | Spring AMQP 集成简单，Exchange 路由灵活，运维成本低 |
| 复杂路由（按规则分发、广播、优先级） | **RabbitMQ** | Direct / Topic / Fanout / Headers 交换机，支持优先级队列 |
| 对接外部系统 / 标准协议 | **RabbitMQ** | AMQP 标准协议，插件支持 MQTT / STOMP |
| IoT 设备上报 | 设备侧 **MQTT Broker**，后端汇入 **Kafka** | 海量长连接交给 EMQX 等专用 Broker，汇聚后的数据流进 Kafka；小规模可直接用 RabbitMQ MQTT 插件 |
| 多租户、跨地域复制、存储独立扩容 | **Pulsar** | 存算分离，原生多租户与 Geo 复制，详见 [其他 MQ](./5_other_mq) |
| 已在公有云上 | 优先云厂商托管版 | 运维成本往往比引擎差异更重要 |

选型时可以按下面的顺序过一遍：

1. **有没有硬性语义要求**：需要原生事务消息、任意延迟 → RocketMQ；需要长期保留与回放、流处理 → Kafka；需要复杂路由 → RabbitMQ
2. **量级**：日均消息量与峰值 QPS 是否超出 RabbitMQ 的舒适区（削峰的系统级设计见 [高并发 · 异步与削峰](/high-con/4_async_peak_shaving)）
3. **团队与生态**：已有的运维能力、语言栈、是否已有托管服务；同一公司尽量收敛到一到两种 MQ

## 三、常见误区

| 误区 | 正解 |
|------|------|
| "Kafka 就是最好的 MQ" | Kafka 擅长高吞吐与回放，但没有原生延迟消息，也没有 RocketMQ 那样"本地事务 + 发消息"的事务消息；小流量、强业务语义的场景未必合适 |
| "Kafka 不支持事务" | Kafka 支持事务：跨分区原子写 + 配合 `read_committed` 实现精确一次；它不提供的是半消息回查式的**事务消息** |
| "RabbitMQ 性能差" | 吞吐量级低于 Kafka / RocketMQ，但低负载下延迟很低、路由能力最强；对中低并发业务完全够用 |
| "RabbitMQ 镜像队列保证高可用" | 镜像队列已在 4.0 移除，高可用应使用仲裁队列 |
| "用了 RocketMQ 事务消息 / Kafka EOS，消费端就不用幂等" | 任何 MQ 都可能重复投递，消费端必须幂等：业务写入与去重记录（业务键唯一约束）放在同一个本地事务里，详见 [系统架构 · 幂等](/architecture/5_idempotence) |
| "在数据库事务里发消息就能保证一致" | 事务回滚了消息却发出去了，或事务提交了消息没发出去；应使用本地消息表、RocketMQ 事务消息，或在提交后发送并以本地消息表兜底 |
| "MQ 解决了分布式事务" | MQ 只能做到最终一致，中间状态仍需业务侧幂等、对账与补偿 |
| "换 MQ 很简单" | 顺序、事务、回放、重试语义差异很大，换 MQ 通常要改生产与消费逻辑，并重新设计监控和运维 |

## 小结

- Kafka 偏数据管道与事件流，RocketMQ 偏业务消息与事务，RabbitMQ 偏灵活路由与中低并发解耦
- Kafka 的事务是跨分区原子写与 EOS，RocketMQ 的事务消息是半消息回查，RabbitMQ 没有对应的事务消息
- 延迟消息：Kafka 不原生支持，RocketMQ 5.x 支持任意时间，RabbitMQ 用 TTL + DLX 或插件
- 版本基线：Kafka 4.0 去掉 ZooKeeper，RabbitMQ 4.0 去掉镜像队列，RocketMQ 5.x 引入 Proxy 与 Controller
- Pulsar 适合多租户、跨地域复制的平台型场景，普通业务项目仍以三大 MQ 为主（见 [其他 MQ](./5_other_mq)）
- 选型先看语义硬需求，再看量级，最后看团队与生态；无论选哪种，消费幂等与可靠投递都要业务自己兜底
