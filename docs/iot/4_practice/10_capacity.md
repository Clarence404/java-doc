# 压测与瓶颈排查

> 前置阅读：[可靠上报与接入层主备](./3_reliable_uplink)、[数据流水线](./4_pipeline)、[性能分析方法论](/high-perf/2_methodology)

Conduit 的吞吐从约 100 条/秒走到单机可靠无损 11,500 条/秒，中间每修掉一处瓶颈，下一处才露出来，还有几次结论是被自己的后续实验推翻的。本篇讲压测方法与合格判据、按时间线的八次定位、瓶颈迁移总表和方法教训，基线为 JDK 21、Spring Boot 3.5。

---

## 一、本篇做什么

压测发生在 2026-10-27 到 11-01 的六天里，每一次都有测试报告留在仓库的 [`docs/test-reports/`](https://github.com/Clarence404/conduit-iot/tree/811e441/docs/test-reports)。先看全貌：

| 日期 | 现象 | 瓶颈在哪 | 本篇章节 |
|------|------|---------|---------|
| 10-27 | 客户端全绿，入库只有约 100 条/秒 | 流水线每批只写一次 InfluxDB，批固定 100 条 | 三 |
| 10-27 / 28 | 投递停止，健康检查全绿，重启救不回 | EMQX 磁盘持久会话在积压下楔死 | 四 |

| 10-28 | 入库峰值 2,943 条/秒 | 流水线每条消息 2 次 Redis 网络往返 | 六 |
| 10-29 | 「入口天花板约 8,300 条/秒」 | 假象：发压器少喂了 1/6 | 七 |
| 10-29 | 9,000 条/秒时连接被强杀 | EMQX 单连接进程单核封顶 | 八 |
| 10-30 | 约 1,000 台设备时 EMQX 反复崩溃 | 文件描述符软限制 1024 | 九 |

每一节都按同一个顺序写：现象、怎么测、排除了哪些假设、结论与修复、修复后的数据。性能分析的通用套路（先定指标、再找瓶颈、一次只改一个变量）见 [性能分析方法论](/high-perf/2_methodology)，本篇只讲它在一个真实项目里走出来的样子。

## 二、压测方法

### 1、环境与负载

| 项 | 规格 |
|----|------|
| 被压机（单机部署） | VMware 虚拟机，8 vCPU / 7.6 GB 内存 / 16 GB 磁盘，Rocky Linux 10，独立部署包全部容器 |
| 拆分部署 | 两台 8 vCPU 虚拟机：一台只跑 EMQX，一台跑其余服务 |
| 宿主机 / 发压机 | 20 核 28 线程、32 GB 内存的台式机，虚拟机与发压程序在同一台物理机上 |
| 版本 | EMQX 5.10.5、InfluxDB 3 Core 3.12.0、Redis 7（`appendfsync always`）、PostgreSQL 16 |
| 报文 | QoS 1，3 个测点，默认不带消息 `id`（只有逐跳 QoS 1 保证） |

发压脚本在仓库 [`docs/script/loadtest/`](https://github.com/Clarence404/conduit-iot/tree/811e441/docs/script/loadtest)：

| 脚本 | 作用 |
|------|------|
| `loadgen.py` | 多进程 MQTT 发压器：建设备、刷新密钥、按速率发布、统计 PUBACK 时延；`--fleet` 模式每个进程用一个事件循环管 2,500 条连接，用来模拟海量低频设备 |
| `ladder.py` | 阶梯压测：逐档加设备数（或固定设备数逐档提速），每档稳态保持后按判据自动判定，首个不合格的档位即停；支持多台电脑分片发压 |
| `capacity_test.py` | 逐级加压，找积压不增长的最大稳态速率 |
| `remote.py` | 远程助手：查 Prometheus、数 InfluxDB 行数、数 EMQX 日志 |

压测用一个专门的「压测产品」，设备由 `loadgen.py provision` 通过正式 API 创建，密钥存在本地不入库的 `devices.json` 里。演示模拟器默认排除这个产品（`SIM_EXCLUDE_PRODUCTS=压测产品`），原因见第七节。

```bash
cd docs/script/loadtest
python loadgen.py provision --devices 600     # 把压测设备补齐到 600 台
python loadgen.py refresh                     # 每次压测前刷新密钥
python loadgen.py run --devices 600 --rate 16.67 --seconds 120 --workers 16   # 600 × 16.67 ≈ 10,000 条/秒
python ladder.py run --plan 2000,5000,8000 --rate 1 --hold 300               # 每台每秒 1 条，逐档加设备
```

### 2、三类测试

报告必须写明属于哪一类，三类的目的和读数方式都不同：

| 类型 | 目的 | 速率 |
|------|------|------|
| 容量测试 | 找无损的最大稳态速率 | 逐级上调到不合格，回退一档 |
| 压力测试 | 刻画失效模式与恢复能力 | 刻意过载，必须同时核对失效日志 |
| 回归对比 | 改造前后比吞吐 | 固定在容量以下的同一速率 |

### 3、接入 QPS 与入库 TPS

- **接入 QPS**：EMQX 确认（PUBACK）的条数
- **入库 TPS**：InfluxDB 里实际多出来的行数

两者在过载时会分开：EMQX 先向设备回 PUBACK，之后才在订阅端队列满时丢弃。10-28 的一轮 9,000 条/秒压测里，EMQX 确认了 8,881 条/秒，同时累计丢弃 51,671 条。所以**对外只能用入库 TPS**，接入 QPS 里可能含着随后被丢掉的消息。PUBACK 在 MQTT 里的含义见 [通信协议](../1_basics/1_protocol)，带 `id` 的端到端回执怎么补上这个缺口见 [可靠上报与接入层主备](./3_reliable_uplink)。

### 4、合格判据：计数守恒

速率证明不了不丢，计数才行。一次合格的容量测试要比对五个独立口径，全部相等：

| 口径 | 来源 |
|------|------|
| 客户端 publish 次数 | 发压器的「实际发送」 |
| 客户端 PUBACK 数 | 发压器的「已确认」 |
| EMQX 接收数 | `emqx_messages_received` 的计数差（不是 `rate`） |
| 流水线入库数 | `conduit_pipeline_processed_total{type="property"}` 的计数差 |
| InfluxDB 实际行数 | 直接 SQL `count(1)`，不经过应用的内存计数器，最有分量 |

同时要求 EMQX 丢弃增量、死信增量、EMQX 失效日志（`mailbox_overflow` / `maximum heap size` / `mqueue_is_full`）都是 0。

`ladder.py` 的阶梯压测在守恒之外再加稳定性判据，任一条不满足即不合格：

1. 全部设备通过鉴权（首次被拒的设备像真实设备一样 2 秒后重连一次，仍被拒才算）
2. 守恒：客户端收到 PUBACK 的条数 = InfluxDB 中压测产品在本档时间窗的实际行数，丢弃与死信为 0
3. 运行中没有设备掉线
4. PUBACK 时延 p99 不超过 1 秒
5. 稳态结束时总线积压与 transport 会话队列都不超过 5 秒的流量
6. EMQX 日志里没有连接被强杀、队列满、`emfile`，也没有过载告警（如 `runq_overload`）
7. 发压机 CPU 平均不超过 85%，超过则本档判为「结果不可信」

第 7 条是给自己设的：发压程序和被测虚拟机在同一台物理机上，发压机一满，测到的就是物理机的上限。

守恒判据本身也踩过坑，都记在 [VM 最大吞吐报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-29-vm-max-throughput.md) 里：

- 截取失效日志的时间锚点没带时区，Docker 按本地时间解释，多截了 8 小时，把 0 次数成 295 次
- 固定等 120 秒排空，高档位积压可达百万条，把「没排完」判成了「丢了」；改为等入库计数停止增长
- 用 Prometheus 里两个计数器相减，两端抓取时刻不同，实测会差 ±261 条，曾把合格的档位判成失败；最后一律以 InfluxDB 行数为准

## 三、流水线上限：每批只写一次

**现象**。第一轮按 1,000 条/秒（200 台 × 每秒 5 条）打 180 秒，客户端全绿：发送 180,873 条全部确认，PUBACK p50 1.0 ms、p99 51.8 ms。服务端完全跟不上：

| 时刻 | 消费组 lag |
|------|-----------|
| 24 秒 | 11,044 |
| 88 秒 | 68,574 |
| 195 秒 | 162,572 |

停止加压后，消费组已读条数 60 秒内只增长 6,000，即 **100 条/秒**，待确认条数全程恒为 100。server 容器 CPU 只有 3%～17%，说明不是算不过来，是在等 I/O。健康检查、EMQX 控制台全程显示正常——只看客户端会把这一轮判成通过。

**怎么定位**。三步排除：

| 实验 | 结果 | 结论 |
|------|------|------|
| 批 100 / 读取阻塞 1 秒 | 精确 100 条/秒 | 基线 |
| 批 1000 / 读取阻塞 1 秒 | 998 条/秒 | 10 倍且线性，每批有固定开销 |
| 批 100 / 读取阻塞 50 毫秒 | 仍 100 条/秒 | 读取阻塞不是原因 |
| 直接写 InfluxDB 10 行，连测 5 次 | 426 / 984 / 990 / 987 / 990 毫秒 | 就是它 |

InfluxDB 3 的 `--wal-flush-interval` 默认 1 秒，写入要等下一次 WAL 刷盘才返回；流水线每批只写一次 InfluxDB，于是**吞吐 = 批大小 ÷ 1 秒**。批大小当时写死 100，演示负载 17.4 条/秒只用到 17%，永远暴露不出来。

**修复**（提交 `076ec17`，后续又调整过默认值）：

```yaml
conduit:
  influx:
    max-request-bytes: 8388608   # 单次写入请求的字节上限，须小于 InfluxDB 的 10 MiB
  pipeline:
    batch-size: 20000            # 每批最多读多少条；-1 表示不限
    block: 1s
```

- 批大小可配。最初默认 `-1`（不限），第五节发现它会无界占内存后改为 20000：按「批大小 ÷ 1 秒」理论上限 2 万条/秒
- 写入按字节切块。把批调到 10 万条时 InfluxDB 返回 413（请求超过 10 MiB），而当时除 400 外的 HTTP 错误都被当成可恢复错误，流水线无限重试同一个超大载荷，健康检查仍是 UP。批太小只是慢，批太大是彻底停摆
- 413 与 400 一起改判为不可恢复

**修复后**。积压的 211,491 条一次读出，76 秒处理完，InfluxDB 实际行数 210,891 与发送数一致，约 **2,780 条/秒**。注意这是排空积压的速度，不是稳态入口速率。

修复过程中自己还引入过一次回归：默认批大小改成 `-1` 后，`XPENDING` 的 `COUNT` 不接受非正数，认领超时消息的路径直接报错，`PipelineIT` 红了 2 项；改为批大小非正时单次认领退回 1000 条。批处理的实现细节见 [数据流水线](./4_pipeline)，「攒批换吞吐」的通用道理见 [异步与批量](/high-perf/8_async_batch)。

## 四、磁盘持久会话在积压下静默楔死

这是整轮压测里最危险的一个发现：数据在丢，而所有监控都是绿的。

**现象**。同一天按 3,000 条/秒打 150 秒后，EMQX 的投递完全停止：

| 观测点 | 状态 |
|--------|------|
| EMQX 会话 | 在途 32 条冻结，`connected=true`，丢弃计数 0 |
| transport 投递线程 | 空闲，停在取队列上 |
| EMQX 与 transport 之间的 TCP | 收发队列都是 0 |
| 容器 | 没有重启，没有 OOM |
| 两侧日志 | 零错误 |
| 健康检查 | transport UP，主实例已连接 |

那 32 条「在途」消息既不在网络上、也不在 transport 里，只存在于 EMQX 会话进程的账本里。在途窗口占满后不再取下一批，投递永久停止。

**为什么重启救不回来**。重启 transport 后：接管会话 → 投递恰好 32 条 → 连接进程被杀 → 重连 → 再被杀，死循环。EMQX 日志给出了机制：

```text
[error] maximum heap size reached
Max Heap Size: 50331648        # Erlang 字 × 8 = 384 MB
emqx_persistent_session_ds:replay_batch/4
```

重放持久会话的积压时连接进程超过堆上限被杀；384 MB 正好是配置值 256 MB 的 1.5 倍。触发所需的积压只有约 3.3 万条。唯一的恢复方式是用同一个 clientId、`cleanStart=true` 连一次把会话丢掉——代价是积压永久丢失。

**排除的三个假设**：

| 假设 | 怎么验证 | 结果 |
|------|---------|------|
| `mqtt.retry_interval = infinity` 导致永不重传、窗口占满 | 对已楔死的会话改成 30 秒观察 150 秒；先改配置再建新会话重跑 | 都没用：前者零变化，后者照样在约 70 秒后冻结。这个配置对持久会话不生效 |
| transport 是瓶颈 | 看冻结时的线程栈与 socket | 投递线程空闲、socket 为空 |
| 会话用久了损坏 | 用全新会话重跑 | 同样约 70 秒后冻结 |

**对比实验**。唯一变量是 `durable_sessions.enable`，同一套 3,000 条/秒 × 180 秒负载：

| | 磁盘持久会话 | 内存持久会话 |
|---|---|---|
| 最终投递数 | 39,811（冻结） | 307,263（排空） |
| 停压后积压 | 不动 | 归零 |
| 丢弃计数 | 0（另有约 29 万条滞留在持久存储里） | 53,552（可见） |
| 连接超堆被杀 | 有，重连即死循环 | 0 |
| 恢复方式 | 人工丢弃会话，丢整个积压 | 自愈 |

内存会话那一轮的账能对上：客户端确认 360,415 ≈ 投递 307,263 + 丢弃 53,552。失败模式从「静默整批丢，必须人工」变成了「丢多少有计数，自己恢复」。

**修复**。关闭磁盘持久会话，改用内存持久会话：

```yaml
# deploy/dev/docker-compose.yml（节选）
environment:
  EMQX_DURABLE_SESSIONS__ENABLE: "false"
  EMQX_MQTT__MAX_MQUEUE_LEN: ${EMQX_MAX_MQUEUE_LEN:-100000}
  EMQX_MQTT__MAX_INFLIGHT: ${EMQX_MAX_INFLIGHT:-512}
```

代价是 EMQX 重启会丢掉还没投递的消息，这正是带 `id` 的设备侧重发要覆盖的场景。同时给 transport 加了会话监控：经 EMQX REST API 轮询自己的会话，「在途窗口占满且投递总数连续 6 次采样不变」就把健康检查置为 DOWN——这是唯一能发现楔死的信号，细节见 [部署与可观测](./11_deploy)。

**修复后**（[修复验证报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-28-session-wedge-fix-verification.md)）。同样 3,000 条/秒 × 180 秒：投递 367,376 条、丢弃 0、队列峰值 128 条、停压后队列与在途都归零；e2e 五个故障场景全部通过，重启与强杀 EMQX 两个场景里设备侧各重发 20 条，说明不是碰巧没有在途消息。

这次发现还推翻了前一天刚写下的一条决定（「不实施会话异常检测，因为原因不明、未复现」）：机制明确、压测可复现、只要入库慢于接入就会触发、而且零可观测。

## 五、transport 微批与在途窗口

**现象**。上一节内存会话那一轮里，307,263 条在约 250 秒内投完，持续投递速率只有约 **1,230 条/秒**，低于 3,000 条/秒的接入速率，所以队列触顶丢了 53,552 条。瓶颈在 transport 的单线程投递：每条消息一次 `XADD`。

**第一步：微批**。把报文攒成一批再写总线，稳态投递速率到约 1,980 条/秒，刚好越过 3,000 条/秒负载下的积压临界点（上一节「修复后」的数据就是微批之后的）。

**第二步：定量对照**。固定 6,000 条/秒过载、每组 90 秒，看 EMQX 向 transport 的投递速率（[对照报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-28-throughput-ab.md)）：

| 组 | 在途窗口 `max_inflight` | 批大小 | Redis `appendfsync` | 稳态（条/秒） | 相对基线 |
|----|------------------------|--------|---------------------|--------------|---------|
| 基线 | 32 | 32 | always | 2,605 | — |
| A | 32 | 32 | everysec | 3,442 | +32% |
| B1 | 256 | 32 | always | 3,662 | +41% |
| B2 | 256 | 256 | always | 3,309 | +27% |
| B3 | 1024 | 64 | always | 4,000 | +54% |

**被推翻的规则**。当天早些时候刚把「批大小必须等于在途窗口」写进了计划、配置示例和监控判据，这组数据否定了它：两组「相等」的配置都不是最优，256 / 256 垫底，最优的是窗口为批的 16 倍。原推理只对了一半：

- 批大于窗口：批永远攒不满，每批白等满 `batch-delay`——这一半成立
- 批等于窗口：EMQX 发 N 条、等全部确认、再发 N 条，这是停等协议，流水线深度为 1
- 窗口远大于批：提交当前批的同时下一批已在途，深度为窗口 ÷ 批

正确规则是 **`batch-size ≤ max_inflight`，且窗口应为批的若干倍**。报告里也分了强弱：「窗口大于批能显著提升吞吐」三轮一致、有机理解释，是强信号；B1 比 B2 高 10% 可能落在测量噪声内，不主张具体倍数。

**第三个约束后来才补上**。默认值一度定为 1024 / 64，随后在压力测试里发现连接被 `mailbox_overflow` 强杀：在途消息堆在 EMQX 连接进程的 Erlang 信箱里，信箱上限 `force_shutdown.max_mailbox_size` 默认 1000，1024 大于 1000 必然溢出。只看吞吐时漏掉了它。最终规则与默认值：

```yaml
# conduit-transport 的 application.yml（节选）
conduit:
  transport:
    mqtt:
      batch-size: ${TRANSPORT_BUS_BATCH_SIZE:64}    # batch-size ≤ max_inflight ≪ max_mailbox_size
      batch-delay: ${TRANSPORT_BUS_BATCH_DELAY:5ms} # PUBACK 的最坏额外延迟
```

仓库默认 `max_inflight` 512、批 64、信箱 1000。

**放弃的优化**。`appendfsync` 从 `always` 放宽到 `everysec` 有 +32%，但没有采用：transport 是写入 Redis 成功后才回 PUBACK 的，改成 `everysec` 意味着 Redis 崩溃时最多丢 1 秒已经向设备确认过的消息，这正是整个项目在消除的「已确认但没收下」。它只用来定位瓶颈，不作为调优建议。AOF 刷盘策略的取舍见 [Redis 核心原理](/cache/2_redis_core)。

**顺带发现的部署缺陷**。压测后宿主机满 swap：server 容器占了 4.7 GiB。原因是镜像入口写的是 `-XX:MaxRAMPercentage=75`，容器没有内存上限时 JVM 按宿主机总内存计算，四个 Java 容器各自认为可以用 5.6 GB 堆，而整台机器只有 7.6 GB。JVM 的行为完全正确，错在编排。修复是给每个 Java 服务设 `mem_limit`（server 1500m、transport 512m、模拟器 384m），并把流水线批大小从不限改为 20000——只加内存上限会把「宿主机 OOM」变成「JVM OOM」，两项必须一起定。

## 六、流水线：每条消息两次 Redis 往返

**现象**。6,000 条/秒过载下的三段速率峰值：接入 8,881、投递到总线 5,110、**入库 2,943** 条/秒。入库成了最窄的一段，消费组积压 38 万条，待确认恰好是一个批大小，说明流水线在满负荷而不是空转。

**排除的三个嫌疑**（[定位报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-28-pipeline-redis-roundtrips.md)）：

| 嫌疑 | 实测 | 结论 |
|------|------|------|
| InfluxDB 写入慢 | 单次写入 0.9 秒，但每批只写一次；CPU 0.16% | 排除 |
| JVM 内存上限（当天刚加，最自然的怀疑对象） | 堆占用 12.6%，GC 暂停 0.008 秒/秒 | 排除 |
| Redis `appendfsync always` | `XADD` 平均 6.92 微秒 | 排除为主因 |

**定位**。读代码：一批里 InfluxDB 写入、确认、在线状态都是每批一次，只有两处在逐条循环里——查设备身份是一次 `GET`，更新最新值是一次 `EVALSHA`。即每条消息 2 次网络往返，2 × 约 0.15 毫秒 ≈ 0.3 毫秒/条 ≈ 3,300 条/秒，与实测峰值 2,943 吻合。

**一个把人带偏的坑**。Redis 的 `commandstats` 会把 Lua 脚本内部调用的命令一并计数。第一次分析把脚本里的 2 次 `HGET`、2 次 `HSET` 也当成了独立往返，得出「每条 6 次往返」，据此预测约 1,100 条/秒，与实测 2,943 对不上。核对脚本后才发现这 4 次调用在服务端执行、没有网络开销。模型与实测不符时，先怀疑模型。

**修复**。身份改为批内去重后一次 `MGET` 预取；最新值改为一次 pipeline 提交全批，Lua 脚本原样复用（「旧数据不覆盖新值」按测点比较时间戳的语义不能为吞吐放弃）。一致性由 `LatestValueStoreIT#batchUpdateProducesExactlyTheSameStateAsOneByOneUpdates` 守住：同一组含乱序、同设备多条、同时间戳的输入，逐条写与批量写的 Redis 原始内容完全相等。

## 七、一份被作废的报告：发压器少喂了 1/6

批量化之后做了一轮容量测试，得出「可持续 6,600 条/秒，入口天花板约 8,000 条/秒，由单连接架构决定」。这份报告当天就被作废，原文头部加了作废说明，[仍留在仓库里](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-29-capacity-after-batching.md)。两处测量缺陷：

**一、实际供给比名义目标低 1/6**。压测产品带物模型，演示模拟器把它当成演示产品接管，给前 100 台设备重置了密钥，发压器手里那 100 台的密钥随即失效。而 paho 的 `connect()` 只发起 TCP，鉴权被拒不抛异常，脚本照样报「连接数 600、客户端错误 0」，那 100 台的消息一条也发不出去。名义 10,000 条/秒实际只喂进 8,333，EMQX 恰好收到 8,334——所谓的天花板就是供给本身。

识别特征：**接入量永远恰好是名义目标的固定比例**（当时是 5/6）。真正的容量上限是一个绝对值，不会随你给多少按比例缩放。复测证实供给 16,667 收 16,680、供给 20,000 收 20,009，全是「给多少收多少」。

**二、只记速率峰值，没做计数守恒**。改用守恒判据后，5,000 条/秒三次运行有两次丢消息（丢失率 0 / 1.55% / 4.8%），「可持续 6,600」高于实际无损速率。

修复在工具侧和产品侧各一处：`loadgen.py run` 等 CONNACK 到齐，有设备没通过鉴权就直接报错退出；模拟器新增 `SIM_EXCLUDE_PRODUCTS`（默认 `压测产品`），在读物模型、重置密钥之前跳过。server 另加了按原因计数的鉴权指标 `conduit.mqtt.auth{result, reason}`，密钥对不上时看板上「拒绝 · wrong_secret」直接不为 0，不用再靠对数推断。

同一份报告里还有一个更早的教训：初版发压器是 600 个 Python 线程，目标越高实际打出的越少（目标 8,000 打出 2,857，目标 10,000 只打出 1,679）。**判「容量以内」之前必须先确认喂进去的量达到了目标**，否则队列不涨只说明客户端打不动。

## 八、EMQX 单连接进程单核封顶

作废那份报告时，把「单连接是瓶颈」这个归因一起撤回了。后来的直接证据说明撤得太宽：8,300 是假的，结构问题是真的。

**先修信箱**。守恒判据下，信箱上限 1000 时 5,000 条/秒三次两次丢，日志是 `mailbox_overflow`。调到 10000 后 5,000 通过，7,000 多次运行有过有败，9,000 失败（入库约 7,410 条/秒到顶）。事后查明压测机实际运行的在途窗口是 1024 而不是仓库里的 512——压测机的配置落后于仓库，之前那次修正从未部署上去。从此多了一条纪律：**压测与排障前必须回读运行中的实际配置**。

**流水线分阶段计时**。新增指标 `conduit.pipeline.stage{stage=total|identity|decode|influx|latest|ack}`，单消费者、WAL 1 秒时：

| 目标（条/秒） | 每批条数 | 总耗时 | 写 InfluxDB | 写最新值 |
|--------------|---------|--------|------------|---------|
| 5,000 | 5,357 | 1,018 ms | 616 ms | 259 ms |
| 7,000 | 10,633 | 1,430 ms | 633 ms | 506 ms |

两条规律：写 InfluxDB 几乎不随批大小变化（它在等 WAL 刷盘，不是在传数据）；写最新值随批大小线性增长（约 48 微秒/条）。

**三个没起作用的改动**：

| 改动 | 结果 |
|------|------|
| WAL 刷盘间隔 1 秒 → 100 毫秒 | 负优化：写入降到约 79 毫秒，但批从约 1 万条缩到约 1,700 条，每批的固定开销摊不薄，吞吐 7,434 → 4,721（−36%），已回滚。那 1 秒等待是在攒批，不是浪费 |
| 最新值 Lua 快路径 | 自身波动 12% 大于与基线的差距 8%，测不出收益；脚本等价，保留 |
| 流水线 4 个消费者并发 | 单独测不出可分辨的收益；当时推断「流水线抢了 transport 的 Redis」，实测 Redis 只有 20%，推断错误 |

**直接证据**。用 EMQX 自带的 `recon` 在 9,000 条/秒下取 3 秒窗口的进程工作量（reductions）：

| 进程 | reductions |
|------|-----------|
| transport 的连接进程 | 1,524 万～1,805 万 |
| 任一设备的连接进程 | 约 4.6 万 |

transport 的连接进程约为单个设备连接的 350 倍，占 EMQX 全部工作约 35%；而 8 个调度器整体只有 41%～48%。EMQX 每条连接是一个 Erlang 进程，一个进程只能用一个核，全平台上行都挤过这一个进程，它已经顶在单调度器上限。此前对流水线和批大小的优化都在它下游，所以都看不到效果。

**验证方向再写代码**。先停掉 transport，换成 4 个只回 PUBACK 的探测订阅者做共享订阅，14,000 条/秒 × 90 秒：EMQX 收 1,259,995，订阅端实收 1,259,995，丢弃 0、强杀 0。再验证安全性：共享组成员离线时，落给它的消息排进它的会话，重连后补收，不丢。

**修复**（提交 `65ad9a2`）。主实例开多条连接，用共享订阅分摊 EMQX 的投递：

```yaml
conduit:
  transport:
    mqtt:
      client-id: ${TRANSPORT_CLIENT_ID:conduit-transport}
      connections: ${TRANSPORT_MQTT_CONNECTIONS:4}   # 设为 1 即退回单连接普通订阅
      shared-group: conduit-transport                # 订阅 $share/conduit-transport/conduit/+/+/up/#
```

EMQX 侧分发策略用 `hash_clientid`，同一设备固定走同一条连接，单设备保序。这个配置键在 `mqtt` 下，写成 `broker` 下会被静默忽略——又一次「命令成功但没生效」，以回读为准。多连接与主备切换怎么配合见 [可靠上报与接入层主备](./3_reliable_uplink)。

**共享订阅之后，下一处马上露出来**。10,000 条/秒时写最新值阶段 1,856 毫秒，占每批周期的 55%；Redis 在 12,000 条/秒时峰值 91%，其中 `evalsha` 占 58.9%。Redis 一满，transport 的 `XADD` 排队，回 PUBACK 变慢，EMQX 信箱又堆起来。修复是写最新值前先合并同一批里被后续消息完全覆盖的数据点（`LatestCoalescer`，提交 `141bdd6`）：10,000 档写最新值 1,856 → 98 毫秒，每批周期 3,367 → 942 毫秒。

**修复后的容量阶梯**（守恒判据，600 条连接）：

| 目标（条/秒） | EMQX 收 | 丢弃 | InfluxDB 行 | 整机 CPU | 结论 |
|--------------|---------|------|------------|---------|------|
| 10,000 | 1,200,000 | 0 | 1,200,000 | 约 84% | 通过 |
| 11,500 | 1,379,994 | 0 | 1,379,994 | — | 通过（两次都过） |
| 13,000 | 1,559,999 | 0 | 1,559,999 | 约 92% | 通过（三次过两次） |
| 16,000 | 1,920,000 | 0 | 1,498,501 | 96%～97% | 失败 |

结论：这台 8 vCPU 虚拟机上**可靠无损 11,500 条/秒**，13,000 是边缘，16,000 撞到硬件墙（8 个 vCPU 全满，1 分钟负载 15）。墙从软件移到了硬件。

**负载下强杀主实例**。10,000 条/秒下第 40 秒 `docker kill` 主 transport，备实例约 25 秒后接管，InfluxDB 最终行数等于实发数，零丢失；各口径的计数与重复的来源见 [可靠上报与接入层主备](./3_reliable_uplink)。

::: warning 数字的适用范围
这组数字测自压测机上的配置（信箱 10000、在途窗口 1024、transport 批 512），与仓库默认值（信箱 1000、窗口 512、批 64）不同，按仓库默认值部署复现不出来。另外「600 条连接打 11,500 条/秒」不等于「能接 11.5 万台每 10 秒一报的设备」，原因见下一节。
:::

## 九、12,000 条/秒的 CPU 去向与 900 台持续压测

容量到了硬件墙，要再提高就得先知道每条消息的 CPU 花在哪。

**CPU 拆解**（[报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-30-cpu-breakdown-12k.md)）。压测机上没有 `pidstat` / `perf`，做法是在负载中段对 `/proc/stat`、`/proc/softirqs` 和全部进程的 `/proc/<pid>/stat` 各取一次快照求差。实际供给约 11,400 条/秒、61 秒窗口：

| 进程 | 占用（核） | 约合每条消息 |
|------|-----------|-------------|
| EMQX | 2.69 | 236 微秒 |
| 内核软中断与硬中断（不计入任何进程） | 2.25 | 197 微秒 |
| conduit-server | 0.59 | 52 微秒 |
| transport 主实例 | 0.53 | 46 微秒 |
| Redis | 0.31 | 27 微秒 |
| InfluxDB | 0.16 | 14 微秒 |

EMQX 与内核网络合计约 5.3 核，占忙碌 CPU 的约 70%；平台自身（server、transport、Redis、InfluxDB）约 1.6 核。再往上，主要矛盾不在本项目的代码里，而在 MQTT 接入与网络栈。这直接促成了拆分部署：把 EMQX 单独放一台主机。

这一轮本身按守恒判据是失败的（昨天 13,000 三次过两次，今天 11,400 就失败），说明在墙附近单次结果波动很大，不能据单次下结论。还排除了一条误线索：`docker stats` 多次显示 EMQX 空闲时 CPU 55%～118%，而按线程采样 30 秒合计只有约 0.03 核——`docker stats` 的单次瞬时值是采样假象。

**900 台持续压测**（[报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-30-soak-900-devices.md)）。把压测设备从 600 加到 900、目标 11,700 条/秒长时间跑，属于压力测试，不产生容量结论。两轮都在十分钟内人工停止，但各有一个发现：

- **第一轮：EMQX 反复崩溃**。开压约 3 分钟后 EMQX 进入崩溃循环，10 分钟内重启 5 次。日志是 `emfile`（打开文件数超限）：Docker 默认的文件描述符软限制是 1024，每条 MQTT 连接占一个，900 台压测设备 + 174 台模拟设备 + transport 的 4 条就超了。内置数据库打不开日志文件，整个节点崩溃，设备重连再次打满，形成循环。**这不只是压测问题：按原编排，单个 EMQX 接到约 1,000 台设备就会反复崩溃**。修复是给 emqx 服务加 `ulimits.nofile` 软硬均 1048576

- **第二轮：连接数本身有成本**。修复后不再崩溃，但 CPU 饱和、持续丢失。对比上一节：600 条连接 11,500 条/秒无损，900 条连接 11,700 条/秒明显过载。多出来的连接在 EMQX 与内核上有显著开销，**吞吐不能按「条/秒 ÷ 每台频率」换算成设备数**

## 十、拆分部署与设备数阶梯

前面都是「少量连接、每条高频」，真实设备是「海量连接、每条低频」。拆分部署（EMQX 一台虚拟机，其余服务一台）之后改测设备数。拆分部署包的组成见 [部署与可观测](./11_deploy)。

### 1、每台每 10 秒一条

每档全部设备建连后保持 300 秒（[报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-30-device-ladder-split.md)）：

| 设备数 | 消息速率 | 结果 | PUBACK = InfluxDB 行 | EMQX 主机 CPU（核） | EMQX 内存 |
|--------|---------|------|---------------------|-------------------|----------|
| 10,000 | 1,000 条/秒 | 通过 | 299,987 = 299,987 | 1.14 | 1.2 GB |
| 15,000 | 1,500 条/秒 | 通过 | 449,995 = 449,995 | 1.27 | 1.5 GB |
| 20,000 | 2,000 条/秒 | 通过 | 599,990 = 599,990 | 1.61 | 2.1 GB |

2 万台时两台虚拟机都只用了不到 2 核，EMQX 内存约每万台增加 0.6～0.7 GB。过程中有两个发现：

**鉴权回调偶发失败（已修复）**。5,000 档有 1 台设备鉴权被拒，EMQX 日志是 `http_connector_do_request_failed, reason: closing`，server 端没收到请求。EMQX 用 8 条 HTTP 长连接回调鉴权，空闲时不主动关；Tomcat 默认空闲约 20 秒或同一连接满 100 个请求就关。EMQX 恰好在关闭的瞬间复用这条连接，请求发不出去，不重试，直接判设备未授权：

```yaml
server:
  tomcat:
    keep-alive-timeout: 30m          # 让连接只由 EMQX 一侧决定何时断开
    max-keep-alive-requests: -1
```

**3 万台时虚拟网卡挂死（测试环境限制）**。建连停在约 24,800 条后，EMQX 所在虚拟机整个断网，连 ping 都不通，内核日志是 `e1000 ... Detected Tx Unit Hang`。这台虚拟机用的是 VMware 的模拟网卡 e1000，换成半虚拟化的 vmxnet3 后不再挂死。这是测试虚拟机的网卡类型限制，不是 EMQX 或平台的上限。

换网卡后复测 2.5 万台却出现成批掉线：约 3,400 台一次性断开，p99 到 9.6 秒。已确认的消息没有丢（PUBACK 661,785 = InfluxDB 661,785），但按掉线判为失败。原因留到下一节。

### 2、每台每秒 1 条：第一次

`ladder.py` 首次正式使用（[报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-30-ladder-1s.md)）：2,000 台通过；5,000 台不合格——403 台掉线，p99 3.3 秒，EMQX 告警 `runq_overload`。守恒成立，应用主机只用了 3.7 核、没有积压。

这一轮得到一个重要的数：EMQX 每条消息的 CPU 约 0.9 毫秒，而上一节 600 条连接高频发送时约 0.24 毫秒。每台设备各占一条连接、每条消息单独一次网络往返，比少量连接批量发送贵数倍。**连接数才是成本**。

## 十一、鉴权超时：不是应用问题

拆分部署下两次出现设备鉴权被拒：EMQX 日志 `http_connector_do_request_failed, reason: timeout`（5 秒），server 端没收到请求，EMQX 随后把一条鉴权连接判为僵尸并重建。最初立项为「鉴权长连接偶发半开」，听上去像上一节 keep-alive 问题的变种。

**取证**（[排查报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-30-auth-timeout-investigation.md)）：

1. **两端连接表一致**。闲置约 13 分钟后，EMQX 一侧的 8 条鉴权连接与 server 容器内的 8 条一一对应，队列为空——空闲不会造成半开
2. **事故都发生在建连突发的开头**。一次是 3 万台档开始建连时（12 次超时），一次是闲置后 300 台集中建连时（116 次超时，同一毫秒批量触发）
3. **虚拟机被冻结过约 3 秒**。虚拟机内每 30 秒一行的采样，全天唯一一次超过 30 秒的间隔就在事故时刻；内核同时报 `sched: RT throttling activated`，是虚拟机被宿主机暂停后时钟跳变的典型迹象
4. **虚拟网卡在宿主侧丢了大量入站包**。VMware 日志里「取不到接收缓冲」的报错按分钟计数，高峰一分钟 3 万多次，全部与建连突发或过载重合；而虚拟机内核自己的 `rx_dropped` 是 0——丢包发生在虚拟化层

**对照实验**。清理掉宿主机上两个持续占 CPU 的无关进程后，其他都不变：

| 场景 | 缺缓冲丢包 | 鉴权失败 | 掉线 | p99 |
|------|-----------|---------|------|-----|
| 闲置后 300 台集中建连 | 0 | 0 | 0 | 2.3 ms |
| 5,000 台 × 每秒 1 条，180 秒 | 0 | 0 | 0 | 16.2 ms |

同一个 5,000 台场景，半小时前 p99 是 3.3 秒、掉线 403 台。差别只在宿主机负载。

**结论**：不是连接半开，是宿主机 CPU 紧张导致的虚拟网卡丢包。完整的链路是：

1. 宿主机 CPU 紧张（发压程序 + 两台虚拟机 + 其他程序），虚拟机得不到调度、短暂冻结
2. 虚拟机来不及补充网卡接收环，VMware 在宿主侧丢弃入站包
3. 恰好丢了鉴权请求或回应的那条 TCP 按指数退避重传，总等待超过 EMQX 的 5 秒鉴权超时，设备被判未授权
4. 一条连接 10 秒无响应，EMQX 视为僵尸重建

同一机制也解释了上一节 5,000 台档的掉线和 2.5 万台档的成批断开。

**处置与复测**（[复测报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-10-30-ring-timeout-retest.md)）：

- EMQX 鉴权回调超时从 5 秒放宽到 10 秒。丢包使鉴权超时这件事在任何网络都可能发生，设备会重连、不丢数据，但没必要卡得这么紧
- 网卡接收环从 1024 调到 4096。人为把宿主机 CPU 压到约 80% 做对照：1024 时 EMQX 主机丢 5,911 个包，4096 时为 0。接收环只决定能扛多长的停顿，不是根因
- 宿主机正常后复测此前不合格的两档，都通过：

| 场景 | 结论 | PUBACK = InfluxDB 行 | 掉线 | p99 |
|------|------|---------------------|------|-----|
| 5,000 台 × 每秒 1 条 | 通过 | 1,499,992 = 1,499,992 | 0 | 15 ms |
| 25,000 台 × 每 10 秒 1 条 | 通过 | 749,967 = 749,967 | 0 | 31 ms |

这次排查的教训是**先把「环境」当作嫌疑人**：应用日志里的超时，根因可能在三层之下。看 CPU 时 Load 与利用率各说明什么见 [Load 与 CPU 利用率](/os/5_load_cpu)。

## 十二、每秒 1 条的设备数上限

宿主机空闲（约 6%）、接收环 4096、鉴权超时 10 秒，继续向上探测（[报告](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/test-reports/2026-11-01-ladder-1s-higher.md)）：

| 设备数 | 结论 | 设备收到确认 / InfluxDB 行 | 掉线 | p99 | EMQX 主机 CPU | 应用主机 CPU | EMQX 主机缺缓冲丢包 |
|--------|------|--------------------------|------|-----|--------------|-------------|-------------------|
| 5,000 | 通过 | 1,499,992 = 1,499,992 | 0 | 15 ms | 42% | 34% | 0 |
| 6,000 | 不合格 | 1,727,016 = 1,727,016 | 818 | 2.5 s | 78% | 38% | 约 14.3 万 |
| 6,500 | 不合格 | 1,847,621 = 1,847,621 | 548 | 4.0 s | 88% | 36% | 约 23.6 万 |
| 8,000 | 不合格 | 1,837,555 < 1,837,830 | 1,977 | 8.0 s | 93% | 24% | 未采 |

三档不合格都**没有丢失已确认的消息**：InfluxDB 行数不少于设备收到的确认数（8,000 档多出的 275 行是已入库、但确认在设备掉线前没送达的）。不合格的原因是掉线与 p99。发压机 CPU 约 50%、应用主机不超过 38%，都不是瓶颈。

**瓶颈在 EMQX 主机的内核收包，不是 EMQX 进程**。6,000 档稳态时 EMQX 主机 8 核的 CPU 构成：

| 采样 | 用户态 | 内核态 | 软中断 | 空闲 |
|------|-------|--------|--------|------|
| 第 1 次 | 13.6% | 4.6% | 60.5% | 21.4% |
| 第 2 次 | 14.7% | 5.0% | 61.2% | 19.2% |
| 第 3 次 | 9.5% | 2.4% | 83.7% | 4.4% |

- 用户态（几乎全是 EMQX）只占 10%～15%，约 1 核；60%～84% 花在内核软中断，即网卡收包与协议栈处理
- 网卡中断分布严重不均：8 个队列里队列 0 的中断次数约为其他队列的 6 倍，对应的内核线程单核跑到 82%
- 软中断跟不上，接收环来不及补充，宿主侧开始丢包；丢包引发重传与掉线重连，负载进一步上升，所以 CPU 从 5,000 台的 42% 跳到 6,500 台的 88%，增幅远超设备数的增幅
- EMQX 容器走 Docker 桥接网络，每个包多一次桥接与 NAT，也计在软中断里

**结论**：在这套本地环境下，每台每秒 1 条的设备数上限在 5,000～6,000 台之间。限制来自 EMQX 所在虚拟机的虚拟网卡与内核收包路径，EMQX 本身只用了约 1 核，所以这不是平台或 EMQX 的上限，**不能外推到物理机或云主机**。这个数字只反映本系列对应的提交 `811e441` 当时的这套环境，后续复测结论以仓库最新测试报告为准。

## 十三、瓶颈迁移总表

| 次序 | 瓶颈 | 怎么发现的 | 修复 | 修复前 → 修复后 |
|------|------|-----------|------|----------------|
| 1 | 流水线每批只写一次 InfluxDB，批固定 100 | 服务端 lag 单调上涨；批大小与吞吐线性 | 批可配，写入按字节切块，413 改判不可恢复 | 约 100 → 排空约 2,780 条/秒 |

| 6 | EMQX 单连接进程单核封顶 | `recon` 看进程 reductions | 主实例 4 条连接共享订阅；同批合并最新值 | 当天早上可靠无损约 5,000 → 11,500 条/秒 |
| 7 | 文件描述符软限制 1024 | 900 台时 EMQX 崩溃循环，日志 `emfile` | `ulimits.nofile` 1048576 | 约 1,000 台即崩溃 → 不再崩溃 |
| 8 | 鉴权长连接被 Tomcat 关闭 | EMQX 日志 `reason: closing` | Tomcat keep-alive 30 分钟、不限请求数 | 偶发鉴权被拒 → 0 |
| 9 | 宿主机 CPU 紧张 → 虚拟网卡丢包 | 两端连接表、虚拟机冻结记录、虚拟化层丢包计数 | 清理宿主机、接收环 4096、鉴权超时 10 秒 | 5,000 台掉线 403 → 掉线 0，p99 15 ms |
| 10 | EMQX 主机内核收包软中断 | `/proc/stat` 构成、网卡队列中断分布 | 未解决，属本地虚拟化网络的上限 | 每秒 1 条 5,000 台通过，6,000 台起不合格 |

当前的容量口径：

- **单机部署**（8 vCPU 虚拟机，600 条连接）：可靠无损 11,500 条/秒，13,000 为边缘，16,000 是硬件墙
- **拆分部署**（两台 8 vCPU 虚拟机，与发压机同在一台物理机）：每台每 10 秒 1 条时 2.5 万台无损；每台每秒 1 条时 5,000 台通过，6,000 台起掉线
- 两组数字都反映提交 `811e441` 当时的这套本地环境，尤其是虚拟化网络的上限，不是平台的上限；后续复测结论以仓库最新测试报告为准

## 十四、方法教训

六天里结论被推翻了好几次，每次推翻都留下一条纪律：

- **只看客户端会把失败判成通过**。PUBACK 只说明 Broker 收下了。每一轮都要同时看服务端的 lag、丢弃、死信和实际行数
- **速率证明不了不丢，计数才行**。先守恒，再谈吞吐
- **先确认喂进去的量**。接入量恰好是名义目标的固定比例，先查负载端
- **改远程配置必须回读**。`sed` 管道符没转义、`docker compose up -d` 没重建容器、配置键写错层级，都是命令成功但没生效；一组「调大有效」的数据差点就是这么来的
- **压测前回读运行中的实际配置**，不以仓库内容为准。部署漂移曾让一条决定写错
- **只看吞吐会漏掉失效**。容量参数要同时核对吞吐与失效日志；搜强杀日志要用 `check_oom_shutdown|maximum heap size|mqueue_is_full|mailbox_overflow` 四个关键词，只搜一个会得到 0 条
- **模型与实测不符时先怀疑模型**。「每条 6 次往返」的模型预测 1,100，实测 2,943，错的是模型
- **单次结果说明不了什么**。同一配置两轮能差 33%；墙附近 13,000 三次过两次。结论分强弱，速率按区间理解
- **那 1 秒等待在攒批**。看上去是浪费的等待，可能正是吞吐的来源
- **本地虚拟机压测先看宿主机**。宿主机不紧张、网卡缺缓冲丢包计数没有增长，再相信结果

## 十六、已知限制与没做的

- **本篇的数字与结论只到提交 `811e441` 为止**，后续复测结论以仓库最新测试报告为准
- **所有数字都来自一台物理机上的虚拟机**。发压机与被测虚拟机抢同一组 CPU 和内存，拆分部署的数字反映的是虚拟化网络的上限；平台真正的上限要在物理机、云主机或分机发压下重测，`ladder.py` 的多机分片模式写好了但还没在正式一轮里用过
- **每秒 1 条的上限只定位到 5,000～6,000 台之间**，1 万～2 万台的档位因为阶梯在首个不合格档即停而没有执行；网卡收包集中在一个队列的原因没有查明
- **降低收包开销的方向还没有结论**。[交接文档](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/handoffs/2026-11-02-split-loadtest-ceiling.md) 列了三个候选：EMQX 容器改用宿主机网络（去掉 Docker 桥接与 NAT）、给网卡开 RPS / RFS 把收包分散到多个核、换物理机或另找电脑发压。在本篇依据的提交里它们都还是待定方向，没有对照数据
- **「1,000 台设备逐档提速」的 QPS / TPS 计划没有执行**。它用来在连接数固定的前提下单独刻画消息吞吐，[计划](https://github.com/Clarence404/conduit-iot/blob/811e441/docs/superpowers/plans/2026-10-30-qps-tps-1k-devices-test-plan.md) 已写好
- **单机 11,500 条/秒的配置没有进仓库默认值**。压测机上的信箱 10000、窗口 1024、批 512 是按「这台机器上不崩溃的最大吞吐」取的；信箱 1000 与共享订阅的组合没有测过
- **10 万条队列满载会撑爆连接进程的堆**。实测队列填满时会话进程堆到 513 MB，超过 384 MB 的实际上限被杀，约合每条 5.4 KB。「覆盖主备切换窗口」要求队列大，「不撑爆堆」要求队列小，两者冲突，默认值仍是 100000，调大前必须先确认堆余量
- **没有长时间浸泡**。最长的一档是 300 秒稳态；压测机磁盘只有 16 GB
- **没有混合租户负载**。一个高负载租户会不会拖慢其他租户，要等 [多租户与授权](./6_tenant) 里提到的配额与资源治理做完才有意义
- **延迟下限由 WAL 刷盘间隔决定**。4,000 条/秒时端到端延迟 P50 约 1.5 秒，其中约 0.9 秒在等 InfluxDB 刷盘；缩短它会让吞吐下降，是延迟换吞吐与持久性的取舍

## 小结

- 合格判据是计数守恒：客户端 PUBACK 数 = InfluxDB 实际行数，丢弃、死信、失效日志为 0；阶梯压测再加掉线、p99、积压、过载告警和发压机 CPU 五条。对外只用入库 TPS，因为过载时 EMQX 先确认再丢弃
- 流水线最初被钉在 100 条/秒：每批只写一次 InfluxDB，写入等 WAL 刷盘 1 秒，批固定 100。批可配、写入按字节切块、413 改判不可恢复之后排空约 2,780 条/秒
- EMQX 磁盘持久会话在约 3.3 万条积压下楔死，所有健康信号为绿，重启只会进入重放超堆的死循环。改内存持久会话后丢弃可见、可自愈，另加会话监控把「投递停滞」接进健康检查
- transport 微批加上「窗口为批的若干倍且远小于信箱上限」把投递从约 1,230 提到约 4,000 条/秒；流水线把每条 2 次 Redis 往返改成批量后，出口不再是最窄处
- EMQX 每条连接是一个单核封顶的进程。主实例开 4 条连接做共享订阅、同批合并最新值之后，8 vCPU 虚拟机上可靠无损 11,500 条/秒，负载下强杀主实例零丢失，墙移到了硬件
- 连接数本身有成本：600 条连接的吞吐不能换算成设备数。拆分部署下每 10 秒 1 条 2.5 万台无损，每秒 1 条 5,000 台通过、6,000 台起掉线，瓶颈是 EMQX 主机的内核收包软中断
- 鉴权超时与成批掉线的根因在三层之下：宿主机 CPU 紧张让虚拟机短暂冻结，虚拟网卡在宿主侧丢包，TCP 重传超过了 5 秒鉴权超时
- 有一份容量报告当天作废：发压器少喂了 1/6，接入量恰好是名义目标的固定比例。之后才有了「等 CONNACK」「回读配置」「守恒判据」这几条纪律
