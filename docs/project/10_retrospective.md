# 复盘

> 前置阅读：[项目演进总览](./0_overview)、[跨服务一致性](./7_consistency)、[项目难点与亮点面试题解答](/interview/16_scenario_highlights)

青柚商城订单服务从 3 人的模块化单体走到大促下单峰值 5000 QPS，前九篇各讲了一个阶段的取舍。本篇把这些决策串成一条线，讲做对的事、走过的弯路、准实时对账什么时候值得做、还没做的事，以及怎么把它讲成自己的项目经历。

---

## 一、四个阶段

![青柚商城订单服务的四个阶段](../assets/project/qingyou-evolution-timeline.svg)

| 阶段 | 规模 | 主要矛盾 | 文章 |
|------|------|---------|------|
| 一、单体起步 | 日订单 1 万，下单峰值约 20 QPS，3 人 | 尽快上线，同时别给后面埋坑 | [工程搭建](./1_project_setup)、[数据建模](./2_data_model)、[接口设计](./3_api_design) |
| 二、读多扛流量 | 日订单 10 万，商品详情读约 2000 QPS | 数据库读压力大、同步调用拖慢下单 | [引入缓存](./4_cache)、[异步化](./5_async) |
| 三、拆分服务 | 日订单 100 万，20 人 4 个小组 | 发布互相阻塞、库存与支付需要独立扩容 | [拆分服务](./6_split)、[跨服务一致性](./7_consistency) |
| 四、大促稳定性 | 大促下单峰值 5000 QPS，日常约 300 QPS | 流量尖峰、依赖故障扩散、问题难定位 | [稳定性](./8_stability)、[可观测与发布](./9_observability_release) |

每个阶段的变化都由数字或组织上的信号触发，而不是由「技术该升级了」触发：缓存等到数据库 CPU 高峰到 75% 才上，拆服务等到团队规模、发布冲突、差异化扩容三个信号同时出现才做。

## 二、决策时间线

| 阶段 | 决策 | 当时的理由 | 回头看 |
|------|------|-----------|--------|
| 一 | [工程搭建](./1_project_setup)：模块化单体，模块间只走 `api` 包，ArchUnit `ModuleBoundaryTest` 在 CI 守边界 | 3 人、20 QPS、两个月上线；微服务要的注册发现、网关、分布式事务 3 个人维护不过来 | 最值的一笔投入：阶段三拆库存时 `InventoryApi` 加 `@HttpExchange` 就成了远程契约，订单的调用处不用改 |
| 一 | [数据建模](./2_data_model)：雪花 `id` 做主键，对外订单号 `order_no` 单独一列，按字符串返回 | 不暴露业务量；给阶段三改订单号规则留口子 | 对。阶段三只改了 `order_no` 的生成规则，主键和表结构没动；但存量订单号的格式问题留到了后面，见第四节 |
| 一 | 数据建模：金额 `DECIMAL(12,2)`，状态只靠 `WHERE status = 旧状态` 条件更新流转 | 金额精度、并发改状态都是上线后很难改的坑 | 对。条件更新后来直接成了支付消息消费、超时关单、预占确认的幂等手段 |
| 一 | 数据建模：扣库存用 `stock >= ?` 条件更新，和写订单共享一个本地事务；不做预占 | 20 QPS 下单行锁竞争可以忽略，本地事务最简单 | 阶段一合适；拆服务后这个事务包不住了，成了 6、7 两篇的主要工作量 |
| 一 | [接口设计](./3_api_design)：`Idempotency-Key` 存入 `biz_no`，由 `uk_user_biz` 兜底；失败统一 `ProblemDetail`，错误码按模块加前缀 | 防重复下单、错误可区分、约定一次定好后面只做加法 | 对。拆服务时 `PayErrorCode` 连包迁出、前缀不变，远程调用里的 `code` 原样透传到前端 |
| 二 | [引入缓存](./4_cache)：只给商品详情上 Caffeine + Redis 两级缓存；订单详情、库存扣减、下单计价都不读缓存 | 详情读约 2000 QPS，数据库 CPU 高峰 75% | 对。上线一周回源约 8 QPS，数据库 CPU 高峰回落到 30%，下单 P99 回到 150 ms 左右 |
| 二 | 引入缓存：Redis 一主一从 + Sentinel，延迟双删用应用内定时任务，不上 binlog 订阅 | 数据只有几百 MB；写入口只有一个，不为低概率场景加主题或 CDC | 可以接受。风险写进了代价表，由 30 分钟 TTL 兜底 |
| 二 | [异步化](./5_async)：RocketMQ 5 托管实例 + 本地消息表 `t_outbox` + 去重表 `t_consume_record` | WMS 变慢拖垮下单；短信故障后没人补发 | 对。阶段三 `payment-service`、`inventory-service` 各建一份照搬，一致性方案几乎没有新增机制 |
| 二 | 异步化：超时关单改为 15 分钟定时消息 + 每 10 分钟扫描兜底 | 每分钟一次的扫描开始出现在慢查询里 | 对；阶段一先用扫描也合理，见第四节 |
| 三 | [拆分服务](./6_split)：只拆库存和支付，HTTP 接口客户端，Nacos 注册与配置，新服务先上 Kubernetes | 三个拆分信号同时出现；先拆边界清楚、出错可回退的两块 | 对。不拆订单、不上服务网格，4 个小组仍能按自己的节奏发布 |
| 三 | 拆分服务：数据按「先拆部署 → binlog 同步 → 对账 → 停写切换」迁移，不在业务代码里双写；`order_no` 改为嵌入用户 ID 低位 | 条件更新双写出错时没有可兜底的「正确值」 | 对。`t_inventory` 约 8 万行，同步和对账都在分钟级 |
| 三 | 拆分服务：下单过渡写法「远程 `deduct` → 写单 → 失败 `restore`」 | 让拆分能独立上线 | 有三个已知的洞，过渡期靠人工补，见第四节 |
| 三 | [跨服务一致性](./7_consistency)：按环节选方案，库存预占 `reserve / confirm / release` + 本地消息表 + 预占过期回查 + 每日对账；不用 Seata | 按 0.1% 的失败率估算每天约 1000 单落进缝里，人工修不过来 | 对。留下的缺口是对账每日一次，见第五节 |
| 四 | [稳定性](./8_stability)：超时预算收紧（网关 5s → 3s，`reserve` 读超时 800ms → 500ms）、Resilience4j 熔断与舱壁、网关限流 + 下单频控、按 7500 QPS 压测、提前扩容与 48 小时发布冻结 | 年中大促库存服务一慢，下单线程被占满，25 分钟里下单成功率只有 58% | 这些问题在 6、7 的代价表里早已列出，却等到一次大促事故才兑现；如果重来，大促前就按清单做完 |
| 四 | 稳定性：只对活动白名单 SKU 分 10 桶，按 `order_no` 哈希选桶、桶空换桶；不做 Redis 预扣 | 爆款预占是单行条件更新，单行约 600 TPS 是硬上限 | 对。预占、确认、释放和对账都沿用原来的模型，只多了换桶、再平衡与合并；代价是最后几件可能误判售罄，限购 1–2 件时可以接受 |
| 四 | [可观测与发布](./9_observability_release)：OpenTelemetry Java Agent 采集，`t_outbox` 存 `traceparent` 让 Trace 穿过消息；按 SLO 燃烧率告警；Argo Rollouts 按 Pod 数分流的金丝雀发布 | 一个下单失败要翻三处日志；发布从每周 1 次变成每天数次 | 定位时间从平均 40 分钟降到 8 分钟；但链路追踪接得偏晚，见第四节 |

## 三、做对的几件事

| 做法 | 体现在哪 | 换来了什么 |
|------|---------|-----------|
| **边界先于部署** | 模块化单体 + `api` 包 + ArchUnit；单体里也不跨模块 `JOIN`、不建外键 | 拆库存和支付时只改调用方式和事务边界，订单代码不碰对方的表 |
| **每个决策都写「暂不做」和触发条件** | 工程搭建、拆分服务里的「不做」表，跨服务一致性的「明确不做」 | 每一步都只解决眼前的瓶颈；到了阶段四，要做的事已经有清单 |
| **正确性交给数据库约束** | `uk_user_biz`、`uk_topic_key`、`uk_order_sku`、`t_consume_record` 主键，加上带旧状态的条件更新 | 下单幂等、消息去重、预占的空回滚与悬挂，用的是同一套手段，不依赖锁 |
| **一套可靠消息机制用到底** | `t_outbox` 在异步化引入，跨服务一致性直接复用；不用事务消息 | 新服务照搬即可，排查时都能查表回答「这笔订单的消息发没发」 |
| **写操作不自动重试，结果未知按失败处理** | 拆分后的 `deduct`、`restore`、`markPaid`，以及之后的 `reserve` | 不会因为重试扣两次库存；未知状态交给释放、回查和对账收敛 |
| **每个一致性窗口都有对用户的说法** | 「支付成功，订单确认中」、关单与付款竞态后的原路退款通知 | 最终一致没有变成客服工单 |

## 四、走过的弯路与如果重来

有些决策在当时是对的，只是换方案时付了本可以更小的代价：

| 弯路 | 当时的情况 | 付出的代价 | 如果重来 |
|------|-----------|-----------|---------|
| 超时关单从定时扫描起步（[数据建模](./2_data_model) → [异步化](./5_async)） | 阶段一还没有 MQ，每分钟扫一次 `idx_status_created` | 关单最多晚 1 分钟、库存多占 1 分钟；日订单 10 万后待支付常驻上千笔，扫描进了慢查询 | 阶段一仍然用扫描，但把关单写成按订单号的单笔幂等操作（后来的 `closeIfUnpaid(orderNo)`），换触发方式时只换调度，不动关单逻辑 |
| 订单号规则中途更换（[数据建模](./2_data_model) → [拆分服务](./6_split)） | 阶段一 `order_no` 就是 19 位雪花 ID 字符串，阶段三改为嵌入用户 ID 低位 | 单独一列 + 按字符串传输让改规则本身很便宜；但阶段一、二的存量订单号不含用户 ID 低位，真按 `user_id` 分片时，这部分旧订单按订单号定位可能要另行兼容 | 阶段一就把用户 ID 低位嵌进 `order_no`，成本只是生成器多几行 |
| 拆分过渡期的「先扣后补」（[拆分服务](./6_split) → [跨服务一致性](./7_consistency)） | 为了让拆分独立上线，下单先远程 `deduct`，写单失败再 `restore` | 超时不知道扣没扣、`restore` 可能失败、两步之间可能崩溃；过渡期靠每日核对脚本加人工修 | 库存预占的三个接口和拆库存同一批上线，过渡写法只在灰度切流期间存在 |
| 支付成功先同步调用 `markPaid`（[拆分服务](./6_split) → [跨服务一致性](./7_consistency)） | 支付迁出时先保持同步调用，失败让渠道重试回调 | 订单服务长时间不可用时只能人工补单 | `t_outbox` 在阶段二已经就绪，支付迁出时直接改发 `payment-succeeded` 消息 |
| 链路追踪接得晚（[接口设计](./3_api_design) → [可观测与发布](./9_observability_release)） | 阶段一的 `traceId` 由 `TraceIdFilter` 写入 MDC，只在单进程内有效 | 拆服务后请求跨 4 个进程，一个下单失败要翻网关、`mall-app`、库存服务三处日志，定位平均 40 分钟 | 拆服务的同一批就接入 OpenTelemetry Java Agent，至少把 trace 上下文传起来，大盘与 SLO 可以晚一点 |

几条弯路有一个共同点：**换方案的那一步本身没问题，问题在新旧方案并存的过渡期**。复盘之后的做法是，过渡写法上线时同时写明它的下线条件和下线日期。

## 五、准实时对账什么时候值得做

### 1、现在的状态

[跨服务一致性 · 每日对账](./7_consistency#七、每日对账) 每天凌晨 2 点跑一次，不一致最长一天后才被发现。但它不是唯一的防线，前面还有几层更快的收敛机制：

| 机制 | 频率 | 覆盖的问题 |
|------|------|-----------|
| 消费重试与死信告警 | 秒级到小时级 | 消息处理失败 |
| `t_outbox` 最老待发送时长告警 | 超过 1 分钟 | 中继或 Broker 故障，消息没发出去 |
| 预占过期回查 `ReservationExpireJob` | 每 5 分钟，大促期间每分钟 | 释放失败、确认消息丢失导致的 RESERVED 悬留 |
| 超时关单兜底扫描 | 每 10 分钟 | 定时消息丢失，订单一直待支付 |
| 每日对账 | 每天一次 | 以上都没拦住、只能从数据上看出来的差错 |

所以每日对账抓到的，是穿过了前面所有机制的漏网之鱼。100 万日订单下，只要差错数稳定、都能自动修复，每日一次就够了。

### 2、触发条件

出现下面任一信号，再把对账窗口从一天缩到分钟级：

| 信号 | 为什么一天太长 |
|------|---------------|
| 每日对账的差错数持续上升，或出现自动修复覆盖不了的新类型 | 说明前面某层机制有缺陷，等一天才发现，差错已经累积了一天 |
| 「付了钱订单还是待支付」类工单增多 | 用户比对账更早发现问题，客服在替系统对账 |
| 大促当天 | 爆款的 `reserved` 与预占记录对不上会直接造成少卖或超卖，次日发现时活动已经结束 |
| 新增资金路径（如新支付渠道、退款链路变复杂） | 资金类差错的处理时效要求高于库存类 |

不值得做的情况也很明确：差错每天个位数、全部能自动修复，且上表的告警都在正常工作。这时准实时对账只是再造一层已有的告警。

### 3、大致做法

- **只做资金相关的检查项**：先做「支付单 vs 订单」两项，库存类仍留在每日对账
- **复用每日对账的逻辑**：同样从只读从库按 `order_no` 拉数据、归并比对、写同一张差错表，自动修复复用补发 `payment-succeeded` 等幂等路径，不写专用修数据 SQL
- **窗口与在途**：每 5～15 分钟一个窗口，按 `updated_at` 增量拉取，并跳过最近几分钟的数据，跳过的时长要大于正常的一致性窗口（消息积压时可到分钟级），否则在途数据会被误报为差错
- **每日对账保留**：准实时对账只是补充，最终仍以每日对账为准

窗口划分与在途数据的处理见 [海量数据对账 · 时间窗口与在途数据](/scenario/3_reconcile#五、时间窗口与在途数据)。要做到秒级，可以订阅三个库的 binlog 做流式比对，见 [Flink CDC](/flink/6_cdc)，但那是又一套要运维的设施，在差错还很少的时候不值得。

## 六、没做的事及触发条件

| 没做 | 现在为什么不做 | 触发条件 | 到时先做什么 |
|------|--------------|---------|-------------|
| 多活与异地容灾 | 单元化要按 `user_id` 路由流量、拆分数据并双向同步，改造面覆盖全部服务 | 业务对机房级故障提出明确的 RTO / RPO 要求，或单地域容量接近上限 | 先做同城容灾与切换演练，再评估单元化，见 [多活与容灾](/high-avail/9_multi_active) |
| `t_order` 分库分表 | 先做历史订单归档；`order_no` 已嵌入用户 ID 低位 | 归档后单表仍超过 5000 万行，或热数据装不进 Buffer Pool | 按 `user_id` 分片，迁移按 [分库分表与中间件 · 不停机迁移五步](/database/5_practice/3_sharding#_1、不停机迁移五步) |
| 服务网格 | 只有 4 个 Java 服务，负载均衡和超时由 Spring Cloud 在进程内完成；金丝雀按 Pod 数分流已经够用 | 金丝雀需要精确权重或按用户、地域灰度（现在 `mall-app` 平时 4 个 Pod，5% 那一步实际是一个 Pod 的份额）；或出现多语言服务、需要服务间 mTLS | 先评估 Ambient 模式，再给 Argo Rollouts 配 `trafficRouting`，取舍见 [服务网格 · 落地取舍](/microservices/21_service_mesh#_3、落地取舍) |
| Redis 预扣库存 | 10 个桶已能扛住爆款的预占；预扣会让库存有两份，预占与对账都要重做 | 单 SKU 每秒上万的秒杀活动 | 单独走 [秒杀](/scenario/4_seckill) 的链路，不改普通下单 |
| 生产全链路压测 | 影子库改造涉及 4 个服务和 RocketMQ，一次漏改就污染生产数据；同构压测环境的结论目前可信 | 压测环境与生产的差异大到结论不可信，例如第三方支付渠道、网络出口成为瓶颈 | 先在一条链路上试点流量染色与影子库，再逐步铺开，见 [容量评估与规划 · 全链路压测与影子库](/high-con/8_capacity_planning#五、全链路压测与影子库) |
| Seata 等分布式事务框架 | 参与方只有订单、库存、支付三方；TC 集群是新的单点；全局锁会让爆款下单串行 | 同步参与下单的服务明显变多（如优惠券、积分抵扣都要在下单时同步扣减），手写协调的代码失控 | 先看能否继续用预占 + 本地消息表，原理见 [分布式事务 · Seata](/distributed/4_transaction#八、seata) |
| 继续拆订单、商品、用户 | 订单共享 `t_order` 和状态机；商品、用户扩 `mall-app` 实例即可 | 交易组再分组或订单查询压力独立变大；商品组与交易组发布冲突明显 | 先拆订单查询，写路径不动 |
| Redis Cluster | 缓存只有几百 MB，单个 Redis 远没用完 | 商品数涨到百万级、单条详情变大 | 评估分片后的多 key 命令限制 |
| binlog 订阅删缓存 | 商品只有一个写入口，提交后删除已覆盖 | 商品数据被搜索、推荐等多个系统消费 | 统一的商品变更订阅，见 [CDC 工具](/database/5_practice/0_cdc_tools) |
| 顺序消息 | `order-paid` 每笔订单只有一条，下游之间没有先后依赖 | 订单状态事件变多、消费方依赖事件顺序 | 按订单号的 FIFO Topic |

「先拆订单查询」「先看能否继续用预占」这类第一步，是本篇的建议，不是前面文章里已经做出的决定。

---

## 七、讲项目时怎么讲

把这个系列当成自己的项目经历讲时，按下面的顺序，控制在 3～5 分钟：

| 步骤 | 讲什么 | 青柚的例子 |
|------|-------|-----------|
| 1、一句话定位 | 业务、规模、你负责什么 | 生鲜电商的订单服务，从日订单 1 万做到大促下单峰值 5000 QPS，我负责下单与库存一致性 |
| 2、按阶段讲矛盾 | 每个阶段一个数字、一个矛盾、一个决策，不按技术清单罗列 | 详情读 2000 QPS 把数据库压到 75% → 只给商品详情上两级缓存 |
| 3、挑一两个难点深讲 | 用「背景问题 → 方案要点 → 可量化的效果 → 追问」展开 | 库存预占的空回滚与悬挂；本地消息表从异步化复用到跨服务一致性 |
| 4、主动讲没做的和代价 | 为什么不用、什么时候会用 | 为什么不用 Seata、为什么不拆订单、为什么对账每日一次 |
| 5、讲弯路 | 一条真实的弯路和如果重来怎么做 | 拆分过渡期的「先扣后补」 |

几个要点：

- **数字要自洽**：日订单 100 万平均每秒约 12 单，晚高峰约 300 QPS；说不清数字从哪来，面试官会顺着追问到底
- **讲决策，不讲名词**：「用了 RocketMQ」不是亮点，「为什么本地消息表而不是事务消息」才是
- **弯路是加分项**：能说出代价和改进，比只讲成功更像真的做过

每道亮点题的五段式写法与常见追问见 [项目难点与亮点面试题解答](/interview/16_scenario_highlights)，其中 Q5 讲的正是本地消息表；数字一律换成自己项目的实测值。

## 小结

- 四个阶段的每次变化都由数字或组织信号触发：读压力上来才加缓存，三个拆分信号同时出现才拆服务
- 最值的投入在阶段一：模块边界、独立的订单号列、数据库约束加条件更新，后面每一步都在用
- 一套 `t_outbox` + `t_consume_record` 从异步化用到跨服务一致性，不另起机制
- 弯路集中在过渡期：先扣后补、同步 `markPaid`、链路追踪偏晚；过渡写法上线时就要写明下线条件
- 阶段四的稳定性清单早在 6、7 的代价表里，却等到年中大促出事才兑现；热点库存选分桶而不是 Redis 预扣，是为了不推翻预占模型
- 准实时对账在差错上升、用户先于系统发现问题或大促时才值得做，先只做资金类检查项，每日对账保留
- 多活、分库分表、服务网格、Redis 预扣、生产全链路压测、Seata 都有明确的触发条件，没到就不做
- 讲项目按「定位 → 阶段矛盾 → 难点深讲 → 没做的事 → 弯路」展开
