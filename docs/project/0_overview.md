# 项目演进总览

项目演进模块用一个虚构的「青柚商城」订单服务，按真实项目的成长顺序，从单体起步一路演进到分布式、上线运维。每篇只讲这个阶段遇到的问题、可选方案、最终决策和代价，原理与细节都链接到各模块的主文档。

**版本基线（2026 年 10 月）**：JDK 21、Spring Boot 4、Spring Cloud 2025.1、MySQL 8.4、Redis 8、RocketMQ 5、Kubernetes 1.37

---

## 一、项目背景

青柚商城是一家做生鲜与日用品的中型电商，本模块只跟踪其中的**订单服务**：用户下单、扣减库存、支付、发货通知到售后的主链路。全系列共用下面这套设定，各篇的数字、命名都以此为准。

| 设定 | 取值 |
|------|------|
| 仓库 | `qingyou-mall`，Maven 多模块，Java 包名 `com.qingyou` |
| 核心实体 | 用户、商品、库存、订单、支付单 |
| 团队 | 起步 3 人全栈，阶段三扩到 20 人、4 个小组 |
| 部署 | 起步两台云主机；阶段三起迁到 Kubernetes |

本系列与 [订单](/scenario/5_order_system) 的分工：那篇按系统设计题的写法讲订单系统**最终长什么样**，这里讲它是**怎么一步步长成那样的**，以及每一步为什么这么选。

---

## 二、演进路线

| 阶段 | 规模 | 主要矛盾 | 对应文章 |
|------|------|---------|---------|
| 一、单体起步 | 日订单 1 万，下单峰值约 20 QPS | 尽快上线，同时别给后面埋坑 | [工程搭建](./1_project_setup)、[数据建模](./2_data_model)、[接口设计](./3_api_design) |
| 二、读多扛流量 | 日订单 10 万，商品详情读约 2000 QPS | 数据库读压力大、同步调用拖慢下单 | [引入缓存](./4_cache)、[异步化](./5_async) |
| 三、拆分服务 | 日订单 100 万，20 人 4 个小组 | 单体发布互相阻塞、库存与支付需要独立扩容 | [拆分服务](./6_split)、[跨服务一致性](./7_consistency) |
| 四、大促稳定性 | 大促下单峰值 5000 QPS | 流量尖峰、依赖故障扩散、问题难定位 | 稳定性、可观测与发布 |

每个阶段的数字只用来说明「为什么到了这一步要变」：在上一阶段就引入下一阶段的方案，往往是过度设计；到了瓶颈还不变，则会在线上付出代价。最后一篇「复盘」把全部决策串起来，整理成讲项目时的思路。

## 四、阅读方式

每篇都按同一个结构写：

1. **背景**：项目走到这一步，出现了什么问题，有哪些数字
2. **选项**：可选的几种方案，各自的代价
3. **决策**：选了哪个、为什么，以及明确不做什么
4. **关键实现**：只放最能说明决策的少量代码与配置
5. **代价与后续**：这个决策带来的新问题，由后面哪一篇解决

建议按编号顺序读，每篇开头都会交代承接的上一步；只关心某个阶段时，也可以从对应的文章单独读起。
