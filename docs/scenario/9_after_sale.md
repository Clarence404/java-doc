# 售后与退款

> 前置阅读：[订单](./7_order_system)、[支付](./8_payment)

售后要把一笔已经成交的订单部分或全部撤回来：钱退给用户，货回到仓库，券、积分各归其位。本篇讲售后单的状态机、可退多少怎么算、各方按什么顺序回退、超时怎么处理，基线为 MySQL 8.4、RocketMQ 5。

---

## 一、需求与挑战

### 1、售后类型

| 类型 | 什么时候 | 钱 | 货 |
|------|------|------|------|
| 未发货退款 | 已支付、还没出库 | 全退，含运费 | 没有离开仓库，库存直接放回可售 |
| 已发货仅退款 | 没收到货、少件、协商补偿 | 全退或部分退 | 不退回 |
| 退货退款 | 已收到货 | 商家收到退货后再退 | 寄回，质检后入库 |
| 换货 | 已收到货 | 不退 | 等于一次退货加一张新的发货单，本篇不展开 |

### 2、职责边界

| 谁 | 管什么 |
|------|------|
| 售后服务 | 售后单、审核、算可退金额、编排各方回退、超时处理 |
| 订单服务 | 订单主状态；全部退完时把订单关闭 |
| 支付中心 | 把钱退回去：占用可退额度、生成退款单号、调渠道，见 [支付](./8_payment) |
| 库存、优惠券、积分 | 各自的回退，都由事件触发、各自幂等 |

量不大时售后单可以放在订单服务里，[订单](./7_order_system) 就是这样写的。单独拆成服务是因为它流程长、规则多、改动频繁，而订单主流程要求稳定。

### 3、挑战

| 挑战 | 说明 |
|------|------|
| 多次部分退款 | 一笔订单可以分几次退，件数和金额的累计都不能超 |
| 金额怎么算 | 用了券、满减、运费之后，退其中一件该退多少 |
| 多方回退不同步 | 钱退了、券没还；或者库存放回去了、退款却失败 |
| 结果不确定 | 渠道退款要等几分钟到几天，退回的货在路上 |
| 各种超时 | 商家不审核、用户不寄回、商家收到货不确认 |
| 被人钻空子 | 退了钱又留下货、赠送的积分花掉之后再退款 |

## 二、整体架构

![售后与退款整体架构](../assets/scenario/after-sale-arch.svg)

售后服务自己不动钱、不动货、不动券。它做三件事：记下这次售后要退什么（售后单），决定什么时候可以退（状态机），以及在退款成功之后通知各方把各自的东西还回去（事件）。

---

## 三、售后单与状态机

### 1、表结构

```sql
CREATE TABLE after_sale (
    id                BIGINT       PRIMARY KEY,
    after_sale_no     VARCHAR(32)  NOT NULL,
    order_no          VARCHAR(32)  NOT NULL,
    user_id           BIGINT       NOT NULL,
    type              VARCHAR(16)  NOT NULL,           -- REFUND_ONLY / RETURN_REFUND
    status            VARCHAR(16)  NOT NULL,
    refund_cent       BIGINT       NOT NULL,           -- 这次申请退多少，申请时算好
    request_no        VARCHAR(64)  NOT NULL,           -- 客户端生成，同一次申请重试时不变
    return_tracking_no VARCHAR(64),                    -- 退货运单号
    deadline_at       DATETIME(3),                     -- 当前状态最晚停留到什么时候，见第七节
    created_at        DATETIME(3)  NOT NULL,
    updated_at        DATETIME(3)  NOT NULL,
    UNIQUE KEY uk_no (after_sale_no),
    UNIQUE KEY uk_request (order_no, request_no),
    KEY idx_deadline (status, deadline_at)
);

CREATE TABLE after_sale_item (
    id             BIGINT       PRIMARY KEY,
    after_sale_no  VARCHAR(32)  NOT NULL,
    order_item_id  BIGINT       NOT NULL,
    quantity       INT          NOT NULL,              -- 这一行退几件
    refund_cent    BIGINT       NOT NULL,              -- 这一行退多少钱
    KEY idx_after_sale (after_sale_no),
    KEY idx_order_item (order_item_id)
);
```

售后单的 ID 和订单在同一个分片上（都按用户分片），申请时可以和订单行在一个事务里。

### 2、状态机

![售后单状态机](../assets/scenario/after-sale-state.svg)

每一次流转都是带原状态的条件更新，影响 1 行才继续往下做：

```sql
UPDATE after_sale SET status = #{to}, deadline_at = #{deadline}, updated_at = NOW(3)
WHERE after_sale_no = #{no} AND status = #{from};
```

商家同意和用户撤销同时发生、超时任务和人工操作同时发生，都只有一个生效。

### 3、售后状态不放进订单主状态

订单的主状态只表达「这笔订单走到哪一步了」。一笔订单可以同时有几张售后单，各自处在不同阶段，把「退款中」塞进订单主状态会让状态数成倍增加。订单上只需要两样东西：每一行已经申请退了几件，以及全部退完时把订单改成已关闭。

## 四、可退多少

### 1、件数在售后侧占住，金额以支付中心为准

件数和金额分开管：

- **件数**是售后自己的事，支付中心不知道订单有几行。申请时用一条条件更新占住，同一行的两个并发申请不会都成功
- **金额**的上限只在支付中心记一份（交易单上的已申请退款额）。售后算出金额交给支付中心，超了由它拒绝。两边各记一份额度迟早对不上

```sql
-- 申请时占住件数；售后单被拒绝或关闭时再减回去
UPDATE order_item SET refund_qty = refund_qty + #{n}
WHERE id = #{orderItemId} AND refund_qty + #{n} <= quantity;
```

### 2、一件退多少钱

一行的实付金额，是这一行的金额减去分摊到它头上的优惠；怎么分摊见 [优惠券和营销](./5_coupon) 的「分摊到商品行」。下单时这个数就算好并存在订单行上，售后只读不重算。

退其中几件时按件数比例算，**最后一次退用减法**：

```java
/** 这一行本次退 n 件该退多少。lineRefunded 是这一行此前各次售后已占用的金额之和。 */
static long refundCent(long linePaidCent, int quantity, int refundedQty, long lineRefunded, int n) {
    if (refundedQty + n == quantity) {
        return linePaidCent - lineRefunded;            // 最后一次：剩多少退多少，尾差不会留下
    }
    return linePaidCent * n / quantity;                // 向下取整
}
```

一行实付 100 元、共 3 件，分三次各退 1 件：前两次各退 33.33 元，最后一次退 100 − 66.66 = 33.34 元，合计正好 100 元。每次都按比例取整的话，会留下 1 分钱永远退不出去。

### 3、运费、券和满减

这几条是业务规则，各家不一样，但要在下单时就定好，并把结果存进订单：

| 项目 | 常见规则 |
|------|------|
| 运费 | 未发货全退；已发货后原运费不退，退货的运费按责任方承担 |
| 优惠券 | 部分退款不返还；整单全部退完才返还，返还时已过有效期的直接置为过期 |
| 满减 | 退掉一件后不再满足门槛，也不重新计价，只按这一行分摊后的实付退 |
| 抵扣的积分 | 按行分摊，退哪一行就退回哪一行抵扣的积分 |

不重新计价是因为重算会让「已经付过的钱」变成一个不确定的数：同一笔订单先退 A 再退 B，和先退 B 再退 A，结果应该一样。

## 五、退款的顺序：先收回，再退钱，后归还

一次退款涉及三类动作：

| 类别 | 是什么 | 例子 |
|------|------|------|
| 收回 | 平台因为这笔订单给出去的东西 | 下单赠送的积分、赠品、返的券 |
| 退钱 | 把用户付的钱退回去 | 调支付中心 |
| 归还 | 用户因为这笔订单付出的、钱以外的东西；以及要放回去的资源 | 抵扣的积分、用掉的券、库存 |

顺序是**先收回，再退钱，后归还**：

- **收回放在最前面**，因为它可能做不到。赠送的积分已经被花掉了，就要从退款金额里折抵，或者让积分变成负数，这会影响到底退多少钱。退完钱再发现收不回来，就只能追讨
- **归还放在最后**，因为它不会失败，只会延迟，可以一直重试。反过来先把券还给用户、退款却失败了，券可能已经被用到另一笔订单上，再想撤回就要牵连第二笔订单

```java
/** 审核通过（仅退款），或确认收到退货（退货退款）之后调用。 */
public void startRefund(String afterSaleNo) {
    AfterSale a = afterSaleMapper.selectByNo(afterSaleNo);
    long refundCent = recallService.recall(a);          // 1. 收回：幂等，返回折抵之后实际应退的金额
    if (afterSaleMapper.toRefunding(afterSaleNo, a.status(), refundCent) == 0) {   // 带原状态的条件更新，同时记下实际应退金额
        return;                                         // 已被别的线程或撤销操作处理
    }
    // 2. 退钱：请求号固定用售后单号，重试多少次都是同一张退款单
    payClient.refund(a.tradeNo(), afterSaleNo, refundCent);
}

/** 消费支付中心的退款成功事件。 */
@Transactional
public void onRefundSuccess(RefundSuccess event) {
    String afterSaleNo = event.requestNo();
    if (afterSaleMapper.transit(afterSaleNo, "REFUNDING", "COMPLETED") == 0) {
        return;                                         // 重复事件
    }
    // 3. 归还：只写一条事件，订单、库存、优惠券、积分各自消费
    outbox.append("AFTER_SALE_COMPLETED", afterSaleNo, AfterSaleCompleted.of(afterSaleMapper.selectByNo(afterSaleNo)));
}
```

各方收到「售后完成」事件后做的事：

| 谁 | 做什么 | 怎么保证只做一次 |
|------|------|------|
| 订单 | 各行都退完了就把订单改为已关闭 | 带原状态的条件更新 |
| 库存 | 未发货的：已售减、可售加。退货的不在这里处理，等入库质检 | 预占记录的状态条件更新，见 [库存与票务](./6_inventory) |
| 优惠券 | 整单退完才返还 | 条件里带订单号和「已使用」状态，见 [优惠券和营销](./5_coupon) |
| 积分 | 退回这一行抵扣的积分 | 流水上「类型 + 售后单号」唯一 |
| 商户账户 | 从待结算款里扣回这笔钱 | 凭证号由退款单号派生，见 [账户与记账](./10_account_ledger) |

渠道退款的几种结果：

- **处理中**：最常见，银行卡退款可能要几个工作日。售后单停在「退款中」，等支付中心的事件；查渠道是支付中心的事，售后不自己去查
- **失败**：账户已注销、交易超过渠道的可退期限等。支付中心释放额度并发出失败事件，售后单转人工，改为退到站内余额或线下打款
- **调用超时**：结果未知。用同一个售后单号再调一次，支付中心返回的是同一张退款单

## 六、退货物流

退货退款比仅退款多出两步：用户把货寄回，商家确认收到。

1. 商家同意后，售后单进入「待寄回」，用户寄出并填写运单号
2. 售后服务按运单号订阅物流轨迹，物流显示已签收时提醒商家
3. 商家确认收货并质检：没问题就进入「退款中」；货不对、有损坏则拒绝或协商部分退款
4. 入库由仓储完成，质检合格的进可售库存，残次的进锁定库存，各写一条库存流水

物流轨迹只用来提醒和计时，不直接推动退款：签收的可能是驿站，包裹里也可能不是原来的货。真正的依据是商家的确认，或者确认超时。

## 七、超时自动处理

售后流程里每个等别人操作的状态都要有期限，否则会一直挂着。

| 状态 | 等谁 | 期限（示例） | 到期后 |
|------|------|------|------|
| 待审核 | 商家 | 48 小时 | 自动同意 |
| 待寄回 | 用户 | 7 天 | 自动关闭，把占住的件数减回去 |
| 待收货 | 商家 | 物流签收后 7 天 | 自动确认收货，进入退款 |
| 退款中 | 渠道 | 按渠道承诺的时效 | 不自动处理，超时告警、人工跟进 |

实现上每次流转都把下一个期限写进 `deadline_at`，到点的触发用 [延迟任务](./25_delay_task) 或定时扫描：

```sql
SELECT after_sale_no, status FROM after_sale
WHERE status IN ('APPLIED', 'WAIT_RETURN', 'WAIT_RECEIVE') AND deadline_at < NOW(3)
ORDER BY deadline_at LIMIT 200;
```

到点只是一个「该检查了」的信号。真正执行时仍然是带原状态的条件更新：商家在最后一秒点了拒绝，自动同意的那条更新影响 0 行，什么都不发生。所以期限改了、状态变了，都不需要去取消已经发出的延迟消息。

「退款中」不设自动处理，是因为钱的去向只有渠道知道，超时不代表失败。

## 八、防刷

| 风险 | 做法 |
|------|------|
| 改请求里的金额 | 金额只在服务端算，客户端只传退哪一行、几件 |
| 同一行并发申请多次 | 件数用条件更新占住；同一次申请靠请求号的唯一键 |
| 花掉赠送的积分再退款 | 先收回，收不回的从退款金额里折抵 |
| 仅退款被滥用 | 按用户统计近期的退款率和仅退款次数，超过阈值的转人工审核 |
| 退回的不是原来的货 | 高价值商品强制质检后再退；退货运单号要和售后单绑定，重量明显不符的提醒商家 |
| 极速退款带来的垫付 | 只对信用好的用户开启：寄出即退，平台先垫付，货没收到再追回。垫付额度要有上限，并单独记账 |

## 九、容量估算

沿用 [支付](./8_payment) 的假设：**日成功支付 500 万笔**，退款率 5%，1 KB = 1024 B。

**售后单**：5,000,000 × 5% = 250,000 张/天，日均 250,000 ÷ 86,400 ≈ 2.9 张/秒。大促之后的几天是高峰，按日均的 20 倍，2.9 × 20 = 58 张/秒。

**存储**：每张售后单 0.5 KB，平均 1.5 行明细、每行 0.2 KB，合计 0.8 KB，索引放大 1.5 倍为 1.2 KB。每天 250,000 × 1.2 KB = 300,000 KB ≈ 293 MB，每年约 107 GB，随订单表一起按用户分片即可。

**超时扫描**：同时处在等待状态的售后单，按平均停留 3 天算约 250,000 × 3 = 750,000 张，走 `(status, deadline_at)` 索引每次取 200 行，没有压力。

从这几个数能看出，售后不是一个要扛量的系统，每秒几十张单任何一种实现都能做到。难的是不能错：每一分钱、每一件货、每一张券的去向都要对得上。

---

## 小结

- 售后服务只管售后单、金额计算和编排，钱、货、券、积分都由各自的系统回退
- 件数在售后侧用条件更新占住，金额的上限只在支付中心记一份
- 行实付在下单时算好存下来，退款按件数比例取整，最后一次用减法，不留尾差；退款不重新计价
- 顺序是先收回、再退钱、后归还：收回可能做不到，会影响退多少；归还只会延迟，可以一直重试
- 每个等人操作的状态都设期限，到点只是检查的信号，执行靠带原状态的条件更新
- 退款中不自动处理，钱的去向以渠道的结果为准
