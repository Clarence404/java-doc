# 同类问题横向对照

> 前置阅读：[系统设计方法论](./1_design_method)

同一个问题在不同场景里的解法并不一样，差别来自争抢的是什么、量有多大、错了的代价有多高。本篇把七个常见问题在各场景里的做法放在一起对照，只列结论与选择依据，实现细节见各篇正文。

---

## 一、不能超发

有限的东西被并发争抢：库存、券、红包份额、座位、空闲司机、可退额度。共同的要求是**判断和扣减必须是一个原子动作**，不同的是这个动作放在哪里做。

| 场景 | 争抢的是什么 | 做法 | 为什么这么选 |
|------|------|------|------|
| [库存与票务](./6_inventory) | 可售库存 | 一条条件更新：`available >= n` 才扣减；多个 SKU 按固定顺序逐个更新 | 判断与扣减在同一条语句里由行锁保证；库存充足时不会像乐观锁那样失败重试 |
| [秒杀](./11_seckill) | 活动库存 | Redis 里一个 Lua：判已购、判库存、扣减、记已购；数据库的 `stock > 0` 条件更新做最终兜底 | 条件更新本身能防超卖，但所有请求争同一行的行锁，数据库撑不住瞬时流量 |
| [优惠券和营销](./5_coupon) | 券的张数、每人限领 | 领券用一个 Lua 扣库存、加已领数、记待落库；用券走数据库条件更新 | 领券是抢库存，写入集中在一个模板上；用券是改自己的券，天然按用户分散 |
| [抢红包](./12_red_packet) | 红包份额 | 发的时候把每一份金额算好放进 List，抢是 Lua 里弹出一份并记下领取人 | 抢的时候不做计算，只是领走一份，也便于事后逐份对账 |
| [库存与票务](./6_inventory)（选座） | 座位 | Lua 对一组座位先全部检查、再全部置位；数据库条件更新要求影响行数等于座位数 | 一次选的几个座位必须全成或全败 |
| [支付](./8_payment) | 可退额度 | 条件更新：已申请退款加本次金额不超过实付才占用，渠道退款失败再释放 | 两个并发的部分退款加起来不能超过实付 |
| [排行榜和积分](./14_rank_system) | 积分余额 | 条件更新：`balance >= n` 才扣 | 不需要先查再改，也不用版本号重试 |
| [附近的人](./20_geo_nearby) | 空闲司机 | Lua 判断司机仍是空闲才占用并移出空闲池，再用数据库条件更新落地 | 两个订单同时查到同一个司机是常态 |
| [扫码登录](./24_qr_login) | 一个二维码只换一个会话 | 领取的 Lua 里直接删掉二维码 | 同一个二维码不可能换出第二个会话 |

怎么选：

- **量不大、按用户或按商品分散**：数据库一条条件更新就够，库存、积分、可退额度都是这样。
- **写入集中在一个 key 上、瞬时量很大**：前面加一层 Redis Lua 预扣，数据库只接预扣成功的那一小部分，秒杀和领券是这样。
- **每一份都不一样**（金额不同、座位不同）：事先把每一份生成好，抢的时候只是领走，红包份额和座位是这样。
- **Redis 里的结果不是最终结论**：上面用到 Redis 的几种做法，后面都还有数据库的条件更新或唯一键。Redis 主从切换丢了数据，最坏是多放进来几个请求，被数据库挡住。

## 二、幂等与防重

重复来自四个地方：客户端重试、消息重复投递、渠道重复回调、任务重跑。各场景用的办法可以归成六类。

| 办法 | 用在哪些场景 | 要点 |
|------|------|------|
| 业务键上的唯一约束 | [订单](./7_order_system) 的下单幂等号、[支付](./8_payment) 的渠道流水号、[优惠券和营销](./5_coupon) 的发放键、[抢红包](./12_red_packet) 的领取记录、[评论系统](./16_comment) 的请求号、[即时通讯](./18_im) 的客户端消息号、[消息通知中心](./19_notification) 的去重键、[延迟任务](./25_delay_task) 的任务键 | 「先查有没有、再插入」挡不住并发：两个请求都会查到没有。以唯一键冲突为准，冲突就按已处理返回 |
| 带原状态的条件更新 | [订单](./7_order_system) 的状态流转、[支付](./8_payment) 的回调与关单、[优惠券和营销](./5_coupon) 的锁券与核销、[库存与票务](./6_inventory) 的预占记录、[大文件上传](./23_file_upload) 的合并、[扫码登录](./24_qr_login) 的状态迁移 | 重复消息再执行影响 0 行，直接结束；回调和关单同时到，只有一个生效，不用加锁 |
| 版本号或写绝对值 | [商品详情页](./3_product_detail) 的缓存重建、[购物车](./4_cart) 的异步刷盘、[搜索](./22_search_system) 写索引、[计数服务](./17_counter) 的阅读数刷盘、[即时通讯](./18_im) 的已读位点 | 旧数据晚到时写不进去；同一个值写两次结果一样，不需要去重记录 |
| 位点和数据同一个事务 | [计数服务](./17_counter) 的消费位点、[海量数据导入导出](./29_sheet_export) 的断点行号 | 先写数据再存位点，中间挂掉会把最后一批再写一遍；放进同一个事务就没有这个窗口 |
| 固定的外部单号 | [支付](./8_payment) 的退款单号、[订单](./7_order_system) 关单后到账的自动退款、[海量数据对账](./28_reconcile) 的差错退款 | 单号在申请时生成一次并落库，重试始终用同一个，对方按它去重；临时拼单号会在重试时拼出新的，造成重复退款 |
| 一次性凭证 | [秒杀](./11_seckill) 的下单令牌、[大文件上传](./23_file_upload) 的秒传挑战 | 用一次就删，脚本没法提前构造请求 |

几处容易做错的地方：

- **去重记录要和业务写入在同一个事务里**。[支付](./8_payment) 的回调处理是先插去重记录、再改交易单、再记账，一起提交；如果先在 Redis 里占一个标记再处理，处理失败时标记已经占住，渠道重发会被误判成处理过了。
- **分表之后，唯一键要带上分片键**。唯一约束只在单张表内有效：[评论系统](./16_comment) 的请求号带内容 ID，[即时通讯](./18_im) 的消息号带会话 ID，[消息通知中心](./19_notification) 的去重键里含接收人。
- **条件要带上「是谁占的」，防止 ABA**。券被订单 A 锁定、解锁后又被订单 B 锁定，A 的关单消息重复到达时不能把 B 的券解开，所以 [优惠券和营销](./5_coupon) 解锁的条件里带着锁券的业务单号；[库存与票务](./6_inventory) 释放座位同理。
- **幂等键谁来生成**。用户的一次操作由客户端生成请求号（加购、发评论、发消息）；系统之间的事件由接收方按业务字段拼（[消息通知中心](./19_notification)），因为调用方重试时随机号会变。
- **有时候刻意不做幂等**。[扫码登录](./24_qr_login) 换发会话时先删二维码再返回，响应丢了只能重新扫码：要让重试拿到同一个会话，就得把令牌在 Redis 里多留一段时间，泄露窗口变大，而重新扫一次的代价很小。

## 三、热点

先分清是写热点还是读热点，再看落在数据库的一行上，还是 Redis 的一个 key 上。

| 场景 | 热在哪里 | 做法 |
|------|------|------|
| [库存与票务](./6_inventory) | 一个 SKU 的库存行，所有下单都更新它 | 一行拆成多个桶，预占时随机选桶；后台在桶之间调剂，余量很少时并回一个桶 |
| [秒杀](./11_seckill)、[优惠券和营销](./5_coupon) | Redis 里的库存 key，全部落在集群的一个分片上 | 库存拆成多个 key、按用户哈希选一个；售罄后各实例本地记几秒，不再访问 Redis |
| [计数服务](./17_counter) | 爆款内容的计数行、阅读数 key | 点赞类由消费者按对象合并增量，500 条合成一次更新；阅读数只对热点名单里的对象把 key 分桶 |
| [支付](./8_payment) | 平台自营时的「商户待结算」账户，每笔支付都更新它 | 拆成多个子账户随机记入，或流水先落库、余额按批汇总 |
| [评论系统](./16_comment) | 爆款内容的评论区，每秒几万次打开 | 第一页的组装结果在本地缓存 1 到 2 秒；点赞数不放评论表，楼层号不用主体表的行做自增 |
| [商品详情页](./3_product_detail) | 爆款商品的详情 | 多级缓存逐层收敛回源；可预知的提前预热，突发的靠访问频次探测后提高本地缓存的权重 |
| [短链接](./21_shorturl) | 热门短链的跳转与点击量 | Redis 前再加本地缓存；点击量不放主表 |
| [Feed 流和消息推送](./15_feed_stream) | 大 V 发一条内容要写上千万个收件箱 | 超过粉丝阈值的作者不推给全部粉丝，见第四节 |
| [即时通讯](./18_im) | 大群的会话行、大群的在线推送 | 大群不更新会话表里的最新序号；1 秒内多条消息合并成一次「有新消息」 |
| [排行榜和积分](./14_rank_system) | 亿级总榜是一个大 key；同一个榜每秒几十万次加分 | 按用户取模分片，取 Top N 时归并；加分先在本地按用户聚合几百毫秒再批量写 |

写热点的办法归起来是三种：

- **拆**：一行或一个 key 拆成多个桶，库存、券、阅读数、待结算账户都是。拆完要解决「总数还有、每个桶都不够」，所以都有调剂或合并。
- **合**：把多次更新合成一次，计数的增量合并、榜单的本地聚合都是。代价是数字晚几百毫秒到几秒。
- **挪**：把更新最频繁的那一列从主表挪走，点赞数、点击量、会话的最新序号都是。

读热点基本是同一个办法：实例本地缓存一到几秒，回源时同一个 key 只放一个请求过去。

还有一种情况是**看着像热点、其实不是**。[抢红包](./12_red_packet) 里每个红包的 key 各带自己的哈希标签，不同红包落在不同的槽；单个红包最多几百份、上千人点开，落在一个分片上只是上千次脚本调用，不需要拆。

## 四、读扩散与写扩散

一条内容要到达很多人：发的时候给每个人写一份（写扩散），还是只存一份、每个人读的时候去取（读扩散）。三个场景的分界线不一样，判断的依据是同一个：**接收人数乘以发送频率，和读的频率相比谁大**。

| 场景 | 写扩散用在 | 读扩散用在 | 分界的依据 |
|------|------|------|------|
| [Feed 流和消息推送](./15_feed_stream) | 普通作者：发布时写进每个粉丝的收件箱 | 大 V：只写自己的发件箱，粉丝浏览时再拉来归并 | 粉丝数阈值（如 5000）。1000 万粉丝全量推一条要写 1000 万次 |
| [即时通讯](./18_im) | 单聊和小群（如 500 人以内）：每个成员一条收件箱索引 | 大群：只写一份群时间线，上线时逐群比对位点 | 群人数。10 万人的群每秒 5 条消息，写扩散是每秒 50 万条索引 |
| [消息通知中心](./19_notification) | 个人消息和人群定向通知：每个接收人一行 | 全员公告：只存一份，每个用户记一个读到哪条的游标 | 接收范围。全员公告写扩散一次要写上亿行，而大部分人不会看 |

几点共性：

- **写扩散读起来简单**：每个人只有一个位点，一次就能拉到全部新内容，单条已读、删除也好做。代价是存储和写入量随人数放大。
- **读扩散省写入**，但读的人要逐个来源去比对。它成立的前提是来源不多：一个人关注的大 V、加入的大群、有效期内的公告都只有几个到几十个。
- **写扩散的扇出要可靠**：三个场景都是同一个事务里写内容和待发记录，再经消息队列分批扇出；消费端靠 `ZADD` 的天然幂等或收件箱上的唯一键挡住重复。不在请求线程里直接起线程池扇出，进程一崩就丢。

同样的取舍也出现在不叫这个名字的地方。[购物车](./4_cart) 只存加购时的价格，当前价格读的时候再查：存了就要在改价时更新几百万个购物车，这就是一次写扩散。

## 五、分页与批量读取

分页分两种：给用户翻页，和后台任务分批读。两种都不该用偏移量，原因不同。

| 情况 | 场景 | 做法 | 为什么 |
|------|------|------|------|
| 列表头部不断有新内容 | [Feed 流和消息推送](./15_feed_stream)、[评论系统](./16_comment)、[消息通知中心](./19_notification) | 用上一页最后一条的排序值或 ID 做游标 | 偏移量翻页时，新内容插进来会让后面的页重复或漏掉 |
| 排序值自己一直在变 | [评论系统](./16_comment) 的热度榜 | 第一页把前 200 个 ID 存成一份短期快照，翻页在快照里取 | 热度分在变，按名次翻页同样会重复或遗漏 |
| 后台分批读一张大表 | [海量数据对账](./28_reconcile)、[海量数据导入导出](./29_sheet_export)、[延迟任务](./25_delay_task) | 按主键游标：`id > 上一批最后一个` 取一批，位点存下来 | 偏移量越往后扫得越多，100 万行按 5000 一页合计要扫约 1 亿行 |
| 处理完的行不会再命中条件 | [优惠券和营销](./5_coupon) 的过期扫描、[评论系统](./16_comment) 的级联隐藏 | 每次取前 N 行处理，循环到取不出来为止 | 不需要游标，条件自己会往前走 |
| 搜索引擎里翻页 | [搜索](./22_search_system) | 限制最多翻到 1 万条；导出和无限滚动用 `search_after` | 深分页会拖垮集群 |
| 按位点补齐 | [即时通讯](./18_im) 的离线同步 | 取序号大于本地位点的消息，一次 200 条 | 位点就是游标，读操作天然幂等 |
| 取出来还要过滤 | [附近的人](./20_geo_nearby) | 多取（100 个）再过滤，凑够 20 个为止 | 直接取 20 个，排除自己、过期和不可见的之后可能一个不剩 |

后台分批读还有三件事各篇都提到：

- **读从库或离线库，并且限速**，不要压到业务主库。
- **分批读到的不是同一个快照**。导出的文件要标明「数据截至任务开始时间」，并在任务开始时记下主键的上界。
- **位点决定了能不能断点续跑**。位点和数据不在一个事务里时，写入必须自己幂等。

## 六、到点执行

「到了某个时间做一件事」在各场景里的做法差别最大，因为要求不一样：有的只要不漏，有的要准时，有的要能取消，有的其实根本不需要定时。

| 场景 | 到点要做什么 | 做法 | 为什么这么选 |
|------|------|------|------|
| [短链接](./21_shorturl)、[扫码登录](./24_qr_login) | 过期后不能再用 | 读的时候判断，加上缓存自己的过期时间 | 不需要任何定时任务 |
| [优惠券和营销](./5_coupon) | 券过期 | 用券的条件里带着有效期，这是真正的保障；另有定时扫描把状态改成已过期，只为展示和统计 | 不给每张券发一条延迟消息：上亿张券就是上亿条消息，而且集中在同一时刻触发 |
| [订单](./7_order_system)、[秒杀](./11_seckill) | 超时关单 | 消息队列的定时消息，加每分钟一次的扫表兜底 | 延迟固定、量大、不需要取消；定时消息负责准时，扫表负责不漏 |
| [支付](./8_payment) | 交易过期、回调没到 | 下单时把过期时间传给渠道，本地关单比渠道晚 1 分钟；查单任务的间隔逐次拉长 | 过期后渠道自己拒绝付款，本地关单只是收尾 |
| [库存与票务](./6_inventory) | 预占超时、锁座超时 | 主路径是订单的关单事件；兜底扫描发现超时的预占，先向订单服务确认再释放 | 过期不等于空闲，用户可能正在付款 |
| [抢红包](./12_red_packet) | 24 小时没抢完的退回 | 定时扫描过期红包：先关闭，等一段时间，对账补齐，再退款 | 直接按「总额减已入账」退会多退，可能还有抢到但没入账的 |
| [消息通知中心](./19_notification) | 免打扰时段结束后再发、失败后重试 | 推迟到静默结束并加随机打散；重试时间记在任务表上由调度扫描 | 几百万条推迟的消息不能在同一秒发出 |
| [延迟任务](./25_delay_task) | 多个业务共用，时长从秒到几十天，要能取消 | 全部落库，快到期的才装进内存时间轮，到期后投到业务方的消息队列 | 定时消息没法取消，时长也有上限 |

从这张表能归出五条：

- **能在读的时候判断，就不要定时任务**。过期类的需求大多如此，定时扫描只是为了让展示和统计跟上。
- **到点只是「该检查一下了」的信号**。真正的判断靠带原状态的条件更新：关单消息到了但订单已支付，更新影响 0 行，什么都不发生。所以这类任务不需要取消。
- **准时和不漏分开保证**。消息负责准时，扫表负责不漏，两个一起用；接入通用的延迟任务服务之后，订单自己的低频扫表也不能去掉。
- **过期不等于可以释放**。涉及钱和货的，先向上游确认：库存释放前问订单，关单前先关渠道的交易，红包退款前先对账。
- **同一时刻大量到期要打散**。提交时加随机抖动，投递时限速；必须准点生效的大批量变更，改成提前写好带生效时间的数据，读的时候按时间选。

## 七、对账与校准

只要一份数据存在两个地方，就会有对不上的时候：Redis 和数据库、自己和渠道、余额和流水、计数和明细。各场景的做法不同，但都要先回答同一个问题：**以谁为准**。

| 场景 | 对的是哪两边 | 以谁为准 | 怎么对、怎么修 |
|------|------|------|------|
| [秒杀](./11_seckill) | Redis 的已购集合与数据库的订单 | 数据库 | 找出「已购但迟迟没有订单」的用户，回补库存；校验剩余加已成交等于初始库存 |
| [优惠券和营销](./5_coupon) | Redis 的库存与数据库的券 | 总量这个恒等式 | 校验 Redis 剩余加待落库加已落库等于总量；少发的补发，多扣的回补 |
| [抢红包](./12_red_packet) | Redis 的领取记录与数据库的入账记录 | Redis 的领取记录 | 退款之前补齐缺失的入账；校验总额等于已领加已退 |
| [库存与票务](./6_inventory) | 流水与余额、预占明细与余额、库存与订单、Redis 与数据库 | 流水（余额是它的快照） | 四层逐一核对；修复时写一条调整流水，不直接改余额 |
| [支付](./8_payment) | 自己的交易与渠道账单 | 渠道 | 日终下载账单逐笔比对，差错进差错池；修正用红字冲正，不改历史 |
| [排行榜和积分](./14_rank_system) | Redis 的榜单与积分流水 | 流水 | 按流水重算当期榜单；余额应等于流水合计 |
| [计数服务](./17_counter) | 计数与关系表 | 关系表 | 只对最近没有变化的对象按关系表重数，带条件更新写回；阅读数没有明细，不对账 |
| [搜索](./22_search_system) | 数据库与索引 | 数据库 | 靠版本号保证增量不乱，靠全量重建纠偏，没有定期对账 |
| [附近的人](./20_geo_nearby) | 门店表与 Redis 里的门店位置 | 门店表 | 增量同步之外每天全量重建一份，原子替换 |

[海量数据对账](./28_reconcile) 讲的是量大时怎么比：两边按同一个规则分片，先比每片的笔数、金额合计和记录哈希之和，不一致的分片再比明细。

几条共同的原则：

- **先定事实来源**。钱以渠道和流水为准，货以流水为准，计数以明细为准，缓存和索引以数据库为准。派生的那一份错了可以重算，事实来源错了只能靠流水追查。
- **写出一个恒等式**。「剩余加已发等于总量」「余额等于流水合计」「总额等于已领加已退」，对账就是定期验它，不成立就告警。
- **对的时候数据还在变**。秒杀等一段时间再判定没有订单，红包关闭后等过消息的不确定窗口，计数只修正静默的对象并用条件更新写回，支付把跨日的交易挂到次日复核。
- **修也要留痕**。调整流水、红字冲正、差错表，都是追加一条记录，而不是直接改数。事后能查到是谁、为什么改的。
- **对不了的就承认是近似**。阅读数没有明细，丢了找不回来，就不做对账；未读数显示的是「99+」，不准时重数一遍即可。

## 小结

- 不能超发：判断和扣减放进一个原子动作，量小用数据库条件更新，量大且集中时前面加 Redis Lua，数据库始终兜底
- 幂等：唯一键和带原状态的条件更新是两个主力，去重记录要和业务写入同一个事务，分表后唯一键带上分片键
- 热点：写热点靠拆、合、挪，读热点靠一到几秒的本地缓存；先确认真的是热点
- 扩散模型：看接收人数乘以发送频率，人少写扩散、人多读扩散，分界线各场景自己定
- 分页：用户翻页用游标，后台分批读用主键游标并存位点
- 到点执行：能读时判断就不定时；到点只是检查的信号，准时靠消息、不漏靠扫描
- 对账：先定以谁为准，写出恒等式定期验，修正只追加不改数
