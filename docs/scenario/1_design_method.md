# 系统设计方法论

> 前置阅读：[容量评估与规划](/high-con/8_capacity_planning)、[分布式理论](/distributed/2_theorem)

系统设计题没有标准答案，但有一套稳定的推进顺序，本模块后面的每个场景都是它的一次实例。本篇讲评估维度、七步答题流程与每一步的产出，并以短链接为例完整走一遍，基线为通用后端技术栈。

---

## 一、系统设计题考什么

面试官或评审人看的不是「有没有用上 Kafka」，而是你能不能在不确定的需求下，把问题拆清楚、做出有依据的选择。

| 评估维度 | 看什么 | 加分表现 | 减分表现 |
|----------|--------|----------|----------|
| 问题拆解 | 能否把模糊需求收敛成可设计的范围 | 主动问清核心功能与规模，明确不做什么 | 一上来就画架构图 |
| 量化意识 | 设计是否基于数量级 | 先估 QPS、存储，再决定要不要分库、加缓存 | 「数据量大所以分库分表」 |
| 架构能力 | 主链路是否完整、组件职责是否清晰 | 先跑通最简方案，再逐步演进 | 堆砌组件，说不清每个组件解决什么问题 |
| 深度 | 能否在一两个点上讲到底 | 讲清热点、一致性、故障时的具体做法 | 每个点都只说名词 |
| 取舍 | 是否知道每个选择的代价 | 「选 A 是因为 X，代价是 Y，用 Z 兜底」 | 只讲优点，或把方案说成没有缺点 |
| 沟通 | 是否边讲边确认、能接住追问 | 每一步给结论，主动询问深入方向 | 闷头讲 20 分钟，或被追问就推翻重来 |

设计文档评审同理：评审人关心的也是范围、数量级、主链路、风险与取舍，只是比面试多了排期、灰度和回滚计划。

## 二、答题流程总览

![系统设计答题流程](../assets/scenario/design-method-flow.svg)

七步的核心是**先广后深**：前四步用约 20 分钟把问题和数据对齐，第五步给出能跑通的完整方案，后两步才挑最关键的瓶颈深入。时间分配只是参考，面试官把话题引向某一步时，跟着走即可。

| 步骤 | 产出 | 一句话要求 |
|------|------|------------|
| 需求澄清 | 功能清单、非功能指标、明确不做的部分 | 写下来，后面每个决策都回到这里找依据 |
| 容量估算 | 峰值读写 QPS、存储总量、带宽 | 只要数量级，结论比精确值重要 |
| 接口设计 | 3–5 个核心接口 | 只列主链路，写清幂等与分页方式 |
| 数据模型 | 核心表 / key 结构、主键、索引、分片键 | 由查询方式反推，而不是先建表再想怎么查 |
| 高层架构 | 一张组件图 + 读写两条数据流 | 先最简可用，再说为什么需要加组件 |
| 深入瓶颈 | 1–2 个关键问题的具体方案 | 讲到命令、状态、失败处理这一层 |
| 扩展与取舍 | 规模扩大 10 倍、组件故障时怎么办 | 主动讲代价和兜底 |

## 三、需求澄清

**需求澄清决定后面所有设计的方向。** 同样叫「设计一个 Feed 流」，日活 1 万和日活 1 亿、能否接受几秒延迟，答案完全不同。澄清分三类问题：

### 1、功能需求

先列出所有可能的功能，再和对方确认**核心的 2–3 个**，其余明确标记为「本次不展开」。

- 核心用例是什么：谁在什么场景下做什么操作，例如「用户发帖、关注者在首页看到」
- 读和写分别是什么：写入路径与读取路径往往需要完全不同的设计
- 有没有排序、搜索、统计、通知这类派生需求：它们通常会引入额外组件
- 数据要保留多久，能否删除或修改：决定冷热分离和缓存失效策略

### 2、非功能需求

| 维度 | 要问的问题 | 影响的设计 |
|------|------------|------------|
| 规模 | DAU 多少、读写比多少、峰值是均值的几倍 | 是否分库分表、缓存与机器数 |
| 延迟 | 核心接口 P99 期望多少 | 同步还是异步、是否需要预计算 |
| 一致性 | 写完能否立刻读到，能否接受短暂不一致 | 缓存策略、读主还是读从、是否需要分布式事务 |
| 可用性 | 目标几个 9，故障时哪些功能可以降级 | 冗余与切换、降级开关、多活 |
| 准确性 | 能否丢数据、能否重复，例如计数允许误差吗 | 幂等、对账、MQ 可靠投递 |
| 安全 | 是否有防刷、防遍历、敏感数据 | 限流、鉴权、ID 混淆、加密 |

SLA 与几个 9 对应的停机时间见 [可用性度量](/high-avail/1_sla_slo)。

### 3、约束

- 已有技术栈与基础设施：是否已有 Redis 集群、Kafka、ES，团队熟悉什么
- 时间与人力：一个月上线和半年上线，方案的复杂度上限不同
- 外部依赖：第三方支付、短信、推送的配额与可用性
- 合规：数据是否要留在境内、日志是否需要脱敏

::: tip 澄清的收尾
把结论复述一遍，例如「核心是发帖和看首页 Feed，DAU 1000 万，读写比 100:1，Feed 允许秒级延迟，不做搜索和推荐」，对方点头后再往下走。
:::

## 四、容量估算

**估算的目的是做决策，不是算准数字。** 每算出一个数，都要顺带说出它意味着什么：「峰值写 2 万 TPS，单个 MySQL 主库扛不住，要分库」「总数据 50 GB，单库就能放下，不需要分片」。

### 1、速算模板

| 估什么 | 公式 | 速算技巧 |
|--------|------|----------|
| 平均 QPS | 日请求量 ÷ 86400 | 一天按 10⁵ 秒算，1 亿次 / 天 ≈ 1000 QPS（精确约 1157） |
| 峰值 QPS | 平均 QPS × 峰值系数 | 日常 2–5 倍；大促、秒杀 10–100 倍 |
| 读写拆分 | 总 QPS 按读写比拆开 | 读写比决定缓存还是写扩展是主要矛盾 |
| 存储 | 日增条数 × 单条大小 × 保留天数 × 副本数 | 再乘 1.3–2 计入索引与预留 |
| 带宽 | 峰值 QPS × 平均响应大小 | 1 Gbps ≈ 125 MB/s，大文件走 CDN / 对象存储 |
| 缓存 | 热数据条数 × 单条大小 | 二八原则：缓存 20% 的热数据 |
| 机器数 | 峰值 QPS ÷ 单机 QPS × 冗余系数 | 单机 QPS 以压测为准，冗余按可用区数计算 |

从 DAU 推峰值、机器数的冗余系数与存储公式的完整推导，见 [容量评估与规划](/high-con/8_capacity_planning#一、流量估算方法)，这里不重复。

### 2、常用数量级

这些数字只用于估算阶段的判断，具体以压测和所用版本为准。

| 对象 | 数量级 | 常见用法 |
|------|--------|----------|
| 普通业务接口（单机） | 1000–5000 QPS | 估算应用机器数 |
| Redis 单分片简单命令 | 约 10 万 ops/s | 判断是否需要多分片或本地缓存 |
| MySQL 单主库写入 | 数千 TPS | 超过即考虑异步削峰或分库 |
| MySQL 单表 | 千万级行（经验值约 2000 万） | 判断是否需要分表 |
| Kafka 单分区 | 数万条 / 秒 | 估算分区数 |
| 内存访问 / SSD 随机读 / 同机房 RTT | 约 100 ns / 100 µs / 0.5 ms | 判断一次请求能串行几次远程调用 |
| 跨地域 RTT | 数十毫秒 | 判断能否跨地域同步写 |

### 3、估算时的习惯

- **先说假设**：「假设 DAU 1000 万、人均 10 次读」，对方可以随时纠正
- **取整算**：1 亿 ÷ 10⁵ = 1000，不要在白板上做长除法
- **读写分开**：读 10 万 QPS 和写 10 万 TPS 是完全不同的问题
- **只估关键路径**：首页 Feed 的读、发帖的写，后台报表不用估

## 五、接口与数据模型

### 1、接口设计

只写主链路的 3–5 个接口，每个接口说清四件事：

| 要点 | 说明 | 示例 |
|------|------|------|
| 方法与路径 | 资源化命名，动词用 HTTP 方法表达 | `POST /api/v1/posts`、`GET /api/v1/feed` |
| 关键参数 | 只写影响设计的参数 | 发帖带 `requestId`；Feed 带 `cursor`、`size` |
| 幂等 | 写接口如何防重复提交 | 客户端生成 `requestId`，服务端唯一约束 |
| 分页 | 大列表用游标分页，不用 offset | 返回 `nextCursor`，避免深分页与数据漂移 |

写接口的幂等不需要现场展开，一句「用请求号加唯一约束兜底」即可，细节见 [幂等设计](/architecture/3_idempotence)。URL、状态码与错误结构的约定见 [API 设计规范](/engineering/4_api_design_rule)。

### 2、数据模型

**由查询反推模型。** 先列出主链路上的每一个查询，再决定表结构、索引与分片键。

1. 列实体与关系：用户、帖子、关注关系、Feed 收件箱
2. 列查询：按用户查帖子、按用户查关注列表、按用户查收件箱并按时间倒序
3. 为每个查询定索引：`(user_id, created_at)` 这样的联合索引能同时覆盖过滤与排序
4. 选存储：强事务与关联查询用 MySQL；高频读的 KV 与排序用 Redis；全文检索用 ES；海量时序明细用列存或 OLAP
5. 选分片键：让最高频的查询落在单个分片上，通常是 `user_id` 或订单号中嵌入的用户基因

| 常见问题 | 后果 | 做法 |
|----------|------|------|
| 主键用随机 UUID | B+ 树页分裂，写入放大 | 用发号器或雪花 ID，见 [分布式 ID 生成](/distributed/8_id_generator) |
| 计数字段放在主表 | 热门行写冲突 | 计数单独存，见 [计数服务](./17_counter) |
| 分片键与查询不匹配 | 每次查询都要广播所有分片 | 建异构索引表或同步到 ES |
| 大字段与热字段同表 | 缓存与 IO 效率低 | 冷热字段拆表，大对象放对象存储 |

## 六、高层架构与组件选型

### 1、先画最简方案

**第一张图只放必需的组件：** 客户端 → 网关 / 负载均衡 → 无状态应用服务 → 数据库。用它把读写两条数据流讲通，然后结合估算结果说明「哪里扛不住」，再逐个加组件。每加一个组件，都要能回答它解决的是哪个数字。

### 2、常用积木

| 积木 | 解决什么 | 典型触发条件 | 主文档 |
|------|----------|--------------|--------|
| 缓存 | 读多写少、读延迟 | 读 QPS 远超数据库能力 | [缓存架构设计](/high-con/3_cache_architecture)、[缓存一致性](/cache/10_cache_consistency) |
| 消息队列 | 削峰、解耦、异步 | 写入有突发峰值，或一个动作触发多个下游 | [异步与削峰](/high-con/4_async_peak_shaving)、[MQ 选型](/messaging/6_selection) |
| 分库分表 | 单库写入与容量上限 | 写 TPS 或单表行数超出单机能力 | [数据层扩展](/high-con/5_data_scaling)、[分库分表与中间件](/database/5_practice/3_sharding) |
| 搜索引擎 | 全文检索、多条件组合筛选 | 模糊查询、按非分片键的复杂查询 | [搜索数据库](/nosql/5_search_db)、[搜索](./9_search_system) |
| 对象存储 + CDN | 图片、视频、文件 | 大对象、带宽占用高 | [对象存储](/architecture/5_object_storage)、[大文件上传](./10_file_upload) |
| 分布式 ID | 全局唯一、趋势递增的主键 | 分库后自增主键不可用 | [分布式 ID 生成](/distributed/8_id_generator) |
| 定时 / 延迟任务 | 超时关单、到期处理 | 有时间驱动的状态迁移 | [分布式调度](/distributed/6_job_scheduler) |
| 限流与降级 | 保护系统不被打垮 | 流量可能超出容量 | [限流与过载保护](/high-avail/7_rate_limiting)、[降级](/high-avail/6_degradation) |

### 3、选型的说法

选型时用「需求 → 选择 → 代价」的句式，而不是罗列产品名：

- 「Feed 允许秒级延迟，所以发帖后用 MQ 异步写扩散，代价是粉丝看到新帖有延迟，大 V 改为拉模式」
- 「订单要强一致地扣库存，所以库存预占走同步调用加幂等，支付后的积分发放走事务消息实现最终一致」

## 七、深入瓶颈与取舍

最简方案讲完后，主动指出 1–2 个最关键的瓶颈深入下去；如果对方已经指定方向，就按对方的走。常见的深入点有三类：

### 1、热点

- 读热点：本地缓存 + 热点探测，必要时同一 key 多副本
- 写热点：单行库存、单个计数器拆成分桶，或先在内存 / Redis 聚合再批量落库
- 并发回源：缓存失效瞬间大量请求打到数据库，用 Single Flight 合并

具体手段与选型见 [热点问题](/high-con/6_hotspot)。

### 2、一致性

- 先确认需要多强的一致性：大部分场景只要求最终一致，并给出可接受的延迟上限
- 缓存与数据库：先更新数据库再删缓存，配合过期时间兜底
- 跨服务：一个流程只选一种方案（同步幂等预占、事务消息或 Outbox），并配对账
- 兜底永远是对账：定时比对两边数据，发现差异就修复，见 [海量数据对账](./3_reconcile)

### 3、可用性

- 单点：每个有状态组件说明如何冗余、主从如何切换
- 依赖故障：超时、重试、熔断、隔离，见 [超时、重试与隔离](/high-avail/4_timeout_retry_bulkhead)
- 降级：明确哪些是核心功能必须保住，哪些可以关掉，例如统计、推荐、个性化

### 4、常见取舍

| 取舍 | 选左边 | 选右边 | 判断依据 |
|------|--------|--------|----------|
| 一致性 vs 可用性 | 资金、库存 | 计数、Feed、点赞 | 不一致的业务代价有多大 |
| 同步 vs 异步 | 用户必须立刻知道结果 | 结果可以稍后通知 | 用户等待的耐心与下游能力 |
| 推 vs 拉 | 读多、粉丝少 | 写扩散成本过高的大 V | 写放大倍数与读延迟要求 |
| 预计算 vs 实时计算 | 读频繁、口径固定 | 查询条件多变 | 读写比与维度组合数 |
| 精确 vs 近似 | 金额、库存 | UV、热门排行 | 误差能否被业务接受（如 HyperLogLog） |
| 自研 vs 用现成组件 | 核心差异化能力 | 通用能力 | 团队维护成本 |

## 八、以短链接为例走一遍

下面用前面的七步把 [短链接](./6_shorturl) 压缩成一次约 45 分钟的回答，详细实现见该篇。

**1. 需求澄清**：核心是生成短链和跳转；需要点击统计；支持过期时间；自定义别名作为次要功能。跳转延迟要低，统计允许分钟级延迟；短码不能被顺序遍历。

**2. 容量估算**：假设生成峰值 1000 QPS、跳转峰值 10 万 QPS（读写比约 100:1），累计 1 亿条，每条约 500 B。

| 项目 | 计算 | 结论 |
|------|------|------|
| 存储 | 1 亿 × 500 B = 50 GB，加索引约 75 GB | 单个 MySQL 主从即可，不分库 |
| 短码空间 | 62⁶ ≈ 568 亿 | 6 位够用多年 |
| 缓存 | 20% 热数据 × 300 B ≈ 6 GB | Redis Cluster 少量分片 |
| 跳转服务 | 10 万 ÷ 单机 5000 = 20 台 | 无状态，按冗余部署约 30 台 |

**3. 接口设计**：`POST /api/v1/short-urls`（入参长 URL、过期时间、可选别名，返回短链）；`GET /{code}` 返回 302。

**4. 数据模型**：`short_url(id, short_code 唯一, long_url, long_url_hash, expire_at)`；点击量不放主表，计数放 Redis、明细放 OLAP。

**5. 高层架构**：生成服务从发号器取 ID、混淆后转 Base62，写库并预热缓存；跳转服务查 Redis，未命中回源 MySQL，异步把点击事件发到 Kafka，由 Flink 聚合。

**6. 深入瓶颈**：

- 短码生成：发号器 + 可逆混淆无冲突且不可遍历；哈希方案必须按常态处理冲突
- 跳转性能：缓存命中率是关键，空值缓存防穿透，热门短链加本地缓存
- 302 还是 301：需要统计就用 302 + `Cache-Control: no-store`

**7. 扩展与取舍**：规模扩大 10 倍后存储到 750 GB，按短码分库；Redis 故障时限流回源数据库；统计链路故障时丢弃统计、保证跳转。

::: tip 对照其他案例
本模块其他场景同样可以按这七步阅读：[秒杀](./4_seckill) 的重点在第六步的库存热点与削峰，[Feed 流和消息推送](./8_feed_stream) 的重点在第七步的推拉取舍，[计数服务](./17_counter) 的重点在数据模型与写热点。
:::

## 九、常见失分点

| 失分点 | 表现 | 改进 |
|--------|------|------|
| 跳过需求澄清 | 题目一出就开始画图 | 先花 3–5 分钟问清核心功能与规模 |
| 估算不落到决策 | 算出数字却没有结论 | 每个数字后面接一句「所以……」 |
| 组件堆砌 | 一开始就上 Kafka、ES、分库分表 | 从最简方案出发，按瓶颈逐个加 |
| 只有名词没有细节 | 「用 Redis 缓存」「用 MQ 解耦」 | 讲到 key 结构、命令、失败时怎么办 |
| 只讲正常路径 | 不提重复请求、消息丢失、节点宕机 | 每条链路问自己「这一步失败了会怎样」 |
| 忽略数据一致性 | 双写缓存和数据库、跨服务直接改 | 说明一致性要求与兜底对账 |
| 过度设计 | 日活 1 万也上多活、分库分表 | 方案与估算出的规模匹配 |
| 不讲代价 | 每个方案都只有优点 | 用「选 A，代价是 Y，用 Z 兜底」的句式 |
| 被追问就推翻 | 一被质疑就换方案 | 先分析质疑点，能补救就局部修正 |

---

## 小结

- 系统设计考的是拆解、量化、架构、深度、取舍与沟通，组件名本身不加分
- 按「需求澄清 → 容量估算 → 接口设计 → 数据模型 → 高层架构 → 深入瓶颈 → 扩展与取舍」先广后深地推进
- 需求澄清分功能、非功能、约束三类，结束时复述结论再往下走
- 容量估算只要数量级，每个数字都要落到一个设计决策上；详细方法见容量规划
- 数据模型由查询反推，分片键让最高频的查询落在单个分片
- 架构从最简方案出发，每加一个组件都要能说出它解决的瓶颈
- 深入时围绕热点、一致性、可用性，用「选择 + 代价 + 兜底」的句式讲取舍
