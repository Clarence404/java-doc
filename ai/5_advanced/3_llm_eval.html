LLM 应用评估与上线

前置阅读：Prompt 工程、RAG 检索增强生成、AI Agent 智能体

LLM 功能从 Demo 到生产，难点是确认每次改动让它变好还是变坏。本篇讲评估集与评估方法、CI 门禁与护栏、线上可观测与灰度回滚、成本与延迟优化，基线为 Spring AI 2、LangChain4j 1。

一、为什么 LLM 应用需要专门评估

传统接口的测试是「给定输入，断言输出等于期望值」，LLM 应用打破了这个前提：

特点带来的问题
输出非确定同一输入多次调用结果不同，assertEquals 失效；temperature 设为 0 也不能保证完全一致
变更面广Prompt 改一个字、换模型版本、调检索 Top-K、改切块大小，都可能让一部分原本答对的问题答错
回归不可见改动修好了 A 类问题，同时悄悄弄坏了 B 类问题；没有评估集就只能靠用户投诉发现
厂商侧变化模型别名（如 xxx-latest）背后的快照会被厂商更新，自己什么都没改效果也可能变
质量多维正确、忠实、格式、语气、安全、延迟、成本要同时满足，单一指标说明不了问题

所以 LLM 应用需要一套和单元测试平行的机制：用一份有版本的评估集，对每次变更打分，并和上一个基线比较。模型生产厂商的公开榜单只能参考，衡量的是通用能力，不是你的业务场景。

二、评估集建设

评估集是整个闭环的地基，宁可少而准，不要多而脏。

1、数据从哪来

  • 线上日志抽样：最真实的来源。按场景、意图、用户群分层抽样，而不是随机抽，否则高频简单问题会占满样本；入库前先脱敏
  • 黄金集（Golden Set）：业务专家逐条标注期望答案或评分要点，覆盖核心场景，数量几十到几百条即可，是门禁的主要依据
  • 对抗样本：提示注入、越权请求（问别人的订单）、诱导编造（问不存在的产品）、超长输入、多语言混杂、空输入
  • 失败回流：线上差评、人工转接、护栏拦截的样本，复核后补进评估集，这是评估集持续变好的主要途径

2、覆盖哪些维度

维度例子
场景与意图咨询、查询、办理、闲聊、超出范围
难度单跳事实、多跳推理、需要计算、需要多次工具调用
有无答案知识库里有 / 没有 / 部分有，「没有」时应如实说没有
输入形态口语、错别字、精确型号与错误码、长文本
安全直接与间接提示注入、敏感信息、越权

每条样本至少包含：输入（含必要的上下文与用户身份）、期望结果（标准答案、评分要点或期望调用的工具及参数）、标签（场景、难度、来源）。

3、数据版本管理

评估集和代码一样要有版本：放在 Git（小规模 JSONL）或数据平台（大规模），每次评估结果都记录「评估集版本 + Prompt 版本 + 模型标识 + 检索参数」，否则分数无法对比。评估集更新后要先用当前线上版本重新跑出新基线，再和候选版本比较。包含真实用户数据的样本按 数据安全 的要求脱敏，并控制访问权限。

三、评估方法

从便宜到昂贵排列，能用前面的就不用后面的：

方法适用特点
规则与精确匹配分类、抽取、是否调用了某工具、是否包含必需字段确定、便宜、可在 CI 每次跑
结构化输出校验JSON 输出、工具参数先过 JSON Schema 或反序列化，再断言字段取值
参考答案相似度有标准答案的问答Embedding 余弦相似度或关键要点命中率，只能做粗筛
LLM-as-a-Judge开放式回答的正确性、忠实度、语气灵活，但有偏差，需要校准
人工抽检校准 Judge、上线前验收、争议样本最准也最贵，按比例抽

1、LLM-as-a-Judge 的偏差与校准

用另一个模型按评分标准给回答打分，是开放式回答最常用的评估方式，但它有几种已知偏差：

  • 位置偏差：两两比较时倾向于选排在前面（或后面）的答案，做法是交换顺序各评一次
  • 长度偏差：倾向于给更长、更「全面」的回答高分
  • 自我偏好：倾向于给同家族模型的输出高分，Judge 尽量和被测模型不是同一个
  • 评分漂移：1–10 分这类细粒度打分不稳定，改成二元判断（通过 / 不通过）或少档位，并按要点逐条判断

校准方法：让人工标注一批样本（几十到上百条），计算 Judge 与人工结论的一致率，一致率达标后才用于门禁；Judge 的 Prompt 和模型同样要版本化，换 Judge 等于换尺子，基线要重跑。要求 Judge 先给理由再给结论，便于人工复核。

2、RAG 专项指标

RAG 要把检索和生成分开评：检索看 Recall@K、MRR、上下文精确率，生成看答案忠实度、答案相关性和无答案处理，具体定义与评估集构建见 RAG 检索增强生成，本篇不重复。

3、Agent 专项

Agent 除了最终答案，还要评过程：是否调用了正确的工具、参数是否正确、步数是否在合理范围、遇到工具报错能否恢复。评估时把工具替换成返回固定数据的桩，避免产生真实副作用，也让结果可复现。

四、离线评估流水线

1、什么变更要触发评估

Prompt 模板、系统提示、模型或模型版本、采样参数、工具定义、检索参数（切块、Top-K、Rerank）、Embedding 模型，任何一项变更都按代码变更对待：提交 → 跑评估集 → 和基线对比 → 门禁 → 合并。

2、门禁怎么设

  • 硬门槛：格式校验通过率、安全类对抗样本拦截率要求接近 100%，任何一条退化都阻断
  • 相对门槛：整体通过率不低于基线减去一个容忍值（非确定性带来的波动），容忍值通过同一版本重复跑几次来确定
  • 分组看：总分不变但某个场景大幅下降同样要阻断，报告按标签分组输出
  • 成本与延迟：平均 Token 用量和 P95 延迟也纳入对比，防止效果提升但成本翻倍

完整评估集调用次数多、耗时长，可以分两档：每次提交跑小规模冒烟集（规则类为主），合并到主干或发布前跑全量集（含 Judge）。评估调用走独立的 API Key 与配额，不和线上流量抢限额。

3、Java 侧：JUnit 驱动

评估本质上是参数化测试，用 JUnit 读取评估集逐条调用、汇总通过率即可，不必引入新的技术栈。Spring AI 提供了 Evaluator 接口（输入 EvaluationRequest：用户问题、上下文文档、模型回答；输出带 isPass() 的 EvaluationResponse），内置 RelevancyEvaluator（回答是否切题）与 FactCheckingEvaluator（回答是否有上下文依据）两种以 LLM 为评判的实现，具体构造方式以所用版本的官方文档为准：

@SpringBootTest
@Tag("llm-eval")   // 单独的 Tag，默认构建不跑，CI 评估阶段才跑
class SupportBotEvalTest {

    @Autowired SupportBot bot;                 // 被测的业务服务
    @Autowired ChatClient.Builder judgeBuilder; // Judge 用的模型，配置成与被测模型不同

    @Test
    void goldenSetShouldNotRegress() {
        var evaluator = new RelevancyEvaluator(judgeBuilder);
        var cases = EvalDataset.load("eval/support-golden-v12.jsonl");
        int pass = 0;
        for (var c : cases) {
            var answer = bot.answer(c.question());
            // 规则检查优先：便宜、确定
            if (!c.mustContain().stream().allMatch(answer.text()::contains)) continue;
            var req = new EvaluationRequest(c.question(), answer.contextDocs(), answer.text());
            if (evaluator.evaluate(req).isPass()) pass++;
        }
        double rate = (double) pass / cases.size();
        EvalReport.write("support", "v12", rate);          // 落盘，供 CI 对比与归档
        assertThat(rate).isGreaterThanOrEqualTo(Baseline.of("support") - 0.02);
    }
}

LangChain4j 没有与之对应的统一评估接口，同样用 JUnit + 一个 Judge 用的 AiServices 接口（返回布尔或枚举结构化输出）实现。规模变大后可以接入专门的评估平台（开源的 Promptfoo、RAGAS 等，或可观测平台自带的评估功能），Java 侧只负责产出「输入 / 输出 / 上下文」数据。

五、护栏

护栏（Guardrails）是包在模型调用前后的确定性检查，评估回答「整体好不好」，护栏负责「这一次请求能不能放行」。

1、输入护栏

  • 提示注入检测：关键词规则或分类模型识别「忽略之前的指令」之类的输入，命中后降级（如关闭写工具）并记录；它只是弱信号，不能当唯一防线，分层防护见 Prompt 工程
  • 敏感信息脱敏：手机号、身份证号、银行卡号等在发给第三方模型前替换成占位符，回答返回前再按需还原；是否允许数据出境、出组织，由数据分级决定
  • 范围与长度：超出业务范围的问题直接走拒答模板；限制输入长度和单用户频率，防止刷 Token

2、输出护栏

  • 格式校验：结构化输出先过 Schema 校验，失败时带错误信息重试一次，仍失败则降级，不把半截 JSON 交给下游
  • 事实与引用检查：RAG 回答要求带来源编号，校验引用的编号确实存在于本次检索结果中；涉及金额、日期、状态的回答与业务系统数据核对
  • 越权与敏感检查：输出中不应出现当前用户无权看到的数据、系统提示内容、内部链接；前端不自动渲染模型生成的外链和图片
  • 拒答策略：拦截后返回统一的拒答文案或转人工，不把拦截原因原样暴露给用户（避免被反复试探），原因写进审计日志

流式输出时输出护栏比较棘手：要么缓冲一段再放行，要么边输出边检测、命中后中断并撤回，按场景的风险等级取舍。

3、工具调用的最小权限

挂了工具之后，风险从「说错话」变成「做错事」。工具按场景拆分、以当前用户身份执行、副作用操作人工确认、限制调用步数，这些规则在 AI Agent 智能体 中展开，本篇不重复。

框架层面，LangChain4j 的 AiServices 支持声明输入、输出护栏；Spring AI 可以用自定义 Advisor 在调用前后插入检查。无论用哪种，护栏逻辑本身应是普通 Java 代码，可单测、可单独开关。

六、线上可观测

1、记录什么

每次模型调用作为调用链上的一个 Span，至少包含以下维度：

维度内容用途
标识Trace ID、会话 ID、用户（脱敏）、业务场景串联一次用户请求里的多次模型与工具调用
版本Prompt 版本、模型标识、检索参数版本出问题时定位是哪次变更引入的
用量输入 / 输出 Token、缓存命中 Token成本看板与异常告警
延迟首 Token 时间、总耗时、工具耗时体验与容量
结果结束原因（正常 / 截断 / 工具调用）、护栏是否拦截、用户反馈质量监控与样本回流
内容Prompt 与回答原文排障，默认不记，按需采样

Spring AI 基于 Micrometer 自动产生模型调用、Advisor、工具、向量库的观测数据，Token 用量指标为 gen_ai.client.token.usage，详见 Spring AI；链路接入与上下文传播见 链路追踪。

2、内容的采样存储与脱敏

Prompt 和回答原文对排障和评估集回流很有价值，但体积大且含用户数据：

  • 默认只记元数据，原文按比例采样，护栏拦截、用户差评、报错的请求全量保留
  • 原文落盘前脱敏，存到单独的存储并设置保留期，访问需要审批和审计
  • 不要把原文写进普通应用日志或 Span 属性里随链路系统到处复制

3、OpenTelemetry GenAI 语义约定

OpenTelemetry 为大模型调用定义了 GenAI 语义约定（属性如 gen_ai.operation.name、gen_ai.request.model、gen_ai.usage.input_tokens），让不同框架、不同可观测后端的数据可以统一查询。该约定目前仍处于 Development（实验性）状态，属性名仍可能调整，接入时以所用版本的官方页面为准；Prompt 与回答内容的采集在约定中是可选的，默认不开启。OpenTelemetry 的通用接入见 OpenTelemetry。

4、线上质量信号

离线评估只能覆盖已知问题，线上要靠信号发现未知问题：点赞点踩、重新生成、转人工、用户在回答后立刻改写问题、护栏拦截率、结构化输出解析失败率、「没有找到」比例。这些指标按 Prompt 版本和模型分组看，配合 告警 发现突变；也可以对采样的线上流量异步跑 Judge 打分，作为趋势指标。

七、灰度与回滚

1、Prompt 版本化与配置化

Prompt 和代码一样需要评审和版本，但它的变更频率更高，常见两种做法：

  • 随代码发布：Prompt 作为资源文件放在仓库里，走正常的评审与发布流程，简单可靠，适合大多数团队
  • 配置中心下发：Prompt 以「名称 + 版本号」存配置中心，运行时按版本加载，可以不发版切换和回滚；代价是要自己保证配置变更同样经过评估门禁

无论哪种，调用记录里都要带 Prompt 版本号，回滚就是把版本指针切回去。

2、灰度方式

方式做法适合
影子流量复制线上请求给新版本跑，结果只记录不返回用户，离线对比换模型、大改 Prompt，先看效果和成本
按比例灰度按用户 ID 哈希分流 1% → 10% → 50% → 100%，同一用户固定落在同一版本常规上线
A/B 实验两个版本各占一部分流量，对比满意度、转人工率等业务指标两个方案都可行、需要用数据决定

影子流量会额外消耗配额，要限流并排除有副作用的工具调用。通用的灰度与功能开关做法见 发布策略。

3、模型切换与降级

  • 固定模型快照：生产配置使用带日期或版本号的模型标识，而不是 latest 别名，升级模型走一遍评估和灰度
  • 备用模型：主模型持续报错或超时时切到备用模型（另一家厂商或自建模型），备用模型同样要跑过评估集
  • 降级到规则或缓存：模型整体不可用时，常见问题返回缓存答案或 FAQ 检索结果，办理类请求引导到传统表单或人工
  • 熔断与超时：模型调用按外部依赖治理，错误分类与重试见 API 直接接入，熔断与降级的通用设计见 降级

八、成本与延迟优化

成本和延迟大头都在 Token 上，优化按收益从高到低：

1、缓存

类型做法注意
精确缓存以「规范化后的输入 + Prompt 版本 + 模型」为键缓存回答只适合与用户无关的问题；Prompt 版本变更自动失效
语义缓存输入向量化，与历史问题相似度超过阈值就复用答案阈值过低会答非所问，必须带上权限与租户隔离，命中结果也要过输出护栏
提示缓存厂商侧缓存长前缀（系统提示、工具定义、长文档），后续请求只为增量付全价稳定内容放在最前面，变化内容放后面，见 API 直接接入

2、小模型路由

不是每个请求都需要最强的模型：意图分类、抽取、改写、摘要交给小模型，复杂推理和多步工具调用才交给大模型。路由可以是规则（按场景），也可以先用小模型判断难度再决定，路由策略本身也要进评估集，防止把难题分给小模型。

3、减少 Token

  • 系统提示精简，示例只保留有代表性的几条
  • RAG 控制 Top-K 与片段长度，Rerank 后再送入模型
  • 对话历史设窗口并做摘要，工具返回值只保留模型需要的字段
  • 限制最大输出 Token，要求简洁回答；推理模型限制思考预算

4、流式与批处理

  • 流式输出：不减少总耗时，但大幅缩短用户看到第一个字的时间，交互场景默认开启，传输层见 SSE（Server-Sent Events）
  • 并行：互不依赖的多次调用（多路检索、多个子任务）并行发起，用虚拟线程或异步客户端
  • 批处理：离线任务（批量打标、摘要、评估集跑分）走厂商的 Batch 接口，用更长的完成时间换更低的成本和更宽的配额

九、上线检查清单

评估

  • [ ] 有带版本的评估集，覆盖核心场景、无答案问题与对抗样本
  • [ ] LLM Judge 与人工标注的一致率已校准
  • [ ] 评估已接入 CI，门禁含硬门槛、相对门槛与分组结果
  • [ ] 当前版本的基线分数、Token 用量、P95 延迟已记录

安全

  • [ ] 输入护栏：注入检测、敏感信息脱敏、长度与频率限制
  • [ ] 输出护栏：格式校验、引用核对、越权与外链检查、统一拒答
  • [ ] 工具按场景最小授权，以用户身份执行，副作用操作人工确认
  • [ ] RAG 按用户权限过滤检索结果

可观测

  • [ ] 每次调用记录 Prompt 版本、模型标识、Token、延迟、结束原因
  • [ ] 原文采样存储已脱敏，有保留期与访问审计
  • [ ] 有质量信号看板与告警（拦截率、解析失败率、差评率、成本突增）

发布与运维

  • [ ] 生产使用固定的模型快照标识
  • [ ] Prompt 可按版本回滚，灰度按用户固定分流
  • [ ] 有备用模型与规则 / 缓存降级方案，超时与熔断已配置
  • [ ] 评估与线上使用独立的 API Key 与配额，按业务设置用量上限

小结

  • LLM 输出非确定、变更面广，必须用带版本的评估集对每次变更打分并与基线比较
  • 评估集来自线上分层抽样、专家标注的黄金集、对抗样本和失败回流，记录评估集、Prompt、模型、检索参数四个版本
  • 评估方法由便宜到昂贵：规则、Schema 校验、相似度、LLM-as-a-Judge、人工抽检；Judge 有位置、长度、自我偏好偏差，要用人工标注校准
  • Prompt、模型、检索参数的变更走 CI 门禁：硬门槛 + 相对门槛 + 分组结果，Java 侧用 JUnit 驱动即可
  • 护栏是请求前后的确定性检查，输入防注入与脱敏，输出做格式、引用、越权检查和统一拒答；工具权限最小化
  • 线上记录版本、Token、延迟与质量信号，原文采样并脱敏；GenAI 语义约定仍在演进
  • 上线用影子流量与按用户灰度，固定模型快照，备好备用模型与规则、缓存降级
  • 降本优先缓存与小模型路由，再压缩 Token；流式改善首字延迟，离线任务走批处理
