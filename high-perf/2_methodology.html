性能分析方法论

前置阅读：性能指标

性能分析最常见的错误是"凭经验猜"，方法论的价值在于给出可重复的排查路径，让每一步都有数据支撑。本篇讲 USE / RED 方法、自顶向下的瓶颈定位流程、用 Amdahl 定律决定优化顺序，以及可验证的优化闭环。

一、USE 方法：面向资源

对每一种资源检查三个维度：使用率、饱和度、错误。 由 Brendan Gregg 提出：

维度含义示例
Utilization（使用率）资源忙碌的时间占比CPU 使用率 85%、磁盘 %util 95%
Saturation（饱和度）资源无法立即处理、需要排队的程度Load 高于核数、线程池队列堆积、磁盘 aqu-sz 升高
Errors（错误）资源相关的错误事件网卡丢包、TCP 重传、连接获取超时

常见资源的 USE 检查清单：

资源使用率饱和度错误
CPUtop us+syLoad Average、vmstat r 列——
内存free usedSwap 使用、vmstat si/soOOM Killer 日志
磁盘iostat -x %utilawait、aqu-szdmesg IO 错误
网络sar -n DEV 带宽丢包、socket backlog 溢出重传、netstat -s 错误计数
线程池活跃线程 / 最大线程队列长度拒绝次数
连接池活跃连接 / 最大连接等待获取连接的线程数获取连接超时

iostat 列名

较新版本的 sysstat 中平均队列长度列名为 aqu-sz，旧版本为 avgqu-sz，含义相同。

USE 的优点是覆盖完整、不遗漏，适合"系统整体变慢但不知道原因"时做第一轮排查。线程池、连接池、锁这类软件资源同样适用 USE。

二、RED 方法：面向服务

对每个服务（或接口）采集请求速率、错误、耗时三个指标：

指标含义Prometheus 示例
Rate每秒请求数rate(http_server_requests_seconds_count[1m])
Errors每秒失败请求数或错误率状态码 5xx 的 rate
Duration请求耗时分布（分位数）histogram_quantile(0.99, ...)
  • RED 回答"哪个服务、哪个接口有问题"，USE 回答"哪种资源有问题"，两者互补：先用 RED 找到慢接口，再用 USE 查它所在机器与依赖的资源。
  • Spring Boot + Micrometer 暴露的 http.server.requests 指标就是 RED 所需的数据；分位数直方图需开启 management.metrics.distribution.percentiles-histogram.http.server.requests=true。监控体系建设见 可观测性。

三、瓶颈定位流程

1、自顶向下

从现象出发逐层下钻，每一层用数据排除或确认，再进入下一层：

步骤要回答的问题手段下钻方向
① 系统资源CPU、内存、IO、网络是否打满或饱和top、vmstat、iostat、sarCPU 高 → 看是哪个进程/线程；IO 高 → 看哪个进程在读写
② JVMGC 是否频繁、停顿是否过长、堆是否持续上涨GC 日志、jstat -gcutil、JFRGC 问题 → JVM 层性能策略；内存泄漏 → 堆 dump 分析
③ 应用线程/锁哪些方法耗 CPU、线程卡在哪里、是否有锁竞争jstack、Arthas thread / trace、火焰图热点方法 → 代码优化；BLOCKED 多 → 锁优化
④ 外部依赖时间是否花在等待 DB、缓存、RPC、MQ链路追踪、慢查询日志、客户端耗时埋点慢 SQL → 数据访问性能

2、快速判断：CPU 忙还是在等

请求慢时，先看 CPU 是高还是低，这是最实用的分叉点：

  • CPU 高、RT 高：计算型瓶颈。用 CPU 火焰图找热点方法，或检查是否 GC 线程占满 CPU。
  • CPU 低、RT 高：等待型瓶颈。线程在等锁、等 IO、等连接池、等下游。用 jstack 看线程状态分布，或用 async-profiler 的 wall-clock 模式（-e wall）采样。

具体故障排查步骤（CPU 飙高、内存泄漏、死锁）见 JVM 故障排查 与 线上诊断。

四、Amdahl 定律：决定优化顺序

1、公式

局部优化对整体的加速上限：S = 1 / ((1 - p) + p / k)，其中 p 为被优化部分占总耗时的比例，k 为该部分自身的加速倍数。

推导：设原总耗时为 1，未优化部分耗时 1 - p 不变，被优化部分从 p 变为 p / k，新耗时为 (1 - p) + p / k，加速比即原耗时除以新耗时。

被优化部分占比 p自身加速 k整体加速比
5%∞1.05
10%10 倍1.10
50%10 倍1.82
90%10 倍5.26
90%∞10

2、推论

  • 先优化占比最大的部分：占比 5% 的环节即使降到 0，整体也只快约 5%。
  • 并行化同样受限：任务中有 10% 必须串行，无论加多少核，加速比上限都是 10 倍。
  • 微基准的收益不能直接外推：某方法快 30%，要乘以它在接口总耗时中的占比才是真实收益。

Little 定律

容量与并发的关系用 Little 定律 L = λW 估算，推导与示例见 性能指标。典型用法：下游 RT 从 20ms 涨到 200ms，调用方占用的线程数放大 10 倍，线程池被打满。

六、长尾治理

P99 往往不是"慢代码"造成的，而是排队、GC、缓存未命中、邻居干扰等偶发因素；扇出越多，偶发因素越会变成常态。 所以长尾要单独治理，而不是只盯平均耗时。

1、P99 放大

场景现象原因
并行扇出调用 N 个下游，整体耗时取最慢的一个至少一个下游命中 P99 的概率 1 - 0.99^N，N = 100 时约 63%
串行链路多跳调用逐级叠加每一跳的长尾叠加，且上游超时通常大于下游
重试失败后重试拉长总耗时一次超时 + 一次重试，耗时可达单次的两倍以上

降低扇出本身（聚合接口、批量 API、合并下游）往往比优化单个下游更有效。

2、对冲请求（Hedged Request）

先向一个副本发请求，等待超过该接口的 P95 等阈值仍未返回，再向另一个副本补发一份，取先返回的结果并取消另一个。

  • 只额外增加少量请求（阈值取 P95 时理论上约 5%），却能显著削掉长尾，来自 Google 的 The Tail at Scale。
  • 只适用于幂等、无副作用的读请求，写请求不能对冲。
  • 下游整体过载时对冲会加剧拥塞，应设置对冲比例上限，并与熔断、限流配合。
  • gRPC 的 hedging policy、部分数据库与缓存客户端提供对冲或"推测执行"能力，使用前确认所用版本是否支持。
  • 基于 CompletableFuture 的实现示例见 异步与批量 - 长尾治理。

3、超时预算（Deadline Propagation）

给整条请求一个总时限，每一跳用"剩余预算"作为自己的超时，而不是每跳各自配置固定超时。

做法说明
入口设总预算如网关给下单请求 800ms
向下传递截止时间通过请求头或 RPC 元数据传递 deadline（gRPC 原生支持 deadline 传播）
每跳扣减本跳超时 = 剩余预算 − 本地处理余量；预算已耗尽时直接失败，不再调用下游
重试也占预算剩余预算不足以完成一次调用时不再重试

超时与重试的具体取值策略见 超时、重试与隔离。

七、优化闭环

性能优化应是一个可验证的循环，而不是一次性"拍脑袋"修改：

阶段做什么产出
1、建立基线在固定环境、固定数据量、固定压测模型下测出当前指标QPS、P50/P99、错误率、资源使用率
2、提出假设根据分析数据指出瓶颈并预测收益"该接口 70% 耗时在 N+1 查询，改为批量后 P99 预计降低 60%"
3、实验一次只改一个变量，在相同条件下复测对比数据
4、验证与基线对比，确认收益符合预期且无副作用（正确性、资源、其他接口）结论与记录
5、固化上线、加监控告警、把基线纳入回归（如 CI 中的 JMH 或定期压测）防止性能回退

注意事项：

  • 环境一致：压测环境与线上的硬件、JVM 参数、数据规模差异越大，结论越不可信。
  • 预热：JIT 编译、缓存、连接池都需要预热，冷启动数据不能作为基线。
  • 看分布不看平均：以 P99 等分位数和资源使用率共同判断。
  • 记录每一次实验：包括无效的尝试，避免重复踩坑。

微观代码对比使用 JMH 基准测试，系统级验证使用 压测。

小结

  • USE 面向资源（使用率、饱和度、错误），RED 面向服务（速率、错误、耗时），先 RED 找接口再 USE 查资源
  • 自顶向下：系统资源 → JVM → 线程/锁 → 外部依赖；先判断"CPU 忙还是在等"
  • Amdahl 定律决定优化顺序：先优化占比最大的部分，微基准收益要乘以占比
  • 长尾要单独治理：减少扇出、对冲请求（仅幂等读）、超时预算逐跳传递
  • 优化是闭环：基线 → 假设 → 单变量实验 → 验证 → 固化
