高性能总览

本模块聚焦系统级的性能优化策略与方法：如何度量、如何定位瓶颈、在各层有哪些通用手段。 具体技术的原理与调优（GC、JIT、索引、Redis、Kafka、Netty 等）在各自模块中已有专题，本模块只做方法串联并给出链接。

一、什么是高性能

"三高"中的高性能，关注的是单次请求更快、单位资源处理更多：

维度目标核心指标
延迟（Latency）单个请求处理得更快，长尾更短RT 的 P50 / P99 / P999
吞吐（Throughput）同样的机器每秒处理更多请求QPS / TPS、MB/s
资源利用率（Efficiency）同样的流量消耗更少的 CPU、内存、IO、带宽CPU 使用率、GC 开销、每请求资源成本

三者并不总是同向：批量化提升吞吐但会增加单条延迟；缓存降低延迟但消耗内存。优化之前必须先明确目标是哪一个，并把它写成可度量的指标（如"下单接口 P99 从 800ms 降到 200ms，CPU 不增加"）。指标定义见 性能指标。

二、优化分层

性能问题可以出现在请求链路的任何一层，每一层的手段、收益和代价差异很大：

层次典型手段典型收益主要代价详见
代码更优算法、集合预分配、减少对象创建和装箱、缩小锁粒度局部数倍，热点路径上效果明显低，但需要 Profiler 指明热点代码级优化
JVMGC 选型、堆与代大小、JIT 预热、减少停顿主要改善长尾与吞吐稳定性参数改动风险需压测验证GC 调优、JIT
中间件/缓存多级缓存、池化、MQ 异步、批量读路径常见十倍级一致性、运维复杂度缓存、池化技术、异步与批量
数据库索引、SQL 改写、深分页治理、批量写、消除 N+1慢 SQL 优化常见十到千倍低～中，需关注索引写放大数据访问性能
架构同步转异步、预计算、请求合并、读写分离、拆分量级提升高：一致性、链路变长、团队协作异步与批量、数据层扩展
网络连接复用、HTTP/2、压缩、高效序列化、CDN、减少往返跨机房/公网场景收益显著中：协议升级、兼容性IO 与网络优化

经验规律：

  • 越靠近数据和 IO 的优化，收益往往越大。一个接口 500ms，其中 480ms 在等 SQL，优化 Java 代码没有意义。
  • 越靠近架构的优化，代价越高且越难回滚，应在代码、SQL、缓存等低成本手段用尽后再考虑。

三、核心原则

1、先度量，再优化

  • 没有基线数据就无法判断优化是否有效，也无法说明收益。
  • 线上用 APM / 链路追踪 / 指标系统定位慢在哪里；微观代码用 JMH 基准测试 对比；整体容量用 压测 验证。

2、优化瓶颈，而不是凭感觉猜热点

  • 按 Amdahl 定律，只优化占总耗时 5% 的环节，即使将其降到 0，整体也只快 5%。
  • 用 Profiler 和火焰图找到真正的热点，见 性能分析方法论 与 性能分析工具。

3、常用优化思路

思路本质典型例子
空间换时间用内存/存储换计算与 IO缓存、索引、预计算、布隆过滤器
时间换空间用计算换内存/带宽压缩、位图、编码优化
异步化把非关键路径移出主流程CompletableFuture 并行调用、MQ 解耦
批量化摊薄每次操作的固定开销批量 SQL、Redis Pipeline、MQ 批量发送
池化复用创建代价高的资源连接池、线程池
并行化利用多核与多节点并行调用下游、分片处理
减少往返降低网络 RTT 次数聚合接口、批量 API、Keep-Alive
就近访问缩短物理距离CDN、本地缓存、同机房部署
做减法不做不必要的事去掉冗余查询、按需加载字段、减少日志

4、避免过早优化

  • 优化会增加复杂度，应只针对有数据证明的瓶颈，并权衡可读性和维护成本。
  • 但"避免过早优化"不等于"不考虑性能"：数据结构选型、接口粒度、索引设计等决定性能上限的问题，应在设计阶段就考虑。

四、与高并发、高可用的关系

模块关注点典型问题典型手段
高性能（本模块）单次请求更快、资源更省接口慢、CPU 高、GC 频繁代码/SQL/缓存优化、池化、异步、批量
高并发流量大时扛得住峰值流量、热点、容量不足水平扩展、削峰填谷、热点隔离、容量规划
高可用故障时不停服依赖故障、雪崩、机房故障限流、熔断、降级、冗余、容灾

三者相互支撑：

  • 高性能是高并发的基础：由 Little 定律，线程数固定时 RT 减半，可承载 QPS 翻倍，性能优化本身就是最便宜的"扩容"。
  • 高性能也服务于高可用：RT 稳定、长尾短，就不容易因为下游变慢导致线程池耗尽和级联故障。
  • 反过来，某些高可用手段（重试、多副本同步）会增加延迟，需要在性能和可用性之间取舍。
