性能指标

性能优化的第一步是"能度量"。本文梳理衡量系统性能的业务指标、延迟分布指标与资源指标，以及它们之间的数量关系。 压测时如何采集这些指标见 性能测试，分析方法见 性能分析方法论。

一、常见性能指标

1、QPS（Queries Per Second）

  • QPS 是衡量系统处理请求能力的一个重要指标，表示系统每秒钟能够处理多少个请求。
  • QPS 高低直接决定了系统的吞吐量和响应能力，是容量规划的基础数据。

2、TPS（Transactions Per Second）

  • TPS 表示每秒处理的事务数量，通常用于数据库或消息队列等需要进行事务处理的场景。
  • 与 QPS 的区别在于，TPS 针对的是一个完整的业务事务（可能包含多次请求），而 QPS 更侧重于单个请求的数量。例如"下单"是 1 个事务，内部可能产生 5 次接口调用。

3、RT（Response Time）

  • RT 用来衡量系统对一个请求的响应速度，即从客户端发起请求到接收到响应的时间。
  • 通常以毫秒（ms）为单位，RT 过高意味着系统存在性能瓶颈或资源不足。
  • RT 必须看分布而不是只看平均值，见下文第二节。

4、并发数（Concurrency）

  • 并发数是指在同一时刻系统正在处理（已接收、未返回）的请求数量，是衡量系统并发能力的一个重要维度。
  • 注意区分"在线用户数"与"并发数"：在线用户大部分时间处于思考/浏览状态，并不产生请求。

5、吞吐量（Throughput）

  • 吞吐量是指单位时间内系统可以处理的请求或数据的数量，通常与 QPS、TPS、并发数和带宽等指标结合使用。
  • 对 Web 服务吞吐量一般就是 QPS；对 MQ、存储、网络则常以 MB/s、条/秒衡量。

二、平均值 vs 分位数

1、为什么平均值会误导

平均 RT 会把少数极慢请求"摊平"。假设 100 个请求中 98 个耗时 10ms、2 个耗时 2000ms：

统计方式结果解读
平均值49.8ms看起来很健康
P5010ms一半用户体验良好
P992000ms每 100 次请求就有约 1～2 次很慢
Max2000ms存在长尾，可能是 GC、锁或慢 SQL
  • 平均值掩盖长尾，而用户感知和超时故障恰恰由长尾决定。
  • 一个页面往往扇出调用多个服务，扇出越多，命中某个服务 P99 的概率越高：调用 100 个服务时，至少一次碰上 P99 慢请求的概率约为 1 - 0.99^100 ≈ 63%。

2、常用分位数

指标含义典型用途
P50（中位数）50% 请求快于该值反映"一般体验"
P9090% 请求快于该值常规 SLA 口径
P9999% 请求快于该值核心接口 SLO、超时设置依据
P99999.9% 请求快于该值金融、交易等长尾敏感场景

3、实践要点

  • 分位数不能求平均、不能直接相加：多实例的 P99 要基于直方图合并（如 Prometheus histogram_quantile），不能对各实例 P99 取平均。
  • 压测报告至少给出 QPS + P50/P99 + 错误率 三件套，只报平均 RT 的报告没有参考价值。
  • 注意协调遗漏（Coordinated Omission）：压测工具在服务卡顿时会少发请求，导致测出的长尾偏乐观。wrk2、Gatling 的固定速率模式可以缓解。

业务指标告诉你"慢了"，资源指标告诉你"卡在哪"。

四、指标之间的关系：Little 定律

1、公式

排队论中的 Little 定律（Little's Law）描述了稳态系统中三者的关系：

并发数 = 吞吐量（QPS） × 平均响应时间（RT，单位秒）

2、应用示例

已知推算
QPS = 2000，RT = 50ms系统内平均并发 = 2000 × 0.05 = 100
线程池 200 线程（全阻塞 IO），RT = 100ms理论最大 QPS ≈ 200 / 0.1 = 2000
连接池 20 连接，SQL 平均 5ms数据库侧理论上限 ≈ 20 / 0.005 = 4000 次/秒

3、推论

  • RT 上升会直接吃掉容量：并发资源（线程、连接）固定时，RT 翻倍，可承载 QPS 减半。这就是下游变慢会拖垮上游线程池的原因。
  • 降低 RT 等价于扩容：把接口从 100ms 优化到 50ms，同样的线程数可以多扛一倍流量——这是高性能对高并发的直接贡献。
  • 定律只在稳态下成立；当请求到达速率超过处理能力，队列无限增长，RT 会急剧恶化（拐点），这就是压测中"QPS 不再上升、RT 陡增"的点。

五、常用组件 QPS 参考

以下为经验量级，实际值强烈依赖硬件、数据规模、请求复杂度和配置，仅用于估算和发现"数量级错误"，不能替代压测。

1、Tomcat 与 Undertow

  • Tomcat：作为常用的 Java Web 容器，Tomcat 的 QPS 通常受限于服务器硬件、线程池配置、JVM 设置等因素，简单接口一般可以达到几千到数万。
  • Undertow：相比 Tomcat 更轻量，基于 XNIO，在 HTTP/2 和异步处理方面表现更好。在相同硬件配置下，Undertow 的 QPS 通常略高于 Tomcat；但对大多数业务而言，瓶颈在业务逻辑和下游，而非容器本身。

2、MySQL

MySQL 的 QPS 与表设计、索引、SQL 写法、硬件配置和并发连接数等因素有关：

  • 普通查询：走索引的简单查询，单实例每秒可处理数千到数万条。
  • 事务性操作：涉及事务和复杂查询时，QPS 会降低，可能在数百到几千之间。

3、Redis

Redis 基于内存存储，单实例 QPS 通常在 10 万级，Pipeline 批量下可更高。

  • 单线程模型：命令执行是单线程的，依赖 IO 多路复用处理大量连接；Redis 6 起网络 IO 可多线程。
  • 吞吐量：简单命令（GET/SET/INCR）吞吐远高于 MySQL；大 Key、KEYS、复杂 Lua 会严重拉低吞吐。
  • Redis Cluster：通过分片扩展，集群 QPS 近似线性提升，可支撑百万级。

4、消息队列（MQ）

MQ 的吞吐取决于实现、消息大小、刷盘与副本策略、网络带宽等：

  • Kafka：顺序写 + 批量 + 零拷贝，单集群可达每秒数百万条消息，适合日志与流处理。
  • RocketMQ：单机可达十万级 TPS，支持事务消息、延时消息，适合业务消息。
  • RabbitMQ：路由灵活、可靠性机制完善，单机一般在万级到数万级。
  • ActiveMQ：老牌 MQ，吞吐较低，适合中小规模系统。

5、Elasticsearch

  • 在合理硬件和索引设计下，查询可达每秒数千到数万。
  • 写入吞吐视 Mapping、副本数、refresh 间隔而定，一般在几千到几万条每秒，批量 _bulk 写入可显著提升。
  • 通过分片和副本机制横向扩展。

6、Nginx

  • 事件驱动 + 异步非阻塞，单机可支持每秒数万至数十万 HTTP 请求（静态资源、简单反代）。
  • 通常作为系统的流量入口，承担静态资源、TLS 卸载、负载均衡。

7、MongoDB

  • 单节点 QPS 可达数千至数万（取决于查询复杂度和索引）。
  • 通过分片集群可继续扩展；强一致写（w: majority）会增加延迟。

8、Apache Cassandra

  • 分布式宽列存储，基于 LSM 树，写入性能突出，大规模集群可实现每秒数百万写入。
  • 读写性能稳定且线性扩展，适合 IoT、时序、大数据写多读少场景。

9、ZooKeeper

  • 写请求需经 Leader 广播并过半确认，写 QPS 通常在数千到一万左右；读可由各节点本地响应，吞吐更高。
  • 关注一致性与可靠性，适合配置管理、选主、分布式协调，不适合当高频存储用。

10、gRPC

  • 基于 HTTP/2 + Protobuf，支持多路复用和双向流，单机可达数万至数十万次调用。
  • 同等条件下通常比 JSON over HTTP/1.1 的 REST 延迟更低、吞吐更高，适合服务间高频通信。
