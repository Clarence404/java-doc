性能指标

本篇目标：掌握衡量性能的业务指标、延迟分布与资源指标，并用 Little 定律把 QPS、RT、并发数联系起来。

性能优化的第一步是"能度量"。压测时如何采集这些指标见 性能测试。

一、业务指标

QPS、RT、并发数三者由 Little 定律联系在一起（见第四节），其余指标是它们在不同场景下的变体。

指标含义单位注意点
QPS（Queries Per Second）每秒处理的请求数次/秒容量规划的基础数据
TPS（Transactions Per Second）每秒完成的业务事务数笔/秒一个事务可能包含多次请求，如"下单"1 笔内部产生 5 次接口调用
RT（Response Time）从发出请求到收到响应的耗时ms必须看分布而不是平均值，见第二节
并发数（Concurrency）同一时刻已接收、未返回的请求数个不等于在线用户数：在线用户大部分时间在浏览，不产生请求
吞吐量（Throughput）单位时间处理的请求或数据量次/秒、MB/s、条/秒Web 服务一般就是 QPS；MQ、存储、网络常用 MB/s 或条/秒

二、平均值 vs 分位数

1、为什么平均值会误导

平均 RT 会把少数极慢请求"摊平"。 假设 100 个请求中 98 个耗时 10ms、2 个耗时 2000ms：

统计方式结果解读
平均值49.8ms看起来很健康
P5010ms一半用户体验良好
P992000ms每 100 次请求就有约 1～2 次很慢
Max2000ms存在长尾，可能是 GC、锁或慢 SQL
  • 平均值掩盖长尾，而用户感知和超时故障恰恰由长尾决定。
  • 扇出会放大长尾：一次请求并行调用 100 个服务时，至少碰上一次 P99 慢请求的概率约为 1 - 0.99^100 ≈ 63%。治理手段见 性能分析方法论 的长尾治理一节。

2、常用分位数

指标含义典型用途
P50（中位数）50% 请求快于该值反映"一般体验"
P9090% 请求快于该值常规 SLA 口径
P9999% 请求快于该值核心接口 SLO、超时设置依据
P99999.9% 请求快于该值金融、交易等长尾敏感场景

3、实践要点

  • 分位数不能求平均、不能直接相加：多实例的 P99 要基于直方图合并（如 Prometheus histogram_quantile），不能对各实例 P99 取平均。
  • 压测报告至少给出 QPS + P50/P99 + 错误率 三件套，只报平均 RT 的报告没有参考价值。
  • 注意协调遗漏（Coordinated Omission）：闭环压测工具在服务卡顿时会少发请求，导致测出的长尾偏乐观。wrk2 的固定速率模式、Gatling 等工具的开放模型（按到达速率注入）可以缓解。

三、资源指标

业务指标告诉你"慢了"，资源指标告诉你"卡在哪"。

资源核心指标常用命令/来源异常信号
CPU使用率（us/sy/wa）、Load Average、上下文切换top、vmstat 1、pidstat -wus 高：计算热点；sy 高：系统调用/锁竞争；wa 高：IO 等待
内存已用/可用、Swap、Page Faultfree -m、vmstat、/proc/meminfo发生 Swap、OOM Killer
磁盘 IOIOPS、吞吐、await、%utiliostat -x 1await 显著升高、%util 接近 100%
网络带宽、PPS、重传率、连接数（TIME_WAIT）sar -n DEV 1、ss -s、netstat带宽打满、重传率 > 1%、端口耗尽
JVM GC停顿时间、频率、晋升速率、堆占用jstat -gcutil、GC 日志、JFRFull GC 频繁、单次停顿超出 SLO
线程活跃线程数、BLOCKED/WAITING 数、线程池队列长度jstack、Arthas thread、Micrometer线程池满、大量线程 BLOCKED
  • Load Average 表示处于可运行 + 不可中断（通常是 IO）状态的平均进程数，需要与 CPU 核数对比：长期高于核数说明有排队。
  • %util 在 SSD / NVMe 等可并行处理请求的设备上接近 100% 不一定代表饱和，应结合 await 与队列长度判断。
  • GC 指标的解读见 JVM 层性能策略，监控工具见 JVM 诊断工具。

四、指标之间的关系：Little 定律

1、公式与直观理解

稳态系统中：平均并发数 L = 到达速率 λ × 平均停留时间 W，即 并发数 = QPS × RT（秒）。

直观推导：观察一段时间 T，共到达 λT 个请求，每个请求在系统里停留 W 秒，它们累计"占用系统"的时间为 λT × W；把这段累计时间平摊到 T 上，平均同时在系统中的请求数就是 λT × W / T = λW。

  • 定律不依赖到达分布和服务时间分布，只要求系统处于稳态（长期看到达速率等于离开速率）。
  • "系统"可以是任意边界：整个服务、一个线程池、一个连接池、一次数据库调用。

2、应用示例

已知推算
QPS = 2000，RT = 50ms系统内平均并发 = 2000 × 0.05 = 100
线程池 200 线程（全阻塞 IO），RT = 100ms理论最大 QPS ≈ 200 / 0.1 = 2000
连接池 20 连接，单次持有连接 5ms数据库侧理论上限 ≈ 20 / 0.005 = 4000 次/秒
QPS 1000，单次持有连接 20ms平均需要 1000 × 0.02 = 20 个连接（再留余量应对峰值与波动）

3、推论

  • RT 上升会直接吃掉容量：并发资源（线程、连接）固定时，RT 翻倍，可承载 QPS 减半。这就是下游变慢会拖垮上游线程池的原因。
  • 降低 RT 等价于扩容：接口从 100ms 优化到 50ms，同样的线程数可以多扛一倍流量——这是高性能对高并发的直接贡献。
  • 定律只在稳态下成立：到达速率超过处理能力时队列持续增长，RT 急剧恶化，这就是压测中"QPS 不再上升、RT 陡增"的拐点。

五、常用组件量级参考

以下为单实例/单集群的经验量级，只用于估算和发现"数量级错误"，不能替代压测。 实际值强烈依赖硬件、数据规模、请求复杂度和配置；基于这些量级做流量与机器数估算的方法见 容量评估与规划。

小结

  • 业务指标看 QPS、RT、并发数，RT 必须看分位数，报告至少给出 QPS + P50/P99 + 错误率
  • 分位数不能求平均或相加，多实例要基于直方图合并；压测注意协调遗漏
  • 资源指标用来定位"卡在哪"：CPU、内存、磁盘、网络、GC、线程
  • Little 定律 L = λW：RT 上升会吃掉容量，降低 RT 等价于扩容
  • 组件量级只用于发现数量级错误，最终以压测为准
