MQ 选型与其他 MQ

本篇目标：能按业务特征在 Kafka / RocketMQ / RabbitMQ 之间做出有理由的选择，了解 Pulsar 的定位，避开选型时的常见误判。

前置阅读：Kafka、RocketMQ、RabbitMQ

前面三篇分别讲了三大 MQ 的原理与用法。选型时真正起作用的往往不是"谁性能最高"，而是消息语义（事务、延迟、回放、路由）和团队能否运维得住。本篇把差异收拢到一张表里，再给出场景化的建议。

一、三大 MQ 对比

一句话定位：Kafka 是事件流平台（日志即存储），RocketMQ 是面向业务消息的中间件，RabbitMQ 是灵活路由的消息代理。

维度Kafka（4.x）RocketMQ（5.x）RabbitMQ（4.x）
定位分布式事件流平台业务消息中间件通用消息代理
协议自有二进制协议自有协议（Remoting）/ 5.x Proxy 提供 gRPCAMQP 0-9-1 / AMQP 1.0，插件支持 MQTT / STOMP
吞吐量（相对）最高高中
延迟毫秒级，批量参数影响大毫秒级毫秒级，低负载下通常最低
顺序消息分区内有序队列内有序（5.x 按 MessageGroup）单队列 + 单消费者有序
事务事务 = 跨分区原子写 + 精确一次（EOS），不是半消息回查原生事务消息（半消息 + 本地事务 + 回查）无事务消息；只有 AMQP tx（性能差）与 Publisher Confirms
延迟消息不原生支持5.x 任意时间定时消息（4.x 为 18 个固定级别）TTL + 死信交换机，或延迟消息插件
消息存储按时间 / 大小长期保留按时间保留（默认数天）经典 / 仲裁队列消费确认后删除；Stream 长期保留
消息回放支持（重置 Offset）支持（重置消费位点）Stream 支持；经典 / 仲裁队列不支持
死信无内置，常用 DeadLetterPublishingRecoverer 写 DLT内置重试队列 + 死信队列内置死信交换机（DLX）
高可用副本 ISR + Leader 选举，元数据 KRaft主从 / DLedger（4.x），5.x Controller 模式自动切主仲裁队列（Raft）；4.0 已移除经典镜像队列
运维依赖4.0 起不再依赖 ZooKeeper，只用 KRaftNameServer + Broker（5.x 可加 Proxy）单一 Erlang 集群，部署最简单
生态Connect / Streams / Flink / CDC 最完善国内电商、金融场景广泛，云厂商托管成熟Spring AMQP 成熟，多语言客户端齐全
典型场景日志、埋点、数据管道、事件溯源订单、支付等业务链路，最终一致事务业务解耦、复杂路由、中低并发通知

几点说明：

  • 吞吐量只看量级关系：具体数字取决于消息大小、批量、刷盘和副本策略，压测前不要拿网上的"百万 / 十万 / 万"直接下结论
  • Kafka 的"事务"和 RocketMQ 的"事务消息"是两回事：前者解决"消费—处理—生产"链路的原子性（读一个 Topic、写另一个 Topic 且只生效一次），后者解决"本地数据库事务与发消息"的一致性
  • RabbitMQ 新项目直接用仲裁队列，需要回放或大积压时用 Stream；镜像队列在 4.0 已删除，老集群升级前要先迁移

二、场景决策表

场景推荐原因
日志收集 / 埋点上报Kafka顺序写、高吞吐、长期保留，Flink / Spark 直接消费
大数据 Pipeline / 事件溯源 / CDCKafka多个消费者组独立消费同一份数据，可按 Offset 回放；CDC 工具见 数据库 · CDC 工具
流式计算（读—处理—写）Kafka事务 + EOS，Kafka Streams / Connect 生态完善
电商核心链路（订单 / 支付 / 库存）RocketMQ事务消息、定时消息（超时关单）、重试与死信开箱即用
本地事务 + 发消息的最终一致RocketMQ 事务消息，或任意 MQ + 本地消息表半消息回查保证"本地事务成功则消息必达"；方案对比见 分布式 · 分布式事务
中低并发业务解耦 / 微服务通知RabbitMQSpring AMQP 集成简单，Exchange 路由灵活，运维成本低

已在公有云上优先云厂商托管版运维成本往往比引擎差异更重要

选型时可以按下面的顺序过一遍：

  1. 有没有硬性语义要求：需要原生事务消息、任意延迟 → RocketMQ；需要长期保留与回放、流处理 → Kafka；需要复杂路由 → RabbitMQ
  2. 量级：日均消息量与峰值 QPS 是否超出 RabbitMQ 的舒适区（削峰的系统级设计见 高并发 · 异步与削峰）
  3. 团队与生态：已有的运维能力、语言栈、是否已有托管服务；同一公司尽量收敛到一到两种 MQ

三、Apache Pulsar

Pulsar 是 Apache 顶级项目，同时提供队列和流两种语义，最大特点是存算分离：Broker 只负责计算，消息持久化交给 BookKeeper。

1、架构与特性

特性说明
存算分离Broker 无状态，Topic 归属可在 Broker 间快速迁移；存储由 Bookie 集群承担，两层独立扩缩容
分段存储一个分区的数据按 Segment 分散在多个 Bookie 上，扩容新 Bookie 后新数据直接写入，无需像 Kafka 那样做分区重分配
分层存储冷数据可卸载到 S3 等对象存储，适合超长保留
多租户原生 Tenant / Namespace / Topic 三级隔离，可按租户配置配额与权限
订阅模型Exclusive / Failover / Shared / Key_Shared，一套系统覆盖队列与流
Geo 复制原生跨集群、跨地域复制
协议兼容通过 KoP 等协议处理器兼容 Kafka 客户端（成熟度需按版本评估）

2、订阅模式：一套系统同时覆盖队列与流

Pulsar 把「怎么分发给消费者」交给订阅（Subscription）决定，同一个 Topic 可以同时挂多个不同模式的订阅：

订阅模式分发方式顺序相当于
Exclusive一个订阅只允许一个消费者，多连会报错全局有序单消费者的流
Failover多个消费者，只有主消费者在收，主挂了备接管有序Kafka 消费组（分区内）
Shared多个消费者轮询分发，逐条确认不保证顺序传统工作队列（RabbitMQ 竞争消费）
Key_Shared多个消费者，同一 Key 固定发给同一消费者同 Key 有序按业务键并行 + 局部有序

逐条确认（而不是只提交位点）也让 Pulsar 天然支持单条重投、否认确认（negative ack）与死信，这正是 Kafka 需要靠 Share Group 补齐的能力。

3、和 Kafka 的关键差异

维度KafkaPulsar
存储位置分区数据存在 Broker 本地磁盘Broker 无状态，数据分段存到 BookKeeper
扩容新 Broker 需要分区重分配（搬迁数据）新 Bookie 直接接收新分段，Broker 扩容只迁移 Topic 归属，不搬数据
消费确认按分区提交位点（累计确认）逐条确认 + 累计确认都支持
多租户靠 Topic 命名与 ACL 约定原生 Tenant / Namespace 隔离，配额与策略按租户配置
跨地域复制MirrorMaker 2 等外部组件内置 Geo-Replication
冷数据分层存储（Tiered Storage）分层存储，冷段卸载到对象存储
生态Connect、Streams、Flink / Spark 集成最成熟Pulsar Functions、IO Connectors，生态相对小
运维代价4.0 起只需 Kafka 自身（KRaft）Broker + Bookie + 元数据存储三类组件，排障要同时理解计算层与存储层

4、什么时候选它

  • 平台型消息中台：要给多个团队、多个业务线共用一套集群，需要原生多租户隔离与配额。
  • 跨机房 / 跨地域复制是硬需求，希望用内置能力而不是自己维护复制链路。
  • 海量 Topic 或需要频繁弹性扩缩容，不希望每次扩容都搬迁分区数据。
  • 同一份数据既要流式回放、又要队列式竞争消费，希望用订阅模式统一。
  • 前提：团队有能力运维多组件集群。如果只是普通业务解耦、日志采集，Kafka / RocketMQ / RabbitMQ 更省心。

当前现状：Pulsar 已进入 4.x LTS 阶段，元数据存储除 ZooKeeper 外还可选 etcd、Oxia 等；国内外均有大规模生产案例。但它组件更多（Broker + Bookie + 元数据），排障需要同时理解两层，社区与中文资料也少于 Kafka、RocketMQ。适合有平台团队、明确需要多租户或跨地域复制的场景，普通业务项目不建议为"架构先进"单独引入。

另外，Kafka 社区也在补齐"队列语义"：KIP-932（Share Group，即 Queues for Kafka）允许多个消费者共享消费同一分区并逐条确认，在 4.x 中从早期访问、预览逐步推进，生产使用前请确认所用版本中该特性的状态。

四、常见误区

误区正解
"Kafka 就是最好的 MQ"Kafka 擅长高吞吐与回放，但没有原生延迟消息，也没有 RocketMQ 那样"本地事务 + 发消息"的事务消息；小流量、强业务语义的场景未必合适
"Kafka 不支持事务"Kafka 支持事务：跨分区原子写 + 配合 read_committed 实现精确一次；它不提供的是半消息回查式的事务消息
"RabbitMQ 性能差"吞吐量级低于 Kafka / RocketMQ，但低负载下延迟很低、路由能力最强；对中低并发业务完全够用
"RabbitMQ 镜像队列保证高可用"镜像队列已在 4.0 移除，高可用应使用仲裁队列
"用了 RocketMQ 事务消息 / Kafka EOS，消费端就不用幂等"任何 MQ 都可能重复投递，消费端必须幂等：业务写入与去重记录（业务键唯一约束）放在同一个本地事务里，详见 系统架构 · 幂等
"在数据库事务里发消息就能保证一致"事务回滚了消息却发出去了，或事务提交了消息没发出去；应使用本地消息表、RocketMQ 事务消息，或在提交后发送并以本地消息表兜底
"MQ 解决了分布式事务"MQ 只能做到最终一致，中间状态仍需业务侧幂等、对账与补偿
"换 MQ 很简单"顺序、事务、回放、重试语义差异很大，换 MQ 通常要改生产与消费逻辑，并重新设计监控和运维

小结

  • Kafka 偏数据管道与事件流，RocketMQ 偏业务消息与事务，RabbitMQ 偏灵活路由与中低并发解耦
  • Kafka 的事务是跨分区原子写与 EOS，RocketMQ 的事务消息是半消息回查，RabbitMQ 没有对应的事务消息
  • 延迟消息：Kafka 不原生支持，RocketMQ 5.x 支持任意时间，RabbitMQ 用 TTL + DLX 或插件
  • 版本基线：Kafka 4.0 去掉 ZooKeeper，RabbitMQ 4.0 去掉镜像队列，RocketMQ 5.x 引入 Proxy 与 Controller
  • Pulsar 以存算分离、多租户、Geo 复制见长，四种订阅模式让一套系统同时覆盖队列与流；但组件多、门槛高，平台型场景再引入
  • 选型先看语义硬需求，再看量级，最后看团队与生态；无论选哪种，消费幂等与可靠投递都要业务自己兜底
