冗余与故障转移

前置阅读：可用性度量

冗余解决"有没有备份"，故障转移解决"备份能不能自动顶上"，只有冗余没有自动切换，MTTR 取决于人工响应速度；只有切换没有防脑裂，切换本身会制造更大的故障。本篇讲如何消除单点、健康检查与自动切换的机制和时效、防脑裂，以及梳理强弱依赖并准备降级预案。

一、消除单点

单点（SPOF，Single Point of Failure）是指一旦故障就导致整体不可用的组件。梳理方式：沿请求链路逐层问"这一层只有一个吗？挂了会怎样？"

层次常见单点冗余方案
接入层单个 DNS 解析、单台 Nginx多 DNS 服务商、LVS / Nginx + Keepalived VIP、云 SLB
网关 / 应用单实例部署无状态化 + 多实例 + 负载均衡，跨可用区部署
注册 / 配置中心单节点 Nacos / ZooKeeper3 或 5 节点集群；客户端本地缓存兜底
数据库单主库主从 + 自动切换、MGR
缓存单 RedisSentinel / Cluster；缓存失效时的限流保护
消息队列单 Broker多副本（Kafka ISR、RocketMQ DLedger）
基础设施单机柜、单可用区、单机房跨机架反亲和、多可用区、多活，见 多活与容灾
人与流程只有一个人会操作、预案没人演练值班轮换、Runbook、定期演练

应用无状态化是冗余的前提：Session 放 Redis 或改用 Token、本地文件改对象存储、本地定时任务改分布式调度，这样任意实例都可被替换。

二、冷备 / 温备 / 热备

类型备用节点状态数据同步切换时间（RTO）成本典型场景
冷备未运行，只有备份文件定期全量备份小时级 ~ 天级低归档数据、非核心系统
温备已部署但不承接流量异步复制，可能落后分钟级中容灾机房、报表库
热备运行中，随时接管实时 / 半同步复制秒级 ~ 分钟级高核心数据库、网关
多活同时承接流量双向同步或分片隔离秒级（切流即可）最高核心交易链路

冷备不等于没用：备份是防误删、防勒索的最后一道防线，复制无法防止 DELETE 被同步到所有副本。备份必须定期做恢复演练，否则等于没有备份。MySQL 的备份类型、工具与恢复流程见 数据备份与恢复。

三、冗余架构模式

模式说明优点缺点示例
主备（Active-Standby）主节点服务，备节点待命简单，无写冲突备节点资源闲置；切换有中断MySQL 主从、Keepalived 双机
主主（Active-Active）两个节点同时读写资源利用率高写冲突、自增 ID 冲突，需要冲突解决MySQL 双主（通常仅单边写）
集群（Cluster）N 个对等或分片节点，多数派决策自动选主、可水平扩展实现复杂，需要奇数节点Redis Cluster、MGR、etcd、Kafka

生产中 MySQL "双主"通常配置为双主单写：两边互为主从，但同一时刻只有一边接受写入，本质仍是主备，只是切换后无需重建复制关系。

四、健康检查

1、主动检查与被动检查

方式原理优点缺点
主动检查定时探测 /health 端口或接口无流量时也能发现故障探测接口健康不代表业务健康
被动检查统计真实请求的失败 / 超时反映真实业务状态需要有流量；会牺牲少量请求

两者通常组合使用。Nginx 开源版只支持被动检查：

upstream backend {
    # 10s 内失败 3 次则摘除 10s，之后再试探
    server 10.0.0.1:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.3:8080 backup;          # 其余节点都不可用时才启用
}

location /api/ {
    proxy_pass http://backend;
    proxy_connect_timeout 1s;
    proxy_next_upstream error timeout http_502 http_503;
    proxy_next_upstream_tries 2;          # 最多换 2 个实例，避免重试放大
    # 非幂等请求（POST）默认不会转发到下一个实例，不要随意加 non_idempotent
}

主动健康检查需要 Nginx Plus 或第三方模块：

# nginx_upstream_check_module（Tengine 内置）
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    check interval=3000 rise=2 fall=3 timeout=1000 type=http;
    check_http_send "GET /actuator/health HTTP/1.0\r\n\r\n";
    check_http_expect_alive http_2xx;
}

2、Kubernetes 探针

三种探针回答三个不同的问题：startup 问"启动完了吗"，liveness 问"还活着吗，要不要重启"，readiness 问"现在能接流量吗"。 探针失败的后果不同，检查内容也必须不同。探针配置与 Pod 生命周期见 Kubernetes。

探针失败后果应检查什么不应检查什么
startupProbe超过阈值则重启；成功前不执行另外两个探针应用是否启动完成—
livenessProbe重启容器进程自身是否已无法恢复（死锁、事件循环卡死、关键内部组件损坏）任何外部依赖：DB 挂了重启也没用，反而让所有实例一起重启
readinessProbe从 Service Endpoints 摘除，不重启本实例能否接收流量（启动预热完成、未处于停机中、实例独占的资源可用）多个实例共享的依赖（DB、Redis、下游服务）

为什么 readiness 也不应包含 DB、Redis 等共享依赖：

  • 共享依赖一抖动，所有实例同时判定为未就绪，Service 后面没有任何可用 Endpoint，局部的依赖故障被放大成整个服务 100% 不可用
  • 摘流量解决不了共享依赖的问题：流量换到哪个实例，连的都是同一个 DB，摘除只对"这个实例自己坏了"有意义
  • 依赖故障应由调用路径处理：超时、熔断、降级让能服务的请求继续服务（例如读缓存兜底），见 超时、重试与隔离 与 降级

Spring Boot 官方文档对此也有同样的建议：检查外部状态要非常谨慎。Spring Boot 2.3+ 提供可用性状态端点，在 K8s 环境下自动启用：

management:
  endpoint:
    health:
      probes:
        enabled: true            # 暴露 /actuator/health/liveness 与 /readiness（Boot 4 起默认开启）
        add-additional-paths: true   # 同时在主端口暴露 /livez、/readyz
      group:
        readiness:
          include: readinessState    # 默认即只含可用性状态；不要加入 db、redis 等共享依赖
状态何时变化
LivenessState.CORRECT应用上下文刷新完成后
ReadinessState.ACCEPTING_TRAFFIC所有 ApplicationRunner / CommandLineRunner 执行完成后，预热逻辑放在 Runner 中即可推迟就绪，见 优雅上下线与变更
ReadinessState.REFUSING_TRAFFIC优雅停机开始时自动切换；也可以在代码中通过 AvailabilityChangeEvent.publish 主动切换

探针走主端口

如果 Actuator 使用独立的管理端口，业务端口的 Web 容器卡住时探针仍可能返回成功。开启 add-additional-paths 后在主端口探测 /livez、/readyz，探针结果才能反映真正对外服务的端口。

startupProbe:
  httpGet: { path: /livez, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30           # 最多给 150s 启动时间，启动慢的应用不必把 liveness 阈值放得很宽
livenessProbe:
  httpGet: { path: /livez, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3            # 宁可慢一点重启，也不要因为一次 Full GC 停顿误杀
readinessProbe:
  httpGet: { path: /readyz, port: 8080 }
  periodSeconds: 5
  failureThreshold: 3            # 连续 3 次失败则摘除流量

五、故障检测与自动切换

机制适用层原理切换时间
VIP 漂移（Keepalived）LVS / Nginx / 数据库主备VRRP 协议选出 Master 持有虚拟 IP，Master 失联后 Backup 接管 VIP秒级
注册中心摘除微服务实例心跳超时后实例被标记不健康或删除，客户端刷新列表秒级 ~ 分钟级
哨兵选主Redis 主从多个 Sentinel 投票判定客观下线，选出新主秒级（取决于 down-after-milliseconds）
共识选主etcd / MGR / Kafka KRaftRaft 等共识算法多数派选举 Leader秒级

1、Keepalived VIP

vrrp_script chk_nginx {
    script "/etc/keepalived/check_nginx.sh"   # Nginx 进程不存在时返回非 0
    interval 2
    weight -20                                # 检查失败则降低优先级，触发切换
    fall 3
    rise 2
}

vrrp_instance VI_1 {
    state BACKUP              # 两台都配 BACKUP + nopreempt，避免主恢复后抢回 VIP 造成二次抖动
    nopreempt
    interface eth0
    virtual_router_id 51
    priority 100              # 另一台配 90
    advert_int 1
    virtual_ipaddress {
        10.0.0.100/24
    }
    track_script {
        chk_nginx
    }
}

2、注册中心摘除的时效

注册中心摘除机制最坏感知时间
Nacos 2.x 临时实例gRPC 长连接断开即摘除；进程假死时依赖连接探活秒级
Nacos 1.x 临时实例5s 心跳，15s 标记不健康，30s 删除15 ~ 30s + 客户端刷新
Eureka30s 续约，90s 租约过期；另有服务端 / 客户端多级缓存可达 2 ~ 3 分钟

注册中心总有感知延迟，调用方必须配合超时 + 重试其他实例 + 熔断，才能覆盖这段时间窗口，见 超时、重试与隔离。主动下线应先从注册中心注销再停进程，见 优雅上下线与变更。

3、选主

自动选主的关键是多数派（Quorum）：N 个节点至少 ⌊N/2⌋ + 1 个同意才能产生新主，所以集群取奇数节点（3 节点容忍 1 个故障，5 节点容忍 2 个）。Raft 的选举与任期机制见 分布式理论。

六、脑裂与 fencing

脑裂（Split-Brain）：网络分区导致两侧都认为对方故障，同时存在两个"主"并各自接受写入，恢复后数据冲突甚至无法合并。

场景表现
Keepalived 心跳线中断两台都持有 VIP，ARP 表来回跳
Redis Sentinel 分区旧主在少数派一侧继续接受写入，恢复后被降级为从，期间写入丢失
数据库主备误切换旧主未真正宕机，应用仍有连接写入旧主
防护手段原理示例
多数派仲裁只有拿到多数票的一方可以成为主Raft、Sentinel quorum、MGR
Fencing Token每次选主递增任期号，存储层拒绝旧任期的写入Raft term、ZooKeeper zxid、分布式锁的递增 token
STONITH"爆头"：切换前强制隔离旧主（断电、摘网卡、撤销权限）Pacemaker、云厂商 API 关停实例
旧主自我降级旧主无法与足够多的副本通信时拒绝写入Redis min-replicas-to-write
第三方仲裁引入仲裁节点 / 仲裁机房判断谁存活两地三中心的仲裁点、Keepalived 检测网关连通性
# redis.conf：从库少于 1 个或延迟超过 10s 时，主库拒绝写入，限制分区期间的数据丢失
min-replicas-to-write 1
min-replicas-max-lag 10

七、数据层高可用

方案说明切换方式数据一致性
主从复制 + 半同步主库写，从库读；至少一个从库收到 binlog 才返回需配合 MHA / Orchestrator半同步下基本不丢，退化为异步时可能丢
MHA监控主库，故障时从最新从库补齐差异 binlog 并提升自动，30s 左右尽力补齐；项目已多年未维护
Orchestrator识别复制拓扑，自动提升并重建拓扑，自身基于 Raft 高可用自动，秒级依赖复制模式
MGR / InnoDB Cluster基于 Paxos 的组复制，单主模式自动选主自动，秒级；需多数派存活强一致（多数派确认）
Redis Sentinel哨兵监控主从，客观下线后选新主并通知客户端自动，秒级异步复制，切换可能丢少量写
Redis Cluster16384 槽分片，每分片主从，节点间 Gossip 判定故障自动，秒级同上
分片 + 多副本数据水平分片，每个分片多副本容错依赖具体中间件依赖具体中间件
多活数据同步双向复制，就近写入，依赖幂等与冲突解决切流最终一致，见 多活与容灾

应用侧同样要配合切换：

  • 连接串不写死主库 IP：使用 VIP、DNS 域名、中间件代理（ProxySQL / MySQL Router）或 Sentinel 客户端
  • 连接池能感知切换：设置合理的 maxLifetime、连接校验，避免切换后长时间持有指向旧主的连接
  • 读写分离注意复制延迟：写后立即读的场景强制走主库

复制原理与延迟排查见 MySQL 主从复制，Sentinel 与 Cluster 的配置见 Redis 集群。

八、依赖治理

冗余解决"自己的单点"，依赖治理解决"别人的故障"。 一个服务的可用率不可能高于它所有强依赖可用率的乘积（串联公式见 可用性度量），所以要做的是：减少强依赖、让弱依赖真正"弱"、为每个依赖准备好出问题时的动作。

1、强弱依赖梳理

类型判定标准示例（下单链路）失败时的处理
强依赖失败则核心功能无法完成，且没有可接受的替代结果库存扣减、订单写库、支付保证依赖自身高可用；快速失败并给出明确提示
弱依赖失败时核心功能仍可完成，只损失体验或附加功能优惠推荐、积分、评价、营销埋点超时短、可熔断、可降级，或改为异步

梳理方法：

  1. 从链路追踪拓扑出发，列出每个核心接口的全部下游，而不是凭印象列举，见 链路追踪
  2. 逐个标注强弱，由业务方确认"这个依赖挂了，功能还能不能用"
  3. 用故障注入验证标注：对标注为弱依赖的下游注入延迟与异常，核心接口成功率不应下降，见 混沌工程

最常见的问题：弱依赖被写成了强依赖

同步调用、没有超时或超时过长、异常没有捕获直接抛出、结果被当成必填字段使用，都会让一个"只是展示积分"的依赖拖垮下单。梳理后要逐一检查代码路径，而不只是在文档上标注。

2、依赖降级预案

每个依赖都应有一份事先写好、演练过的预案，故障时照着执行，而不是临场讨论：

预案项内容示例（推荐服务）
超时与重试读取超时、是否重试、重试次数200ms，不重试
熔断阈值触发条件与恢复窗口慢调用比例 50%，10s 后半开探测
降级方式默认值、缓存旧数据、隐藏模块、排队返回热门商品静态列表
开关手动降级开关的位置与负责人配置中心 reco.degrade=true，负责人 A
恢复条件何时关闭降级、如何确认恢复下游成功率恢复 99.9% 持续 10 分钟

超时与重试的取值见 超时、重试与隔离，降级的实现方式见 降级。

3、非核心依赖异步化

不需要在请求内拿到结果的调用，都应移出同步链路。 下单成功后发积分、发通知、写行为日志，改为发布事件由消费方异步处理，下游故障只会造成消息积压，不再影响下单成功率。

  • 事件发布要可靠：订单写库与发消息的一致性可用本地消息表 / Outbox 保证
  • 消费方必须幂等，消息可能重复投递
  • 异步化的模式与削峰设计见 异步与削峰

小结

  • 沿请求链路逐层找单点，应用无状态化是冗余的前提；备份要做恢复演练
  • 健康检查主动与被动结合；liveness 只查进程自身，readiness 只查本实例能否接流量，二者都不应包含 DB、Redis 等共享依赖
  • 自动切换依赖多数派，必须配合 fencing 等手段防脑裂；注册中心有感知延迟，调用方要用超时、重试其他实例与熔断兜底
  • 依赖治理：梳理强弱依赖并用故障注入验证，为每个依赖写好预案，非核心依赖异步化
