多活与容灾

本篇目标：理解 RPO / RTO 与容灾等级，掌握同城双活、两地三中心、异地多活（单元化）的架构差异、数据同步难点与切流步骤，并能按业务规模选型。

前置阅读：优雅上下线与变更

单机房内的冗余（见 冗余与故障转移）只能防实例级、机架级故障。机房断电、光缆被挖断、整个云可用区故障时，需要跨机房甚至跨地域的容灾能力。越往上走，难点越不在应用层，而在数据：物理距离带来的延迟无法消除，跨地域强一致与低延迟不可兼得（见 CAP 理论）。

一、容灾指标：RPO 与 RTO

RPO 衡量丢多少数据，由复制方式决定；RTO 衡量停多久，由备用环境的状态和切换自动化程度决定。

指标全称含义决定因素
RPORecovery Point Objective故障后最多丢失多长时间的数据数据复制方式（同步 / 半同步 / 异步 / 定期备份）
RTORecovery Time Objective故障后多长时间恢复服务备用环境状态（冷 / 温 / 热）、切换自动化程度
容灾级别架构RPORTO
数据级异地定期备份小时 ~ 天天级
应用级（冷 / 温备）异地部署应用，数据异步复制秒 ~ 分钟小时级
业务级（热备）备用机房实时同步，可快速切换秒级分钟级
多活多机房同时服务接近 0（单元内）秒 ~ 分钟（切流）

国内金融、政务系统的容灾级别通常按 GB/T 20988《信息系统灾难恢复规范》划分，核心系统一般要求达到较高等级，并定期做真实切换演练。数据级容灾的备份策略与恢复演练见 数据备份与恢复。

二、同城双活

同城双活通常是"应用双活、数据主备"，能防单机房故障，防不了城市级灾难。

同一城市两个机房（或云上两个可用区），距离通常在几十公里内，RTT 约 1 ~ 2ms，可以跨机房同步调用和同步复制。

层次做法
接入层两机房各自有 SLB，由带健康检查的 GSLB（智能 DNS）按权重分流
应用层两机房都部署全量无状态服务，同机房优先调用（注册中心按机房 / zone 路由）
缓存每机房独立缓存集群，或跨机房主从
数据库通常仍是单主：主库在机房 A，机房 B 为半同步从库；B 的写请求跨机房写 A
切换机房 A 故障时，B 从库提升为主，GSLB 摘除 A 的入口

准确地说，大多数"同城双活"是应用双活、数据主备。它投入相对可控，能防单机房故障，但防不了城市级灾难（地震、大范围断电）。MySQL 主从复制与半同步的细节见 MySQL 主从复制。

三、两地三中心

同城双中心 + 异地灾备中心：同城两中心按上一节做双活或主备，另在数百公里外建一个灾备中心，通过异步复制接收数据。

中心角色数据复制平时状态
生产中心主写—承接流量
同城灾备同城热备 / 双活同步或半同步承接部分流量或热备
异地灾备城市级灾难兜底异步（RPO 秒 ~ 分钟）温备，通常不承接流量

问题：异地中心长期不承接流量，真要切换时往往不敢切——配置漂移、容量不足、依赖缺失都要在切换那一刻才暴露。这正是异地多活要解决的问题。

四、异地多活

异地多活的前提是一次请求的读写都在本地域完成，这要求业务做单元化改造。

多个地域同时对外提供读写服务。以北京—上海为例，RTT 约 25 ~ 30ms，一次用户请求若产生十几次跨地域 RPC 或同步写，延迟不可接受。因此异地多活的前提是：一次请求的读写都在本地域完成，这需要单元化。

挑战原因解法
跨地域延迟光速限制，无法优化单元内闭环，禁止跨单元同步调用
数据写冲突两地同时修改同一数据按用户分片，同一数据只在一个单元写
全局数据库存、商家等无法按用户拆分中心单元集中写，各单元读副本
数据一致性跨地域只能异步复制接受最终一致；切流时先禁写再追平
切换风险路由、数据、容量任一环节出错常态化演练，逐步切流

五、单元化

单元（Cell / Unit）：一个能完成全部业务闭环的自包含部署集合，包含接入、应用、缓存、消息和属于本单元的数据分片。

1、路由维度

选择一个贯穿业务的路由键，所有请求和数据都按它划分到单元：

业务常用路由键说明
电商交易买家 userId订单、购物车、支付单都归属买家
外卖 / 出行城市 / 区域天然地理隔离
SaaS租户 ID大租户可独占单元

路由通常是两级映射：userId → 分片号（如 userId % 100）→ 单元，第二级映射存放在配置中心，切流只需修改分片到单元的映射：

# 配置中心下发的单元路由表
unit-routing:
  shard-count: 100
  units:
    - name: unit-sh
      shards: "0-49"
      gateway: https://sh.api.example.com
    - name: unit-bj
      shards: "50-99"
      gateway: https://bj.api.example.com
// 网关过滤器：计算归属单元，误入的请求转发到正确单元（纠错兜底）
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    String userId = exchange.getRequest().getHeaders().getFirst("X-User-Id");
    if (userId == null) {
        return chain.filter(exchange);                    // 未登录流量按就近处理
    }
    int shard = (int) (Long.parseLong(userId) % routing.getShardCount());
    Unit target = routing.unitOf(shard);
    if (!target.getName().equals(localUnit)) {
        return forwardTo(exchange, target.getGateway());  // 跨单元转发，同时打点监控
    }
    return chain.filter(exchange);
}

2、数据分类

数据类型示例写入位置读取位置
单元型订单、购物车、用户资产归属单元归属单元
全局型库存、商家、商品主数据中心单元各单元只读副本（容忍秒级延迟）
共享只读类目、地区码、配置后台统一维护各单元本地

设计要点：

  • 单元内闭环：单元型数据的读写、服务调用都不出单元；跨单元调用只允许出现在少数异步、非核心场景
  • 全局 ID 带单元信息或全局唯一：避免两地生成相同主键，见 分布式 ID 生成
  • 强一致场景走中心：如扣减库存，由中心单元处理或在各单元预分配库存额度
  • 未登录流量：按就近路由，登录后再按 userId 落到归属单元

六、数据同步

单元化从源头减少写冲突，但复制回环、主键冲突、复制延迟仍要由同步组件和切流流程处理。

单元之间仍需同步数据，用于容灾（对端保留备份分片）和全局数据下发。

问题说明处理方式
复制回环A 写入同步到 B，B 的 binlog 又同步回 A同步写入时打来源标记（事务标记表 / GTID 来源），同步组件过滤
写冲突两地同时改同一行单元化从源头避免；兜底按 update_time / 版本号"后写胜"并告警
主键冲突两地自增 ID 重复分布式 ID；或自增步长错开（auto_increment_increment / offset）
复制延迟跨地域异步复制有秒级延迟监控延迟；切流前必须追平
DDL 同步表结构变更需两地一致统一变更平台，先兼容再切换
工具说明
Canal阿里开源，伪装为 MySQL 从库订阅 binlog，是多数同步方案的底座
Otter基于 Canal 的跨机房数据同步系统，支持双向同步与回环控制（社区已不活跃）
DRC 类系统数据复制中心，阿里、携程等公司内部方案，云上对应阿里云 DTS 双向同步等产品
X-Pipe携程开源的 Redis 跨机房复制方案
MirrorMaker 2Kafka 官方跨集群复制

七、流量调度

跨地域调度靠 GSLB 与 HTTPDNS 做粗粒度分流，单元化的精确路由在接入网关完成。 接入层各层的职责见 接入层架构。

层次手段切换时效注意事项
GSLB（智能 DNS）按地域、运营商、健康状态返回不同入口 IP受 TTL 与客户端缓存影响，分钟级TTL 调小（如 60s），但部分运营商会忽略 TTL；普通 DNS 轮询没有健康检查，不能用于故障切换
HTTPDNSApp 直接向调度服务查询 IP秒级仅适用于自有客户端
接入网关按路由表把请求转发到归属单元秒级（推送路由表）单元化的核心调度点
服务调用注册中心按单元 / 机房隔离秒级防止单元间误调用

八、切换与演练

计划内切流靠"先禁写、再追平、后切路由"做到数据零丢失；真实故障时只能接受少量差异并事后对账。

标准切流步骤（以把分片 0 ~ 9 从上海切到北京为例）：

步骤操作目的
1确认北京单元容量余量（压测数据 + 当前水位）避免切过去被压垮
2上海单元对分片 0 ~ 9 禁写防止切换过程中两边同时写
3等待上海 → 北京数据同步延迟归零保证数据追平，RPO = 0
4修改路由表，推送到所有网关流量切到北京
5北京单元对分片 0 ~ 9 开放写恢复服务
6验证核心指标，观察跨单元转发量确认切换成功

禁写窗口通常为秒级到分钟级，是计划内切换可以做到"数据零丢失"的关键。真实故障时源单元已不可用，无法追平，只能接受异步复制带来的少量数据差异，事后通过对账修复。

演练要求：

  • 常态化：按月或按季度做真实切流，而不是只在文档里有预案
  • 从小到大：先切 1% 分片，再逐步扩大到整个单元
  • 有观测、可回切：切换全程盯 SLO 指标，异常立即回切
  • 与 混沌工程 结合，定期模拟机房级故障

九、方案选型

先把单机房内的高可用做扎实，再考虑跨机房。

方案防御故障范围RPO / RTO改造成本资源成本适用规模
单机房多副本实例、机架0 / 秒级低1x大多数中小系统
同城双活（数据主备）单机房≈ 0 / 分钟级中约 2x中大型业务、核心交易
两地三中心城市级灾难秒 ~ 分钟 / 小时级中约 3x金融、政务等强监管行业
异地多活（单元化）地域级故障单元内 ≈ 0 / 分钟级高（业务、数据、中间件全面改造）2x ~ 3x超大规模互联网业务

多活是组织级工程，需要业务改造、中间件支持、运维平台和演练机制同时到位；没有演练的多活只是昂贵的冷备。

小结

  • RPO 看数据复制方式，RTO 看备用环境状态与切换自动化程度，二者决定容灾等级
  • 同城双活多为应用双活、数据主备；两地三中心的异地中心长期不承接流量，真要切时往往不敢切
  • 异地多活靠单元化：选好路由键，单元型数据单元内闭环，全局数据中心写、各单元读副本
  • 数据同步要处理复制回环、写冲突、主键冲突和延迟；计划内切流先禁写、再追平、后切路由
  • 跨地域调度用带健康检查的 GSLB / HTTPDNS，精确路由在网关；没有常态化演练的多活只是昂贵的冷备
