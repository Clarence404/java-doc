2026/9/29大约 8 分钟

可用性度量

本篇目标：用 SLI / SLO / 错误预算把"多可用才够"变成可计算、可告警、可约束发布的数字，并会估算串并联系统的可用率。

参考链接：Google SRE Book - Service Level Objectives · SRE Workbook - Alerting on SLOs

相关：指标监控 · 告警体系

高可用首先是一个可度量的目标。没有度量，"系统很稳定"只是感觉；有了 SLO 和错误预算，稳定性投入与迭代速度之间才有可量化的取舍依据。

一、几个 9 与停机时间

可用率 = 可用时间 / 总时间（或成功请求数 / 总请求数）。下表按年 365 天、月 30 天计算：

可用率俗称年停机月停机周停机
99%2 个 9≈ 3.65 天≈ 7.2 小时≈ 1.68 小时
99.9%3 个 9≈ 8.76 小时≈ 43.2 分钟≈ 10.1 分钟
99.95%3 个 9 半≈ 4.38 小时≈ 21.6 分钟≈ 5 分钟
99.99%4 个 9≈ 52.6 分钟≈ 4.32 分钟≈ 1 分钟
99.999%5 个 9≈ 5.26 分钟≈ 25.9 秒≈ 6 秒
  • 互联网核心业务一般以 99.95% ~ 99.99% 为目标，金融、通信核心系统追求 5 个 9
  • 每多一个 9，成本通常是数量级上升：4 个 9 意味着单次故障必须在分钟级自动恢复，人工介入基本来不及，必须依赖自动故障转移
  • 目标不是越高越好：用户侧网络、终端本身就达不到 5 个 9，过高的目标只会浪费投入

二、SLA / SLO / SLI

概念全称含义面向示例
SLIService Level Indicator可量化的服务质量指标工程团队成功请求占比、P99 延迟、数据新鲜度
SLOService Level Objective对 SLI 设定的内部目标值工程 + 产品30 天滚动窗口内成功率 ≥ 99.9%
SLAService Level Agreement对外承诺，违约有赔偿客户 / 商务月可用率 < 99.9% 返还 10% 服务费

三者关系：SLI 是度量，SLO 是目标，SLA 是合同。SLO 必须比 SLA 更严格，给团队留出反应余量，例如 SLA 99.9%、SLO 99.95%。

1、常用 SLI

服务类型SLI计算方式
在线 API可用性非 5xx 请求数 / 总请求数（4xx 属调用方错误，一般不计入失败）
在线 API延迟延迟 < 300ms 的请求数 / 总请求数
消息消费新鲜度消费延迟 < 60s 的消息占比
批处理完成率按时完成的任务数 / 总任务数
存储持久性可成功读回的数据占比

延迟 SLI 用"达标请求占比"而不是"平均值"：平均值会掩盖长尾，而"P99 < 300ms"与"99% 请求 < 300ms"等价，且可直接参与错误预算计算。

2、SLO 制定原则

  • 从用户视角选指标：在网关 / 负载均衡入口统计，而不是只看单个实例的 CPU
  • 按关键链路分别定义：下单、支付的 SLO 与商品评论不同
  • 使用滚动窗口：常用 28 天或 30 天，避免月初"重置"后放松
  • 先按历史数据定，再逐步收紧：一开始定得过高会导致错误预算长期为负，失去约束意义

三、错误预算

错误预算 = 1 - SLO，表示在一个周期内允许"不可用"的额度。

SLO（30 天）时间维度预算请求维度预算（月 1 亿请求）
99.9%43.2 分钟10 万次失败
99.95%21.6 分钟5 万次失败
99.99%4.32 分钟1 万次失败

1、错误预算如何约束发布

预算状态策略
剩余 > 50%正常迭代，可以做有风险的发布与实验
剩余 10% ~ 50%放慢节奏，发布必须灰度，加强变更评审
剩余 < 10%冻结功能发布，只允许稳定性修复与紧急安全补丁
已耗尽全面冻结，复盘并投入可靠性改进，直到窗口内预算恢复

错误预算把"开发要快、运维要稳"的矛盾变成共同规则：预算充足时鼓励创新，预算耗尽时稳定性优先。这一策略需要事先由研发、测试、运维、产品共同签字认可，否则执行不下去。

2、燃烧速率告警

燃烧速率（Burn Rate）= 实际错误率 / (1 - SLO)。燃烧速率为 1 表示刚好在窗口结束时用完预算。按阈值告警比按"错误率 > x%"更能反映对 SLO 的真实威胁：

告警级别长窗口短窗口燃烧速率消耗 30 天预算
立即呼叫（Page）1 小时5 分钟14.42%
立即呼叫（Page）6 小时30 分钟65%
工单（Ticket）3 天6 小时110%

长短双窗口同时满足才触发：长窗口保证显著性，短窗口保证故障恢复后告警能及时解除。

# Prometheus 规则：SLO 99.9%，1h + 5m 双窗口，燃烧速率 14.4
groups:
  - name: order-api-slo
    rules:
      - record: slo:error_ratio:rate5m
        expr: |
          sum(rate(http_server_requests_seconds_count{application="order-api",status=~"5.."}[5m]))
          / sum(rate(http_server_requests_seconds_count{application="order-api"}[5m]))
      - record: slo:error_ratio:rate1h
        expr: |
          sum(rate(http_server_requests_seconds_count{application="order-api",status=~"5.."}[1h]))
          / sum(rate(http_server_requests_seconds_count{application="order-api"}[1h]))
      - alert: OrderApiErrorBudgetFastBurn
        expr: |
          slo:error_ratio:rate1h > (14.4 * 0.001)
          and slo:error_ratio:rate5m > (14.4 * 0.001)
        labels:
          severity: page
        annotations:
          summary: "order-api 错误预算快速燃烧（1h 内将消耗 2% 月度预算）"

四、MTBF / MTTR / MTTD

指标全称含义改进手段
MTBFMean Time Between Failures平均无故障时间代码质量、容量规划、变更管控、混沌演练
MTTDMean Time To Detect平均发现时间基于 SLO 的告警、拨测、链路追踪
MTTRMean Time To Recovery平均恢复时间（含发现、定位、止血）自动故障转移、一键回滚、降级开关、预案

可用率 = MTBF / (MTBF + MTTR)。例如平均 30 天（720 小时）出一次故障、每次恢复 1 小时，可用率 = 720 / 721 ≈ 99.86%。

提升可用性有两条路：让故障更少（提高 MTBF），或让恢复更快（降低 MTTR）。工程上 降低 MTTR 往往更划算——故障无法杜绝，但"先止血后定位"（切流、回滚、降级）能把分钟级恢复变为常态。止血手段清单、On-call 与复盘等降低 MTTR 的做法见 故障应急与复盘。

五、可用性计算

1、串联系统

请求依次经过多个组件，任一组件故障则整体故障：A = A₁ × A₂ × … × Aₙ

链路各组件可用率整体可用率年停机
网关 → 订单 → 库存 → DB99.9% × 99.9% × 99.9% × 99.95%≈ 99.65%≈ 30.6 小时

结论：串联的依赖越多，整体可用率越低，且低于其中最差的组件。这也是减少同步强依赖、非核心依赖异步化或可降级的根本原因。

2、并联系统

多个相同组件互为冗余，全部故障才整体故障：A = 1 - (1 - A₁)ⁿ

单实例可用率实例数整体可用率
99%199%
99%299.99%
99%399.9999%
99.9%299.9999%

3、混合系统

典型部署：负载均衡（99.99%）→ 两个应用实例并联（各 99.9%）→ 数据库主库（99.95%）：

  • 应用层并联：1 - (0.001)² = 99.9999%
  • 整体串联：0.9999 × 0.999999 × 0.9995 ≈ 99.94%

瓶颈立刻显现：再增加应用实例几乎没有收益，真正拉低可用率的是单点的数据库，应优先做数据层高可用，见 冗余与故障转移。

并联公式的前提

并联公式假设各副本故障相互独立。实际中同机架断电、同一版本 Bug、共享的配置中心 / DNS 故障都会让副本同时失效，所以冗余要跨故障域（机架、可用区、机房）部署，发布要灰度而不是全量同时生效。

六、如何度量

度量方式说明适用
服务端指标基于 Micrometer / Prometheus 统计成功率、延迟分布SLI 主数据源
入口日志网关 / Nginx access log 聚合，覆盖应用未收到的请求补充负载均衡层失败
拨测（Synthetic）多地定时探测关键接口发现"全挂了却没有指标"的场景
真实用户监控（RUM）客户端上报端到端体验

Spring Boot 开启直方图与 SLO 边界，供延迟 SLI 计算：

management:
  endpoints:
    web:
      exposure:
        include: health,prometheus
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
      slo:
        http.server.requests: 100ms,300ms,1s   # 生成 le="0.3" 等桶
# 可用性 SLI（5 分钟）
sum(rate(http_server_requests_seconds_count{status!~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m]))

# 延迟 SLI：300ms 内完成的请求占比
sum(rate(http_server_requests_seconds_bucket{le="0.3"}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m]))

小结

  • SLI 是度量、SLO 是目标、SLA 是合同，SLO 要比 SLA 严格；延迟 SLI 用"达标请求占比"而不是平均值
  • 错误预算 = 1 - SLO，按剩余预算决定发布节奏，需要各方事先认可
  • 用多窗口燃烧速率告警代替固定错误率阈值
  • 可用率 = MTBF / (MTBF + MTTR)，降低 MTTR 往往比提高 MTBF 更划算
  • 串联拉低可用率、并联提升可用率，但并联要求副本跨故障域、故障相互独立
