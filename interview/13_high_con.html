高并发面试题解答

高并发面试题解答

题目清单见 高并发面试题，细节见 高并发模块；三高另外两页：高性能 · 高可用。

版本基线：JDK 21 / 25 LTS、Spring Boot 4.x，与旧版本不同处单独说明。

一、总体设计

Q1：如何设计一个高并发系统？从哪些维度入手？

一句话：先算清楚流量有多大，再按「能扩、少打、慢做、分散」四个思路逐层设计，最后用限流降级兜底、用压测和水位监控验证。

  • 估算：DAU → 平均 QPS → 峰值 QPS → 存储量，峰值决定要准备多少机器
  • 能扩：每一层都能靠加机器扩容（服务无状态、负载均衡、分库分表）
  • 少打：请求尽量在前面就被挡住，不落到最慢的数据库（CDN、静态化、多级缓存）
  • 慢做：不需要马上完成的工作扔进 MQ 异步处理；分散：避免流量集中到一台机器、一个 key、一行数据
  • 扛不住时的限流、熔断、降级属于高可用，见 高可用面试题解答

→ 详见 高并发总览

Q2：高并发、高性能、高可用三者的区别与联系？

一句话：同一个系统的三个角度：高性能看单个请求快不快，高并发看流量大时扛不扛得住，高可用看出故障时会不会停服。

对比关注点看什么指标
高性能单次请求更快、更省资源RT、P99、CPU
高并发流量大时扛得住峰值 QPS、水位
高可用出故障不停服可用率 SLA、恢复时间
  • 高性能是高并发的基础：单个请求从 100ms 降到 20ms，同样的线程能多扛 5 倍 QPS
  • 高可用是高并发的底线：流量超过容量时，靠限流降级保住核心功能，而不是整个系统一起崩
  • 很多手段一举多得：缓存既让请求变快，又替数据库分担流量

→ 详见 高并发总览

Q3：读多写少的场景如何设计？（CDN + 多级缓存 + 读写分离）

一句话：让读请求尽量在前面、便宜的层被挡住：浏览器 / CDN → Nginx → 本地缓存 → Redis → 数据库，挡不住的实时读再交给从库分担。

  • 命中率是相乘的：Redis 命中 95%，前面再加一层 80% 的本地缓存，数据库只剩 20% × 5% = 1% 的读
  • 按数据选层：静态文件走 CDN；所有人看到都一样的热点数据放本地缓存；每人不同的数据放 Redis
  • 余额、库存精确值这类要求准确的数据，最多缓存到 Redis
  • 页面静态化：详情页主体做成静态页，价格库存走单独接口
  • 读写分离只能扩读，不能扩写，还要处理主从延迟（见 Q23）

→ 详见 缓存架构设计、接入层架构、数据层扩展

Q4：写多的场景如何设计？（MQ 削峰 + 异步处理）

一句话：主流程只做必须马上完成的事，其余写操作放进 MQ，让下游按自己的能力慢慢消费；写入能力真到顶了，再靠合并写和分库分表扩容。

  • 同步改异步：发通知、记日志这类操作发消息就返回
  • 削峰填谷：高峰时先把请求存进 MQ，消费端按数据库能承受的速度写入
  • 合并写：点赞数、浏览数这类计数先在内存或 Redis 累加，定期批量写库
  • 扩展写能力：按业务拆库，再对大表水平分库分表（见 Q24）
  • 代价是数据不再立刻一致，要靠可靠投递、幂等消费和对账来保证最终一致（见 Q21）

→ 详见 异步与削峰

二、接入层

Q5：一个请求从 DNS 到应用服务要经过哪些层？每层解决什么问题？

一句话：一般是 DNS → CDN → 四层负载均衡 → 七层网关 → 应用集群。越靠前的层越便宜、吞吐越高，能在前面处理掉的流量就别往后放。

  • DNS / GSLB：按地区、运营商把用户导到最近的机房；生效慢（有缓存），只适合粗粒度调度
  • CDN：在离用户近的节点缓存静态内容，没命中才回源站
  • 四层负载均衡（LVS、云 SLB）：只看 IP 和端口转发连接，扛海量连接
  • 七层网关（Nginx、Spring Cloud Gateway）：看得懂 HTTP，做路由、HTTPS 解密、鉴权、限流
  • 每一层都要有多个实例，任何一层是单点，整个系统就是单点

→ 详见 接入层架构

Q6：四层负载均衡（LVS）和七层负载均衡（Nginx）有什么区别？为什么常组合使用？

一句话：四层负责「扛连接」，七层负责「懂业务」。所以常见做法是四层放在最前面做统一入口，后面挂多台七层网关。

对比四层（LVS / SLB）七层（Nginx / 网关）
看到什么只有 IP + 端口完整 HTTP 请求
能做什么转发连接按 URL 路由、鉴权、限流、灰度
性能极高（在内核里转发）较高，靠多实例扩展
健康检查端口通不通接口返回是否正常
  • LVS 的 DR 模式性能最好：响应不经过 LVS，直接回给客户端
  • 七层网关只做通用逻辑（鉴权、限流），不写业务代码，且要无状态方便扩容

→ 详见 接入层架构

Q7：CDN 的原理是什么？动态内容能否走 CDN？

一句话：CDN 把用户导到最近的边缘节点，节点缓存公开的静态内容，没命中或过期才回源站取。下单、支付、个人数据这类动态请求不缓存，可以绕过 CDN 或只用它加速网络链路。

  • 静态资源用独立域名走 CDN，文件名带内容哈希，就可以设很长的缓存时间
  • 静态化页面也能放 CDN，但缓存时间要短，内容变了主动刷新
  • 回源保护：大量节点同时回源会压垮源站，要开回源合并、大促前提前预热
  • 刷新通常分钟级才生效，要求准确的数据不要写进静态内容

→ 详见 接入层架构

Q8：什么是页面静态化？适合什么场景？

一句话：把「每次请求都查库拼页面」改成「数据变了生成一次 HTML，之后直接返回文件」，读流量交给 CDN 和 Nginx。适合读多写少、所有人看到都一样的页面。

  • 全量静态化：数据变更时用模板生成完整 HTML，适合文章、帮助中心、活动页
  • 页面片段化：主体静态，价格、库存、登录状态由前端单独调接口，适合商品详情、秒杀页
  • 边缘渲染：在 CDN 节点上拼装页面片段，适合大型电商、门户

常见坑：把价格、库存写死在静态页里（应该走异步接口单独获取）。

→ 详见 接入层架构

Q9：为什么要在接入层做 TLS 卸载？

一句话：HTTPS 握手很耗 CPU，放在最外层的 SLB / Nginx 统一处理，后端应用就不用再做加解密，证书也只在一处管理。

  • 会话复用：断线重连时跳过完整握手
  • 升级到 TLS 1.3：完整握手只需一次往返
  • 用 ECDSA 证书：签名计算比同等强度的 RSA 省 CPU
  • OCSP Stapling：服务端顺带返回证书状态，客户端不用再单独去查
  • 卸载后内网是明文；安全要求高时（零信任），服务之间改用双向 TLS（mTLS）

→ 详见 接入层架构

Q10：长连接网关如何支撑百万级连接？

一句话：长连接的压力不在 QPS，而在同时在线的连接数。做法是单独部署一个只管连接的网关（Netty 这类少量线程管大量连接的模型），业务交给后端服务。

  • 网关只负责连接、编解码、心跳，业务通过 RPC / MQ 交给后端
  • 用 Redis 记录「用户在哪个网关节点」，推消息时先查再投递
  • 负载均衡用四层，按连接数分配；负载均衡的空闲超时要大于客户端心跳间隔，否则连接被误断
  • 防重连风暴：网关重启时，客户端按「越来越长 + 随机」的间隔重连，避免同一秒全部涌入
  • 调大系统参数，如文件句柄上限 ulimit -n（见 Q39）

→ 详见 接入层架构、Netty 总览

三、水平扩展

Q11：垂直扩展和水平扩展的区别？各自适用什么场景？

一句话：垂直扩展是换更强的机器，几乎不用改代码，但有上限且是单点；水平扩展是加更多同样的机器，能一直加，但要求服务无状态。一般先垂直、后水平，但应用从第一天就该写成无状态。

对比垂直扩展水平扩展
改造成本几乎没有无状态化、负载均衡、数据分片
上限单机硬件上限接近线性，受数据库、锁等共享资源限制
成本高配机器越来越贵大致按台数线性增长
可用性单点多台天然互为备份
适用早期业务、数据库主库、应急应用层、缓存层、分片后的存储

→ 详见 水平扩展与无状态化

Q12：什么是无状态服务？应用中有哪些常见的"状态"需要外置？

一句话：无状态就是请求打到哪台机器结果都一样，机器可以随时加减。做法是把所有「存在本机」的东西搬到共享组件里。

  • Session：放 Redis（Spring Session），或改用 JWT 令牌
  • 上传、导出的文件：放对象存储（OSS / S3 / MinIO），不放本地磁盘
  • 本地计数、限流：改用 Redis 计数或分布式限流
  • 定时任务：用分布式调度（XXL-JOB）或分布式锁，避免多台机器重复执行
  • 自查：有没有用 static 集合存业务数据、有没有假设「下次请求还能读到本地文件」

→ 详见 水平扩展与无状态化

Q13：Session 在集群环境下如何共享？

一句话：推荐两种：Session 统一存 Redis（Spring Session），或者用 JWT 这种不在服务端存状态的令牌。粘性会话只是临时补丁。

方案问题
粘性会话（同一用户固定打到同一台）负载不均，机器下线会话就丢
Session 复制机器越多复制越重，只适合小集群
存 Redis多一次网络访问，Redis 要高可用
JWT无法主动让它失效（踢人、改密码），要加黑名单
  • Spring Boot 3 引入 spring-session-data-redis 就会自动用 Redis 存 Session

常见坑：往 Session 里放大对象（每次请求都要序列化后经网络传输）。

→ 详见 分布式会话、水平扩展与无状态化

Q14：K8s HPA 自动扩容有哪些局限？应用扩容后下游会出现什么问题？

一句话：HPA 按指标自动加减 Pod，但它有延迟、指标可能选错，而且只扩应用层；应用扩了，压力就转到数据库等下游，最常见的是数据库连接数超限。

  • 有延迟：拉镜像、JVM 启动、预热要 30 秒到几分钟，所以目标值要设低一点（如 CPU 60%），大促前手动提前扩
  • 就绪太早：JVM 还没预热就接流量会很慢，健康检查要等预热完再通过
  • 内存指标不适合 JVM：堆涨上去一般不还给系统，导致只扩不缩；计算型看 CPU，IO 型看 QPS，消费者看消息积压
  • 缩容抖动：设缩容稳定窗口（如 300 秒），配合优雅停机
  • 下游问题：数据库总连接数 = 实例数 × 每个实例的连接池大小，扩容后可能超过 max_connections，新实例一启动就报 Too many connections

→ 详见 水平扩展与无状态化、并发参数调优

四、缓存架构

Q15：多级缓存的架构是怎样的？各层的一致性如何取舍？

一句话：浏览器 / CDN → Nginx → 应用本地缓存 → Redis → 数据库。越靠前越快、扛得越多，但数据变了越难及时更新。所以按数据特点选层，每层都设过期时间兜底。

层级怎么更新可接受多久不一致放什么
CDN / 浏览器过期 + 主动刷新分钟到小时图片、JS、静态页
Nginx短过期（1～10 秒）秒级商品详情、活动页
本地缓存短过期 + 消息广播删除毫秒到秒级热点商品、配置
Redis改库后删缓存毫秒级业务数据
  • 余额、库存精确值、权限不进本地缓存和 CDN
  • 过期时间加随机值，避免同时失效；监控各层命中率，突然下降要告警

→ 详见 缓存架构设计、缓存一致性

Q16：缓存穿透、缓存击穿、缓存雪崩分别是什么？如何解决？

一句话：穿透是查不存在的数据，击穿是一个热点 key 过期，雪崩是一大批 key 同时过期或 Redis 挂了，三者都会让请求直接打到数据库。

问题现象解法
穿透查不存在的数据，每次都打到库参数校验；布隆过滤器提前拦；空值也缓存（短过期）
击穿热点 key 过期瞬间大量请求一起查库加锁只放一个请求去查库；逻辑过期 + 后台刷新
雪崩大量 key 同时过期或 Redis 宕机过期时间加随机值；多级缓存兜底；Redis 高可用；熔断降级

→ 详见 缓存架构设计、缓存面试题解答

Q17：如何做缓存预热？预热时如何避免压垮数据库？

一句话：在流量来之前把能预知的热点数据提前加载进缓存；预热本身要分批、限速，预热完再接流量。

  • 启动预热：应用启动时加载配置、字典、热门数据；写在 ApplicationRunner 里，K8s 就绪检查自然会等它跑完
  • 定时预热：按访问统计，把第二天的热门数据提前写进 Redis
  • 活动预热：大促、秒杀前把活动商品和库存推到 Redis 和本地缓存
  • 批量写入时过期时间加随机值，避免同一时刻一起过期变成雪崩
  • 突发热点没法预热，靠实时探测后放进本地缓存（见 Q28）

→ 详见 缓存架构设计

五、异步与削峰

Q18：MQ 如何实现削峰填谷？消费速率如何控制？

一句话：MQ 写入能力比数据库强得多，高峰流量先存进队列，消费端再按下游能承受的速度慢慢处理，用延迟换稳定。前提是业务能接受这点延迟。

  • 例：瞬时 10 万 QPS 持续 10 秒，数据库只能扛 5000 TPS；100 万条消息按 5000 TPS 消费约 200 秒处理完，数据库一直很安全
  • Kafka：调 max.poll.records，消费者数不超过分区数；RocketMQ：调消费线程数和批量大小；RabbitMQ：用 prefetch 限制未确认消息数
  • 也可以在消费代码里用 RateLimiter 限速；注意总速度 = 单实例速度 × 实例数

常见坑：消费逻辑不做幂等（MQ 只保证至少投递一次，消息可能重复）。

→ 详见 异步与削峰

Q19：消息积压了怎么处理？

一句话：先分清是消费变慢了（下游出问题）还是生产突然变多（正常高峰）。前者先修下游，盲目加消费者只会把下游压得更惨；后者再加消费能力。

  • 监控：Kafka 看消费延迟（lag），RocketMQ 看堆积量，持续增长就告警
  • 修下游：消费慢大多是数据库或下游接口变慢，先恢复它们
  • 加消费者：Kafka 消费者数不能超过分区数；不够就把消息转到分区更多的临时 Topic 再并行消费
  • 提效率：批量消费、批量写库
  • 止损：时效性强的旧消息过期就丢，处理了也没意义

→ 详见 异步与削峰、消息队列

Q20：流量整形和限流有什么区别？

一句话：都在控制流量速度，区别是超出的部分怎么办：整形让它排队等着，限流直接拒绝。

对比流量整形限流
目标把忽高忽低的流量变平稳保护系统不被压垮
超出部分排队、延后处理直接拒绝
常用手段漏桶、MQ 缓冲令牌桶、滑动窗口
典型场景下单、支付回调、数据同步接口防刷、网关总量保护
  • 常组合使用：网关先限流挡掉超出总容量的部分，放进来的再进 MQ 排队，消费端匀速写库

→ 详见 异步与削峰、限流与过载保护

Q21：异步化之后如何保证最终一致性？本地消息表的原理是什么？多实例下如何避免重复投递？

一句话：靠「消息一定发出去 + 消费重复了也没事 + 定期对账」三件事。本地消息表就是把业务数据和要发的消息写在同一个数据库事务里，要么都有、要么都没有，再由后台任务把消息发到 MQ。

  • 本地事务成功但消息没发：用本地消息表或 RocketMQ 事务消息
  • 消息重复：消费端做幂等（唯一键、状态机、去重表）
  • 消费失败：有限次重试，再进死信队列人工补偿；长时间不一致靠定时对账
  • 多实例发消息：用 SELECT … FOR UPDATE SKIP LOCKED 让每个实例锁不同的行（MySQL 8.0+），或用分布式锁只让一个实例发
  • 即便这样仍可能重复发（发成功了但事务回滚），所以消费端必须幂等

→ 详见 异步与削峰、分布式事务

六、数据层扩展

Q22：数据层扩展的演进顺序是什么？为什么不一上来就分库分表？

一句话：按改造成本从低到高：缓存 → 读写分离 → 冷热分离 → 按业务拆库 → 分库分表 → 换专用存储，前一步能解决就不走下一步。分库分表成本最高、最难回退。

  • 缓存、读写分离：解决读压力大
  • 冷热分离：数据多但大部分是历史数据，归档后主表就小了，很多系统靠这一步就能撑很久
  • 按业务拆库：不同业务抢同一个库的资源
  • 分库分表：单表太大、单库写入到顶；代价是查询必须带分片键、跨库查询和事务都变难、以后扩容要迁数据
  • 专用存储：搜索用 ES、分析用 ClickHouse 这类关系库不擅长的场景

→ 详见 数据层扩展

Q23：读写分离如何处理主从延迟？

一句话：MySQL 主从复制默认异步，从库一般落后毫秒级，大事务时能到秒级，刚写完就去从库读可能读到旧数据。按业务对一致性的要求选办法。

  • 强制读主库：支付后查余额、下单后查订单，用 Hint 指定走主库
  • 写后短时间读主库：用户写操作后几秒内（Redis 打个标记）的读都走主库
  • 缓存兜底：写库同时写缓存，读优先读缓存
  • 业务容忍：发帖、评论等，前端提示「处理中」
  • 等从库追上：读从库前用 GTID 等待对应的事务同步完成

常见坑：以为开了半同步复制就没延迟（它只降低丢数据风险，读延迟还在）。

→ 详见 数据层扩展

Q24：什么时候需要分库分表？分片键如何选择？

一句话：单表太大、单库写不动，并且缓存和归档都解决不了时才分。经验值是单表超过约 2000 万行或 50GB（要结合压测）。先按业务拆库，再拆仍然过大的表。

  • 覆盖核心查询：大部分查询都带分片键，否则要查所有分片
  • 分布均匀：避免大商家、大 V 的数据都落到一个分片
  • 不会变：分片键一改就要迁移数据
  • 关联表用同一个分片键：如订单和订单明细都按 user_id 分，才能在同一分片内 JOIN
  • 优先选 user_id、tenant_id 这类业务核心维度

→ 详见 数据层扩展、分库分表与中间件

Q25：哈希、范围、一致性哈希几种分片算法各有什么优缺点？

一句话：哈希分得匀但扩容要大搬家；范围扩容简单但新数据都挤在最后一个分片；一致性哈希扩容只搬一部分但实现复杂；映射表最灵活但多查一次。

算法优点缺点
哈希取模分布均匀分片数一变，几乎所有数据都要迁移
范围（ID 区间 / 按月）扩容简单，适合范围查询新数据集中在最新分片，形成写热点
一致性哈希扩容只迁移一部分数据实现复杂，要加虚拟节点才均匀
映射表最灵活，大租户可单独搬多一次查询，映射表本身要高可用
  • 分表后需要全局唯一、大致递增的 ID（雪花算法、号段）；用 UUID 做主键会让索引频繁分裂、写入变慢

→ 详见 数据层扩展、一致性哈希

Q26：分库分表后如何按非分片键查询？跨分片分页怎么做？

一句话：不带分片键的查询，靠把分片信息编进 ID、另建一份按其他字段分片的索引表、或同步到 ES 来解决；跨分片分页要禁止深分页，改成「按上次最后一条 ID 往后查」。

  • 基因法：把 user_id 的低几位编进 order_id，只拿订单号也能算出在哪个分片
  • 异构索引表：按 seller_id 再存一份（通过 Binlog / MQ 同步），用空间换查询
  • ES：复杂条件、运营后台的查询统一走 ES
  • 深分页：LIMIT 10000, 10 要每个分片都取 10010 行再合并，改成 WHERE id > ? ORDER BY id LIMIT 10
  • 跨分片聚合交给汇总表或 ClickHouse；跨分片事务尽量避免，否则用最终一致方案

→ 详见 数据层扩展

Q27：分库分表如何平滑扩容？

一句话：按「双写 → 迁移历史数据 → 校验 → 逐步切读 → 切写」一步步来，全程能回滚。更好的办法是一开始就分好足够多的逻辑表，扩容时整张表搬走，不用逐行重新算分片。

  • 双写：新旧库同时写，以旧库为准（应用双写或用 Canal 同步 Binlog）
  • 迁移：全量拷贝历史数据，新增数据靠双写追平
  • 校验：对比行数并抽查内容，修复差异
  • 切换：先按比例把读流量切到新库观察，再以新库为准切写，旧库保留一段时间方便回滚
  • 例：一开始就建 1024 张表分布在 8 个库，扩容只是把部分表整张搬到新库；也可以直接用 TiDB 这类分布式数据库

→ 详见 数据层扩展

七、热点问题

Q28：如何发现突发热点 key？集中式探测的原理是什么？

一句话：能预知的热点提前预热，突发热点靠实时探测。集中式探测（如京东 JD-hotkey）是各实例上报访问次数，由一个统计集群汇总判断，再把热点推给所有实例，通常 1 秒内全集群生效。

  • 流程：客户端每 500ms 批量上报 → 统计节点按滑动窗口计数（如 1 秒超过 1000 次就算热点）→ 推送给所有应用实例 → 实例把它放进本地缓存 → 热度下降后自动过期
  • 只在单机统计会漏判：全局 5 万 QPS 的热点分到 100 台机器，每台只有约 500 QPS
  • 事后排查可用 redis-cli --hotkeys（需要淘汰策略是 LFU 类）

常见坑：生产环境用 MONITOR 找热点（会严重拖慢 Redis）。

→ 详见 热点问题

Q29：Redis 热点 key 如何处理？（探测 + 本地缓存 + key 打散）

一句话：一个热点 key 只落在一个 Redis 分片上，会把这台机器的 CPU 或网卡打满，加机器也没用。首选探测到后放进本地缓存，其次把 key 复制多份分散到不同分片。

  • 本地缓存：每个实例在 JVM 里缓存几秒，代价是几秒的不一致
  • key 打散：复制成 key#0 ~ key#N，读时随机选一个；代价是写要写 N 份
  • 读从节点：客户端配置读从节点（如 Lettuce ReadFrom.REPLICA_PREFERRED），可能读到稍旧的数据
  • 千人一面的数据还可以前移到 Nginx / CDN；最后一道防线是按参数值限流（Sentinel 热点参数限流）

常见坑：打散时写成 {item:1}#0（花括号是 hash tag，所有副本仍在同一个分片），可用 CLUSTER KEYSLOT 检查。

→ 详见 热点问题

Q30：秒杀场景下同一行库存的高并发扣减如何优化？

一句话：MySQL 更新同一行要排队拿锁，单行每秒只能扛几百次。主流做法是 Redis 里用 Lua 原子预扣库存，成功后发 MQ 异步写库，再定期对账；并发更高时再把库存分桶，入口先削峰。

  • 并发不高：直接 UPDATE ... SET stock = stock - 1 WHERE item_id = ? AND stock > 0
  • Redis 预扣：一段 Lua 脚本原子完成「是否买过 + 库存够不够 + 扣减」，消费端幂等写库，超时未支付要把库存加回去
  • 分桶：库存拆到多个 key 或多行，分散压力（见 Q31）
  • 前置削峰：发令牌、排队、网关限流，只放进和库存差不多数量的请求

常见坑：先查库存再扣减（两步之间会被别人抢，导致超卖；必须是一步完成的条件扣减）。

→ 详见 热点问题、秒杀

Q31：什么是分桶库存？有什么代价？

一句话：一个 Redis key 只能在一个分片上处理，分桶就是把总库存拆成 N 份放到不同分片（或数据库的 N 行），一个大热点变成 N 个小热点。

  • 例：库存 10000 拆成 10 个 key：stock:1001:0 ~ stock:1001:9，每个 1000
  • 扣减：按 userId % 10 选桶，桶里没货就试下一个
  • 售罄：记录已经卖空的桶数，全部卖空才算售罄
  • 数据库侧同理：一行库存拆成 N 行，分散行锁
  • 代价：可能出现「别的桶还有货、这个桶没了」，要遍历或定期重新平衡；查总库存和对账变复杂

→ 详见 热点问题

Q32：什么是 Single Flight？和批量请求合并有什么区别？

一句话：Single Flight 是同一个 key 的并发请求只让一个真正去查，其他的等着共用结果，常用来防缓存击穿；请求合并是把一小段时间内不同 key 的请求攒成一次批量查询，目的是减少调用次数。

对比Single Flight请求合并
合并什么相同 key 的并发请求不同 key 的请求
目的防击穿、避免重复计算减少下游调用次数
额外等待没有要等攒批的时间窗口
代价那一次失败，所有等待者一起失败流量低时反而变慢
  • 实现：ConcurrentHashMap<K, CompletableFuture<V>> 用 putIfAbsent 抢执行权，执行完 remove(key, future)

→ 详见 热点问题、异步与批量

八、并发参数调优

Q33：线程数如何设置？CPU 密集型和 IO 密集型有何不同？

一句话：公式只能给个起点，最终以压测时性能开始下降的那个点为准，上线后再用动态线程池微调。

  • CPU 密集型（主要在计算）：CPU 核数 + 1
  • IO 密集型（主要在等数据库、等接口）：核数 × (1 + 等待时间 / 计算时间)，等待是计算的 9 倍时，8 核约 80 个线程
  • 按流量反推：线程数 ≈ 目标 QPS × 单个请求耗时，如 1000 QPS × 50ms ≈ 50
  • 等待和计算的比例很难测准，而且往往数据库、下游接口先扛不住

常见坑：线程开得越多越好（线程切换本身耗 CPU，反而更慢）。

→ 详见 并发参数调优、线程池

Q34：线程池核心线程满了之后，是先扩到最大线程数还是先进队列？Tomcat 线程池有何不同？

一句话：JDK 线程池是先进队列：核心线程满了先排队，队列满了才加线程到最大值，还满就拒绝。Tomcat 反过来，线程没到上限时优先加线程，不排队。

  • JDK 顺序：核心线程 → 队列 → 非核心线程（到 max）→ 拒绝策略
  • Tomcat 用自己的队列（TaskQueue），所以 Web 请求能尽快有线程处理
  • 后果：JDK 线程池队列很大时，线程几乎永远加不到 max，任务在队列里等到调用方都超时了

常见坑：想要「先加线程再排队」却配了大队列（应调小队列，或设 core = max 并开 allowCoreThreadTimeOut(true) 回收空闲线程）。

→ 详见 并发参数调优

Q35：队列长度如何确定？为什么不是越大越好？

一句话：任务在队列里等的时间必须比调用方的超时短，否则等到执行时对方早放弃了，白干。可按 队列长度 ≤ 线程数 × 可接受排队时间 / 单任务耗时 估算。

  • 例：单任务 100ms、20 个线程、队列 500，队尾任务要等 500 / 20 × 100ms = 2.5 秒
  • 只能接受 500ms 排队时，队列最多 20 × 500 / 100 = 100
  • 队列太大还会让最大线程数永远用不上（见 Q34）

常见坑：用无界队列（任务无限堆积，最后 OOM）。

→ 详见 并发参数调优

Q36：Tomcat 的 threads.max、max-connections、accept-count 分别是什么关系？开启虚拟线程后哪些还生效？

一句话：三道闸门：最多 threads.max 个线程干活；线程都忙时连接还能接，最多 max-connections 个；再多的连接在系统队列里排着，长度是 accept-count；还满就连接失败。

参数默认值含义
server.tomcat.threads.max200最多多少个线程处理请求
server.tomcat.max-connections8192最多保持多少个连接
server.tomcat.accept-count100系统层排队的连接数（受 somaxconn 限制）
  • 开启虚拟线程（Spring Boot 3.2+ spring.threads.virtual.enabled=true）后每个请求一个虚拟线程，threads.max 不再限制并发；max-connections 仍然有效，accept-count 是系统层的，也不受影响
  • 瓶颈会转到数据库连接池等下游，要用连接池大小或信号量限住下游并发

→ 详见 并发参数调优

Q37：数据库连接池是不是越大越好？水平扩容时要注意什么？

一句话：不是。数据库同时能干活的数量有限，连接多了只会互相排队。扩容时要守住总数：所有实例的连接池上限加起来 ≤ 数据库 max_connections 的 80%，剩下的留给运维和监控。

  • 这是上限不是目标：max_connections=2000、40 个实例时每个池最多 40
  • 实际需要的往往很少：单实例 500 QPS、每次占用连接 10ms，平均只要约 5 个连接
  • 扩容前重新算：实例从 40 扩到 80，池子不调小就会超，新实例启动直接报 Too many connections
  • 多个服务共用一个库时，这个上限要在服务之间分

→ 详见 并发参数调优、池化技术

Q38：Lettuce 需要配置连接池吗？什么时候池才会被使用？

一句话：一般不需要。Lettuce 一条连接就能同时处理多个线程的请求，Spring 默认所有普通命令都共用这一条连接，配了池 GET / SET 也不会用到。

  • 只有这些情况才用池：阻塞命令（BLPOP、XREAD BLOCK，避免卡住共享连接）、事务（MULTI / EXEC，需要独占连接）、手动关闭共享连接后
  • 启用池要额外引入 commons-pool2
  • Jedis 不一样：一个连接同时只能处理一个请求，必须用池，大小约等于访问 Redis 的并发线程峰值
  • Redisson 自带连接池

常见坑：Redis 变慢就调大 max-active（普通命令根本不走池，应该先查命令延迟和大 key）。

→ 详见 并发参数调优

Q39：服务器出现大量 TIME_WAIT 是什么原因？如何解决？

一句话：TIME_WAIT 出现在主动关闭连接的一方，要等一段时间（2MSL）才释放。大量 TIME_WAIT 基本是因为用了短连接，比如调下游 HTTP 没用连接池、没开 Keep-Alive。先改成复用连接，再考虑调内核参数。

  • net.ipv4.tcp_tw_reuse：允许发起连接时复用 TIME_WAIT 的端口
  • net.ipv4.ip_local_port_range：扩大本机作为客户端时能用的端口范围，如 10000 65535
  • 相关参数还有 ulimit -n（每个连接占一个文件句柄）、somaxconn（会截断 Tomcat 的 accept-count）
ss -ant | awk '{print $1}' | sort | uniq -c   # 统计各状态连接数

常见坑：开启 tcp_tw_recycle（NAT 环境下会丢包，Linux 4.12 已删除）。

→ 详见 并发参数调优

九、容量评估

Q40：如何从 DAU 估算系统的峰值 QPS？

一句话：日请求量 = DAU × 每人操作次数 × 每次调用接口数，平均 QPS = 日请求量 / 86400，峰值 QPS = 平均 QPS × 峰值系数。准备容量看的是峰值，不是平均值。

  • 例：500 万 DAU × 每人 20 次 = 1 亿次 / 天，平均约 1157 QPS
  • 日常峰值按二八原则（80% 请求集中在 20% 时间）约为平均的 4 倍，约 4600；大促按历史数据再乘 10，约 4.6 万
  • 峰值系数日常 2～5，大促、秒杀可达 10～100，用历史数据修正
  • 写入量单独算：下单转化率 2% 时，下单峰值约 920 TPS

常见坑：按分钟平均值估峰值（秒杀开始那一秒可能是分钟平均的几十倍）。

→ 详见 容量评估与规划

Q41：如何评估单机能力？需要多少台机器？多可用区部署时冗余系数怎么算？

一句话：单机能力只能靠压测，取「P99 满足要求且 CPU 不超过 70%」时的 QPS。机器数 = 峰值 QPS / 单机 QPS × 冗余系数；部署在 N 个可用区、要扛住挂掉 1 个时，冗余系数是 N / (N − 1)（2 个区是 2，3 个区是 1.5）。

  • 例：峰值 4.6 万、单机 1500，基础需要约 31 台
  • 3 个可用区挂 1 个，剩下 2 个要扛全部：每个区至少 16 台，共 48 台
  • 验证：任一区挂掉，剩 32 × 1500 = 4.8 万，够用；还可再乘 1.2 的估算误差
  • 压测环境要和生产同规格，按真实比例混合接口，逐级加压

常见坑：只算应用机器不算下游（48 台 × 每台连接池会不会超过数据库连接上限，Redis、MQ 同理）。

→ 详见 容量评估与规划

Q42：什么是全链路压测？如何保证压测数据不污染生产？（流量染色、影子库、挡板）

一句话：单机压测测不出网关、中间件、数据库这些共享环节的瓶颈，全链路压测就是在生产环境用真实链路跑压测流量。不污染数据靠给流量打标记，并让带标记的请求写到隔离的「影子」存储里。

  • 流量染色：压测请求带一个标记头，网关要把外部请求伪造的同名头去掉
  • 标记一路传下去：线程间、RPC、HTTP、MQ 消息都要带着这个标记
  • 影子存储：带标记的请求写影子库 / 影子表、影子 Redis key、影子 Topic
  • 挡板：支付、短信等第三方返回模拟结果，并模拟真实的响应时间
  • 数据隔离：压测账号用独立 ID 段，不进结算和报表，结束后清理

常见坑：影子库数据量太少（测出来的是小表性能，要按生产数据量准备）。

→ 详见 容量评估与规划

Q43：生产环境压测有哪些风险？如何控制？

一句话：风险是压测流量抢了真实用户的资源、压垮共享组件、数据写错地方。第一原则是不影响真实用户，而且随时能一键停。

  • 时间：选业务低峰期，提前通知相关团队和值班人员
  • 分级加压：按目标量的 10% → 30% → 50% → 100% 逐步加，每级稳定了再加
  • 盯指标：同时看压测流量和真实流量的响应时间、错误率，以及资源水位
  • 自动停：真实流量变慢或资源水位超过阈值（如 80%）时自动停止发压
  • 手动开关：配置中心一个总开关，网关直接拦掉所有压测请求；提前备好扩容、限流、降级预案

→ 详见 容量评估与规划

Q44：大促前需要做哪些准备？

一句话：主线是「估流量 → 扩容 → 压测验证 → 预热 → 值守 → 复盘」，按时间点提前排好，并按功能重要程度准备好降级开关。

  • 提前 30 天：预估流量，全链路压测找瓶颈，列出扩容清单（应用、数据库、Redis、MQ 分区）
  • 提前 7 天：扩容完成后再压测一次，整理降级开关和限流阈值，停止非必要变更（封网）
  • 提前 1 天：缓存预热，检查降级开关能用，值班人员就位
  • 大促中盯水位、按预案逐级降级；大促后分批缩容，复盘这次的峰值和瓶颈
  • 降级优先级：下单、支付不降级只限流；详情、购物车用兜底数据；评论、推荐直接关；积分、通知延后处理

→ 详见 容量评估与规划

Q45：容量水位如何监控？HPA 扩容阈值和容量规划水位有什么区别？

一句话：水位 = 当前峰值 / 容量上限，上限来自压测结果。HPA 阈值看的是单个 Pod 的 CPU，分钟级自动扩缩；规划水位看的是整个集群的 QPS 和上限，用来做按天、按周的人工扩容决策。

  • 水位分级：低于 50% 可考虑缩容；50%～70% 正常；70%～85% 开始准备扩容；超过 85% 立即扩容并准备限流降级
  • HPA 目标（如 CPU 60%）比单机容量点（70%）低，中间差的是扩容生效前的缓冲时间
  • HPA 解决不了「副本数已经到上限」或「数据库先扛不住」，这正是规划水位要提前发现的
  • 监控项：QPS、P99、错误率、GC、线程池和连接池的使用与排队、下游响应时间；除了实时告警，还要按增长趋势预测何时触顶
