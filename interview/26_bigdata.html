大数据面试题解答

题目清单见 大数据高频面试题；细节见 大数据总览。

版本基线：Spark 4.2（读写 Iceberg 暂用 4.1）、Hadoop 3.5、Iceberg 1.12、Paimon 2.0、Flink 2.2、DolphinScheduler 3.4 / Airflow 3.3、StarRocks / Doris 4.1、JDK 21 / Spring Boot 4。

一、基础与架构

Q1：批处理和流处理有什么区别？项目里怎么选？

一句话：批处理一次算一批固定的数据，结果确定、便于对账；流处理数据来一条算一条，延迟低但运维重。选型不看"批好还是流好"，看每个需求要多新鲜的数据。

时效典型需求做法
T+1 / 小时级经营日报、财务对账Spark SQL 按分区批处理，调度驱动
分钟级准实时报表、库存预警Flink 写 Paimon / Iceberg，OLAP 直接查
秒级实时大屏、风控拦截Kafka + Flink，结果写 Redis / Doris
  • 能用批就不用流：流作业要处理状态膨胀、乱序、反压（下游处理不过来时压力往上游传）
  • 对账永远以批处理结果为准，实时结果用来看趋势

→ 详见 大数据基础

Q2：MapReduce 的思想是什么？为什么说 Shuffle 最贵？

一句话：Map 把数据切片后各自并行处理，Shuffle 按 key 把数据重新分发，Reduce 汇总同一个 key 的数据；Shuffle 要排序、落盘、跨网络传输，是整个作业最慢的一步。

  • Map：每个任务读一个分片，输出 (key, value)，任务之间完全独立
  • Shuffle：按 key 的哈希把数据送到对应 Reduce，保证同一个 key 落到一起
  • Combiner：Map 端先局部聚合再发出去，减少 Shuffle 数据量；只适用于求和、计数、最大值这类可以分步合并的聚合
  • 今天 Spark 的宽依赖、Flink 的 keyBy 都是同一套思想的延续

常见坑：求平均值不能直接用 Combiner，要拆成"和 + 个数"再合并。

→ 详见 大数据基础

Q3：什么是存算分离？代价是什么？

一句话：数据放对象存储，计算跑在 Kubernetes 上，两边各自扩缩；换来弹性、多引擎共享和更低成本，代价是读数据要走网络，对象存储列目录慢、重命名不是原子操作。

  • 收益：计算用完即释放；Spark、Flink、Trino、Doris 读同一份数据，不用来回拷贝
  • 网络延迟：靠计算节点本地缓存弥补（Doris / StarRocks 存算分离模式、Alluxio）
  • 重命名非原子：用零重命名提交器，或直接用 Iceberg / Paimon 这类表格式，靠一次原子元数据提交让文件可见
  • 小文件：对象存储按请求计费，写入端要控制文件大小并定期合并
  • 自建机房、已有大规模 HDFS 集群或对延迟极敏感时，存算一体仍是合理选择

→ 详见 大数据基础

Q4：Lambda 和 Kappa 架构有什么区别？现在主流是什么？

一句话：Lambda 批、流两条链路并行，批处理兜底正确性，但同一套逻辑要写两遍；Kappa 只保留流，重算靠 Kafka 重放，但重放大量历史又慢又贵。现在主流是基于湖仓的流批一体。

  • Lambda 最大的痛点：实时 GMV 和第二天日报口径稍有差异，数字就对不上
  • Kappa 的问题：Kafka 长期保留全量数据成本太高，用流重放一年订单远不如批处理快
  • 流批一体：数据统一落在 Paimon / Iceberg 表上，Flink 流式写入和增量读，Spark 批量重算
  • 延迟分级：秒级走 Kafka + Flink 直出，分钟级走湖仓流式链路，T+1 对账走批处理

常见坑：以为上了 Kappa 就不需要批处理，结果历史重算只能靠 Kafka 重放，保留期一过就无从补救。

→ 详见 大数据基础

二、数仓建模

Q5：数仓为什么要分层？ODS / DWD / DWS / ADS 各放什么？

一句话：分层是把复杂计算拆成职责单一的几步，公共的清洗和汇总只做一次，从而统一口径、复用计算、隔离上游变化、出问题能逐层追溯。

层放什么示例
ODS 贴源层原样接入业务库和日志，不做业务加工ods_order_info_inc
DWD 明细层按业务过程建最细粒度事实表：清洗、去重、统一单位dwd_trade_order_detail_inc
DWS 汇总层按粒度 + 周期轻度汇总，沉淀公共指标dws_trade_user_order_1d
ADS 应用层面向具体报表、接口的结果ads_trade_gmv_1d
  • DIM 存放用户、商品、日期等公共维度，被 DWD 和 DWS 共用
  • 只向下引用、不跨层；每层按天分区，任务可安全重跑

常见坑：ADS 直接读 ODS，等于绕过了全部清洗和口径统一。

→ 详见 数仓分层与建模

Q6：星型模型和雪花模型怎么选？事实表有哪几种？

一句话：数仓普遍用星型模型，事实表周围直接挂反范式的维度表，JOIN 少、SQL 简单；雪花模型把维度再拆细，冗余少但 JOIN 多，只在维度极大的场景考虑。

  • 列存和廉价存储下冗余几乎不花钱，而 JOIN 是分布式查询最贵的操作之一
  • 事务事实表：一次业务事件一行，如下单明细，回答"发生了多少"
  • 周期快照事实表：某对象在周期末的状态，如每天每个 SKU 的库存，回答"现在有多少"
  • 累积快照事实表：一个订单一行，记录下单、支付、发货、签收等里程碑，用来分析流程时效
  • 度量要区分可加性：金额可以逐层相加，转化率、去重用户数不行，要存分子分母或重新去重

→ 详见 数仓分层与建模

Q7：什么是缓慢变化维？拉链表怎么实现？

一句话：缓慢变化维处理的是"维度属性会变"，比如用户从普通会员升级为 VIP；拉链表（SCD Type 2）给每个版本存一行，用 start_date / end_date 标出有效区间，当前版本的 end_date 统一为 9999-12-31。

  • Type 1 直接覆盖，不留历史，适合纠错、昵称这类不关心历史的属性
  • Type 2 每日更新：先按主键去重当天变更，再用一条 MERGE INTO 关闭旧版本、插入新版本
  • 事实表关联拉链维度时，用业务日期落在 [start_date, end_date] 区间内作为条件，取到的是"下单当时"的等级
  • 只把需要追踪历史的属性放进比较条件，频繁变化又不需要历史的属性拆到 Type 1 维度

常见坑：不先去重，同一主键命中多行，Iceberg 的 MERGE 会直接报错。

→ 详见 数仓分层与建模

Q8：原子、派生、衍生指标是什么？怎么保证同一个指标只有一个口径？

一句话：原子指标定义"算什么"，派生指标在它上面加统计周期、业务限定和统计粒度，衍生指标是派生指标之间的比率；口径一致的关键是同一个指标只算一次。

  • 原子：下单金额 = 下单业务过程的 SUM(amount)，不可再拆
  • 派生：最近 7 日 · 手机品类 · 各省份 · 下单金额
  • 衍生：最近 7 日支付转化率 = 支付用户数 ÷ 下单用户数
  • 只算一次：派生指标只在 DWS 由一个任务计算，报表和接口都从同一处取数
  • 指标字典登记业务口径（含不含退款）和技术口径（哪张表哪个字段），变更走评审并记录版本

→ 详见 数仓分层与建模、数据治理

三、Spark 与湖仓

Q9：Spark 的 Job、Stage、Task 是怎么划分的？

一句话：每触发一次动作（如 write、count）产生一个 Job；Job 在宽依赖（需要 Shuffle 的地方）处切成多个 Stage；每个 Stage 按分区数生成同样多的 Task。

  • 转换是惰性的：filter、join 只记录计划，动作才真正执行，优化器因此能看到全貌做谓词下推、列裁剪
  • 窄依赖：filter、select 只依赖父的一个分区，在同一个 Task 里流水线执行
  • 宽依赖：groupBy、非广播 join、repartition 依赖父的所有分区，要 Shuffle
  • 物理计划里每个 Exchange 节点就是一次 Shuffle，用 explain("formatted") 查看

常见坑：同一个 DataFrame 被多个动作使用又没 cache()，每个动作都会从头重算一遍。

→ 详见 Spark

Q10：Spark 数据倾斜怎么发现、怎么处理？

一句话：一个 Stage 里大部分 Task 几秒完成，少数几个跑几十分钟甚至 OOM，就是倾斜；处理顺序是先交给 AQE，再拆空值和大 key，聚合倾斜用加盐两阶段聚合。

  • 识别：Spark UI 里 Task 耗时和 Shuffle Read 的最大值比中位数大十倍以上
  • 常见来源：大量 user_id 为空或 0、头部商家和爆款商品、按只有几个取值的状态字段分组
  • AQE（自适应查询执行，运行时按实际数据量重新优化）会自动拆分排序合并 Join 中的倾斜分区，但管不了 groupBy
  • 加盐：给 key 拼随机前缀打散到 N 个分区先局部聚合，再去掉前缀全局聚合
  • 能广播小表就广播，直接省掉 Shuffle

常见坑：countDistinct 不能加盐拆两步，要先按 (key, user_id) 去重再计数。

→ 详见 Spark

Q11：Iceberg 这类表格式解决了 Hive 表的什么问题？原理是什么？

一句话：Hive 表只是"目录约定"，没有文件级元数据和事务；表格式用一棵不可变的元数据树记录"某一时刻这张表由哪些文件组成"，提交就是原子地切换树根。

  • 元数据树：Catalog 指针 → metadata.json → 清单列表 → 清单文件 → 数据文件，查询靠清单里的列统计跳过文件，不用列目录
  • 乐观并发：写入不加锁，提交时对 Catalog 指针做比较并交换（CAS），被别人抢先就基于新版本重试
  • 行级更新：写时复制（COW，重写整个文件）适合读多写少；读时合并（MOR，只写删除标记）适合频繁 upsert
  • Schema 演进靠列 ID，加列、改名都是纯元数据操作；隐藏分区让查询不用手写分区列
  • 每个快照都可查，支持时间旅行和回滚

→ 详见 数据湖与湖仓

Q12：Iceberg、Paimon、Hudi、Delta 怎么选？小文件怎么治理？

一句话：批处理和多引擎共享选 Iceberg，Flink 实时入湖和主键 upsert 选 Paimon，Hudi、Delta 适合各自已有的技术栈；小文件靠写入侧控制加定期合并。

格式设计重心适合
Iceberg多引擎共享的开放表标准离线 DWS / ADS、对外共享
Paimon流式更新，原生主键和完整变更流实时 ODS / DWD
Hudi / Delta增量处理 / Spark 生态已有对应技术栈
  • Catalog 优先选 REST 协议实现（如 Polaris、Gravitino），能统一权限和下发临时存储凭证
  • Iceberg 维护顺序：合并数据文件 → 合并清单 → 过期快照 → 清理孤儿文件
  • Paimon 主键表在写入时异步合并，一般不用单独调度合并任务

→ 详见 数据湖与湖仓

四、集成、调度与数据服务

Q13：业务库同步到数仓，全量和增量怎么衔接？时间戳增量有哪些坑？

一句话：小表每天全量覆盖，大表按 update_time 增量或订阅 binlog 做 CDC；全量和增量衔接的原则是增量起点必须早于全量快照时刻，宁可重叠，不可留缝，重叠部分靠幂等合并消除。

  • CDC 工具（Flink CDC、Debezium、SeaTunnel）内置"先全量快照、再从对应 binlog 位点接续"，直接用即可
  • 硬删除丢失：被删除的行不会出现在时间戳增量里，要改软删除、改用 CDC 或定期全量补删
  • 长事务漏数：事务提交晚于批次截止时间，下一批又从截止时间开始，要每批往前多拉一段窗口
  • 更新时间不可靠：脚本直接改库没刷 update_time，只能靠 CDC 或全量兜底
  • 合并时先按主键去重，再用 update_time 比较，防止旧数据覆盖新数据

→ 详见 数据集成

Q14：数据任务怎么做到能重跑、能补数？

一句话：同一个业务日期跑一次和跑 N 次结果相同：所有日期来自调度传入的业务日期参数，写入按分区整体覆盖，写库、发消息这类外部副作用以业务日期去重。

  • 区分两个时间：运行时间是任务实际执行的时刻，数据时间是这次负责算哪一天；SQL 里出现 current_date() 就是隐患
  • 数仓表用 INSERT OVERWRITE ... PARTITION (dt = '${dt}')；Spark 多分区覆盖要开 partitionOverwriteMode=dynamic
  • 写回 MySQL 用同一事务内先删后插，或写临时表后 RENAME 交换
  • DolphinScheduler 补数时所选日期是调度时间，节点用 $[yyyy-MM-dd-1] 时要补 10-01 应选 10-02
  • 有跨天依赖（拉链表、累计值）的补数必须串行

常见坑：INSERT INTO 追加写分区表，重跑后数据翻倍。

→ 详见 任务调度

Q15：对外提供报表查询接口，怎么防止重查询拖垮 OLAP 集群？

一句话：消费方不直连 OLAP，统一走查询服务；服务层限制查询代价、按数据版本缓存、按全局和租户两级限流，引擎层再用资源组和大查询熔断兜底。

  • 接口约束：日期区间上限、必填过滤条件、维度走枚举白名单，在入口就挡掉扫全表的请求
  • 超时两层：引擎侧 query_timeout 主动终止查询，客户端 socketTimeout 做网络兜底；连接池不宜大
  • 缓存：ADS 只在 ETL 产出时变化，把数据版本号放进缓存键，新数据产出后旧键自然失效
  • 引擎隔离：StarRocks 资源组 / Doris Workload Group，对外接口、内部 BI、临时分析、物化视图刷新各一组
  • 大结果集走异步导出，由引擎直接卸数到对象存储

→ 详见 OLAP 查询与数据服务

Q16：分钟级实时数仓怎么搭？出错了怎么回放？

一句话：埋点经网关进 Kafka，Flink SQL 逐层写 Paimon 的 ODS / DWD / DWS，StarRocks 用外部 Catalog 加异步物化视图做 ADS；DWD 去重保证从 Kafka 重放是安全的。

  • ODS 用追加表原样落地；DWD 用 first-row 合并引擎按 event_id 只保留第一条；DWS 用 aggregation 合并引擎写入即累加，Flink 作业几乎无状态
  • 延迟约 3–5 分钟，主要由各层 checkpoint 间隔和物化视图刷新间隔决定；秒级需求另走 Kafka 直连 OLAP
  • 下游配 consumer-id，防止未消费的快照被过期清理
  • 端到端新鲜度用数据自带的 last_event_time 衡量，而不是只看作业是否在运行
  • 批量重算历史分区不会自动传给流式下游，要按血缘逐层重算并刷新物化视图
