JVM 面试题解答

细节详见 JVM 总览。

版本基线：JDK 21 / 25 LTS，与 JDK 8 / 17 不同处单独说明。

一、内存结构

1、JVM 的运行流程是什么？

一句话：源码先被 javac 编译成字节码，JVM 用类加载器把 class 读进内存，再由执行引擎（解释器 + JIT 编译器）翻译成机器码交给 CPU 执行。

  • 类加载子系统：加载 → 链接（验证、准备、解析）→ 初始化，生成 Class 对象
  • 运行时数据区：程序计数器、虚拟机栈、本地方法栈、堆、方法区
  • 执行引擎：解释器逐条执行，JIT 把热点代码编译成机器码，垃圾收集器负责回收内存
  • 需要调用 C/C++ 库时走本地方法接口（JNI）

→ 详见 JVM 内存结构

2、JVM 内存区域有哪些？各区域的作用是什么？

一句话：每个线程私有的程序计数器、虚拟机栈、本地方法栈管「代码怎么执行」；所有线程共享的堆和方法区管「数据放在哪」。

  • 程序计数器：记录当前执行到哪条字节码，唯一不会 OOM 的区域
  • 虚拟机栈：每调用一个方法压入一个栈帧，存局部变量等；递归太深报 StackOverflowError
  • 堆：存对象和数组，也存静态变量和字符串常量池（JDK 7 起），GC 主要管这里
  • 方法区（JDK 8 起叫元空间）：存类的结构信息，用的是本地内存
  • 直接内存：NIO 用的堆外缓冲区，不属于规范定义的区域，但同样会 OOM

→ 详见 JVM 内存结构

3、堆和栈的区别？堆和方法区的区别？

一句话：栈是线程私有的，方法调用时分配、返回时释放；堆是所有线程共享的，放对象，靠 GC 回收。方法区也是共享的，但放的是类的信息，不是对象。

对比虚拟机栈堆方法区（元空间）
线程私有共享共享
存什么局部变量、方法调用信息对象、数组、静态变量类结构、方法字节码、常量池
何时释放方法返回GC 回收类卸载
大小参数-Xss-Xms / -Xmx-XX:MaxMetaspaceSize
  • 局部变量是基本类型时值在栈上；是引用时栈上只存引用，对象本身在堆上

→ 详见 JVM 内存结构

4、方法区在 JDK 8 后有什么变化？为什么用元空间替代永久代？

一句话：JDK 8 用元空间（放在本地内存）取代了永久代（放在堆里、大小固定）；字符串常量池和静态变量早在 JDK 7 就移到堆里了。

  • 永久代大小要事先定死，很难估准，动态生成的类一多就报 PermGen space
  • 元空间用本地内存，按需增长，类信息的回收也不再和堆 GC 绑在一起
  • 还有一个原因：方便 HotSpot 和 JRockit 合并，JRockit 本来就没有永久代

常见坑：MaxMetaspaceSize 默认不设上限，建议显式设置；MetaspaceSize 是第一次触发元空间 GC 的阈值，不是初始大小。

→ 详见 JVM 内存结构

5、Java 对象一定在堆上分配吗？

一句话：语义上都在堆上；但 JIT 发现对象不会被方法外用到（不逃逸）时，可以把对象拆成几个局部变量，根本不创建对象，这叫标量替换。

  • HotSpot 没有把整个对象放到栈上的「栈上分配」，教材常这么说但不准确
  • 标量替换依赖方法内联和逃逸分析，默认开启，但效果不稳定
  • 大多数对象分配在线程私有的 TLAB（堆里给每个线程划的一小块）里，它仍然是堆

→ 详见 JIT 编译

6、什么是内存泄漏？和内存溢出的区别？

一句话：内存泄漏是对象已经没用了却还被引用着，回收不掉，这是原因；内存溢出（OOM）是要分配内存时空间不够，这是结果。

  • 泄漏一直积累最终会导致溢出，但溢出也可能只是内存给少了
  • 泄漏的表现：每次 GC 后老年代占用还在涨，Full GC 也降不下来
  • 常见泄漏：静态集合只加不删、监听器不注销、ThreadLocal 不 remove()、缓存没有上限
  • 排查：导出 heap dump，用 MAT 找是谁一直引用着这些对象

→ 详见 JVM 故障排查

7、OOM 有哪几种类型？各是什么原因？

一句话：看 OutOfMemoryError 后面跟的消息，就知道是哪块内存不够，排查方向完全不同。

错误消息哪块内存常见原因
Java heap space堆泄漏、大对象、流量突增、堆太小
GC overhead limit exceeded堆GC 一直在忙却几乎回收不到东西
Metaspace元空间动态代理生成大量类、类加载器泄漏
Direct buffer memory直接内存堆外缓冲区没释放、上限太小
unable to create native thread系统线程线程数超过系统限制、线程无限增长
  • StackOverflowError 不是 OOM，通常是递归太深

常见坑：把容器 OOMKilled 当成 JVM OOM；那是进程总内存超过容器限制被系统杀掉（退出码 137），没有 Java 异常也没有 heap dump。

→ 详见 JVM 故障排查

8、String 常量池在哪里？JDK 6 和 JDK 7+ 有什么区别？

一句话：JDK 6 在永久代，JDK 7 起移到堆里，池里的字符串可以正常被 GC 回收。

  • 常量池本质是一张固定桶数的哈希表，桶数用 -XX:StringTableSize 调
  • 移到堆里的好处：不会再因为永久代太小而溢出
  • 这次迁移也改变了 intern() 的行为（见下题）

→ 详见 JVM 内存结构

9、String.intern() 的作用和使用场景？

一句话：池里已经有相同内容的字符串就返回池里那个；没有的话，JDK 7 起把当前对象的引用登记进池（JDK 6 是复制一份到永久代）。

  • 所以 new String("ab") + new String("c") 得到的对象调 intern() 后，JDK 7+ 与字面量 "abc" 用 == 比是 true，JDK 6 是 false
  • 适用：大量重复、取值有限的字符串（状态、编码、标签），intern 后共用一个对象省内存
  • G1 的字符串去重（-XX:+UseStringDeduplication）只共享底层字节数组，String 对象还是各自独立，== 结果不变

常见坑：对用户输入、订单号这类数量不受控的字符串调 intern()，常量池会越来越大。

→ 详见 JVM 内存结构

二、类加载

10、类加载的完整过程是怎样的？

一句话：加载 → 验证 → 准备 → 解析 → 初始化，中间三步合称「链接」。

  • 加载：按类名读取字节码，生成类的元数据和堆里的 Class 对象
  • 验证：检查字节码格式和语义，防止恶意或损坏的 class
  • 准备：给静态变量分配内存并赋零值（0、null）；编译期常量直接赋值
  • 解析：把符号引用（名字）换成直接引用（地址），HotSpot 多数推迟到第一次用时
  • 初始化：执行静态赋值和 static {} 块，父类先于子类，JVM 保证只执行一次

→ 详见 类加载机制

11、双亲委派模型的原理和作用？

一句话：类加载器收到请求先交给父加载器，父加载器加载不了才自己加载。作用是避免同一个类被加载多次，以及防止核心类库被篡改。

  • 流程：先看自己是否已加载过 → 交给父加载器，一路到最顶层 → 都找不到才自己 findClass
  • JDK 9 起三层加载器：Bootstrap（核心模块）、Platform（部分平台模块，原来的 Extension）、Application（classpath）
  • 父子关系是通过 parent 字段组合的，不是继承
  • 就算绕过委派，也不能自己定义 java.* 包下的类

→ 详见 类加载机制

12、如何打破双亲委派？为什么 Tomcat 要打破？

一句话：重写 loadClass() 改变委派顺序，或者让父加载器反过来借用子加载器（线程上下文类加载器），都算打破双亲委派。

  • SPI（如 JDBC）：DriverManager 在上层加载器里，看不到应用里的驱动，就借当前线程的类加载器去加载
  • Tomcat：每个 Web 应用一个加载器，JDK 的类仍交给上层，其余类先在本应用里找
  • 热部署：新建一个加载器加载新版本的类，把旧加载器整个丢掉
  • Tomcat 为什么要打破：一个 Tomcat 部署多个应用，它们可能依赖同一个库的不同版本；按双亲委派只能共享一个版本，「先自己找」才能让各应用互相隔离

→ 详见 类加载机制

13、类的初始化时机有哪些？（主动引用 vs 被动引用）

一句话：只有「主动使用」类时才触发初始化，比如 new 对象、读写静态字段、调静态方法、反射调用；其他引用方式都不会。

  • 主动引用还包括：初始化子类时先初始化父类、带 main 方法的启动类
  • 被动引用一：通过子类访问父类的静态字段，只初始化父类
  • 被动引用二：new Parent[10] 建数组，不会初始化 Parent
  • 被动引用三：引用编译期常量，常量已经在编译时复制到调用方
  • ClassLoader.loadClass() 只加载不初始化；Class.forName(name) 默认会初始化

→ 详见 类加载机制

14、如何判断两个类是否相同？

一句话：全限定类名相同，并且是同一个类加载器加载的，两个条件缺一不可。

  • 同一个 .class 文件被两个加载器加载，就是两个不同的类：互相赋值抛 ClassCastException，instanceof 返回 false
  • 线上常见于热部署、插件化、多个应用共享对象，报出「X cannot be cast to X」这种怪错误

→ 详见 类加载机制

15、static final 常量为什么在准备阶段就能赋值？

一句话：编译期常量（static final 且值是基本类型或字符串字面量）的值在编译时就确定了，直接写在 class 文件里，准备阶段读出来赋上就行，不用等初始化。

public static int value = 123;                  // 准备阶段是 0，初始化阶段才变 123
public static final int MAX = 100;              // 准备阶段直接是 100
public static final Object LOCK = new Object(); // 不是编译期常量，初始化阶段赋值

→ 详见 类加载机制

三、字节码执行

16、JVM 字节码是基于栈还是基于寄存器执行的？

一句话：基于栈。指令从操作数栈顶取数据，算完再把结果压回栈顶。

对比栈式（JVM）寄存器式（Android 的 Dalvik / ART）
单条指令短较长，要写寄存器编号
指令条数较多较少
移植性不依赖硬件，好移植和寄存器模型有关
  • JIT 编译出的机器码照样会充分用 CPU 寄存器，栈式只是字节码层面的设计

→ 详见 字节码执行

17、i++ 和 ++i 的字节码有什么区别？

一句话：区别只在「先读值」还是「先加 1」：i++ 先把旧值读到栈上再给变量加 1，++i 先加 1 再读值。

  • j = i++：iload → iinc → istore，j 拿到旧值
  • j = ++i：iinc → iload → istore，j 拿到新值
  • 单独写一行 i++; 时两者都只编译成一条 iinc，没有任何区别

常见坑：i = i++ 之后 i 不变，因为先把旧值压栈，加 1 之后又用旧值覆盖了 i。

→ 详见 字节码执行

18、Lambda 为什么用 invokedynamic 实现，而不是编译成匿名内部类？

一句话：把「怎么生成实现类」推迟到运行时决定，这样不用生成一堆 class 文件，而且以后 JDK 改进实现方式时，老代码不用重新编译就能受益。

  • 编译时：Lambda 体变成当前类的一个私有方法，使用的地方放一条 invokedynamic 指令
  • 第一次执行：JVM 在内存里生成一个实现类，并把这条指令和它绑定
  • 之后执行：直接用绑定好的结果；不捕获变量的 Lambda 通常一直复用同一个实例
  • 和匿名类比：匿名类每个都生成一个 Outer$1.class，this 指匿名类自己；Lambda 的 this 指外面的对象

→ 详见 字节码执行

四、垃圾回收

19、如何判断对象是否可以被回收？

一句话：HotSpot 用可达性分析：从一组「根」（GC Roots）出发顺着引用往下找，找不到的对象就是垃圾。没有用引用计数。

  • 引用计数的问题：A、B 互相引用但外面没人用它们，计数都不为 0，永远回收不掉
  • 四种引用强度：强引用不回收；软引用内存不够时回收；弱引用下次 GC 就回收；虚引用只用来收到「对象被回收了」的通知

→ 详见 GC 原理

20、有哪些 GC Roots？为什么它们可以作为根？

一句话：GC Roots 是程序「正在用」的入口，比如线程栈里的局部变量、类的静态字段，程序随时可能访问它们，所以它们本身一定是活的。

  • 虚拟机栈里的局部变量、方法参数
  • 已加载类的静态字段、常量池里的引用
  • native 代码持有的引用、被 synchronized 锁住的对象
  • JVM 内部引用，如系统类加载器、常驻的异常对象

只回收一部分区域时（比如只回收年轻代），别的区域指向它的引用也要当成根，这些引用记在「卡表」里

→ 详见 GC 原理

21、常见垃圾回收算法有哪些？

一句话：标记-清除、复制、标记-整理三种，各有取舍：分别会产生碎片、浪费空间、移动成本高。

算法做法缺点用在哪
标记-清除标记活的，清掉其余有内存碎片CMS 老年代
复制活的复制到另一块，原块整个清空要留一块空闲空间年轻代
标记-整理标记后把活的挪到一端移动对象、改引用开销大老年代、Full GC
  • 年轻代用 Eden + 两个 Survivor 的方式复制，只浪费 10% 空间，不是一半

→ 详见 GC 原理

22、分代收集的原理是什么？新生代和老年代用的是哪种算法？

一句话：大多数对象很快就死，活得越久的越不容易死。所以把堆分成年轻代和老年代：年轻代存活少，用复制；老年代存活多，用标记-清除或标记-整理。

  • 默认比例：Eden : S0 : S1 = 8 : 1 : 1，老年代 : 年轻代 = 2 : 1
  • 晋升老年代：熬过的 GC 次数达到阈值（默认 15）；Survivor 放不下；大对象直接进老年代
  • 动态年龄：同年龄及以下的对象加起来超过 Survivor 一半，就把这个年龄当阈值
  • G1、分代 ZGC 也分代，只是每代是一组逻辑上的 Region，不是连续的一块

→ 详见 GC 原理、JVM 内存结构

23、Minor GC、Major GC 和 Full GC 的区别与触发条件？

一句话：Minor（Young）GC 只回收年轻代；Major GC 只回收老年代；Full GC 回收整个堆加元空间。口头上常把 Major 和 Full 混着说，排查时以 GC 日志为准。

  • Young GC 触发：Eden 放不下新对象
  • G1 的 Mixed GC：并发标记完成后，回收年轻代 + 一部分垃圾最多的老年代 Region
  • Full GC 触发：老年代放不下晋升的对象或大对象、元空间到阈值、并发收集来不及、调了 System.gc()
  • 目前只有 CMS 会单独回收老年代（真正意义上的 Major GC）

→ 详见 GC 原理

24、Minor GC 需要扫描整个老年代吗？跨代引用怎么处理？

一句话：不需要。老年代里哪些地方引用了年轻代，都记在「卡表」里，Young GC 只扫被标记过的那几块。

  • 卡表：把老年代按 512 字节切成卡页，某页里有对象指向年轻代，就把这页标成「脏」
  • 写屏障：每次给引用赋值时，JIT 插入的一小段代码顺手更新卡表
  • G1 给每个 Region 维护一个 RSet，记录别的 Region 指向它的引用，原理相同

→ 详见 GC 原理

25、什么是三色标记？并发标记为什么会漏标，CMS 和 G1 分别怎么解决？

一句话：三色标记用白（没看过）、灰（看过但它引用的还没看完）、黑（全部看完）表示标记进度。GC 和业务线程同时跑时，业务改了引用，可能把活对象当垃圾漏掉。

  • 漏标要同时满足两个条件：黑对象新指向了一个白对象；并且所有灰对象到这个白对象的路径都被删了
  • CMS 用增量更新：记下新增的引用，最后重新扫一遍，破坏条件一
  • G1 用 SATB（开始时的快照）：删引用前先记下旧值，按标记开始时的样子算，破坏条件二，代价是多留一些本轮回收不掉的「浮动垃圾」
  • ZGC 不用这两种，靠染色指针和读屏障

→ 详见 GC 原理

26、System.gc() 一定会触发 Full GC 吗？-XX:+DisableExplicitGC 有什么影响？

一句话：System.gc() 只是建议，多数收集器默认会做一次 Full GC，但 JVM 可以忽略或改成并发 GC。不要随手加 DisableExplicitGC，可能导致堆外内存 OOM。

  • 原因：堆外缓冲区（DirectByteBuffer）要等 Java 对象被回收后才释放
  • 堆外内存不够时 JDK 会主动调 System.gc() 来释放，禁用后这一步失效，最终报 Direct buffer memory
  • 想避免显式 GC 造成长停顿，用 -XX:+ExplicitGCInvokesConcurrent，让它改成一次并发 GC

→ 详见 GC 原理

五、垃圾收集器

27、Serial、Parallel、CMS、G1、ZGC 各有什么特点？

一句话：发展主线是把越来越多的 GC 工作从「暂停业务线程（STW）」挪到「和业务线程同时跑」。

收集器特点停顿现状
Serial单线程长单核、小堆
Parallel多线程，吞吐优先较长JDK 8 默认，适合批处理
CMS并发回收老年代短JDK 14 已移除
G1分成 Region，优先回收垃圾多的可控（默认目标 200ms）JDK 9 起默认
ZGC几乎全程并发亚毫秒JDK 21 起用分代 ZGC
  • 机器 CPU 少于 2 个或内存小于 1792MB 时，JVM 默认选 Serial；生产环境建议显式指定收集器

→ 详见 GC 收集器

28、CMS 的垃圾回收过程？它有什么缺点？

一句话：四个阶段：初始标记、并发标记、重新标记、并发清除，只有第 1、3 步短暂暂停业务线程。

  • 内存碎片：标记-清除不整理，碎片多了只能 Full GC
  • 抢 CPU：并发阶段和业务线程抢 CPU，核数少时很明显
  • 浮动垃圾：并发期间产生的新垃圾本轮收不掉，要提前启动；预留空间不够会退化成单线程 Full GC，停顿极长
  • JDK 14 已移除，新项目用 G1 或 ZGC

→ 详见 GC 收集器

29、G1 的工作原理？Region 是什么？为什么它能预测停顿时间？

一句话：G1 把堆切成很多大小相同的 Region，每次在停顿目标内优先回收垃圾最多、最划算的那些 Region，名字 Garbage First 就是这个意思。

  • Region：每块 1MB～32MB，可以随时充当 Eden、Survivor、老年代；超过半块的大对象放专门的 Humongous Region
  • RSet：每个 Region 记录谁引用了自己，回收单个 Region 不用扫全堆
  • 回收方式：Young GC 回收年轻代；老年代占用到阈值后启动并发标记，再做 Mixed GC 分批回收老年代
  • 能预测停顿：G1 记着每个 Region 的垃圾比例和历史回收耗时，按 MaxGCPauseMillis 挑出能在时限内回收完的那批，还会自动调整年轻代大小

常见坑：用 -Xmn / NewRatio 固定年轻代大小，G1 没法自己调，停顿目标就失效了。

→ 详见 GC 收集器

30、ZGC 如何实现低延迟？

一句话：标记、搬移对象、修正引用几乎全部和业务线程同时进行，停顿不随堆变大而变长；关键技术是染色指针和读屏障。

  • 染色指针：把 GC 状态记在 64 位指针的几个空闲位上，看指针就知道对象状态
  • 读屏障：业务线程读引用时顺手检查，发现指向旧地址就当场改成新地址，所以对象可以边跑边搬
  • 暂停只剩几个很短的点，JDK 16 起降到亚毫秒级
  • 代价：读屏障带来少量吞吐损耗，并发阶段多占 CPU，堆要留足余量

常见坑：堆给得太紧，回收赶不上分配，业务线程分配内存时会被卡住等待（Allocation Stall）。

→ 详见 GC 收集器

31、什么是分代 ZGC？各 JDK 版本如何启用？

一句话：分代 ZGC 就是在 ZGC 上加了年轻代和老年代，让短命对象回收得更频繁、更便宜，吞吐和内存占用都比不分代的版本好。

JDK 版本启用方式
JDK 21～22-XX:+UseZGC -XX:+ZGenerational
JDK 23-XX:+UseZGC，分代成为默认
JDK 24+-XX:+UseZGC，不分代模式已删除
  • SoftMaxHeapSize 可以设一个软上限，平时尽量控制在它以下，突发时仍能用到 -Xmx

→ 详见 GC 收集器

六、JIT 编译

32、为什么 Java 程序刚启动时慢，运行一段时间后变快？分层编译是怎样的？

一句话：刚启动时代码是解释执行的，某个方法被调用得足够多以后，JIT 才把它编译成机器码，这个过程叫预热。分层编译就是先用 C1 快速编译，再用 C2 深度优化。

  • 0 层：解释执行，顺便统计调用次数等信息
  • 1～3 层：C1 编译，编得快、优化少，其中 3 层会收集详细的运行数据
  • 4 层：C2 根据收集到的数据做激进优化；假设不成立时退回解释执行（逆优化）
  • 长时间运行的循环可以在循环中途切到编译后的代码（OSR）
  • 缓解预热：上线前先打预热流量、就绪探针放在预热之后、JDK 24+ 的 AOT 缓存

→ 详见 JIT 编译

33、逃逸分析能保证对象在栈上分配吗？

一句话：不能，而且 HotSpot 根本没有真正的栈上分配。逃逸分析发现对象不逃逸后，做的是标量替换（把对象拆成局部变量）和去掉不必要的锁。

  • 逃逸分析依赖内联：对象传给一个没被内联的方法，就算逃逸
  • 分析太复杂、或对象必须作为整体存在时，JIT 会放弃，对象照样在堆上分配
  • 准确说法：不逃逸的对象「有机会」被拆掉，从而不在堆上分配

→ 详见 JIT 编译

34、方法内联有什么好处和代价？

一句话：内联就是把被调方法的代码直接抄到调用处。好处是省掉调用开销，还能给后续优化（逃逸分析、常量折叠等）提供更多上下文；代价是机器码变大。

  • 默认只内联小方法：普通方法 35 字节以内，热点方法 325 字节以内
  • 接口或可被重写的方法：实际只出现过 1～2 种类型时能内联，3 种及以上通常不内联
  • 内联时的假设失效（比如加载了新子类），会退回解释执行
  • 实践：热点路径上的方法写短一点，别让一个调用点对应太多实现类

→ 详见 JIT 编译

七、JVM 调优与排查

35、JVM 常用参数有哪些？

一句话：按堆、栈、元空间、收集器、诊断几类来记。

  • 堆：-Xms / -Xmx 设初始和最大堆，服务端设成一样；容器里用 -XX:MaxRAMPercentage 按比例设
  • 栈：-Xss 设每个线程的栈大小，Linux 默认 1MB
  • 元空间 / 直接内存：-XX:MaxMetaspaceSize 建议显式写上限；-XX:MaxDirectMemorySize 默认约等于最大堆
  • 收集器：-XX:+UseG1GC / -XX:+UseZGC，G1 用 -XX:MaxGCPauseMillis 设停顿目标
  • 诊断：-XX:+HeapDumpOnOutOfMemoryError 加 -XX:HeapDumpPath 保留 OOM 现场，-Xlog:gc* 打 GC 日志

→ 详见 GC 调优

36、如何确定堆内存大小？-Xms 和 -Xmx 为什么推荐设成相同？

一句话：先测出 Full GC 后老年代稳定剩下多少（活跃数据量），G1 给它的 3～4 倍，ZGC 至少 4 倍；-Xms 和 -Xmx 设成一样，避免运行中堆反复扩缩。

  • 活跃数据量从 GC 日志或 jstat -gc 里看 GC 后的老年代占用
  • 堆在两个值之间扩缩时，会多做 GC、向系统申请或归还内存，带来停顿抖动
  • 设成一样也让容量规划更直观

→ 详见 GC 调优

37、容器中如何设置 JVM 内存？为什么会被 OOMKilled？

一句话：用 MaxRAMPercentage 按容器内存的比例设堆（通常 50%～75%），给堆外留足空间。OOMKilled 是整个进程内存超过容器限制被系统杀掉，不是 JVM 的 OOM。

  • 默认比例只有 25%，偏保守；显式写了 -Xmx 时这个比例不生效
  • 堆外还有元空间、直接内存、线程栈、JIT 代码缓存等，都算容器内存，要设上限
  • 确认 OOMKilled：kubectl describe pod 看到 Reason: OOMKilled、退出码 137
  • 小配额容器（CPU < 2 或内存 < 1792MB）默认会选 Serial，要显式指定收集器

→ 详见 GC 调优、JVM 层性能策略

38、jcmd 和 NMT 能做什么？

一句话：jcmd 是 JDK 9 之后首选的诊断工具，jstack、jmap、jinfo 能干的它基本都能干，还能控制 JFR 录制。NMT 统计 JVM 自己用的堆外内存，用来查「进程内存远大于 -Xmx」。

  • 常用：jcmd <pid> Thread.print 看线程栈，GC.heap_dump 导堆，GC.heap_info 看堆概况，VM.flags 看生效参数
  • GC.class_histogram 看哪类对象最多，但会触发一次 Full GC
  • NMT：启动加 -XX:NativeMemoryTracking=summary，先 VM.native_memory baseline，过一阵再 summary.diff 看哪块在涨
  • NMT 统计不到第三方本地库自己申请的内存

常见坑：容器里 attach 失败，多半是执行用户或 /tmp 目录和目标进程不一致，进容器内执行即可。

→ 详见 诊断工具

39、如何排查 CPU 100% 问题？

一句话：top 找进程 → top -H -p <pid> 找最忙的线程 → 线程号转十六进制 → 在 jstack 输出里按 nid 找到它的调用栈。

printf "%x\n" <tid>                              # 线程号转十六进制
jstack <pid> | grep "nid=0x<hex>" -A 30
  • 常见原因：死循环、自旋、频繁 GC、正则回溯、大量序列化或加解密
  • 最忙的是 GC 线程就去看 GC 日志；是 JIT 编译线程多半是启动期的短暂现象
  • 隔几秒多抓几次，确认一直卡在同一处；Arthas thread -n 3 一步就能定位

常见坑：以为死锁会导致 CPU 高；死锁线程是挂起的，不耗 CPU，表现是接口没响应。

→ 详见 JVM 故障排查

40、如何排查内存溢出问题？线上能开 -XX:+HeapDumpOnOutOfMemoryError 吗？

一句话：先看 OOM 消息确定是哪块内存，堆 OOM 就拿 heap dump 用 MAT 找泄漏。HeapDumpOnOutOfMemoryError 线上推荐开启，它是事后分析的关键证据。

  • 用 jstat -gcutil 看 GC 后老年代是否持续上涨，区分泄漏和内存不够
  • MAT 里先看 Leak Suspects，再看谁占内存最多（Dominator Tree），最后查它被谁引用着（Path to GC Roots）
  • 为什么线上要开：导出 dump 会停顿、要占磁盘，但 OOM 时服务本来就不可用了，没有 dump 就无从分析
  • 配合 -XX:+ExitOnOutOfMemoryError 让进程直接退出、由 K8s 重启；容器里 dump 目录要挂持久卷

→ 详见 JVM 故障排查

41、如何排查频繁 Full GC？

一句话：先从 GC 日志里看 Full GC 是什么原因触发的，再对症处理；GC 后老年代降不下来，优先怀疑内存泄漏。

  • 内存泄漏：heap dump + MAT 找引用链
  • 堆太小、活跃数据接近老年代容量：按活跃数据的 3～4 倍扩堆
  • 对象过早进入老年代：调大年轻代或 Survivor
  • 元空间不够（日志里是 Metadata GC Threshold）：调大上限，查是不是动态生成了大量类
  • 有人调 System.gc()：找到调用方，或加 -XX:+ExplicitGCInvokesConcurrent

→ 详见 GC 调优

八、Java 内存模型（JMM）

42、JMM 是什么？解决了什么问题？

一句话：JMM 是 Java 规范里的一套规则，规定一个线程的写操作什么时候、在什么条件下能被其他线程看到，屏蔽不同 CPU 和编译器的差异，解决可见性、原子性、有序性问题。

  • 抽象模型：共享变量放在主内存，每个线程有自己的工作内存（对应 CPU 缓存、寄存器）
  • 对开发者的承诺：只要正确同步（volatile、锁、final），程序就像按顺序执行一样
  • 不要和 JVM 内存结构（堆、栈）混淆：一个讲并发规则，一个讲内存怎么划分

→ 详见 Java JMM 内存模型

43、happens-before 的 8 条规则是什么？

一句话：A happens-before B 的意思是：A 的结果对 B 可见，而且在 B 看来 A 排在前面。它不等于 A 在时间上先执行。

  • 程序顺序：同一线程里，前面的操作 hb 后面的
  • 锁：解锁 hb 之后对同一把锁的加锁；volatile：写 hb 之后对同一变量的读
  • 线程启动：start() hb 新线程里的所有操作；线程终止：线程里的所有操作 hb 别人从 join() 返回
  • 中断：interrupt() hb 被中断线程发现中断；终结：构造函数结束 hb finalize() 开始
  • 传递性：A hb B、B hb C，则 A hb C

→ 详见 Java JMM 内存模型

44、volatile 能保证原子性吗？适合什么场景？

一句话：不能。volatile 保证可见性和禁止重排序，但 count++ 这种「读-改-写」三步操作仍然不是原子的。

  • 实现：编译器和 JIT 在 volatile 读写前后插入内存屏障（阻止重排序的指令），并且每次都真正去读写这个变量，不缓存在寄存器里
  • 适合：状态标志（volatile boolean running）、一写多读的配置、DCL 单例里的实例引用
  • 需要原子性时用 AtomicInteger / LongAdder，或加锁

→ 详见 Java JMM 内存模型

45、为什么 DCL 单例需要 volatile？不加会有什么问题？

一句话：instance = new Singleton() 分三步：分配内存、执行构造器、把地址赋给变量，后两步可能被调换。不加 volatile，别的线程可能拿到一个不为 null 但构造器还没跑完的对象。

private static volatile Singleton instance;   // 关键在 volatile
// getInstance()：if (instance == null) { synchronized (Singleton.class) { if (instance == null) instance = new Singleton(); } }
  • 第一次检查是无锁的快速路径，第二次检查防止重复创建
  • 更简单的替代：静态内部类单例（JVM 保证类只初始化一次）、枚举单例

→ 详见 Java JMM 内存模型

46、synchronized 除了互斥，还有什么内存语义？

一句话：还保证可见性和有序性：前一个线程在锁里做的所有修改，下一个拿到同一把锁的线程一定能看到。

  • 对应 happens-before 的锁规则：解锁 hb 之后对同一把锁的加锁
  • 锁里的代码不会被重排序到锁外面
  • 所以 synchronized 同时提供原子性、可见性、有序性

→ 详见 Java JMM 内存模型

47、final 字段的内存语义是什么？

一句话：其他线程只要拿到了对象引用，就一定能看到它的 final 字段初始化之后的值；普通字段没有这个保证。

  • 原理：构造函数里对 final 字段的写，不会被重排到「把对象引用交出去」之后
  • 前提：构造过程中 this 没有泄露出去（没在构造函数里把 this 交给别人）
  • 这是 String 这类不可变对象不用加锁就能安全共享的基础

→ 详见 Java JMM 内存模型

九、虚拟线程

48、虚拟线程和平台线程的区别？

一句话：平台线程和操作系统线程一一对应，很重，只能开几千个，所以要池化；虚拟线程（JDK 21 正式）由 JVM 调度，很多个虚拟线程轮流跑在少量平台线程上，可以开到百万级，不需要池化。

  • 底层的平台线程叫载体线程，数量默认约等于 CPU 核数
  • 提升的是阻塞型任务的吞吐量，不是单个任务的速度
  • 对下游的并发限制改用 Semaphore 或连接池控制
  • 创建：Executors.newVirtualThreadPerTaskExecutor()；Spring Boot 3.2+ 配 spring.threads.virtual.enabled=true

→ 详见 虚拟线程

49、虚拟线程的挂载/卸载（mount/unmount）机制是什么？

一句话：虚拟线程运行时「挂」在某个载体线程上；遇到阻塞（IO、sleep、等锁）时，JDK 把它的调用栈存到堆上并「卸」下来，载体线程去跑别的虚拟线程；等阻塞结束，再挂到任意一个空闲载体线程上继续跑。

  • JDK 把 Socket IO、j.u.c 锁、sleep 等阻塞点都改造过了，业务代码写法不用变
  • 恢复时不是一次把整个栈拷回来，只先拷顶上几帧，用到再拷
  • 卸不下来的情况叫钉住（pinning），见第 51 题

→ 详见 虚拟线程

50、虚拟线程为什么不适合 CPU 密集型任务？

一句话：虚拟线程的好处来自「阻塞时让出载体线程」；CPU 密集型任务不阻塞，一直占着载体线程，而载体线程数约等于核数，开再多虚拟线程也不会更快。

  • 还会让同一调度器上的 IO 型虚拟线程排队等待
  • CPU 密集型任务仍用固定大小的平台线程池或 ForkJoinPool

→ 详见 虚拟线程

51、虚拟线程中使用 synchronized 有什么问题？如何解决？

一句话：JDK 21～23 里，虚拟线程在 synchronized 块里阻塞或调 wait() 会钉住载体线程，钉住的多了载体线程就不够用；这些版本上把锁内会阻塞的代码改成 ReentrantLock。JDK 24 起已修复，不用再改。

  • JDK 24+ 仍会钉住：本地代码（JNI / FFM）回调 Java 后在其中阻塞、类初始化时阻塞
  • 诊断：JFR 事件 jdk.VirtualThreadPinned（默认开启）、jcmd <pid> Thread.dump_to_file -format=json
  • 虚拟线程数量巨大，用 ThreadLocal 缓存大对象会放大内存；传上下文优先用 JDK 25 的 ScopedValue

→ 详见 虚拟线程
