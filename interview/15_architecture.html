系统架构面试题解答

题目清单见 系统架构面试题；细节见 系统架构总览。微服务拆分、网关、链路追踪的题目见 微服务面试题解答 与 Spring Cloud 面试题解答，系统设计题见 业务场景面试题解答。

版本基线：JDK 21 / 25、Spring Boot 4（Spring Framework 7、Spring Security 7）、MySQL 8.4 LTS、Redis 8.x、RocketMQ 5.x、AWS SDK for Java 2.x、MyBatis-Plus 3.5.x。

一、架构模式

Q1：分层架构、整洁架构、六边形架构有什么区别？

一句话：三者都在分离关注点，区别在依赖方向。传统分层是业务层依赖持久层，业务规则被表结构和 ORM 绑住；整洁架构和六边形架构都要求「业务核心不依赖技术细节」，由内层定义接口、外层实现。

  • 分层架构：表现层 → 业务层 → 持久层，简单直接，业务复杂后容易变成贫血模型 + 事务脚本
  • 整洁架构：依赖只能从外层指向内层（Entities ← Use Cases ← Adapters ← Frameworks）
  • 六边形架构：强调内外对称，驱动端（Controller、MQ 消费者）调用入站端口，被驱动端（数据库、第三方）实现出站端口
  • 收益：不启动 Spring 也能对业务规则做单元测试，换数据库或 MQ 只改适配器
  • 规则简单的 CRUD 系统用分层架构就够了，不必为模式而模式

→ 详见 架构模式与风格

Q2：CQRS 适用于什么场景？读模型延迟怎么处理？

一句话：CQRS 把写模型（领域模型，保证业务规则）和读模型（为查询优化的宽表、ES 索引）拆开。它的主要动机是读写模型差异大，而不是读多写少。

  • 适用：查询要跨多个聚合或服务拼装、需要全文检索和多维筛选、不同查询方需要不同形态的视图
  • 单纯读多写少，先用缓存和读写分离解决
  • 写侧：事件和业务数据在同一事务写进 Outbox，不要在 handler 里直接发 MQ
  • 读模型最终一致：命令返回后前端先展示结果；关键页面按 ID 回读写库；或返回版本号，查询时等读模型追上
  • 投影器要幂等（版本号条件更新）、可重建（重放事件或全量回灌）

→ 详见 架构模式与风格

Q3：事件溯源是什么？快照和事件版本演进怎么做？

一句话：不存当前状态，只追加存储导致状态变化的全部事件，当前状态靠按顺序重放得到；适合账务、交易流水这类需要完整审计追溯的领域，和「数据量大」无关。

  • 快照：每 N 个事件存一份快照，加载时从最近快照开始重放
  • 版本演进：事件写入后不能改，新增版本号，读旧事件时用 upcaster 转成新结构
  • 并发控制：按 expectedVersion 追加，版本已变就拒绝，调用方重新加载后重试
  • 查询必须配合 CQRS 投影读模型；Kafka 适合分发事件，不适合当事件存储（难以按聚合读取、没有按版本的乐观写）
  • apply 只改状态、不能有副作用，因为重放时会反复执行

→ 详见 架构模式与风格

Q4：冷热数据如何分离？为什么不能双写 MQ？DROP PARTITION 能直接归档吗？

一句话：最常用的是定时任务按主键游标分批归档（插入归档表 → 删除已归档的行，每批一个短事务）；写入量大、冷库要近实时时，订阅 binlog 做 CDC 归档。

  • 只归档终态数据，还可能被修改的数据迁走后更新会找不到行
  • 冷库在另一个系统时没法共用事务：先幂等写冷库、校验后再删热库
  • 业务同时写库和写 MQ 是双写，任一边失败就丢数据；可靠做法是 CDC 读 binlog，或同事务写 Outbox
  • DROP PARTITION 是直接删除，不是归档；先 EXCHANGE PARTITION（或导出）、校验，再删
  • 分区表用 RANGE COLUMNS(created_at)，复合表达式做不了分区裁剪

→ 详见 数据冷热分离

Q5：客户端直传对象存储怎么设计？MinIO 现在还能用吗？

一句话：文件不经过应用服务，业务服务只负责鉴权、签发预签名 URL、记录元数据；客户端直接 PUT 到对象存储，完成后由事件通知或回调确认。

  • 预签名 URL 最长 7 天，上传 URL 建议 5~15 分钟；限制大小区间用 POST Policy 或带策略的 STS 凭证
  • 大文件：服务端发起 Multipart Upload，为每个分片签发预签名 URL，最后服务端 Complete
  • 孤儿对象：未确认的上传先放 tmp/ 前缀，由生命周期规则定期清理
  • MinIO 社区版：2021 年改 AGPLv3，2025 年停止发布二进制与镜像并进入维护模式，仓库已归档；新项目优先云对象存储，自建可评估 Ceph RGW、SeaweedFS 等
  • 业务代码只依赖 S3 协议，换存储只改配置

→ 详见 对象存储、自建选型与 MinIO 现状

Q6：主数据变更如何可靠分发、防止下游乱序？

一句话：审批事务里同时写 Outbox，由投递任务发 MQ；事件带完整快照和版本号，下游按版本号只接受更新的数据。

  • 事件携带 objectCode、version 和变更后的完整快照，而不是差异，重复处理结果不变
  • 以 objectCode 作为消息 key，同一主数据进同一个分区，减少乱序
  • 顺序消息只能降低乱序概率；可靠的是下游 upsert 时比较版本号，旧版本不覆盖新数据
  • 缓存在提交后删除并带 TTL；唯一性由数据库唯一索引保证，不靠应用层先查后插

→ 详见 主数据系统设计

二、DDD

Q7：DDD 的核心概念有哪些？

一句话：战略设计划边界（子域、限界上下文、上下文映射），战术设计建模型（实体、值对象、聚合、领域服务、仓储、领域事件），统一语言贯穿始终。

概念说明
限界上下文模型和术语的边界，同一个词在不同上下文含义不同
实体 / 值对象实体按标识判等、状态可变；值对象按属性判等、不可变（适合 record）
聚合根一组需要一起保持一致的对象的唯一入口，保护业务不变量
领域事件「订单已支付」这类业务事实，驱动跨聚合、跨上下文的后续动作
仓储以聚合为单位持久化，接口在 domain 层、实现在 infrastructure 层
  • 子域：核心域重点建模，支撑域够用即可，通用域优先采购或用开源

→ 详见 DDD 领域驱动设计

Q8：聚合设计有哪些原则？一个事务能改多个聚合吗？

一句话：聚合尽量小、通过 ID 引用其他聚合、一个事务只修改一个聚合，聚合之间用领域事件达到最终一致。

  • 在边界内保护真正的不变量，如「订单总额等于明细之和」「已支付订单不能改明细」
  • 大聚合并发冲突多、加载慢；多数聚合只有根实体加几个值对象
  • 聚合根不暴露 setter，不把内部可变集合直接交出去，状态变化走表达业务意图的方法
  • 转账要改两个账户：同库强一致时可以有意识地在一个本地事务里改（按 ID 顺序加锁）；跨库跨服务就引入「转账单」聚合，用事件或 Saga

常见坑：实体只重写 equals 不重写 hashCode，放进 HashSet 就出错；标识要在创建时确定，不要等自增回填。

→ 详见 DDD 领域驱动设计

Q9：贫血模型和充血模型有什么区别？领域服务和应用服务怎么分？

一句话：贫血模型的实体只有 getter / setter，规则堆在 Service 里成了事务脚本；充血模型把规则放回实体和聚合根。应用服务编排用例，领域服务承载不属于单个实体的业务规则。

对比应用服务领域服务
职责编排用例、事务边界、权限校验跨多个聚合的业务判断
是否含业务规则不含含
依赖仓储、领域服务、外部端口只依赖领域对象和端口接口
  • 远程调用不要放进数据库事务：先在事务外查询组装，再开短事务写入
  • 领域对象不注入 Spring Bean，需要外部能力时由应用层或领域服务通过接口传入

→ 详见 DDD 领域驱动设计

Q10：限界上下文和微服务是什么关系？防腐层做什么？

一句话：限界上下文是模型和语言的边界，常常是微服务拆分的候选边界，但不是一一对应：一个上下文可以拆成多个服务，一个模块化单体里也可以有多个上下文。

  • 上下文之间的集成方式：合作关系、共享内核、客户-供应商、跟随者、防腐层、开放主机服务 / 发布语言、各行其道
  • 防腐层（ACL）：在 infrastructure 层把上游 DTO 转换成本上下文的值对象，防止上游模型污染自己
  • 上游是遗留系统、第三方或模型不稳定时，优先用防腐层
  • 上下文映射也反映团队关系：上游不配合时下游只能跟随或加防腐层

→ 详见 DDD 领域驱动设计

Q11：领域事件如何可靠投递？为什么不能在 Repository.save() 里发 MQ？

一句话：save() 仍在事务内，在这里或事务里发 MQ，事务回滚后下游却已收到事件；提交后再直接发，又可能在发送前崩溃丢事件。可靠做法是 Transactional Outbox。

  • 流程：聚合收集事件 → 应用服务在同一本地事务保存聚合并写 Outbox 表 → 提交后由投递任务（轮询或 CDC）发 MQ → 下游幂等消费
  • 同上下文内、允许丢失的动作（发站内信、刷本地缓存）可以用 @TransactionalEventListener(phase = AFTER_COMMIT)
  • 跨上下文、不能丢的事件一律走 Outbox 或 RocketMQ 事务消息
  • 事件要带事件 ID、聚合 ID 和发生时间，消费方按业务键去重

→ 详见 DDD 领域驱动设计

Q12：DDD 在 Spring Boot 项目里怎么落地？什么项目不适合？

一句话：按 interfaces / application / domain / infrastructure 四层组织，domain 层不依赖其他层和框架；业务规则简单的 CRUD 系统用分层架构即可，不必上 DDD。

  • interfaces：Controller、MQ 消费入口、DTO 转换
  • application：用例编排、事务边界，不写业务规则
  • domain：实体、值对象、聚合、领域服务、仓储接口、领域事件
  • infrastructure：仓储实现、防腐层、Outbox 投递
  • 起步方式：先和业务专家梳理统一语言与上下文（如事件风暴），从核心域、从模块化单体开始

常见坑：Repository 返回 PO、Service 直接改实体字段、一个聚合几十个字段，都是「名义 DDD」。

→ 详见 DDD 领域驱动设计

三、幂等设计

Q13：什么是幂等？哪些 HTTP 方法天然幂等？

一句话：同一个请求执行一次和执行多次，对系统状态的影响相同。HTTP 规范里 GET、HEAD、OPTIONS、PUT、DELETE 是幂等的，POST、PATCH 不是；但这只是协议约定，实现不会自动幂等。

方法安全（不改状态）幂等
GET / HEAD / OPTIONS是是
PUT / DELETE否是
POST / PATCH否否
  • 重复请求的来源：用户重复点击、超时重试（超时不等于失败）、MQ 重投、支付渠道重推、定时任务重复触发
  • 能用「设为某值」就不用「增加某值」；客户端能确定资源 ID 时用 PUT /orders/{requestNo} 代替 POST

→ 详见 幂等设计

Q14：接口幂等如何设计？按操作类型怎么选方案？

一句话：以数据库为最终防线：插入用业务键唯一约束，更新用条件更新（状态机、版本号），消费用「去重记录与业务写入同一本地事务」，提交类用请求号写进唯一列。

操作类型首选方案
插入（建单、支付流水）业务键唯一约束，冲突返回首次结果
更新（状态流转、扣减）WHERE status = 旧状态 条件更新，按影响行数判断
消费（MQ、回调、事件）同事务去重记录 + 唯一约束
提交（表单）请求号写进业务表唯一列
  • 幂等键用业务唯一键（订单号 + 动作），不用 MQ 的 msgId，重发、补发时 msgId 会变
  • 优先级：唯一约束 / 同事务去重 > 条件更新 > 请求号与 Token > Redis 状态机（加速层）
  • 冲突时返回首次结果，调用方才能放心重试

→ 详见 幂等设计

Q15：用 Redis SETNX 做幂等有什么问题？正确写法是什么？

一句话：「SETNX 成功就处理、失败就当重复跳过」，一旦业务抛异常或进程崩溃，占位还在，之后的重试和重投都被当成「已处理」跳过，请求就丢了。

  • 正确做法一：去重记录和业务结果在同一本地事务提交，靠唯一约束兜底；业务失败回滚，去重记录也不存在，可以重试
  • 正确做法二：Redis 状态机，SET key PROCESSING NX EX <短TTL> → 成功后改为 DONE 并设长 TTL → 失败时删除 key
  • 看到 PROCESSING 只能返回「处理中」（HTTP 409 / MQ 不确认等重投），不能当作成功
  • 更严格时占位值带 UUID，完成和释放用 Lua 比较后再改写
  • Redis 与数据库不是原子的，业务层仍要唯一约束或条件更新兜底

→ 详见 幂等设计、消息队列面试题解答

Q16：Token 防重复提交有什么局限？Idempotency-Key 请求头怎么用？

一句话：经典 Token 是打开页面领 Token、提交时 Lua 原子「校验并删除」。它在校验时就被删掉，之后业务失败用户重试会被拒；并发重复请求拿到的是报错而不是首次结果。生产上更推荐把请求号写进业务表唯一列。

  • Idempotency-Key（IETF 草案，Stripe 等支付 API 的做法）：客户端为每个逻辑请求生成唯一值，重试时原样带上
  • 服务端按「调用方 + key」记录请求指纹和首次响应，重复请求直接返回首次响应
  • 同 key 不同请求体返回 422；首次请求还在处理中返回 409；必须带 key 却没带返回 400
  • key 设保留期（如 24 小时）并写进接口文档；前端按钮置灰只是体验优化，不是防线

→ 详见 幂等设计

Q17：支付回调如何保证幂等？分布式锁能保证幂等吗？

一句话：支付回调靠支付单的状态条件更新（WAITING → SUCCESS 只会成功一次）加支付流水号唯一约束；分布式锁只把并发请求串行化，不记录「做没做过」，单独用不能保证幂等。

  • 先验签，再校验金额、商户号与本地一致，事务提交后才给渠道应答成功
  • 后续动作（发货、积分）通过 Outbox 事件触发，回调里只做校验和落库
  • 订单已取消后才收到支付成功，不能忽略，要走退款或人工处理
  • 回调可能不来：定时主动查单，与回调走同一个幂等入口
  • 锁会因租约过期失效，锁内仍要有条件更新作为真正的判断

→ 详见 幂等设计、订单

四、访问控制

权限模型对比（RBAC / ABAC / ReBAC / ACL）与数据权限拦截见 安全面试题解答 Q14、Q16；正文见 权限模型：RBAC 与 ABAC、权限系统架构设计。

Q18：鉴权放在网关还是服务？权限变更后如何及时生效？

一句话：网关负责认证和粗粒度授权（URL、角色），服务负责细粒度授权和数据权限；权限数据必须缓存，难点是变更后多快生效。

  • 网关把用户标识透传给下游前，必须先删除客户端自带的同名 Header，防止伪造
  • 服务间调用不能默认内网可信：透传用户 Token，或用服务身份（Client Credentials / mTLS）
  • 常见折中：JWT 只放 userId 和角色，权限码放 Redis / 本地缓存
  • 刷新：改权限后主动删缓存或广播失效，TTL 兜底；或用权限版本号，不一致就重新加载
  • 改一个角色的权限要失效所有持有该角色的用户，用户多时按角色维度缓存

→ 详见 权限系统架构设计；Token 刷新与吊销见 JWT 令牌机制
