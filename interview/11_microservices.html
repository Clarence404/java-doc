微服务面试题解答

2026/10/9大约 17 分钟

微服务面试题解答

题目清单见 微服务面试题，模块入口见 微服务总览；Nacos、网关、Feign、Sentinel、Seata 等组件题见 Spring Cloud 面试题解答，熔断限流策略见 高可用面试题解答。

版本基线：Istio 1.24+、Dubbo 3.3、Spring Cloud 2025.1.x。

一、拆分与演进

Q1：微服务和单体架构各有什么优缺点？什么时候该拆分？

一句话：微服务用「分布式的麻烦」换来「各自发布、各自扩容、故障隔离」。没有「多少人就该拆」的硬标准，一般先用单体把业务跑通、边界看清，再按需拆。

对比单体微服务
开发调试简单，本地调用网络调用会超时、失败
发布改一行也要整体发布按服务单独发布
扩容只能整体扩只扩热点服务
一致性本地事务要靠 Saga、Outbox 等最终一致方案
  • 该拆的信号：多个团队抢同一个发布窗口、模块迭代节奏差别大、个别模块要单独扩容
  • 先别拆的信号：业务边界还模糊、团队小、容器化和监控等基础设施没跟上（先在单体内做模块化）

→ 详见 微服务优势与挑战

Q2：微服务和 SOA 的区别是什么？

一句话：微服务可以看成「轻量版 SOA」：去掉企业服务总线（ESB）和重协议，服务拆得更细，每个服务自己管数据。

对比SOA微服务
通信ESB 总线 + WS-* 重协议HTTP / gRPC / MQ，逻辑放在服务里，管道只负责传输
粒度粗，面向系统集成细，一个业务能力一个服务
数据常共享数据库每个服务独立存储
目标跨系统复用快速迭代、独立交付

→ 详见 微服务优势与挑战

Q3：微服务拆分的原则是什么？如何避免过度拆分和「分布式单体」？

一句话：按业务边界拆（DDD 里的限界上下文，就是「一块业务说同一套话」的范围），每个服务职责单一、数据独占。最怕拆成「分布式单体」：服务分开了，却还得一起发布、一起出故障。

  • 不要按技术分层拆（controller 服务、dao 服务）
  • 一个服务一个库，禁止多个服务读写同一张表
  • 好的拆分：一个需求通常只改一个服务；一个需求要改五个服务还得按顺序发布，就是拆错了
  • 防过度拆分：服务数量和团队维护能力匹配；总是一起改的模块不要拆开

→ 详见 微服务设计模式、DDD 领域驱动设计

Q4：如何把单体迁移到微服务？绞杀者模式怎么做？

一句话：一点点迁，不推倒重写。新功能直接做成新服务；老功能用绞杀者模式逐个搬出去，像藤蔓一点点包住老树。

  • 第 1 步：单体前面加一个网关，所有流量先走网关（先只做转发）
  • 第 2 步：挑一个模块抽成新服务，网关把这部分路由切过去；出问题切回单体即可回滚
  • 第 3 步：新服务稳定后删掉单体里的旧代码，重复直到单体下线
  • 先抽：变化频繁、边界清楚、耦合少的模块
  • 数据迁移最难：先让新服务通过接口读写老数据，再双写或用 CDC（监听数据库变更日志）同步到新库，最后断开旧表

→ 详见 微服务优势与挑战

二、通信与 RPC

Q5：客户端服务发现与服务端服务发现有什么区别？

一句话：客户端发现是调用方自己去注册中心拿实例列表、自己挑一个直连（Nacos + LoadBalancer、Dubbo）；服务端发现是调用方只访问一个固定地址，由平台转发（Kubernetes Service、服务网格）。

对比客户端发现服务端发现
谁做负载均衡调用方进程内平台或代理
多语言每种语言要有 SDK与语言无关
网络跳数直连，少一跳多一次转发
  • 注册中心不在调用路径上：它短暂故障时，调用方用本地缓存的列表照样能调

→ 详见 微服务设计模式

Q6：服务间同步调用与异步消息怎么选？

一句话：要马上拿到结果就同步调用；能晚点处理、要削峰、一个事件有多方关心，就用消息队列。常见组合是核心链路同步、非核心链路异步。

  • 同步例子：下单时要立刻知道库存扣没扣成功
  • 异步例子：下单后发积分、发通知、做统计
  • 同步要注意：每次调用都设超时，调用链别太深
  • 异步要注意：消息可靠投递、重复消费要幂等（同一消息处理多次结果一样）、最终一致

→ 详见 微服务设计模式、消息队列基础

Q7：gRPC、Dubbo 与 HTTP（REST）分别适合什么场景？

一句话：对外、给浏览器和第三方用 REST；内部调用量大、要流式或多语言用 gRPC；Java 为主、想要框架自带治理用 Dubbo。性能差距只在调用量大、消息体大时才明显，选型更看团队熟悉度和维护成本。

对比RESTgRPCDubbo 3
接口定义URL + DTO.proto 文件生成代码Java 接口 jar
浏览器直接调可以需要转换Triple 协议可以
服务治理靠 Spring Cloud 组件靠网格或自建框架自带

常见坑：gRPC 用长连接，四层负载均衡只在建连时分配一次，请求会全落在一台上，要按请求做均衡。

→ 详见 服务通信、RPC 协议

三、服务网格与 Dubbo

Q8：什么是服务网格？istiod 负责什么，控制面与数据面如何分工？

一句话：服务网格把重试、熔断、加密、监控这些通信能力从业务代码里拿出来，交给和服务一起部署的代理去做。好处是和语言无关、改配置不用发版；代价是多一层代理和一套要运维的控制面。

  • 控制面 istiod：从 Kubernetes 读服务信息，把路由和安全规则翻译成代理配置下发；还当证书机构，给每个服务发证书
  • 数据面：真正转发流量的代理（Sidecar 模式是每个 Pod 一个 Envoy；Ambient 模式是 ztunnel + waypoint），负责路由、负载均衡、加密和监控数据
  • 早期的 Pilot、Citadel、Galley 已合并成 istiod，按功能理解即可

→ 详见 服务网格

Q9：Istio 的 Sidecar 模式与 Ambient 模式有什么区别？ztunnel 与 waypoint 各做什么？

一句话：Sidecar 模式给每个 Pod 塞一个代理，什么都在 Pod 里做；Ambient 模式（1.24 起正式可用）业务 Pod 里没有代理，把工作拆给两类组件。

  • ztunnel：每个节点一个，负责四层的事——加密（mTLS）、身份、按身份授权
  • waypoint：可选，按命名空间或服务部署，负责七层的事——HTTP 路由、重试、按路径授权
对比SidecarAmbient
资源开销随 Pod 数量增长每节点一个 ztunnel，七层按需部署
接入、升级要重启业务 Pod打标签就接入，升级不重启业务
七层能力默认就有部署 waypoint 后才有
适合每个服务都要完整治理主要为了加密 / 零信任、想省资源

→ 详见 服务网格

Q10：为什么 VirtualService 的路由规则顺序很重要？

一句话：VirtualService 的路由规则从上往下匹配，第一条命中就生效。精确规则（比如按请求头去灰度版本）要写在前面，兜底规则放最后。

  • 写反了：兜底规则会接走所有请求，后面的灰度规则永远不生效
  • 对比：Kubernetes Gateway API（HTTPRoute）按规则的精确程度排优先级，不看书写顺序

→ 详见 服务网格

Q11：Istio 如何实现 mTLS？SPIFFE 身份是什么？网格下的链路追踪是零侵入的吗？

一句话：istiod 给每个服务发短期证书并自动更换，代理之间自动加密互认（mTLS，双方都验对方证书），业务代码不用改。

  • SPIFFE 身份：证书里写的服务身份，形如 spiffe://cluster.local/ns/production/sa/order-service，绑定的是 Kubernetes ServiceAccount 而不是 IP
  • 有了身份就能用 AuthorizationPolicy 规定「谁能调谁」
  • 平滑接入：先用 PERMISSIVE（明文和加密都收），全部接好后切 STRICT
  • 链路追踪不是完全零侵入：代理只看到单次请求，应用要把收到的追踪头转发到下游请求上；Spring Boot 接入 Micrometer Tracing 后自动处理

→ 详见 服务网格、零信任架构

Q12：服务网格与 Spring Cloud 如何选？组合使用时要注意什么？

一句话：纯 Java、要按业务参数做治理（比如按商品 ID 限流）选 Spring Cloud；多语言、全面上了 Kubernetes、有专门平台团队选 Istio。

对比Spring CloudIstio
实现依赖库，在业务进程里进程外代理，业务无感
性能无额外转发每次调用多过一层代理
治理粒度能到方法和业务参数只认路径、请求头、身份
运维门槛低高

常见坑：一起用时同一能力两边都开，比如重试两边都配，重试次数会相乘。网格管加密和统一监控，SDK 管业务级治理。

→ 详见 服务网格

Q13：Dubbo 的注册中心宕机为什么不影响已建立的调用？什么是应用级服务发现？

一句话：注册中心只是通讯录。消费方启动时把提供方地址缓存到本地，调用时直接和提供方长连接通信，不经过注册中心。所以它挂了，已有调用照常，只是感知不到新上线或下线的实例。

  • 应用级服务发现（Dubbo 3）：注册中心按「应用」登记实例，而不是按「每个接口」登记，注册和推送的数据量大大减少
  • 这样也和 Spring Cloud、Kubernetes 的「按应用 / 服务」模型对齐
  • 3.x 默认接口级和应用级都注册，兼容老消费方；全部升级后设 dubbo.registry.register-mode=instance 只留应用级

→ 详见 Dubbo

Q14：Triple 协议与 dubbo 协议有什么区别？

一句话：dubbo 协议是 TCP 上的私有协议，快但不好跨语言、过不了普通网关；Triple 是 Dubbo 3 推荐的协议，基于 HTTP、兼容 gRPC，curl 和浏览器都能直接调。

对比dubbo 协议Triple
传输私有 TCPHTTP/1.1、HTTP/2、HTTP/3
跨语言 / 网关差和 gRPC 互通，可放在 HTTP 网关后
流式调用不支持支持

常见坑：3.2 起默认严格检查序列化类，DTO 不实现 Serializable 会调用失败。

→ 详见 Dubbo

Q15：Dubbo 默认的 failover 为什么对写操作是陷阱？

一句话：默认的 failover 失败就换一台重试（默认再试 2 次）。但超时不等于失败，提供方可能已经执行成功、只是回得慢，重试就会重复扣款、重复下单。

  • 读接口：用默认 failover 没问题
  • 写接口、不幂等的接口：改成 failfast（失败立即报错，不重试），或者把幂等做好
  • 记日志这类旁路调用：failsafe（出错直接忽略）
  • 发通知这类：failback（失败后在后台重发）

→ 详见 Dubbo、幂等设计

Q16：Dubbo SPI 与 Java SPI 有什么区别？@Adaptive、@Activate 做什么？

一句话：Java 自带的 SPI（ServiceLoader）只能把所有实现全部加载出来遍历；Dubbo SPI 按名字取实现，用到哪个才创建哪个，还能自动注入依赖、自动套包装类。

  • @Adaptive：运行时根据调用参数里的配置，决定用哪个实现（比如按配置切换协议、负载均衡策略）
  • @Activate：按条件自动启用并排序，典型用法是过滤器链
  • Wrapper：自动包在实现外面的一层，统一加监听、过滤逻辑，类似 AOP
  • 协议、负载均衡、容错策略、过滤器、序列化都是通过 Dubbo SPI 装配的

→ 详见 Dubbo、SPI 机制

Q17：Dubbo 和 Spring Cloud 怎么选？

一句话：内部服务高频互调、看重性能、团队熟悉 Dubbo，选 Dubbo；对外接口多、跨语言、想跟紧 Spring Boot 新版本，选 Spring Cloud。也常混用：内部 Dubbo，对外 REST。

对比Dubbo 3Spring Cloud
通信RPC 长连接HTTP
接口约定Java 接口 jarHTTP 地址 + DTO
治理框架自带多个组件拼起来
Spring Boot 4目前基于 Boot 3.5，以官方发布为准已支持

→ 详见 Dubbo

四、微服务模式

Q18：BFF 是什么？和 API 网关有什么区别？

一句话：API 网关是所有客户端的统一大门，做鉴权、限流、路由这些通用的事；BFF（Backend for Frontend）是给某一类客户端专门做的接口层，比如 App 一个、Web 一个，负责合并请求、裁剪字段。

  • BFF 由对应的前端团队负责，只做拼装和适配，不放核心业务逻辑
  • 常见组合：网关在前做通用能力，后面按客户端类型分多个 BFF
  • 目的：避免一个「万能网关」被各端的需求拉扯

→ 详见 微服务设计模式

Q19：Database per Service 之后如何做跨服务查询？API Composition 还是 CQRS？

一句话：简单查询、数据量小用 API Composition——同时调几个服务、在内存里拼结果；要跨服务分页、排序、复杂筛选就用 CQRS——专门维护一份给查询用的数据（比如 ES 宽表），靠事件异步更新。

  • API Composition：实时、简单，但数据多了内存拼接扛不住
  • CQRS：查询灵活，代价是读到的数据会有短暂延迟
  • 「独占数据」指的是归属权：同一个 MySQL 实例上分不同库、只授权给对应服务也可以；但禁止多个服务直接读写同一张表

→ 详见 微服务设计模式、架构模式与风格

Q20：Outbox 模式如何保证「写库 + 发消息」的原子性？

一句话：在同一个本地事务里同时写业务表和一张「待发消息表」（outbox），事务提交两者就一起生效；再由单独的进程把待发消息发到 MQ，发成功就标记完成，失败就重试。

  • 为什么不能在事务里直接发 MQ：可能事务回滚了消息却已发出，或事务提交了消息却没发成功
  • 投递方式：定时扫 outbox 表（简单，但有延迟和数据库压力），或监听数据库变更日志（CDC，如 Debezium，延迟低）
  • 消息可能发多次，消费方要按业务键幂等
  • 用 RocketMQ 时也可以直接用它的事务消息

→ 详见 微服务设计模式、分布式事务

Q21：Saga 的编排式与协同式有什么区别？

一句话：Saga 把跨服务的大事务拆成一串本地事务，中途失败就倒着执行补偿。编排式有一个「总指挥」统一调度；协同式没有总指挥，各服务听事件自己往下走。

对比编排式协同式
控制协调者集中调度各服务监听事件自主推进
流程可见性清楚，好监控步骤多了难追踪
适合步骤多、补偿复杂步骤少

常见坑：Saga 没有隔离性，中间状态别人看得到，要靠「处理中」这类状态设计和补偿幂等兜底。

→ 详见 微服务设计模式、分布式事务

Q22：消费者驱动契约测试解决什么问题？

一句话：服务各自发布，提供方改了接口很容易把调用方搞坏；契约测试让调用方写下「我需要你返回什么」，提供方在 CI 里用它验证，一旦改坏就构建失败。

  • 比端到端测试便宜：不用把一堆服务都拉起来
  • 契约由调用方定义，所以叫「消费者驱动」
  • 常用工具：Spring Cloud Contract、Pact

→ 详见 微服务设计模式、契约测试

五、分布式场景

Q23：微服务之间的分布式事务如何处理？

一句话：能不用分布式事务就不用。优先用最终一致方案（Outbox、事务消息、Saga、对账补偿），只有必须同步拿到一致结果的链路才用 Seata 这类方案。

  • 下单后通知别的服务、允许短暂不一致：Outbox / 事务消息 + 幂等消费
  • 长流程、跨外部系统：Saga
  • 资金类、要先预留资源：TCC（先冻结，再确认或取消）
  • 普通数据库增删改、要同步一致、并发不高：Seata AT

→ 详见 分布式事务、分布式面试题解答

Q24：微服务接口如何实现幂等？

一句话：超时重试、MQ 重复投递、Dubbo 自动重试都会让同一个请求来好几次，所以写接口必须幂等。核心是给每次操作一个唯一标识，服务端按它去重。

  • 唯一索引（如订单号）：插入类操作，最简单可靠
  • 去重表，和业务写入放在同一个本地事务：MQ 消费、通用写接口
  • Token：先领一个 token，提交时删掉，删成功才处理，用于防表单重复提交
  • 状态机 / 乐观锁（WHERE status = ? 或版本号）：状态流转、扣减类操作
  • Redis SET NX：高并发快速判重，但要有数据库兜底

→ 详见 幂等设计、系统架构面试题解答

Q25：分布式接口请求的顺序性如何保证？

一句话：先想办法让业务不依赖顺序；真要顺序，也只要求同一业务键（如订单号）内有序：同一个键路由到同一处、实例内串行执行，最后在数据层用版本号兜底。

  • 能消掉就消掉：调用方等上一步成功再发下一步、把两次调用合成一个接口、同步全量状态而不是「减 20」这种增量指令
  • 路由：Dubbo 一致性哈希负载均衡、Nginx 按请求头哈希；异步场景改走 MQ，用业务键做分区键（顺序消息）
  • 实例内：按业务键哈希到固定数量的单线程队列，同一个键排队执行
  • 数据层兜底：请求带单调递增的序列号，UPDATE ... WHERE last_seq < ? 只接受更新的请求；状态流转再加前置状态条件

常见坑：用分布式锁保证顺序。锁只保证同一时刻一个请求在执行，不保证谁先拿到，后发的请求照样可能先执行。

→ 详见 微服务设计模式、消息队列基础

Q26：服务间如何传递认证信息与上下文（用户身份、灰度标记、traceId）？

一句话：都靠请求头一跳一跳往下传，每一跳都要转给下一跳，否则到第二跳就丢了。

  • 用户身份：网关验完令牌后，先删掉客户端自己带的同名请求头，再写入用户信息；或者原样转发 Authorization 让下游自己再验
  • 灰度标记：HTTP 客户端用拦截器加请求头；MQ 写进消息头；Dubbo 用 RpcContext 附带
  • traceId：Micrometer Tracing 自动加到请求头并写进日志 MDC

常见坑：请求上下文绑定在当前线程上，切到线程池或 @Async 后就拿不到了，要用 TaskDecorator 等方式手动带过去。
