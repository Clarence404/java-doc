开发总结-三高架构

精华提炼，细节详见 高性能 / 高并发 / 高可用

题目清单见 高性能面试题 · 高并发面试题 · 高可用面试题，本页按三份清单的分组与顺序作答，题号全页连续。锁、volatile、CAS、同步器、死锁等 Java 语言层并发题见 开发总结-Java 并发；缓存三大问题的实现细节见 开发总结-缓存。

三者关系：高性能关注单次请求有多快、多省（RT、资源效率）；高并发关注流量大时扛不扛得住（吞吐、扩展性）；高可用关注出故障时停不停服（冗余、隔离、自愈）。

一、高性能

1、指标与方法论

Q1：QPS、TPS、RT、并发数之间是什么关系？如何用 Little 定律估算所需线程数或连接数？

核心结论：稳态系统中 并发数 L = 到达速率 λ × 平均停留时间 W，即 并发数 = QPS × RT（秒）。TPS 是业务事务口径，一笔事务（如"下单"）内部可能包含多次请求。

已知推算
QPS = 2000，RT = 50ms系统内平均并发 = 2000 × 0.05 = 100
线程池 200 线程（全阻塞 IO），RT = 100ms理论最大 QPS ≈ 200 / 0.1 = 2000
QPS 1000，单次持有连接 20ms平均需要 1000 × 0.02 = 20 个连接，再留余量
  • "系统"可以是任意边界：整个服务、一个线程池、一个连接池
  • RT 上升直接吃掉容量：线程、连接固定时 RT 翻倍，可承载 QPS 减半；反过来降低 RT 等价于扩容
  • 只在稳态成立：到达速率超过处理能力时队列持续增长，出现压测中"QPS 不再上升、RT 陡增"的拐点

Q2：为什么不能只看平均响应时间？P99 和 P999 分别意味着什么？

核心结论：平均值会把少数极慢请求"摊平"，而用户感知和超时故障恰恰由长尾决定。P99 表示 99% 的请求快于该值，P999 表示 99.9% 的请求快于该值。

100 个请求：98 个 10ms、2 个 2000ms结果
平均值49.8ms，看起来很健康
P5010ms
P992000ms，每 100 次就有 1～2 次很慢
  • P99 是核心接口 SLO 和超时设置的依据；P999 用于金融、交易等长尾敏感场景
  • 扇出放大长尾：并行调用 100 个下游，至少碰上一次 P99 慢请求的概率 1 - 0.99^100 ≈ 63%
  • 分位数不能求平均、不能相加，多实例要基于直方图合并（Prometheus histogram_quantile）
  • 压测注意协调遗漏：闭环工具在服务卡顿时少发请求，长尾被低估，用 wrk2 固定速率或 Gatling 开放模型

→ 详见 性能指标

Q3：USE 方法和 RED 方法分别适合什么场景？

核心结论：USE 面向资源，回答"哪种资源有问题"；RED 面向服务 / 接口，回答"哪个接口有问题"。实践中先用 RED 找到慢接口，再用 USE 查它所在机器与依赖的资源。

方法对象三个维度适用场景
USECPU、内存、磁盘、网络，以及线程池、连接池等软件资源使用率、饱和度（排队）、错误系统整体变慢但不知道原因时做第一轮全面排查
RED服务、接口请求速率、错误、耗时分布监控大盘与告警，定位具体慢接口
  • 饱和度比使用率更能说明问题：Load 高于核数、线程池队列堆积、连接池有等待线程
  • Spring Boot + Micrometer 的 http.server.requests 就是 RED 数据，分位数需开启 percentiles-histogram

Q4：接口突然变慢，你的排查思路是什么？（系统资源 → JVM → 线程/锁 → 外部依赖）

核心结论：自顶向下逐层下钻，每一层用数据排除或确认；最实用的分叉点是"CPU 忙还是在等"。

步骤要回答的问题手段
① 系统资源CPU、内存、IO、网络是否打满或饱和top、vmstat、iostat、sar
② JVMGC 是否频繁、停顿是否过长、堆是否持续上涨GC 日志、jstat -gcutil、JFR
③ 线程 / 锁哪些方法耗 CPU、线程卡在哪里、是否有锁竞争jstack、Arthas thread / trace、火焰图
④ 外部依赖时间是否花在等 DB、缓存、RPC、MQ链路追踪、慢查询日志、客户端耗时埋点
  • CPU 高、RT 高：计算型瓶颈，看 CPU 火焰图，或确认是否 GC 线程占满 CPU
  • CPU 低、RT 高：等待型瓶颈（锁、IO、连接池、下游），看 jstack 线程状态分布或 wall-clock 火焰图
  • 线上"突然"变慢时，先关联最近的发布与配置变更

→ 详见 性能分析方法论

Q5：Amdahl 定律对性能优化有什么指导意义？

核心结论：局部优化对整体的加速上限为 S = 1 / ((1 - p) + p / k)（p 为被优化部分的耗时占比，k 为该部分自身加速倍数），所以先优化占比最大的部分。

占比 p自身加速 k整体加速比
5%∞1.05
50%10 倍1.82
90%10 倍5.26
  • 占比 5% 的环节即使降到 0，整体也只快约 5%
  • 并行化同样受限：10% 必须串行时，加多少核加速比上限都是 10 倍
  • 微基准快 30%，要乘以该方法在接口总耗时中的占比才是真实收益

2、分析工具与基准测试

Q6：火焰图怎么看？CPU 火焰图和 wall-clock 火焰图有什么区别？

核心结论：纵轴是调用栈（下层调用上层，顶部是采样时正在执行的方法），横轴宽度是样本占比、不是时间顺序；找顶部的"平顶"（自身热点）和中间的"宽塔"（热点子树）。CPU 火焰图宽度代表 CPU 时间，wall-clock 火焰图宽度代表墙钟时间（含阻塞与等待）。

事件宽度代表适用
cpuCPU 时间CPU 高：计算热点、序列化、正则、GC 线程占比
wall墙钟时间CPU 不高但很慢：等下游、等锁、等连接池
alloc分配字节数GC 频繁的根因
lock锁等待时间锁竞争
  • 颜色只区分帧类型（Java、JIT 内联、C++/JVM、内核、native），不表示热度
  • wall 模式下 Unsafe.park、epoll_wait 很宽只说明线程在等，要看谁在等、等什么，需配合 -t 按线程拆分
  • 采样 30～60 秒，且在问题发生期间、高负载下采样
asprof -d 30 -f /tmp/cpu.html <pid>              # CPU（3.x 为 asprof，2.x 为 profiler.sh）
asprof -e wall -t -d 30 -f /tmp/wall.html <pid>  # wall-clock，按线程拆分

Q7：线上 CPU 使用率飙高，如何定位到具体的代码行？

核心结论：先找到高 CPU 的进程和线程，把线程 ID 转成十六进制去线程栈里找对应的 nid，栈顶即热点代码；若是 GC 线程则转查 GC 日志。偶发或多个线程分摊时，直接抓 30～60 秒 CPU 火焰图更可靠。

top                                   # 1. 找到高 CPU 的 Java 进程
top -H -p <pid>                       # 2. 找到高 CPU 的线程 TID
printf "%x\n" <tid>                   # 3. TID 转十六进制，如 12345 → 3039
jstack <pid> | grep -A 30 "nid=0x3039"  # 4. 看该线程栈，定位到类与行号
  • Arthas 更快：thread -n 3 直接列出最忙的 3 个线程及其栈，profiler start / profiler stop 生成火焰图
  • 单次 jstack 只是瞬时快照，连续抓 3～5 次对比，栈顶稳定出现的方法才是热点
  • 线程名是 GC Thread / G1 Conc 等时，问题在分配速率或内存泄漏，见 Q12

→ 详见 JVM 故障排查、线上诊断、性能分析工具

Q8：JFR 能采集哪些信息？适合排查什么问题？

核心结论：JFR（JDK Flight Recorder）是 JDK 内置的事件录制器，可采集方法采样热点、对象分配、GC、锁竞争、IO、异常等事件；默认配置开销通常在 1%～2% 以内，适合生产常驻录制、问题发生后回溯，尤其是偶发、难复现的问题。

# 启动即常驻录制，保留最近 6 小时
java -XX:StartFlightRecording=name=bg,settings=default,maxage=6h,dumponexit=true,filename=/data/jfr/app.jfr -jar app.jar
# 问题发生后导出内存中的录制
jcmd <pid> JFR.dump name=bg filename=/tmp/snapshot.jfr
  • JDK 11 起开源免费，OpenJDK 8u262 起也已包含
  • 用 JMC 打开分析，或用 async-profiler 的 jfrconv 转成火焰图、jfr print 命令行查看
  • 局限：CPU 采样粒度较粗；要看精细的 CPU / wall 火焰图仍用 async-profiler

→ 详见 性能分析工具

Q9：为什么用 System.nanoTime 循环测性能不可靠？JMH 是如何解决的？

核心结论：手写计时循环会被 JIT 预热、死代码消除、常量折叠、循环优化和 Profile 污染干扰，测到的不是真实性能。JMH 把预热、进程隔离、结果消费和统计做成了框架能力。

陷阱说明JMH 的对策
JIT 预热解释执行与 C2 编译后性能可差数十倍@Warmup 预热轮次
死代码消除结果未被使用，计算被整段删除return 结果或 Blackhole.consume()
常量折叠输入是编译期常量输入放在 @State 对象的非 final 字段
循环优化循环展开、OSR 与真实调用不同由 JMH 控制调用次数
Profile 污染同一 JVM 先后测多个实现互相影响@Fork 独立 JVM 进程，正式测试至少 2
统计不足单次测量波动大多轮迭代，输出 Score ± Error
  • 解读结果看误差区间是否重叠、看随 @Param 规模变化的趋势，用 -prof gc 解释差异
  • JMH 回答"A 写法比 B 快多少"，系统能扛多少仍要靠压测

3、JVM 层

Q10：低延迟和高吞吐场景分别怎么选垃圾收集器？

核心结论：通用在线服务默认 G1；P99 敏感、大堆且 CPU 有余量时选分代 ZGC；批处理、离线计算只看总耗时选 Parallel。多数服务用 G1 + 合理堆大小即可。

收集器典型停顿吞吐适用场景JDK 21 启用方式
G1可设目标（默认 MaxGCPauseMillis=200）中高通用在线服务默认（服务器级机器）
分代 ZGC通常亚毫秒级，与堆大小基本无关中高，并发阶段额外占 CPUP99 敏感、大堆-XX:+UseZGC -XX:+ZGenerational
Parallel较长最高批处理、离线计算-XX:+UseParallelGC
Serial长低1 核或很小内存的容器-XX:+UseSerialGC
  • JVM 判断不是"服务器级机器"（CPU 少于 2 或内存小于约 1792MB）时默认选 Serial，容器 CPU limit 为 1 时要显式指定收集器
  • JDK 23 起分代成为 ZGC 默认模式，JDK 24 移除非分代模式
  • 停顿不是 P99 的主要来源时，换收集器收益有限

Q11：应用刚启动时 RT 毛刺明显，原因是什么？如何缓解？

核心结论：刚启动的 JVM 以解释执行和 C1 为主，热点方法要调用足够多次才由 C2 编译到峰值性能；叠加类加载、懒初始化、连接池和缓存为空，新实例一上来接满流量就会产生 RT 毛刺。缓解靠"预热流量 + 就绪后置 + 预热权重"。

手段做法
预热流量启动后、就绪前主动调用核心接口若干轮
就绪探针后置预热逻辑放在 ApplicationRunner 中，完成后 readiness 才通过
预热权重负载均衡对新实例逐步放量（Dubbo warmup、Envoy slow start）
提前初始化连接池 minimumIdle、缓存预加载、单例提前创建
保证 CPUCPU limit 过小会显著拉长 JIT 编译时间
  • AppCDS 只缩短类加载，解决不了 JIT 预热；CRaC、Leyden AOT 缓存（JDK 24+）、Native Image 改造成本高，只在启动时间直接影响弹性扩容或 Serverless 时考虑

Q12：为什么降低对象分配速率往往比调 GC 参数更有效？

核心结论：分配速率直接决定 Young GC 的频率和对象过早晋升的压力；调参只能改变"怎么回收"，减少分配才是"少产生垃圾"，而且对所有收集器都成立。

测量手段看什么
GC 日志分配速率 ≈ Eden 大小 / Young GC 间隔
async-profiler -e alloc分配最多的调用栈
JFR分配采样事件，按类、按栈聚合
JMH -prof gcgc.alloc.rate.norm，每次操作分配的字节数
  • 常见手段：避免装箱、集合与 StringBuilder 预分配、减少中间对象和多层 DTO 转换、大结果集流式读取、复用 IO 缓冲区、避免 G1 Humongous 大对象
  • 逃逸分析效果依赖内联、不稳定，以分配火焰图实测为准
  • 老年代 GC 后持续上涨是内存泄漏，调参数无用，要做堆 dump 分析

4、代码与池化

Q13：有哪些常见的代码级性能优化手段？HashMap 初始容量应该如何设置？

核心结论：先用 Profiler 确认热点再动手，冷代码优先可读性。HashMap 按 预期元素数 / 0.75 + 1 设置初始容量，或直接用 JDK 19+ 的 HashMap.newHashMap(n)、Guava Maps.newHashMapWithExpectedSize(n)。

类别手段
对象Pattern、ObjectMapper、DateTimeFormatter 等线程安全的昂贵对象作为 static final 复用
集合已知大小时预分配；List 上不做高频 contains
字符串循环内用 StringBuilder；热点路径避免 split / replaceAll 反复编译正则
装箱累加、计数用基本类型，Stream 用 IntStream / mapToInt
锁缩小临界区、IO 移出锁；计数用 LongAdder
异常与日志不用异常做流程控制；日志用占位符 + 异步 Appender（见 Q14）
算法嵌套循环查找（O(n²)）改为 Map 索引
  • 误区：new HashMap<>(n) 不能保证不扩容，因为扩容阈值是 容量 × 0.75

→ 详见 代码级优化

Q14：为什么不建议用异常做流程控制？日志有哪些常见的性能坑？

核心结论：创建异常时 fillInStackTrace() 要遍历调用栈，代价远高于普通对象，高频抛出会成为 CPU 热点；日志的坑主要在"级别不满足时参数照样计算"和"同步写磁盘阻塞业务线程"。

  • 异常：先做廉价校验，只让极少数边界情况走异常；高频业务异常不需要栈时用 super(message, null, false, false) 关闭栈追踪；注意 -XX:+OmitStackTraceInFastThrow 会让频繁抛出的内置异常丢失堆栈
日志坑正确做法
字符串拼接、toString() 无论是否输出都执行使用 SLF4J {} 占位符
占位符挡不住参数本身的计算（如 JSON 序列化）加 isDebugEnabled() 判断
同步 Appender 磁盘 IO 阻塞业务线程Logback AsyncAppender / Log4j2 AsyncLogger，注意队列满时策略
%L、%M、%C 位置信息需要获取调用栈，生产慎用
大循环逐条打日志、生产全量 DEBUG控制日志量

→ 详见 代码级优化

Q15：数据库连接池的大小如何确定？连接池是不是越大越好？

核心结论：不是越大越好。连接池大小由数据库能并行处理多少决定，连接超过数据库的并行能力只会增加上下文切换和锁竞争，RT 反而变差。先用经验公式估算，再用 Little 定律校验。

  1. 经验公式（HikariCP Wiki）：connections = 核数 × 2 + 有效磁盘数，核数是数据库服务器的物理核数，算出的是数据库侧总连接数，多个实例要分摊
  2. Little 定律校验：所需连接数 = 单实例 QPS × 每次持有连接的时间；算出的值远大于公式时，先缩短持有时间（优化慢 SQL、事务内不做 RPC），而不是加大池子
  3. 全局上限：所有实例 maximumPoolSize 之和 ≤ 数据库 max_connections × 80%，扩容前重新核算（见 Q69）
参数要点
maximumPoolSize默认 10，按上面三步确定
minimumIdle官方建议不设置（等于最大值），固定大小
connectionTimeout默认 30s，线上建议 2～5s 快速失败
maxLifetime比数据库 wait_timeout、防火墙、LB 空闲超时短几十秒
keepaliveTimeHikariCP 5.1.0 起默认 120000ms（2 分钟），更早版本默认 0（禁用）
  • 判断池太小：hikaricp_connections_pending 持续大于 0，且数据库本身不忙

Q16：如何发现和排查连接泄漏？

核心结论：连接借出后长期不归还，池会逐渐耗尽，典型表现是获取连接超时而数据库很空闲。用 leakDetectionThreshold 打出借出时的调用栈，配合 active / pending 指标定位。

常见原因处理
手动获取连接未在 finally / try-with-resources 中关闭统一交给框架管理连接
异常路径上事务未正确结束检查回滚逻辑
持有连接期间调用外部服务事务内不做 RPC，这是连接池耗尽最常见的原因
  • leakDetectionThreshold 默认 0（关闭），排查时设为略大于最长正常 SQL 耗时
  • 监控 hikaricp_connections_active 长期贴近上限、pending 持续大于 0 即告警

→ 详见 池化技术

Q17：HTTP 客户端连接池需要关注哪些参数？为什么会出现 NoHttpResponseException？

核心结论：关注总连接数、每路由连接数、三类超时和连接存活时间，客户端全局单例复用。NoHttpResponseException / Connection reset 通常是客户端拿到了已被服务端关闭的空闲连接：客户端空闲超时大于服务端 Keep-Alive 超时。

参数（Apache HttpClient 5）默认要点
MaxConnTotal25整个池的上限
MaxConnPerRoute5调用单一下游时并发超过 5 就排队，最常见的隐形瓶颈
获取连接 / 建连 / 读超时—三类分别设置，获取连接超时宜短
TimeToLive、evictIdleConnections—限制连接寿命，后台清理空闲连接
ValidateAfterInactivity—空闲一段时间后借出前先校验
  • OkHttp 默认 ConnectionPool 保留 5 个空闲连接、空闲 5 分钟；maxRequestsPerHost 默认 5 且只影响异步调用
  • 解决 NoHttpResponseException：让客户端空闲超时小于服务端 Keep-Alive 超时（Nginx keepalive_timeout 默认 75s，Tomcat keepAliveTimeout 默认取 connectionTimeout），开启空闲清理与借出校验；幂等请求可配合一次重试

→ 详见 池化技术

Q18：什么对象不应该池化？

核心结论：只有创建代价高、可安全复用的资源才值得池化，通常只有连接、线程、大块缓冲区和初始化极慢的对象；普通小对象池化反而更慢。

不该池化的场景原因
普通小对象（DTO、集合、StringBuilder）TLAB 指针碰撞分配极快，年轻代回收几乎零成本；池化延长生命周期、增加老年代压力和同步开销
内部状态复杂、难以可靠重置的对象归还后残留状态导致数据串扰
并发极高、池竞争激烈池本身的锁成为瓶颈，改用 ThreadLocal 每线程一份
虚拟线程创建成本极低，池化违背设计初衷；但仍需信号量或连接池限制下游并发

→ 详见 池化技术

5、异步、批量与 IO

Q19：如何把一个串行调用多个下游的接口优化为并行？需要注意什么？

核心结论：相互独立的下游调用用 CompletableFuture 在独立、有界的线程池中并行发起，RT 从各段之和降为最慢的一段。关键是线程池、超时、异常三件事。

CompletableFuture<Product> productF = CompletableFuture.supplyAsync(() -> productClient.get(id), ioPool);
CompletableFuture<Price> priceF = CompletableFuture.supplyAsync(() -> priceClient.get(id), ioPool);
CompletableFuture<List<Review>> reviewF = CompletableFuture.supplyAsync(() -> reviewClient.top(id, 10), ioPool)
        .exceptionally(ex -> List.of())                              // 非核心数据失败降级
        .completeOnTimeout(List.of(), 200, TimeUnit.MILLISECONDS);
ProductDetailVO vo = CompletableFuture.allOf(productF, priceF, reviewF)
        .thenApply(v -> ProductDetailVO.of(productF.join(), priceF.join(), reviewF.join()))
        .orTimeout(500, TimeUnit.MILLISECONDS)                       // 整体超时预算
        .join();                                                     // 异常包装为 CompletionException
  • 不要用 commonPool：默认线程数为核数 − 1，被阻塞 IO 占满会拖垮所有使用它的代码
  • 核心数据失败整体失败并给出明确异常；非核心数据用 exceptionally / completeOnTimeout 降级
  • join() 抛出 CompletionException，取 getCause() 区分超时与业务失败
  • HTTP / RPC 客户端必须自带超时（见 Q20）；ThreadLocal、链路追踪上下文需要显式传递

→ 详见 异步与批量

Q20：CompletableFuture.orTimeout 超时后，底层任务会被取消吗？

核心结论：不会。orTimeout / completeOnTimeout 只是让 Future 提前完成，正在执行的下游调用不会被中断，IO 线程和连接仍被占用；CompletableFuture.cancel(true) 同样不会中断执行线程。

  • 后果：慢下游持续占住线程，ioPool 会被逐渐占满
  • 解决：HTTP / RPC 客户端本身必须设置连接和读超时，且不大于这里的超时预算

→ 详见 异步与批量

Q21：什么是对冲请求（Hedged Request）？有什么使用前提？

核心结论：先向一个副本发请求，超过阈值（常取该接口 P95）仍未返回，就向另一个副本再发一份，取先返回的结果。只额外增加少量请求（阈值取 P95 时理论上约 5%），却能显著削掉长尾，思路来自 Google 的 The Tail at Scale。

前提说明
只用于幂等、无副作用的读写请求重复发送会造成重复副作用
下游能路由到不同副本两次落到同一台慢节点没有意义
延迟阈值取 P95 左右太早会成倍放大下游流量，太晚削不掉长尾
控制总量下游整体过载时对冲加剧拥塞，设对冲比例上限，与重试共用重试预算，配合熔断限流
  • 优先用框架能力，如 gRPC 的 hedgingPolicy

→ 详见 异步与批量、性能分析方法论

Q22：什么是请求合并？适合什么场景，有什么代价？

核心结论：把一个短窗口（如 10ms）内的不同 key 单查请求收集起来，合并成一次批量查询，再把结果分发回各调用方，下游调用次数从 N 降到 N / 批大小。代价是每个调用方多等"窗口等待 + 批量加载耗时"。

维度说明
适用QPS 高、下游有批量接口、对几毫秒延迟不敏感
不适用QPS 低（凑不满批，只增加延迟）、强实时场景
实现要点有界队列、达到 maxBatch 立即触发、批量加载放独立线程池、不存在的 key 显式返回空、调用方设超时
  • 与 SingleFlight 的区别：SingleFlight 合并相同 key 的并发请求（防击穿），请求合并针对不同 key 的批量化，见 Q64
  • 成熟实现可参考 java-dataloader

Q23：什么是零拷贝？Kafka 为什么吞吐量高？开启 TLS 后有什么影响？

核心结论：零拷贝让数据不经过用户态加工、减少内核与用户态之间的拷贝，只在"大块数据原样搬运"时收益明显。Kafka 高吞吐来自顺序追加写 + 页缓存 + 批量与压缩 + 分区并行，消费发送时用 sendfile 零拷贝。开启 TLS 后数据必须在用户态加密，Broker 无法再用 sendfile 向消费者发送，吞吐明显下降。

方案Java API适用典型应用
内存映射 mmapFileChannel.map()需要在用户态读写文件内容RocketMQ CommitLog
文件直传 sendfileFileChannel.transferTo()文件内容不加工、直接发往 SocketKafka 消费发送、Nginx 静态文件、Netty FileRegion
  • Netty 启用 SslHandler 后同样要改用 ChunkedWriteHandler 分块发送
  • 直接内存、CompositeByteBuf 属于用户态少拷贝，不是操作系统零拷贝
  • 普通 JSON 接口要经过业务处理和序列化，用不上零拷贝

Q24：HTTP/1.1、HTTP/2、HTTP/3 在连接复用上有什么区别？

核心结论：HTTP/1.1 靠 Keep-Alive 复用连接，但一个连接同时只能处理一个请求；HTTP/2 单连接多路复用多个流，仍有 TCP 层队头阻塞；HTTP/3 基于 QUIC（UDP）多路复用，解决了 TCP 层队头阻塞。

头部压缩无HPACKQPACK
典型用途大多数内部 RESTgRPC、浏览器、网关移动端弱网、CDN 边缘

  • 服务间 HTTP/1.1 调用用连接池 + Keep-Alive；高频内部调用可考虑 gRPC（HTTP/2 + Protobuf）

6、数据访问

Q25：慢 SQL 如何发现、分析和优化？为什么要按总耗时排序？

核心结论：慢 SQL 治理是"发现 → 聚合排序 → 分析 → 优化 → 验证 → 预防"的闭环。按总耗时（次数 × 单次耗时）排序，是因为数据库压力由总消耗决定，高频的中等慢 SQL 往往比偶发的极慢 SQL 危害更大。

阶段手段
发现slow_query_log=ON、long_query_time=0.5；APM 中的 SQL 耗时
聚合排序pt-query-digest 按总耗时排序
分析EXPLAIN / EXPLAIN ANALYZE（8.0.18+）：访问类型、索引、扫描行数、filesort / 临时表
优化加索引、调整联合索引顺序、消除函数与隐式转换、改写或拆分 SQL
验证与预防对比执行计划与耗时；上线前 SQL 审核、慢 SQL 告警
  • 例：单次 2 秒、每天 10 次的报表 SQL，远不如单次 20ms、每秒 500 次的列表查询压力大
  • 高频 N+1 查询单次很快，调低 long_query_time 采样后按总耗时才能发现

→ 详见 数据访问性能

Q26：深分页为什么慢？有哪些优化方案？游标分页需要什么索引？

核心结论：LIMIT offset, n 要先读出 offset + n 行再丢弃前 offset 行（非覆盖索引时还要回表），偏移越大越慢。首选游标（Seek）分页；必须跳页时用延迟关联。

方案做法局限
游标 / Seek 分页记录上一页最后一条的排序值和 id，(create_time, id) < (?, ?) 语义的条件 + LIMIT n不支持随机跳页
延迟关联子查询先在覆盖索引上查出 n 个主键，再关联回表仍要扫描 offset 行索引，只省掉回表
限制最大页数产品只允许翻前 N 页需要产品配合
搜索引擎ES search_after引入数据同步
  • 索引：过滤列 + 排序列的联合索引即可，如 WHERE user_id = ? ORDER BY create_time DESC 建 (user_id, create_time)；InnoDB 二级索引叶子节点自带主键 id 且作为最后一个排序维度，复合游标可直接利用
  • 排序值不唯一时必须带上 id 组成复合游标，否则翻页重复或遗漏
  • 批量导出、数据迁移等全量遍历一律按主键游标：WHERE id > ? ORDER BY id LIMIT 1000

→ 详见 数据访问性能、MySQL 索引

Q27：JDBC 批量插入为什么没有变快？rewriteBatchedStatements 的作用是什么？

核心结论：真正的批量写入要同时满足三个条件：批量 API + 驱动改写 + 分批提交事务。MySQL 驱动默认即使调用 executeBatch() 也逐条发送，rewriteBatchedStatements=true 让驱动把一批 INSERT 改写成多值 INSERT 一次发送，才真正省掉 N 次网络往返。

条件说明
批量 APIaddBatch() / executeBatch()、MyBatis ExecutorType.BATCH、JPA hibernate.jdbc.batch_size
驱动改写URL 加 rewriteBatchedStatements=true
事务分批关闭自动提交，每 500～1000 行提交一次
  • 改写后的语句总长受 max_allowed_packet 限制；一次提交几十万行会导致长时间锁、主从延迟
  • Hibernate 使用 GenerationType.IDENTITY 主键时无法批量插入
  • MyBatis foreach 拼超长 SQL 解析开销大，大批量优先用 BATCH 执行器

→ 详见 数据访问性能、MySQL JDBC 驱动要点

Q28：什么是 N+1 查询问题？如何发现和解决？

核心结论：先查出 N 条主记录，再对每条单独查一次关联数据，共 1 + N 次查询。最通用的解法是先收集 id，用 IN 批量查询后在内存中组装，查询次数降为 2。

解法适用
IN 批量查询 + 内存组装最通用，适合跨表、跨服务
JOIN 一次查出一对一或一对少
JPA JOIN FETCH / @EntityGraphJPA 项目；一对多 fetch 与分页同时用会在内存中分页
Hibernate @BatchSize懒加载时按批加载关联集合
  • 隐蔽来源：JPA @OneToMany 懒加载在循环中访问、MyBatis 嵌套 select 关联、循环调用单条 RPC
  • 发现：统计单请求 SQL 条数、APM 链路中观察重复 SQL、Hibernate Statistics

→ 详见 数据访问性能

Q29：IN 列表过长会带来什么问题？

核心结论：SQL 变长、解析与传输开销上升，更关键的是执行计划可能变差：值个数超过阈值后优化器改用统计信息估算，甚至放弃 range 访问退化为全表扫描。按几百个一批分批查询。

  • 超过 eq_range_index_dive_limit（默认 200）后，优化器不再逐个 index dive，改用索引统计估算行数，估算偏差可能选错索引
  • 范围分析所需内存超过 range_optimizer_max_mem_size（默认 8MB）时放弃 range 访问
  • 批量接口、请求合并同样要限制单批上限

7、综合案例

Q30：讲一次你做过的接口性能优化：如何定目标、建基线、定位和验证？

核心结论：按"定 SLO → 建基线 → 自顶向下定位 → 一次只改一项 → 压测验证 → 灰度与防回归"讲，每一步都有数据。以下单接口为例（示例数据）：P99 800ms，目标单实例 300 QPS 下 P99 ≤ 250ms、错误率 < 0.1%。

阶段做法与发现
基线固定脚本、数据量、环境，预热后取稳态：P99 800ms，错误全是获取连接超时，单请求 26 条 SQL
定位Trace 看时间分布（三段 RPC 串行、逐条查 SKU）→ wall 火焰图显示在等 Socket 与 getConnection → 慢日志按总耗时发现 N+1 → Little 定律：300 × 0.11s ≈ 33 个连接 > 池 20
优化N+1 批量化 → 事务内 RPC 移出（改可靠消息）→ 独立调用并行化 → 读多写少数据本地缓存 → 日志瘦身与异步
结果P99 800ms → 195ms，错误率 0.3% → 0.02%，pending 峰值 15 → 0
  • 收益最大的是"减少等待"类改动（批量化、RPC 移出事务），而不是调 GC 或加大连接池
  • 讲清"没做什么"同样加分：JFR 显示 GC 不是瓶颈，所以没调 GC；Little 定律说明问题在持有时间，所以没加大池子

Q31：如何证明一项优化确实有效，而不是环境波动？

核心结论：控制变量 + 看分布 + 看误差。同一环境、同一脚本、同一数据量，预热后取稳态，一次只改一个变量，并确认差异大于测量波动。

  • 压测对比：对比 P50 / P99 / P999 与资源使用率，而不是只看平均值；多次重复，逐步加压看拐点是否右移
  • 微基准：纯 CPU 改动用 JMH 单独验证，两组 Score ± Error 区间重叠说明差异不显著
  • 归因：每项改动单独压测，收益才能对应到具体改动
  • 看副作用：数据库 CPU、下游 QPS、缓存命中率、错误率有没有被转移或恶化
  • 线上验证：先灰度 1 个实例，与其他实例的 P99、错误率同时段对比

二、高并发

1、总体设计

Q33：如何设计一个高并发系统？从哪些维度入手？

核心结论：先估算流量（DAU → 平均 QPS → 峰值 QPS → 存储量），再按"能扩、少打、慢做、分散"四个思路逐层设计，最后用限流降级守住底线、用容量规划和水位监控持续验证。

思路含义典型手段
能扩任何一层都能靠加机器提升容量无状态化、负载均衡、分库分表
少打让请求尽量不落到最慢、最贵的那一层CDN、页面静态化、多级缓存
慢做非核心、可延迟的工作移出请求链路MQ 异步、削峰填谷、排队
分散避免流量集中到单点、单 key、单行热点打散、分桶、请求合并

按请求从外到内的维度：接入层（Q37）→ 水平扩展（Q43）→ 缓存（Q47）→ 异步削峰（Q50）→ 数据层扩展（Q54）→ 热点（Q60）→ 参数调优（Q65）→ 容量评估（Q72）；超出容量时的限流、熔断、降级属于高可用，见第三部分。

→ 详见 高并发总览

Q34：高并发、高性能、高可用三者的区别与联系？

核心结论：三者是同一系统的三个观察角度——高性能看单次请求多快，高并发看流量大时扛不扛得住，高可用看出故障时停不停服。

模块核心问题衡量指标典型手段
高性能单次请求如何更快、更省资源RT、P99、CPU / 内存占用池化、异步与批量、JVM 与 SQL 优化
高并发流量大时如何扛得住峰值 QPS、并发数、水位接入分层、水平扩展、缓存、削峰、分片、热点治理
高可用出故障时如何不停服可用率 SLA、MTTR冗余、限流、熔断、降级、隔离、故障转移
  • 高性能是高并发的基础：由 Little 定律，单机 RT 从 100ms 降到 20ms，同样的线程数可承载 5 倍 QPS
  • 高可用是高并发的底线：流量超过容量时靠限流、降级保住核心链路，而不是整体雪崩
  • 同一手段兼顾多个目标：缓存既降 RT 又分担 DB 流量；多副本既扩读能力又提供故障转移

→ 详见 高并发总览

Q35：读多写少的场景如何设计？（CDN + 多级缓存 + 读写分离）

核心结论：让读请求在越靠前、越便宜的层级被拦截：浏览器 / CDN → Nginx 缓存 → 应用本地缓存 → Redis → 数据库，命中率逐层相乘；缓存解决不了的实时读再用读写分离分担。

  • 命中率叠加：Redis 命中 95% 时 DB 承担 5% 读流量；前面再加一层 80% 命中的本地缓存，DB 只剩 20% × 5% = 1%
  • 按数据特征选层：静态资源走 CDN；千人一面的热点可放 Nginx / 本地缓存；千人千面的只能到 Redis；余额、库存精确值等强一致数据最多缓存到 Redis
  • 页面静态化：商品详情、活动页主体静态化，价格库存走异步接口（见 Q40）
  • 读写分离：只扩读不扩写，必须配套主从延迟策略（见 Q55）

→ 详见 缓存架构设计、接入层架构、数据层扩展

Q36：写多的场景如何设计？（MQ 削峰 + 异步处理）

核心结论：主链路只做必须同步完成的步骤，其余写入交给 MQ 按下游能力匀速消费；写入本身到顶时再靠批量合并、分库分表扩展写能力。

手段做法
同步转异步事件通知、受理 + 异步回执、Write-Behind（见 Q50）
削峰填谷洪峰先落 MQ，消费端限速落库
用户侧排队秒杀类场景用令牌、排队先把请求量压到与库存相当
合并写计数类热点内存 / Redis 聚合后定期落库（见 Q62）
扩展写能力垂直分库、水平分库分表（见 Q56）
  • 代价是最终一致：需要本地消息表 / 事务消息 + 幂等消费 + 对账（见 Q53）

→ 详见 异步与削峰

2、接入层

Q37：一个请求从 DNS 到应用服务要经过哪些层？每层解决什么问题？

核心结论：典型路径是 DNS / GSLB → CDN → 四层负载均衡 → 七层网关 → 应用集群。越靠前的层看到的信息越少但吞吐越高、单位请求成本越低，能在前面消化的流量就不要放到后面。

层级职责典型组件
DNS / GSLB按地域、运营商、机房健康把用户导向就近入口智能 DNS、GSLB、HTTPDNS
CDN边缘缓存可公开内容，只回源未命中部分云 CDN
四层负载均衡按 IP + 端口转发 TCP / UDP，扛海量连接LVS、云 SLB / NLB
七层网关理解 HTTP：路由、TLS 卸载、鉴权、限流、灰度Nginx、OpenResty、Ingress、Spring Cloud Gateway
应用集群执行业务逻辑无状态服务 + 水平扩展
  • DNS 最便宜但生效慢、不可控（Local DNS 与客户端缓存），入口 TTL 常设 60～300 秒，只做机房级粗调度
  • 每一层都要有冗余，接入层任何一层是单点，整个系统就是单点

→ 详见 接入层架构

Q38：四层负载均衡（LVS）和七层负载均衡（Nginx）有什么区别？为什么常组合使用？

核心结论：四层负责"扛连接"，七层负责"懂业务"。四层只看 IP 和端口，内核态转发开销极低；七层能解析 HTTP 做路由、鉴权、限流，但单机能力低。组合使用：四层做入口 VIP，后面挂多台七层网关水平扩展。

对比四层（LVS / SLB）七层（Nginx / 网关）
工作层次传输层，IP + 端口应用层，HTTP
能力转发连接，不解析内容按 URL / Header 路由、TLS 卸载、鉴权、限流、灰度
性能极高（内核态；DR 模式响应直接回客户端）较高，多实例扩展
健康检查TCP 端口级HTTP 接口级
  • LVS 模式：NAT（请求响应都经过 LVS）、DR（只改 MAC，性能最好，需同一二层网络）、TUN（IP 隧道）、FULLNAT（可跨 VLAN，需 TOA 透传客户端 IP）
  • 七层网关必须无状态，且只做通用横切逻辑，不写业务逻辑

→ 详见 接入层架构

Q39：CDN 的原理是什么？动态内容能否走 CDN？

核心结论：CDN 通过全局调度把用户导向就近的边缘节点，节点缓存可公开、可缓存的内容，未命中或过期时才回源。动态请求（下单、支付、个人数据）不缓存，可以绕过 CDN 或只利用 CDN 做回源链路加速。

内容走法
静态资源（JS / CSS / 图片 / 视频）独立域名 → CDN → 对象存储，文件名带内容哈希 + 长期 max-age
静态化页面CDN → Nginx → 页面文件，短 TTL + 变更主动刷新
动态请求绕过 CDN 或只做加速回源
  • 回源保护：大量节点同时回源会冲垮源站，开启回源合并、大促前 CDN 预热、源站前加 Nginx proxy_cache
  • CDN 失效靠 TTL 或主动刷新，通常分钟级生效，强一致数据不要放进静态内容

→ 详见 接入层架构

Q40：什么是页面静态化？适合什么场景？

核心结论：把"每次请求都查库渲染"的页面变成"数据变更时生成一次、之后直接读文件"，读流量由 CDN 和 Nginx 消化。适合读多写少、千人一面的页面。

方式做法适用
全量静态化数据变更时用模板生成完整 HTML，推送到 Nginx / 对象存储文章、帮助中心、活动落地页
页面片段化主体静态化，价格、库存、登录态由前端异步请求接口商品详情页、秒杀页
边缘渲染CDN 边缘用 ESI 或边缘函数拼装片段大规模电商、门户
  • 价格、库存这类强一致数据不要写死在静态页里，放到异步接口单独获取

→ 详见 接入层架构

Q41：为什么要在接入层做 TLS 卸载？

核心结论：TLS 握手（尤其是非对称加密部分）是入口层最主要的 CPU 开销之一。在最外层 SLB / Nginx 集中卸载，证书集中管理，后端应用不再处理加解密，入口层也能集中做握手优化。

配套优化作用
会话复用（Session Cache / Ticket）重连时跳过完整握手
TLS 1.3完整握手只需 1-RTT
ECDSA 证书签名运算比同等强度 RSA 更省 CPU
OCSP Stapling服务端附带证书状态，客户端不必单独查询
  • 卸载后内网是明文，是否内部加密取决于安全要求；零信任架构下服务间改用 mTLS

→ 详见 接入层架构

Q42：长连接网关如何支撑百万级连接？

核心结论：长连接场景的压力不在 QPS 而在同时在线的连接数。做法是独立部署只管连接的网关（Netty 等 Reactor 模型，少量 IO 线程管理大量连接），业务交给后端，再解决路由、心跳、重连风暴和 OS 参数。

要点做法
独立网关WebSocket / MQTT 网关只做连接、编解码、心跳，业务经 RPC / MQ 交给后端
连接路由表Redis 记录 userId → 网关节点，下行消息先查路由再投递
四层负载均衡长连接走 TCP 转发，按连接数而不是请求数均衡
空闲超时对齐负载均衡空闲超时必须大于客户端心跳间隔
防重连风暴网关重启或切机房时，客户端指数退避 + 随机抖动重连
系统参数调大 ulimit -n、somaxconn 等（见 Q71）

→ 详见 接入层架构、Netty 总览

3、水平扩展

Q43：垂直扩展和水平扩展的区别？各自适用什么场景？

核心结论：垂直扩展换更强的机器，几乎不用改代码但有硬件天花板且是单点；水平扩展加同构机器，接近线性但需要无状态化、负载均衡和数据分片。原则是先垂直、后水平，但应用层从第一天就保持无状态。

对比垂直扩展（Scale Up）水平扩展（Scale Out）
改造成本几乎为零无状态化、负载均衡、数据分片
上限单机硬件天花板接近线性，受共享资源（DB、锁）限制
成本曲线高配机器非线性上涨近似线性
可用性单点多副本天然冗余
适用早期业务、数据库主库、短期应急应用层、缓存层、分片后的存储层

→ 详见 水平扩展与无状态化

Q44：什么是无状态服务？应用中有哪些常见的"状态"需要外置？

核心结论：无状态服务是任意请求路由到任意实例结果一致，实例可随时增删而不需要数据迁移。做法是把所有状态外置到共享组件。

状态外置方案
HTTP SessionRedis 集中存储（Spring Session）或 JWT 无状态令牌
本地文件（上传、导出）对象存储（OSS / S3 / MinIO）
本地计数、限流Redis 计数 / 分布式限流
本地定时任务分布式调度（XXL-JOB）或分布式锁
本地缓存允许短暂不一致 + 广播失效
WebSocket 长连接连接注册表 + MQ 广播 / 路由
  • 检查点：static 可变集合存业务数据、写本地磁盘并假设下次还能读到、定时任务与 MQ 消费能否多实例并行

→ 详见 水平扩展与无状态化

Q45：Session 在集群环境下如何共享？

核心结论：四种方案——粘性会话、Session 复制、集中存储、无状态 Token。推荐集中存储（Spring Session + Redis）或 Token（JWT），粘性会话只是补丁。

方案问题
粘性会话（IP Hash / Cookie）负载不均，实例下线会话丢失
Session 复制实例越多复制开销越大，只适合小集群
集中存储（Redis）多一次网络访问，Redis 需高可用
Token（JWT）服务端无状态，但主动失效（踢人、改密）需要黑名单等额外机制
  • Spring Boot 3 引入 spring-session-data-redis 即自动配置 Redis 存储，不再需要声明存储类型；用 spring.session.redis.namespace 隔离多应用
  • 外置后避免在 Session 里放大对象，每次请求都要序列化传输

→ 详见 分布式会话、水平扩展与无状态化

Q46：K8s HPA 自动扩容有哪些局限？应用扩容后下游会出现什么问题？

核心结论：HPA 按 期望副本数 = ceil(当前副本数 × 当前指标值 / 目标值) 调整副本，局限在于有延迟、指标可能选错、扩的只是应用层；应用扩容后压力转移到下游，最典型的是 DB 连接数超限。

局限应对
扩容延迟：拉镜像 + JVM 启动 + 预热，30 秒到数分钟目标值设低于规划水位（HPA 常取 CPU 60%，单机容量点按 70%），大促前提前手动扩容，保持合理 minReplicas
就绪过早：JIT 未编译就接流量readiness 在预热完成后才通过
内存指标不适合 JVM：堆扩张后通常不归还 OS，只扩不缩计算密集型用 CPU（需设好 requests）；IO 密集型用 QPS / 在途请求数（Prometheus Adapter、KEDA）；消费者按 MQ Lag
缩容抖动scaleDown.stabilizationWindowSeconds: 300，配合优雅停机
到达 maxReplicas 或下游先到顶由容量规划水位提前发现（见 Q77）
  • 下游问题：DB 连接总数 = 实例数 × 单实例池大小，可能超过 max_connections，新实例启动即报 Too many connections；Redis 连接、MQ 分区数（消费者数受分区数上限约束）同理，扩容前要核算

→ 详见 水平扩展与无状态化、并发参数调优

4、缓存架构

Q47：多级缓存的架构是怎样的？各层的一致性如何取舍？

核心结论：浏览器 / CDN → Nginx 本地缓存 → 应用本地缓存 → Redis → DB，越靠前命中率越高、延迟越低，但失效越难控制。按数据特征选层，每层都用 TTL 兜底。

层级一致性保障可接受的不一致窗口适用数据
CDN / 浏览器仅 TTL + 主动刷新分钟 ~ 小时图片、JS/CSS、静态页
Nginx 本地缓存短 TTL（1 ~ 10s）秒级商品详情、活动页
应用本地缓存短 TTL + MQ / Pub-Sub 广播失效毫秒 ~ 秒级热点商品、配置
Redis更新 DB 后删缓存 + 延迟双删 / Binlog 订阅毫秒级业务数据
  • 余额、库存精确值、权限等强一致数据不进本地缓存和 CDN，最多缓存到 Redis
  • TTL 加随机抖动；监控各层命中率，骤降要告警

→ 详见 缓存架构设计、缓存一致性

Q48：缓存穿透、缓存击穿、缓存雪崩分别是什么？如何解决？

核心结论：不存在的数据挡在缓存前（防穿透），热点 key 重建只放一个请求回源（防击穿），失效时间和故障域都要打散（防雪崩）。

问题现象核心解法
穿透查询不存在的数据，每次都打到 DB参数校验；布隆过滤器预过滤；缓存空值（短 TTL）
击穿单个热点 key 过期瞬间大量请求并发重建互斥锁 / SingleFlight 只允许一个请求回源；逻辑过期 + 异步刷新
雪崩大量 key 同时失效或 Redis 整体不可用TTL 加随机抖动；多级缓存兜底；Redis 集群高可用；熔断降级

→ 详见 缓存架构设计、开发总结-缓存

Q49：如何做缓存预热？预热时如何避免压垮数据库？

核心结论：在流量到来前把可预知的热点提前加载进缓存；预热本身要分批 + 限速控制对 DB 的并发，并在预热完成后才接流量。

方式做法
启动预热应用启动时加载配置、字典、Top N 热门数据到本地缓存
定时预热按访问统计把次日热门数据写入 Redis
活动预热大促 / 秒杀前推送活动商品、库存到 Redis 和本地缓存
流量回放新集群上线、机房切换时回放线上访问日志
  • 预热逻辑放在 ApplicationRunner 中，K8s readiness 自然等到预热结束
  • 批量写入 Redis 时 TTL 加随机抖动，避免同时过期形成雪崩
  • 突发热点无法预热，靠实时探测后晋升本地缓存（见 Q60）

→ 详见 缓存架构设计

5、异步与削峰

Q50：MQ 如何实现削峰填谷？消费速率如何控制？

核心结论：MQ 写入能力远高于数据库，洪峰先落进队列，消费端再按下游容量匀速处理——用延迟换稳定。前提是业务能接受这个延迟。

  • 示例：瞬时 10w QPS 持续 10 秒，DB 只能承受 5000 TPS：10 秒写入 100w 条消息，消费端 5000 TPS 约 200 秒处理完，DB 始终在安全水位
MQ控制消费速率
Kafkamax.poll.records；消费者实例数 ≤ 分区数；必要时 pause() / resume()
RocketMQ消费线程数、pullBatchSize、consumeMessageBatchMaxSize
RabbitMQprefetch（basic.qos）限制未确认消息数；消费者数
  • 消费逻辑内还可用 RateLimiter 精确限速；注意单实例限速时总速率 = 单实例速率 × 实例数，下游有硬上限时按 下游容量 / 实例数 设置或改用分布式限流
  • MQ 至少一次投递，消费必须幂等

→ 详见 异步与削峰

Q51：消息积压了怎么处理？

核心结论：先判断是"消费变慢"（下游故障）还是"生产突增"（正常洪峰）：前者先修下游，盲目扩容只会加重下游压力；后者再扩消费能力。

  1. 监控：Kafka 看 consumer lag，RocketMQ 看消费组堆积量（diffTotal），积压持续增长即告警
  2. 修下游：消费慢多由 DB、下游接口变慢引起，先恢复下游
  3. 扩消费：增加消费者实例（Kafka 受分区数上限约束）；或把消息转存到分区更多的临时 Topic 再并行消费
  4. 提效：批量消费、批量落库
  5. 止损：对时效敏感的消息设置过期丢弃，不处理已无意义的旧请求

→ 详见 异步与削峰、消息队列

Q52：流量整形和限流有什么区别？

核心结论：两者都控制流量速率——整形让超出部分排队等待，限流让超出部分直接失败。

对比项流量整形限流
目标把不均匀的流量变平滑保护系统不被超出容量的流量压垮
超出部分缓冲、排队、延后处理直接拒绝（快速失败）
典型手段漏桶、MQ 缓冲、排队令牌桶、滑动窗口、计数器
请求结果最终都会被处理（延迟增加）被拒请求需客户端重试或放弃
场景下单、支付回调、数据同步接口防刷、网关总量保护
  • 组合使用：网关先限流挡住超出总容量的请求，放行的请求进 MQ 整形，消费端匀速落库

→ 详见 异步与削峰、限流与过载保护

Q53：异步化之后如何保证最终一致性？本地消息表的原理是什么？多实例下如何避免重复投递？

核心结论：用"可靠投递 + 幂等消费 + 补偿对账"保证最终一致。本地消息表（Outbox）把业务数据和待发消息写在同一个本地事务里，保证"数据存在 ⇔ 消息存在"，再由中继任务投递到 MQ。

问题方案
本地事务成功但消息没发出本地消息表 / RocketMQ 事务消息
消息重复投递消费端幂等：唯一键约束、状态机、去重表
消费失败有限次重试 + 死信队列 + 补偿
异步步骤失败需回滚Saga，每步定义补偿操作
长时间不一致定时对账，自动修复或告警
  • 多实例防重复投递：SELECT … FOR UPDATE SKIP LOCKED 让各实例锁定不同的行并行投递（MySQL 8.0+ / PostgreSQL 9.5+，需要 (status, id) 索引）；或用分布式锁 / 单实例调度，同一时刻只有一个实例执行中继
  • 即便如此仍是至少一次：发送成功但事务回滚时下个周期会再发，消费端必须幂等；追求低延迟可改用 CDC（Debezium 监听 outbox 表 Binlog）

→ 详见 异步与削峰、分布式事务

6、数据层扩展

Q54：数据层扩展的演进顺序是什么？为什么不一上来就分库分表？

核心结论：按改造成本从低到高：缓存 → 读写分离 → 冷热分离 → 垂直分库 → 水平分表 / 分库分表 → 引入专用存储，能用前一步解决就不走下一步。分库分表带来分片键约束、跨分片查询、分布式事务和扩容迁移，是成本最高、最难回退的一步。

步骤解决的瓶颈
缓存读 QPS 高、数据可缓存
读写分离读 QPS 高、实时性要求较高
冷热分离数据量大但大多是历史数据
垂直分库不同业务争抢同一个库
水平分库分表单表行数、单库写入与存储到顶
专用存储搜索、分析、时序等关系库不擅长的查询
  • 很多系统先做归档与冷热分离就足以撑很长时间

→ 详见 数据层扩展

Q55：读写分离如何处理主从延迟？

核心结论：MySQL 复制默认异步，从库通常落后毫秒级，大事务或从库负载高时可达秒级，"写后立即读"可能读到旧数据。按一致性要求选策略：

策略做法适用
强制走主库显式 Hint 路由到主库（ShardingSphere HintManager.setWriteRouteOnly()）支付后查余额、下单后查订单
写后窗口内读主用户写操作后 N 秒内（如 Redis 标记 3s）的读请求走主库修改资料后立即查看
缓存兜底写 DB 同时写缓存，读优先读缓存读多、可缓存的数据
业务容忍前端提示"处理中"或延迟跳转发帖、评论等弱一致场景
等待 GTID读从库前 WAIT_FOR_EXECUTED_GTID_SET强一致但仍想分流读
  • 半同步复制只降低数据丢失风险，并不消除读延迟

→ 详见 数据层扩展

Q56：什么时候需要分库分表？分片键如何选择？

核心结论：单库写入压力、单表数据量过大，且缓存、归档都解决不了时才分；先按业务垂直分库，再对仍然过大的表水平拆分。经验阈值（需结合压测）：单表超过 2000 万行或 50GB、单库写 TPS 接近压测上限、存储接近实例上限。

分片键原则说明
覆盖核心查询绝大多数查询带分片键，否则广播到所有分片
分布均匀避免大商家、大 V 集中到一个分片；不要用时间戳做哈希分片键
不可变修改分片键意味着数据迁移
关联表同键订单与订单明细同分片键（绑定表），保证同分片 JOIN
业务语义优先 user_id、tenant_id 等核心维度

→ 详见 数据层扩展、分库分表

Q57：哈希、范围、一致性哈希几种分片算法各有什么优缺点？

核心结论：哈希分布均匀但扩容要重分布；范围扩容简单但易成写热点；一致性哈希扩容只迁移部分数据但实现复杂；映射表最灵活但多一次查询。

算法优点缺点
哈希取模 hash(key) % N分布均匀N 变化时几乎所有数据要迁移
范围（ID 区间 / 按月建表）扩容简单，范围查询友好新数据集中在最新分片，易成写热点
一致性哈希扩容只迁移部分数据实现复杂，需虚拟节点调匀分布
映射表（key → 分片）最灵活，可单独迁移大租户多一次查询，路由表本身要高可用
  • 分表后需要全局唯一且趋势递增的分布式 ID（雪花、号段），UUID 作 InnoDB 主键会导致页分裂

→ 详见 数据层扩展、一致性哈希

Q58：分库分表后如何按非分片键查询？跨分片分页怎么做？

核心结论：非分片键查询靠基因法、异构索引表或同步到 ES，避免广播；跨分片深分页每个分片都要取 offset + n 行再归并，应禁止深分页、改用游标分页。

  • 基因法：把 user_id 的低几位嵌入 order_id，按 order_id 查询也能定位分片
  • 异构索引表：按 seller_id 再冗余一份（Binlog / MQ 同步），用存储换查询
  • ES：复杂条件、运营后台查询统一走 ES
跨分片操作处理
分页 LIMIT 10000, 10每分片取 10010 行归并 → 改 WHERE id > ? ORDER BY id LIMIT 10
聚合 / 排序预计算汇总表，或交给 ClickHouse / Doris
JOIN绑定表同键分片、小表广播、应用层组装
事务尽量同分片，否则最终一致（本地消息表、Seata）

→ 详见 数据层扩展

Q59：分库分表如何平滑扩容？

核心结论：按"双写 → 历史数据迁移 → 校验 → 灰度切读 → 切写"平滑进行，全程保留回滚窗口；更好的做法是一开始就规划足够的逻辑分片，扩容时整表迁移而不重新哈希每一行。

  1. 双写：新旧分片同时写（以旧库为准），应用双写或 Binlog 同步（Canal / DTS）
  2. 迁移：全量拷贝历史数据，增量由双写 / Binlog 追平
  3. 校验：对比行数与抽样内容，修复差异
  4. 灰度切读：按比例把读流量切到新分片观察
  5. 切写：以新库为准，停写旧库，保留回滚窗口后下线
  • 逻辑分片预规划：如 1024 张表分布在 8 个库，扩容只把整张表搬到新库
  • 分布式数据库（TiDB、OceanBase）可免去应用层分片，代价是运维体系与成本

→ 详见 数据层扩展

7、热点问题

Q60：如何发现突发热点 key？集中式探测的原理是什么？

核心结论：可预知热点提前预热，突发热点靠实时探测，事后排查用 Redis 工具。集中式探测（如 JD-hotkey）由客户端上报访问、计算集群汇总判定、再推送给所有实例，从探测到全集群生效通常在 1 秒内。

方式优缺点
客户端统计简单无组件；单机视角，全局热点分散到多实例后可能漏判
代理层统计全局视角；需要代理层
redis-cli --hotkeys无需改代码（要求 LFU 类淘汰策略）；离线分析
集中式探测全局准确、秒级；需部署独立组件

JD-hotkey 流程：客户端 SDK 本地计数、每 500ms 批量上报 → Worker 按 key 哈希分配、滑动窗口统计（如 1s 内 > 1000 次判定为热点）→ 长连接推送给所有应用实例 → 实例把该 key 缓存到 JVM 本地 → 热度下降后自动过期。

  • 单机阈值要按实例数折算：100 个实例时，全局 5 万 QPS 的热点在单机只有约 500 QPS
  • MONITOR 严重影响性能，生产慎用

→ 详见 热点问题

Q61：Redis 热点 key 如何处理？（探测 + 本地缓存 + key 打散）

核心结论：热点 key 会打满单个分片的 CPU / 网卡，加机器无效。首选探测后晋升本地缓存，其次多副本打散，还可以前置到 Nginx / CDN。

手段做法代价
本地缓存热点 key 缓存到每个实例 JVM（短 TTL，如 3 秒）秒级不一致
key 打散复制为 key#0 ~ key#N，读时随机选一个写放大 N 倍，更新瞬间副本短暂不一致
读从节点Cluster 模式客户端开启从节点读（如 Lettuce ReadFrom.REPLICA_PREFERRED）读到复制延迟
大 value 拆分热点同时是大 key 时拆分或压缩读取需组装
前置到接入层千人一面的数据在 Nginx / CDN 返回失效更难控制
  • 打散不能用 {item:1}#0 这种 hash tag 写法，否则副本仍在同一分片；可用 CLUSTER KEYSLOT 校验
  • 最后一道防线是热点参数限流（Sentinel 按参数值限流）

→ 详见 热点问题

Q62：秒杀场景下同一行库存的高并发扣减如何优化？

核心结论：InnoDB 对同一行的更新必须串行持锁，单行 TPS 通常只有几百。主流做法是Redis Lua 原子预扣 + MQ 异步落库 + 对账，超高并发再加分桶，并在入口先削峰。

方案做法要点
DB 条件更新UPDATE ... SET stock = stock - 1 WHERE item_id = ? AND stock > 0能防超卖，适合并发不高的普通商品
Redis 预扣 + 异步落库Lua 原子完成"判重 + 判库存 + 扣减"，成功后发 MQ，消费端幂等落库对账 Redis 与 DB；处理 MQ 发送失败、超时未支付回补
分桶库存拆成 N 个桶分散到不同分片 / 行（见 Q63）桶间不均时需遍历或再平衡
前置削峰令牌发放、排队、网关限流，只放行与库存相当的请求从源头减少无效请求
  • 防超卖的底线：最终扣减必须是原子的条件更新（Lua 或带 stock >= n 条件的 SQL），不能"先查再扣"
  • 多个 key 的 Lua 脚本要用 hash tag（如 stock:{itemId}）保证同槽

→ 详见 热点问题、秒杀系统设计

Q63：什么是分桶库存？有什么代价？

核心结论：单个 Redis key 仍受单分片单线程上限约束，分桶把总库存拆成 N 份分布到不同分片（或数据库的 N 行），把一个热点拆成 N 个温点。

步骤做法
初始化库存 10000 拆成 10 桶：stock:1001:0 ~ stock:1001:9，每桶 1000
扣减按 userId % 10 选桶，桶库存不足时尝试下一个桶
售罄判断维护"已售罄桶数"，全部售罄才返回售罄
数据库侧一行库存拆成 N 行（item_id + bucket_no），分散行锁
  • 代价：可能出现"其他桶还有库存但当前桶已空"的误判，需要遍历或定期再平衡；总库存查询与对账变复杂

→ 详见 热点问题

Q64：什么是 Single Flight？和批量请求合并有什么区别？

核心结论：Single Flight 让相同 key 的并发请求只有一个真正执行，其余等待共享结果，回源次数降为 1，是防缓存击穿的通用手段；请求合并是把窗口内不同 key 的请求合并成一次批量查询，目的是减少下游调用次数。

对比Single Flight请求合并
合并对象相同 key 的并发请求不同 key 的请求
目的防击穿、避免重复计算批量化，降低下游调用次数
额外等待无，等待的是正在执行的那次窗口等待 + 批量加载
代价失败时所有等待者一起失败，等待方要设超时低 QPS 时反而变慢
  • 实现：ConcurrentHashMap<K, CompletableFuture<V>> 用 putIfAbsent 抢占，执行完 remove(key, future)

→ 详见 热点问题、异步与批量

8、并发参数调优

Q65：线程数如何设置？CPU 密集型和 IO 密集型有何不同？

核心结论：公式只是起点，最终以阶梯压测的拐点为准，上线后用动态线程池微调。

任务类型估算公式说明
CPU 密集型CPU 核数 + 1多 1 个线程应对偶发缺页、中断
IO 密集型CPU 核数 × (1 + 等待时间 / 计算时间)等待 / 计算 = 9 时，8 核约 80 个线程
按流量反推目标 QPS × 单任务平均耗时Little 定律，1000 QPS × 50ms ≈ 50
  • 等待与计算的比例很难准确测量，且下游（DB、RPC）的承载能力往往先于 CPU 到顶
  • 线程过多会导致 CPU sys 态高、上下文切换开销大

→ 详见 并发参数调优、线程池

Q66：线程池核心线程满了之后，是先扩到最大线程数还是先进队列？Tomcat 线程池有何不同？

核心结论：JDK 线程池是先进队列：核心线程满 → 任务入队 → 队列满 → 才创建非核心线程直到 max → 仍满则拒绝。Tomcat 工作线程池使用自定义 TaskQueue，行为相反：线程数未到 threads.max 时优先创建线程而不是排队。

  • 后果：队列很大时线程数几乎不会增长到 max，排队延迟可能早已超过调用方超时
  • 希望"先加线程再排队"：调小队列，或令 core = max 并开启 allowCoreThreadTimeOut(true) 回收空闲线程

→ 详见 并发参数调优

Q67：队列长度如何确定？为什么不是越大越好？

核心结论：排队时间必须小于调用方超时，否则任务执行了也是白做。上限可按 队列长度 ≤ 线程数 × (可接受排队时间 / 单任务耗时) 估算。

  • 例：单任务 100ms、20 个线程、队列 500，队尾任务要等 500 / 20 × 100ms = 2.5s 才开始执行
  • 若只能接受 500ms 排队，队列应 ≤ 20 × 500 / 100 = 100
  • 必须用有界队列：无界队列会堆积到 OOM，且让 max 线程数永远不生效

→ 详见 并发参数调优

Q68：Tomcat 的 threads.max、max-connections、accept-count 分别是什么关系？开启虚拟线程后哪些还生效？

核心结论：三者是三道闸：最多 threads.max 个线程处理请求 → 线程全忙时连接仍被接收并等待，直到连接数达到 max-connections → 之后新连接停留在 OS 全连接队列（长度 accept-count）→ 队列也满则客户端连接被拒绝或超时。

参数默认值含义
server.tomcat.threads.max200最大工作线程数
server.tomcat.max-connections8192NIO 最大连接数
server.tomcat.accept-count100OS 全连接队列长度（listen backlog，受 somaxconn 截断）
  • 开启虚拟线程（Spring Boot 3.2+ spring.threads.virtual.enabled=true）：每个请求一个虚拟线程，threads.max 不再是并发上限；max-connections 仍然生效，成为容器层唯一的并发闸门；accept-count 属于 OS 监听队列，与线程模型无关
  • 瓶颈转移到下游连接池，必须用连接池大小或信号量限制下游并发；synchronized 块内阻塞会钉住载体线程（JDK 24 起已改善）

→ 详见 并发参数调优

Q69：数据库连接池是不是越大越好？水平扩容时要注意什么？

核心结论：不是，池大小由数据库并行能力决定（原理见 Q15）。扩容时要守住全局上限：所有应用实例 maximumPoolSize 之和 ≤ 数据库 max_connections × 80%，剩下 20% 留给运维、监控、定时任务与故障时的连接重建。

  • 这是上限不是目标值：max_connections=2000、40 个实例时单实例池最多 40；实际按 Little 定律确定，单实例 QPS 500、持有 10ms 平均只需约 5 个连接
  • 扩容前重新核算：实例从 40 扩到 80，单实例池不调小就会超限，新实例启动即报 Too many connections
  • 多个服务共用一个库时，上限要在服务之间分配

→ 详见 并发参数调优、池化技术

Q70：Lettuce 需要配置连接池吗？什么时候池才会被使用？

核心结论：通常不需要。Lettuce 基于 Netty，单连接多路复用且线程安全；Spring Data Redis 的 LettuceConnectionFactory 默认 shareNativeConnection = true，即使配置了连接池，普通 GET / SET 等命令仍然走同一条共享连接，max-active 对它们基本不起作用。

池只在以下情况被使用：

  • 阻塞命令（BLPOP、BRPOP、XREAD BLOCK 等），避免阻塞共享连接
  • 事务（MULTI / EXEC、WATCH），需要独占连接
  • 显式 setShareNativeConnection(false) 后，所有操作都从池中借连接
客户端连接模型是否需要池
Lettuce（Spring Boot 默认）单连接多路复用仅阻塞命令、事务；启用池需引入 commons-pool2
Jedis阻塞 IO，一个连接同时只处理一个请求必须用池，maxTotal ≈ 访问 Redis 的并发线程峰值
Redisson基于 Netty，内置连接池调 connectionPoolSize 等
  • Redis 变慢时先查共享连接上的命令延迟与大 key，而不是一味调大 max-active

→ 详见 并发参数调优

Q71：服务器出现大量 TIME_WAIT 是什么原因？如何解决？

核心结论：TIME_WAIT 出现在主动关闭连接的一方，要等待 2MSL 才释放。大量 TIME_WAIT 的根因通常是短连接：调用下游 HTTP 没用连接池、没开 Keep-Alive。应优先修复连接复用，而不是只调内核参数。

9、容量评估

Q72：如何从 DAU 估算系统的峰值 QPS？

核心结论：日请求量 = DAU × 人均操作次数 × 每次操作的接口调用数，平均 QPS = 日请求量 / 86400，峰值 QPS = 平均 QPS × 峰值系数，再用历史数据修正。峰值而不是均值决定要准备多少容量。

项目（商品详情服务示例）数值
DAU × 人均浏览 × 每次调用500 万 × 20 × 1 = 1 亿 / 天
平均 QPS1 亿 / 86400 ≈ 1157
日常峰值二八原则 日请求量 × 80% / (86400 × 20%) ≈ 平均 × 4 ≈ 4600
大促峰值日常峰值 × 10（历史大促数据）≈ 4.6 万
  • 日常峰值系数 2～5，大促 / 秒杀可达 10～100；按同类活动历史峰值比与业务增长率修正
  • 警惕瞬时峰值：秒杀开始前 1 秒可能是分钟均值的数十倍，按分钟监控数据会严重低估
  • 写入量单独估：下单转化 2% 时，下单峰值 ≈ 4.6 万 × 2% ≈ 920 TPS

→ 详见 容量评估与规划

Q73：如何评估单机能力？需要多少台机器？多可用区部署时冗余系数怎么算？

核心结论：单机能力只能压测得出，取"P99 满足 SLA 且 CPU ≤ 70%"时的 QPS 作为单机容量点。机器数 = ⌈峰值 QPS / 单机 QPS × 估算误差系数 × 故障冗余系数⌉；部署在 N 个可用区、要容忍 1 个可用区故障时，冗余系数为 N / (N − 1)（2 个可用区为 2，3 个为 1.5，4 个约 1.33）。

步骤（峰值 4.6 万 QPS，单机 1500，3 个可用区）结果
基础机器数 46000 / 1500 ≈ 30.7至少 31 台
故障冗余：剩余 2 个可用区要扛全部流量，每区 ≥ ⌈30.7 / 2⌉ = 163 × 16 = 48 台
验证：任一可用区故障，剩余 32 × 1500 = 48000 ≥ 46000满足
再叠加估算误差 1.2（可选）3 × 19 = 57 台
  • 压测环境与生产同规格、按真实流量比例混合接口、阶梯加压；单可用区部署按 N+1 冗余
  • 别忘了下游：48 台 × 单实例连接池是否超过 max_connections × 80%，Redis、MQ 同理

→ 详见 容量评估与规划

Q74：什么是全链路压测？如何保证压测数据不污染生产？（流量染色、影子库、挡板）

核心结论：单机压测证明不了网关、中间件、数据库、第三方这些共享环节，全链路压测在生产环境用真实链路跑压测流量。不污染生产靠五件事：流量染色透传、影子存储、下游挡板、数据隔离清理、熔断开关。

环节做法
流量染色压测请求带 X-Stress-Test 等标记；网关校验来源，外部请求带该头一律剥离
全链路透传进程内 TransmittableThreadLocal；RPC / HTTP 放请求头或 Baggage；MQ 写消息属性；定时任务在任务数据上记标记
影子存储影子库 / 影子表、影子 key 前缀（设 TTL）、影子 topic + 影子消费组；按标记路由数据源
下游挡板支付、短信等第三方按标记返回模拟结果，并注入与生产相近的 RT
数据隔离与清理压测账户用独立 ID 段；不进结算、对账、报表；结束后清理；定期扫描生产库发现压测数据即告警
  • 影子库要按生产数据量级准备数据，否则压出来的是"小表性能"

→ 详见 容量评估与规划

Q75：生产环境压测有哪些风险？如何控制？

核心结论：风险是压测流量挤占真实用户资源、压垮共享组件、数据写错地方。首要目标是不影响真实用户，必须能随时一键停止。

措施做法
时间窗口业务低峰期，提前通知相关团队与值班
分级加压目标量的 10% → 30% → 50% → 100%，每级稳定后再加
实时监控同时盯压测流量与真实流量的 RT、错误率，以及核心资源水位
自动熔断真实流量 P99 或错误率超阈值、核心资源水位超过设定值（如 80%）时自动停止发压
手动开关配置中心全局开关，网关直接拦截所有带压测标记的请求
预案事先准备扩容、限流、降级预案，压测中发现瓶颈当场验证

→ 详见 容量评估与规划

Q76：大促前需要做哪些准备？

核心结论：主线是"估算 → 扩容 → 压测验证 → 预热 → 值守 → 复盘"，按时间节点提前排好，并按业务优先级梳理降级开关。

阶段事项
T-30 天流量预估；全链路压测找瓶颈；确定扩容清单（应用、DB、Redis、MQ 分区）
T-7 天完成扩容并再次压测；梳理降级开关与限流阈值；封网
T-1 天缓存预热；检查降级开关可用；值班与应急联系人就位
大促中实时监控水位；按预案逐级降级；热点探测与动态限流
大促后分批缩容；复盘峰值与瓶颈，沉淀下次的峰值系数
优先级功能降级方式
P0 核心下单、支付、库存不降级，限流保护
P1 重要商品详情、购物车静态兜底数据 / 延长缓存
P2 次要评论、推荐、足迹直接关闭，返回空

Q77：容量水位如何监控？HPA 扩容阈值和容量规划水位有什么区别？

核心结论：水位 = 当前峰值 / 容量上限，容量上限来自压测（单机容量点 × 实例数，弹性伸缩时按 maxReplicas 计算，下游按各自上限）。HPA 阈值与规划水位口径不同：HPA 按单 Pod CPU 分钟级自动扩缩，目标常取 60%；规划水位按 QPS 与集群容量上限计算，用于天 / 周级的人工决策。

水位状态动作
< 50%健康可评估缩容
50% ~ 70%正常关注增长趋势
70% ~ 85%预警启动扩容评估：调高 maxReplicas、下游扩容、申请资源
> 85%危险立即扩容，准备限流降级
  • HPA 目标（60%）低于单机容量点（70%），差值是扩容生效前的缓冲（调度、拉镜像、启动、预热需要分钟级）
  • HPA 能把单 Pod CPU 稳在 60%，但扛不住"副本已到 maxReplicas"或"数据库先到顶"，这正是规划水位要提前发现的
  • 监控指标：QPS、P99 / P999、错误率、GC、线程池活跃与队列、连接池活跃与等待、下游 RT；告警区分趋势预警（按周增长预测触顶）与实时告警

→ 详见 容量评估与规划、水平扩展与无状态化

1、可用性度量

Q78：SLA 99.99% 意味着每年多少故障时间？每月呢？

核心结论：99.99%（4 个 9）每年约 52.6 分钟，每月（按 30 天）约 4.32 分钟，每周约 1 分钟。

可用率年停机月停机
99%≈ 3.65 天≈ 7.2 小时
99.9%≈ 8.76 小时≈ 43.2 分钟
99.95%≈ 4.38 小时≈ 21.6 分钟
99.99%≈ 52.6 分钟≈ 4.32 分钟
99.999%≈ 5.26 分钟≈ 25.9 秒
  • 每多一个 9，成本通常数量级上升：4 个 9 要求单次故障分钟级自动恢复，人工介入基本来不及，必须依赖自动故障转移
  • 互联网核心业务一般以 99.95%～99.99% 为目标，目标不是越高越好

Q79：SLA、SLO、SLI 分别是什么？三者什么关系？

核心结论：SLI 是度量，SLO 是目标，SLA 是合同。SLO 必须比 SLA 更严格，给团队留出反应余量，例如 SLA 99.9%、SLO 99.95%。

概念含义示例
SLI可量化的服务质量指标非 5xx 请求占比、延迟 < 300ms 的请求占比
SLO对 SLI 设定的内部目标30 天滚动窗口内成功率 ≥ 99.9%
SLA对外承诺，违约有赔偿月可用率 < 99.9% 返还 10% 服务费
  • 延迟 SLI 用"达标请求占比"而不是平均值，可直接参与错误预算计算
  • 从用户视角（网关 / 负载均衡入口）统计；按关键链路分别定义；用 28 或 30 天滚动窗口；先按历史数据定，再逐步收紧

→ 详见 可用性度量

Q80：什么是错误预算？如何用它约束发布节奏？

核心结论：错误预算 = 1 − SLO，是一个周期内允许"不可用"的额度。SLO 99.9% 时，30 天预算为 43.2 分钟，或月 1 亿请求中 10 万次失败。按剩余预算决定发布节奏：

预算状态策略
剩余 > 50%正常迭代，可以做有风险的发布与实验
剩余 10% ~ 50%放慢节奏，发布必须灰度，加强变更评审
剩余 < 10%冻结功能发布，只允许稳定性修复与紧急安全补丁
已耗尽全面冻结，投入可靠性改进直到窗口内预算恢复
  • 错误预算把"开发要快、运维要稳"变成共同规则，需要研发、测试、运维、产品事先共同认可才能执行

Q81：为什么基于燃烧速率告警比直接按错误率告警更好？

核心结论：燃烧速率 = 实际错误率 / (1 − SLO)，直接对应"按当前速度多久会耗尽预算"。固定错误率阈值不区分持续时间：短暂尖刺会误报，长时间的小幅泄漏会漏报；燃烧速率告警只在真正威胁 SLO 时触发。

告警级别长窗口短窗口燃烧速率消耗 30 天预算
立即呼叫（Page）1 小时5 分钟14.42%
立即呼叫（Page）6 小时30 分钟65%
工单（Ticket）3 天6 小时110%
  • 长短双窗口同时满足才触发：长窗口保证显著性，短窗口保证恢复后告警及时解除
  • 例：SLO 99.9% 时，Page 规则为 1h 与 5m 错误率都 > 14.4 × 0.001

Q82：MTBF、MTTR 是什么？提升可用性应优先降低哪一个？

核心结论：MTBF 是平均无故障时间，MTTR 是平均恢复时间（含发现、定位、止血），可用率 = MTBF / (MTBF + MTTR)。工程上优先降低 MTTR 更划算：故障无法杜绝，但"先止血后定位"能把分钟级恢复变为常态。

指标改进手段
MTBF代码质量、容量规划、变更管控、混沌演练
MTTD（平均发现时间）基于 SLO 的告警、拨测、链路追踪
MTTR自动故障转移、一键回滚、降级开关、预案
  • 例：平均 720 小时出一次故障、每次恢复 1 小时，可用率 = 720 / 721 ≈ 99.86%；恢复缩到 6 分钟即接近 99.99%

→ 详见 可用性度量、故障应急与复盘

Q83：四个 99.9% 的服务串联，整体可用率是多少？两个 99% 的实例并联呢？

核心结论：串联 A = A₁ × A₂ × … × Aₙ，四个 99.9% 串联为 0.999⁴ ≈ 99.6%（年停机约 35 小时）；并联 A = 1 − (1 − A₁)ⁿ，两个 99% 并联为 1 − 0.01² = 99.99%。

  • 串联的依赖越多，整体可用率越低，且低于其中最差的组件，所以要减少同步强依赖，非核心依赖异步化或可降级
  • 混合系统找短板：LB 99.99% → 两个 99.9% 应用并联（99.9999%）→ 单主库 99.95%，整体约 99.94%，再加应用实例几乎无收益，瓶颈是数据库单点
  • 并联公式假设故障相互独立；同机架断电、同一版本 Bug、共享配置中心故障会让副本同时失效，冗余要跨故障域部署、发布要灰度

→ 详见 可用性度量

Q84：冷备、温备、热备有什么区别？

核心结论：区别在备用节点平时的状态和数据同步方式，决定了切换时间（RTO）和成本。

类型备用节点状态数据同步RTO成本
冷备未运行，只有备份文件定期全量备份小时级 ~ 天级低
温备已部署但不承接流量异步复制，可能落后分钟级中
热备运行中，随时接管实时 / 半同步复制秒级 ~ 分钟级高
多活同时承接流量双向同步或分片隔离秒级（切流即可）最高
  • 冷备不等于没用：备份是防误删、防勒索的最后防线，复制会把 DELETE 同步到所有副本；备份必须定期做恢复演练

Q85：主备、主主、集群三种模式各有什么优缺点？

核心结论：主备简单无写冲突但备节点闲置、切换有中断；主主资源利用率高但有写冲突；集群靠多数派自动选主、可扩展但实现复杂。

Q86：K8s 的 liveness 和 readiness 探针有什么区别？为什么探针不建议检查数据库等共享依赖？

核心结论：liveness 问"还活着吗，要不要重启"，失败即重启容器；readiness 问"现在能接流量吗"，失败只从 Service Endpoints 摘除、不重启。两者都不应包含 DB、Redis、下游服务等共享依赖。

探针失败后果应检查不应检查
startupProbe超阈值重启；成功前不执行另外两个探针是否启动完成—
livenessProbe重启容器进程自身是否已无法恢复（死锁、事件循环卡死）任何外部依赖
readinessProbe摘除流量，不重启本实例能否接流量（预热完成、未在停机中）多实例共享的依赖

为什么不查共享依赖：

  • 共享依赖一抖动，所有实例同时判定失败：liveness 会让所有实例一起重启；readiness 会让 Service 后面没有任何 Endpoint，局部依赖故障被放大成 100% 不可用

  • 摘流量解决不了共享依赖的问题：换到哪个实例，连的都是同一个 DB

  • 依赖故障应由调用路径的超时、熔断、降级处理，让能服务的请求继续服务

  • Spring Boot 2.3+ 提供 /actuator/health/liveness 与 /readiness，readiness 组默认只含 readinessState；开启 add-additional-paths 在主端口探测 /livez、/readyz，避免独立管理端口掩盖业务端口卡死

Q87：Keepalived 如何实现 VIP 漂移？

核心结论：Keepalived 基于 VRRP 协议，多台节点中优先级最高的成为 Master 并持有虚拟 IP（VIP），定期发送通告；Backup 在超时时间内收不到通告，或 Master 的健康检查脚本失败导致优先级下降时，Backup 接管 VIP，秒级完成切换。

  • track_script 定时检查 Nginx 等进程，失败时 weight -20 降低优先级触发切换
  • 两台都配 state BACKUP + nopreempt，避免原主恢复后抢回 VIP 造成二次抖动
  • 风险是脑裂：心跳线中断时两台都持有 VIP，需第三方仲裁（如检测网关连通性），见 Q88

Q88：什么是脑裂？有哪些防护手段？fencing token 是什么？

核心结论：脑裂是网络分区导致两侧都认为对方故障，同时存在两个"主"并各自接受写入，恢复后数据冲突甚至无法合并。核心防护是多数派仲裁，并让存储层能拒绝"旧主"的写入。

防护手段原理示例
多数派仲裁只有拿到多数票的一方能成为主Raft、Sentinel quorum、MGR
Fencing Token每次选主递增任期号，存储层拒绝旧任期写入Raft term、ZooKeeper zxid、分布式锁的递增 token
STONITH切换前强制隔离旧主（断电、摘网卡、撤权限）Pacemaker、云 API 关停实例
旧主自我降级联系不上足够副本时拒绝写入Redis min-replicas-to-write
第三方仲裁仲裁节点 / 仲裁机房判断谁存活两地三中心仲裁点
  • fencing token：旧主可能只是暂停（Full GC、网络抖动）而未真正下线，恢复后仍以为自己是主；每次写入携带单调递增的 token，存储层记录见过的最大 token，拒绝更小的，旧主的写入就会失败
  • 集群取奇数节点：3 节点容忍 1 个故障，5 节点容忍 2 个

Q89：MySQL 主库宕机如何自动切换？MHA、Orchestrator、MGR 有什么区别？

核心结论：自动切换 = 监控判定主库故障 → 选出数据最新的从库提升为主 → 其余从库改指向新主 → 应用连接切到新主。MHA 与 Orchestrator 基于传统主从复制做外部切换，MGR 是基于 Paxos 的组复制、内置选主。

方案原理切换一致性
MHA监控主库，故障时从最新从库补齐差异 binlog 并提升自动，30s 左右尽力补齐；项目已多年未维护
Orchestrator识别复制拓扑，自动提升并重建拓扑，自身基于 Raft 高可用自动，秒级依赖复制模式
MGR / InnoDB Cluster组复制，单主模式自动选主自动，秒级；需多数派存活多数派确认，强一致

应用侧配合：

  • 连接串不写死主库 IP：用 VIP、DNS、ProxySQL / MySQL Router 等代理
  • 连接池设合理的 maxLifetime 和连接校验，避免长时间持有指向旧主的连接
  • 半同步复制降低切换丢数据风险，但退化为异步时仍可能丢

→ 详见 冗余与故障转移

Q90：如何梳理强弱依赖？弱依赖故障时怎样保证主链路不受影响？

核心结论：强依赖是失败即核心功能无法完成且无替代结果的依赖（库存扣减、订单写库、支付）；弱依赖失败时核心功能仍可完成（推荐、积分、评价）。梳理后要让弱依赖真正"弱"：超时短、可熔断、可降级或改为异步，并用故障注入验证。

梳理方法：

  1. 从链路追踪拓扑出发列出每个核心接口的全部下游，而不是凭印象
  2. 由业务方逐个确认"这个依赖挂了，功能还能不能用"
  3. 对标注为弱依赖的下游注入延迟与异常，核心接口成功率不应下降

保证主链路：

  • 最常见的问题是弱依赖被写成了强依赖：同步调用、没有超时或超时过长、异常直接抛出、结果被当成必填字段，要逐一检查代码路径
  • 每个依赖写好预案：超时与重试、熔断阈值、降级方式、开关位置与负责人、恢复条件
  • 不需要在请求内拿到结果的调用（发积分、发通知）改为事件异步处理，下游故障只造成消息积压

→ 详见 冗余与故障转移

3、负载均衡

Q91：常见负载均衡算法有哪些？一致性哈希解决什么问题？

核心结论：实例同构、请求耗时相近用轮询；耗时差异大看连接数或响应时间（最少连接、P2C）；需要"同一个 key 落到同一实例"用哈希。一致性哈希解决的是扩缩容时只迁移少量 key，而普通取模在节点数变化时几乎所有 key 都要重新映射。

算法适用场景注意事项
轮询 / 加权轮询实例配置相同或按权重分配、预热期逐步放量Nginx 用平滑加权轮询，避免连续打到同一实例
随机 / 加权随机客户端负载均衡小流量下分布不均
最少连接长短请求混合、长连接新实例会被瞬间灌满，需配合预热
P2C实例性能波动大的 RPC随机挑两个取较优，Envoy LEAST_REQUEST 默认即 P2C
一致性哈希本地缓存亲和、有状态服务、分布式存储热点 key 导致单实例过载；用虚拟节点改善均匀度

→ 详见 负载均衡、一致性哈希

Q92：四层负载均衡和七层负载均衡的区别？

核心结论：四层按 IP + 端口转发连接、不解析内容，性能极高，负责"扛连接"；七层解析 HTTP，可按 URL / Header 路由、做 TLS 卸载、鉴权与限流，负责"懂业务"。生产上四层做入口 VIP，后面挂多台七层网关。详细对比见 Q38。

  • 高可用视角的差异：四层健康检查通常只到 TCP 端口级，七层可以探测 HTTP 健康接口并按状态码做失败转移

→ 详见 接入层架构、负载均衡

Q93：服务端负载均衡与客户端负载均衡（Spring Cloud LoadBalancer）有什么区别？

核心结论：服务端负载均衡是独立的代理层（Nginx / LVS / SLB），对调用方透明；客户端负载均衡是调用方从注册中心拉取实例列表、在本地进程内选择实例，少一跳、无代理单点，是微服务间调用的主流方式。

对比服务端（Nginx / LVS / SLB）客户端（SCL / Dubbo）
位置独立代理层调用方进程内
实例列表静态配置或服务发现集成注册中心推送 / 拉取，本地缓存
优点透明、语言无关少一跳、无代理单点、可按调用上下文路由
缺点多一跳、代理需要高可用每种语言要 SDK；实例列表有感知延迟
  • Spring Cloud LoadBalancer（替代已停止维护的 Ribbon）：默认轮询，可换随机或按元数据 weight 加权；支持区域优先（同可用区优先，无可用实例再跨区）与 Hint 路由；实现 ReactorServiceInstanceLoadBalancer 可按版本、标签做灰度
  • 灰度路由要求灰度标记全链路透传（Feign 拦截器、MQ 消息头）

→ 详见 负载均衡、Spring Cloud 服务治理

Q94：负载均衡如何配合健康检查摘除故障实例？会话保持有哪些做法？

核心结论：主动检查（定时探测健康接口）与被动检查（按真实请求失败 / 超时摘除）结合使用；失败转移只对幂等请求开启并限制次数。会话保持是给有状态服务打的补丁，优先做无状态化。

  • Nginx 开源版只支持被动检查：max_fails=3 fail_timeout=10s，配合 proxy_next_upstream error timeout 与 proxy_next_upstream_tries 2；主动检查需 Nginx Plus 或 Tengine 的 upstream check 模块
  • 非幂等请求（POST）默认不会转发到下一个实例，不要随意加 non_idempotent
  • 注册中心摘除有感知延迟（Nacos 2.x 秒级，Eureka 可达 2～3 分钟），调用方要配合超时、重试其他实例与熔断
会话保持方式问题
IP 哈希NAT / 代理后大量用户共用一个 IP，负载严重倾斜
Cookie 粘滞实例故障时会话仍然丢失
一致性哈希（按 userId）扩缩容时部分用户迁移
无状态化（推荐）Session 外置到 Redis 或改用 Token

→ 详见 负载均衡、冗余与故障转移

4、超时、重试与隔离

Q95：超时设置的原则是什么？上下游超时应该如何配合？

核心结论：每一次跨进程调用都必须显式设置超时，按下游 P99～P999 加 20%～50% 余量、按接口分别配置。上下游配合的规则是"越靠近用户越长，越靠近数据越短"，上游超时必须覆盖下游的全部尝试。

超时类型建议
连接超时同机房 100ms ～ 1s，连不上通常意味着实例不可用
读取超时按下游 P99～P999 加余量
获取连接超时几百毫秒，池耗尽时快速失败
整体超时 / deadline由上游剩余时间决定
  • 很多客户端默认超时过长或不超时：OpenFeign 默认连接 10s、读取 60s，JDBC 驱动 socketTimeout 默认 0（不限）
  • 上游超时推导：T_上游 ≥ T × (N + 1) + B + S（T 下游单次超时、N 重试次数、B 退避总时长、S 自身耗时）；算不过来时缩短下游超时、减少重试或去掉某一层重试，而不是加大上游超时
  • 开启 Spring Cloud CircuitBreaker + Resilience4j 时 TimeLimiter 默认只有 1s，可能先于 Feign 读超时触发，要显式配置并保持一致

→ 详见 超时、重试与隔离

Q96：重试适用于哪些场景？非幂等接口能直接加重试吗？

核心结论：重试只用来消化短暂故障（网络抖动、实例切换），且只对幂等操作开启。非幂等接口不能直接加重试：读取超时时下游可能已经执行成功，重试会造成重复扣款、重复下单，必须先做幂等（幂等键、唯一约束、状态机）。

错误类型是否重试
连接失败、连接被拒绝可以，请求未到达下游，换实例最安全
读取超时仅幂等操作
503 / 429 过载信号谨慎，遵守 Retry-After
4xx 参数错误、业务异常不重试
熔断打开（CallNotPermittedException）不重试

→ 详见 超时、重试与隔离、幂等设计

Q97：指数退避是什么？为什么要加 Jitter？

核心结论：指数退避让每次重试的等待时间按指数增长（100ms、200ms、400ms…），给下游恢复时间；Jitter（随机抖动）把大量客户端的重试时刻打散，避免它们在同一时刻集中重试、形成周期性尖峰。

RetryConfig config = RetryConfig.custom()
    .maxAttempts(3)                                   // 总调用次数（含首次）
    .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(
        Duration.ofMillis(100), 2.0, 0.5, Duration.ofSeconds(2)))  // 初始、倍数、±50% 抖动、上限
    .ignoreExceptions(BusinessException.class, CallNotPermittedException.class)
    .build();
  • 在线请求的重试等待控制在百毫秒级，整体仍要落在上游超时之内；秒级、分钟级退避只适合异步任务和消息重投

→ 详见 超时、重试与隔离

Q98：什么是重试放大？如何用"只在一层重试"、重试预算、deadline 传播来控制？

核心结论：每层都"重试 3 次"时放大是乘法：3 层调用、每层最多 3 次尝试，最底层会收到 3 × 3 × 3 = 27 倍请求，下游本来只是过载，被重试流量直接打垮。

规则做法
只在一层重试放在直接调用不稳定依赖的那一层，其他层失败直接向上返回
单请求限次最多尝试 2～3 次，换实例重试（proxy_next_upstream_tries、SCL 重试）也计入
重试预算按客户端统计，重试量不超过正常请求的一定比例（如 10%），超出直接失败；可用令牌桶实现：成功返还 ratio 个额度，每次重试消耗 1 个
deadline 传播上游把剩余时间传给下游，下游用 min(自身超时, 剩余时间)，剩余不足时不再调用或重试
  • gRPC 原生支持 deadline 传播；HTTP 自行约定请求头（如 X-Timeout-Ms），传相对时长而不是绝对时间戳，避开机器间时钟偏差
  • Resilience4j 默认装饰顺序中 Retry 在最外层，每次尝试都经过熔断统计，CallNotPermittedException 必须排除在重试之外

→ 详见 超时、重试与隔离

Q99：线程池隔离和信号量隔离的区别？各自适用什么场景？

核心结论：线程池隔离给每个依赖独立线程池，慢调用只占隔离池线程，调用方可按超时放弃等待，隔离最强但有线程切换开销；信号量隔离只限制并发数，调用仍在当前线程执行，几乎无开销但慢调用仍占调用方线程。

对比线程池隔离信号量隔离
隔离程度强中
开销线程切换、上下文传递（ThreadLocal、链路追踪需额外处理）几乎没有
超时控制调用方可放弃等待（Future 超时）依赖下游客户端自身超时
适用外部 HTTP 调用、慢且不稳定的依赖内部快速依赖、调用量大的场景
  • 配额按 Little 定律估算：并发 ≈ 该依赖 QPS × P99 延迟，如 200 QPS、P99 50ms 稳态约 10，配额取 15～20
  • 实现：Resilience4j ThreadPoolBulkhead / Bulkhead、Sentinel 并发线程数限流

→ 详见 超时、重试与隔离

5、熔断

Q100：熔断器的三种状态是什么？如何切换？半开状态放行多少请求？

核心结论：Closed 正常放行并统计失败率 / 慢调用率 → 超过阈值进入 Open，直接拒绝走降级 → 熔断时长到期进入 Half-Open，放行少量探测请求 → 探测成功回到 Closed，失败回到 Open 并重新计时。

状态行为进入条件
Closed正常放行，持续统计初始状态；或半开探测成功
Open直接拒绝，不调用下游统计窗口内指标超过阈值
Half-Open放行少量探测请求Open 持续熔断时长后自动进入
  • 半开放行数：Sentinel 只放行 1 个探测请求；Resilience4j 放行 permittedNumberOfCallsInHalfOpenState 个（默认 10，建议显式配置），按这批请求的失败率判断

→ 详见 熔断

Q101：熔断有哪几种策略？慢调用阈值、最小请求数、熔断时长怎么定？

核心结论：三类策略——慢调用比例、异常比例、异常数。慢调用比例最常用，因为"变慢"往往比"报错"更早出现，也更伤资源。

参数建议
慢调用 RT 阈值下游正常 P99 的 1.5 ~ 2 倍，且小于调用方超时
比例阈值50% ~ 60%，太低容易误熔断
最小请求数按低峰期流量设定，避免"2 个请求失败 1 个就熔断"
统计窗口5 ~ 10s（时间窗口）或最近 50 ~ 100 次（计数窗口）
熔断时长5 ~ 30s，与下游典型恢复时间匹配
  • 异常数策略适合调用量小、比例波动大的接口
  • Resilience4j 默认值偏宽松：minimumNumberOfCalls 与 slidingWindowSize 均为 100，waitDurationInOpenState 60s，slowCallDurationThreshold 60s，每个实例都应显式设置
  • 熔断粒度推荐按接口，而不是按整个依赖服务

→ 详见 熔断

Q102：哪些异常应该计入熔断统计，哪些不应该？

核心结论：只计入反映下游健康度的失败；与下游健康无关的业务异常不计入，否则会误熔断。

  • 计入：超时、连接失败、5xx、下游返回的"系统繁忙"类错误
  • 不计入：参数校验失败、业务规则拒绝（如余额不足）等 4xx 类业务异常，Resilience4j 用 ignore-exceptions 配置
  • 被熔断拒绝本身（CallNotPermittedException、DegradeException）不能再被重试，否则熔断形同虚设

→ 详见 熔断

Q103：Sentinel、Hystrix、Resilience4j 的区别？新项目怎么选？

核心结论：新项目在 Sentinel 和 Resilience4j 之间选：用 Spring Cloud Alibaba 体系、需要控制台动态调规则选 Sentinel；追求轻量、与 Spring Cloud CircuitBreaker 标准集成选 Resilience4j。Hystrix 2018 年起进入维护模式，不再用于新项目。

统计窗口滑动时间窗口计数或时间窗口滑动时间窗口

其他能力限流、热点参数、系统自适应保护限流、重试、TimeLimiter请求合并、缓存

Spring 集成Spring Cloud AlibabaSpring Cloud CircuitBreaker已从 Spring Cloud 2020 移除

→ 详见 熔断

Q104：@SentinelResource 的 blockHandler 和 fallback 有什么区别？

核心结论：blockHandler 只处理 Sentinel 规则触发抛出的 BlockException（流控、熔断、系统保护）；fallback 处理业务代码抛出的异常。两者都配置时，被限流熔断走 blockHandler。

  • blockHandler 方法签名 = 原方法参数 + 最后一个 BlockException 参数，必须 public；放在其他类时用 blockHandlerClass 指定，且方法为 static
  • fallback 方法参数与原方法一致，可额外加一个 Throwable 参数
  • 非幂等写操作的兜底不要静默返回成功，应抛出明确异常

6、降级

Q105：降级和熔断有什么区别和联系？

核心结论：熔断回答"要不要继续调用下游"，是被动触发的保护机制；降级回答"停止之后返回什么、放弃什么"，是预先定义的应对策略。熔断打开后通常执行降级逻辑，但降级不一定由熔断触发。

对比熔断降级
性质被动触发的保护机制预先定义的应对策略
触发下游失败率 / 慢调用率超阈值熔断、限流、超时、异常，或人工打开开关
关注点是否调用下游返回什么、放弃什么

→ 详见 降级

Q106：服务降级有哪些级别和手段？如何给功能分级？

核心结论：按业务重要性给功能分为核心、重要、一般、边缘四级，故障时从最不重要的开始放弃；核心链路不降级，只能靠扩容和限流保护。

级别示例降级策略
核心下单、支付、登录不降级，扩容、限流保护
重要库存展示、优惠计算返回缓存或近似值
一般推荐、评论、足迹返回兜底数据或隐藏
边缘埋点、日志上报、报表直接关闭或改为异步
手段示例
返回兜底数据个性化推荐改为热销榜
关闭功能大促期间关闭商品评价
读降级读缓存或静态快照
写降级同步写改为 MQ 异步，稍后补偿
精度降级实时销量改为分钟级更新
页面降级活动页切换为 CDN 静态快照
提示降级"系统繁忙，请稍后重试"

→ 详见 降级

Q107：静态降级和动态降级（开关）分别怎么实现？

核心结论：静态降级写死在代码里，由异常自动触发（fallback 兜底）；动态降级由配置中心开关控制，无需重启即可生效。两者配合：静态降级兜住意外故障，动态开关用于预案和人工干预。

  • 静态降级：@SentinelResource(fallback = ...)、Resilience4j fallbackMethod，兜底返回本地缓存的热销榜等，并上报降级指标
  • 动态降级：开关放在 Nacos 等配置中心，用 @ConfigurationProperties 绑定（配置变更后自动刷新，无需 @RefreshScope），代码中判断开关关闭时直接走兜底、不再调用下游
  • 每个手动开关写清打开条件、影响范围、负责人和恢复条件，纳入故障预案

→ 详见 降级

Q108：Sentinel 规则持久化到 Nacos 后，控制台修改的规则为什么重启会丢失？

核心结论：因为数据流是单向的。sentinel-datasource-nacos 只负责从 Nacos 拉取并监听规则；Sentinel 控制台默认把规则直接推到应用内存，不会写回 Nacos。应用重启后重新从 Nacos 加载，控制台上改的规则就丢了。

  • 解决一：改造 Dashboard 的规则发布逻辑，让控制台修改写入 Nacos（推模式），应用再从 Nacos 监听生效
  • 解决二：约定只在 Nacos 中修改规则，控制台仅用于查看

→ 详见 降级、Spring Cloud Alibaba - Sentinel

Q109：降级逻辑设计时要注意什么？为什么非幂等写操作不能静默降级？

核心结论：降级逻辑平时不执行，最容易在真正需要时失效，所以要有业务价值、不依赖故障源、可观测、定期演练。非幂等写操作若静默返回"成功"，用户以为下单 / 扣款成功而实际没有执行，造成数据不一致和客诉，用户重试还可能重复执行，必须明确报错或改为"受理 + 异步处理"。

  • 兜底数据要有业务价值：避免返回 null 或空列表导致前端报错
  • 降级逻辑不依赖故障源：推荐服务故障时兜底不能再调推荐服务，也不要调另一个同样可能过载的远程服务
  • 可观测：每次降级打日志、上报指标，降级量突增要告警
  • 避免级联降级：A 的兜底依赖 B 的数据，B 也在降级，最终返回无意义数据
  • 定期演练：真实打开开关、注入故障验证降级路径

→ 详见 降级

7、限流与过载保护

Q110：常见限流算法有哪些？令牌桶和漏桶的区别？

核心结论：四种——固定窗口、滑动窗口、令牌桶、漏桶。令牌桶允许突发（空闲时攒下的令牌可被瞬间消耗），适合入口限流；漏桶强制匀速输出、不允许突发，适合保护处理能力固定的下游。

算法突发流量典型场景
固定窗口边界处可达 2 倍阈值粗粒度配额（如每天调用次数）
滑动窗口平滑，精度取决于子窗口数服务端 QPS 统计（Sentinel）
令牌桶允许，上限为桶容量网关、用户级 / API 级限流（Guava RateLimiter、Gateway RedisRateLimiter）
漏桶不允许第三方 API 配额、匀速写入（Sentinel "匀速排队"）

→ 详见 限流与过载保护

Q111：固定窗口限流有什么问题？滑动窗口如何解决？

核心结论：固定窗口有临界突发：窗口 1 的最后 100ms 和窗口 2 的最前 100ms 各放行 100 次，200ms 内实际通过 200 次，是阈值的 2 倍。滑动窗口把大窗口拆成多个子窗口随时间滑动，只统计最近 N 个子窗口的总和，子窗口越多越平滑、内存越大。

  • Sentinel 秒级统计就是滑动窗口（LeapArray），默认 1s 拆成 2 个 500ms 子窗口
  • 分布式场景可用 Redis ZSET 记录每次请求时间戳实现精确滑动窗口（见 Q112）

→ 详见 限流与过载保护

Q112：如何用 Redis + Lua 实现滑动窗口限流？member 和时间戳要注意什么？

核心结论：用 ZSET 以时间戳为 score 记录每次请求，Lua 脚本原子完成"清理窗口外记录 → 计数 → 写入"。两个关键细节：member 必须唯一，时间取 Redis 服务端时间。

-- KEYS[1] 限流 key；ARGV[1] 窗口毫秒；ARGV[2] 上限；ARGV[3] 本次请求唯一 ID
local key, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2])
local t = redis.call('TIME')                                  -- Redis 服务端时间，避免多实例时钟漂移
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)          -- 清理窗口外记录
if redis.call('ZCARD', key) < limit then
    redis.call('ZADD', key, now, now .. '-' .. ARGV[3])        -- member 唯一，同毫秒请求不互相覆盖
    redis.call('PEXPIRE', key, window)
    return 1
end
return 0
  • member 若直接用时间戳，同一毫秒的多个请求会互相覆盖、少计数
  • Lua 中先调用 TIME 再写入要求 Redis 5+（默认按效果复制），更老版本需 redis.replicate_commands()
  • ZSET 每个请求占一个元素，内存与阈值成正比，只适合阈值较小的场景；阈值大时用令牌桶或子窗口计数
  • Redis 不可用时要有降级策略：放行（fail-open）并依赖单机限流兜底，强管控场景改为拒绝

→ 详见 限流与过载保护

Q113：限流应该放在哪一层？网关限流能替代服务内限流吗？

核心结论：多层叠加，越靠外越粗粒度、越省资源，越靠内越精确、越贴近真实容量。网关限流不能替代服务内限流：网关管的是集群总量，挡不住负载不均或部分实例变慢时的单机过载，自我保护的限流必须在服务内做。

层次典型实现维度主要作用
接入层CDN / WAF、Nginx limit_reqIP、URL挡恶意刷量和 CC 攻击
网关Spring Cloud Gateway、APISIX + Redis 令牌桶用户、租户、API集群级配额，按调用方公平分配
服务Sentinel、Resilience4j、Guava实例级 QPS / 并发按单机容量自保，不依赖外部组件
方法 / 资源Sentinel 热点参数、下游客户端限流参数值、下游资源热点 key 单独限速，保护下游配额
  • 按用户 / IP 限流时注意 key 基数与过期；经过 CDN / SLB 后要从可信 X-Forwarded-For 取真实 IP

Q114：限流阈值如何确定？被限流时应该返回什么？

核心结论：阈值来自压测：单机阈值 ≈ 压测拐点 × 0.7～0.8，集群阈值 ≈ 单机阈值 × 实例数并按负载不均打折，先宽松上线再按命中数据收紧。被限流是正常业务结果：超配额返回 429，服务过载返回 503，都带 Retry-After。

场景状态码说明
超过调用方配额（按用户 / AppKey）429 Too Many Requests + Retry-After调用方自己降速
服务整体过载（过载保护、按优先级卸载）503 Service Unavailable + Retry-After客户端应退避
gRPCRESOURCE_EXHAUSTED / UNAVAILABLE语义同上
  • 集群阈值平均拆到单机时，扩缩容会让总阈值被动变化；需严格控制总量用网关集中限流或 Sentinel 集群流控
  • 客户端收到 429 / 503 不能立即重试，按 Retry-After 或指数退避，并计入重试预算
  • Spring Cloud Gateway 的 RequestRateLimiter 触发时直接写 429 并结束响应、不抛异常，ErrorWebExceptionHandler 捕获不到；默认响应体为空、不带 Retry-After，需要时自行扩展
  • Gateway 的 KeyResolver 不要把空 key 兜底成固定值，否则所有匿名请求共用一个桶；用 deny-empty-key 拒绝

→ 详见 限流与过载保护

Q115：为什么并发数限流比 QPS 限流更能应对下游变慢？和 Little 定律有什么关系？

核心结论：由 Little 定律 并发数 = 吞吐量 × 平均 RT，QPS 阈值不变时 RT 上涨会让在途请求成倍堆积；并发上限不变时，吞吐会随 RT 自动收缩，线程池始终安全。

  • 实现：Sentinel FLOW_GRADE_THREAD、Resilience4j Bulkhead，或一个 Semaphore

Q116：什么是过载保护？Sentinel 系统自适应保护和 BBR 思想是什么？

核心结论：固定阈值只在"容量不变"时成立，依赖变慢、Full GC、宿主机争抢都会让真实容量临时下降。过载保护根据系统实时状态决定是否放行。BBR 思想源自 TCP 拥塞控制：系统最佳在途量 ≈ 最大吞吐 × 最小延迟，在途请求超过这个估算值时拒绝新请求。

  • Sentinel SystemRule：从整机维度保护入口流量（只对 EntryType.IN 生效），可设 load、CPU 使用率、入口平均 RT、入口并发线程数、入口总 QPS 阈值
  • load 超阈值时不直接拒绝，而是再做 BBR 式判断：当前并发 > 最大成功 QPS × 最小 RT 才拒绝，避免误杀
  • load 指标只在 Linux / Unix 生效；容器中 load 反映宿主机，容器内优先用 CPU、RT、并发数指标
  • 同类实现：Kratos 的 BBR 限流器、Netflix concurrency-limits（Vegas / Gradient 动态调整并发上限）

→ 详见 限流与过载保护

Q117：负载卸除时如何按优先级丢弃请求？客户端自适应节流是怎么工作的？

核心结论：必须丢请求时先丢不重要的：给请求分级，在途请求越多，允许进入的优先级越高。客户端自适应节流让调用方根据后端的接受率在本地按比例提前拒绝，减轻后端"拒绝本身"的成本。

  • 按优先级卸载：以压测拐点并发为上限，如 CRITICAL（下单、支付）到上限才拒绝、NORMAL 在 80% 开始卸载、LOW（推荐、埋点、报表）在 60% 开始卸载，被卸载请求返回 503 + Retry-After
  • 优先级由网关按路由或调用方写入，不信任客户端自带的值；已超过调用方 deadline 的请求直接丢弃；越早卸载越省资源
  • 客户端节流（Google SRE）：统计最近一段时间（如 2 分钟）的请求数 requests 与被接受数 accepts，本地拒绝概率 p = max(0, (requests − K × accepts) / (requests + 1))，K 通常取 2；后端正常时 p 为 0
  • 与熔断的区别：熔断是开 / 关二值切换，自适应节流按比例连续调节，更平滑

→ 详见 限流与过载保护

8、优雅上下线与变更

Q118：什么是优雅停机？如何在 Spring Boot 中实现？

核心结论：优雅停机是先摘流量、再处理完在途请求和异步任务、最后释放资源退出，让停机过程不产生失败请求。最常见的错误是顺序颠倒：先停 Web 容器再注销，调用方感知下线之前仍把请求发过来。

顺序动作
1从注册中心注销 / 从 K8s Endpoints 摘除
2等待调用方刷新实例列表（数秒）
3Web 容器停止接收新请求，处理完在途请求
4停止 MQ 消费、定时任务，等待线程池任务完成
5关闭连接池、释放资源，进程退出
server:
  shutdown: graceful                     # 2.3+ 支持；3.4 起嵌入式容器默认开启
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s      # 每个生命周期阶段最长等待
  • 自定义线程池设 setWaitForTasksToCompleteOnShutdown(true) 与 setAwaitTerminationSeconds；@Scheduled 需开启 spring.task.scheduling.shutdown.await-termination
  • MQ 消费者先停止拉取、处理完已拉取消息并提交位点，未提交的会重投，消费必须幂等；Dubbo 内置优雅停机
  • 禁止 kill -9，它不会触发 JVM Shutdown Hook

→ 详见 优雅上下线与变更

Q119：K8s 中如何配合实现优雅停机？preStop 的作用是什么？为什么需要 sleep？

核心结论：Pod 删除时，从 Endpoints 摘除与发送 SIGTERM 是并行发生的，kube-proxy、Ingress、注册中心客户端感知摘除都需要时间。preStop 在 SIGTERM 之前执行，sleep 一段时间让流量先摘干净，再让应用开始停机。

spec:
  terminationGracePeriodSeconds: 60      # 总宽限期，包含 preStop 耗时，超时后 SIGKILL
  containers:
    - name: order-service
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "curl -s -X POST localhost:8080/internal/offline; sleep 15"]
参数建议
preStop 等待覆盖 Endpoints 传播 + 注册中心推送 + 客户端缓存刷新，一般 10 ~ 20s
timeout-per-shutdown-phase大于 P99.9 请求耗时，一般 20 ~ 30s
terminationGracePeriodSeconds≥ preStop 等待 + 应用停机超时 + 余量
  • 微服务场景在 preStop 中先主动从注册中心注销（调用方有本地实例缓存）
  • SIGTERM 要能到达 JVM：Dockerfile 用 exec 形式 ENTRYPOINT ["java", "-jar", "app.jar"] 或 tini 作 PID 1；shell 形式时 JVM 收不到信号，最终被 SIGKILL

→ 详见 优雅上下线与变更

Q120：PodDisruptionBudget 的作用是什么？它能约束滚动更新吗？

核心结论：PDB 限制通过 Eviction API 发起的自愿中断同时驱逐的 Pod 数，如 kubectl drain、集群自动缩容回收节点、托管集群节点升级。它不能约束滚动更新：滚动期间的可用实例数由 Deployment 的 maxUnavailable / maxSurge 控制。

机制约束不约束
maxUnavailable / maxSurgeDeployment 自身的滚动更新节点维护、驱逐
PDB走 Eviction API 的自愿中断滚动更新、直接 kubectl delete pod、节点宕机等非自愿中断
  • 滚动更新不减可用实例：maxUnavailable: 0 + maxSurge: 1，配合 minReadySeconds 给预热留余量
  • PDB 不要把驱逐堵死：minAvailable 等于副本数（或单副本配 minAvailable: 1）会让 kubectl drain 一直卡住；副本数会被 HPA 调整时优先用 maxUnavailable: 1 或百分比

→ 详见 优雅上下线与变更

Q121：为什么新实例启动后需要预热？有哪些预热手段？

核心结论：新实例 JIT 未编译、本地缓存为空、连接池未建立、懒加载 Bean 未初始化，RT 明显偏高，直接接满流量可能被打垮，甚至触发熔断和级联故障。手段是"预热完成再就绪 + 权重逐步放量"。

冷启动原因预热手段
JIT 未编译启动后执行预热请求；小流量逐步放大
本地缓存为空启动时加载热点数据
连接池未建立启动阶段主动获取连接，配置 minimumIdle
类加载、懒加载预热调用核心接口
  • Spring Boot 在所有 ApplicationRunner 执行完才置为 ACCEPTING_TRAFFIC，预热放在 Runner 中，readiness 自然等到预热结束
  • 注册中心的注册时机早于就绪：Spring Cloud 自动注册在 Web 容器启动时触发，Nacos 等调用方可能在预热前就发现实例；可关闭自动注册、预热后代码注册，或先注册低权重
  • 权重预热：Dubbo 内置 warmup（默认 10 分钟线性增长）；Nacos 由发布平台分步调权重；SCL 需自定义负载均衡器按启动时间计算权重

→ 详见 优雅上下线与变更、JVM 层性能策略

Q122：变更三板斧是什么？配置变更如何灰度？

核心结论：变更三板斧是可灰度、可监控、可回滚，任何一项做不到的变更都不应在高峰期上线。配置变更通常秒级推送到全部实例、没有滚动过程，比代码发布更危险，要先推少量实例观察。

原则常见做法
可灰度单机 → 单机房 → 1% → 10% → 全量，每批之间留观察时间
可监控发布大盘对比新旧版本成功率 / RT；燃烧速率告警
可回滚镜像版本化、kubectl rollout undo、功能开关、配置历史版本
  • 配置灰度：Nacos Beta 发布到指定 IP，观察后再全量；发布前 Schema 校验，代码对非法值兜底为默认值；保留历史版本一键回滚；审批与操作审计
  • 配套规则：发布期间异常先回滚再排查；变更可追溯；大促前封网；错误预算不足时冻结非紧急变更
  • 表结构变更遵循先扩展后收缩（Expand-Contract），保证任一时刻回滚代码不需要回滚表结构

Q123：RPO 和 RTO 分别是什么？

核心结论：RPO（Recovery Point Objective）是故障后最多丢失多长时间的数据，由数据复制方式决定；RTO（Recovery Time Objective）是故障后多长时间恢复服务，由备用环境状态与切换自动化程度决定。

应用级（冷 / 温备）异地部署应用，数据异步复制秒 ~ 分钟小时级
业务级（热备）备用机房实时同步，可快速切换秒级分钟级
多活多机房同时服务接近 0（单元内）秒 ~ 分钟（切流）

Q124：同城双活和异地多活的区别？各自解决什么问题？

核心结论：同城双活利用同城机房间 1～2ms 的 RTT，可以跨机房同步调用和同步复制，大多是"应用双活、数据主备"，防单机房故障；异地多活面对 25～30ms 的跨地域 RTT，只能异步复制，必须单元化让一次请求在本地域闭环，防城市 / 地域级故障。

对比同城双活异地多活
距离与 RTT同城几十公里，1 ~ 2ms跨城市，如北京—上海 25 ~ 30ms
数据通常单主，另一机房为半同步从库按路由键分片，各单元写自己的数据，异步同步
改造成本中高（业务、数据、中间件全面改造）
防御范围单机房故障地域级故障

→ 详见 多活与容灾

Q125：两地三中心是什么架构？异地灾备中心为什么"不敢切"？

核心结论：两地三中心 = 同城双中心 + 异地灾备中心：同城两中心做双活或主备（同步 / 半同步复制），异地中心通过异步复制接收数据（RPO 秒～分钟），平时通常不承接流量。"不敢切"是因为异地中心长期不承接流量，配置漂移、容量不足、依赖缺失都要到切换那一刻才暴露，切换本身风险极高。

  • 这正是异地多活要解决的问题：让每个中心常态承接流量，能力持续被验证
  • 没有常态化演练的灾备只是昂贵的冷备

→ 详见 多活与容灾

Q126：什么是单元化？如何选择路由键？全局数据如何处理？

核心结论：单元是一个能完成全部业务闭环的自包含部署集合（接入、应用、缓存、消息和本单元的数据分片）。选一个贯穿业务的路由键，所有请求和数据按它划分到单元，单元型数据的读写和调用都不出单元；无法按路由键拆分的全局数据中心单元集中写，各单元读副本。

业务常用路由键
电商交易买家 userId（订单、购物车、支付单都归属买家）
外卖 / 出行城市 / 区域
SaaS租户 ID（大租户可独占单元）
数据类型示例写入读取
单元型订单、购物车、用户资产归属单元归属单元
全局型库存、商家、商品主数据中心单元各单元只读副本（容忍秒级延迟）
共享只读类目、地区码、配置后台统一维护各单元本地
  • 路由两级映射：userId → 分片号（如 userId % 100）→ 单元，映射放配置中心，切流只改分片到单元的映射；网关对误入请求转发到正确单元
  • 强一致场景（如扣库存）走中心单元，或给各单元预分配库存额度；全局 ID 带单元信息或全局唯一

Q127：双向数据同步如何避免复制回环和写冲突？

核心结论：复制回环靠给同步写入打来源标记、同步组件过滤；写冲突靠单元化从源头避免（同一数据只在一个单元写），兜底按版本号或 update_time "后写胜"并告警。

Q128：计划内切流为什么要先禁写？

核心结论：跨单元是异步复制，源单元总有尚未同步到目标单元的数据。先禁写防止切换过程中两边同时写，再等同步延迟归零，才能做到 RPO = 0；禁写窗口通常为秒级到分钟级。

步骤操作
1确认目标单元容量余量

  • 演练要常态化、从小比例分片开始、全程盯 SLO、异常立即回切

10、混沌工程

Q129：混沌工程是什么？和传统测试有什么区别？有哪些工具？

核心结论：混沌工程在可控范围内主动注入真实世界会发生的故障，验证系统在异常条件下能否保持稳态，提前发现弱点并证明冗余、熔断、降级、切流预案真的有效。传统测试验证功能是否符合预期，混沌工程发现未知弱点，以稳态指标是否偏离假设来判定。

对比传统测试混沌工程
目标验证功能是否符合预期发现异常条件下的未知弱点
输入构造的正常 / 异常输入宕机、延迟、丢包、资源耗尽等真实故障
环境测试环境从预发逐步推进到生产
判定用例通过 / 失败稳态指标是否偏离假设
工具特点
ChaosBlade（阿里）主机、容器、K8s、JVM 方法级故障注入
Chaos Mesh（CNCF）K8s 原生，CRD 声明实验，Schedule 做周期实验、Workflow 编排
Chaos Monkey（Netflix）随机终止实例，混沌工程鼻祖
LitmusK8s 原生，实验市场丰富

→ 详见 混沌工程

Q130：混沌实验的流程是什么？如何控制爆炸半径？

核心结论：流程是 建立稳态假设 → 设计实验 → 注入故障 → 观察指标 → 修复加固并重跑验证，形成闭环。控制爆炸半径的核心是"从小开始、有终止条件、能自动恢复"。

阶段输出物
建立假设稳态指标与基线，如"下游延迟 +300ms 时下单成功率仍 > 99.9%、P99 < 500ms"
设计实验故障类型、注入目标、爆炸半径、终止条件、回滚方案
注入故障ChaosBlade / Chaos Mesh 执行，设置自动恢复时间
观察指标对比监控与告警，验证假设
修复加固补超时、熔断、副本、告警阈值，然后重新实验
  • 爆炸半径：从单实例、小比例流量开始逐步扩大；先测试环境、再预发、再生产低峰期
  • 实验命令加 --timeout / duration 自动恢复，准备一键回滚；稳态指标越过终止条件（如成功率 < 99.5%）立即停止
  • 实验前通知相关团队与值班，避免被误判为真实故障

→ 详见 混沌工程

Q131：如何用故障注入验证熔断、降级是否生效？

核心结论：针对依赖注入"变慢"和"不可用"两类故障，在正常压力下观察熔断是否按阈值打开、降级是否返回有意义的兜底、核心成功率是否保持，恢复后确认熔断经半开探测自动关闭。

# 假设：库存服务 checkStock 变慢到 800ms（超过 Sentinel 慢调用阈值 500ms）时，下单接口 10s 内熔断并走降级
./blade prepare jvm --pid <inventory-pid>                       # JVM 实验前必须先挂载 Agent
./blade create jvm delay --time 800 \
  --classname com.example.InventoryService --methodname checkStock \
  --pid <inventory-pid> --timeout 600                           # 10 分钟后自动恢复
# 对下单接口施加正常水平的压力，观察 Sentinel Dashboard：熔断是否打开、降级量与成功率
./blade destroy <experimentUid>                                 # 销毁实验，确认熔断自动恢复
  • 验证降级：对依赖注入 100% 丢包或方法抛异常，确认兜底数据有业务价值、不依赖故障源
  • 同一思路验证其他预案：Pod Kill 验证故障摘除、DB 方法延迟验证获取连接超时与舱壁隔离、滚动发布中杀 Pod 验证优雅停机

11、故障应急与复盘

Q132：故障如何分级？P0 和 P1 的判定标准与响应要求有什么不同？

核心结论：分级决定响应规格（谁被叫起来、多快响应、要不要对外通告），标准要事先量化、最好与 SLO 挂钩，不能在现场讨论"这算不算大故障"。P0 是核心业务全面不可用或数据、资损问题；P1 是核心业务部分不可用或重要功能完全不可用。

级别判定标准（满足任一）响应要求通报范围
P0核心业务（下单、支付、登录）全面不可用；数据丢失或泄露；资损持续扩大5 分钟内响应，立即拉应急群，负责人与技术负责人到场管理层、客服，必要时对外公告
P1核心业务部分不可用或成功率明显下降（如 > 5% 用户受影响）；重要功能完全不可用15 分钟内响应，值班 + 相关服务负责人技术负责人、业务方、客服
P2非核心功能不可用；核心性能明显下降但可用30 分钟内响应相关团队
P3影响很小或有绕过方案1 个工作日内提单跟踪
  • 定级宁高勿低，影响扩大随时升级；燃烧速率超阈值可自动定为 P1

→ 详见 故障应急与复盘

Q133：线上出现故障时的处理流程是什么？为什么要先止血后定位？

核心结论：流程是 发现 → 响应 → 止血 → 恢复 → 复盘。先止血是因为可用性由 MTTR 决定，而根因定位耗时不可控；大部分线上故障由发布、配置、数据变更或流量变化引起，回滚、切流、降级往往几分钟就能恢复业务。

阶段关键动作常见误区
发现告警、巡检、客服反馈；确认影响范围只盯告警，忽略客服和舆情
响应确认告警、定级、拉应急群、指定应急指挥（IC）多人同时处理却没人统筹
止血按预案回滚、切流、降级、限流在线上边猜边改代码
恢复验证核心指标回到正常，逐步撤销临时措施指标刚好转就宣布恢复
复盘1 ~ 3 个工作日内完成只写经过不写改进
  • 止血的第一个问题永远是"最近有没有变更"，有疑似变更先回滚
  • 止血前花一分钟保留现场（jstack、jmap -histo、GC 日志、异常实例先摘流量不销毁），但不能阻塞止血
  • P0 / P1 明确分工：IC 统筹决策、技术处理人排查执行、沟通负责人定时同步、记录人记时间线

→ 详见 故障应急与复盘

Q134：常见的止血手段有哪些？分别适用于什么场景？

核心结论：按"影响小、见效快"的顺序选择，手段要平时准备好、演练过，故障时只做选择和执行。

手段适用场景注意事项
回滚故障与最近的发布、配置变更时间吻合最常用最有效；要求数据库变更向后兼容
切流单实例、单机房或单地域故障先确认目标有足够容量
摘除 / 重启个别实例假死、内存泄漏、连接泄漏先摘流量保留现场再重启，重启只是临时手段
降级开关非核心依赖故障或资源紧张按预案顺序打开
限流流量突增超过容量，或保护故障中的下游优先限低优先级流量
扩容流量增长导致资源不足瓶颈在数据库等共享资源时，扩应用反而加剧故障
隔离攻击流量恶意刷量、CC 攻击按 IP、设备、账号封禁
数据修复错误数据写入导致的故障先止住错误写入再修数据，修复脚本需复核

Q135：如何降低 MTTD 和 MTTR？

核心结论：缩短 MTTD 靠告警质量（对准用户可感知的症状、少而准）；缩短 MTTR 靠变更关联、预案 Runbook、统一观测入口和演练。

手段作用做法
基于 SLO 的告警缩短 MTTD、减少误报告警对准成功率、延迟，用燃烧速率告警
告警降噪防止重要告警被淹没聚合、抑制、静默；每条告警都应可操作，否则删除
变更关联快速定位诱因发布、配置、数据变更统一记录，告警时自动展示前后变更
预案与 Runbook缩短决策和执行时间触发条件、影响判断、止血步骤、验证方法、升级联系人，告警直接链接 Runbook
统一观测入口缩短定位时间指标、日志、链路通过 TraceId 关联
故障演练验证预案可用、熟悉操作定期混沌实验与切流演练
  • 配套 On-call：主备值班、明确升级路径（如 5 分钟未确认升级备值班，15 分钟未定位升级负责人）

Q136：什么是无责复盘？复盘报告应包含哪些内容？

核心结论：无责复盘的目的是改进系统而不是追究个人：一次误操作能造成故障，说明系统缺少防护；追责只会让大家隐瞒信息，下次更难找到真实原因。报告要能从时间线得出 MTTD / MTTR，用 5 Whys 找到系统层面的根因，并产出有负责人和截止日期的改进项。

部分内容
概要级别、影响时长、影响范围（用户数、订单数、资损）、错误预算消耗
时间线按分钟记录：故障开始、告警、响应、关键决策、止血、恢复
关键指标MTTD、MTTR 与各阶段耗时
根因分析直接原因、根本原因，5 Whys 逐层追问
做得好的哪些告警、预案、操作发挥了作用
改进项每项有负责人、截止日期、验收标准，按预防 / 发现 / 恢复三类考虑
  • 例：根因不是"某人把超时从 3s 改成了 300ms"，而是超时配置缺乏集中管理、灰度缺乏与基线的自动对比
  • 同一根因的故障再次发生，先检查上次的改进项是否落实
