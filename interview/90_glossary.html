Java 与 JVM

  • ABA 问题：值从 A 改成 B 又改回 A，CAS 看不出变过，用版本号戳解决 → 原子类（Atomic）
  • AQS（抽象队列同步器）：用一个 state 加一条等待队列，撑起 JUC 里大部分锁和同步器 → 显式锁（Lock）
  • BlockingQueue（阻塞队列）：取不到就等、放不下就等的队列，线程池和生产消费模型都靠它 → 集合框架
  • CAS（Compare-And-Swap）：先比较内存值是否还是预期值，是才替换，靠 CPU 指令保证原子 → 原子类（Atomic）
  • ConcurrentHashMap：线程安全的 HashMap，JDK 8 起用 CAS 加桶级锁，读基本不加锁 → 集合框架
  • DCL（双重检查锁）：加锁前后各判断一次再创建单例，实例字段必须加 volatile → JMM 内存模型
  • Fork/Join：把大任务拆小并行算再合并，空闲线程会去偷别人的任务做 → Fork/Join 与定时任务
  • G1（Garbage-First）：把堆切成很多 Region，优先回收垃圾最多的，停顿时间可预期 → GC 收集器
  • happens-before：JMM 的可见性规则：A 先行于 B，A 的写入 B 一定能看到 → JMM 内存模型
  • HashMap：数组加链表 / 红黑树的哈希表，按 key 的 hash 定位桶，非线程安全 → 集合框架
  • invokedynamic：运行时才绑定调用目标的字节码指令，Lambda 和字符串拼接靠它 → Lambda 与 Stream
  • JIT（即时编译）：把运行频繁的热点代码编译成机器码，越跑越快 → JIT 编译
  • JMM（Java 内存模型）：规定多线程下一个线程的写何时对别的线程可见、能否被重排 → JMM 内存模型
  • LongAdder：高并发计数器，把热点拆到多个槽各自累加，求和时再汇总 → 原子类（Atomic）
  • Mark Word（对象头）：对象头里的一块，存哈希码、GC 年龄和锁状态 → 内存结构
  • OOM（OutOfMemoryError）：内存不够用了，堆、元空间、直接内存、线程数都可能触发 → 故障排查
  • ReentrantLock：可重入的显式锁，比 synchronized 多了公平、超时、可中断 → 显式锁（Lock）
  • ScopedValue：ThreadLocal 的轻量替代，只在一段作用域内只读传值 → 虚拟线程
  • SPI（Service Provider Interface）：接口由框架定、实现由第三方提供，运行时按配置文件发现加载 → SPI 机制
  • ThreadLocal：每个线程各存一份变量副本，用完要 remove，否则泄漏或串数据 → 线程基础
  • TLAB（线程本地分配缓冲）：每个线程在 Eden 里预占一小块，分配对象不用抢锁 → 内存结构
  • volatile：保证变量的可见性和禁止重排，但不保证 i++ 这类复合操作原子 → JMM 内存模型
  • ZGC：几乎全程并发的低延迟收集器，停顿通常不到 1 毫秒 → GC 收集器
  • 安全点（Safepoint） / STW：GC 要暂停所有线程（STW），线程只能停在安全点上 → GC 原理
  • 单例模式：保证一个类只有一个实例，常用静态内部类或枚举实现 → 单例模式
  • 钉住（Pinning）：虚拟线程阻塞时卸载不下来，连带占住底层载体线程 → 虚拟线程
  • 动态代理：运行时生成代理类拦截方法调用，Spring AOP 的底层 → 动态代理
  • 反射：运行时拿到类的字段、方法并调用，框架的基础能力 → 反射
  • 泛型擦除：泛型只在编译期检查，编译后类型参数被擦成上界或 Object → 泛型
  • 分代收集：按对象存活时间分新生代和老年代，用不同算法分别回收 → GC 原理
  • 红黑树：近似平衡的二叉搜索树，增删查都是 O(log n)，HashMap 树化用它 → 树
  • 静态分派 / 动态分派：重载按声明类型在编译期选，重写按实际类型在运行期选 → 面向对象与 Object
  • 拒绝策略：线程池和队列都满了时怎么处理新任务，如抛异常或调用者执行 → 线程池
  • 可达性分析：从 GC Roots 出发顺着引用找，找不到的对象就是垃圾 → GC 原理
  • 内存屏障（Memory Barrier）：禁止 CPU 和编译器把屏障两侧的读写重排，volatile 等语义靠它实现 → JMM 内存模型
  • 三色标记：并发标记时用黑灰白三色记进度，靠写屏障防止漏标 → GC 原理
  • 时间复杂度：用大 O 描述数据量变大时，算法耗时增长得有多快 → 复杂度分析
  • 双亲委派：类加载器先让父加载器去加载，父加载不了才自己来 → 类加载机制
  • 锁升级：synchronized 按竞争程度从轻量级锁膨胀到重量级锁 → synchronized
  • 锁消除 / 锁粗化：JIT 去掉不可能有竞争的锁，或把连续的加锁合并成一次 → synchronized
  • 逃逸分析：JIT 判断对象会不会跑出方法，不逃逸就拆成局部变量免分配 → JIT 编译
  • 线程池（ThreadPoolExecutor）：复用一组线程执行任务，核心线程、队列、最大线程依次兜底 → 线程池
  • 虚拟线程：JDK 21 的轻量线程，阻塞时自动让出载体线程，可开百万个 → 虚拟线程
  • 引用类型（强 / 软 / 弱 / 虚）：四种引用强度，决定对象在什么情况下可以被 GC 回收 → GC 原理
  • 元空间（Metaspace）：JDK 8 起存类元数据的地方，用本地内存，替代了永久代 → 内存结构
  • 字符串常量池：相同字面量的字符串只存一份，intern 可手动放入复用 → String

数据库、缓存与消息队列

  • ACID：事务的四个保证：原子性、一致性、隔离性、持久性 → MySQL 事务与锁
  • AOF（追加日志）：Redis 把每条写命令追加到文件，重启时重放来恢复数据 → Redis 核心原理
  • B+ 树（B+ Tree）：InnoDB 索引结构，矮胖多叉、数据都在叶子且叶子串成链表，适合范围查 → MySQL 索引
  • binlog（二进制日志）：MySQL Server 层记录数据变更的日志，用于主从复制和按时间点恢复 → MySQL 主从与高可用
  • Buffer Pool（缓冲池）：InnoDB 在内存里缓存数据页和索引页，读写先走它，减少磁盘 IO → InnoDB 存储结构
  • Cache Aside（旁路缓存）：读时缓存没有就查库回填，写时先更新库再删缓存 → 缓存一致性
  • CDC（变更数据捕获）：订阅数据库变更日志（如 binlog），把增删改实时同步给下游 → CDC 工具
  • Change Buffer：普通二级索引页不在内存时先把改动记下来，之后再合并，省随机读 → MySQL 索引
  • GTID（全局事务 ID）：给每个事务一个全局唯一编号，主从切换时按编号续传，不用找位点 → MySQL 主从与高可用
  • ICP（索引下推）：把能用索引列判断的条件下推到存储引擎先过滤，减少回表 → MySQL 索引
  • ISR（同步副本集合）：跟上 Leader 的副本集合，Leader 挂了只从这里选新 Leader → Kafka
  • Kafka 事务与幂等生产者：幂等生产者加事务，让 Kafka 内的读-算-写每条只生效一次 → Kafka
  • LSM-Tree（日志结构合并树）：写先进内存再顺序刷成有序文件、后台合并，写快读稍慢 → 列式与 OLAP 数据库
  • MVCC（多版本并发控制）：每行保留多个历史版本，读不加锁也能看到一致的快照 → MySQL 事务与锁
  • RDB（快照）：Redis 定时把内存数据整体落成快照文件，恢复快但可能丢最近数据 → Redis 核心原理
  • Read View（读视图）：快照读时生成的「当前有哪些事务未提交」清单，用来判断哪个版本可见 → MySQL 事务与锁
  • Rebalance（再均衡）：消费者组成员或分区变化时重新分配分区，期间可能停顿和重复消费 → Kafka
  • redo log（重做日志）：InnoDB 先写的物理日志，宕机后用它把已提交的修改补回来 → MySQL 事务与锁
  • undo log（回滚日志）：记录修改前的旧值，用于事务回滚，也是 MVCC 版本链的来源 → MySQL 事务与锁
  • 半同步复制：主库提交前至少等一个从库确认收到 binlog，降低主库宕机丢数据风险 → MySQL 主从与高可用
  • 布隆过滤器（Bloom Filter）：用位数组判断元素「一定不存在或可能存在」，常用来拦缓存穿透 → Redis 典型应用场景
  • 大 Key（Big Key）：单个 value 过大或元素过多的 Key，读写和删除都会卡住 Redis → Redis 实战
  • 倒排索引（Inverted Index）：从「词」查到「包含它的文档列表」，全文搜索的核心结构 → Elasticsearch 原理
  • 覆盖索引（Covering Index）：查询要的列索引里都有，直接从索引返回，不用回表 → MySQL 索引
  • 隔离级别：规定并发事务之间能看到彼此多少改动，从读未提交到串行化共四档 → MySQL 事务与锁
  • 哈希槽（Hash Slot）：Redis Cluster 把 key 映射到 16384 个槽，再把槽分给各个节点 → Redis 集群
  • 缓存穿透：查的数据缓存和库里都没有，请求每次都打到数据库 → 缓存最佳实践
  • 缓存击穿：某个热点 Key 过期瞬间，大量请求同时回源压垮数据库 → 缓存最佳实践
  • 缓存淘汰策略：内存满了按 LRU、LFU 等规则挑 Key 删掉，给新数据腾地方 → Redis 核心原理
  • 缓存雪崩：大量 Key 同时过期或缓存整体宕机，流量一下全压到数据库 → 缓存最佳实践
  • 回表（Back to Table）：二级索引只存主键，查其他列还得拿主键回聚簇索引再查一次 → MySQL 索引
  • 间隙锁（Gap Lock）：锁住索引记录之间的空隙不让插入，RR 下用来防幻读 → MySQL 事务与锁
  • 聚簇索引（Clustered Index）：按主键组织的 B+ 树，叶子节点直接存整行数据 → MySQL 索引
  • 看门狗（Redisson Watchdog）：加锁不指定过期时间时，后台定期给锁续期，进程挂了就不再续、锁自动过期 → Redisson
  • 快照读与当前读：普通 SELECT 读 MVCC 快照不加锁，加锁读和增删改读最新版本并加锁 → MySQL 事务与锁
  • 两级缓存（L1 + L2）：本地缓存挡第一层、Redis 挡第二层，兼顾速度和多实例共享 → 两级缓存（L1 + L2）
  • 两阶段提交（2PC）：redo 先 prepare、写完 binlog 再 commit，保证两份日志结论一致 → MySQL 事务与锁
  • 幂等消费：同一条消息被消费多次，结果和只消费一次一样 → 消息队列基础
  • 哨兵（Sentinel）：监控 Redis 主从，主库挂了自动选从库升主并通知客户端 → Redis 集群
  • 深分页：LIMIT 偏移量很大时要先扫过并丢弃前面所有行，越翻越慢 → MySQL 索引
  • 事务消息：先发半消息、本地事务成功后再投递，失败由 Broker 回查状态 → RocketMQ
  • 顺序消息：同一业务 key 的消息进同一分区或队列，按发送顺序被消费 → 消息队列基础
  • 死锁（Deadlock）：两个事务互相等对方持有的锁，InnoDB 检测到后回滚其中一个 → MySQL 事务与锁
  • 死信队列（DLQ）：重试多次仍失败的消息转存到这里，等人工排查或修复后重投 → 消息队列基础
  • 索引失效：函数运算、隐式转换、左模糊等写法让优化器用不上索引 → MySQL 索引
  • 消费位点（Offset）：消费者在分区里读到的位置，按分区累计提交，重启从这里继续 → Kafka
  • 消息积压：生产速度长期大于消费速度，消息在队列里越堆越多 → 消息队列基础
  • 延迟双删：更新库前后各删一次缓存，第二次延迟执行，清掉并发读回填的旧值 → 缓存一致性
  • 延迟消息：消息发出后先不投递，到指定时间才让消费者看到 → RocketMQ
  • 主从延迟（复制延迟）：从库回放 binlog 跟不上主库，刚写的数据在从库读不到 → MySQL 主从与高可用
  • 最左前缀原则：联合索引从最左列开始连续匹配才能用上，跳过中间列就断了 → MySQL 索引

分布式、微服务与架构

  • 2PC（两阶段提交）：协调者先问各方能否提交，都说行再统一提交，任一方不行就全部回滚 → 分布式事务
  • BASE：基本可用、软状态、最终一致，用放宽一致性换可用性 → 分布式理论
  • BFF（Backend for Frontend）：给每种前端单独配一层后端，按页面需要聚合和裁剪接口 → 微服务设计模式
  • CAP：发生网络分区时，一致性和可用性只能保一个 → 分布式理论
  • CQRS（命令查询职责分离）：写和读用两套模型，写侧保证正确，读侧按查询需要单独建表 → 架构模式与风格
  • Fencing Token（防护令牌）：每次拿锁发一个递增编号，存储端拒收旧编号的写，防止过期锁乱写 → 分布式锁
  • Gossip：节点之间随机互相传话，消息像流言一样最终传遍全集群 → 分布式理论
  • Little 定律：系统里的并发请求数 = 吞吐量 × 平均响应时间 → 性能指标
  • Outbox（事务发件箱 / 本地消息表）：业务数据和待发消息写进同一个本地事务，再由后台把消息可靠投出去 → 分布式事务
  • P99（分位数）：99% 的请求都比它快，比平均值更能反映慢请求的体验 → 性能指标
  • Paxos：经典共识算法，多数派通过两阶段投票对一个值达成一致 → 分布式理论
  • Quorum（NWR）：写 W 份、读 R 份，只要 W + R > N 就一定能读到最新写入 → 分布式理论
  • Raft：好理解的共识算法：选出一个 Leader，由它复制日志到多数节点 → 分布式理论
  • Redlock：向多个独立 Redis 加锁、过半成功才算拿到锁，安全性有争议 → 分布式锁
  • RPO / RTO：RPO 是最多丢多少数据，RTO 是多久能恢复服务 → 多活与容灾
  • Saga：长事务拆成一串本地事务，某步失败就按反方向逐个补偿 → 分布式事务
  • SLA / SLO / SLI：SLI 是测量值，SLO 是内部目标，SLA 是对外承诺并带赔偿 → 可用性度量
  • TCC（Try-Confirm-Cancel）：先预留资源，成功就确认、失败就取消，由业务代码自己实现三步 → 分布式事务
  • 舱壁隔离（Bulkhead）：给不同依赖分配独立的线程池或配额，一个坏了不拖垮全部 → 超时、重试与隔离
  • 错误预算：1 减 SLO 就是允许出错的额度，用完了就先停发布、修稳定性 → 可用性度量
  • 单元化：按用户等维度把流量和数据切成多个自包含单元，请求在单元内闭环 → 多活与容灾
  • 读扩散（拉模式）：内容只存一份，读的时候再去各个来源拉取合并 → Feed 流和消息推送
  • 读写分离：写走主库、读走从库来分担压力，要处理主从延迟读到旧数据 → 数据层扩展
  • 对冲请求（Hedged Request）：请求迟迟不回就再发一份给别的实例，谁先回用谁，用来砍长尾 → 异步与批量
  • 多活（异地多活）：多个机房同时对外服务，一个机房挂了流量切到其他机房 → 多活与容灾
  • 防腐层（ACL）：在新旧系统之间加一层转换，别让对方的模型污染自己的领域 → 服务拆分
  • 分布式锁：跨进程、跨机器的互斥锁，保证同一资源同一时刻只有一个人改 → 分布式锁
  • 分库分表：单库单表扛不住时按分片键把数据拆到多个库表，代价是跨分片查询和事务变难 → 数据层扩展
  • 服务发现：服务启动时登记地址，调用方从注册中心查到可用实例再调用 → 注册发现
  • 服务网格（Service Mesh）：把重试、熔断、加密等通信能力下沉到 Sidecar 代理，业务代码不用管 → 服务网格
  • 混沌工程：在可控范围内主动注入故障，验证系统真出事时扛不扛得住 → 混沌工程
  • 降级：压力大或依赖故障时，主动关掉次要功能或返回兜底数据保核心 → 降级
  • 绞杀者模式（Strangler Fig）：新功能逐个搬到新服务，旧系统一点点被替代，最后下线 → 微服务优势与挑战
  • 聚合根（Aggregate Root）：一组强相关对象的唯一入口，外部只能通过它修改内部数据 → DDD 领域驱动设计
  • 康威定律：系统结构会长成组织沟通结构的样子，拆服务要和团队边界对齐 → 服务拆分
  • 令牌桶（Token Bucket）：按固定速率往桶里放令牌，拿到令牌才放行，允许一定突发 → 限流与过载保护
  • 漏桶（Leaky Bucket）：请求先进桶，再按固定速率流出，把突发流量削成匀速 → 限流与过载保护
  • 幂等：同一个请求执行一次和执行多次，结果完全一样 → 幂等设计
  • 脑裂（Split-Brain）：网络断开后两边都以为自己是主，同时写入导致数据冲突 → 冗余与故障转移
  • 燃烧速率（Burn Rate）：错误预算被消耗的速度，按它告警比直接按错误率告警更准 → 可用性度量
  • 热 Key：少数 Key 被集中访问，把单个缓存分片或节点打满 → 热点问题
  • 热点 Key：少数 Key 被集中访问，把单个缓存节点或数据库行打爆 → 热点问题
  • 熔断（Circuit Breaker）：下游错误率太高就暂时不调它直接失败，过一会儿再放少量请求试探 → 熔断
  • 时间轮：把延迟任务按到期时间挂到环形槽位上，指针转到哪个槽就执行哪批 → 延迟任务
  • 事件溯源（Event Sourcing）：不存当前状态，只存变更事件，状态靠重放事件算出来 → 架构模式与风格
  • 限界上下文（Bounded Context）：一个业务模型的适用边界，边界内术语含义唯一，常对应一个服务 → DDD 领域驱动设计
  • 写扩散（推模式）：发布时就把内容写进每个接收人的收件箱，读的时候直接取 → Feed 流和消息推送
  • 削峰填谷：用消息队列把瞬时洪峰缓存起来，让下游按自己的能力慢慢消费 → 异步与削峰
  • 雪花算法（Snowflake）：用时间戳 + 机器号 + 序列号拼出趋势递增的 64 位唯一 ID → 分布式 ID 生成
  • 一致性哈希：节点和数据都映射到哈希环上，增删节点只影响相邻一小段数据 → 一致性哈希
  • 优雅停机：下线前先摘流量、处理完手头请求再退出，用户无感知 → 优雅上下线与变更
  • 指数退避：重试间隔按倍数拉长并加随机抖动，避免大家同时重试压垮下游 → 超时、重试与隔离
  • 自适应限流：不靠固定阈值，而是根据系统负载或实时并发自动调节放行量 → 限流与过载保护
  • 最终一致性：允许短时间数据不一致，但不再有新更新后各副本终会一致 → 分布式理论

网络、操作系统与运维

  • cgroup（控制组）：Linux 给一组进程限额 CPU、内存、IO 的机制，容器资源限制靠它 → Docker
  • CSRF（跨站请求伪造）：诱导已登录用户的浏览器带着 Cookie 发出非本人意愿的请求 → 常见漏洞与防护
  • D 状态（不可中断睡眠）：进程多半在等磁盘 IO，kill -9 也杀不掉，还会被算进 Load → 进程间通信与进程状态
  • DNS 解析：本地解析器从根、顶级域到权威服务器一级级问，最后拿到 IP → DNS
  • eBPF：在内核里安全跑小程序，不改应用就能采集性能和网络数据 → 持续剖析与 eBPF
  • Feature Flag（功能开关）：用配置开关决定功能是否生效，让代码部署和功能发布分开 → 环境管理
  • Flaky 测试（不稳定测试）：代码没改却时过时不过的测试，多因时间、顺序、异步等待 → 集成测试
  • GitOps：Git 仓库就是期望状态，集群里的代理不断拉取并自动对齐 → Argo CD
  • HPA（水平自动扩缩容）：按 CPU 或自定义指标自动增减 Pod 副本数 → Kubernetes
  • HTTP/2 多路复用：一条 TCP 连接上并行跑多个请求，帧交错发送互不排队 → HTTP
  • Ingress：K8s 的七层入口规则，按域名和路径把外部流量转给 Service → Nginx、Ingress 与 Gateway API
  • JWT（JSON Web Token）：自带签名的令牌，服务端验签就能信任里面的用户信息 → JWT 令牌机制
  • Load Average（平均负载）：一段时间内在跑和排队等跑的任务数（含 D 状态），不等于 CPU 使用率 → Load 与 CPU 利用率
  • mmap（内存映射）：把文件映射进进程地址空间，读写内存就等于读写文件 → 内存管理与 Page Cache
  • mTLS（双向 TLS）：客户端和服务端互相出示证书验明身份，常用于服务间调用 → HTTPS 与 TLS
  • Nagle 算法：把小包攒一攒再发，和延迟确认叠加会多出几十毫秒延迟 → TCP 与 UDP
  • Namespace（Linux 命名空间）：让进程只看到自己的 PID、网络和挂载点，容器隔离靠它 → Docker
  • OAuth2：授权框架：用户授权第三方应用拿令牌访问资源，不用交出密码 → OAuth2
  • OIDC（OpenID Connect）：在 OAuth2 上加一张 ID Token，专门回答「登录的用户是谁」 → OIDC
  • OOM Killer：内存耗尽时内核按评分挑一个进程强杀，Java 进程常被带走 → 内存管理与 Page Cache
  • OpenTelemetry（OTel）：厂商中立的可观测性标准，统一采集链路、指标和日志 → OpenTelemetry
  • Page Cache（页缓存）：内核拿空闲内存缓存文件内容，读写文件先过它再异步落盘 → 内存管理与 Page Cache
  • PKCE：授权码流程里用一次性随机串绑定请求，防授权码被截获冒用 → OAuth2
  • Pod：K8s 最小调度单位，一组共享网络和存储的容器 → Kubernetes
  • QUIC：基于 UDP 的传输协议，自带加密和多路复用，HTTP/3 跑在它上面 → HTTP
  • RBAC（基于角色的访问控制）：权限先授给角色，再把角色分给用户，用户不直接持有权限 → 权限模型：RBAC 与 ABAC
  • RED / USE 方法：RED 看服务的请求量、错误、耗时，USE 看资源的使用率、饱和度、错误 → 指标监控
  • Service（K8s）：给一组 Pod 一个稳定的虚拟 IP 和域名，顺带做负载均衡 → Kubernetes
  • SQL 注入：输入被拼进 SQL 当成代码执行，用参数化查询就能根治 → 常见漏洞与防护
  • SSO（单点登录）：登录一次就能访问多个互信系统，不用每个系统各登一遍 → 单点登录
  • TIME_WAIT：主动关闭方要再等 2MSL 才释放连接，防止旧包串进新连接 → TCP 与 UDP
  • TLS 握手：双方协商算法、交换密钥并校验证书，TLS 1.3 只要 1 个往返 → HTTPS 与 TLS
  • Trace / Span（链路 / 跨度）：Trace 是一次请求的完整调用链，Span 是链上的一段操作 → 链路追踪
  • XSS（跨站脚本）：恶意脚本被注入页面，在其他用户的浏览器里执行 → 常见漏洞与防护
  • 测试金字塔：单元测试最多、集成测试次之、端到端最少的分层比例 → 测试工程总览
  • 测试替身（Test Double）：测试里替代真实依赖的对象，含 Dummy、Stub、Spy、Mock、Fake → Mock 测试
  • 滚动发布（Rolling Update）：分批用新实例替换旧实例，全程不停服 → 发布策略
  • 灰度发布 / 金丝雀发布：新版本先放一小部分流量，指标正常再逐步扩大，出问题只影响少数用户 → 发布策略
  • 僵尸进程（Zombie）：子进程已退出但父进程没回收，只占进程号不占内存 → 进程间通信与进程状态
  • 金丝雀发布（Canary）：先切一小部分流量到新版本，指标正常再逐步放大 → 发布策略
  • 蓝绿发布（Blue-Green）：新旧两套环境并存，验证后一次切流量，回滚只需切回去 → 发布策略
  • 零拷贝（Zero-copy）：数据不经用户态来回拷贝，直接在内核里从文件送到网卡，如 sendfile → IO 与 NIO
  • 零信任（Zero Trust）：不因身在内网就默认可信，每次访问都校验身份和设备 → 零信任架构
  • 契约测试（Contract Test）：消费者写下对接口的期望，提供方据此验证，防止改接口坑下游 → 契约测试
  • 前向保密（Forward Secrecy）：每次连接用临时密钥，私钥日后泄露也解不开以前的流量 → HTTPS 与 TLS
  • 三次握手：建连时 SYN、SYN+ACK、ACK 三步，确认双方收发正常并同步序号 → TCP 与 UDP
  • 上下文切换：CPU 换线程运行时要保存、恢复寄存器等现场，有不小开销 → 进程、线程与协程
  • 四次挥手：TCP 是全双工，双方各发一次 FIN 并确认，才算彻底关闭 → TCP 与 UDP
  • 探针（Probe）：K8s 定期检查容器：存活检查失败就重启，就绪检查失败就摘掉流量 → 冗余与故障转移
  • 伪共享（False Sharing）：多个线程改同一缓存行里的不同变量，缓存反复失效拖慢性能 → CPU 缓存与伪共享
  • 系统调用（Syscall）：用户程序请内核办事的入口，要从用户态切到内核态 → 用户态、内核态与系统调用
  • 拥塞控制：按网络拥堵程度调整发送速率，避免把网络打爆，如 CUBIC、BBR → TCP 与 UDP
  • 指标基数（Cardinality）：标签值组合出的时间序列数，放入用户 ID 这类标签会撑爆存储 → 指标监控

框架与新兴方向

  • Agent（智能体）：让大模型自己规划步骤、反复调用工具，直到把任务做完的程序 → AI Agent 智能体
  • AOP（面向切面编程）：把日志、事务这类横切逻辑抽出来，靠代理织入到目标方法前后 → AOP
  • Bean 生命周期：Bean 从实例化、属性注入、初始化回调到销毁的完整过程 → IoC 容器
  • ByteBuf：Netty 的字节容器，读写双指针、可池化，靠引用计数释放内存 → ByteBuf 与内存管理
  • Checkpoint（检查点）：Flink 定期给所有算子状态拍一致性快照，故障后从快照恢复 → 状态与容错
  • Embedding（向量化）：把文本转成一串数字向量，语义越接近，向量距离越近 → Embedding 向量化
  • Event Bus（事件总线）：Vert.x 组件之间按地址收发消息的通道，支持点对点、广播和请求响应 → Event Bus
  • EventLoop（事件循环）：绑定一个线程不停处理就绪 IO 和任务，里面绝不能做阻塞操作 → Channel 与 EventLoop
  • Exactly-once（精确一次）：故障重放后每条数据对结果只生效一次，靠快照加事务或幂等写入 → 状态与容错
  • Function Calling（工具调用）：模型只返回要调哪个函数和参数，由应用执行后把结果回传给模型 → Function Calling（工具调用）
  • GOP（图像组）：两个关键帧之间的一组帧，越长越省码率，但起播和拖动越慢 → 音视频基础
  • HLS：把流切成小片段加 m3u8 列表走 HTTP 分发，兼容性好但延迟高 → 流媒体协议
  • IoC（控制反转） / DI（依赖注入）：对象由容器创建并把依赖注入进来，业务代码不再自己 new → IoC 容器
  • LoRA：冻结原模型，只训练插进去的小型低秩矩阵，显存和成本大幅下降 → 模型微调
  • MCP（模型上下文协议）：让 AI 应用用统一协议接入外部工具和数据源的开放标准 → MCP 协议
  • MQTT QoS：MQTT 的投递等级：0 最多一次、1 至少一次、2 恰好一次 → 通信协议
  • NAT 穿透（ICE / STUN / TURN）：先用 STUN 探出公网地址尝试直连，打不通再走 TURN 中继 → WebRTC 实时通信
  • RAG（检索增强生成）：先从知识库检索相关片段放进提示词，再让模型据此回答 → RAG 检索增强生成
  • Reactor 模型：用少量线程监听 IO 事件再分发给处理器，Netty 用主从多线程版 → Reactor 模型
  • SFU（选择性转发单元）：多人音视频的转发服务器，只转发不混流，是会议的主流方案 → WebRTC 实时通信
  • Shuffle：按 key 跨节点重新分发数据，宽依赖的主要开销，也是数据倾斜的源头 → Spark
  • Starter：一个聚合依赖的包，引入后就带上对应的自动配置 → 自定义 Starter
  • Token：大模型读写文本的最小单位，计费和上下文长度都按它算 → 大模型基础概念
  • Verticle：Vert.x 的部署单元，标准 Verticle 固定跑在一个 Event Loop 上 → Event Loop 与 Verticle
  • 背压（Backpressure）：下游按自己的处理能力向上游要数据，防止生产太快压垮消费者 → WebFlux
  • 边缘计算：把采集、过滤和推理放到设备附近做，减少上云流量和延迟 → 边缘计算
  • 窗口（Window）：把无界流切成有限的桶再聚合，常见滚动、滑动和会话窗口 → 时间、水位线与窗口
  • 构建期增强：把扫描、装配等启动工作挪到构建阶段完成，运行时直接用结果 → Quarkus 概览
  • 湖仓（Lakehouse）：在对象存储上加一层表格式，同时拿到湖的低成本和仓的事务能力 → 数据湖与湖仓
  • 缓慢变化维（SCD） / 拉链表：维度属性会随时间变化，常用拉链表记下每个版本的生效区间 → 数仓分层与建模
  • 幻觉（Hallucination）：模型一本正经地编出不存在的事实，根源是按概率续写 → 大模型基础概念
  • 码率控制（CBR / VBR / CRF）：决定码率怎么分配：恒定码率、可变码率或按画质恒定 → 音视频基础
  • 上下文窗口（Context Window）：模型一次能处理的 Token 上限，输入和输出共用这个额度 → 大模型基础概念
  • 设备影子（Device Shadow）：云端给每台设备存一份期望状态和上报状态，设备离线也能先改后同步 → 设备影子
  • 事务传播行为：方法嵌套调用时，内层是加入外层事务、另开新事务还是不用事务 → 事务管理
  • 数仓分层（ODS / DWD / DWS / ADS）：数据按原始、明细、汇总、应用逐层加工，复用口径、隔离变化 → 数仓分层与建模
  • 水位线（Watermark）：事件时间的进度标记，表示更早的数据基本到齐，可以触发窗口计算 → 时间、水位线与窗口
  • 提示注入（Prompt Injection）：在输入或检索内容里夹带指令劫持模型，不能只靠提示词防 → Prompt 工程
  • 维度建模（星型模型）：用事实表记录业务过程、维度表描述上下文，查询直观好理解 → 数仓分层与建模
  • 响应式编程（Mono / Flux）：用异步数据流加回调组织代码，少量线程就能扛高并发 → WebFlux
  • 向量数据库：存储向量，用 HNSW 等近似索引快速找出最相似的 Top-K → 向量数据库
  • 循环依赖（三级缓存）：Spring 提前暴露半成品 Bean 的引用，解决单例之间互相注入 → IoC 容器
  • 原生镜像（Native Image）：GraalVM 把应用提前编译成本地可执行文件，启动快、内存小 → 原生镜像与云原生部署
  • 粘包与拆包：TCP 是字节流，没有消息边界，要在应用层用长度字段或分隔符切帧 → 粘包与拆包
  • 自动配置：Spring Boot 按类路径和条件注解自动注册 Bean，用户自定义的优先 → 启动流程与自动配置
