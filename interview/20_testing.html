测试工程面试题解答

题目清单见 测试工程面试题；细节见 测试工程总览。

版本基线：JDK 21 / Spring Boot 4（Spring Framework 7）、JUnit 6、Mockito 5、Testcontainers 2.0.x、Spring Cloud Contract 5.0.x / Pact JVM 4.7.x、k6 2.x。

一、测试分层与单元测试

Q1：测试金字塔是什么？和测试蜂巢怎么选？

一句话：金字塔是「单元测试最多、越往上越少」，蜂巢是「集成测试最多、两头少」；形状不重要，关键是每类风险交给最便宜又真能发现它的那一层。

  • 金字塔：适合规则多、计算多的服务（计价、风控），规则组合用单元测试穷举最划算
  • 蜂巢：适合逻辑少、主要在调别人和中间件的微服务，风险集中在 SQL、序列化、超时上，Mock 掉反而什么都证明不了
  • 折扣顺序错 → 单元测试；字段映射错 → 切片测试；MySQL 方言差异 → 集成测试；上游改字段类型 → 契约测试
  • 端到端只留关键路径的一两条冒烟，不在多层重复测同一件事

→ 详见 测试工程总览

Q2：一个好的单元测试长什么样？

一句话：快、互相独立、任何时候跑结果都一样、靠断言判成败，并且只测一个行为、名字能说清「什么条件下期望什么结果」。

  • FIRST：Fast（毫秒级）、Independent（无顺序依赖）、Repeatable（不读系统时间 / 随机数）、Self-validating（有断言）、Timely（和代码同时写）
  • 结构用 Arrange-Act-Assert（准备 / 执行 / 验证），执行那段只有一行
  • 测试里不写 if、循环和计算，期望值直接写字面量，否则会和实现犯同样的错
  • 时间、随机数通过注入 Clock 等方式固定下来

常见坑：

  • 测私有方法、过度断言无关字段、捕获异常后什么都不做，测试看着绿其实没验证

→ 详见 单元测试

Q3：覆盖率 100% 能说明测试充分吗？

一句话：不能。覆盖率只说明哪些代码「没被执行过」，不说明执行过的代码「有没有被正确验证」，删光断言覆盖率一点都不变。

  • 覆盖率（JaCoCo）擅长找没人测过的分支，比如异常分支
  • 变异测试（PIT）：故意把代码改出小 Bug（如 < 改成 <=），测试还能通过就说明断言不够有力
  • PIT 很慢，只对核心领域模块开，放夜间流水线，不进 PR 必过门禁
  • 门槛看新代码覆盖率（Sonar 质量门禁 ≥ 80%），整体覆盖率只看趋势

常见坑：

  • 把覆盖率或杀死率设成团队 KPI，结果大家补没有断言的测试凑数

→ 详见 单元测试

二、Mock 与测试替身

Q4：Mock、Stub、Spy、Fake 有什么区别？

一句话：它们都是测试替身（顶替真实依赖的对象），区别在于怎么用：Stub 喂返回值、Mock 验证调用、Spy 包住真实对象局部改写、Fake 是能真正工作的轻量实现。

替身干什么例子
Stub返回预设值，断言结果和状态支付客户端固定返回「成功」
Mock验证某个调用发生了、参数对不对验证支付后发了 OrderPaidEvent
Spy大部分走真实逻辑，个别方法打桩只改价格计算器里的一个折扣方法
Fake有真实逻辑的简化实现用 HashMap 实现的内存仓储
  • 实用规则：查询打桩，命令验证，对查询方法 verify 只会把测试绑死在实现上
  • Spy 打桩用 doReturn，when(spy.m()) 会先真实执行一次

→ 详见 Mock 测试

Q5：什么时候不该用 Mock？

一句话：依赖越稳定、越容易构造，Mock 越不划算；值对象、自己写的纯计算类、不属于你的第三方类型，都不该 Mock。

  • 值对象、DTO、record：直接 new 真实值，Mock 只会让测试更长更脆
  • 简单协作者（计算器、校验器）一起参与测试，单元指一个「行为」而不是一个类
  • RestClient、JdbcTemplate 等第三方类型：包一层自己的接口再 Mock，接口实现用 WireMock / Testcontainers 测
  • 仓储优先用内存 Fake，测试只关心最终状态，被测代码多查一次也不用改测试

常见坑：

  • 一个测试里五六个 when、Mock 返回 Mock、重构不改行为却大面积变红，都是过度 Mock 的信号

→ 详见 Mock 测试

Q6：为什么说 mockStatic / mockConstruction 是坏味道？

一句话：需要它们，说明依赖是写死在代码里的（静态调用、方法内 new），调用方没法替换；正确做法是改成注入，而不是靠工具硬改。

  • mockStatic：把静态调用包成接口或 Supplier 注入，测试直接传 lambda
  • mockConstruction：改为构造器注入依赖或注入工厂
  • 必须 try-with-resources 关闭，否则会污染同线程后续测试；且只对当前线程生效
  • 时间别 Mock LocalDateTime.now()，注入 Clock
  • 合理用途只有一个：给遗留代码先加护栏，锁住行为后重构，再删掉这些 Mock

→ 详见 Mock 测试

Q7：@MockitoBean 和 @Mock 有什么区别？为什么它会拖慢测试？

一句话：@Mock 是纯 Mockito，不启动 Spring；@MockitoBean 是在 Spring 上下文里把某个 Bean 换成 Mock，它会参与上下文缓存键，Mock 组合不统一就会反复启动上下文。

  • 能不启动 Spring 就不启动：构造器注入的类直接 new 加 @Mock，毫秒级
  • @MockitoBean 只用在切片测试或必须启动上下文的集成测试里
  • Boot 的 @MockBean / @SpyBean 在 Boot 4 已删除，改用 Spring Framework 的 @MockitoBean / @MockitoSpyBean
  • 提速：把「外部依赖一律 Mock」收敛成一个组合注解，所有集成测试共用同一组 Mock

常见坑：

  • 同一个 Bean 在不同测试类里的 Mock 字段名不一致，也会被当成不同上下文

→ 详见 Spring Boot 测试

三、集成与契约测试

Q8：集成测试为什么推荐 Testcontainers，而不是 H2？

一句话：集成测试要回答「我的代码和这个中间件配合得对不对」，H2 只是长得像，方言、函数、锁行为都和生产不同，容易「测试绿、上线红」。

方式优点问题
H2 / 嵌入式无需 Docker，快行为与生产不同
Testcontainers与生产同版本，每次全新、用完即删需要 Docker，首次拉镜像慢
共享测试库不占本地资源数据互相污染，没法并行
  • H2 还会让团队刻意回避数据库特性（jsonb、SKIP LOCKED），甚至写两套方言
  • 速度问题用单例容器 + Spring 上下文缓存解决

→ 详见 集成测试

Q9：Flaky 测试是什么？怎么治理？

一句话：代码没变、结果时红时绿的测试；危害是团队养成「红了就重跑」，真回归也被放过，所以要找根因、隔离，而不是重跑掩盖。

  • 时间相关：注入 Clock，用固定时钟
  • 异步没等到：用 Awaitility 轮询断言（反复检查直到满足或超时），禁止 Thread.sleep
  • 顺序依赖、共享状态：每个测试自己准备数据，用随机顺序把依赖暴露出来
  • 固定端口、时区：一律随机端口，构建里固定时区
  • 发现与隔离：rerunFailingTestsCount 只用来识别 Flaky，确认后打 @Tag("flaky") 移出主流水线并指定负责人和期限

→ 详见 集成测试

Q10：Maven 的 Surefire 和 Failsafe 有什么区别？

一句话：Surefire 在 test 阶段跑单元测试、失败立刻中断；Failsafe 在 integration-test 阶段跑集成测试，失败先记下、等清理完成后在 verify 阶段再判定。

  • 命名即配置：单元测试以 Test 结尾，集成测试以 IT 结尾
  • mvn test 只跑单元测试，几秒出结果；mvn verify 才跑集成测试
  • Failsafe 在 package 之后运行，可以测打好的 jar，且保证清理阶段一定执行
  • 两类报告分开输出，CI 里能分别统计耗时和失败

→ 详见 集成测试

Q11：什么是消费者驱动契约？Spring Cloud Contract 和 Pact 怎么选？

一句话：把调用方「以为的接口」写成双方都要遵守的契约，调用方用契约生成的桩测试，提供方用同一份契约验证实现，不用部署对方就能发现接口不兼容。

  • 解决的问题：调用方自己 Mock 对方，对方改了字段名 Mock 不知道，测试全绿上线才报错
  • 契约只包含消费者真正用到的字段，提供方改没人用的字段不会失败
  • Spring Cloud Contract：契约放提供方仓库，JVM 为主，2026 年起移交 Stubborn Contract 维护
  • Pact：契约由消费者测试生成，发到 Pact Broker，多语言，自带 can-i-deploy（部署前检查两个版本能否一起上线）
  • 选型：纯 JVM 且已在用 SCC 就继续；多语言或新引入优先 Pact；外部客户调用改用 OpenAPI + 破坏性变更检查

→ 详见 契约测试

四、TDD 与性能测试

Q12：TDD 的红-绿-重构是什么？什么时候值得用？

一句话：先写一个会失败的测试（红），用最快的方式让它通过（绿），再在测试保护下整理代码（重构），每轮几分钟；规则复杂、生命周期长的核心代码最划算。

  • 「先看到红」是对测试本身的测试，从没失败过的测试可能根本没测到东西
  • 绿阶段允许写死返回值，下一个测试会逼出通用实现
  • 重构不能长期省略，设计改进几乎都发生在这一步
  • 适合：业务规则、状态机、修 Bug（先写复现测试）、公共库 API
  • 不适合：探索性原型、UI 视觉、很薄的胶水代码；需求不清时先澄清

常见坑：

  • 步子太大长时间红着，或测实现细节导致每次重构都改一堆测试

→ 详见 TDD 测试驱动开发

Q13：负载测试、压力测试、浸泡测试有什么区别？

一句话：工具一样，回答的问题不同：负载看预期峰值下达不达标，压力看超过峰值后怎么退化、能否恢复，浸泡看长时间运行会不会泄漏或衰减。

类型负载形态通过标准
负载爬坡到预期峰值后保持P95 / P99、错误率达到阈值
压力加压到峰值 1.5–2 倍以上限流降级生效，撤压后能恢复
浸泡峰值 60%–80% 跑 4–24 小时延迟、内存、连接数不随时间爬升
  • 先跑冒烟（1–5 个虚拟用户），把脚本和数据问题挡在大压测之前
  • 容量点不是崩溃点，而是「P99 达标且 CPU ≤ 70%」时的负载

→ 详见 性能测试

Q14：开放模型和闭合模型有什么区别？什么是协调遗漏？

一句话：闭合模型固定并发用户数、收到响应才发下一个；开放模型按固定速率发请求、不管上一个回没回。闭合模型在系统卡顿时自己也停了，慢请求没被记录，这就是协调遗漏，会让 P99 看起来比真实好得多。

  • 例子：服务 Full GC 停 2 秒，闭合模型只多记 10 个慢样本，真实流量下这 2 秒约有 2000 个请求在排队
  • 面向大量独立用户的在线接口用开放模型（用户不会因为你慢就少来）
  • 闭合模型只适合本身就是固定并发的调用方，比如固定线程池的批处理
  • 看 P95 / P99 不看平均值；k6 出现 dropped_iterations 说明负载没打足，结果不能用
  • wrk 是闭合模型，wrk2 用 -R 固定速率并修正延迟
