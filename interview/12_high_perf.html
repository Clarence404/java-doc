高性能面试题解答

题目清单见 高性能面试题；细节见 高性能模块；三高另外两页：高并发 · 高可用。

版本基线：JDK 21 / 25 LTS、Spring Boot 4.x、MySQL 8.4 LTS，与旧版本不同处单独说明。

一、指标与方法论

Q1：QPS、TPS、RT、并发数之间是什么关系？如何用 Little 定律估算所需线程数或连接数？

一句话：并发数 = QPS × RT（秒），这就是 Little 定律。比如 QPS 2000、RT 50ms，系统里平均同时有 100 个请求在处理。

  • QPS 是每秒请求数；TPS 是每秒业务事务数，一笔「下单」可能包含多次请求
  • 反推容量：200 个线程、每个请求 100ms，最多扛约 2000 QPS
  • 估连接数：QPS 1000、每次占用连接 20ms，平均要 20 个连接，再留余量
  • RT 翻倍，同样的线程和连接能扛的 QPS 就减半；反过来，降低 RT 就等于扩容

常见坑：流量超过处理能力时公式不再成立，请求开始排队，压测里表现为「QPS 上不去、RT 突然飙升」。

→ 详见 性能指标

Q2：为什么不能只看平均响应时间？P99 和 P999 分别意味着什么？

一句话：平均值会把少数很慢的请求「摊平」，而用户卡顿和超时恰恰由这些慢请求造成。P99 是「99% 的请求比它快」，P999 是「99.9% 的请求比它快」。

  • 例子：98 个请求 10ms、2 个 2000ms，平均 49.8ms 看着健康，P99 却是 2000ms
  • P99 用来定接口目标和超时时间；金融交易等对慢请求敏感的场景看 P999
  • 扇出放大：并行调 100 个下游，至少碰上一次慢请求的概率约 63%
  • 多台机器的 P99 不能求平均，要用直方图数据合并计算

常见坑：压测工具在服务卡住时少发请求，慢请求被低估；用固定速率发压的工具（如 wrk2）。

→ 详见 性能指标

Q3：USE 方法和 RED 方法分别适合什么场景？

一句话：USE 看资源（CPU、内存、磁盘、连接池），回答「哪种资源出问题」；RED 看接口，回答「哪个接口出问题」。一般先用 RED 找到慢接口，再用 USE 查它用到的资源。

方法看什么三个指标用在哪
USECPU、内存、磁盘、网络、线程池、连接池使用率、饱和度（排队）、错误整体变慢、不知道原因时全面排查
RED服务、接口请求量、错误、耗时监控大盘和告警
  • 饱和度比使用率更说明问题：比如线程池队列在堆积、连接池有人在等
  • Spring Boot 的 http.server.requests 指标就是现成的 RED 数据

→ 详见 性能分析方法论

Q4：接口突然变慢，你的排查思路是什么？（系统资源 → JVM → 线程/锁 → 外部依赖）

一句话：从外往里一层层查，每层用数据排除；最关键的一刀是先分清「CPU 在忙」还是「在等」。

  • 系统资源：CPU、内存、磁盘、网络有没有打满（top、vmstat、iostat）
  • JVM：GC 是否频繁、停顿是否长、堆是否一直涨（GC 日志、jstat）
  • 线程和锁：线程卡在哪、有没有抢锁（jstack、Arthas、火焰图）
  • 外部依赖：时间是不是花在等数据库、缓存、RPC（链路追踪、慢查询日志）
  • CPU 高 + 慢：计算瓶颈，看 CPU 火焰图；CPU 低 + 慢：在等锁、等 IO、等连接，看线程状态

常见坑：一上来就看代码。线上「突然」变慢，先查最近有没有发布或改配置。

→ 详见 性能分析方法论

Q5：Amdahl 定律对性能优化有什么指导意义？

一句话：一个环节只占总耗时的一小部分，把它优化到 0 整体也快不了多少。所以要先优化占比最大的部分。

  • 公式：整体加速比 = 1 / ((1 - p) + p / k)，p 是这部分的耗时占比，k 是它自己快了几倍
  • 例子：占 5% 的环节降到 0，整体只快约 5%；占 90% 的环节快 10 倍，整体快约 5 倍
  • 并行也一样：有 10% 必须串行，加多少核最多也只快 10 倍
  • 微基准测出某方法快了 30%，要乘上它在接口里的占比，才是真实收益

二、分析工具与基准测试

Q6：火焰图怎么看？CPU 火焰图和 wall-clock 火焰图有什么区别？

一句话：纵向是调用栈，下面调用上面；横向宽度是「被采样到的次数占比」，不是时间先后。重点找顶部很宽的「平顶」，那就是热点。

类型宽度代表用在哪
cpu占用 CPU 的时间CPU 高，找计算热点
wall实际经过的时间（含等待）CPU 不高但很慢，找在等什么
alloc分配的内存量GC 频繁，找谁在大量创建对象
lock等锁时间锁竞争
  • 颜色只区分代码类型（Java、JVM、内核等），不代表热不热
  • 要在问题发生时、高负载下采 30～60 秒
asprof -d 30 -f /tmp/cpu.html <pid>   # async-profiler 抓 30 秒 CPU 火焰图

常见坑：wall 图里 park、epoll_wait 很宽就以为找到了问题。它只说明线程在等，要按线程拆开（-t）看谁在等、等什么。

→ 详见 性能分析工具

Q7：线上 CPU 使用率飙高，如何定位到具体的代码行？

一句话：先找到最耗 CPU 的线程，把线程 ID 转成十六进制，到 jstack 输出里找对应的 nid，栈顶就是热点代码。

top -H -p <pid>                          # 找到高 CPU 的线程 ID
printf "%x\n" <tid>                      # 转十六进制，如 12345 → 3039
jstack <pid> | grep -A 30 "nid=0x3039"   # 看这个线程在执行什么
  • 用 Arthas 更快：thread -n 3 直接列出最忙的 3 个线程和调用栈
  • 一次 jstack 只是瞬间快照，连抓 3～5 次，反复出现的才是热点
  • 偶发或多个线程分摊时，直接抓 30～60 秒 CPU 火焰图更可靠
  • 最忙的是 GC 线程时，问题在对象分配太多或内存泄漏，转查 GC 日志（见 Q12）

→ 详见 JVM 故障排查、线上诊断、性能分析工具

Q8：JFR 能采集哪些信息？适合排查什么问题？

一句话：JFR 是 JDK 自带的「飞行记录仪」，能记录热点方法、对象分配、GC、锁竞争、IO、异常等事件。默认开销通常在 1%～2% 以内，适合在生产上一直开着，出问题后回头看。

  • 特别适合偶发、难复现的问题：问题过去了，录制还在
  • JDK 11 起免费开源，OpenJDK 8u262 起也有
  • 用 JMC 图形界面打开分析，也能转成火焰图
  • 局限：CPU 采样比较粗，要精细的火焰图还是用 async-profiler
jcmd <pid> JFR.dump name=bg filename=/tmp/snapshot.jfr   # 导出常驻录制

→ 详见 性能分析工具

Q9：为什么用 System.nanoTime 循环测性能不可靠？JMH 是如何解决的？

一句话：JIT 编译器会在背后优化代码：没预热时跑得慢、结果没用到的代码会被整段删掉、常量会被提前算好，所以手写循环测到的不是真实性能。JMH 把预热、隔离、防优化都做好了。

  • 预热：刚启动是解释执行，编译后可能快几十倍；JMH 用 @Warmup 先跑几轮
  • 防删代码：把结果 return 出去或交给 Blackhole.consume()，让 JIT 不敢删
  • 防提前计算：输入放在 @State 对象的非 final 字段里
  • 隔离：@Fork 每个测试单独起一个 JVM，避免互相干扰
  • 看结果：两组 Score ± Error 区间重叠，说明差异不显著

常见坑：拿 JMH 结果说系统能扛多少。JMH 只回答「A 写法比 B 快多少」，容量还得靠压测。

三、JVM 层

Q10：低延迟和高吞吐场景分别怎么选垃圾收集器？

一句话：普通在线服务用默认的 G1；对 P99 很敏感、堆大且 CPU 有富余用分代 ZGC；批处理只看总耗时用 Parallel。大多数服务 G1 + 合理的堆大小就够了。

收集器停顿适用
G1可设目标，默认 200ms通用在线服务（默认）
分代 ZGC通常不到 1msP99 敏感、大堆
Parallel较长，但吞吐最高批处理、离线计算
Serial长1 核或很小内存的容器
  • JDK 21 开分代 ZGC 要写 -XX:+UseZGC -XX:+ZGenerational，JDK 23 起分代是默认
  • 如果 P99 主要不是 GC 停顿造成的，换收集器帮助不大

常见坑：容器只给 1 核 CPU 时 JVM 会默认选 Serial，要显式指定收集器。

→ 详见 JVM 层性能策略

Q11：应用刚启动时 RT 毛刺明显，原因是什么？如何缓解？

一句话：刚启动时代码还没被 JIT 编译成高效的机器码，加上类加载、连接池和缓存都是空的，一上来就接满流量就会变慢。解决办法是先预热、再接流量、慢慢加量。

  • 预热：启动后、标记就绪前，主动调几轮核心接口
  • 就绪后置：预热放在 ApplicationRunner 里，做完 readiness 探针才通过
  • 逐步放量：负载均衡给新实例慢慢加权重（如 Dubbo warmup、Envoy slow start）
  • 提前初始化：连接池建好最小连接、缓存预加载
  • CPU 给够：CPU 限额太小，JIT 编译会很慢

常见坑：以为 AppCDS 能解决。它只加快类加载，解决不了 JIT 预热。

→ 详见 JVM 层性能策略、优雅上下线与变更

Q12：为什么降低对象分配速率往往比调 GC 参数更有效？

一句话：创建对象越快，GC 就越频繁。调参只是换一种回收方式，少创建对象才是「少产生垃圾」，而且对哪种收集器都有效。

  • 怎么测：看 GC 日志算分配速率，或用 async-profiler -e alloc 找分配最多的代码
  • 常见手段：避免装箱、集合和 StringBuilder 预设大小、少做多层 DTO 转换
  • 大结果集用流式读取，不要一次全读进内存
  • 以分配火焰图实测为准，不要指望 JIT 的逃逸分析自动帮你优化

常见坑：老年代每次 GC 后还一直涨，那是内存泄漏，调参没用，要 dump 堆分析。

→ 详见 JVM 层性能策略

四、代码与池化

Q13：有哪些常见的代码级性能优化手段？HashMap 初始容量应该如何设置？

一句话：先用 Profiler 确认热点再改，不热的代码优先保证可读。HashMap 初始容量按「预期元素数 / 0.75 + 1」设，或直接用 JDK 19 起的 HashMap.newHashMap(n)。

  • 复用昂贵对象：Pattern、ObjectMapper、DateTimeFormatter 这类线程安全的对象做成 static final
  • 集合和字符串：已知大小就预分配；循环里拼字符串用 StringBuilder
  • 少装箱：累加、计数用基本类型，Stream 用 mapToInt
  • 锁：缩小加锁范围，IO 移到锁外；高并发计数用 LongAdder
  • 算法：两层循环查找改成先建 Map 再查

常见坑：以为 new HashMap<>(n) 放 n 个元素不会扩容。元素数超过「容量 × 0.75」就会扩容。

→ 详见 代码级优化

Q14：为什么不建议用异常做流程控制？日志有哪些常见的性能坑？

一句话：创建异常要收集整个调用栈，比普通对象贵得多，高频抛出会变成 CPU 热点。日志的坑主要是「不输出也在拼字符串」和「同步写磁盘卡住业务线程」。

  • 异常：先做简单校验，只让极少数情况走异常；高频业务异常可以关掉收集调用栈
  • 日志用 {} 占位符，不要字符串拼接；参数本身很贵（如转 JSON）时先判断 isDebugEnabled()
  • 用异步日志（Logback AsyncAppender、Log4j2 AsyncLogger），注意队列满了怎么处理
  • 日志格式里的行号、方法名（%L、%M）要取调用栈，生产慎用

常见坑：生产开全量 DEBUG，或在大循环里逐条打日志。

→ 详见 代码级优化

Q15：数据库连接池的大小如何确定？连接池是不是越大越好？

一句话：不是越大越好。连接池大小取决于数据库能同时处理多少请求，超出后数据库忙着切换和抢锁，反而更慢。先用经验公式估，再用 Little 定律校验。

  • 经验公式：数据库服务器核数 × 2 + 磁盘数，这是数据库侧的总连接数，多个应用实例要分摊
  • Little 定律：所需连接数 = 单实例 QPS × 每次占用连接的时间；算出来太大，先缩短占用时间（优化慢 SQL、事务里不调 RPC）
  • 全局上限：所有实例的最大连接数加起来不超过数据库 max_connections 的 80%，扩容前重新算
  • connectionTimeout 默认 30 秒，线上建议 2～5 秒，拿不到连接快速失败
  • maxLifetime 要比数据库、防火墙的空闲超时短几十秒

常见坑：连接不够就加大池子。先看等待连接的线程数（pending）持续大于 0 且数据库本身不忙，才说明池真的小了。

→ 详见 池化技术、数据库连接池

Q16：如何发现和排查连接泄漏？

一句话：连接泄漏就是借了不还，池子慢慢被耗光，典型表现是「拿连接超时，但数据库很闲」。打开 HikariCP 的 leakDetectionThreshold，它会打印出借连接时的调用栈。

  • leakDetectionThreshold 默认关闭，排查时设成比最长正常 SQL 稍大
  • 监控：活跃连接长期贴着上限、等待数持续大于 0 就告警
  • 常见原因：手动拿连接没在 finally 或 try-with-resources 里关；异常路径上事务没结束
  • 最常见的原因：在事务里调用外部服务，连接被一直占着

常见坑：手动管理连接。尽量交给框架（Spring 事务、MyBatis）统一借还。

→ 详见 池化技术

Q17：HTTP 客户端连接池需要关注哪些参数？为什么会出现 NoHttpResponseException？

一句话：要关注总连接数、每个目标地址的连接数、超时和连接存活时间，客户端全局只建一个复用。NoHttpResponseException 一般是客户端拿到了一个服务端已经关掉的空闲连接。

  • Apache HttpClient 5 默认每个目标地址只有 5 个连接，调同一个下游并发超过 5 就排队，最容易被忽视
  • 获取连接、建立连接、读数据三种超时分开设，获取连接的超时要短
  • 设置连接最大寿命，后台定期清理空闲连接，空闲久了借出前先校验
  • 解决 NoHttpResponseException：客户端空闲超时要小于服务端 Keep-Alive 超时（Nginx 默认 75 秒）；幂等请求可以重试一次

常见坑：每次请求 new 一个客户端，连接池完全没用上。

→ 详见 池化技术

Q18：什么对象不应该池化？

一句话：只有「创建很贵、又能安全复用」的东西才值得池化，比如连接、线程、大块缓冲区。普通小对象池化反而更慢。

  • 普通小对象（DTO、集合）：JVM 分配新对象极快，回收也几乎不花钱；池化反而让它们活得久、进老年代，还要加锁
  • 状态复杂、难以重置干净的对象：归还后残留数据，下一个使用者会读到脏数据
  • 并发极高时池本身的锁会成为瓶颈，改用 ThreadLocal 每个线程一份
  • 虚拟线程：创建成本极低，不要池化；要限制下游并发，用信号量或连接池

→ 详见 池化技术

五、异步、批量与 IO

Q19：如何把一个串行调用多个下游的接口优化为并行？需要注意什么？

一句话：互不依赖的下游调用用 CompletableFuture 放到一个独立、有上限的线程池里同时发起，总耗时从「各段相加」变成「最慢的那段」。关键要管好线程池、超时、异常三件事。

var priceF = CompletableFuture.supplyAsync(() -> priceClient.get(id), ioPool);
var reviewF = CompletableFuture.supplyAsync(() -> reviewClient.top(id), ioPool).exceptionally(ex -> List.of());
  • 核心数据失败就整体失败；非核心数据失败或超时就降级（返回空、默认值）
  • 整体设一个超时预算（如 orTimeout(500ms)），HTTP / RPC 客户端自己也要设超时（见 Q20）
  • join() 抛出的是 CompletionException，用 getCause() 区分超时还是业务失败
  • ThreadLocal、链路追踪的上下文不会自动传到池里的线程，要手动传

常见坑：不传线程池，用默认的 commonPool。它只有「核数 − 1」个线程，被阻塞 IO 占满会拖垮全局。

→ 详见 异步与批量

Q20：CompletableFuture.orTimeout 超时后，底层任务会被取消吗？

一句话：不会。orTimeout 只是让这个 Future 提前以超时结束，正在跑的下游调用不会被打断，线程和连接还被占着；cancel(true) 也一样中断不了。

  • 后果：慢下游一直占着线程，线程池会被慢慢占满
  • 解决：HTTP / RPC 客户端自己必须设连接和读超时，而且不能大于这里的超时预算
  • completeOnTimeout 同理，只是超时后给一个默认值

→ 详见 异步与批量

Q21：什么是对冲请求（Hedged Request）？有什么使用前提？

一句话：先发一个请求，等了一会儿（通常是该接口的 P95 耗时）还没回来，就再向另一个副本发一份，谁先回来用谁。只多发约 5% 的请求，就能大幅削掉慢请求。

  • 只能用于幂等、没有副作用的读请求，写请求重复发会出问题
  • 两次请求要能落到不同机器上，否则没意义
  • 等待时间取 P95 左右：太早会让下游流量翻倍，太晚削不掉慢请求
  • 下游整体过载时对冲会雪上加霜，要限制对冲比例，配合熔断限流
  • 优先用框架现成的能力，如 gRPC 的 hedgingPolicy

→ 详见 异步与批量、性能分析方法论

Q22：什么是请求合并？适合什么场景，有什么代价？

一句话：把很短时间内（如 10ms）查不同 key 的单条请求攒起来，合成一次批量查询，再把结果分给各个调用方。下游调用次数大大减少，代价是每个请求要多等一个窗口时间。

  • 适合：QPS 高、下游有批量接口、能接受多等几毫秒
  • 不适合：QPS 低（攒不满一批，只是白白变慢）、强实时场景
  • 实现要点：队列要有上限、攒够一批立刻发、查不到的 key 也要明确返回空、调用方设超时
  • 和 SingleFlight 的区别：SingleFlight 合并的是「相同 key」的并发请求（防缓存击穿），请求合并针对「不同 key」

→ 详见 异步与批量

Q23：什么是零拷贝？Kafka 为什么吞吐量高？开启 TLS 后有什么影响？

一句话：零拷贝就是数据不经过程序加工、直接在内核里从文件送到网卡，少了几次复制。Kafka 吞吐高靠顺序写、页缓存、批量压缩和分区并行，发给消费者时用了零拷贝。开 TLS 后数据必须在程序里加密，零拷贝就用不了了。

方式Java API谁在用
mmap 内存映射FileChannel.map()RocketMQ
sendfile 文件直传FileChannel.transferTo()Kafka、Nginx 静态文件
  • 只有「大块数据原样搬运」时收益明显；普通 JSON 接口要序列化，用不上
  • Netty 的 CompositeByteBuf、直接内存属于程序里的「少拷贝」，不是操作系统的零拷贝

常见坑：开 TLS 后不调整容量评估，吞吐会明显下降、CPU 上升。

→ 详见 IO 与网络优化、IO / NIO 专题

Q24：HTTP/1.1、HTTP/2、HTTP/3 在连接复用上有什么区别？

一句话：HTTP/1.1 能复用连接，但一个连接同时只能跑一个请求；HTTP/2 一个连接能同时跑多个请求，但 TCP 丢包时还是全部卡住；HTTP/3 改用基于 UDP 的 QUIC，解决了这个问题。

对比HTTP/1.1HTTP/2HTTP/3
连接复用一次一个请求一个连接多个请求一个连接多个请求
队头阻塞（前面卡住后面全等）有TCP 层仍有解决
典型用途内部 REST 调用gRPC、浏览器移动端弱网、CDN
  • 复用连接是最便宜的优化：短连接每次都要握手，跨地域时光建连就要几十上百毫秒
  • 服务间调用用连接池 + Keep-Alive；高频内部调用可以考虑 gRPC

六、数据访问

Q25：慢 SQL 如何发现、分析和优化？为什么要按总耗时排序？

一句话：流程是「发现 → 按总耗时排序 → EXPLAIN 分析 → 优化 → 验证」。按总耗时（次数 × 单次耗时）排，是因为数据库压力看的是总消耗，经常跑的中等慢 SQL 往往比偶尔跑的超慢 SQL 危害更大。

  • 发现：开慢查询日志（如超过 0.5 秒记录），或看 APM 里的 SQL 耗时
  • 排序：用 pt-query-digest 汇总，按总耗时排
  • 分析：EXPLAIN 看有没有走索引、扫了多少行、有没有额外排序
  • 优化：加索引、调整联合索引列顺序、去掉索引列上的函数和隐式类型转换、改写 SQL
  • 例子：每天跑 10 次、每次 2 秒的报表，远不如每秒 500 次、每次 20ms 的列表查询压力大

→ 详见 数据访问性能

Q26：深分页为什么慢？有哪些优化方案？游标分页需要什么索引？

一句话：LIMIT 100000, 10 要先读出 100010 行再扔掉前 10 万行，页越深越慢。首选游标分页：记住上一页最后一条，下一页从它后面接着查。

  • 游标分页：WHERE (create_time, id) < (上页最后的值) ORDER BY ... LIMIT 10，缺点是不能随机跳页
  • 必须跳页时用延迟关联：先在索引上只查出 10 个 id，再回表取完整数据
  • 也可以让产品限制最多翻几页，或改用搜索引擎（ES search_after）
  • 索引：过滤列 + 排序列建联合索引，如 WHERE user_id = ? ORDER BY create_time 建 (user_id, create_time)
  • 批量导出、数据迁移一律按主键游标：WHERE id > ? ORDER BY id LIMIT 1000

常见坑：排序字段有重复值时只用它做游标，翻页会重复或漏数据；要带上 id 一起做游标。

→ 详见 数据访问性能、MySQL 索引

Q27：JDBC 批量插入为什么没有变快？rewriteBatchedStatements 的作用是什么？

一句话：MySQL 驱动默认即使调了 executeBatch() 也是一条条发的。加上 rewriteBatchedStatements=true，驱动才会把一批 INSERT 合成一条多值 INSERT 一次发出去。

  • 真正变快要同时做到三点：用批量 API、开驱动改写、分批提交事务
  • 批量 API：JDBC addBatch()、MyBatis ExecutorType.BATCH、JPA 配 hibernate.jdbc.batch_size
  • 分批提交：关掉自动提交，每 500～1000 行提交一次；一次提交几十万行会长时间锁表、主从延迟
  • 合并后的 SQL 不能超过 max_allowed_packet

常见坑：Hibernate 主键用 IDENTITY（数据库自增）时无法批量插入。

→ 详见 数据访问性能、MySQL JDBC 驱动

Q28：什么是 N+1 查询问题？如何发现和解决？

一句话：先查出 N 条主记录，再对每条单独查一次关联数据，一共 1 + N 次查询。最通用的解法：收集所有 id，用一次 IN 批量查出来，在内存里拼起来，查询变成 2 次。

  • 一对一或一对少的关联，也可以直接 JOIN 一次查出
  • JPA：JOIN FETCH 或 @EntityGraph；懒加载可加 @BatchSize 按批加载
  • 常见来源：JPA 懒加载在循环里访问、MyBatis 嵌套查询、循环里逐条调 RPC
  • 发现：统计单个请求执行了多少条 SQL，或在链路追踪里看重复 SQL

常见坑：JPA 一对多 JOIN FETCH 和分页一起用，会把数据全查出来在内存里分页。

→ 详见 数据访问性能

Q29：IN 列表过长会带来什么问题？

一句话：SQL 变长、解析变慢只是小事，关键是执行计划可能变差：值太多时优化器改用粗略估算，可能选错索引甚至全表扫描。按几百个一批分批查。

  • MySQL 中 IN 的值超过 eq_range_index_dive_limit（默认 200）后，优化器不再逐个精确估算，改用统计信息估，可能估错
  • 范围分析用的内存超过上限（默认 8MB）时，会放弃走索引范围扫描
  • 批量接口、请求合并也一样，要限制单批的大小

→ 详见 数据访问性能

七、综合案例

Q30：讲一次你做过的接口性能优化：如何定目标、建基线、定位和验证？

一句话：按「定目标 → 建基线 → 定位瓶颈 → 一次只改一项 → 压测验证 → 灰度上线、防回归」来讲，每一步都拿数据说话。

  • 目标和基线（示例数据）：下单接口 P99 800ms，目标 300 QPS 下 P99 ≤ 250ms；基线压测发现报错全是拿连接超时，单请求 26 条 SQL
  • 定位：链路追踪看到三段 RPC 串行、逐条查 SKU；Little 定律算出需要约 33 个连接，但池只有 20
  • 优化：N+1 改批量查、把 RPC 移出事务、独立调用改并行、加本地缓存、日志瘦身
  • 结果：P99 800ms → 195ms，错误率 0.3% → 0.02%
  • 讲清「没做什么」也加分：GC 不是瓶颈所以没调 GC；问题在连接占用时间所以没加大池子

常见坑：只讲做了什么，不给数据。没有前后对比的数字，面试官没法判断收益。

→ 详见 端到端优化案例

Q31：如何证明一项优化确实有效，而不是环境波动？

一句话：控制变量、看分布、看误差。同一环境、同一脚本、同样数据量，预热后取稳定阶段的数据，一次只改一个地方，差异要明显大于测量本身的波动。

  • 压测对比 P50 / P99 / P999 和资源使用率，不只看平均值；多跑几次
  • 纯 CPU 的改动用 JMH 单独验证，两组误差区间重叠就说明没有显著差异
  • 每项改动单独压测，才能说清收益来自哪一项
  • 看副作用：数据库 CPU、下游 QPS、缓存命中率有没有变差
  • 线上先灰度 1 台，和其他实例同时段对比 P99 和错误率

→ 详见 端到端优化案例、性能分析方法论

Q32：优化上线后，如何防止性能回归？

一句话：把性能基线放进发布流程，让变慢的版本在发布前被拦住、上线后被及时发现。

  • 发布前：核心接口压测作为发布检查项，P99 变差超过阈值就阻断
  • CI：关键热点方法的 JMH 基准放进 CI，和历史结果对比
  • 灰度：灰度实例和老版本对比 P99、错误率，异常自动暂停
  • 监控：P99 超目标、连接池有等待等持续 1 分钟就告警
  • 沉淀：记录每次优化实验（包括无效的），复盘清单纳入评审
