AI 面试题解答

题目清单见 AI 面试题；细节见 AI 总览。

版本基线：Spring AI 2.0.x（Spring Boot 4；Boot 3 对应 1.1.x）、LangChain4j 1.x、MCP 规范 2026-07-28；模型型号与价格以各厂商官方页面为准。

一、大模型基础

Q1：Token 是什么？怎么准确统计 Token 数？

一句话：Token 是模型切分文本的最小单位，也是计费和长度限制的单位；一个汉字或单词对应几个 Token 取决于模型的分词器，不能用固定比例估算。

  • 准确值看响应里的 usage 字段：输入、输出、缓存命中分开给出，这就是计费依据，要记进日志和监控
  • 发送前预估：Anthropic 有 count_tokens 接口；OpenAI 系编码在 Java 里可以用 jtokkit 离线计数
  • 开源模型用模型自带的 tokenizer 文件计数
  • 工具定义、系统提示、对话历史都算输入 Token，容易被漏算

→ 详见 大模型选型

Q2：上下文窗口是什么？多轮对话为什么越聊越贵？

一句话：上下文窗口是模型单次请求能装下的 Token 上限，系统提示、检索结果、历史消息和输出都要装进去；模型本身无状态，每一轮都要把之前的历史重新发一遍，所以长会话的成本近似按轮数平方增长。

  • 先算「系统提示 + 检索结果 + 历史 + 预留输出」，再选模型或调参数
  • 控制历史：按消息条数或 Token 数开窗口，早期消息定期摘要
  • 能用 RAG 只挑相关片段，就不要把整篇文档硬塞进长上下文
  • 本地模型的默认上下文较短，超出部分会被静默截断，模型「看不到」却不报错

→ 详见 大模型基础概念、历史管理、Ollama

Q3：temperature 是干什么的？怎么设置？

一句话：temperature 控制采样的随机程度：越低输出越稳定、越保守，越高越发散、越有创意；抽取、分类、结构化输出用低值，创作类任务才调高。

  • 常和 top_p、top_k 一起出现，一般只调其中一个
  • temperature 设为 0 也不保证每次输出完全一样，固定 seed（部分模型支持）也只是尽力复现，确定性要靠缓存结果和代码校验
  • 部分推理模型不接受自定义 temperature，传了直接报错，以模型文档为准
  • Spring AI 2.0 取消了框架自带的默认 temperature，不配置就用厂商默认值

常见坑：把旧项目的 temperature: 0.7 照搬到推理模型上，请求直接失败。

→ 详见 大模型基础概念、Spring AI、Ollama

Q4：大模型为什么会「幻觉」？怎么降低？

一句话：模型按概率生成「看起来最合理」的下一个 Token，本身没有「我不知道」的机制；遇到训练数据里没有、过期或私有的知识时，它会自信地编一个答案。

  • 缺知识：用 RAG 注入最新的私有文档，要求只依据资料回答并标注来源
  • 允许说不知道：检索为空或相似度低于阈值时，明确让模型回答「没有找到依据」
  • 工具参数幻觉：开 strict 模式，解析后再做业务校验，非法时把错误回传让模型修正
  • 结构化输出只保证格式正确，不保证内容正确，关键字段仍要代码校验

常见坑：以为微调能减少幻觉。微调不会让模型更「诚实」，学到错误样本反而会放大。

→ 详见 大模型基础概念、RAG 检索增强生成、Function Calling（工具调用）

Q5：推理模型和普通模型有什么区别？还需要写「一步一步思考」吗？

一句话：推理模型回答前会先在内部思考，复杂的数学、逻辑、多步规划更准，但更慢更贵；对它们写「一步一步思考」基本没用，要用 API 参数控制推理深度。

  • OpenAI 用 reasoning.effort（Chat Completions 是 reasoning_effort），Anthropic 用 output_config.effort
  • 思考过程即使不返回，也按输出 Token 计费，并占用 max_tokens
  • Prompt 写目标、约束和完成标准，不要规定每一步怎么想
  • 简单的分类、抽取调低 effort 或关闭思考，能明显降低延迟和成本

→ 详见 Prompt 工程

Q6：怎么估算大模型 API 的调用成本？

一句话：按 Token 分项相加：未命中缓存的输入、缓存写入、缓存读取、输出各乘各自的单价；月成本再乘调用量和重试放大系数。

  • 单次成本 = 未缓存输入 × 输入单价 + 缓存写入 × 写入单价 + 缓存读取 × 读取单价 + 输出 × 输出单价
  • 推理 Token 按输出计费；输出单价通常是输入的数倍，控制输出长度很划算
  • 多轮历史、工具定义都会重复计入输入
  • 降本手段：简单任务路由到轻量档、Prompt Caching、离线任务走 Batch、限制输出长度

→ 详见 大模型选型、API 直接接入

Q7：大模型选型看哪些维度？

一句话：看七个维度：能力档位、延迟、上下文、价格、数据驻留、开源与否、许可证；最终用自己业务的几十到几百条样本做小评测，公开榜单只做初筛。

  • 代码只依赖「旗舰 / 均衡 / 轻量」档位，型号写在配置里，换型号不改代码
  • 按任务路由：意图分类走轻量档，最终回答走均衡档，多步规划走旗舰档；旗舰超时或限流时降级
  • 数据不能出公司：开源权重模型私有化部署
  • 开源权重不等于开源许可，有的附带月活上限等条款，商用前看模型卡

→ 详见 大模型选型

二、Prompt 与结构化输出

Q8：怎么写好 Prompt？System Prompt 能当安全边界吗？

一句话：四条原则：清晰具体、交代背景和目的、给出示例、约定输出格式；System Prompt 能提升行为一致性，但不是安全边界，用户输入和检索内容都可能让模型偏离它。

  • 交代「为什么做、给谁用」比堆规则更有效，模型能处理规则没覆盖的情况
  • Few-shot：给 3–5 个覆盖各类别和边界的示例，示例风格要多样
  • 模板外置并带版本号，调用时记录模板版本、模型和 usage，改动前后跑回归评测
  • 安全控制落在代码里：权限、确认、校验，而不是写在提示词里

→ 详见 Prompt 工程

Q9：怎么让模型稳定输出 JSON？Spring AI 的 .entity() 是怎么做的？

一句话：优先用厂商的原生结构化输出：把 JSON Schema 交给 API，模型解码时就保证符合 Schema，比在 Prompt 里写「请返回 JSON」可靠得多。

  • 协议层：OpenAI Responses 用 text.format，Chat Completions 用 response_format，Anthropic 用 output_config.format
  • Spring AI .entity(Xxx.class)：根据 record 生成 Schema，拿到结果反序列化成对象；加 useProviderStructuredOutput() 后改用厂商原生约束，不支持时退回到把格式说明拼进 Prompt
  • LangChain4j：AI Service 方法直接返回 POJO，开启 JSON Schema 能力更稳
  • Schema 只管结构，取值范围、内容真假仍要代码校验

常见坑：Prompt 里写 product_name，record 字段却是 productName，模型困惑，退回 Prompt 模式时还会映射失败。

→ 详见 Prompt 工程、Spring AI

Q10：Prompt Caching 怎么才能命中？

一句话：缓存按请求前缀精确匹配，所以 Prompt 要按「越稳定越靠前」排列：工具定义 → System Prompt → 固定资料和示例 → 对话历史 → 本轮问题。

  • 命中部分按折扣价计费，首 Token 延迟也更低
  • 有的厂商对长前缀自动缓存，有的要显式标记断点（如 Anthropic 的 cache_control）
  • 系统提示里拼当前时间、用户 ID、请求 ID，会让缓存全部失效
  • 前缀低于最小可缓存长度不会缓存也不报错；只调用一次的前缀不值得缓存（写入比普通输入贵）

→ 详见 Prompt 工程、API 直接接入

三、Function Calling 与 MCP

Q11：一次 Function Calling 的完整流程是什么？tool_call_id 有什么用？

一句话：两轮请求：第一轮带上工具定义，模型返回「想调哪个工具、传什么参数」；应用自己执行后把结果回传，第二轮模型再生成最终回答。模型从不执行函数。

  • 第一轮：请求带 tools（名称、描述、参数 JSON Schema）
  • 模型返回调用意图：OpenAI 是 finish_reason: tool_calls，arguments 是字符串形式的 JSON，要再解析一次
  • 第二轮：结果以 role: tool 消息追加，带上 tool_call_id
  • tool_call_id 用来把结果和调用意图一一配对，一次返回多个并行调用时全靠它

→ 详见 Function Calling（工具调用）

Q12：OpenAI 和 Anthropic 的工具调用协议有什么区别？

一句话：概念一样，字段不同；直接对接 API 要分别解析，用 Spring AI、LangChain4j 时框架会抹平差异。

  • OpenAI 新模型和新功能优先落在 Responses API（function_call / function_call_output）
  • Anthropic 调用工具前常先输出一段说明文字，不要假设 content 里只有工具块
  • 工具出错时不要直接抛异常中断，把错误信息作为工具结果回传（Anthropic 可标 is_error: true），让模型自己重试或换条路

工具定义tools[].function.parameterstools[].input_schema
需要调用的信号finish_reason: tool_callsstop_reason: tool_use
参数JSON 字符串JSON 对象（tool_use 块）
回传结果role: tool + tool_call_iduser 消息里的 tool_result + tool_use_id

→ 详见 Function Calling（工具调用）

Q13：tool_choice 有哪几种取值？strict 模式和结构化输出怎么分工？

一句话：auto 模型自己判断、none 禁止调用、required（Anthropic 叫 any）至少调一个、指定工具名则必须调那一个；strict 保证工具参数符合 Schema，结构化输出保证最终回答符合 Schema。

  • required / any 不锁定是哪个工具，要锁定必须用指定工具的写法
  • 部分模型不支持强制调用，传了会 400，这时用 auto + strict 或改用结构化输出
  • strict 一般要求 additionalProperties: false、所有字段列入 required，可选字段用 null 类型
  • 分工：要执行动作用 Function Calling，只要格式化数据用结构化输出

→ 详见 Function Calling（工具调用）

Q14：MCP 是什么？和 Function Calling 是什么关系？

一句话：MCP（Model Context Protocol）是把「工具从哪来」标准化的开放协议，工具提供方写一次 MCP Server，所有支持 MCP 的应用都能接；它在 Function Calling 之上，模型侧照样走 Function Calling，并不知道 MCP 的存在。

  • 三个角色：Host（AI 应用）、Client（Host 里连某个 Server 的组件）、Server（暴露能力的服务）
  • Server 能力：Tools（模型决定调用）、Resources（应用读取的只读数据）、Prompts（用户选择的模板）
  • 流程：Client 拿到工具列表转成模型的工具定义；模型发起调用后，Client 通过 JSON-RPC 转发给 Server 执行
  • 治理：2024 年由 Anthropic 发起，2025 年 12 月捐赠给 Linux 基金会下的 Agentic AI Foundation

→ 详见 MCP 协议

Q15：MCP 的 stdio 和 Streamable HTTP 有什么区别？为什么废弃 HTTP+SSE？

一句话：stdio 是 Host 启动 Server 子进程、用标准输入输出通信，适合本地工具；Streamable HTTP 是一个 HTTP 端点，响应可以是普通 JSON 或 SSE 流，适合远程共享。HTTP+SSE 在 2025-03-26 版本就被 Streamable HTTP 取代了。

  • stdio：凭据从环境变量注入，不走 OAuth；stdout 就是协议通道，Banner 和控制台日志必须关掉
  • Streamable HTTP：一个端点（通常 /mcp）搞定，不必维持单独的 SSE 长连接
  • 2026-07-28 版本协议改为无状态：去掉 initialize 握手和会话 ID，便于水平扩展；但 Java SDK（2.0.x）还停在 2025-11-25，未跟进前多实例仍要按会话 ID 粘滞，或用 Spring AI 的 STATELESS 模式
  • 同一版本还废弃了 Sampling、Roots，新实现不要再依赖

→ 详见 MCP 协议

Q16：远程 MCP Server 怎么做认证？什么是令牌透传和工具投毒？

一句话：远程 HTTP 传输按规范用 OAuth 2.1：MCP Server 是资源服务器，只接受签发给自己的令牌；HTTP 端点默认没有任何认证，暴露出去之前必须先加安全层。

  • 客户端通过受保护资源元数据（RFC 9728）发现授权服务器，用授权码 + PKCE 拿令牌
  • 禁止令牌透传：不能把客户端的令牌原样转发给下游 API，否则形成「混淆代理」
  • 工具投毒：工具名称和描述原样进入模型上下文，恶意 Server 可以在描述里藏指令，或在批准后偷偷改描述
  • 应对：只接可信来源并固定版本、升级时比对工具描述、工具名白名单、副作用操作人工确认

→ 详见 MCP 协议

四、RAG

Q17：RAG 的完整流程是什么？

一句话：「先查资料再回答」：离线把文档切块、向量化后写进向量库；在线把用户问题向量化，检索出最相关的几段拼进 Prompt，让模型依据它们回答并标注来源。

  • 索引阶段：加载 → 切块 → Embedding → 连同来源、权限等元数据入库，文档变化时增量更新
  • 查询阶段：（改写问题）→ 向量化 → 相似度 + 元数据过滤取 Top-K →（Rerank）→ 拼接 → 生成带引用的回答
  • 两个阶段必须用同一个 Embedding 模型和维度，否则向量不在同一个空间里
  • 解决的问题：知识过期、私有数据、幻觉与可追溯

→ 详见 RAG 检索增强生成

Q18：文档怎么切块？块大小和重叠怎么定？

一句话：每块讲清一件事：太大会稀释相似度、浪费 Token，太小会丢上下文；默认用递归切分，起点是 300–800 Token、相邻块重叠 10%–15%，再用评估集比几组参数。

  • 策略：固定长度、递归切分（默认）、按标题结构切分、父子块（小块检索、命中后把整节交给模型）
  • 单位要分清：Spring AI 的 TokenTextSplitter 按 Token，LangChain4j 的递归切分默认按字符
  • 给每块加「文档标题 > 章节标题」前缀再向量化，能改善「本节」「该接口」这类指代不清的片段
  • 换切块策略要全量重建索引，所以早期就要定下来

→ 详见 RAG 检索增强生成

Q19：余弦相似度、点积、欧氏距离怎么选？换 Embedding 模型为什么要全量重建？

一句话：文本语义检索默认用余弦相似度；向量已归一化（长度为 1）时，点积和余弦完全等价，欧氏距离的排序也一致。换模型要重建，是因为不同模型的向量不在同一个空间里，混在一起检索毫无意义。

  • 向量库索引的距离类型必须和查询用的一致，否则召回率明显下降
  • 是否已归一化要按模型确认，自己截断维度后必须重新归一化
  • 存储 = 条数 × 维度 × 每维字节数；Matryoshka 模型可以只取前 N 维，存储降到三分之一以下、召回损失通常很小
  • 入库时把模型名、维度写进元数据，换模型时双写、灰度切换

→ 详见 Embedding 向量化

Q20：HNSW 和 IVF 的原理与取舍？带过滤条件的向量检索为什么会结果不足？

一句话：HNSW 是分层图，从顶层快速跳到目标区域再逐层下沉，召回高、延迟低但吃内存；IVF 先聚类再只查最近的几个簇，省内存、建得快，但要训练、数据分布变了要重建。

  • HNSW 参数：m、ef_construction 管建图质量，ef_search 越大召回越高、越慢
  • 量化（SQ / PQ / BQ）用少量召回换大量内存，常配合原始向量精排
  • 过滤陷阱：先取 Top-K 再过滤，条件严时会「过滤过头」，结果不满 LIMIT
  • 对策：Qdrant、Milvus 在索引内过滤；pgvector 0.8 起用迭代扫描（hnsw.iterative_scan）缓解
  • 选型先看现有组件：已有 PG 用 pgvector，已有 ES 用 ES，独立部署选 Qdrant，亿级以上选 Milvus

→ 详见 向量数据库

Q21：混合检索为什么用 RRF 融合？Rerank 为什么能提升效果？

一句话：向量检索懂语义但对型号、错误码这类精确词不敏感，BM25 正好相反，两路并行再用 RRF 按名次合并；Rerank 用交叉编码器把「问题 + 片段」放在一起打分，比双塔向量检索精准得多，只用于精排。

  • RRF 分数 = Σ 1 / (k + 名次)，k 通常取 60；只看名次，不用把余弦分数和 BM25 分数归一到同一尺度
  • Rerank 慢，所以先粗检索 Top-30～50，精排后取前 3～5 条交给模型
  • Query 改写：把带指代、口语化的问题改写成独立的检索语句，或拆成多个子问题
  • 按问题类型逐步叠加，不必一上来就全上

→ 详见 RAG 检索增强生成

Q22：怎么评估一个 RAG 系统？

一句话：检索和生成分开评：先看有没有找到对的片段，再看答案是否忠实于片段；评估集用 50–200 条真实问题，标注标准答案和应命中的片段。

  • 检索指标：Recall@K（找没找到）、MRR（排得靠不靠前）、上下文精确率（噪声多不多）
  • 生成指标：忠实度（每个论断能否在上下文里找到依据）、答案相关性、无答案时是否如实说「没找到」
  • 生成指标常用 LLM 按评分标准打分（LLM-as-a-judge），要定期人工抽检校准
  • 每次改切块、换模型、调参数都跑一遍回归

→ 详见 RAG 检索增强生成

Q23：什么时候用 Prompt、RAG，什么时候才该微调？

一句话：先写评估集，再按 Prompt → RAG → 微调的顺序试：缺知识用 RAG，缺的是「做事方式」（稳定格式、语气、领域习惯）而 Prompt 加示例又达不到时，才考虑微调。

  • 想让模型「记住产品手册」用 RAG：微调学到的知识难更新、不能引用来源
  • 微调前提：几百条以上高质量样本、有人持续维护、收益明确（如用小模型替换大模型）
  • LoRA 冻结原权重，只训练一条低秩旁路；QLoRA 再把基座以 4 bit 加载，单张消费级显卡也能训
  • 上线时模型 ID 走配置，灰度切流量并保留原模型降级

→ 详见 模型微调

五、Agent

Q24：工作流和 Agent 有什么区别？ReAct 是什么？

一句话：工作流是代码预先写好执行路径，LLM 只负责其中的步骤；Agent 是 LLM 自己决定下一步做什么、调哪个工具。能用工作流就不用 Agent，它更便宜、可控、好测试。

  • ReAct：推理（Thought）→ 行动（调用工具）→ 观察结果 → 再推理，循环到给出答案
  • 现在的循环由原生 Function Calling 驱动，Spring AI、LangChain4j 替你跑循环，你负责定义工具和设上限
  • Agent = 模型 + 工具 + 记忆 + 规划
  • 只有步骤数事先确定不了、确实需要自主探索时才上 Agent，并从单 Agent + 少量工具开始

→ 详见 AI Agent 智能体

Q25：多 Agent 有哪些编排模式？

一句话：从简单到复杂有五种：链式、路由、并行、编排者-执行者、评估-优化；只有编排者-执行者真正需要模型自主规划，其余都能用普通代码串起来。

  • 选型顺序：先用链式、路由、并行这类确定性工作流，确实需要运行时动态拆分任务再上编排者-执行者
  • 最朴素的实现：把子 Agent 包装成编排者的工具；子 Agent 之间不共享记忆，要限制嵌套深度
  • 框架：LangChain4j 有实验性的 langchain4j-agentic，复杂有状态流程可以用 LangGraph4j
模式典型用途
链式生成 → 校对 → 翻译
路由客服分流，简单问题走小模型
并行多维度评审、投票
编排者-执行者子任务在运行时才能确定
评估-优化有明确标准的写作、代码生成

→ 详见 AI Agent 智能体

Q26：怎么防止 Agent 失控、误执行有副作用的操作？

一句话：假设模型随时可能被说服去调用任何它能调用的工具，所以靠四件套兜底：调用上限与超时、工具最小权限、副作用操作人工确认、全链路可观测。

  • 上限：LangChain4j maxToolCallingRoundTrips，Spring AI spring.ai.tools.limits.*；整个任务再设总超时和 Token 预算
  • 最小权限：按场景拆工具集，数据库工具用只读账号；用户、租户 ID 从服务端上下文取，不让模型填
  • 人工确认：退款、发邮件、删数据这类工具只生成「待确认操作」，用户在界面确认后走普通业务接口执行
  • 可观测：记录每一轮的模型输入输出、工具参数和结果

→ 详见 AI Agent 智能体、Function Calling（工具调用）

六、Java 框架

Q27：Spring AI 和 LangChain4j 怎么选？

一句话：两者能力已大面积重合；Spring Boot 项目、看重和 Spring 生态（配置、观测、安全）一致优先 Spring AI，非 Spring 项目、喜欢接口声明式写法或想用现成的 Agent 编排模块选 LangChain4j。

  • 版本：Spring AI 2.0.x 对应 Boot 4，1.1.x 对应 Boot 3.5；LangChain4j 用 langchain4j-bom 管理版本
  • 共同能力：两者都支持结构化输出、对话记忆、RAG 和 MCP 客户端
  • 两者都能接主流厂商，不必因为某个单点功能做决定
维度Spring AILangChain4j
编程模型ChatClient 链式调用 + Advisor 链AiServices 接口代理
Spring 集成原生自动配置、Micrometer 观测提供 Boot 3 / 4 Starter，可选
非 Spring 项目能用但不是主场纯 Java 即可

→ 详见 LangChain4j

Q28：Spring AI 的 Advisor 是什么？2.0 的工具调用循环由谁驱动？

一句话：Advisor 包住一次 ChatClient 调用，类似 Servlet Filter，用来插入记忆、检索、日志等横切逻辑；2.0 起工具循环不再藏在 ChatModel 里，而是由自动注册的 ToolCallingAdvisor 在 Advisor 链中驱动。

  • 顺序看 getOrder()，数值越小越靠外；记忆 Advisor 在工具循环外层，一轮对话只读写一次历史
  • 工具循环默认有调用次数上限，防止模型死循环
  • 直接调用 ChatModel 时，返回的工具调用不会被自动执行
  • 1.x 的 toolNames(...)、FunctionCallback 已删除，统一用 @Tool 或 ToolCallback

→ 详见 Spring AI、Spring AI

Q29：LangChain4j 的 AiServices 是怎么工作的？

一句话：用一个 Java 接口描述 AI 能力，框架生成动态代理；调用接口方法时，代理解析注解组装请求，依次经过护栏、记忆、检索、工具，再把模型输出转换成方法的返回类型。

  • 返回类型可以是 String、record（自动结构化输出）、Result<T>（带 Token 用量和来源）、TokenStream（流式）
  • 记忆、工具、检索器、护栏都在 AiServices.builder(...) 上组合；Spring Boot 中用 @AiService 自动注册成 Bean
  • executeToolsConcurrently() 只并发同一轮里的多个调用，有依赖的调用由模型在后续轮次发起
  • 护栏是兜底，不能替代工具权限和数据访问控制

→ 详见 LangChain4j

Q30：多用户场景下 ChatMemory 怎么隔离？

一句话：按会话 ID 取各自的记忆，而且会话 ID 必须由服务端根据登录态生成，不能信任前端传来的值，否则用户能读到别人的对话。

  • 最常见的 bug：把一个 ChatMemory 注册成单例 Bean，所有用户共用一份历史
  • Spring AI：MessageChatMemoryAdvisor + 每次请求传 ChatMemory.CONVERSATION_ID
  • LangChain4j：chatMemoryProvider(id -> ...) + 方法参数上的 @MemoryId
  • 多实例部署改用 JDBC、Redis 等持久化存储，并设置窗口大小

→ 详见 LangChain4j、Spring AI

七、工程化与安全

Q31：本地部署开源模型要多少显存？Ollama 用在生产要注意什么？

一句话：显存 ≈ 总参数 × 每参数字节数 + KV Cache + 10%–20% 运行时开销；Ollama 适合开发、离线和小规模内网，高并发生产推理交给 vLLM 等专门服务，应用侧都走 OpenAI 兼容接口。

  • 4-bit 量化约 0.5～0.6 字节 / 参数，8B 模型权重约 5 GB；KV Cache 随上下文长度和并发数线性增长
  • MoE 模型按总参数算显存：只激活部分专家省的是计算，所有专家权重都要加载
  • 默认上下文较短，RAG 内容超长会被静默截断，要调大 num_ctx 或 OLLAMA_CONTEXT_LENGTH
  • API 没有鉴权，绑定 0.0.0.0 就对整个网络开放；对外必须经过带认证、TLS、限流的网关

→ 详见 大模型选型、Ollama

Q32：调用大模型 API 时，哪些错误该重试？怎么限流？

一句话：400、401、403、404 这类请求本身有问题的不重试；429、5xx、Anthropic 的 529 过载做指数退避重试并遵循 retry-after。官方 Java SDK 已内置重试，只需配次数和超时。

  • 额度类 429（月度上限）重试无效，要告警或降级
  • 上层策略：重试仍失败就切备用模型、给整次用户请求设总超时，不要和 SDK 内置重试叠太多层
  • 本地限流：按模型做令牌桶或信号量，把 RPM / TPM 控制在配额内，而不是等 429 再退避
  • 按异常类型处理，不要匹配错误消息字符串；离线批量走 Batch 接口

→ 详见 API 直接接入

Q33：什么是直接 / 间接提示注入？怎么分层防护？

一句话：直接注入是用户在对话框里输入「忽略之前的指令」；间接注入藏在模型读取的外部内容里（检索文档、网页、工具或 MCP 返回值），用户本人可能毫不知情，挂了有副作用的工具时更危险。

  • 靠 Prompt 防不住：模型无法可靠区分指令和数据，核心思路是限制「被说服之后能造成的损害」
  • 隔离不可信内容：放进明确标签，声明其中只是数据（降低成功率，不是安全边界）
  • 工具最小权限 + 副作用人工确认，工具以当前用户的身份执行
  • 按权限检索：RAG 检索阶段就按用户权限过滤，模型看不到无权看的文档；过滤条件用 builder 构造，不拼字符串
  • 输出校验：前端不自动渲染模型生成的外链和 Markdown 图片，防止把数据拼进 URL 带出去

→ 详见 Prompt 工程、RAG 检索增强生成

八、Agent 协议与上下文工程

Q34：A2A 协议是什么？和 MCP 有什么区别？

一句话：A2A（Agent2Agent）是让不同团队、不同框架做的 Agent 互相发现、委派任务的开放协议；MCP 管 Agent 连工具，A2A 管 Agent 连 Agent，两者互补，一个 Agent 常常两个都用。

维度MCPA2A
连接对象工具、数据源其他 Agent
对方行为确定的函数自主决策的黑盒
交互一次调用，很快返回有状态的任务，可长时间运行、中途要补充输入
  • Agent Card：Agent 的「名片」，写明技能、地址、认证方式，默认放在 /.well-known/agent-card.json
  • 任务有完整的状态流转，长任务用 SSE 推进度或 Webhook 回调
  • 由 Google 发起、已捐给 Linux 基金会，规范 1.0，官方有 Java SDK
  • 选择标准：对方只执行确定操作就做成 MCP 工具，需要自己规划、多轮交互才做成 A2A Agent

→ 详见 AI Agent 智能体

Q35：Agent Skills 是什么？和工具、MCP 有什么区别？

一句话：Skill 是一个带 SKILL.md 的目录，把某类任务的操作说明、脚本、参考资料打包在一起，Agent 用到时才加载；工具和 MCP 决定 Agent「能做什么」，Skill 告诉它「该怎么做」。

  • 渐进式加载：启动时只读每个 Skill 的名称和描述（约 100 Token），任务相关才读正文，脚本和参考文件用到时再读
  • 每个 Skill 只常驻约 100 Token 的元数据，装几十个也只多占几千 Token；description 要写清「做什么 + 什么时候用」，Agent 靠它判断是否激活
  • 和系统提示的区别：系统提示每轮都在，Skill 按需出现；和 RAG 的区别：RAG 按相似度捞片段，Skill 是整理好的完整流程
  • 2025 年由 Anthropic 推出并开放为规范，多家 Agent 工具已支持

常见坑：第三方 Skill 里的脚本会被 Agent 执行，要像第三方依赖一样审查来源。

→ 详见 AI Agent 智能体

Q36：什么是上下文工程？Agent 跑长任务时上下文怎么管？

一句话：提示词工程关心指令怎么写，上下文工程关心每一轮窗口里放哪些内容。上下文越长，模型越容易漏看信息，所以目标是用最少、最有用的 Token 让模型做对事。

  • 系统提示从最小版本开始，按实际失败补充；工具职责单一、返回精简，不把整段 JSON 原样丢给模型
  • 按需加载：先只放文件路径、查询条件这类引用，模型需要时再用工具读取
  • 压缩：窗口快满时把历史总结成摘要再继续；对话记忆一律设窗口大小
  • 结构化笔记：把进度、待办写到窗口外，需要时读回
  • 子 Agent：探索性工作交给子 Agent 在干净的上下文里做，只返回精简结论

常见坑：工具注册几十个、职责重叠，模型选错工具，Token 也白白浪费。
