音视频面试题解答

2026/10/10大约 12 分钟

音视频面试题解答

题目清单见 音视频高频面试题；细节见 音视频总览。

版本基线：FFmpeg 9.0、SRS 6.0（v6.0-r2）、ZLMediaKit 主干、MediaMTX 1.21、LiveKit 1.13；WHIP 为 RFC 9725、WHEP 仍是草案；GB/T 28181-2022；JDK 21 / Spring Boot 4。

一、音视频基础

Q1：转码和转封装有什么区别？为什么说「能转封装就不转码」？

一句话：转封装只是把压缩好的数据换个「盒子」装（比如 FLV 换成 MP4），几乎不耗 CPU；转码要先解码成原始画面再重新压缩，又贵又伤画质，所以能不转就不转。

对比项转封装（Remux）转码（Transcode）
CPU极低，一台机器能跑成百上千路很高，一路 1080p 转多档能占满几个核
画质无损每编一次损失一次
能改什么只改容器和协议编码、分辨率、码率、水印都能改
  • 典型转封装：RTMP 转 HLS / HTTP-FLV、FLV 录像转 MP4（ffmpeg -c copy）
  • 必须转码的场景：终端不支持源编码、要出多档清晰度、要加水印或裁剪
  • 转码只从原始「母版」做一次，不要 1080p 转 720p 再转 480p

→ 详见 音视频基础

Q2：I / P / B 帧和 GOP 是什么？直播的 GOP 该怎么设？

一句话：I 帧能独立解码，P 帧、B 帧只记录和别的帧的差异；两个关键帧之间的一组帧叫 GOP，它的长短直接决定首屏快慢、切片长短和延迟。

  • I 帧最大，是播放器「进入」码流的起点；B 帧压缩率最高，但要等后面的帧到了才能解码
  • GOP 越长越省码率，但首屏要等更久、HLS 切片只能切得更长、丢包后花屏更久
  • 直播通常 GOP 1～2 秒、固定间隔（-sc_threshold 0 关掉场景切换插关键帧）、关闭 B 帧
  • 秒开靠 GOP 缓存：服务器缓存最近一个完整 GOP，新观众先收这段，代价是落后直播最多一个 GOP

常见坑：多码率档位关键帧不对齐，播放器切清晰度时跳帧或花屏。

→ 详见 音视频基础、秒开与 GOP 缓存

Q3：H.264、H.265、AV1 怎么选？为什么 WebRTC 的流转推 CDN 还要转音频？

一句话：H.264 + AAC 是兼容性兜底；H.265 省码率但授权复杂、浏览器支持不一，适合自家 App 和监控；AV1 编码慢但免版税，适合「编一次播很多次」的点播。

  • H.265 / AV1 同画质码率约降 30%～50%，但网页播放前要做能力探测，不支持就回退 H.264
  • 所有档位至少保留一份 H.264，保证老设备和全部浏览器能播
  • WebRTC 默认音频是 Opus，RTMP / FLV 和传统 HLS 只认 AAC，转推时服务器要把 Opus 转成 AAC
  • 音频转码比视频便宜得多，但要在流媒体服务器上显式打开

→ 详见 音视频基础、音频编码

二、流媒体协议

Q4：RTMP、HTTP-FLV、HLS、WebRTC、SRT 各自延迟多少？怎么选？

一句话：推流看稳定和编码器支持（RTMP、SRT、WHIP），拉流看能否大规模分发（HTTP-FLV、HLS、WebRTC）；先定业务能接受的延迟，再选协议。

协议典型延迟主要用途
RTMP1～3 秒OBS / 编码器推流的事实标准
HTTP-FLV1～3 秒国内网页 / App 直播拉流主力
HLS常规 6～30 秒全平台兼容、CDN 最友好、点播
LL-HLS2～5 秒想要 iOS 原生播放又要降延迟
WebRTC0.1～0.5 秒连麦、会议、强互动
SRT0.3～1 秒弱网、远距离推流
  • 常见组合：RTMP / SRT 推流 → 流媒体服务器转封装 → HTTP-FLV / HLS 经 CDN 分发，连麦再引入 WebRTC
  • 延迟越低成本越高：WebRTC 分发要大量 SFU 节点，单位观众成本远高于 HTTP 分发

→ 详见 流媒体协议、延迟对比

Q5：HLS 为什么延迟高？LL-HLS 是怎么降下来的？

一句话：HLS 要把流切成几秒一片的文件，播放器还会先攒约 3 片再播，光这一项就十几秒；LL-HLS 把切片再拆小、提前告诉播放器下一块地址，把延迟压到 2～5 秒。

  • 延迟来源：编码 + 切片生成 + CDN 回源 + 播放器缓冲（规范建议距末尾至少 3 个目标时长）
  • 部分切片：4 秒切片再拆成几百毫秒的小块，生成一块发布一块
  • 预加载提示：EXT-X-PRELOAD-HINT 让播放器提前发请求，服务器生成后立即返回
  • 阻塞式刷新：播放器带 _HLS_msn / _HLS_part 请求，服务器挂起到切片就绪再返回，代替固定轮询

常见坑：只缩短切片不缩短 GOP，切片必须从关键帧开始，切不短；LL-HLS 还要 CDN 支持请求合并和查询参数缓存键。

→ 详见 流媒体协议

Q6：WebRTC 为什么能做到亚秒级？WHIP / WHEP 解决了什么问题？

一句话：WebRTC 走 UDP、播放端只缓冲几十到几百毫秒、网络差时宁可降清晰度也不攒延迟；WHIP / WHEP 用一个 HTTP 请求统一了 WebRTC 的推拉流信令，让 OBS、FFmpeg 能直接用 WebRTC 推流。

  • 传输：SRTP over UDP，丢包靠 NACK 重传和 FEC 纠错，拥塞控制实时调码率
  • 穿越 NAT：ICE 收集候选地址，STUN 拿公网地址，打不通走 TURN 中继
  • 标准不定义信令：SDP 和候选怎么交换由业务自己做，这正是 Java 后端的活
  • WHIP（RFC 9725）：POST SDP offer，返回 201 + answer + Location，结束时 DELETE，鉴权用 Bearer Token
  • WHEP 是对称的拉流协议，截至 2026 年仍是 IETF 草案，但主流服务器已支持

→ 详见 流媒体协议、WebRTC 实时通信

三、流媒体服务器与 WebRTC

Q7：音视频平台里 Java 后端做什么？SRS、ZLMediaKit、MediaMTX 怎么选？

一句话：音视频数据交给流媒体服务器、FFmpeg 和 CDN（媒体面），Java 后端只管「谁能推、谁能看、房间状态、任务调度、计费」（控制面），不要用 JVM 去中转或逐帧处理视频。

  • Java 常做的事：签发推流 / 播放地址、处理 Hook 回调、编排转码截图审核任务、管理媒资元数据
  • SRS：互联网直播首选，RTMP / HTTP-FLV / HLS / WebRTC 都成熟，有边缘集群和完整回调
  • ZLMediaKit：监控接入首选，GB28181、RTSP、按需拉流最全
  • MediaMTX：Go 单二进制，适合少量摄像头转发、边缘盒子、开发测试
  • 实时多档转码一般不在流媒体服务器里做，而是调度 FFmpeg 拉流转码再推回

→ 详见 音视频总览、流媒体服务器

Q8：流媒体服务器的 HTTP 回调（Hook）要注意什么？

一句话：回调是同步阻塞的、没有签名、还可能丢，所以接口要快、只开内网、做幂等，并用管理 API 定时对账兜底。

  • 要快：推流 / 播放要等回调返回才继续，只做 Redis 级校验，慢操作丢消息队列
  • 只开内网：回调本身不带签名，放在 /internal/** 下，网关不转发，网络策略限制来源
  • 防双推：多台源站时两路推流会落到不同机器，开播用 Redis SET NX 按流名占位，抢不到就拒绝
  • 防误关：on_unpublish 先记「中断」、宽限 30～60 秒再判下播，且只释放 client_id 匹配的占位，旧连接的下播事件关不掉新连接
  • 防丢失：每分钟拉服务器流列表与数据库对比，在播状态和观众数以这里为准

常见坑：SRS 要求 HTTP 200 且 code 为 0 才放行，返回别的值会直接断开客户端。

→ 详见 流媒体服务器、源站回调鉴权、监控与管理 API

Q9：WebRTC 怎么穿越 NAT？STUN 和 TURN 有什么区别？

一句话：ICE 把所有可能的地址（本机、STUN 看到的公网地址、TURN 中继地址）都列出来逐对试，能直连就打洞直连，打不通就走 TURN 中继。

  • STUN：无状态、流量极小，只回答「你在公网上看起来是哪个地址」
  • TURN：有状态的中继，媒体全部经它转发，总能通但消耗服务器带宽
  • 对称型 NAT 对每个目的地址分配不同端口，打洞会失败，只能走 TURN
  • TURN 凭证不能写死在前端：后端用共享密钥现算限时凭证（过期时间:用户ID + HMAC-SHA1），coturn 无需数据库即可校验

常见坑：TURN 带宽要按中继比例做容量规划；coturn 不配 denied-peer-ip 会被当成访问内网的跳板。

→ 详见 WebRTC 实时通信、限时凭证

Q10：多人音视频通话 Mesh、SFU、MCU 有什么区别？

一句话：Mesh 是两两直连，人一多客户端扛不住；SFU 每人只上行一路、服务器只转发不转码，是当前主流；MCU 把所有画面合成一路，CPU 很重，主要用于合流录制和转推直播。

拓扑客户端上行服务端负担适用规模
MeshN−1 路只有信令和 TURN2～4 人
SFU1 路转发带宽大、CPU 小几十人互动
MCU1 路解码 + 合成 + 编码合流录制、对接 SIP
  • simulcast：客户端同时编高中低三层，SFU 给弱网接收者只转低层，不用服务端转码
  • 用 LiveKit 这类成品 SFU 时，Java 后端只签发带房间和权限的 JWT，不再自建信令
  • 直播连麦：主播和嘉宾在 SFU 里互动，合流后用 RTMP 推回源站给普通观众

→ 详见 WebRTC 实时通信、直播系统设计

四、直播、点播与监控

Q11：直播的推流鉴权和播放防盗链怎么做？

一句话：推流地址带过期时间和 HMAC 签名，由流媒体服务器在 on_publish 回调里交给后端校验；播放地址按 CDN 的规则签名，由 CDN 边缘直接校验，不回源业务服务。

  • 签名：HMAC-SHA256(密钥, "/live/{streamKey}:{expire}")，以 expire + sign 两个参数带在推流地址上，路径和过期时间任一被改都失败
  • 校验用常量时间比较（MessageDigest.isEqual），防止按响应时间逐字节猜签名
  • 过期时间只管「何时可以开始推」，窗口 10～30 分钟，已在推的流不会因过期被断开
  • 防盗链由弱到强：Referer 白名单 → URL 签名 → 业务层鉴权（付费校验、限并发观看）
  • 断流宽限期：on_unpublish 后 30～60 秒内重连视为续播，不立刻判下播

常见坑：HLS 只签了 m3u8，切片是相对路径不会带签名，结果「列表能拉、切片全 403」。

→ 详见 直播系统设计、播放防盗链

Q12：用户上传视频后的转码流水线怎么设计？

一句话：客户端分片直传对象存储，上传完成后建任务、投消息队列，转码 Worker 异步消费并回写进度；核心是每一步都幂等，重复事件和重复消费都不会重复转码。

  • 上传：后端签发分片预签名 URL，文件不经过业务服务；对象键由服务端生成，不用用户文件名
  • 防重复建任务：唯一键 (video_id, profile)，重复的上传完成事件只会撞唯一键
  • 防重复执行：Worker 用条件更新抢占任务，带心跳，超时的任务可被接管
  • 产物幂等：输出路径只由视频和档位决定，master.m3u8 最后上传，播放器拿不到半成品
  • 重试分类：网络抖动可重试；文件损坏、格式不在白名单直接 FAILED，与死信队列对齐

常见坑：Java 里拼 shell 字符串调 FFmpeg 会命令注入，要用 ProcessBuilder 参数列表，并用 ffprobe 的 format_name 做白名单防 SSRF。

→ 详见 点播与短视频、FFmpeg 与转码

Q13：付费视频怎么防下载？HLS AES-128 加密和 DRM 有什么区别？

一句话：AES-128 把切片加密，密钥从业务接口取，挡得住「拿到地址就下载」，但挡不住已登录用户从浏览器里抓密钥；要防合法用户录制外传，只能上 DRM，把密钥锁在播放器的解密模块里。

  • AES-128：m3u8 里 EXT-X-KEY 写明密钥地址，播放器取回 16 字节密钥解密切片
  • 密钥接口必须校验短时效播放令牌、返回 Cache-Control: no-store、不能被 CDN 缓存
  • DRM：Widevine（Chrome / Android）、FairPlay（苹果）、PlayReady（微软），全平台要三家都接
  • CENC cbcs 模式：一份 CMAF 切片可同时给三种 DRM 用，不用存三份
  • 中小平台常用折中：AES-128 + 短时效签名 + 水印，版权方要求时才上 DRM

→ 详见 点播与短视频、DRM

Q14：门店摄像头怎么接入平台？RTSP 和 GB/T 28181 怎么选？

一句话：关键看「谁主动连谁」：RTSP / ONVIF 是平台主动连设备，要求能访问设备 IP；GB/T 28181 是设备主动向平台注册并推流，能穿越 NAT，适合设备分散、平台在云上的场景。

  • RTSP：摄像头默认都支持，同网段少量设备快速接入；账号密码不能进日志或前端
  • GB/T 28181：信令走 SIP，流程是注册 → 心跳 → 目录查询 → INVITE → 设备推 RTP / PS 流
  • 开源组合：ZLMediaKit 管媒体，WVP-PRO（Java）管信令
  • 按需拉流：有人看才点播（on_stream_not_found），没人看延迟停流（on_stream_none_reader），同一通道并发点播要去重
  • 网页播放要转成 HTTP-FLV / HLS / WebRTC；H.265 视频和 G.711 音频是兼容性的主要障碍

→ 详见 监控视频接入、按需拉流
