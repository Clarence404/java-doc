2026/10/14大约 20 分钟

延迟任务

前置阅读：分布式调度、RocketMQ、幂等设计

延迟任务就是「在未来某个时刻执行一次」，订单超时关单、到期提醒、失败退避重试都属于这一类。本篇讲各类方案的选型、自研延迟任务服务的近远分层架构，以及不丢、不重、准时的做法，基线为 RocketMQ 5、Redis 8、JDK 21。

一、需求与挑战

1、典型场景

场景延迟时长精度要求特点
订单超时关单15～30 分钟秒级到分钟级量大，绝大多数订单会先支付，任务到期时已无事可做
到期 / 预约提醒几小时到几十天分钟级时间远，中途可能改期或取消
失败退避重试秒级到小时级，逐次拉长秒级回调通知、第三方接口失败后按 1s、5s、30s、5min 递增重试
预约发布 / 定时生效几分钟到几天秒级文章定时发布、活动定点开始，常有大量任务落在同一时刻（整点、零点）

这些场景有一个共同点：任务提交时就知道执行时间，到期只需执行一次。周期性任务（每天凌晨跑报表）是另一类问题，交给 分布式调度。

2、三个指标

指标含义常见要求
精度实际执行时间与预期时间的偏差关单可接受几秒，提醒可接受一两分钟，重试越准越好
规模同时挂着多少未到期任务、每秒到期多少千万级在途任务，日常每秒几百到几千个到期，整点瞬时几十万
可靠性任务会不会丢、会不会重复执行关单、退款类不能丢；所有任务都要容忍重复

三者互相牵制：内存方案最准但规模受限、重启就丢；数据库扫表最可靠但精度取决于扫描周期；分布式方案要同时解决持久化、分片和多实例协作。

二、方案全景与选型

1、六类方案对比

方案精度规模可靠性适用
数据库定时扫表取决于扫描周期，通常分钟级大，要按时间建索引、分片扫描高，任务就是业务数据天级、分钟级任务，以及所有方案的兜底
JDK DelayQueue / ScheduledThreadPoolExecutor毫秒级单机内存，十万级低，进程重启即丢单机内的超时控制、本地重试
时间轮（如 Netty HashedWheelTimer）一个刻度（通常 100 ms～1 s）单机百万级，插入 O(1)低，纯内存连接超时、心跳检测；配合持久化做近期调度层
Redis ZSet取决于轮询间隔，秒级受内存限制，千万级需要分片中，取决于持久化与主从切换中等规模、秒级精度，已有 Redis 的团队
MQ 延迟 / 定时消息秒级大高，消息持久化多副本时长在 Broker 上限内、不需要取消的任务
调度框架（XXL-JOB 等）秒级适合少量任务定义，不适合一任务一调度高周期任务；或作为扫表任务的分片执行器

各方案的实现细节分别在对应主文档里：

  • JDK 单机方案：DelayQueue 内部是按到期时间排序的优先队列，见 集合框架；定时线程池见 Fork/Join 与定时任务
  • Redis：带确认的 ZSet 延迟队列见 Redis 典型应用场景；Redisson RDelayedQueue 已被标记废弃，限制见 Redisson
  • MQ：RocketMQ 4.x 只有 18 个固定延迟级别，5.x 支持任意时间的定时消息，见 RocketMQ；RabbitMQ 的 TTL + 死信与延迟插件见 RabbitMQ
  • 调度框架：分片广播、错过触发、只执行一次见 分布式调度

2、几个容易踩的坑

  • Kafka 没有原生延迟消息：常见变通是按延迟等级建多个 Topic，消费者发现消息未到期就 pause 分区、到期再 resume，本质上和 RabbitMQ「一个时长一个队列」一样，只适合少数几个固定档位，见 MQ 选型
  • Redis key 过期通知不能当延迟任务：过期事件不持久化，订阅方断线期间的事件直接丢失，而且 key 是在被访问或后台抽样时才过期，触发时间不准
  • MQ 定时消息不能取消：已经发出的定时消息到期一定会投递，取消只能靠消费时检查业务状态；RocketMQ 5 的最长延迟受 Broker 配置 timerMaxDelaySec 限制，超出上限的远期任务要先落库
  • 单机方案不能单独使用：DelayQueue、时间轮只能作为「持久化 + 扫描」之上的加速层，进程重启后要能从持久化存储里恢复

3、怎么选

  1. 任务少、精度要求低（天级提醒、几万条）：数据库扫表 + 调度框架分片，最简单可靠
  2. 时长在 MQ 上限内、不需要取消、量大（订单关单）：MQ 定时消息 + 定时扫表兜底，这是订单场景的推荐组合
  3. 时长从秒到几十天都有、需要取消和修改、多个业务共用：自研延迟任务服务，持久化在数据库，近期任务进时间轮，到期后通过 MQ 投递给业务方，下面三到五节就是这个方案

三、自研延迟任务服务

1、整体架构

核心思路是近远分层：远期任务只在数据库里躺着，不占内存；距离到期不足 5 分钟的任务才被预加载进内存时间轮，由时间轮负责精确触发。

组件职责
接入 API提交、取消、修改、查询；按业务类型限流；写库成功即返回任务 ID
任务库所有任务的唯一真相；按到期日分区、按逻辑分片分库
协调中心把 1024 个逻辑分片分配给各个节点，节点持有租约；可用 ZooKeeper、etcd 或 Nacos 实现
预加载器每 30 秒拉取本节点所属分片中、未来 5 分钟内到期且仍为待执行的任务，放入时间轮
内存时间轮1 秒一格，到期后把任务交给投递器
投递器再次确认任务未被取消，批量发到业务方的 MQ Topic，然后把状态改为已投递
业务消费者在业务方，先校验业务状态再执行，按幂等方式处理；失败由 MQ 退避重试，耗尽后进入死信并告警

任务执行在业务方，延迟任务服务只负责「准时、不丢地把任务交出去」。这样服务本身不需要理解业务，也不会被业务的慢执行拖住。

2、任务表

CREATE TABLE delay_task (
    id           BIGINT       NOT NULL,              -- 分布式 ID
    biz_type     VARCHAR(32)  NOT NULL,              -- 业务类型，决定投递到哪个 Topic
    biz_key      VARCHAR(64)  NOT NULL,              -- 业务主键，如订单号
    shard_id     SMALLINT     NOT NULL,              -- 逻辑分片 0～1023 = hash(biz_key) % 1024
    execute_at   DATETIME(3)  NOT NULL,              -- 预期执行时间
    status       TINYINT      NOT NULL,              -- 0 待执行 1 已投递 2 已取消
    payload      VARCHAR(1024),                      -- 只放 ID 等少量参数，执行时回查业务数据
    deliver_time DATETIME(3),
    PRIMARY KEY (id, execute_at),
    UNIQUE KEY uk_biz (biz_type, biz_key, execute_at),
    KEY idx_scan (shard_id, status, execute_at)
) PARTITION BY RANGE COLUMNS (execute_at) (
    PARTITION p20261014 VALUES LESS THAN ('2026-10-15'),
    PARTITION p20261015 VALUES LESS THAN ('2026-10-16')
    -- 由运维任务提前创建未来的分区
);
  • 按到期日分区：预加载只扫今天（跨零点时加上明天）的分区；已执行完的历史分区保留 7 天后直接 DROP PARTITION，不用逐行删除
  • MySQL 分区表要求主键和唯一键都包含分区列，所以主键是 (id, execute_at)，唯一键是 (biz_type, biz_key, execute_at)，后者让业务方重复提交同一任务时只插入一次
  • idx_scan 让预加载按「分片 + 状态 + 时间范围」走索引，每个节点只碰自己的分片
  • 逻辑分片按 biz_key 计算，同一业务对象的任务总在同一分片；1024 个逻辑分片再映射到若干物理库，扩容时搬分片而不是改哈希，做法见 一致性哈希

3、时间轮原理

时间轮是一个环形数组，每个槽代表一个时间刻度，槽里挂着在这个刻度到期的任务链表；指针每隔一个刻度前进一格，把当前槽里的任务全部取出执行。插入只需计算槽位再挂到链表上，是 O(1)；DelayQueue 基于堆，插入和取出都是 O(log n)，任务多时时间轮更省。

延迟超出一圈时有两种处理：

  • 单层带圈数：Netty HashedWheelTimer 的做法，任务记录剩余圈数，指针每经过一次就减 1，减到 0 才执行；默认刻度 100 ms、512 个槽，由单个工作线程推进，适合连接超时这类大量短任务
  • 多级时间轮：像钟表的时、分、秒，远期任务先放在粗粒度的轮里，所在槽到期后按剩余时间重新放入下一级，逐级下沉到秒轮再执行；Kafka 内部管理大量延迟操作用的就是分层时间轮，RocketMQ 5 的定时消息也基于时间轮加日志文件实现

本方案的时间轮只装未来 5 分钟的任务，一层 300 个槽、1 秒一格就够了，不需要多级；更远的任务由数据库这一「最外层」承担，预加载相当于多级时间轮中的「降级」动作。

4、提交、预加载与投递

提交：写库成功即返回。若任务在 5 分钟内到期，且归属本节点，事务提交后顺手放入时间轮；不归属本节点或放入失败都没关系，下一轮预加载会把它捞上来。

预加载：

// Preloader（@Component，注入 DelayTaskMapper mapper、TimeWheel wheel、ShardOwnership ownership）
private static final Duration WINDOW = Duration.ofMinutes(5);

@Scheduled(fixedDelay = 30_000)
public void preload() {
    Instant until = Instant.now().plus(WINDOW);
    for (int shard : ownership.ownedShards()) {             // 只处理租约在手的分片
        long lastId = 0;
        while (true) {
            // WHERE shard_id = ? AND status = 0 AND execute_at < ? AND id > ? ORDER BY id LIMIT 500
            List<DelayTask> batch = mapper.selectDue(shard, until, lastId, 500);
            if (batch.isEmpty()) break;
            batch.forEach(wheel::addIfAbsent);              // 按任务 ID 去重，已在轮里的不重复放
            lastId = batch.getLast().id();
        }
    }
}
  • 查询没有时间下限：已经过期仍是待执行的任务也会被捞出来，节点崩溃、投递失败遗留的任务就在这里自动补上，不需要单独的补偿扫描
  • 过期任务放入时间轮时直接放在当前槽，下一个刻度就投递
  • 预加载周期（30 秒）远小于窗口（5 分钟），任务至少有几次机会在到期前进入内存，单次查询失败不会导致延迟

投递：时间轮每个刻度把到期任务交给投递器，投递器按批处理：

  1. SELECT id FROM delay_task WHERE id IN (...) AND status = 0，过滤掉期间被取消或已被其他节点投递的任务
  2. 按 biz_type 批量发到对应 Topic，消息 key 为 biz_key，消息体带任务 ID
  3. 发送成功后 UPDATE delay_task SET status = 1, deliver_time = NOW(3) WHERE id IN (...) AND status = 0

先发后改：第 2 步成功、第 3 步之前进程崩溃，任务仍是待执行，接手的节点会再发一次，业务方会收到重复消息。反过来先改后发，崩溃时任务已标记投递却没发出去，就丢了。延迟任务服务宁可重复，不能丢失，重复由业务消费者的幂等兜住。

四、关键问题

1、不丢：持久化与确认

环节丢失风险措施
提交写库前服务崩溃写库成功才返回任务 ID，业务方没拿到 ID 就重试，唯一键防重复插入
业务方与提交业务事务提交了，提交任务的调用失败业务方用 Outbox：业务数据与「待提交任务」同事务写入，由中继提交，见 消息队列基础
内存时间轮节点崩溃，轮里的任务全没了内存只是副本，数据库状态仍是待执行，新节点预加载时重新捞出
投递发 MQ 失败或崩溃先发后改，状态没改就会被再次投递
执行业务消费失败MQ 至少一次投递与退避重试，耗尽后进入死信并告警，人工或自动重放

还要有监控兜底：定期统计「execute_at 早于 1 分钟前仍为待执行」的任务数，大于 0 就说明预加载或投递出了问题，要告警。

2、不重：幂等与执行前状态校验

至少一次投递意味着重复不可避免：先发后改的崩溃窗口、分片迁移时新旧节点短暂重叠、MQ 自身重投都会产生重复。业务方的处理原则是到期只是「检查一下」的信号，真正要不要执行由业务状态决定：

// 订单服务的关单消费者：用状态条件更新，影响 0 行说明已支付或已关闭，直接返回
int rows = orderMapper.updateStatus(orderNo, PENDING_PAY, CLOSED);   // WHERE order_no = ? AND status = ?
if (rows == 0) return;
  • 状态类任务（关单、发布、生效）用状态机条件更新，天然幂等，做法见 幂等设计
  • 发送类任务（提醒、通知）没有状态可判断，用 (biz_type, biz_key, 周期) 的唯一发送记录去重
  • 执行前回查最新业务数据，不要信任 payload 里的快照：任务提交后，业务对象可能已经变化

3、准时：分片扫描与预加载

延迟任务的实际触发时间 ≈ 预期时间 + 时间轮刻度 + 投递批处理耗时 + MQ 投递耗时，正常情况下 1～2 秒。影响准时的主要是两件事：

  • 扫描跟不上：每个节点只扫自己的分片，单次扫描量 = 5 分钟窗口内到期的任务数 ÷ 节点数；扫描耗时超过预加载周期时，加节点让分片重新分配即可
  • 到期前没进内存：预加载窗口必须大于「扫描周期 + 一次扫描的最大耗时」，并留出几倍余量；5 分钟窗口、30 秒周期就是按这个原则取的

对精度只要求分钟级的业务（提醒），可以单独一个业务类型、把投递批量做大，不和秒级任务抢投递资源。

4、任务取消与修改

  • 取消：UPDATE delay_task SET status = 2 WHERE biz_type = ? AND biz_key = ? AND status = 0。按 biz_key 取消时不带 execute_at，查询会走每个分区的 uk_biz 前缀，取消的频率远低于提交，可以接受；时间轮里的副本不用删除，投递前的第 1 步会把它过滤掉
  • 修改时间：等价于「取消旧任务 + 提交新任务」，在同一个事务里完成；时间轮里的旧副本同样在投递前被过滤
  • 取消与投递并发：取消提交时投递器可能已经发出了消息，这时取消「慢了一步」，靠业务消费者的状态校验兜底。例如订单已支付后的关单消息，条件更新影响 0 行，什么都不会发生
  • 用 MQ 定时消息的方案没法真正取消，只能在消费时判断，这也是多业务共用时倾向自研服务的原因之一

5、大量任务同一时刻到期

零点券过期、整点活动开始、大促前一批订单同时超时，都会让几十万任务落在同一秒。问题不在时间轮（一个槽挂 100 万个任务只是一条长链表），而在下游：投递器、MQ 和业务消费者要在瞬间处理这一大批。

手段做法
按业务类型限流投递投递器对每个 biz_type 用令牌桶控制速率，超出部分顺延到下一个刻度，见 限流与过载保护
提交时打散业务能接受几分钟误差时，提交时在 execute_at 上加随机抖动（如 0～120 秒），从源头削平尖峰
提前预加载预加载器发现某一分钟的任务数超过阈值，提前把这一分钟的任务装进内存，避免到期前才扫几十万行
批量发送同一 Topic 的任务合并成批量消息发送，减少网络往返
消费端削峰业务消费者按自身能力设置并发，消息在 MQ 里排队，积压处理见 消息队列基础

对「必须在 7:00 准时生效」的大批量变更，更好的做法是不依赖到点执行：提前写好带生效时间的新数据，读取时按时间选择版本，到点只是自然切换。

6、时钟与多实例抢占

多个节点同时扫同一批任务会重复投递，常见两种协调方式：

方式做法问题
全局分布式锁扫描前抢一把锁，抢到的节点扫全部任务只有一个节点干活，扩不出去；锁过期后旧节点仍在投递的问题见 分布式锁
分片归属协调中心把逻辑分片分给各节点，节点只处理自己的分片迁移分片时有短暂重叠，需要业务幂等

本方案用分片归属：节点在协调中心注册临时节点或持有租约，节点数变化时重新分配分片。迁移时，新节点在旧租约过期并额外等待一个安全间隔后才开始扫描，把重叠窗口压到最小；剩下的偶发重复交给投递前的状态过滤和业务幂等。调度框架的「分片广播」也能实现分片归属，只是由调度中心每次触发时下发分片参数，见 分布式调度。

时钟方面：

  • 时间轮的推进用 System.nanoTime() 这种单调时钟，系统时间被 NTP 回拨或跳变不会让时间轮停走或跳格
  • 判断「是否到期」用的是节点的系统时间，各节点要开启 NTP 并监控时钟偏差；由于每个分片只归一个节点，某个节点慢 2 秒只会让它负责的任务晚 2 秒，不会造成重复
  • 不同节点生成的 execute_at 也依赖各自的时钟，业务方按「订单创建时间 + 15 分钟」计算时，以业务数据里的时间为准，不要在延迟任务服务里重新取当前时间

五、以订单超时关单为例

订单场景推荐「RocketMQ 5 定时消息 + 定时扫表兜底」，前提是延迟固定、无需取消、只有一个业务在用；详细流程、关单与释放库存的原子化见 订单。

当公司里关单、提醒、重试、定时发布等多个业务都需要延迟任务时，可以接入通用服务，订单服务的改动很小：

  1. 下单：订单事务里同时写一条 Outbox 记录，提交后由中继调用 submit(bizType = ORDER_CLOSE, bizKey = 订单号, executeAt = 创建时间 + 15 分钟)
  2. 支付成功：调用 cancel(ORDER_CLOSE, 订单号)；取消失败也不要紧，到期的关单消息会因为订单已支付而被条件更新拦下
  3. 到期：延迟任务服务向 ORDER_CLOSE 对应的 Topic 投递消息，订单服务的消费者执行「待支付 → 已关闭」的条件更新，影响 1 行才写释放库存事件
  4. 兜底：订单服务保留「超过 16 分钟仍待支付」的低频扫表，防止延迟任务服务整体故障时订单永远不关

接入通用服务的收益是取消能力和统一的监控、重试、死信处理；代价是多了一个依赖，所以订单自己的兜底扫描不能去掉。

六、容量估算

假设：全公司每天新增 5,000 万个延迟任务（关单 2,000 万、提醒与通知 2,000 万、重试与定时发布 1,000 万），最远延迟 30 天，已执行任务保留 7 天。1 GB 按 1024³ B 计，单行大小以实际 SHOW TABLE STATUS 为准，下面是估算方法。

项目计算结果
提交 QPS5,000 万 ÷ 86,400 ≈ 579 次/秒，峰值按 5 倍约 2,900 次/秒
日常到期速率稳态下到期速率 ≈ 提交速率平均约 579 个/秒，峰值约 2,900 个/秒
单行大小数据约 250 B，加上两个二级索引约 400 B约 400 B
每日新增存储5,000 万 × 400 B = 2 × 10¹⁰ B约 18.6 GB/天
表内总量上界未来 30 天 + 历史 7 天，按 37 天计：37 × 18.6 GB约 690 GB，8 个物理库每库约 86 GB
内存时间轮峰值 2,900 个/秒 × 300 秒窗口 ≈ 87 万个任务，每个约 200 B（ID、分片、业务键、链表节点）约 1.74 × 10⁸ B ≈ 166 MB，分散到 4 个节点每个约 42 MB
预加载扫描每 30 秒拉取新进入窗口的任务：峰值 2,900 × 30每轮约 8.7 万行，按 500 行一批约 174 次查询，分到 4 个节点每个约 44 次

到期洪峰：零点有 100 万张券同时到期。投递器批量发送，每批 100 条，单节点每秒发 200 批即 2 万条，4 个节点约 8 万条/秒，全部投递完约 12.5 秒；如果业务消费者每秒只能处理 1 万条，100 万条在 MQ 里排队约 100 秒才消化完。业务能接受这个延迟就不用处理，不能接受就在提交时打散，或者像价格生效那样改成按生效时间读取。

各项单机能力以压测为准，估算方法见 容量评估与规划。

小结

  • 延迟任务的三个指标是精度、规模、可靠性，内存方案准但会丢，扫表可靠但不准，分布式方案要兼顾两者
  • 量小、精度低用扫表 + 调度框架；时长固定、不需要取消用 MQ 定时消息 + 扫表兜底；多业务共用、要取消和改期才自研服务
  • 自研服务采用近远分层：全部任务落库并按到期日分区，未来 5 分钟的任务预加载进 1 秒一格的时间轮；预加载查询不设时间下限，遗留任务自动补上
  • 投递先发 MQ 再改状态，宁可重复不可丢失；业务消费者执行前校验业务状态，状态类任务用条件更新，发送类任务用唯一发送记录
  • 取消只改数据库状态，内存副本在投递前过滤；与投递并发时由业务状态校验兜底
  • 同一时刻大量到期时，按业务类型限流投递、提交时打散、提前预加载，或改成按生效时间读取
  • 多实例用分片归属代替全局锁，时间轮用单调时钟推进，节点开启 NTP 并监控时钟偏差
