库存与票务

前置阅读：订单、秒杀、热点问题

库存中心要随时回答三个问题：还能卖多少、被谁占着、卖给了谁；票务在此基础上把「数量」细化成「具体某个座位」。本篇讲库存模型、扣减时机、预占释放与防超卖，以及座位图、选座锁座与退票回流，基线为 MySQL 8.4、Redis 8。

一、需求与挑战

1、功能范围

功能要求
库存查询商品页、购物车、结算页展示有货 / 无货或剩余数量
扣减下单预占、支付确认、关单释放、退款回流，全部幂等
多仓多渠道同一 SKU 分布在多个仓库，部分库存划给直播间、门店等渠道专用
运营操作入库、盘点调整、冻结与解冻，每一笔变化都可追溯
票务场次座位图、在线选座、系统自动连座、不选座的按票档售卖、退票回流

本篇只讲库存中心通用设计和票务座位模型。单个爆款 SKU 的瞬时抢购（Redis Lua 预扣、MQ 异步落库）见 秒杀；下单幂等、预占与超时关单的基本流程见 订单，下文只在需要时一句话带过。

2、挑战

挑战说明
不超卖并发下单、重复消息、重试都不能让卖出量超过实物
不少卖预占后用户不付款、服务宕机留下悬挂预占，库存被白白占着
账实一致库存数、预占记录、订单、流水四者长期对得上，出现差异能定位到哪一笔
热点爆款 SKU、热门场次的同一行或同一区域被集中更新
座位粒度票务锁的是具体座位，多人同时抢同一个座位、一次锁多个连座都要全成或全败

二、整体架构

组件职责
库存服务维护 SKU × 仓库的库存四桶，提供预占、确认、释放、回流、冻结接口，全部以业务单号幂等
票务服务场次、区域、座位与票档；选座锁座、出票、退票
MySQL库存与座位的权威数据，所有扣减最终都落在条件更新上
Redis热门商品的预扣层、座位位图与锁座脚本；只做加速，丢失后可从 MySQL 重建
MQ订单事件（支付成功、关单、退款）驱动库存变化；库存变化事件同步到搜索与缓存
定时任务扫描过期预占与锁座、三层对账、生成修复流水

订单服务下单时同步调用库存服务预占（必须当场知道有没有货），之后的确认、释放、回流都由订单事件驱动，库存服务消费时用条件更新保证只生效一次。

三、库存模型

1、四个数量桶

桶含义何时变化
可售 available现在还能被下单的数量入库、释放、解冻、回流时增加；预占、冻结时减少
预占 reserved已下单未支付，暂时扣住下单时增加；支付确认或关单释放时减少
锁定 locked非订单原因冻结：质检、盘点差异、活动专供运营冻结 / 解冻，不会自动释放
已售 sold已支付、尚未出库支付确认时增加；发货出库或未发货退款时减少

不变式是 实物库存 on_hand = 可售 + 预占 + 锁定 + 已售待出库。只存一个 stock 字段的设计说不清「少了的那 5 件是被未支付订单占着，还是被冻结了」，排查超卖少卖时无从下手。

2、表结构

-- 一个 SKU 在一个仓库一行
CREATE TABLE sku_stock (
  sku_id        BIGINT NOT NULL,
  warehouse_id  BIGINT NOT NULL,
  on_hand       INT NOT NULL DEFAULT 0,
  available     INT NOT NULL DEFAULT 0,
  reserved      INT NOT NULL DEFAULT 0,
  locked        INT NOT NULL DEFAULT 0,
  sold          INT NOT NULL DEFAULT 0,
  updated_at    DATETIME(3) NOT NULL,
  PRIMARY KEY (sku_id, warehouse_id),
  CONSTRAINT chk_non_negative CHECK (available >= 0 AND reserved >= 0 AND locked >= 0 AND sold >= 0)
);

-- 库存流水：每一次变化一行，只增不改
CREATE TABLE stock_flow (
  id            BIGINT PRIMARY KEY,
  biz_no        VARCHAR(64) NOT NULL,      -- 下单请求号 / 订单号 / 入库单号 / 盘点单号
  biz_type      VARCHAR(16) NOT NULL,      -- RESERVE / CONFIRM / RELEASE / RETURN / INBOUND / FREEZE / ADJUST
  sku_id        BIGINT NOT NULL,
  warehouse_id  BIGINT NOT NULL,
  d_available   INT NOT NULL,              -- 各桶变化量，可正可负
  d_reserved    INT NOT NULL,
  d_locked      INT NOT NULL,
  d_sold        INT NOT NULL,
  d_on_hand     INT NOT NULL,
  created_at    DATETIME(3) NOT NULL,
  UNIQUE KEY uk_biz (biz_no, biz_type, sku_id, warehouse_id),
  KEY idx_sku_time (sku_id, warehouse_id, created_at)
);
  • MySQL 8.0.16 起 CHECK 约束真正生效，任何一桶被减成负数时语句直接报错，作为条件更新之外的最后一道防线
  • 预占明细沿用 订单 中的 stock_reservation 表（biz_no + sku_id 唯一），本篇给它加上 warehouse_id、expire_at 两列

3、多仓与渠道库存

多仓：库存按 (sku_id, warehouse_id) 存，商品页展示的可售数是各仓之和（或用户收货地址可达仓之和）。下单时库存服务先选仓再预占：

  • 选仓规则按「能整单发货 → 距离最近 → 成本最低」排序；一个仓凑不齐时拆成多个仓预占，订单随之拆成多个包裹
  • 预占失败（并发下被抢光）就换下一个候选仓重试，而不是直接报无货
  • 选仓结果写进预占记录，确认、释放、出库都按这一仓操作

渠道库存：同一批货要分给主站、直播间、线下门店，有两种做法：

做法说明适用
共享池所有渠道扣同一个可售数，先到先得渠道之间没有保量要求
独占配额从可售中划出一块给某渠道，记在 channel_quota(sku_id, channel, quota, used)直播间承诺的专供量、门店自提量
配额 + 共享兜底先扣本渠道配额，配额用完再扣共享池大促常用：保底量和灵活性兼顾

划配额本身就是一次「可售 → 锁定」的冻结（带渠道标记），活动结束未用完的配额解冻回共享池，这样四桶不变式仍然成立。

4、库存流水

流水是库存中心的「账本」，sku_stock 只是它的余额快照：

  • 同一事务写入：每次更新 sku_stock 都在同一个本地事务里插一条流水；流水的 uk_biz 唯一约束同时承担幂等，重复请求撞唯一键直接返回上次结果
  • 只增不改：盘点发现差异时写一条 ADJUST 流水去修正，而不是直接 UPDATE 余额，事后能查到是谁、为什么改的
  • 可回放：某个 SKU 的流水按时间累加，必须等于当前快照，这正是下文对账的第一层

四、扣减时机：下单扣、支付扣还是预占

方式做法优点问题适用
下单扣下单时直接 available - n、sold + n简单，下单成功就一定有货恶意下单不付款就能占光库存；取消要回补低价值、几乎不取消的场景
支付扣下单不动库存，支付成功时才扣不会被未支付订单占库存多人同时付款，后付的人钱付了却没货，只能退款库存充足、虚拟商品
预占 + 确认下单 available → reserved，支付后 reserved → sold，超时 reserved → available付了钱一定有货，未付款的占用有时限多一张预占表、要处理悬挂预占实物电商、票务的默认选择

选择要点：

  • 绝大多数场景选预占 + 确认：「付了钱却没货」对用户伤害最大，而预占带 TTL，恶意占库存的代价被限制在一个支付超时窗口内
  • 恶意占库存再用限购、风控、缩短大促支付超时（如 15 分钟缩到 5 分钟）进一步压缩
  • 这正是 订单 里 TCC 思路的落地：下单 Try 预占、支付后 Confirm、关单 Cancel

五、预占与释放

1、与订单状态机配合

订单事件库存动作预占记录四桶变化
下单预占插入 RESERVED可售 −n，预占 +n
ORDER_PAID确认RESERVED → CONFIRMED预占 −n，已售 +n
ORDER_CANCELLED释放RESERVED → RELEASED预占 −n，可售 +n
发货出库CONFIRMED → SHIPPED已售 −n，实物 −n
未发货退款回流CONFIRMED → RETURNED已售 −n，可售 +n
已发货退货入库退货单单独记质检合格进可售，残次进锁定

每一行都是同一个模式：先条件更新预占记录的状态（带原状态），影响 1 行才改 sku_stock 并写流水，三者同一事务。重复消息、乱序消息改预占记录时影响 0 行，直接结束：

-- 确认：只有仍是 RESERVED 的才能确认
UPDATE stock_reservation SET status = 'CONFIRMED'
WHERE biz_no = ? AND sku_id = ? AND warehouse_id = ? AND status = 'RESERVED';

UPDATE sku_stock SET reserved = reserved - #{n}, sold = sold + #{n}, updated_at = NOW(3)
WHERE sku_id = ? AND warehouse_id = ?;

2、TTL 与超时释放

  • 预占记录写入 expire_at = 下单时间 + 支付超时 + 余量（支付超时 15 分钟时取 20 分钟），余量用来覆盖关单流程本身的耗时
  • 主路径是订单关单事件：订单服务先关渠道交易、再关单、再发 ORDER_CANCELLED，库存释放跟在后面，保证「已付款的订单不会被释放库存」
  • 兜底扫描：每分钟扫 status = 'RESERVED' AND expire_at < NOW() 的记录，不能直接释放，要按 biz_no 向订单服务确认：没有订单（建单前宕机的悬挂预占）或订单已取消才释放；订单已支付则补做确认
  • 释放和确认同时到达时，预占记录的条件更新保证只有一个成功；万一订单在释放之后才到账，由订单侧按「关单后到账」自动退款处理

3、对账修复

层次核对公式发现什么
流水 vs 快照某 SKU 流水各桶累加 = sku_stock 当前值绕过流水直接改库、事务不完整
预占明细 vs 快照RESERVED 记录数量之和 = reserved；CONFIRMED 之和 = sold预占记录与余额不一致
库存 vs 订单CONFIRMED 的 biz_no 集合 = 已支付未发货订单集合支付事件丢失、悬挂预占
Redis vs MySQL热门 SKU 的 Redis 余量 + 处理中 = MySQL 可售预扣层少卖，做法同 秒杀
  • 增量对账每 10 分钟按「最近有变化的 SKU」跑一次，日终全量跑；大表的全量核对放到数仓里做，思路见 海量数据对账
  • 修复也走流水：发现差异后生成 ADJUST 流水并更新快照，同一事务；金额大或原因不明的差异转人工，不自动修

六、防超卖

1、条件更新：首选

UPDATE sku_stock
SET available = available - #{n}, reserved = reserved + #{n}, updated_at = NOW(3)
WHERE sku_id = ? AND warehouse_id = ? AND available >= #{n};

影响 1 行即预占成功，0 行即库存不足。判断与扣减在同一条语句里由行锁保证原子，不会出现「查到有 1 件、两个人都扣」。

2、几种做法对比

做法原理评价
条件更新 available >= n一条 SQL 内判断并扣减首选；库存充足的并发请求都能成功
乐观锁 version先读、在应用里计算、WHERE version = ? 写回只在扣减规则复杂、无法写成一条 SQL 时用；并发时库存充足也会失败重试
悲观锁 SELECT ... FOR UPDATE先锁行再判断能用，但锁持有时间更长，吞吐不如条件更新
Redis 预扣 + DB 落地Lua 原子扣减，MQ 异步落库，DB 条件更新兜底单 SKU 瞬时高并发时用，完整方案见 秒杀
先查后扣 / 分布式锁查询有货再扣，或加锁串行先查后扣有并发漏洞；分布式锁不是防超卖的主手段，DB 条件更新仍要保留

3、多 SKU 下单的死锁

一个订单同时扣 A、B 两个 SKU，另一个订单按 B、A 的顺序扣，两个事务互相等对方的行锁就会死锁。在事务内按 (sku_id, warehouse_id) 排序后再逐个更新，所有事务加锁顺序一致，死锁自然消失；任何一个 SKU 影响 0 行就整体回滚，返回具体是哪个商品没货。

七、热点 SKU：拆分库存

爆款 SKU 的所有预占都落在 sku_stock 的同一行，InnoDB 对同一行的更新只能串行，单行通常只有几百 TPS。

  • 拆行（分桶）：把一行拆成 N 行 (sku_id, warehouse_id, bucket_no)，入库时平均分配，预占时随机选一个桶，桶不够再试下一个；可售总数是各桶之和，具体做法见 热点问题
  • 桶之间再平衡：后台任务把余量大的桶挪一部分给已空的桶，挪动本身是两条条件更新 + 两条流水；剩余很少时合并回一个桶，避免「总数还有、每个桶都不够」
  • 流量更集中：大促 0 点单 SKU 每秒上万次，拆行也扛不住时，前面加 Redis 预扣层，即 秒杀 的方案；库存中心只承接预扣成功的请求
  • 预占记录不是热点：它按 biz_no 插入新行，天然分散

八、票务：座位图模型

1、场馆、场次、区域、座位

层级表说明
场馆布局venue_seat(venue_id, area_code, row_no, col_no, x, y, tags)场馆固定的物理座位，含坐标与标签（过道旁、残障席）
场次show(id, venue_id, start_at, status)一场演出或一个车次、一个航班
区域 / 票档show_area(show_id, area_code, price_cent, sale_mode)同一区域同一价格；sale_mode 区分选座和票池
场次座位show_seat(show_id, seat_id, area_code, status, lock_no, order_id, version)开售前从布局复制一份，状态 AVAILABLE / LOCKED / SOLD / BLOCKED
  • 场馆布局与场次座位分开存：同一个场馆每场演出的舞台、封闭区不同，开售前按场次复制并把不售的座位标为 BLOCKED（主办预留、视线遮挡）
  • show_seat 按 show_id 分片：同一场次的选座、锁座只落在一个分片上，一场 5 万座的演出就是 5 万行，单表完全能承受
  • 座位图的几何信息（坐标、区域轮廓）是静态的，生成 JSON 放 CDN；客户端只拉动态的座位状态

2、两种售卖方式

方式用户看到库存粒度典型场景
选座座位图，点选具体座位单个座位剧院、电影院、体育馆看台
票池（不选座）只选票档和张数票档数量热门演唱会开票、草坪 / 站票区、火车票按席别

热门演唱会常在开票阶段只开票池，让抢票退化成「扣数量」，开票后再统一分配座位，原因见第十节。

九、选座与锁座

1、座位状态位图

座位图请求远多于锁座请求，不能每次都查 5 万行。Redis 里每个「场次-区域」维护一个位图 seat:{showId:area}:taken，一位对应一个座位，1 表示已锁或已售：

  • 一个 5,000 座的区域只占 5,000 ÷ 8 = 625 B，GET 一次取回，客户端按位渲染
  • 票务服务实例本地缓存位图约 1 秒，热门场次几十万人刷座位图也只打到本地
  • 位图只用于展示，有 1 秒延迟没关系，真正的锁座判断在下一步

2、锁座：全成或全败

用户一次选 2–4 个座位，必须全部锁上或全部不锁，否则会出现「只抢到两个人中的一个座位」。

-- KEYS[1] = seat:{showId:area}:taken   KEYS[2] = seat:{showId:area}:owner（座位号 -> lockNo）
-- ARGV[1] = lockNo  ARGV[2..n] = 座位在区域内的序号
-- 返回：0 成功；>0 第一个已被占的座位序号（+1，避免与 0 混淆）
for i = 2, #ARGV do
  if redis.call('GETBIT', KEYS[1], ARGV[i]) == 1 then
    return tonumber(ARGV[i]) + 1
  end
end
for i = 2, #ARGV do
  redis.call('SETBIT', KEYS[1], ARGV[i], 1)
  redis.call('HSET', KEYS[2], ARGV[i], ARGV[1])
end
return 0

Redis 成功后，在建单的同一个本地事务里锁 MySQL：

UPDATE show_seat
SET status = 'LOCKED', lock_no = #{lockNo}, version = version + 1
WHERE show_id = #{showId} AND seat_id IN (#{seatIds}) AND status = 'AVAILABLE';
-- 影响行数必须等于座位数，否则回滚整个事务，再用 lockNo 撤销 Redis 置位
  • MySQL 是权威：Redis 只是把绝大多数冲突挡在数据库前面；Redis 主从切换丢了几个置位，最坏是多几个请求打到 MySQL，被条件更新挡住，不会一座两卖
  • 撤销 Redis 置位时先比对 owner 里的 lockNo 再清位，防止把别人刚锁上的座位清掉
  • 两个 key 用 {showId:area} 做 hash tag 保证同槽；一次选座限定在同一区域，跨区域选座拆成多次

3、并发抢同一个座位

同一个座位只有一个人能成功，其余人立即收到「座位已被选，请重新选择」并刷新座位图，不排队、不重试：替用户排队等一个可能不会释放的座位没有意义。热门场次开售瞬间大量冲突时，提示里直接推荐同区域的相邻空座。

4、锁座 TTL

  • 锁座后的支付时限通常比实物短（剧院、电影 5–10 分钟），show_seat 记录 lock_expire，订单的关单定时消息按同样时长发出
  • 过期不等于空闲：锁座过期后不能在锁座 SQL 里写 OR lock_expire < NOW() 抢过来，用户可能正在付款；释放只走关单流程（先关渠道交易、再关单、再释放座位），与第五节的预占释放完全一致
  • 释放时 UPDATE show_seat SET status = 'AVAILABLE', lock_no = NULL WHERE ... AND status = 'LOCKED' AND lock_no = ?，带上 lock_no 防止 ABA（座位已被别人重新锁上时，旧订单的重复关单消息不会误放）；事务提交后再清 Redis 置位

5、连座分配

「系统帮我选 4 个连座」时：

  1. 在目标票档的各区域里，按位图逐行找长度 ≥ 4 的连续空位段
  2. 候选按评分排序：离舞台中心的距离、行号、是否会在本行留下孤座（左右各剩 1 个空位很难再卖出去，扣分）
  3. 取最高分的候选执行锁座脚本；冲突说明位图已过时，排除这一段换下一个候选，最多尝试 3 次
  4. 找不到 4 连座时，退化为「同排不连续」或「前后两排各 2 个」，由用户确认后再锁

位图的逐行扫描在票务服务内存里完成，一个 5,000 座的区域扫描一遍是微秒级，不需要放进 Lua。

十、不选座：票档票池

  • 每个票档是一行 ticket_tier(show_id, tier, available, reserved, sold)，扣减与第三至六节的通用库存完全相同：预占、确认、释放、条件更新
  • 热门场次开票就是一次秒杀：Redis 预扣、排队、MQ 异步落库，见 秒杀；实名购票的「每证限购 N 张」放进同一个 Lua 脚本，按证件号哈希计数
  • 座位延后分配：开票结束后由分配任务按支付时间或抽签顺序，把同一订单的票连座分配到该票档的座位上，出票时用户才看到座位号。好处是抢票瞬间只扣数量，不会在几十万人的选座冲突上浪费容量
  • 无座位的票档（草坪、站票）只扣数量，入场按电子票核验

十一、退票与回流

场景处理
普通商品未发货退款预占记录 CONFIRMED → RETURNED，已售 −n、可售 +n
普通商品已发货退货退货入库，质检合格进可售，残次进锁定，各写一条流水
票务退票规则先行：开演前多久可退、手续费；SOLD → AVAILABLE 带 order_id 条件，提交后清 Redis 位

票务回流还有两个特殊考虑：

  • 集中释放：退票座位不立刻放回座位图，而是先进回流池，每天固定时间批量放出。逐张实时放回会被黄牛脚本持续盯守秒抢，集中释放能让普通用户有公平的机会
  • 候补优先：开启候补的场次，回流的票先按候补登记顺序分配给候补订单（候补订单已预付，分配成功直接出票），候补清空后才回到公开售卖

十二、库存同步到搜索与缓存

商品列表、搜索结果、商品详情页都要展示「有货 / 无货」，但这些读请求量是下单的成百上千倍，不能都打到库存服务：

  • 最终一致即可：库存表的 binlog 经 CDC 投到 MQ，消费端更新 ES 的 in_stock 字段和 Redis 展示库存；乱序问题用 updated_at 或版本号做外部版本控制，见 搜索
  • 只同步状态翻转：ES 只存「有货 / 无货 / 库存紧张」三档，库存从 100 变成 99 不需要写 ES，只有跨过阈值才更新，写入量下降几个数量级
  • 展示与下单分开：详情页的剩余数量来自缓存，可能滞后几秒；结算和下单一律以库存服务的条件更新为准，缓存说有货、下单时没货就提示用户
  • 座位图同理：位图本地缓存 1 秒，锁座以 Redis 脚本和 MySQL 条件更新为准

十三、容量估算

电商库存：沿用 订单 的口径，日下单 1,000 万笔、大促峰值 6,000 笔/秒，平均每单 2 个 SKU。

环节计算结果
预占峰值6,000 × 21.2 万行更新/秒，分到 16 个库每库 750/秒；热点 SKU 单独拆行或走预扣
流水条数每个 SKU 行一生约 3 次变化（预占、确认或释放、出库或回流）：10,000,000 × 2 × 3每天 6,000 万行
流水存储60,000,000 × 200 B = 1.2 × 10^10 B，索引按 1.5 倍约 16.8 GB/天；在线保留 90 天约 1.5 TB，更早的归档
预占记录10,000,000 × 2 × 150 B = 3 × 10^9 B约 2.8 GB/天，终态记录 30 天后归档

票务：一场 5 万座演唱会选座开售，100 万人在开售后 1 分钟内平均每人刷新座位图 5 次、提交锁座 3 次。

环节计算结果
座位图读1,000,000 × 5 ÷ 60约 8.3 万 QPS，全部由实例本地缓存承接
位图回源50 个实例 × 20 个区域 × 1 次/秒1,000 次/秒，每次约 625 B
锁座请求1,000,000 × 3 ÷ 605 万 QPS，按 20 个区域分散，每个区域约 2,500 QPS
落到 MySQL5 万座最多 5 万次成功锁座，加上 Redis 漏挡的少量冲突平均每秒不到 1,000 次条件更新，单分片可承受

可以看到票务的瓶颈在读座位图和锁座冲突，而不是数据库；这也是热门场次改用「票池开票 + 延后分配座位」的原因。峰值预估、冗余系数与压测见 容量评估与规划。

小结

  • 库存拆成可售、预占、锁定、已售四桶，实物 = 四桶之和；每次变化同一事务写流水，流水唯一约束兼做幂等
  • 多仓按 (sku, warehouse) 存，下单先选仓再预占；渠道配额本质是带渠道标记的冻结
  • 扣减时机默认「预占 + 确认」：付了钱一定有货，未付款占用受 TTL 限制；超时释放以关单事件为主，扫描兜底时先问订单
  • 防超卖首选 available >= n 条件更新，多 SKU 按固定顺序加锁避免死锁；单品瞬时高并发再加 Redis 预扣层，见 秒杀
  • 对账分流水、预占明细、订单、Redis 四层，修复同样写流水
  • 票务按场馆布局、场次、区域、座位四层建模；位图负责展示，Lua 全成或全败锁 Redis，MySQL 条件更新影响行数等于座位数才算锁座成功
  • 锁座过期不等于空闲，释放只走关单流程并带 lock_no；热门场次用票池开票、延后分配座位，退票集中释放、候补优先
