2026/10/9大约 19 分钟

即时通讯

前置阅读：心跳与连接管理、WebSocket、消息队列基础

IM 和 Feed 流 一样是「一个人写、多个人收」，但要求消息不丢、不乱、尽快送达，思路是消息先落库再算发送成功，推送只是加速，拉取才是兜底。本篇讲单聊、群聊、多端登录下的消息可靠性与有序性、离线与换设备补齐，以及大群扇出的存储设计。

一、需求与挑战

1、功能范围

功能要求
单聊在线秒级送达；对方离线时上线后补齐
群聊小群几十到几百人，大群可达数万到十万人
多端手机、PC、Web 同时在线，任何一端发的消息其他端都能看到
消息状态发送中 / 已发送 / 已读，单聊和小群显示已读回执
历史消息换设备后可以向上翻历史

2、挑战

挑战说明
长连接千万级同时在线，连接要保活，断了要能发现并重连
不丢发送方、服务端、接收方任何一段都可能失败，每段都要确认
不重超时重发、网关重推都会产生重复，要能识别
有序同一会话内所有端看到的顺序必须一致
扇出十万人大群发一条消息，写扩散就是十万次写

二、整体架构

层职责状态
接入层维持长连接、鉴权、心跳、协议编解码，上行转发给逻辑层，下行把消息写回连接持有连接，但不存业务数据，可以随时摘除
逻辑层消息去重、分配 seq、落库、ACK、推送、已读、群成员管理无状态，水平扩展
路由层记录「用户的哪台设备连在哪个网关」Redis，带 TTL
存储层消息、会话、同步位点MySQL 分片 + Redis + 冷存储
  • 网关只做连接，不碰业务：网关发布、扩容只影响连接（客户端重连即可），不影响消息逻辑
  • 网关与逻辑层之间用 RPC（gRPC / Dubbo）或每个网关一个专属 MQ Topic；逻辑层推送时按路由找到目标网关
  • 客户端到网关的协议可以用私有 TCP 协议（移动端省流量）或 WebSocket（Web 端），见 自定义私有协议 与 WebSocket

1、路由层

用户的每台设备在建连鉴权后写一条路由，结构为 Hash：im:route:{userId}，field 是 deviceId，value 是 gatewayId:connId。

  • 建连：HSET 写入并设置 TTL（如 15 分钟），同一平台重复登录时把旧连接踢下线
  • 续期：网关每 5 分钟为本机上的在线连接批量续期一次，不随每次心跳写 Redis
  • 断开：只能删除自己写的那条。用户可能已经重连到了另一个网关，旧网关后知后觉地删除就会把新路由删掉，所以要比较 value 再删：
-- KEYS[1] = im:route:{userId}   ARGV[1] = deviceId   ARGV[2] = 本连接写入的 gatewayId:connId
if redis.call('HGET', KEYS[1], ARGV[1]) == ARGV[2] then
    return redis.call('HDEL', KEYS[1], ARGV[1])
end
return 0
  • 网关宕机时它上面的路由来不及删除，靠 TTL 过期；在过期前推送会失败，按「推送失败」处理（见第三节），消息不会丢
  • EXPIRE 作用于整个 Hash，多设备时任何一台续期都会延长全部字段；需要按设备过期可以用 Redis 7.4 起支持的 HEXPIRE，或在 value 里带上最后续期时间由读取方判断

三、单聊消息流程

1、三个 ID

ID谁生成作用
clientMsgId发送端，每条消息一个 UUID发送方重发时的去重键
seq服务端，会话内单调递增会话内排序、断点续传、判断有没有缺消息
msgId（可选）服务端，全局唯一（如雪花 ID）撤回、引用、跨会话检索时唯一定位一条消息，见 分布式 ID 生成

全局 ID 只保证唯一和大致有序，不能保证同一会话里连续，所以排序和补洞都用会话内 seq。单聊的会话 ID 由两个用户 ID 计算得出（如 min:max），两人的消息落在同一个会话里，共享一个 seq 序列。

2、发送：落库之后才 ACK

public record SendCommand(long senderId, long convId, String clientMsgId, int type, String content) {}

public record SendAck(String clientMsgId, long seq, long serverTime) {}

@Service
public class MessageService {

    private final MessageMapper messageMapper;
    private final ConversationMapper conversationMapper;
    private final SeqAllocator seqAllocator;
    private final TransactionTemplate tx;
    private final PushDispatcher pushDispatcher;

    public MessageService(MessageMapper messageMapper, ConversationMapper conversationMapper,
                          SeqAllocator seqAllocator, TransactionTemplate tx, PushDispatcher pushDispatcher) {
        this.messageMapper = messageMapper;
        this.conversationMapper = conversationMapper;
        this.seqAllocator = seqAllocator;
        this.tx = tx;
        this.pushDispatcher = pushDispatcher;
    }

    public SendAck send(SendCommand cmd) {
        Message dup = messageMapper.findByClientMsgId(cmd.convId(), cmd.senderId(), cmd.clientMsgId());
        if (dup != null) {
            return ack(dup);                         // 重发：返回第一次分配的 seq，不再落库、不再推送
        }
        for (int attempt = 0; attempt < 2; attempt++) {
            Message m = Message.of(cmd, seqAllocator.next(cmd.convId()), System.currentTimeMillis());
            try {
                // 消息与会话在同一个分片（都按 conv_id 分片），是一个本地事务
                tx.executeWithoutResult(status -> {
                    messageMapper.insert(m);         // PK (conv_id, seq)，UNIQUE (conv_id, sender_id, client_msg_id)
                    conversationMapper.updateMaxSeq(m.convId(), m.seq());
                });
            } catch (DuplicateKeyException e) {
                Message existing = messageMapper.findByClientMsgId(cmd.convId(), cmd.senderId(), cmd.clientMsgId());
                if (existing != null) {
                    return ack(existing);            // 并发重发，另一条请求已经落库
                }
                seqAllocator.repair(cmd.convId());   // seq 撞了主键：Redis 计数回退过，修正后重试
                continue;
            }
            pushDispatcher.dispatch(m);              // 事务已提交才推送；推送失败由接收方拉取兜底
            return ack(m);
        }
        throw new IllegalStateException("send failed, client retries with the same clientMsgId");
    }

    private static SendAck ack(Message m) {
        return new SendAck(m.clientMsgId(), m.seq(), m.createdAt());
    }
}
  • 去重靠唯一约束：先查只是快速路径，两个并发的重发请求都可能查不到，最终由 UNIQUE (conv_id, sender_id, client_msg_id) 拦住。分片表的唯一索引必须带上分片键 conv_id，否则只在单个分片内唯一。去重方案的完整对比见 幂等设计
  • 落库成功才 ACK：ACK 意味着「服务端不会再丢这条消息」，所以必须在事务提交之后发；发送方收到 ACK 前一直显示「发送中」，超时后用同一个 clientMsgId 重发
  • 推送在提交之后：推送是尽力而为，不放在事务里；即使进程在提交后、推送前崩溃，消息已经在库里，接收方下次同步就能拉到

3、seq 分配

@Component
public class SeqAllocator {

    // key 不存在时返回 -1，由调用方从数据库初始化，避免 Redis 丢 key 后从 1 重新计数
    private static final RedisScript<Long> INCR_IF_EXISTS = RedisScript.of("""
            if redis.call('EXISTS', KEYS[1]) == 0 then
              return -1
            end
            return redis.call('INCR', KEYS[1])
            """, Long.class);

    // 只升不降：把计数推到 ARGV[1] 以上
    private static final RedisScript<Long> RAISE_TO = RedisScript.of("""
            local cur = tonumber(redis.call('GET', KEYS[1]) or '0')
            if cur < tonumber(ARGV[1]) then
              redis.call('SET', KEYS[1], ARGV[1])
            end
            return 1
            """, Long.class);

    private static final long SAFE_GAP = 1000;     // 跳过 Redis 回退前可能已经分配出去、正在落库的号

    private final StringRedisTemplate redis;
    private final MessageMapper messageMapper;     // maxSeq 必须读主库

    public SeqAllocator(StringRedisTemplate redis, MessageMapper messageMapper) {
        this.redis = redis;
        this.messageMapper = messageMapper;
    }

    public long next(long convId) {
        String key = "im:seq:" + convId;
        for (int i = 0; i < 2; i++) {
            Long seq = redis.execute(INCR_IF_EXISTS, List.of(key));
            if (seq != null && seq > 0) {
                return seq;
            }
            // 并发初始化只有一个 SET NX 生效
            redis.opsForValue().setIfAbsent(key, String.valueOf(messageMapper.maxSeq(convId) + SAFE_GAP));
        }
        throw new IllegalStateException("seq init failed: " + convId);
    }

    public void repair(long convId) {
        redis.execute(RAISE_TO, List.of("im:seq:" + convId),
                String.valueOf(messageMapper.maxSeq(convId) + SAFE_GAP));
    }
}
  • Redis 主从是异步复制，主节点宕机切换后，最后几次 INCR 可能丢失，新主节点会再发一次已经用过的 seq。数据库主键 (conv_id, seq) 才是最终防线：撞主键后把计数抬到库里最大值之上再重试
  • 跳号是允许的：seq 只要求单调递增，不要求连续。客户端发现缺号时去拉取，服务端返回该区间里实际存在的消息，客户端就把这段标记为已补齐
  • 缺口不能立刻判为跳号：seq 先分配、后落库，两条并发消息可能 102 先提交、101 还在事务里。如果客户端此时拉 (100, 102) 只拿到空结果就标记为已补齐，101 提交后这台设备就永远不会再拉它。所以拉取接口只把「后一条消息的 created_at 早于当前时间减去写入超时（如 10 秒）」的缺口确认为跳号，更新的缺口返回「未决」，客户端稍后重拉；本设备的 syncSeq 也只推进到第一个未决缺口之前
  • 会话非常多时，seq key 可以设长 TTL（如 30 天不活跃过期），过期后下次发送按上面的流程从库里重新初始化

4、推送、接收 ACK 与重传

  1. 消息服务按接收方 userId 查路由，得到每台在线设备所在的网关，逐个投递
  2. 网关把消息写到连接上，同时记入本连接的「待确认表」（key 为 convId:seq），启动超时计时
  3. 客户端收到后回 ACK（带 convId 与 seq），网关从待确认表里删除，并上报逻辑层更新这台设备的同步位点
  4. 超时未收到 ACK（如 5 秒）就重推，最多 2–3 次；仍失败就放弃推送，不需要额外存储，因为消息早已在库里，客户端重连后会按位点拉取

接收端可能收到同一条消息多次（重推、推送与拉取同时到达），按 (convId, seq) 去重即可，本地数据库对这两列建唯一索引，重复插入直接忽略。

四、消息顺序与可靠性

1、顺序

  • 只保证会话内有序：不同会话之间没有先后可言，也不需要全局排序
  • 以服务端 seq 为准：两个人几乎同时发言，谁先拿到 seq 谁在前，所有端看到的顺序一致；客户端本地发送时间只用来显示「发送中」的临时位置
  • 网络乱序由客户端整理：推送可能后发先至，客户端按 seq 插入；发现 seq 有缺口时（收到 105，本地最大是 102），先展示已有的，同时拉取 (102, 105) 区间；刚产生的缺口可能是还没提交的消息，按第三节的规则过了写入超时才认定为跳号

2、可靠性：三段确认

段确认方式失败时
发送方 → 服务端落库后回 ACK（带 seq）超时用同一个 clientMsgId 重发，服务端唯一约束去重
服务端 → 接收方接收方回 ACK网关重推有限次，之后靠拉取
兜底客户端上线、重连、发现缺号时按位点拉取拉取本身可以无限重试，读操作天然幂等

推送丢了不要紧，拉取一定能补上。这是 IM 可靠性的核心：不追求每次推送都成功，而是保证任何时候按位点拉取都能拿到完整数据。

五、离线消息与多端同步

1、同步位点

每台设备对每个会话记一个 syncSeq：本设备已经连续收到的最大 seq。位点存在两个地方：

  • 客户端本地：真正用来拉取的位点，每台设备各自一份
  • 服务端（im_device_sync 或 Redis）：根据接收 ACK 更新，用于计算「哪些会话有新消息」、清理离线推送

多端之所以不冲突，就是因为位点按设备记：手机看到 seq 300，PC 只看到 250，PC 上线后从 250 往后拉就行。自己在手机上发的消息也走同一个会话、同一套 seq，PC 拉取时自然能看到。

2、上线同步流程

  1. 客户端建连后上报「会话 → 本地位点」列表（只报最近活跃的会话，或者带上一次同步的时间戳）
  2. 服务端批量读取这些会话的 max_seq，返回有新消息的会话及未读数（max_seq - read_seq 是近似值，存在跳号时偏大，需要精确值时另维护计数）
  3. 客户端优先拉当前打开的会话和最近的几十个会话，其余在用户点开时再拉
  4. 每次拉取最多 200 条，从位点往后取；离线太久、缺口超过阈值时只拉最新一页，更早的消息在用户向上翻时按需加载
SELECT conv_id, seq, sender_id, msg_type, content, created_at
FROM im_message
WHERE conv_id = ? AND seq > ?          -- 本设备在该会话的位点
ORDER BY seq
LIMIT 200;

会话很多（上千个）的用户逐个比对位点代价较高，这正是写扩散要解决的问题，见第七节。

六、已读回执

已读也用位点表达，不按消息逐条记：用户读到某个会话的 seq N，就表示 N 及之前的消息都已读。

场景做法
单聊接收方上报 readSeq（只升不降，UPDATE ... SET read_seq = GREATEST(read_seq, ?)），服务端推给发送方，发送方把 seq ≤ readSeq 的消息标为已读
小群（如 ≤ 200 人）每个成员记一个 readSeq；查某条消息的已读人数时统计 read_seq >= 该消息 seq 的成员数，点开详情时才查明细
大群不提供逐条已读，只同步自己的已读位点（各端未读数一致）
  • 已读上报要合并：用户快速滑动时客户端每秒最多上报一次最大值
  • 已读回执推给发送方是尽力而为的通知，丢了也没关系，发送方下次打开会话时拉一次对方的 readSeq 即可
  • 多端之间同步自己的已读位点，用同样的方式：一端读了，其他端的未读数随之清零

七、群聊：读扩散还是写扩散

维度写扩散读扩散
写入消息体一份 + 每个成员一条收件箱索引只写群时间线一份
同步每个用户一个收件箱、一个位点，一次拉全部会话的新消息每个群一个位点，上线时逐群比对
存储索引量 = 消息数 × 群人数与群人数无关
适合单聊、小群大群、超大群

混合方案：单聊和小群（如 ≤ 500 人）写扩散，大群读扩散。客户端同步时先拉自己的收件箱（覆盖所有单聊和小群），再对加入的大群逐个比对位点；一个人加入的大群通常只有几个到几十个，比对成本可控。这与 Feed 流 对大 V 用拉模式是同一个思路。

1、写扩散的可靠性

收件箱按用户分片，和按会话分片的消息表不在同一个库，写收件箱不能和写消息放进一个事务，也不能在事务里直接发 MQ（事务回滚了消息已经发出）。做法：

  • 消息落库的同一个事务里写一条 outbox 记录，由中继投递到 MQ（Transactional Outbox），或者用 RocketMQ 事务消息，见 消息队列基础 的分布式事务一节与 RocketMQ
  • 扇出消费者分批读取群成员，为每个成员写收件箱索引 (user_id, inbox_seq, conv_id, msg_seq)；对 (user_id, conv_id, msg_seq) 建唯一约束，MQ 重复投递时撞唯一键直接跳过
  • 扇出之前推送已经可以开始：在线成员先收到推送，收件箱稍后补齐，两条路径通过 (convId, seq) 在客户端去重

2、大群的推送

十万人大群发一条消息，即使是读扩散，在线推送也是十万次。处理方式：

  • 合并通知：大群在 1 秒内的多条消息只推一次「有新消息」，客户端在会话打开时才拉取正文
  • 只推活跃成员：正在查看该群的成员推正文，其他成员只更新角标
  • 限制发言频率：大群按群维度限流（如每秒 10 条），超出排队或拒绝，见 限流与过载保护；热门大群的群信息、成员数等读取压力见 热点问题

八、心跳与断线重连

长连接的保活和重连细节在 Netty 模块有完整实现，这里只列 IM 场景下的取值和配合：

  • 心跳：客户端在写空闲时发 PING，服务端读空闲超过 3 个心跳周期就关闭连接；移动端心跳间隔要小于运营商 NAT 超时（常见 2–5 分钟），一般取 60 秒左右，并可根据网络类型动态调整。原理与 IdleStateHandler 用法见 心跳与连接管理
  • 重连：指数退避加随机抖动（1 秒、2 秒、4 秒……上限 30 秒左右），避免网关重启后所有客户端同一时刻涌入
  • 重连之后先同步：重连成功、鉴权完成后立即执行第五节的同步流程，补齐断线期间的消息，这一步比心跳本身更重要
  • 网关发布：滚动发布时先摘流量、再通知本机客户端主动重连到其他网关，最后关闭进程，见 优雅上下线
  • 鉴权：建连时校验 token，连接期间 token 到期由客户端刷新后重新认证，见 JWT
  • Web 端用 WebSocket，集群部署与 Nginx 配置见 WebSocket

九、存储选型

1、表结构

-- 消息表：按 conv_id 分片，同一会话的消息在同一个库，拉取是单分片范围扫描
CREATE TABLE im_message (
    conv_id       BIGINT       NOT NULL,
    seq           BIGINT       NOT NULL,
    sender_id     BIGINT       NOT NULL,
    client_msg_id VARCHAR(64)  NOT NULL,
    msg_type      TINYINT      NOT NULL,
    content       VARCHAR(4096) NOT NULL,     -- 图片、文件只存对象存储的地址
    created_at    BIGINT       NOT NULL,
    PRIMARY KEY (conv_id, seq),
    UNIQUE KEY uk_client (conv_id, sender_id, client_msg_id)
);

-- 会话表：与消息同分片，max_seq 和消息在一个本地事务里更新
CREATE TABLE im_conversation (
    conv_id  BIGINT  NOT NULL PRIMARY KEY,
    type     TINYINT NOT NULL,                -- 1 单聊 2 小群 3 大群
    max_seq  BIGINT  NOT NULL DEFAULT 0
);

-- 用户会话表：按 user_id 分片，存已读位点与会话列表排序信息
CREATE TABLE im_user_conv (
    user_id   BIGINT NOT NULL,
    conv_id   BIGINT NOT NULL,
    read_seq  BIGINT NOT NULL DEFAULT 0,
    PRIMARY KEY (user_id, conv_id)
);
  • 按会话分片：拉取、排序、seq 校验都在一个会话内，按 conv_id 分片后全部是单分片操作；按用户的查询（会话列表、已读）放在按 user_id 分片的表里。分片键选择与扩容迁移见 数据层扩展
  • im_conversation.max_seq 每条消息更新一次，大群会成为热点行；大群可以不更新这一列，改为读 Redis 里的 seq 计数作为最新值

2、冷热分离

聊天记录的访问集中在最近几天，越旧越少被翻到：

数据存储说明
最近 7 天MySQL + 客户端本地离线同步、向上翻页几乎都落在这里
7 天到 1 年MySQL 历史库或 HBaserowkey 为 conv_id + seq，同一会话连续存放，范围扫描高效
1 年以上对象存储（按会话、按月压缩归档）按需回捞，或只提供云端搜索
收件箱索引Redis / KV 存储，保留 7 天超过保留期的设备改为按会话位点同步

归档任务按 created_at 分批迁移、校验后删除，查询层根据 seq 或时间判断去哪一层读，做法见 数据冷热分离。

十、容量估算

假设 DAU 1 亿，人均每天发 40 条消息，峰值是均值的 3 倍；单条消息平均 400 B（正文与元数据 300 B + 索引约 100 B）。存储按 1 TB = 10^12 B 换算。

写入 QPS：

  • 每天消息数：100,000,000 × 40 = 4,000,000,000 条（40 亿）
  • 平均写 QPS：4,000,000,000 ÷ 86,400 ≈ 46,296，约 4.6 万
  • 峰值写 QPS：46,296 × 3 ≈ 138,889，约 13.9 万

投递量：70% 是单聊（1 个接收方），30% 是群聊，群平均 20 人（19 个接收方）：

  • 每条消息平均接收方：0.7 × 1 + 0.3 × 19 = 0.7 + 5.7 = 6.4
  • 峰值投递：138,889 × 6.4 ≈ 888,890 次/秒，约 89 万次/秒（在线推送与收件箱写入都是这个量级）

存储：

数据计算结果
消息每天4,000,000,000 × 400 B = 1.6 × 10^12 B1.6 TB/天
热数据 30 天（单副本）1.6 TB × 3048 TB
热数据 30 天（一主两从）48 TB × 3144 TB
全年冷数据（单副本）1.6 TB × 365584 TB，压缩到约三分之一后约 195 TB
收件箱索引每天40 亿 × 6.4 = 256 亿条 × 40 B = 1.024 × 10^12 B约 1 TB/天，保留 7 天约 7.2 TB

连接与实例：

  • 峰值同时在线按 DAU 的 30%：100,000,000 × 30% = 3,000 万条连接
  • 网关单机按 50 万连接估算：30,000,000 ÷ 500,000 = 60 台，按 1.5 倍冗余部署 90 台
  • 心跳间隔 60 秒：30,000,000 ÷ 60 = 50 万次/秒，平均每台网关 500,000 ÷ 90 ≈ 5,556 次/秒，在网关本地处理，不转发、不写 Redis
  • 路由续期每 5 分钟一次：30,000,000 ÷ 300 = 10 万 QPS 打到 Redis，按单分片 2 万 QPS 留余量需要 5 个以上分片
  • 消息库：峰值写 13.9 万 TPS，按单分片 5,000 TPS 估算：138,889 ÷ 5,000 ≈ 27.8，取 2 的幂 32 个分片

大群对比：一个 10 万人的群每秒 5 条消息，写扩散要写 5 × 100,000 = 50 万条收件箱索引/秒，一个群就吃掉整个集群一半以上的投递能力；读扩散只写 5 条，这就是大群必须用读扩散的原因。

单机连接数、单分片 TPS 都要以压测为准，上面只是估算方法，见 容量评估与规划。

小结

  • 架构分四层：网关只管长连接，逻辑层无状态，路由层记录设备所在网关，存储层按会话分片
  • 每条消息三个 ID：clientMsgId 去重，会话内 seq 排序和补洞，全局 msgId 用于撤回与引用
  • 发送：唯一约束去重、本地事务落库、提交后才 ACK 和推送；seq 由 Redis 分配，数据库主键是最终防线，撞键时把计数抬高后重试
  • 可靠性靠三段确认加拉取兜底：推送失败只重推有限次，客户端上线、重连、发现缺号时按位点拉取
  • 同步位点按设备记录，多端互不干扰；已读也用位点表达，只升不降
  • 单聊和小群写扩散（收件箱经 outbox 可靠扇出、唯一约束去重），大群读扩散并合并推送
  • 路由删除要校验归属，避免把用户重连到新网关后的路由删掉；断线重连后第一件事是同步
  • 消息去重的通用做法见 幂等设计。
