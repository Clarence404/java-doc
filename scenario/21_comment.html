评论系统

2026/10/14大约 24 分钟

评论系统

前置阅读：计数服务、排行榜和积分、两级缓存（L1 + L2）

评论挂在视频、文章、动态下面，读远多于写，难点在楼中楼结构、热门内容的读放大和内容审核。本篇讲两级楼中楼的数据模型、带审核的发评论链路、按时间与热度的分页和热评排序、首屏缓存与删除防刷，基线为 MySQL 8.4、Redis 8。

一、需求与挑战

1、功能范围

功能要求
发评论 / 回复对内容发一级评论，对评论发回复；回复要能看出「回复了谁」
列表一级评论按时间或热度排序，下滑翻页；每条一级评论下预览前几条回复，点「查看 N 条回复」展开
审核违规内容不能对外展示；审核未完成时作者自己能看到
删除 / 折叠作者删自己的评论、内容主人删自己帖子下的评论、审核下线；低质评论折叠而不是删除
计数评论总数、每条评论的回复数和点赞数
通知被回复、被 @ 的人收到提醒

2、挑战

挑战说明
结构回复可以一层套一层，无限嵌套难查难展示，要在模型上做取舍
读放大打开一次评论区要拿一级评论、回复预览、用户信息、点赞数、是否已赞，一屏几十个对象
热点爆款内容的评论区每秒几万次打开，全部落在同一个对象上
审核审核要准又不能让用户等太久，机审几毫秒、人审可能几十分钟
一致性删除、审核下线后，列表、计数、缓存、热评榜都要跟着变
刷评机器批量发广告、重复内容刷屏、刷赞把垃圾评论顶上热评

二、整体架构

组件职责
评论服务发评论、删评论、列表查询的入口；做频控、同步机审，写评论表和本地消息表
评论库MySQL 分库分表，按 obj_id 分片，同一内容的评论在同一张表
MQ 评论事件本地消息表投递的事件（发布、审核结果、删除），以 obj_id 为 key 保证同一内容有序
审核服务消费待审事件，跑文本 / 图片模型，可疑的进人审队列，结果回写评论状态
计数服务评论数、回复数、点赞数，由事件或 binlog 驱动，详见 计数服务
缓存Redis 存时间列表、热度 ZSet、评论内容；热点内容再加进程内缓存
通知中心消费发布事件，提醒被回复、被 @ 的人，详见 消息通知中心

写路径：评论服务同步完成「校验 → 机审 → 落库」，其余全部异步；读路径：先走缓存拼出一屏，缓存没有的部分回源分片库。下面按数据模型、写、读、排序、缓存、删除、防刷、通知的顺序展开。

三、数据模型

1、楼中楼：两级还是无限嵌套

方案存法查询适合
两级（root_id + parent_id）回复都挂在所属一级评论下，root_id 指向一级评论，parent_id 指向直接回复的那条一级评论按 root_id = 0 查；一个楼的全部回复按 root_id 一次查完视频、电商、资讯等绝大多数评论区
邻接表无限嵌套（只有 parent_id）每条只记直接父评论展开一棵子树要递归查，或用 WITH RECURSIVE层级很浅的讨论
路径枚举（path）存祖先路径，如 /101/205/208/子树用 path LIKE '/101/%' 前缀查论坛式盖楼、需要完整树形展示
闭包表另建 (祖先, 后代, 深度) 关系表子树、祖先都是一次查询树要频繁移动和统计，评论场景很少用

主流评论区都用两级结构：再深的回复在界面上也只展示成两级，第二级里用「回复 @B」说明回复对象。这样一个楼的全部回复用一个等值条件就能分页，不需要递归。

  • 发一级评论：root_id = 0、parent_id = 0
  • 回复一级评论：root_id = parent_id = 一级评论 ID
  • 回复楼中楼：root_id 继承被回复评论的 root_id，parent_id 为被回复评论的 ID，reply_to_uid 冗余被回复人，展示「回复 @某人」和发通知都不用再查一次

需要完整树形展示的讨论区（如技术论坛）才用路径枚举；path 用 VARCHAR，层级上限要控制（比如 10 层），否则路径过长，索引前缀也会失效。

2、表结构

两张表：评论主体表记录「这个内容的评论区」本身的属性，评论表记录每一条评论。

-- 评论主体：每个可评论的内容一行
CREATE TABLE comment_subject (
  obj_type    TINYINT  NOT NULL COMMENT '1 视频 2 动态 3 文章',
  obj_id      BIGINT   NOT NULL,
  owner_uid   BIGINT   NOT NULL COMMENT '内容作者，可删除本内容下的评论',
  state       TINYINT  NOT NULL DEFAULT 0 COMMENT '0 正常 1 关闭评论 2 仅粉丝可评 3 先审后发',
  top_cmt_id  BIGINT   NOT NULL DEFAULT 0 COMMENT '置顶评论',
  PRIMARY KEY (obj_type, obj_id)
);

-- 评论：按 obj_id 分库分表
CREATE TABLE comment (
  id            BIGINT        NOT NULL COMMENT '分布式 ID，趋势递增',
  obj_type      TINYINT       NOT NULL,
  obj_id        BIGINT        NOT NULL COMMENT '分片键',
  root_id       BIGINT        NOT NULL DEFAULT 0 COMMENT '0 表示一级评论',
  parent_id     BIGINT        NOT NULL DEFAULT 0 COMMENT '直接回复的评论',
  user_id       BIGINT        NOT NULL,
  reply_to_uid  BIGINT        NOT NULL DEFAULT 0 COMMENT '被回复人，冗余',
  content       VARCHAR(2000) NOT NULL,
  status        TINYINT       NOT NULL COMMENT '0 待审 1 已发布 2 仅自己可见 3 审核拒绝 4 已删除',
  folded        TINYINT       NOT NULL DEFAULT 0 COMMENT '1 已折叠',
  req_id        CHAR(32)      NOT NULL COMMENT '客户端请求 ID，防重复提交',
  create_time   DATETIME(3)   NOT NULL,
  update_time   DATETIME(3)   NOT NULL,
  PRIMARY KEY (id),
  KEY idx_list (obj_id, obj_type, root_id, id),
  UNIQUE KEY uk_req (obj_id, user_id, req_id)
);
  • idx_list 覆盖两类主查询：一级评论按时间（root_id = 0 ORDER BY id DESC）和楼中楼展开（root_id = ? ORDER BY id）；id 由 分布式 ID 生成、趋势递增，直接代替 create_time 排序，还能当游标
  • 点赞数、回复数不放在评论表：它们由计数服务维护，评论表只在被编辑、删除、审核时更新，行不会被点赞写热
  • uk_req 防重复提交：客户端每次发评论生成一个请求 ID，网络重试撞唯一键就返回已有评论；唯一键必须带分片键 obj_id，分表后唯一约束只在单表内有效
  • 正文很长或带富文本时可以把 content 拆到单独的内容表，列表扫描只读窄的索引表，按 ID 批量取正文；表设计规范见 MySQL 表设计
  • 楼层号不是必需字段；需要时用 Redis INCR 按内容发号，不要用主体表的一行做自增，热门内容下这一行会成为写热点

3、分片键：按 obj_id

评论区几乎所有查询都是「某个内容下的评论」，按 obj_id 分片后一次列表查询只访问一个分片，楼中楼、计数校准、删除整楼也都在单分片内完成。

查询按 obj_id 分片后
内容下的一级评论、楼中楼单分片，走 idx_list
一条评论详情（只有评论 ID）接口要求同时传 obj_id；只有 ID 的场景用基因法把 obj_id 的分片位嵌进评论 ID
「我发过的评论」跨所有分片，改走按 user_id 分片的异构索引表，由 CDC 同步
后台按时间、关键字检索同步到 ES 查

代价是热门内容的评论全部压在一个分片上。写入量其实不大（一个内容每秒几百条评论已经很罕见），压力主要在读，靠第八节的缓存解决，而不是把一个内容的评论拆到多个分片。分片方案与基因法见 分库分表。

四、发评论链路

1、先审后发还是先发后审

策略做法优点代价适合
先审后发写入后状态为「待审」，审核通过才对外可见违规内容不会被别人看到用户要等审核；人审排队时延迟很长敏感时期、新闻和政务类内容、主人开了「精选评论」
先发后审同步机审通过就发布，再异步复审，违规的下线体验好，评论立即可见违规内容有一段曝光窗口大多数评论区的默认策略
分级机审结果、用户信用、内容热度共同决定兼顾体验和风险规则复杂，要持续调大平台的实际做法

实际都是分级：同步机审明显违规的直接拒绝；结果可疑、新注册账号、热门内容下的评论进入待审；其余先发后审。被风控判定为刷子的账号可以给「仅自己可见」状态：作者看到的评论区和平时一样，其他人看不到，刷子不知道自己被拦，也就不会换号重试。

无论哪种策略，作者自己都应该能立即看到自己的评论（待审的加「审核中」标记），否则用户以为没发成功会反复提交。

2、同步机审与异步审核

阶段内容耗时结果
同步机审敏感词匹配（AC 自动机）、URL 与联系方式规则、黑名单、风控评分几毫秒拒绝 / 待审 / 放行
异步机审文本分类模型、图片和表情审核、上下文语义百毫秒到秒级通过 / 下线 / 转人审
人工审核模型拿不准的、被举报的分钟到小时最终结论
  • 敏感词先做归一化（全角转半角、繁简转换、去掉夹在中间的符号）再匹配，词库热更新时整体替换自动机引用，做法见 Trie 应用场景
  • 同步阶段只放本地计算和 Redis 查询，不同步调用外部的模型服务；模型服务慢或挂了，评论照样能发，只是退化成「全部先发后审」或「全部待审」，由配置开关决定
  • 审核结果以事件形式回写：UPDATE comment SET status = ? WHERE id = ? AND status = ?，带上期望的旧状态，晚到的旧审核结果不会覆盖新状态（比如用户已经删除了，审核通过的消息才到）

3、写入：评论与事件同一个事务

外部调用放在事务外，事务里只有两条 INSERT：

public long publish(CommentCmd cmd) {
    Subject s = subjectCache.get(cmd.objType(), cmd.objId());
    if (s == null || s.closed()) {
        throw new BizException("评论已关闭");
    }
    rateLimiter.check(cmd.userId(), cmd.objId());               // 频控与重复内容，见第十节
    AuditResult r = syncAuditor.check(cmd.userId(), cmd.content()); // 本地敏感词 + 风控评分
    if (r.reject()) {
        throw new BizException("内容不符合社区规范");
    }
    int status = r.status(s);                                   // 已发布 / 待审 / 仅自己可见
    Comment c = Comment.of(idGen.next(), cmd, status);
    try {
        return tx.execute(t -> {
            commentDao.insert(c);                               // uk_req 拦住重复提交
            outboxDao.insert(CommentEvent.created(c));          // 本地消息表，同库同事务
            return c.getId();
        });
    } catch (DuplicateKeyException e) {
        return commentDao.findByReq(cmd.objId(), cmd.userId(), cmd.reqId()).getId();
    }
}
  • 本地消息表和评论在同一个分库，事务提交后由投递任务发到 MQ，失败重试；也可以直接用 CDC 订阅评论表 binlog，效果相同，见 本地消息表
  • 下游（计数、缓存、热评、通知、审核）都按「状态从 A 变到 B」处理事件：只有「变为已发布」才加评论数、进列表缓存、发通知，「从已发布变为删除 / 拒绝」才减，其他变化不动计数
  • 事件里带评论 ID 和状态变化，消费方按评论 ID 幂等，重复投递不会重复计数

五、列表查询

1、按时间：游标分页

一级评论按时间倒序，用上一页最后一条的 ID 作游标：

-- 第一页
SELECT id, user_id, reply_to_uid, content, folded, create_time
FROM comment
WHERE obj_id = ? AND obj_type = ? AND root_id = 0 AND status = 1
ORDER BY id DESC
LIMIT 20;

-- 下一页：cursor 为上一页最后一条的 id
SELECT ... WHERE obj_id = ? AND obj_type = ? AND root_id = 0 AND status = 1 AND id < ?
ORDER BY id DESC
LIMIT 20;
  • 评论区头部不断有新评论插入，LIMIT offset, n 会出现重复和遗漏，而且越往后越慢；游标分页每页都是一次索引范围扫描，原理同 Feed 流的游标分页，接口约定见 API 设计规范
  • status = 1 不在索引里，但删除和待审的比例很低，回表后过滤的代价可以接受；如果某内容被大量删评，可以把 status 放进索引
  • 作者自己的待审、仅自己可见评论单独查一次（uk_req 的前缀 (obj_id, user_id) 正好可用），插到第一页顶部，不进公共缓存

2、楼中楼：预览与展开

一级评论列表里每条带前 3 条回复和回复总数。20 条一级评论的预览如果一条条查，就是 20 次查询，常见写法：

-- 一次取 20 个楼的前 3 条回复
SELECT * FROM (
  SELECT c.*, ROW_NUMBER() OVER (PARTITION BY root_id ORDER BY id) AS rn
  FROM comment c
  WHERE obj_id = ? AND obj_type = ? AND root_id IN (?, ?, ...) AND status = 1
) t
WHERE rn <= 3;

窗口函数写法简单，但它要读出这些楼的全部回复再编号；某个楼有上万条回复时这条 SQL 会很慢。热门内容改为：

  • 把每个楼的前 3 条回复 ID 作为「预览」缓存起来（cmt:preview:<rootId>），发布、删除回复时更新
  • 或者对 20 个楼各发一条 WHERE root_id = ? ORDER BY id LIMIT 3，用 UNION ALL 合并或并行执行，每条都是索引上的一小段

点「查看 N 条回复」后按 root_id 游标分页，正序（id > cursor ORDER BY id），方便顺着对话往下读。回复总数来自计数服务，不现场 COUNT(*)。

3、拼出一屏

一屏数据来自多个服务，接口层并行批量获取后组装：

数据来源批量方式
一级评论 ID 列表时间列表 / 热度 ZSet，未命中查分片库一次 ZRANGE
评论内容（一级 + 预览回复）评论内容缓存 cmt:c:<id>MGET，未命中的批量回源
用户昵称、头像用户服务一次批量接口
点赞数、回复数计数服务一次批量接口
当前用户是否已赞点赞关系只查当前用户，见 计数服务

列表缓存只存 ID，内容按 ID 单独缓存：同一条评论会出现在时间列表、热度列表、预览等多个地方，删除或修改一条评论时只需要删一个内容 key。

4、大 V 热门帖的读放大

一次打开评论区要读 1 个列表 + 80 条评论内容 + 80 个用户 + 一批计数。普通内容每秒被打开几次，问题不大；爆款内容每秒被打开几万次，就是几百万次 key 读取，全部落在同一个列表 key 和同一批内容 key 上，Redis 单分片扛不住。处理办法见第八节：热点内容的首屏结果整体放进进程内缓存，1～2 秒刷新一次。

六、热评排序

1、几种排序公式

公式计算特点
按点赞数score = likes先发的评论一直占着榜首，新评论永远上不去
点赞 + 时间衰减（Hacker News 式）score = (likes + 1) / (age_hours + 2)^1.8越旧分越低，新的好评论能上来；分数随时间变化，要定时重算
对数点赞 + 时间项（Reddit 式）score = log10(max(likes, 1)) + publish_ts / 45000发布越晚基础分越高，每 12.5 小时抵 10 倍点赞；分数只在点赞时变，不用定时重算
Wilson 置信区间下界见下用于有赞有踩：样本少时保守估计，10 赞 0 踩不会排在 900 赞 100 踩前面

Wilson 下界（n 为赞 + 踩，p 为赞的比例，z 取 1.96 对应 95% 置信度）：

lower = (p + z²/(2n) − z × sqrt(p(1−p)/n + z²/(4n²))) / (1 + z²/n)

只有点赞没有踩的评论区，可以把「点赞数 / 曝光数」当成 p 来算，曝光少的评论不会因为一两个赞就冲上去。

实际的热度分通常是组合：基础分用上面某个公式，再乘上调整因子，比如内容作者点过赞、作者回复过的加权，被举报、被折叠、疑似刷赞的降权。

2、热度 ZSet 的维护

每个评论较多的内容维护一个热度 ZSet cmt:hot:<objId>，member 为一级评论 ID，score 为热度分：

  • 点赞事件来自计数服务的 binlog 事件流，按评论聚合后每条评论每隔几秒最多重算一次，避免爆款评论每次被赞都写一次 ZSet
  • 用 Reddit 式这类「只在点赞时变化」的公式，ZSet 只在有事件时更新；用时间衰减公式则要定时任务对活跃内容整体重算
  • 只保留前 500～1000 条：ZADD 后 ZREMRANGEBYRANK cmt:hot:<objId> 0 -1001，排在后面的评论看热度榜的人极少，翻到底后接时间顺序即可
  • 评论很少的内容不建 ZSet，直接查库后在内存里排序

ZSet 的 Top N、分页命令与大 key 拆分见 排行榜和积分。

3、热度榜翻页

热度分一直在变，按名次翻页时第一页的评论可能掉到第二页，造成重复或遗漏：

  • 简单做法：按名次 offset 翻页，客户端按评论 ID 去重；热度变化慢，偶尔漏一两条可以接受
  • 严格做法：第一页时把前 200 个 ID 作为快照存到一个短 TTL 的 key（或直接下发给客户端），后续翻页在快照内取，快照翻完后接时间顺序

置顶评论不进 ZSet，从主体表的 top_cmt_id 读，固定拼在第一页最前面。

七、计数

评论区涉及三个计数：内容的评论总数、每个楼的回复数、每条评论的点赞数，都交给 计数服务：关系以评论表 / 点赞表为准，计数由事件或 binlog 异步算出，读走 Redis 和本地缓存，定期对账。评论场景只需注意：

  • 只数已发布的：计数事件按「变为已发布 +1、从已发布变为其他 -1」生成，待审、仅自己可见、审核拒绝都不计入，否则审核拒绝后数字对不上
  • 总数口径要定：评论总数是只数一级评论还是包括所有回复，产品上要统一；删除一级评论时它的回复是否一起扣减，取决于第九节的处理方式
  • 点赞关系去重和大 V 是否已赞的查法与普通点赞相同，不在评论服务里重复实现

八、缓存

1、缓存什么

key结构内容更新方式
cmt:time:<objId>ZSet最新 200 个一级评论 ID，score 为评论 ID 的时间部分发布事件 ZADD + 截断，删除事件 ZREM
cmt:hot:<objId>ZSet热度前 1000 的一级评论 ID第六节
cmt:preview:<rootId>List / ZSet每个楼的前 3 条回复 ID回复发布、删除时更新
cmt:c:<id>String / Hash单条评论内容按需加载，修改、删除时删 key
  • 时间列表只缓存头部：大部分人只看前两三页，翻得更深的直接查库，走索引的游标分页本来就快
  • 只给评论数超过阈值（如 50 条）或近期活跃的内容建列表缓存，冷内容的评论区直接查库，缓存空间集中给热内容
  • ZSet 的 score 是双精度浮点数，64 位雪花 ID 超过 2^53 会丢精度，不能直接当 score，取 ID 里的毫秒时间戳部分；member 仍然是完整 ID
  • 列表缓存未命中时只允许一个请求回源重建，其余等待结果，防止热门内容的缓存过期后几百个请求同时查库，做法见 热点问题

2、热点内容的多级缓存

层内容TTL作用
进程内（Caffeine）热点内容第一页的完整组装结果（不含「是否已赞」）1～2 秒把单个 key 的每秒几万次读取变成每个实例每秒一次
Redis上表中的列表与内容数小时到数天，读时续期主力缓存
MySQL 分片全量评论—回源
  • 哪些内容算热点：发布者粉丝数、近一分钟评论区打开次数超过阈值，由热点探测推给各实例，见 热点问题
  • 进程内缓存只存「所有人看到都一样」的部分，「我是否已赞」「我自己的待审评论」每次单独查，再合并到结果里
  • 新评论最多晚 1～2 秒出现在别人的首屏上，评论区可以接受；发评论的人自己由客户端把新评论插到本地列表顶部，不用等缓存刷新
  • 两级缓存的失效广播和一致性见 两级缓存（L1 + L2）、缓存一致性

九、删除与折叠

1、软删除

评论一律软删除（status = 4），不物理删：审核申诉、法律取证、对账都要用到原文。

情况展示
删除的是没有回复的一级评论列表里直接不出现
删除的是有回复的一级评论保留位置，显示「该评论已删除」，回复照常展示
删除的是楼中楼回复楼内不出现；其他回复里的「回复 @某人」照常显示
审核下线与删除相同，作者看到「因违规已被删除」

删除时的后续动作都走评论事件：计数减一（只有原状态是已发布才减）、从时间列表和热度 ZSet 中 ZREM、删内容 key 和预览 key。删除接口校验操作人：评论作者本人、内容作者（comment_subject.owner_uid）、管理员三种，权限不同、审计日志里分别记录。

2、一级评论被删，回复怎么办

做法说明适合
保留回复一级评论显示占位，回复照常可见用户自己删的，回复是别人的内容，不应连带删除
级联隐藏回复全部改为隐藏状态审核下线违规楼，回复往往在附和违规内容

级联隐藏要分批：UPDATE comment SET status = 4 WHERE obj_id = ? AND root_id = ? AND status = 1 AND id > ? ORDER BY id LIMIT 500，循环到影响行数为 0，避免一个上万回复的楼在一个大事务里锁住大量行。回复数、评论总数按实际改动的行数扣减；也可以直接让计数服务对该楼重新对账。

整篇内容被删除时不逐条删评论，把 comment_subject.state 改成关闭，评论区整体不可见；评论数据按冷数据策略归档，见 冷热数据分离。

3、折叠

低质量、被多人举报、疑似引流但未达到删除标准的评论，设 folded = 1：不进热度榜和第一页，统一放进「已折叠的评论」入口，点开才看到。折叠比删除温和，误判时用户不容易感知为「被删评」，申诉量也少。

十、防刷与风控

手段做法
频控同一用户每分钟、每小时发评论条数上限；同一用户在同一内容下的条数上限；新账号更严。Redis 滑动窗口实现，见 限流
重复内容归一化后的正文取哈希，用户维度放进短 TTL 的 Set，同一人短时间重复发相同内容直接拒绝；跨账号相同内容（广告矩阵）用 SimHash 近似去重，命中后送审
账号与设备未绑手机、刚注册、设备指纹异常的账号，评论默认待审或仅自己可见
内容规则链接、联系方式、二维码图片默认待审
刷热评热度计算剔除异常点赞（同 IP、同设备集中、短时间暴涨），或把这类点赞的权重降为 0
返回信息被拦截时返回笼统的提示，不告诉对方命中了哪条规则；对刷子用「仅自己可见」比直接报错更有效

频控检查放在机审之前，最便宜的检查先做；风控评分依赖的特征（账号等级、历史违规次数）提前算好放在 Redis，同步阶段只读不算。

十一、通知被回复的人

评论发布（状态变为已发布）后，通知中心消费同一个评论事件，决定通知谁：

场景通知对象
一级评论内容作者
回复reply_to_uid（被回复的人）
正文中 @ 了某人被 @ 的用户，发布时解析并校验 @ 的用户存在
  • 审核通过后再通知：待审评论不发通知，否则被回复的人点进去看不到内容
  • 不通知自己：回复自己、在自己的内容下评论不发
  • 尊重屏蔽关系：被拉黑的用户的回复不通知
  • 聚合：热门内容的作者一分钟收到几千条评论，逐条推送没有意义，由通知中心聚合成「某某等 2,000 人评论了你的视频」

通知的存储、未读数、聚合与推送通道见 消息通知中心。

十二、容量估算

假设 DAU 1 亿，人均每天发 0.5 条评论、打开 20 次评论区；一屏 20 条一级评论 + 每条 3 条回复预览；峰值按发评论 5 倍、浏览 3 倍；1 TB = 10^12 B。

项计算结果
发评论50,000,000 ÷ 86,400 ≈ 579 条/秒，峰值 × 5约 2,900 条/秒，64 个分库每库约 45 条/秒
打开评论区2,000,000,000 ÷ 86,400 ≈ 23,148 次/秒，峰值 × 3约 6.9 万次/秒
评论内容读取69,444 × 80 条约 556 万 key/秒，MGET 批量后每屏 1～2 次调用
单个爆款内容峰值 5 万次/秒打开同一评论区进程内缓存 1 秒刷新，200 个实例只回源约 200 次/秒

MySQL 存储：每条评论正文平均 300 B，加其他字段约 500 B，算上二级索引按 750 B 估算：50,000,000 × 750 B = 3.75 × 10^10 B ≈ 37.5 GB/天，约 13.7 TB/年。按 64 库 × 16 表 = 1,024 张表，一年 182.5 亿行，每张表约 1,780 万行，每个库约 214 GB；两三年后按创建时间归档老评论。

Redis：活跃内容 100 万个 × 时间列表 200 个 ID × 约 70 B ≈ 14 GB；热门评论内容 1 亿条 × 约 600 B ≈ 60 GB；热度 ZSet 只给评论数超过阈值的内容建，量级与时间列表相当。合计百 GB 级，按单分片 25 GB 需要 6～8 个分片，读取 QPS 决定实际要更多分片。单分片能力以压测为准，估算方法见 容量评估与规划。

小结

  • 评论用两级楼中楼：root_id 指向一级评论、parent_id 指向直接回复，reply_to_uid 冗余被回复人；一个楼的回复按 root_id 一次分页，不递归；需要完整树形才用路径枚举
  • 按 obj_id 分片，内容下的查询都在单分片；按用户查走异构索引表，后台检索走 ES；热门内容的压力靠缓存而不是拆分片
  • 发评论分级审核：同步只做本地敏感词和风控，明显违规拒绝、可疑待审、其余先发后审；评论和事件在同一本地事务，下游按状态变化处理
  • 列表用 ID 游标分页；楼中楼预览不要用窗口函数扫整楼，缓存前 3 条或每楼 LIMIT 3
  • 热评用「对数点赞 + 时间项」或时间衰减、有赞有踩时用 Wilson 下界，热度 ZSet 只保留头部；翻页按快照或客户端去重
  • 列表缓存存 ID、内容按 ID 缓存；热点内容首屏放进程内缓存 1～2 秒，「是否已赞」和自己的待审评论单独查
  • 软删除，一级评论有回复时留占位；审核下线可分批级联隐藏；计数、缓存、热评榜都由同一个评论事件驱动
